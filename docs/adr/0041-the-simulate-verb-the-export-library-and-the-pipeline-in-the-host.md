# 0041 — The `simulate` verb: the export library, the folder writer and the pipeline in the host

- **Status:** Accepted (owner, 2026-10-18: "yes to all recommendations" on [P3-04b1](../specs/P3-04b1-the-export-library-files-labels-and-folder-writer.md) and [P3-04b2](../specs/P3-04b2-the-simulate-verb.md), the four-slice plan and the recommended answers to their open questions; the decisions the specs took on research — D1 to D9 of P3-04b2 and E1 to E8 of P3-04b1 — are the owner's to revert). The card rules of P3-04c ([spec](../specs/P3-04c-trade-cards-selection-chart-and-static-html.md), Approved the same day on "yes to all recommendations") are added below as Amendment 1 (2026-10-19). Builds on [ADR 0037](0037-simulation-conventions-and-the-two-stage-seam.md) (the record and its key), [ADR 0038](0038-fill-realism-the-entry-limit-gaps-slippage-ticks-and-the-order-inside-a-minute.md) (item 6, the tick and its unit) and [ADR 0039](0039-an-engine-module-is-reached-from-an-adapter-in-infrastructure-never-from-application.md) (an engine module is reached through a port); no earlier decision is superseded.
- **Date:** 2026-10-19 (built the same day; the library and the writer of P3-04b1 were built on 2026-10-18)
- **Relation to other ADRs:** [ADR 0006](0006-owner-auth-sessions.md) (`owner-reset`) is the precedent for a step that runs in the API image from the command line.

## In short
- **The files of a run are rendered by a pure library and written by the host.** `XDrishti.SimExport` references the Domain only and turns a finished `SimulationRun` into the bytes of `trades.csv`, `open_at_end.csv`, `run.json`, `README.txt` and `manifest.json`, writing to an `IBufferWriter<byte>` that the host owns; the host's `ExportFolderWriter` (in `XDrishti.Api`, internal) puts them under `data/exports/sim/<run-id>/` atomically. Only `XDrishti.Api` references the library.
- **The pipeline is in the host, not in an Application handler — a deliberate exception.** ADR 0039 forbids Application from referencing `XDrishti.SimExport` (a renderer is not a port) and a handler cannot touch the file system, so the order *parse, check the configuration, resolve the universe, gate the tick unit, run the handler, label, render and write, print* is `SimulateCommand` in `XDrishti.Api/Simulate`, on the precedent of `OwnerBootstrap` (a host step that calls handlers). The command holds the order only and no decision that belongs to the Domain (the gate, the labels) or to the library. **Consequence:** the Lab of P5 will call the same handlers and the same library but must re-order the pipeline itself; nothing here is a service it can reuse.
- **The verb is `simulate`, chosen by the first argument alone.** `VerbDispatch.Of(args)` selects it only when `args[0]` is `simulate` and is tested before `--healthcheck`, `migrate` and `owner-reset`, which match anywhere in the arguments and are left as they were, so that `simulate --symbols migrate` or a stray flag never selects another step. It runs in a generic host (`SimulateHost`) with the handlers and the ports, **no `AddApi()`, no vault key, no command-line arguments bound to configuration** (so `--key value` pairs of the verb never become settings), the container validated at build (`ValidateOnBuild`, `ValidateScopes`), built and never started. Logs go to stderr, so stdout holds the banner and the summary only.
- **Exit codes** are part of the contract: 0 done (the files are written, or the identical export was already there and verified), 1 refused with nothing written, 2 the command line or the configuration is wrong, 3 an unexpected failure, 130 cancelled with Ctrl-C (the conventional code).

## Decisions
1. **Where the code lives.** Pure rendering in `XDrishti.SimExport` (CSV, JSON, manifest, banner and readme; one spelling table for every enum, so both writers agree and a member added later fails a test instead of being written as a default); the labels (`RunLabels`, `RunLabelSet`) and the net for the tick unit (`TickUnitCheck`, `TickProbe`) in `XDrishti.Domain.Research`; the file system only in `ExportFolderWriter` and `HashingFileSink`. A library that takes an `IBufferWriter<byte>` lets the host stream to a file and hash as it writes, so memory stays flat for files of tens of megabytes; one that returned `byte[]` or `string` would hold a copy of up to 140 MB. The alternative of internal renderers in `XDrishti.Api` is rejected: presentation code in a host the rules call thin, and its tests inside the Testcontainers project.
2. **The built-in registry is a table.** `BuiltInStrategies` reads a table of entries (id, description, allowed timeframes, default timeframe, parameters with defaults, the builder); `Catalog` gives them as `BuiltInStrategyInfo` values and the engine port gains `BuiltIns`. A later strategy (P3-05, P3-06) is one row; the verb, the script and the export do not change. When stored strategies exist (P3-02d) the port changes (ADR 0039, decision 2) and this table is the seed list. See Amendment 5 of ADR 0037.
3. **The universe is resolved strictly, through the queries that exist.** `--symbols` goes through `ResolveInstrumentsQuery` (a ticker, a canonical symbol or the ISIN of a share or ETF, compared ignoring case); nothing is guessed, any unmatched entry refuses the run and **every** unmatched entry is listed with its reason. `--basket` takes a name (compared ignoring case with the active manual baskets) or an id (a portfolio, archived or unknown basket is refused by the handler as `simulation.basket_not_found`). The run order is the order given; a retired instrument that matches is kept and marked in the summary.
4. **The tick unit is checked before any bar is read.** After the universe is resolved the verb knows every instrument's stored tick and type without reading a bar (`InstrumentDetail` or the basket's `InstrumentSummary`) and calls `TickUnitCheck.Suspect`. **The threshold is 0.01 rupee for a share or an ETF** — the smallest tick the NSE has for them — so a master table that held rupees (a stored `0.05` would convert to 0.0005) is exit 1 before the first read, naming up to three instruments with the stored and the converted value. It is a net, not the guard: the guard is the read of the real table (ADR 0038, item 6). An index, a future, an unknown type, a missing tick (the flagged fallback) and a tick above one rupee (skipped later as `tick_size_invalid`) are not suspects.
5. **The export key and the overwrite policy.** The run key does not cover the basket, so the **export key** (format, run key, basket id, the hash of every file, the extra lines) says whether two exports are the same: two baskets with the same members have one run key and one folder name and different export keys, and the second is refused without `--force`. The same export again is `unchanged` after every file on disk is hashed; a different or modified one is refused unless `--force`, when the old folder is renamed to `<run-id>.previous` — **one previous copy, never deleted by the verb**, because a copy is up to a few hundred megabytes, unbounded growth is a disk problem and deleting the owner's earlier export is not the verb's call. A folder with no valid manifest is never replaced; a symbolic link is never written through; everything is written into a staging folder and renamed in one move, and a killed process's `.staging-*` folder is reported and left for the owner. Folders are 0700 and files 0600 at creation.
6. **`--fills no-slippage` is the same limit with no slippage and no tick rounding of fills** (`FillBasis.Exact` means both), for the hand recomputation of P3-09. Its label says so (`fills: modelled, no slippage, no tick rounding of fills`) and "fills modelled" is never dropped. No other fill number is a flag.
7. **No file and no console line prints a performance statistic.** The labels (`exploration: signal-level mechanics on past data, not evidence of an edge`, the fills, the entry limit, costs none, portfolio limits not simulated, in-sample, the universe and its survivorship, the data line, the engine not yet verified, the tick, the opening bar) are the same text on the console, in `run.json` and in `README.txt`. Counts per category are allowed; ratios, sums and means of R and percentages are not. A scan on a fixed list of whole words (`win`, `loss`, `hit`, `expectancy`, `profit`, `drawdown`, `average`, `mean`, `sum`, `total`, `percent`, `rate`, `ratio` and their forms) and on a digit followed by `%` or ` R` keeps the console text, in a success, a refusal and a failure, free of them; it has a sentinel that can fail.
8. **Logging and secrets.** Five lines with event ids 4405 to 4409 (started, refused, written, unchanged, failed), carrying a strategy id, a count, a code or the run id and no path, price, bar or strategy text. The verb's own code reads no secret: the only one in the process is `Database__Password`, read by the infrastructure. The script `scripts/simulate.sh` reads that one Keychain item (`xdrishti/db/app`), never the vault key or an owner secret, and never echoes it.
9. **Cancellation.** Ctrl-C is turned into a cancellation of the token (the process must not die before the writer has removed its staging folder). A cancellation before the final rename removes the staging folder and exits 130; one that comes after it leaves the complete export and says so.

## Consequences
- **No API, no table, no migration.** A verb is not an endpoint. `backend/contracts` is untouched.
- **The verb runs on the host, not in a container.** `scripts/simulate.sh` runs it with `dotnet run` against the developer database port; there is no `xd-simulate` service. The Lab (P5) and the scanner (P7) are where a screen or a schedule reaches the same handlers.
- **Hand-overs.** P3-03c adds the cost label and the cost flags (`--gross` or `--costs`, `--capital`, `--profile`, `--max-cost-r`) as rows of the parser table and flattens `Costing` into columns; P3-04c adds the cards as entries and extra lines of the manifest and passes `xd-sim-export-2`. Neither modifies a type here. P3-04c did so on 2026-10-19 (Amendment 1).
- **Cost of the exception.** The pipeline has no unit of reuse; the price is that the Lab repeats its order. If the Lab needs the pipeline as a service, the library stays and the order moves into an Application handler behind a port that writes the folder, which is a new ADR.

## Amendment 1 (2026-10-19, P3-04c): the trade cards
Built as specified in [P3-04c](../specs/P3-04c-trade-cards-selection-chart-and-static-html.md); nothing of the types of P3-04b1 was changed (the b1 extension test passes unchanged). The decisions that are rules of the system:
1. **Which trades get a card.** `CardSelection.Choose(run, cap)` is pure and works on `run.Trades` only. The strata (exit reason × side) are **derived from the enums**, not listed (`EndOfData` excluded; a value outside the set goes to one last stratum `other` and is never dropped). Inside a stratum the trades are ordered by `SeededRank` (the lower-case hex SHA-256 of `<run key>|<trade key>`; no random source, independent of input order); the seed is the run key and there is no `--seed`. If all trades fit the cap all get a card, otherwise round *r* gives the *r*-th trade of each stratum in a fixed order until the cap is reached, so the cap is spread equally over the strata that exist: a rare outcome is shown as often as a common one. This is not a picture of how often each outcome happens, and **the sizes of the strata are never printed** (the manifest lists the chosen keys with their stratum name only). `SeededRank` is the one seeded-order primitive: the stratified sampler of P3-09 uses it.
2. **The second read and its guard.** The record keeps no bars, so `BuildTradeCardsQuery(Run, TradeKeys)` (the extension point of P3-09) reads again, one at a time and in the run's universe order, only the instruments that have a chosen trade, with the bounds of the run (`SimulationBounds`, shared with `RunSimulationHandler`); the basket is never resolved again. For each instrument it checks that the row exists, that `BarStreamHash` equals the run's, that the applied actions that change the bars equal the recorded adjustments (ex-date, kind, numerator, denominator) and that the tick equals the recorded one; any difference is `simulation.cards_stale` (a conflict whose field names the instrument and the first difference), the verb exits 1 and **nothing is written** (the second read comes before the first byte of the export). It does not recompute the trade (P3-04d adds that and `simulation.cards_mismatch`). The day bars are adjusted by the replay's own rule (`AdjustmentFactors.FactorAt`, `Price`, `Volume`), re-stated in Application because `ReplayBars` is internal to the simulation library (ADR 0039); a test fixes the two together. Cost: one more read per instrument with a card; the default `--cards 200` on a wide universe roughly doubles the read time, and the owner passes `--cards 5` for the early look.
3. **A card is inert, escaped and deterministic.** No script, no `on…` attribute, no link, image, frame or import; one inline stylesheet with no `url(`; a Content-Security-Policy meta (`default-src 'none'; style-src 'unsafe-inline'`) and a no-referrer meta; the only `href` of the pages is the index's, and its value is a name from `CardNames`. Every dynamic string goes through `Html.Text` / `Html.Attr`, which remove every character of Unicode category Control or Format (so a bidi control such as U+202E cannot reorder text, and a line feed cannot add a line: preformatted blocks escape line by line) and unpaired surrogates, then escape `& < > " '`. The library has its own encoder and not `WebUtility`, because `System.Net` is a forbidden namespace of the pure library and `WebUtility` writes every character from U+00A0 as an entity. No clock, no machine path, no culture-dependent text: equal runs give identical bytes, and a card is at most 150 KB (a full day is about 52 KB).
4. **No statistic in a card or the index.** The text passes the whole-word scan of decision 7, the digit-before-`R` pattern included: R is written after a word (`exact result R +2.000`), never after a number, so the title is `NSE:RELIANCE BUY 2025-03-04, target, exact result R +2.000`. A card prints the numbers of its own trade only; the index shows each card's own result and the count of cards and trades, never a count by exit reason or side.
5. **The folder.** `--cards <0..500>` (default 200; 0 writes no cards and no index). Files: `index.html` and `cards/<nnnn>-<ticker>-<side>-<date>-<exit>.html` (`nnnn` is the place in the run's trade order with at least 4 digits; the ticker is cleaned to `A-Za-z0-9._-` and cut to 24; at most 80 characters). The manifest gains the extra lines `cards.cap=`, `cards.trades=` and one `cards.selected=<trade key>|<stratum>` per card, and **the format string is `xd-sim-export-2` for every export of the verb, with or without cards**; the export key therefore covers the cap, the chosen keys and the hash of every card, so a different `--cards` is a different export (exit 1 unless `--force`) and a hand-edited card is never `unchanged`. Event ids 4410 (cards written: count, bytes) and 4411 (cards stale: symbol, first difference) join 4405 to 4409.
6. **Coupling to the interim definition text.** The rule view reads `StrategyRecord.DefinitionJson`, the interim canonical text of P3-04 until P3-02c defines the real one. A change of that text breaks the golden of the rule view on purpose, and the view then follows the new text; a definition that does not parse, or has no block for the side, is printed raw (escaped) with its SHA-256 and the card says so.
7. **What is not here.** The conditions at the decision bar (P3-04d: `ISimulationEngine.Explain`; a card prints one line saying so), a card for an `OpenAtEnd` trade, `--trade-keys`, `--seed`, a script in a card.

Measured on the 20 invented instruments of the explicit benchmark (two years, 11,749 trades, `--cards 200`): the selection 0.03 s, the second read 2.3 s (about 0.12 s per instrument), rendering 0.18 s, 10.5 MB of cards (the largest 52.9 KB) and a 53 KB index.

## Amendment 2 (2026-10-19, P3-05): declared parameter ranges in the registry
Built as specified in [P3-05](../specs/P3-05-vwap-pullback-the-second-built-in-strategy.md) (the second built-in strategy, `VWAP_PULLBACK`, is one more row of the table of decision 2 and is described in [doc 07](../design/07-strategies.md) §3, not here). What the compile does not judge, the registry does: a free number used in arithmetic (`pull_atr` in `low[1] <= vwap[1] + pull_atr * atr(14)`) is judged by nothing downstream, and a negative one would compile into a nonsense rule. The rules:
1. **The range is data on the row.** `BuiltInParameterInfo(Name, Default, Note)` gains optional trailing members `double? Min = null`, `double? Max = null` and `bool MinExclusive = false` (the maximum is inclusive; null is no bound; existing positional uses compile unchanged). `HasRange`, `Contains(value)` and `RangeText()` (`0 < x <= 3`; one side when one bound is declared) live on the record, so the listing and the refusal print the same text. Only `pull_atr` declares one in this slice: `0 < x <= 3`. ORB's two parameters declare none and `rr` is judged by the exit table of the compile (`0 < rr <= 10`), so their messages and the listing text of ORB are unchanged.
2. **Where and in which order.** `BuiltInStrategies.Build` checks a given value after the unknown-name check (an unknown name keeps its refusal alone) and returns one located problem per violation through the existing `BuiltInBuild.Problems`: path `parameters.<name>`, code `simulation.parameter_out_of_range`, declared once in `SimulationErrors` beside `UnknownParameterCode`, the message naming the range. **A non-finite value (NaN, an infinity) is skipped by the range check**: it is neither in nor out of a range, so it still reaches `StrategyPreparation.Prepare`, which keeps throwing its `ArgumentException`; the order is finite check, then range, then compile.
3. **The listing.** `simulate --list-strategies` prints a declared range after the default, `  --param pull_atr=<number>  default 0.5, range 0 < x <= 3: <note>`, and nothing for a parameter without one, so ORB's lines are byte-identical to before.
4. **No new `Replay` type, no engine change.** The engine stays `sim-5`, the run-record schema 5 and `SimTrade` schema 4; the three message strings of `Simulator.cs` that said the other stop kinds "come with P3-05" now say only that the kind is not run yet (codes, paths and behaviour unchanged). Tested by `VwapPullbackTests` (the range, NaN, infinities, ORB unchanged), `BuiltInCatalogTests` and the listing test of `SimulateCommandTests`.

## Amendment 3 (2026-10-19, P3-06): `--timeframe` accepts every derived timeframe
Built as specified in [P3-06](../specs/P3-06-base-breakout-the-third-built-in-strategy.md) (the third built-in strategy, `BASE_BREAKOUT`, is one more row of the table of decision 2 and is described in [doc 07](../design/07-strategies.md) §3, not here). A swing strategy is evaluated on `1D`, and the flag refused it as "not intraday". The rules:
1. **The parser is a syntax check.** `SimulateOptions.ReadTimeframe` accepts any code of `Timeframes.Aggregated` (`5m`, `10m`, `15m`, `30m`, `1h`, `1D`, `1W`, `1M`); `1m` and anything else stay a usage error (exit 2) with the text `'--timeframe' must be a derived timeframe (5m, 10m, 15m, 30m, 1h, 1D, 1W or 1M), '<value>' is not`. The usage line says `[--timeframe <5m|10m|15m|30m|1h|1D>]` (1W and 1M parse and are refused by the scanner, so they are not advertised). When the flag is absent the timeframe is the registry's `DefaultTimeframe`, as before.
2. **The compile decides what a strategy may run on.** A code the strategy does not declare is refused by the model as `strategy.model.timeframe_not_declared` (a located problem, exit 1, nothing read or written); `1W` and `1M` are refused by the simulator as `simulation.scanner_timeframe_unsupported` (the frame closes a 1D bar at the step of the 15:29 minute, a weekly or monthly bar is not evaluated, ADR 0043).
3. **Tests.** The row of `SimulateOptionsTests` that pinned `--timeframe 1D` as an error is changed on purpose to `1m` (the exact text) and to valid rows for `1D`, `15m`, `1W` and `1M`; `SimulateCommandTests` pins that `BASE_BREAKOUT` builds a request on `1D` with and without the flag; `SimulateDatabaseTests` pins the two refusals of rule 2 against the real handler.
4. **No engine change.** The engine stays `sim-5`, the run-record schema 5 and `SimTrade` schema 4.
5. **A defect found on the way.** The `key` column of `trades.csv` was composed from the trade date (the fill date) while `SimTrade.Key` has followed the decision date since ADR 0043 D6; for a swing trade filled the day after its decision the two differed. The column now writes the decision date, as `SimTrade.Key` does (a failing test first: `TradesCsvTests`); the intraday rows are unchanged because the two dates agree.

## Amendment 4 (2026-10-19, P3-09): the shared pipeline and a further verb
Built as specified in [P3-09](../specs/P3-09-verification-pack-and-the-20-trade-check.md) (the decisions of the pack itself are [ADR 0046](0046-the-verification-pack-and-the-20-trade-check.md)). Decision 1 (a verb is a host step that calls handlers, the order lives in the host) stands; the verbs are now two, and what they share is one place. The rules:
1. **`SimulatePipeline` (internal, `XDrishti.Api/Simulate`)** holds what both verbs share: resolving the universe once and applying the tick gate (with the refusal codes `simulate.universe` and `simulate.tick_unit`), building the request from a strategy id, parameters, timeframe, window, universe, fill rules and cost choice, running `RunSimulationQuery`, the second read through `BuildTradeCardsQuery`, and the console helpers (usage, refusal, the lines of a refused run, the stale log). It was extracted from `SimulateCommand` with **no change of behaviour**: the tests of P3-04b2, P3-04c, P3-03f and P3-10 pass unchanged and are the test of the extraction. The order of the steps and the files of a folder (`Files`, `ExtraLines`, `Manifest`) stay with each verb.
2. **A further verb, `verify-pack`,** is chosen by the first argument alone, like `simulate` and `cost-sheet`, before the older rules (`Verb.VerifyPack`, `VerbDispatch`, a branch in `Program.cs`); it runs on `SimulateHost` as it is and through the same process entry (`SimulateProgram`, with a switch for the verb). The same exit codes 0, 1, 2, 3 and 130.
3. **The parser is shared too.** `SimulateOptions.Tokenize` (the reading of `--flag value` and `--flag=value`, repeats, unknown flags and missing values) and the readers of symbols, basket, dates and the cost choice are `internal`, and `VerifyPackOptions` calls them: one set of usage errors. `UniverseResolver.ResolveAsync` gained an overload that takes the basket and the symbols, so a verb without a `SimulateOptions` can use it.
4. **`ExportFolderWriter.WriteAsync` gained one optional trailing parameter, the folder name below the root** (default `sim`, 1 to 20 lower-case letters, checked by the path guard). The existing callers and tests are unchanged.
5. **`CardPage.Begin` gained an overload** that writes the banner of several runs, for the pooled index of the pack; the single-run overload calls it. No card changed.
6. **Event ids 4419 to 4422** (pack written, pack unchanged, check read, started) join 4405 to 4411; ids 4412 to 4414 are the cost-sheet verb and 4415 to 4418 the result store.
7. **No engine change.** The engine stays `sim-5`, the run-record schema 5 and `SimTrade` schema 4.
