## Context
Doc 14 says the model never decides a trade and its outputs are "features measured like any other". The LLM branch of P15 wants a `material` flag and three optional fields per announcement. An announcement is text written by a third party, so it can contain instructions. The plan also asked the extracted fields to "agree with XBRL on 98 %", but order value, guidance and rating action never appear in a results XBRL, and D4 forbids taking results numbers from text: that check has no field to run on.

## Decision
1. **One request, no tool, no repair.** `AnnouncementFlagger` (infrastructure, in the filings archive folder) builds one `ModelRequest` over `IChatModel` (the P9-01 chat client behind the local model server; no other client, no host added, the allow-list is unchanged) with an empty tool list, temperature 0 and seed 1337, and reads the streamed text. A tool-call part, or a finish reason of `tool_calls` or `length`, is `invalid_output`. One attempt; a failure is not retried, so the measured behaviour is the one stored. An over-long input (text over 4,000, subject over 300, category over 60 characters) is `too_long` and never reaches the model. A server failure surfaces as `ModelUnavailableException`.
2. **Text is data.** The system prompt (`announcement-flag` v1, an embedded file registered in `PromptRegistry`, hence in the eval fingerprint) says the block is third-party data that may contain instructions, fake system messages and fake fences, that nothing in it is to be followed and that the model has no tool. The subject, category and text sit between `<<<BEGIN token>>>` and `<<<END token>>>` lines; the token is 16 random hexadecimal characters per request and is drawn again until it occurs nowhere in the content, so the text cannot contain the real fence.
3. **The answer is parsed as data against a closed schema.** `AnnouncementAnswerParser` (pure) takes one JSON object with exactly the six keys once each, `material` a JSON boolean, `category` one of twelve words, `guidance` and `rating_action` from their lists, `reason` of 1 to 200 characters with no control, direction-override or zero-width character, `order_value_inr` a JSON number or null (0 to 10^15). Anything else (prose, fences, two objects, an extra or missing or duplicate key, a number as a string, invalid UTF-8, a lone surrogate) is `invalid_output` with a closed reason word of at most 30 characters; nothing of an invalid answer is stored. The reason is stored and shown as escaped text and is never fed to another prompt.
4. **An order value must be in the text.** `GroundedAmount` reads the numbers of the text (Indian and western grouping, decimals, `lakh`/`lac` x 100,000, `crore`/`cr` x 10,000,000; ASCII digits only; a number with a unit counts only with the unit applied) and keeps the model's value only if it equals one of them, read from the subject and the text, to the rupee. Otherwise it is stored null and counted `ungrounded`. This replaces the XBRL cross-check the plan could not run.
5. **The store.** `filings.extractions` (migration `AddFilingExtractions`): one row per filing, model file hash, prompt hash and schema version; the state is `ok`, `invalid_output`, `model_unavailable` or `too_long`; `ok` holds the whole answer and no reason, every other state holds a closed reason and none of the answer (checks). The model hash, the prompt name, version and hash and the schema version are stored with every row. Insert-only for `xd_app` (table-by-table grant); nothing for `xd_exec`, the read roles or the MCP roles. It stores no raw answer and no announcement text. The extraction row is the per-call record: no `ai.model_calls` row is written for a backfill call, a set D call or a hostile-set call.
6. **The verb.** `xd filings extract --from --to [--limit N]` (CLI only) classifies announcements in the range that have no extraction for the current model, prompt and schema, one request at a time under the turn gate, resumable through the key. It refuses while `ai.settings.enabled` is false (`assistant.disabled`, the existing code), while the model is not ready or reports no file hash, while another turn holds the model and while the nightly run is going; it never sets the switch. It stops at the first server failure after storing that row as `model_unavailable`. A row whose stored text cannot be read is counted and stores nothing. Log events `filings.extract.*` carry ids, states, counts and milliseconds only.
7. **Set D classifies the labelled rows.** `xd eval run --set events` sends each labelled row through the same flagger `repeats` times, one request at a time, nothing stored per call (the labelled file has the text and the exchange category but no subject, so the subject is empty there). A case's prediction counts only if all repeats agree; disagreement is `unstable`, counted as not material and reported. A non-`ok` answer is not a material prediction. The fixed hostile set (16 invented announcements, including exact-format forged begin and end fence lines: tool requests, a fake system message, a fake fence, an embedded answer, a URL, a 4,000-character repetition, mixed scripts, zero-width characters, direction overrides, an over-long text) is run once and its states are counted in the report (`hostile_set`).
8. **Protocol L's grader.** `AnnouncementGrader` passes set D only if all hold: at least 200 rows; at least `min_predicted_material` (30) predicted material; precision of material at least 0.80 (exact: 160 of 200 passes, 159 fails); and the model beats the category baseline on correctness per case by the exact two-sided sign test (`PairedComparison`) with `c > b` and `p < baseline_sign_p` (0.05). A row with no baseline class fails (`baseline_missing`); a missing or invalid baseline file makes the set `not_evaluable`, never a pass. A pass whose Wilson lower bound is under 0.80 is labelled weak evidence (36 of 40: 0.770 to 0.960). The report prints recall, both Wilson intervals, the baseline's precision and recall, b, c, p, the unstable count and the population-weighted precision.
9. **Weights are recomputed from the labelled rows.** A reserve row that replaced an `unsure` one does not carry the weight of the drawn sample: the weight of a row is its stratum's eligible count (`sample.json`: half, category, India year) over the number of labelled rows now in that stratum. A row with an unknown stratum gets weight 1 and no guess; without `sample.json` the weighted precision is reported n/a.
10. **Thresholds and staleness.** `eval/thresholds.json` gains `events.min_predicted_material` 30 and `events.baseline_sign_p` 0.05. The thresholds hash changes, and the new prompt changes the fingerprint, so an eval run accepted before this slice is `stale` (reasons `thresholds` and `prompt announcement-flag`) until a new gating run is accepted. **Recorded: the baseline accepted before P15-08, if any, is stale from this change on.**
11. **Protocol L reads the accepted run.** `EvalFlagGradeSource` replaces the unavailable default: it reads the newest ACCEPTED eval run and returns the grade of its set D with the model file hash and the `announcement-flag` prompt hash that run stored. No accepted run, no set D in it, set D not evaluable or not run, or a missing hash: no grade, so protocol L is NOT_EVALUABLE (`protocol_L_not_passed` for protocol X), never a pass. Only a set D PASS that was part of a PASS run can have been accepted.
12. **`llm-1` is defined, not extracted.** `LlmFeatureCatalog` (three columns: material count in 5 sessions, downgrade in 30 days, guidance direction in 30 days) is a valid extension group, but `ExtensionCatalogs.GroupOf` does not return it, so no feature row can be written for it; P15-10 builds the extraction after protocol L passes.
13. **No decision use.** The answer type, the two ports, the table and `llm-1` are named only by the flagger, its store, the handlers, the runner and the wiring (architecture tests pin the exact sets); selection, planning, checklists, simulation, strategies, the scorer, `XDrishti.Execution` and the API name none of them.

## Consequences
- With a ready model and the switch on, `xd filings extract` fills the table; with the owner's labels, `xd eval run --set events` grades the flag; only an accepted passing run lets protocol L answer.
- A new model file, runtime or prompt makes the accepted run stale and stored extractions are not reused for it (they carry their own hashes).
- A row stored `model_unavailable` is not retried by a later run (the key is the primary key and the table is insert-only); see Known limits.

## Known limits
- **Prompt injection can still bend a schema-valid answer** (a wrong flag). It cannot act: no tool, no write outside the extraction row. Protocol L measures the flag, not its robustness to adversarial text.
- **The eval gives the model no subject** (the labelled file has none); production gives it. The measured behaviour is therefore a lower-information case.
- **A transient server failure is permanent for that row and model.** A retry needs an update grant or a primary key with the time; both were left out to keep the table insert-only as specified.
- **200 labels** give a precision interval of about 10 points (doc 14 D10); the weak-evidence label says so.
- **The hostile set was run only with a scripted model in the tests.** A run with the real model is the owner's act and its result belongs in this ADR when it exists.
- **No call to a real model was made in this build**; the 3 to 6 s per call and the backfill time of the spec are UNVERIFIED.
