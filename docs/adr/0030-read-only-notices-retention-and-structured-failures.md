# 0030 — Notices are read-only, attention rows are kept for 30 days, and failures carry a kind

- **Status:** Accepted (owner, 2026-10-15: "start the hardening story now", [P2-18](../specs/P2-18-sync-and-import-hardening.md)) — amends [ADR 0027](0027-self-healing-sync-and-actionable-notifications.md) (the GET wrote rows; items never deleted; transient versus permanent decided by message text) and [ADR 0029](0029-dhan-report-imports-and-source-precedence.md) (one guard for every run kind)
- **Date:** 2026-10-15

## Decisions
1. **`GET /api/portfolio/notices` only reads.** The attention items are reconciled (raised, kept, resolved) by the healer tick and at the end of each sync run; the query reads what was stored. Two open tabs cannot make an item flicker, and a query no longer writes (CQS).
2. **Resolved attention rows are deleted after 30 days** (`Portfolio:Heal:AttentionRetentionDays`). `attention_items` is working memory (it remembers `since` and the 24-hour resolved window), not an audit record, so it is the one portfolio table whose DELETE the runtime role gets; audit events and every other table stay append-only. Unresolved rows are never deleted.
3. **Failures carry a kind.** The Dhan clients set an enum (transient, rate-limited, rejected, token-expired, token-refused, not-connected, history-too-large, unexpected) where the status and code are read; retry and persistence rules use the kind, never the text of a message, so rewording a message cannot turn a retry into a permanent failure.
4. **`SyncGuard` knows the kind of run.** Trade import, Undo and Rebuild wait for holdings and trades runs; DP import waits for holdings and ledger runs; the demat import waits for none. The message says it can take a few minutes.
5. **Dropped rows raise an item.** A trades or ledger run that dropped rows for a reason other than a harmless zero amount raises `rows_dropped` (counts and reason codes only) and it resolves when the latest run of that kind drops nothing.
6. **One source of truth for the commands** a notice may carry: the server lists them once, the client allow-list is generated from that list.

## Consequences
- A freshly changed cause can show up to one healer tick (a minute) late, except right after a sync run, which reconciles at its end.
- The runtime role has one DELETE grant; it is limited to a table that holds no history that matters.

## Consequences from the build (2026-10-15)
Built in [P2-18](../specs/P2-18-sync-and-import-hardening.md); the design is in [doc 12](../design/12-portfolio-monitoring.md) §3 "Self-healing and attention items" and "Dhan report imports", [doc 13](../design/13-reports-and-ui.md) "Notifications and pop-ups" and [doc 16](../design/16-configuration.md).
- **One writer, three moments.** `AttentionReconciler` (`Application/Portfolio/Attention`) is the only writer of `portfolio.attention_items`: it loads the facts, derives the items and calls `AttentionStore.ReconcileAsync` - one statement (an upsert of what holds together with the update that resolves the rest). It runs at the end of every healer tick (`PortfolioHealer.TickAsync`), at the end of every holdings, trades or ledger attempt (`SyncHealthRecorder`) and after a Dhan sign-in is stored (`CompleteConnect`); one reconcile runs at a time in the process; a failure is logged and never fails the caller. `GET /api/portfolio/notices` calls `AttentionStore.ListAsync` and writes nothing (a statement-recording test). With `Portfolio:AutoRefresh:Enabled = false` the tick does not run, so neither the periodic reconcile nor the retention happens; the ends of runs and sign-ins still reconcile.
- **Retention.** `ApplyRetentionAsync` (same tick) deletes resolved rows older than `Portfolio:Heal:AttentionRetentionDays` (default 30, compose `XD_PORTFOLIO_HEAL_ATTENTION_DAYS`, range 1 to 3650) with a statement that only touches rows whose `resolved_at` is set. Migration `AttentionRetentionGrant` re-grants DELETE on `portfolio.attention_items` to the runtime role (taken away by `AddSyncHealCounters`) and on no other table; its `Down` takes it away again.
- **`rows_dropped`.** One item per account and kind (`trades`, `ledger`) from the counts of the **latest succeeded** run of that kind: a running, skipped or failed latest run neither raises nor resolves it, a succeeded run that dropped nothing resolves it. Id `attention:dropped:{account}:{trades|ledger}:{8 hex digits of a hash of the set of reason codes}`; information when every reason is `zero_amount`, a warning otherwise; the text holds counts and the plain words of at most three reasons (`DropReasonWords`, a fixed table of the 14 codes; never a name, amount or id); the single action *Open* is the route `/portfolio?focus=sync`, which the Portfolio screen answers by focusing **Sync trades & ledger** (the sync bar when that button is off, the Account picker when all accounts are shown).
- **Failure kinds.** `FailureKind` (`Domain/Common`) is carried as `Error.Cause`; `BrokerFailureKind` gained `RateLimited` so that a 429, or a 4xx that carries DH-904, is a rate limit whether or not the body says so. `SyncFailures.OfMessage` is gone and no code matches a message. A second concurrency conflict in a unit of work is `PortfolioErrors.DataChanged`, a neutral text for manual flows; the broker history run fails the window when its row-by-row save or its finishing unit of work fails, and the price-alert check reports 0 and leaves the alerts active.
- **Guard matrix** (`SyncWaits`, `SyncGuard`): trade import (also a Dhan report's bills), Undo of a trade batch and Rebuild of lots wait for holdings and trades runs; DP-charges import for holdings and ledger runs; demat import for none. The refusal is `409 portfolio.sync_running` with the text "can take a few minutes".
- **Imports.** One phrase table `LedgerText.Phrases` serves the classifier, the account-level cost rule and the depository test; the supersede of imported DP lines and `DpPlanner` decide "the day has a depository charge" from the whole stored day; `BillPlanner` counts every equity leg of a file as a sibling for the exchange salt; `SpreadsheetPackageGuard` refuses an `.xlsx` with more than 50 entries, more than 100 MB declared or an entry of at least 1 MiB expanding more than 200 times, before parsing; `includeDuplicates` values are capped (160,000 characters; reading stops at 20,000 numbers).
- **Returns and screens.** The Cash drawer says only account-level costs count; a finished sync run refreshes the dividend suggestions; per-share amounts show up to 4 decimals; the toast forgets its focus return when no open toast holds focus; the rule for a scope of priced and unpriced holdings (their dividends and charges are in the percentages, not in the net XIRR) is stated and tested; the "holding appeared since" check has a database test.
- **Contract.** `scripts/gen-api.sh` publishes `x-xdrishti-attention-commands` and writes `frontend/src/shared/api/attentionCommands.generated.ts`; the run counts (`BrokerSyncCounts`) gain `rereadVersion` and `rereadDone` (dates only) and the notice description names `rows_dropped`.

## Deviations from the spec (2026-10-15)
- **F4 keeps the re-read progress in the run's counts JSON, not in `broker_sync_windows`.** The spec preferred the existing window rows. Each window read again is added (dates only) to `BrokerSyncCounts.RereadDone`, with the `RereadVersion` of the mapping, in the unit of work that stores the window; the next run, when the run before it failed with the same version, starts from that list. No column or table was added for it. The consequence is that the progress lives as long as the run row does and is taken over only from the run immediately before; ISS-10 (the reason on `needs_reread`) still needs a migration of `broker_sync_windows` and stays open.
- **I1 leaves four qualifier phrases.** *depository*, *dp fee*, *demat fee* and *subscription fee* are in the table without the `Charge` flag, so they qualify only an entry that another phrase has made a charge. That is what the three lists did before; the spec's "no dead phrases" is met by listing each phrase once with its flags, not by making a bare "DP fee" a charge.
- **I3 changes one identity.** A BSE trade whose same-bill NSE sibling is left out (covered by Dhan or skipped) now carries the exchange salt, where it kept the plain identity before. A report imported before the change and again after it can store such a BSE row a second time (Undo the older batch first). No other identity moves; `BillIdentityGoldenTests` still pins the rest.
- **`PortfolioErrors.HoldingChanged` carries the cause `DataChanged`** (reason code `data_changed`, transient). The error a broker history run reports when a unit of work ended as `DataChanged` (the manual flows' neutral "try again", which means nothing to a run) is retried quietly like a failed call; the next run reads the window again. It has its own reason so the health row does not claim that Dhan could not be reached for a local database conflict.
- **The text of a `rows_dropped` item is built on the server** (`DropReasonWords`), and the browser shows it. The spec said the frontend text reuses `dropReasons.ts`; the sync line still uses that table, so the words exist twice (same wording, one table in each tier) and each has its own test.
- **Endpoint summaries.** Only the summary of the tradebook import (`POST /api/portfolio/trades/import`, operation `ImportTrades`) was reworded to say that a ledger-only run does not block it; the summaries of Undo, Rebuild and the report imports keep their generic `sync_running` wording, and the matrix is in doc 12.
