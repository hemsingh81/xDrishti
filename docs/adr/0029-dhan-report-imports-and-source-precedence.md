# 0029 — Dhan's downloaded reports are imported by kind, and API trades take precedence over bill-level report rows

- **Status:** Accepted (owner, 2026-10-15: supplied the reports and asked for the system to be updated — [P2-17](../specs/P2-17-dhan-report-imports.md)) — builds on [ADR 0023](0023-trade-import-and-lot-reconstruction.md), [ADR 0025](0025-dhan-trade-history-and-ledger-sync.md), [ADR 0026](0026-dividends-entered-by-the-owner-and-charges-in-net-returns.md) and [ADR 0028](0028-dividend-csv-import-with-name-matching.md)
- **Date:** 2026-10-15

## Context
A set of Dhan downloads (analysis in `data/dhan/reports/ANALYSIS.md`): the global transaction reports (bill-level trades with side and all charges), DP-charges sheets (legacy `.xls`), a demat holding statement (ISINs), and the Realised P&L / P&L statements. No single file is complete: against the owner's earlier tradebook, some date-and-scrip groups are missing from the transaction reports and some are only there; the depository quantity differs from the net of the trades for a few securities (IPO allotments, demergers, transfers, missing early buys). The transaction-report fees add up exactly to each report's "Total Charges"; first-in first-out over its rows reproduces Dhan's realised P&L for most cash scrips.

## Decisions
1. **One detector, many kinds.** Files are recognised by title line and headers (`.csv`, `.xls`, `.xlsx`): global transaction report, DP charges, demat holding, realised P&L, P&L, dividend payout, trade file with side, tradebook without side. A file of a kind that belongs on another screen is routed there; kinds that are statements of results (the P&L reports) are recognised and not imported.
2. **The global transaction report becomes trades** through the existing preview/import/Undo flow: side from the buy or sell quantity, price = value ÷ quantity, charges = the seven charge columns, identity from bill number, date, normalised name and side. Futures, options and MCX rows are counted and skipped. Bill-level rows are marked `source = bill` so they can be told from CSV trades.
3. **ISIN comes from names** the app already knows: aliases, holdings, the instrument master, and names learned from a demat-holding or DP-charges file; unresolved names are chosen once and remembered.
4. **A BSE row is imported when its ISIN is one the account holds**; otherwise the existing rule (skip) applies.
5. **DP charges are account costs**: stored as ledger entries of class `charges` with `source = import`, counted by the P2-14 net figures once; a line equal to a ledger-API charge of the same day is skipped, and when the ledger API later stores such a charge an imported entry of the same day and amount is voided (amendment k).
6. **The demat holding statement never changes holdings** (the broker API stays authoritative, ADR 0012); it teaches names and produces a comparison with the synced holdings, **returned in the preview and the import result only; no attention item or notice is raised** *(amended: the first text said "raised as a notice"; see amendment c)*.
7. **Precedence:** per (account, trade date, ISIN, side) a group of Dhan-API trades beats an imported bill row. An imported row whose group already exists from the API is skipped (*covered by Dhan*); when the API later stores that group, the bill row is voided (*superseded*). Total differences are shown, not hidden. This prevents double counting without asking the owner to choose.
8. **Personal header lines** (name, client code, mobile, e-mail) are skipped by the readers; the client code is only compared, for a warning, with the code of the reports imported into the account before: the account remembers a salted hash of the first one, never the code (Amendments d; the first reading compared it with the account's Dhan client id).
9. **Spreadsheet reading uses a pinned library** (ExcelDataReader, MIT) because the owner's DP-charges files are legacy `.xls`.

## Consequences
- The owner can load years of trades with sides and charges from files, and the Dhan API read fills what the files miss; the two never count a trade twice.
- Bill-level rows give one average price per scrip per day, so lot costs on days with several fills differ slightly from execution level; quantity and total value are exact.
- Futures, options and commodity trading stays outside the app's figures, however large a part of the owner's trading it is.
- A reconciliation of lot reconstruction against Dhan's realised P&L is possible later with the same detector.

## Consequences from the build (2026-10-15)
- **A price keeps 6 decimals everywhere.** A bill row has one value and one quantity, so the price is value ÷ quantity to 6 decimals and `portfolio.transactions.price` is `numeric(18,6)` for every source (a global change), so on the trade row quantity × price gives the bill's value back to the paisa; lots keep `numeric(18,4)` unit costs (`LotReconstructor` rounds the unit cost to 4 decimals), so the cost of a lot built from a bill row can differ from the bill's value by up to quantity × ₹0.00005 — about ₹0.50 per 10,000 shares — not by a fraction of a paisa.
- **The identity is the bill, the day, the name and the side — not the ISIN.** `g:` + a hash of those, so matching a name later (a choice, a demat statement) never changes what was imported, and the same bill read from another report is the same trade. The price is that the identity depends on the name-normalisation rules, which a golden test pins ([ADR 0028](0028-dividend-csv-import-with-name-matching.md) amendment g).
- **Names find ISINs through two stores.** A choice that points at a holding or an instrument is a `dividend_aliases` row (unchanged, [ADR 0028](0028-dividend-csv-import-with-name-matching.md)); names with an ISIN — taught by a demat statement or a DP-charges sheet, or typed in by the owner — are `portfolio.security_aliases` rows (immutable, unique per account, name key and ISIN). The order of the rules is: the owner's choice, an alias, the ticker in brackets, the name against holdings (open, then closed), the instrument master and the learned names, then a one-word-prefix spelling (flagged `partial_name_match`).
- **A name that cannot be resolved is imported without an ISIN**, not skipped, and shown as *needs a match*; such trades do not join a holding, are never covered or superseded by Dhan's trades, and become useful when the owner chooses (the next import of the same file adds nothing, so the choice is made before the import, or the batch is undone and imported again).
- **Precedence is exact but narrow.** It compares groups by (account, India day, ISIN, side) and needs the ISIN on both sides; it covers the broker's trades only. A CSV tradebook or a manual trade for the same days is **not** compared, so importing a tradebook and the report for one period can count a trade twice. Import one source per period.
- **Charges are a net sum.** The seven charge columns are added; a row whose sum is negative (a refund) is imported with 0 charges and a warning, while the file's own total (negative rows included) is the one checked against the report's "Total Charges".
- **The DP file's costs are ordinary ledger entries** with `source = import`: they leave the lists and the net figures when the batch is undone, and the date from which the ledger's costs are known still comes from the entries read from Dhan, so a sheet that reaches back before them is counted in full under a later "from" date.
- **Reading a spreadsheet is a pinned dependency behind a port**, not a conversion step. There is no guard against a decompression bomb in an `.xlsx`: the limits are 20 files, 10 MB each and 40 MB together on the upload and 20,000 data rows on the first sheet.
- **`Down` is destructive for imports**: it deletes the bill-level trades and the imported ledger entries, because they have no place in the old shape.

## Amendments (2026-10-15)
Made while building [P2-17](../specs/P2-17-dhan-report-imports.md); the spec marks them too.
- **a. Aliases are ISIN-keyed in `security_aliases`; `dividend_aliases` is unchanged.** The spec said the ADR 0028 alias table "now keyed by ISIN too". The build left `dividend_aliases` as it was and gave ISIN-keyed names (those a demat statement or a DP-charges sheet teach, and ISINs typed in as a choice) a table of their own; a choice that points at a holding or instrument still uses the dividend alias.
- **b. Identity by name key.** The spec's identity (`g:` + bill number + date + normalised name + side) is kept, with the name key of the dividend import (the ticker in brackets is not part of it); the ISIN never enters it. The exchange does not either, except on a collision: when the same bill number, scrip, day and side occur on two exchanges in one import, the NSE row keeps the plain identity and every other exchange is salted with its exchange name (a blank exchange with `unknown`), independent of the order of the rows; the reader's repeat key includes the exchange. **Limit:** identities are stable relative to the siblings present in the import (a leg covered by Dhan is not counted), so a rare collision can give the same bill another identity when its sibling is covered or absent.
- **c. The demat mismatch is not an attention item.** The spec (criterion 11) raised a notice when the statement and the synced holdings differ; the build shows the differences in the preview and the import result only ("informational, nothing is changed"), because the attention items are derived from stored facts and a comparison with a file the owner dropped is not one.
- **d. The client code is compared as a remembered hash, not with the Dhan client id.** Decision 8 and the spec's criterion 12 compared the report's client code with the account's Dhan client id; the app does not hold a client id that equals the report's UCC, so the account instead **remembers a salted SHA-256 of the first code it imported** (`accounts.report_client_codes`; the plain code is never stored) and warns, and rejects unless ticked, when a later report's hash differs. An account that remembers none, and a report without a code, never warn. The hash keeps the code out of the database; it does not defend against someone who can read the database and try codes.
- **e. Precedence limits.** It needs the ISIN on both sides, covers the broker's trades only and does not look at CSV or manual trades (Consequences); the spec's wording "per (account, date, ISIN, side)" stands, and the superseding is done inside the unit of work that stores the broker's trades.
- **f. Four-decimal lot costs against six-decimal prices** (Consequences): the price is `numeric(18,6)`, the lot's unit cost stays `numeric(18,4)`. The trade row reproduces the bill's value to the paisa; a lot's cost carries the rounding of its unit cost, up to quantity × ₹0.00005 (about ₹0.50 per 10,000 shares). The earlier wording "a fraction of a paisa" for the lot was wrong and is corrected here and in the spec and doc 12.
- **g. Negative charge rows are imported as 0 with a warning** (`negative_charges`); the reader keeps the negative amount in the file's charge total, which is what the footer check uses.
- **h. No zip-bomb guard** for `.xlsx`; not decided against, only not built (the upload and row limits above are the bounds). The reader is hardened otherwise after the review: an `XmlException` from a damaged `.xlsx` is caught (a damaged file is that file's error, never an exception), and the number of columns read is capped.
- **i. Unresolved names are imported ISIN-less** and flagged, as the spec's scope item 3 said, although its first scope item said rows that cannot be tied to an equity or ETF are skipped: only rows that are not equity by their exchange or name (futures, options, commodity, currency, other) and BSE rows of an ISIN never held are skipped.
- **j. The imported costs do not move the ledger coverage date.** `ledgerChargesFrom` of the net figures is the first entry read from Dhan; a DP sheet that reaches back before it is counted in full while the tiles say "from" the later date.
- **k. A ledger sync supersedes an imported DP entry** (decision 5 seen from the other side). When the Dhan ledger read stores a `charges` entry, an imported (`source = import`) cost entry of the same account, the same day and the same amount is voided (the ledger's own void columns; Undo of the batch stays possible); **one broker entry covers one import line** (two identical imported lines need two ledger entries). The cost is therefore counted once whichever source came first, the mirror of the preview's `already_in_ledger`. **Matching:** a sheet line is matched to a Dhan `charges` entry of the same account, day and amount, preferring entries labelled as depository charges (`DepositoryCharges`: dp charge, dp fee, depository, demat charge, demat fee): if the day has any such entry only those are used, otherwise any `charges` entry of that day (fallback). **Unverified against a real ledger:** the labelling and the assumption that Dhan books the charge on the sheet's day are to be checked with the first real data. The classifier and `LedgerCosts` currently class as charges only 'dp charge(s)', 'demat charge' and 'depository charge' (follow-up: align the phrase lists).
- **l. An import is refused while a sync of the account runs** (`409 portfolio.sync_running`, as that file's own error), so an import and a sync cannot race on the same groups; the owner imports after the run. Amended after the final review: "a sync" is the holdings sync **and any broker history run (trades or ledger)** of the account (`SyncGuard`), and the guard also stands before trade and bill imports, Undo of a trade batch, Rebuild of lots (not dry runs or previews) and the DP and demat imports. **Consequence:** a long backfill (up to 30 minutes) blocks them, and a hung run is released only by the recovery when the API starts or by the next sync (staleness is not looked at).
- **m. Supersede is computed from the whole stored group**, not from the rows of the current run alone: a (account, day, ISIN, side) group completed over several runs still supersedes its bill rows, and the reported difference in totals is that of the whole group.

## Amendment (2026-10-15, P2-18)
[P2-18](../specs/P2-18-sync-and-import-hardening.md) closed the open points of the review; the decisions are in [ADR 0030](0030-read-only-notices-retention-and-structured-failures.md).
- **h (no zip-bomb guard) is superseded.** `SpreadsheetPackageGuard` reads the central directory of an `.xlsx` before parsing and refuses a package with more than 50 entries, more than 100 MB declared in all, or an entry of at least 1 MiB that expands more than 200 times, as that file's error (`portfolio.invalid` on `file`).
- **l (the guard) is kind-aware.** Trade import (also a report's bills), Undo and Rebuild wait for the account's holdings and trades runs; the DP-charges import for holdings and ledger runs; the demat import for none; the refusal says it can take a few minutes. A ledger-only run no longer blocks a trade Undo or Rebuild.
- **One phrase table** (`LedgerText.Phrases`) serves the ledger classifier, the account-level cost rule and the depository test of the supersede; four phrases (*depository*, *dp fee*, *demat fee*, *subscription fee*) only qualify an entry that another phrase made a charge, as before.
- **k and m decide the day from the whole stored day.** The supersede and the sheet's plan (`DpPlanner`) judge "the ledger has a depository charge on the day" on every charge stored for it, not on the entries a save adds.
- **b (identity) counts every equity leg as a sibling.** A leg covered by Dhan's own trades, or a BSE row left out, still takes part in the exchange salt, so the identity does not depend on which siblings are pending. A BSE trade whose same-bill NSE sibling is left out now carries the salt (it did not before).
