# 0018 — Services framework: schedules in the database, one scheduler, the Services screen

- **Status:** Accepted (owner, 2026-10-13: "approved as written") — builds on [ADR 0010](0010-instrument-master-sources-and-scope.md), [ADR 0013](0013-portfolio-import-with-settings-and-daily-refresh.md) and [ADR 0017](0017-trading-calendar-eod-schedule-quality-adjustments-and-csv-undo.md) §2, which each left "the schedule editor / service framework (P1-13)" for later
- **Date:** 2026-10-13

## Context
Three things already run by themselves, each with its own hosted service, its own once-a-day rule and its own `appsettings` keys: the end-of-day data run (`Data:Eod:*`, 15:50), the instrument-master refresh (daily) and the per-account holdings refresh (ADR 0013, set in Accounts). Design doc 04 §3 promises more (pre-open check, price alerts, nightly pipeline, backup, retrain …) and a Services screen where every schedule, its retries, timeout, catch-up and parameters are editable, checked against each other and previewed. Changing a time today means editing configuration and restarting the stack; there is no place to see what ran, what failed and what runs next.

## Decisions
1. **A service is a registered definition plus a row of desired state.** In code, `ServiceDefinition` (id, name, description, `runsAs`, allowed schedule types, default schedule and execution settings, parameter schema with bounds, constraints) is registered by the module that owns the work. In the database (`platform.service_schedules`) one row per service holds the owner's choice: enabled, schedule (type + fields), retries (0–5), timeout (1–240 min), catch-up, notify on failure, parameters (JSON validated against the definition's schema), `revision` (`xmin` concurrency token), who and when. A service without a row runs on its definition's defaults; the first save creates the row. "Restore default" deletes nothing: it writes the defaults.
2. **Schedule types** (design doc 04 §3.1): `daily` (time, days), `weekly` (weekday, time), `after` (another service, runs each time it finishes successfully), `window` (start–end, days; a service that is up between the two times), `interval` (every N minutes within a window, days), `continuous`. A definition lists the types it allows (a data job allows daily/weekly/after, the live feed window, the CSV watcher continuous). "Trading days" is a shortcut for Monday–Friday **and** the calendar of ADR 0017: a daily/weekly/interval schedule fires only on trading days when its `tradingDaysOnly` flag is set (default for market jobs; off for backup and the weekly retrain).
3. **One scheduler** (`ServiceScheduler`, a hosted service in `xd-api`) replaces the per-job hosted services. A pure `ScheduleCalculator` answers "next occurrence after t", "was one missed" and "occurrences on a date" from the schedule, the calendar and the clock — no I/O, tested with a fake clock. The scheduler wakes at least once a minute and at the next occurrence, re-reads the rows (so an edit takes effect without a restart), starts due services, applies the timeout and the retries (back-off 30 s, 2 min, 10 min, 30 min, 1 h; each attempt is recorded) and ends a run as `succeeded | failed | skipped`. A service runs **at most once at a time**; a start while it runs is skipped and recorded. Existing runners (`DataEodRunner`, `DailyRefreshRunner`) keep their work and their once-per-day/skip rules and become the `IScheduledService` implementations behind `eod` and `instrument-master`; they lose their own waiting loops and `Enabled`/`TimeIst` settings. `Data:Eod:*` and the instrument refresh time become **first-start seeds** for the rows (read once when no row exists), then ignored; the docs say so.
4. **Catch-up** (per service, default on for data jobs): at start-up and on every wake-up a missed occurrence (an occurrence time in the past with no run started since, within the same India day, or within 24 h for weekly) is run once at once, recorded with trigger `catch_up`. Never more than one catch-up per service per start. A paused service does not catch up when resumed.
5. **Runs are history** (`platform.service_runs`: service, trigger `scheduled | catch_up | after | manual`, attempt, started, finished, status, message, optional `data_job_id`). The runtime role has INSERT/UPDATE/SELECT, no DELETE; the list is bounded by an age limit enforced on read (default last 200 per service shown), nothing is purged in this slice. Interrupted runs (the process died) are closed as `failed: interrupted` at the next start, like the data and refresh jobs.
6. **Checks on every save** (design doc 04 §3.1), by pure rules over the **whole** set of schedules, so a change to one service is checked against the others: *errors block saving* — a run-after chain that is circular or points at a service that cannot finish (continuous), a window whose start is not before its end, an interval outside 1–120 min or longer than its window, no day selected, a type the service does not allow, a bound broken (retries, timeout, parameters); *warnings are shown and allowed* — end-of-day fetch before 15:35, pre-open check before ~09:08 or after 09:15, nightly pipeline before the end-of-day fetch and the portfolio sync, a backup during market hours (09:15–15:30), a live window that does not cover 09:15–15:30, two services at the same minute, a run-after chain longer than three. Constraints belong to each definition (`MustFollow`, `MustNotOverlap`, `MustCover`) so a rule exists as soon as its service is registered; rules of services that do not exist yet are not shown. The same rules answer a dry run (`/preview`) so the dialog shows issues and the **next three occurrences** while editing, before anything is stored.
7. **The Services screen** (prototype *Services*) shows the checks banner, a trading-day **timeline** (market hours, review cutoff, every enabled schedule as a mark or a band, run-after chains marked), and a table (service, schedule in words with retries/timeout/catch-up, runs as, status — healthy · running · failed · paused, last run with its trigger, next run, actions Run now · Configure · Pause/Resume · History). Run now starts the service through the same path with trigger `manual`. Configure is a dialog with the type-specific fields, execution settings and parameters, the preview and the issues; Save is disabled while an error stands. History is a drawer with infinite scroll. Editing is a normal authenticated action (CSRF, optimistic `revision`; **no step-up**: a schedule is not a credential or a role), and every change is audited (`service.schedule_changed`, `service.paused`, `service.resumed`, `service.run_requested`). A failed run of a service with *notify on failure* raises a notice derived on read (like the data and account notices), id `service:failed:{runId}`.
8. **Not in this slice.** A separate `xd-worker` container: the scheduler runs in `xd-api` as the data runners do today; `IScheduledService` and the tables do not care where they are hosted, so moving it is a deployment change (ADR when it is done). The per-account holdings refresh stays where ADR 0013 put it (Accounts → Portfolio settings, once a day per account); the Services screen lists it as one **read-only row** ("Account & portfolio sync — set per account", last/next run from the existing sync state) with a link, not a second place to edit it. Services that do not exist yet (pre-open check, alerts, nightly pipeline, backup, retrain, feed, CSV watcher) are not shown and not seeded; each story that adds one registers its definition. Data validation is the last step of the end-of-day job (ADR 0017 §4), not a service of its own. **Schedule types not used yet:** window, interval and continuous schedules are computed and checked (calculator, rules, preview, timeline) but only daily, weekly and run-after services exist today. The scheduler starts a window or interval service only at each occurrence (the start of the window, each tick) and does not keep a continuous service up or stop it at the end of a window; the runners for those arrive with the first service that needs them (the live feed, the CSV watcher, the price alerts).

## Consequences
- Times, retries and parameters of the automatic jobs are changed in the app, take effect at the next wake-up (≤ 1 minute), are audited and visible to the next reader; no restart.
- All "what ran, what is next, what failed" questions have one answer; the data screens' "Automatic update" line reads the same next/last run.
- The existing behaviour is kept by moving, not rewriting, the runners' work: the once-per-day, skipped-run and catch-up rules of ADR 0017 §2 and ADR 0010 are expressed as the scheduler's rules and covered by the same tests, re-pointed.
- A bad schedule can still be saved as a warning (e.g. a backup at 11:00): that is the owner's call; errors that would make the scheduler misbehave (cycles, empty windows) cannot be saved.
- The instrument master refresh now decides "was a run missed" from the service run history instead of from the refresh records, so the first start after this change makes up for one run (one conditional request on an unchanged file).
- A run that times out while its work is in a background worker that cannot be stopped (a data job, a refresh) is recorded as failed ("timed out … the job is still running"), is never retried, and a later start does not pile a second job on it or write a skipped record for it. A sequence of retries survives a restart: the scheduler takes it up again from the run history. The failed-run notice of the end-of-day job is the `service_failed` notice of its service (governed by *notify on failure*); the former `data_run_failed` data notice is gone.
- Hosting stays in the API process, so a long run shares the process with the API; unchanged from today, and the reason the worker split is a later, separate decision.
