# 0283 — The hold-out is a chain of fixed blocks, released by an owner act or the auto option, and every cut follows the block in force

- **Status:** Accepted (owner, 2026-11-13, in chat: "Consider my approval and you do due diligence also consider mostly things should be in auto mode with best default values"; spec [HO-01](../specs/HO-01-hold-out-epochs.md) Approved with the due-diligence changes).
- **Date:** 2026-11-13.
- **Relation to other ADRs:** Amends [0207](0207-a-strategy-version-is-pre-registered-the-ledger-counts-every-extra-look-and-a-locked-hold-out-is-fixed-at-the-first-post-and-read-once-by-an-owner-unlock-with-enforcement-and-the-honest-count-as-the-owners-switches.md) §3–4 (one block, read once, "a longer block set by an owner act" not built). Builds on [0243](0243-simulate-everything-is-training-data-fenced-from-the-hold-out-and-from-scorecard-evidence.md) §2 (the shared training cut) and [0272](0272-the-system-replay-is-research-only-fenced-from-evidence-and-hindsight-labelled-and-runs-the-live-pieces-over-as-of-facts-in-memory.md) §3 (a replay never reads the hold-out). Takes the defaults of [0282](0282-auto-mode-defaults-follow-the-owners-instruction-of-2026-11-13-on-where-no-evidence-is-lost-and-no-risk-is-widened.md).
- **Scope of this record:** HO-01a (the chain, the store, the cut behind the port, the release, the labels) and HO-01b (the per-kind looks, the horizon rule, the model reading across blocks, the `holdout-epochs` service, the stalled-block notice, the card, the `Enforce` default and the per-row label), see *Amendment, HO-01b* below.

## Context
The hold-out was one block, fixed at the first Lab post and never advanced. Sessions after its end reached no look and no development run. The look took one fresh slot for ever. The port said "a later block supersedes this one", but nothing built the advance.

## Decision
1. **A chain of fixed blocks.** Block 1 is the stored block exactly as it is (`prev_start` null, its end is `history_last`). Block k+1 is `[end_k + 1 day, end_k + L months]`, L = `Confidence:HoldOut:BlockMonths` (default 6, range 3–12) read when that block is stored. A stored block never changes; the chain has no gaps and no overlaps. Block 1 is never re-cut.
2. **States are derived, never stored:** `filling` (a trading day is left up to its end), `sealed`, `looked` (a fresh look exists), `released` (a row in the release table).
3. **The cut follows the block in force**, the earliest block with no release. `IHoldOutStore.CurrentAsync` returns it, so the Lab window, the training window, the training store gate, the cell refresh and the replay clamp move together, and only forward, only by a release. The training store gate no longer has its own SQL; the replay clamp uses `HoldOutOptions.TrainingCut` and not an inline sum. With nothing released every cut is byte-identical to before.
4. **Release.**
   - **Owner:** `POST /api/lab/holdout/blocks/{start}/release`, fresh password, `forfeitLook`. Allowed only for the earliest unreleased block once it is sealed. An unlooked block is released only with `forfeitLook: true`, and the row records `looked = false`. One transaction stores the release row and block k+1; a lost race stores neither.
   - **Auto:** `Confidence:HoldOut:AutoRelease`, default ON (ADR 0282). A sealed block is released by itself only when it has a fresh look and no look is still available for any kind; an unlooked block or an `unavailable` read keeps the block. The rule is `HoldOutAutoRelease` (pure) and the act is `HoldOutReleaser.TryAutoAsync`; the evening seal step that calls it is HO-01b, which registers one `IHoldOutLookSlot` per kind. Until a kind is registered it holds no block.
   - The release row is insert-only for the runtime role, with the mode, the actor, the setting snapshot hash, whether the block was looked, and the block it opened. A release is permanent; the migration's `Down` refuses while one exists.
5. **`HoldOut:AutoUnlock` defaults ON and never claims block 1.** Block 1 has no pre-dating horizon and its look is irreversible, so its strategy look (including the post-Lab-run auto look in `LabRunner`) stays the owner's act. Automatic looks start at block 2. A look at a filling block is refused (409 `lab.holdout_filling`), by hand and by the auto option. The pre-dating horizon belongs to HO-01b; HO-01a and HO-01b are deployed together.
6. **Released data is labelled.** A Lab run whose window, a replay session whose date, and a cell-statistics refresh whose end reach a released block carry `seen_holdout:<start>`. The result is allowed and never counts as hold-out evidence. Labels are not part of any run key.
7. **Migration `AddHoldOutEpochs`.** The earliest-created block is block 1; any other first-generation row left by the ADR 0207 race is marked `orphan` and never read; a unique index admits one first block and one successor per block; existing unlock rows are untouched.
8. **Fences, pinned by architecture tests.** No code outside `HoldOutStore` names the block or release tables (the EF mapping and the migrations only describe them). The epoch code references no execution, broker or order type.

## Consequences
- `HoldOut:Enforce` stayed OFF in HO-01a (coordinator, 2026-11-13) and defaults ON from HO-01b (ADR 0282), deployed with 01a and 01b together: with it ON an explicit Lab window into the block in force is refused and a PASS without a kept hold-out is capped at MARGINAL.
- New sessions reach learning on a fixed schedule after each owner (or auto) release; nothing reaches it before the first release. Block 1 waits for the owner's look or forfeit release.
- A release changes every default Lab window and training cut, so it changes run keys, as the first block did.
- Strategies built after a release are tuned on data that judged others; the `seen_holdout` label says so.

## Amendment, HO-01b (2026-11-13)
9. **One fresh look per block and kind.** Migration `WidenHoldOutLooks`: the fresh index is unique on `(block_start, kind)` where not `reused_window`; the per-version key is `(strategy_id, version, kind, block_start)`, so a version looks once per block; the kind check admits `system`; a nullable `reason` holds `not_predated`; `research.cell_stats` gains the nullable `seen_holdout` label. `Down` refuses while a `system` row exists or while the narrower keys would be violated.
10. **The pre-dating horizon** is the pure `HoldOutHorizon`. Block k at least 2: the subject (the version's first plan freeze, the model's registration `CreatedAt`, an SR-03 registration) must fall on an India date before the block's start. Block 1: the first stored look of any kind is the horizon (none yet: any strategy or model qualifies), and a `system` look is never fresh. A subject with no known freeze never qualifies. A look that fails it is stored `reused_window` with `reason = not_predated` (and `reusedReason` in the served result) and cannot pass; it burns no slot, so a later pre-dated subject of the kind can still take the fresh one.
11. **Models (D8).** `ModelHoldOutLooks.ReadAsync` reads the model's own newest fresh look across all blocks (`used`, with that block and look); a release no longer erases it. Another model's look or a re-used one at the block in force reads `reused`; a free block in force reads `kept`. The look rows still carry no scored figure (CF-10e part 3), so the newest look is what is read; row 12 (`LabEvidenceReader`) reads the version's newest fresh look and a later fail beats an earlier pass; with only re-used looks the row fails.
12. **The seal service `holdout-epochs`.** After `eod`, not before the session end, `LatestOnly`, enabled at first start, no password to resume. Its handler reads the chain (states are derived from the calendar, so "marking a block sealed" is the read of the day's close, never a write) and runs the registered `IHoldOutSealStep`s by `Order`, each on its own: 20 the strategy auto look (queues the existing `holdout` Lab job as `system:auto-unlock`, `auto` mode; never block 1, never a filling block; newest pre-dated version with a default-options full or robust run whose development rows pass and whose window is clear of the block, ties by the earliest first freeze), 90 the auto release. CF-10e part 3 (model, 30) and SR-03 (system, 40) add a step and an `IHoldOutLookSlot` each with two DI lines. The strategy slot is registered here, so the auto release no longer fails closed with `no_strategy_slot`; a slot that throws reads `Unavailable` and keeps the block.
13. **Stalled block.** `HoldOutStalledNotices` (an `IBellNoticeSource`, derived on read) shows one warning for the block in force once it has been sealed for 20 sessions, naming what holds the auto release (`blockedBy`).
14. **The served view.** `HoldOutBlockView.looks` is `{ strategy, model, system }`, each `fresh` (with subject, verdict, mode) or, for the block in force, `available`, `no_subject` or `unavailable`; `blockedBy` is set on the block in force. The Lab card lists them and offers the release behind the password dialog, which states the forfeit for a block with no look.
15. **Labels.** A snapshot of cell statistics labels each cell row whose trades exit inside a released block (`seen_holdout:<start>`, comma separated); a label is not part of the snapshot key. The label is stored; the cell views do not serve it yet.
16. **`Confidence:HoldOut:Enforce` defaults ON** (code default and settings section). Tests that pinned OFF were changed to ON, none deleted.

Row 12 and the model reading (D8) look at fresh looks only: the fail of a later look stored `reused_window` (including `not_predated`) is ignored by design, as spec D7 says, because such a look cannot count either way. A model registered on or after the horizon is refused before any block figure is read and nothing is stored, so it cannot fill its family's row at the block. A queued look is keyed by the run and the block, so a run that looked at block 2 can be queued again at block 3.

The automatic strategy look is taken only by the seal step. The post-Lab-run auto look (`LabRunner` calling `HoldOutUnlocker.TryAutoAsync`) is removed: block 1 was already skipped, the seal step makes the D10 pick every evening, and the post-run path only added a way to choose the version by choosing which run to post. A queued automatic look re-checks, when it runs, that `AutoUnlock` is still ON, that the version is pre-dated and that the block's strategy slot is free; otherwise it ends cancelled with an info problem and stores nothing. The seal step claims at most one look per evening (a job that already exists for the run and block ends the step).

*Shortcut:* the strategy auto look queues a job and the same evening's auto release reads the slot as still available, so a block is released the evening after its look is stored, not the same evening.
