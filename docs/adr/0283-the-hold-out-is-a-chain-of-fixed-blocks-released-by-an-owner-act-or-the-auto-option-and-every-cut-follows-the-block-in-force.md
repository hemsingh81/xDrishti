# 0283 — The hold-out is a chain of fixed blocks, released by an owner act or the auto option, and every cut follows the block in force

- **Status:** Accepted (owner, 2026-11-13, in chat: "Consider my approval and you do due diligence also consider mostly things should be in auto mode with best default values"; spec [HO-01](../specs/HO-01-hold-out-epochs.md) Approved with the due-diligence changes).
- **Date:** 2026-11-13.
- **Relation to other ADRs:** Amends [0207](0207-a-strategy-version-is-pre-registered-the-ledger-counts-every-extra-look-and-a-locked-hold-out-is-fixed-at-the-first-post-and-read-once-by-an-owner-unlock-with-enforcement-and-the-honest-count-as-the-owners-switches.md) §3–4 (one block, read once, "a longer block set by an owner act" not built). Builds on [0243](0243-simulate-everything-is-training-data-fenced-from-the-hold-out-and-from-scorecard-evidence.md) §2 (the shared training cut) and [0272](0272-the-system-replay-is-research-only-fenced-from-evidence-and-hindsight-labelled-and-runs-the-live-pieces-over-as-of-facts-in-memory.md) §3 (a replay never reads the hold-out). Takes the defaults of [0282](0282-auto-mode-defaults-follow-the-owners-instruction-of-2026-11-13-on-where-no-evidence-is-lost-and-no-risk-is-widened.md).
- **Scope of this record:** the part built as slice HO-01a (the chain, the store, the cut behind the port, the release, the labels). The per-kind looks, the horizon rule, the model reading across blocks, the `holdout-epochs` service and the card are HO-01b and add to this record.

## Context
The hold-out was one block, fixed at the first Lab post and never advanced. Sessions after its end reached no look and no development run. The look took one fresh slot for ever. The port said "a later block supersedes this one", but nothing built the advance.

## Decision
1. **A chain of fixed blocks.** Block 1 is the stored block exactly as it is (`prev_start` null, its end is `history_last`). Block k+1 is `[end_k + 1 day, end_k + L months]`, L = `Confidence:HoldOut:BlockMonths` (default 6, range 3–12) read when that block is stored. A stored block never changes; the chain has no gaps and no overlaps. Block 1 is never re-cut.
2. **States are derived, never stored:** `filling` (a trading day is left up to its end), `sealed`, `looked` (a fresh look exists), `released` (a row in the release table).
3. **The cut follows the block in force**, the earliest block with no release. `IHoldOutStore.CurrentAsync` returns it, so the Lab window, the training window, the training store gate, the cell refresh and the replay clamp move together, and only forward, only by a release. The training store gate no longer has its own SQL; the replay clamp uses `HoldOutOptions.TrainingCut` and not an inline sum. With nothing released every cut is byte-identical to before.
4. **Release.**
   - **Owner:** `POST /api/lab/holdout/blocks/{start}/release`, fresh password, `forfeitLook`. Allowed only for the earliest unreleased block once it is sealed. An unlooked block is released only with `forfeitLook: true`, and the row records `looked = false`. One transaction stores the release row and block k+1; a lost race stores neither.
   - **Auto:** `Confidence:HoldOut:AutoRelease`, default ON (ADR 0282). A sealed block is released by itself only when it has a fresh look and no look is still available for any kind; an unlooked block or an `unavailable` read keeps the block. The rule is `HoldOutAutoRelease` (pure) and the act is `HoldOutReleaser.TryAutoAsync`; the evening seal step that calls it is HO-01b, which registers one `IHoldOutLookSlot` per kind. Until a kind is registered it holds no block.
   - The release row is insert-only for the runtime role, with the mode, the actor, the setting snapshot hash, whether the block was looked, and the block it opened. A release is permanent; the migration's `Down` refuses while one exists.
5. **`HoldOut:AutoUnlock` defaults ON and never claims block 1.** Block 1 has no pre-dating horizon and its look is irreversible, so its strategy look (including the post-Lab-run auto look in `LabRunner`) stays the owner's act. Automatic looks start at block 2. A look at a filling block is refused (409 `lab.holdout_filling`), by hand and by the auto option. The pre-dating horizon belongs to HO-01b; HO-01a and HO-01b are deployed together.
6. **Released data is labelled.** A Lab run whose window, a replay session whose date, and a cell-statistics refresh whose end reach a released block carry `seen_holdout:<start>`. The result is allowed and never counts as hold-out evidence. Labels are not part of any run key.
7. **Migration `AddHoldOutEpochs`.** The earliest-created block is block 1; any other first-generation row left by the ADR 0207 race is marked `orphan` and never read; a unique index admits one first block and one successor per block; existing unlock rows are untouched.
8. **Fences, pinned by architecture tests.** No code outside `HoldOutStore` names the block or release tables (the EF mapping and the migrations only describe them). The epoch code references no execution, broker or order type.

## Consequences
- `HoldOut:Enforce` stays OFF in HO-01a (coordinator, 2026-11-13). Its default flip (ADR 0282) is built in HO-01b and deployed with 01a and 01b together, because with it ON an explicit Lab window into the block in force is refused and a PASS without a kept hold-out is capped at MARGINAL.
- New sessions reach learning on a fixed schedule after each owner (or auto) release; nothing reaches it before the first release. Block 1 waits for the owner's look or forfeit release.
- A release changes every default Lab window and training cut, so it changes run keys, as the first block did.
- Strategies built after a release are tuned on data that judged others; the `seen_holdout` label says so.
- Not built here: a per-row `seen_holdout` label on the cell-statistics rows (the cell tables have no label column; the refresh run carries it), the per-kind looks and the horizon rule (HO-01b), the card (HO-01b).
