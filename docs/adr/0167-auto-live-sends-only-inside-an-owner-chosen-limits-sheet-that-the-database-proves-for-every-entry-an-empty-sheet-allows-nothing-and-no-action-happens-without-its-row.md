# 0167 - auto_live sends only inside an owner-chosen limits sheet that the database proves for every entry; an empty sheet allows nothing, and no action happens without its row

- **Status:** Accepted (decided in P12-09 under the owner's standing run instruction; spec [P12-09](../specs/P12-09-auto-live-within-hard-limits.md), criteria 1 to 14; the screens are P12-10).
- **Date:** 2026-10-31.
- **Relation to other ADRs:** builds on ADR 0156 (schema `execution`, two runtime roles, insert-only by trigger), 0161 (halts; the `loss_cap` trigger), 0163 (the mode ladder: `semi_auto` and `auto_live` are not storable, the mode source stays closed), 0164 (readiness), 0165 (`ModeRouting`) and 0166 (the confirm ticket, the day unlock). It weakens none of them.

## Context
`auto_live` lets software send an entry without the owner's tap. It must be impossible to exceed what the owner chose, and impossible to start by default; and every automatic action must be visible to the owner one by one.

## Decision
1. **A per-account limits sheet, empty by default, and an empty sheet allows nothing.** `execution.limits` holds insert-only complete snapshots: orders a day, notional per order and per day, the day's loss cap, open positions, an allow-list of NSE trading symbols (exact match on the master's trading symbol, `TATAPOWER` is not `TATAPOWER-EQ`), a window, products and `exit_all_on_loss_halt`. An unset cap, an empty list or no window allows nothing (`limits.incomplete`). The ceilings are code constants and constraints (20 orders a day, 10 open positions, 50 symbols, window 09:16 to 15:00, products within `EQ_MIS`); money caps have no ceiling by design. The effective cap is always the stricter of the sheet and P12-01's global registry value.
2. **Raises wait, lowerings do not.** A change that loosens anything against the row in force (a cap up or newly set, a wider window, a symbol or product added, `exit_all_on_loss_halt` OFF; a mixed change counts as a raise) needs the owner's password (step-up without the elevation window) and takes effect at 09:00 India time of the next trading day after one full closed session. A pure lowering needs only the session and is in force at once. The row in force is the newest whose `effective_from` has passed; a later lowering supersedes an earlier pending raise. The trigger `execution.check_limits` repeats the classification and refuses a raise that would take effect before 09:00 India time of the next calendar day (a floor that the calendar rule never undercuts), and stamps a lowering now.
3. **The database proves the countable caps for every system-sent entry.** `execution.ledger_entries` has one row per entry; its trigger `execution.check_ledger_entry` takes an advisory lock per account (through the SECURITY DEFINER `execution.lock_account_ledger`, because the advisory-lock functions are the runtime role's only) and refuses, with the guard's own code, a row whose account is not `semi_auto`/`auto_live` (and `auto_live_enabled` OFF for `auto_live`), whose settings or limits id is not the one in force, whose sheet is incomplete, or that breaks the product, the allow-list, the window (start included, end excluded, India time of the database clock), the notional per order, the orders a day or the notional a day. Twenty parallel reservations for the last slot leave one. The loss cap, open positions and exposure need live positions and prices and stay in the application (D4).
4. **No action without its row, in the same transaction.** `execution.action_log` records every automatic action and every refusal (`auto_entry`, `tap_entry`, `auto_refused`, `tap_refused`, `auto_stop_tighten`, `auto_exit`, `auto_cancel`, `loss_cap_halt`, `loss_cap_notice`) with its codes, the settings and limits ids and a plain-language text. The ledger trigger requires its action-log row to be written in the same transaction (`xmin` is the current transaction) for the same intent; a deferred constraint trigger requires every entry row to have its ledger row by commit. `AutoActions` hands an entry or a reducing action to its hand-over port only after its row is written; a reducing action whose row cannot be written is not taken (the stop already rests at the broker and P12-04's watchdog protects on its own path).
5. **The guard.** `AutoLiveGuard` (pure, under 5 ms) runs only for an `auto_live` account with `auto_live_enabled` and `execution_enabled` ON; otherwise the answer is `mode.not_auto`, read from the two switches alone, with nothing written and nothing routed. When it runs, every rule that fails is listed: the caps above, `cap.open_positions`, `cap.loss_day`/`cap.loss_unavailable` (worst case: `max(0, -realised) + open risk to stops + new risk`, a profit gives no room), `approval.not_owner` (an `auto` approval only with `exec.auto_live_allow_auto_approved`), `plan.provisional`, `qty.above_plan` (never rounded up), `exposure.duplicate`, `strategy.first_use` (routed to a ticket), `pretrade.failed`, `unlock.missing` (`exec.auto_live_require_day_unlock`), `owner.not_attended` (`exec.auto_live_require_attended`, `exec.auto_live_attended_min`), `readiness.not_ready`, `feed.stale` (15 s), `recon.break`, `halt.active`. A `semi_auto` entry is held to the countable caps (`Caps`) the same way. Unavailable never passes.
6. **The loss-cap halt.** `LossCapEvaluator` asks P12-05 for a `loss_cap` halt (`entries`, or `exit_all` when the sheet says so) once per account and session when realised plus unrealised reaches minus the cap, and writes `loss_cap_halt`; an unreadable mark does not halt, it writes one `loss_cap_notice` and the guard refuses entries. `ILossCapSource` gives no number for an incomplete sheet.
7. **Settings.** `exec.auto_live_allow_auto_approved` false (true riskier), `exec.auto_live_require_day_unlock` true and `exec.auto_live_require_attended` true (false riskier), `exec.auto_live_attended_min` 10 (1..30, higher riskier). `auto_live_enabled` stays a column of `execution.settings`, OFF by default.
8. **The always-ask list** (`AlwaysAskList`) maps doc 19 §4's four items to their enforcement points, each with a pure probe of the rule itself; a test fails when an item has no point or a probe no longer holds.
9. **Grants.** xd_app: SELECT on the three tables and INSERT on `limits` (its sequence). xd_exec: SELECT on the three, INSERT on `ledger_entries` and `action_log` (their sequences), EXECUTE on `lock_account_ledger`. No UPDATE, DELETE or TRUNCATE; all three are insert-only by trigger.
10. **API.** `GET /api/execution/limits?accountId=` and `PUT /api/execution/limits/{accountId}` (session, CSRF, the sign-in rate limit; 400 `execution.values_invalid` naming the field, 400 `execution.password_required`, 401/423 from the step-up, 403 `execution.owner_only`, 404 `execution.account_unknown`, 409 `execution.disabled` for a raise while the Trading role is off, 409 `execution.stale` when the database refused the row).
11. **Log ids** 6720 reserved, 6721 refused, 6722 refused by the database, 6723 not auto (debug), 6724 reducing action, 6725 reducing action not taken, 6726 loss-cap halt, 6727 loss mark unavailable, 6728 limits changed, 6729 limits change refused. Short hashes and codes only; never a symbol, a P&L figure, the reason text or the password.

## Composed nowhere
`ReserveEntry`, `AutoActions`, `LossCapEvaluator`, `PgLimits` and `PgLedger` are registered by no host, nothing implements `IEntryHandOver` or `IReduceHandOver`, `IOwnerPresence` has only the closed default (the execution role has no grant on `auth.sessions` and this slice adds none, so nobody is ever attended), and no account can be `semi_auto` or `auto_live` (ADR 0163), so the ledger trigger refuses every row today. Nothing here can send an order.

## Deviations from the spec text
- The guard codes the spec leaves unnamed are `unlock.missing`, `readiness.not_ready`, `halt.active`, `cap.open_positions` and `cap.unavailable` (the ledger could not be read); the database adds `settings.stale`, `limits.stale`, `action_log.missing` and `ledger.missing`.
- The cap columns are nullable (unset allows nothing) so that the owner can store a partial sheet and the view can list what is missing; the spec's checks apply to every value that is set.
- `execution.disabled` (409) is used for a raise while the account's Trading role is off; a lowering is always allowed.
- `exit_all_on_loss_halt` switched OFF counts as a loosening (the halt then keeps positions); ON is a lowering.
- `action_log.id` is an identity column like every other table of the schema (the spec says bigserial; the behaviour is the same).
- The view adds `serverNow` (the database clock); the ceilings omit the order rate, which the API cannot read from the execution service's registry (it is P12-01's `exec.max_orders_per_second`, unchanged).

## Not built, owed
The screens (P12-10); composing the reservation into P12-01's intent handling with a sender; a source of the owner's presence (a grant decision on `auth.sessions` or a narrow SECURITY DEFINER read); the feed for the 15-second loss-cap evaluation; P11/P15 sources of the Soft checks, without which P12-03 reads them unavailable and `auto_live` clears nothing.

## Consequences
An entry without a tap can be sent only for an `auto_live` account with both switches ON, inside a complete sheet the owner chose at least one full session earlier, with every guard rule passing and the database proving the countable caps under a lock, and with its row written in the same transaction. Today nothing can be: no account can be `auto_live`, the sheet is empty and the path is composed nowhere.

## Known limits (review 2026-10-31)
- The global orders-a-day ceiling (`min(sheet, exec.max_orders_per_day)`), the loss cap, open positions and attendance are enforced in the application only; the ledger trigger enforces the sheet's own caps. A writer that bypasses the application would get the sheet's limit, not the stricter global one.
- The database floor for a raise (09:00 IST of the next calendar day) only backstops the application rule (next trading day after one full closed session), which governs.
- If a ledger commit succeeds on the server but its acknowledgement is lost, the result is a `ledger.unavailable` refusal while the row exists: it counts against the caps and nothing is sent (fail closed).
- The loss-cap latch is in memory and lost on restart, and is set only after the halt request succeeded; P12-05 must treat a repeated `loss_cap` request as idempotent.
- `IOwnerPresence` is the closed default (no grant on `auth.sessions` for `xd_exec`), so no owner is ever attended and entries are refused until the owner chooses a source: a grant or a narrow SECURITY DEFINER read.
