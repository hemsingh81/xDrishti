# 0022 — Portfolio Action center evaluated on read, and one-shot price alerts checked by the quotes service

- **Status:** Accepted (owner, 2026-10-13: "approved as written", after the review below) — builds on [ADR 0012](0012-holdings-acquisition-dates-and-returns-model.md) (lots, returns), [ADR 0018](0018-services-framework-and-editable-schedules.md) (services), [ADR 0019](0019-holdings-quotes-day-change-and-the-first-interval-service.md) (quotes), [ADR 0020](0020-portfolio-value-history-benchmark-and-charts.md) (benchmark flows, `platform.app_settings`) and [ADR 0021](0021-portfolio-grouping-and-allocation-charts.md) (sector/basket classification)
- **Date:** 2026-10-13

## Context
Design doc 15 §3 gives the Portfolio screen an **Action center** — holdings that need a decision, each with suggested actions (Open · Set alert · Add to basket · Snooze 7 days · Done) — and §4 **price alerts** (at or below / at or above a level, survive logout, create a notification and an audit entry). Doc 15 says a service evaluates the rules "every minute in market hours and after each sync". Today there is no live feed: prices arrive every 5 minutes from the quotes service (ADR 0019), holdings change at a sync, and the figures every rule needs (unrealised %, weight, sector share, lot ages, XIRR vs the index, basket membership) already have pure calculators or read ports.

## Decisions
1. **Rules are evaluated on read, not by a job.** `GET /api/portfolio/actions` computes the open items from the current holdings, lots, prices, sectors, baskets and benchmark with pure functions (one rule = one function over a read model), exactly like the summary and the groups; **only the owner's decisions are stored** (`portfolio.action_states`: rule, holding/account key, state `snoozed|done`, snoozed-until, who/when). There is no evaluation service to run, lag or fail, and the screen is always consistent with the numbers beside it. A bell notice ("N holdings need a decision") is derived on read like the data and service notices.
2. **Rules in this slice (seven):** *Below cost* (unrealised ≤ −10 %, high ≤ −20 %), *Large gain* (≥ +25 %), *Overweight* (weight in the account > max(15 %, 1.5 × equal-weight share), account has ≥ 3 positions), *Sector concentration* (one sector > 35 % of the account), *Long-term soon* (a profitable open lot becomes older than 12 months within 30 days; informational), *Lagging Nifty* (held > 180 days and XIRR more than 10 pp below the same cash flows in the benchmark, unavailable without benchmark bars), *Not in a basket*. **Not built:** *Results due* (no events data until P15) and *Max holding exceeded* (needs trading buckets and plans, P7). Thresholds are the defaults above, **editable** in Settings (stored as JSON in `platform.app_settings`, validated ranges, "Restore defaults"); items carry the numbers that triggered them.
3. **Decisions on items.** *Snooze* hides an item for 7 days (then it returns if still true). *Done* hides it **for as long as the condition holds**; when the condition stops holding the stored state is dropped, so the same rule can fire again later. *Open* opens the holding drawer, *Add to basket* uses the existing basket-members command, *Set alert* opens the alert dialog prefilled. Snooze, Done and re-open are audited.
4. **Price alerts are one-shot and checked on the quotes tick.** An alert is an instrument (master-list NSE instrument), a direction (`at_or_below` | `at_or_above`), a level (> 0), an optional note and a state (`active` → `triggered` | `cancelled`; never deleted — the app role has no DELETE). The `holdings-quotes` service (ADR 0019) quotes the **union of open holdings and active alert instruments** in the same request (still ≤ 1,000 per call), then, from the quote answer itself (no price is stored for non-held instruments), triggers every active alert whose condition holds: sets `triggered`, the trigger price and time, writes the audit event and the alert shows in the bell (derived on read, id per alert). Latency is therefore **up to one tick (5 minutes)** — doc 15's "every minute" needs the live feed (`xd-feed`, later); the screen says "checked every 5 min". An alert whose condition already holds at the last known price is refused on creation (`400`), at most 200 active alerts. Alerts survive logout and restarts (they are rows); the quotes service skips alert checks outside its window, like quotes.
5. **API** (session + CSRF for changes, no step-up): `GET /api/portfolio/actions?accountId&bucketId&status` (items, counts per rule/severity), `POST /api/portfolio/actions/{id}/snooze|done|reopen`, `GET/PUT /api/portfolio/action-thresholds` (+ reset), `GET /api/portfolio/alerts?status`, `POST /api/portfolio/alerts`, `POST /api/portfolio/alerts/{id}/cancel`. The item id is stable (`rule` + holding key) so a decision survives refreshes.
6. **Screen:** an **Action center** card on the Portfolio screen (grouped by severity, filterable by the existing account/bucket scope, collapsible, count in the header), an **Alerts** panel (drawer from the card and from the holding drawer: active/triggered lists, create, cancel), the thresholds card in Settings, and the bell entries. The per-account tiles of doc 12 §10 are **not** part of this slice (the Group by Account view covers the figures).

## Review before approval (2026-10-13)
Gaps found in the first draft and settled here (the decisions above stand):
- **"Dropping" a done decision needs an UPDATE, not a DELETE** (the app role has no DELETE grant): the states are `snoozed | done | cleared`; a `done` row whose condition no longer holds becomes `cleared` (treated as absent; a later decision on the same item writes it again). The reconciliation runs (1) after every quotes tick and every holdings sync, and (2) opportunistically inside `GET /api/portfolio/actions` when it finds a `done` row with no matching item — the one write a read makes, idempotent and owner-only, because outside market hours no tick runs and a lot edit could otherwise leave a stale `done`.
- **Item ids are path-safe:** `{rule}:{holdingId}` for holding rules and `{rule}:{accountId}:{first 12 hex of SHA-1 of the lower-cased sector}` for concentration (a sector name can contain any character); the sector name is in the item's numbers, not its id.
- **Alerts are for NSE shares and ETFs only** (the quote request is `NSE_EQ`; indices are a different segment and out of scope). "Last known price" for the already-true check is the holding's last price, else the last stored daily close of the instrument, else unknown (then creation is allowed and the next tick decides).
- **What an alert sees:** the last price of the tick, nothing in between (a spike between two ticks is not seen); `at_or_below` ⇒ last ≤ level, `at_or_above` ⇒ last ≥ level. The screen says so.
- **Notices endpoint:** `GET /api/portfolio/notices` returns both kinds (`price_alert_triggered`, `actions_need_decision`); the bell merges it like the data and service notices (query in `shared/api`).
- **Threshold ranges** are fixed in code (below-cost 1–90 %, high 2–95 % and greater than below-cost, gain 1–1000 %, overweight floor 1–100 %, multiple 1–10, minimum positions 2–50, concentration 5–100 %, lag 1–100 pp, lag days 30–3650, long-term window 1–365 days).
- **Audit event types** are added for snooze, done, reopen, thresholds changed, alert created, alert triggered and alert cancelled.
- **Lagging Nifty cost:** one bars read (the index) for all holdings plus one XIRR solve per holding and one for its benchmark — negligible for a few hundred holdings.
- **The 200-alert limit** is checked inside the creating transaction (a race between two creations is possible only with two sessions and costs at most one alert over the limit).

## Consequences
- No new job and no new failure mode: items are as fresh as the prices and the syncs; only alerts depend on the 5-minute tick, which is stated on screen.
- The quotes request grows by the alert instruments; the existing allow-list and throttle are unchanged.
- Decisions (snooze/done) are small rows keyed by rule and holding, so they survive re-imports as long as the holding key does; a closed holding's states are ignored.
- Doc 15 §3–§4 are updated: evaluation on read and on the quotes tick; "every minute" returns with the live feed.
- Results-due and max-holding rules, indicator/trailing alerts and push channels beyond the bell stay later.
