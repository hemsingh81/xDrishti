# 0177 — The expired-options backfill fetches rolling ATM-offset bars from one new allow-listed Data API endpoint at night, behind four gates, after an owner-run probe, with its own cap and no reader

- **Status:** Proposed (built in P14-03 from the owner-Approved spec, 2026-11-01, with the recommended answers). Becomes Accepted when the owner has run the probe, filled the "Probe" table below and accepted the result with `PUT /api/options/backfill/probe-acceptance`. A safety decision: one new broker endpoint, the Data account's token on a new HTTPS client, about 32,000 requests and up to 3 GB of disk.
- **Date:** 2026-11-01.
- **Relation to other ADRs:** follows [0133](0133-new-broker-endpoints-enter-the-allow-list-in-the-commit-of-the-slice-that-uses-them-index-and-vix-history-needs-none.md) (an allow-list row enters in the commit of the slice that uses it) and [0097](0097-the-p7-phase-check-ten-consecutive-scheduled-sessions-from-stored-plan-runs-and-never-met-on-fewer.md) (the pinned list changes in the same commit), copies the recorder pattern of [0176](0176-the-option-chain-recorder-stores-five-minute-index-chains-and-a-daily-stock-pass-from-two-new-allow-listed-data-api-endpoints-behind-three-gates-its-own-cap-and-no-reader.md), [0135](0135-the-depth-recorder-stores-the-20-level-book-of-up-to-50-shares-about-once-a-second-behind-three-gates-a-disk-guard-and-no-reader.md) and [0173](0173-the-trade-tick-recorder-stores-last-trade-updates-of-the-depth-set-when-cumulative-volume-rises-on-a-second-quote-socket-behind-three-gates-its-own-cap-and-no-reader.md) (a fresh-password switch, a disk guard that deletes nothing, no reader), uses the underlyings of [0175](0175-option-contracts-of-a-configured-underlying-list-are-kept-from-the-master-refresh-in-their-own-schema-with-a-dated-lot-history-and-dated-rule-epochs-never-in-the-master-list.md), and the fresh password of [0091](0091-auto-approval-is-an-option-behind-an-owner-setting-default-off-a-new-approval-kind-the-database-checks.md) and [0128](0128-owner-act-capabilities-are-one-insert-only-log-with-a-generic-gate-by-name-off-by-default-and-switched-on-only-by-the-owner-with-a-fresh-password.md). No order, no order-capable scope ([0083](0083-the-plan-record-insert-only-state-trails-owner-only-approvals-lapse-by-default-and-no-order-by-name.md)).

## Context
The live chain recorder of 0176 can only build history forward. Dhan's expired-options data API returns up to five years of candles for the *rolling* contract at an offset from the money (not for a fixed strike). P14-08 (re-marking positions) and P14-11 (a five-year IV history) need those candles. Every field of the endpoint is known only from Dhan's documentation of 2026-11-01, so the build ships a **probe** the owner runs first, and refuses to fetch until the owner has accepted its result.

## Decision
1. **One exact allow-list row, no wildcard.** `POST https://api.dhan.co/v2/charts/rollingoption` is one `Uri` constant in `BrokerEndpoints.Allowed`; no query (not even `?`), trailing slash, other case, host, port, scheme or method is allowed. `/v2/charts/historical` and `/v2/charts` stay refused. `PlanPhaseCheck.PinnedAllowList` gains `POST api.dhan.co/v2/charts/rollingoption` in ordinal order in the same commit; the `rollingoption` case moved from the refused list of `BrokerEndpointsTests` to the allowed list and the new refusal cases were added (GET/PUT/DELETE, a query, `?`, a fragment, a trailing slash, `/v2/charts/RollingOption`, `/v2/charts/rollingoption/1`, `..` segments, another host or port, `http`, user info). The allow-list guard (`ExecutionBoundaryArchitectureTests`) is strict again after this commit: it tolerates only an empty diff against HEAD or a diff whose added **and removed** lines are exactly the literal lists of this slice (a line added twice is not the list), and it is hardened as the known limits of 0176 asked: `git --no-pager -c color.ui=never diff --no-color --no-ext-diff -U0 HEAD -- file`, stdout and stderr both read, a 30-second timeout, and **a failure** when the checkout has a `.git` and git cannot start, exits non-zero or hangs (it no longer passes silently). The one removed line is the old P14-02 assertion that `rollingoption` is refused.
2. **One client, one throttle, nothing logged.** `DhanRollingOptionClient` sends with the Data account's token and client id (headers `access-token`, `client-id`) through the existing credentials port; no logger is injected, so no URL, token, client id or body can reach a log, and a reply carries only an outcome word, the HTTP status, a well-formed Dhan code and, for a success, the bytes for the job to read. `BackfillThrottle` (a singleton; with `ChainThrottle` it is the one `SpacingThrottle` with its own floor) makes any two requests of the process at least `1 / Options:Backfill:RequestsPerSecond` apart and never less than 500 ms (range 0.2 to 2 a second); a larger spacing asked for after a rate limit applies to the very next request. Body (UNVERIFIED, from the documentation): `exchangeSegment` `NSE_FNO`, `interval` as text (`"5"`, `"15"`), `securityId` as a number, `instrument` `OPTIDX`/`OPTSTK`, `expiryFlag` `WEEK`/`MONTH`, `expiryCode`, `strike` `ATM`, `ATM+3`, `ATM-3`, `drvOptionType` `CALL`/`PUT`, `requiredData` `open high low close volume strike oi iv spot`, `fromDate`, `toDate` as `yyyy-MM-dd` (not inclusive).
3. **What is asked (`BackfillPlanner`, pure).** In a fixed order (underlying, expiry flag and code, offset low to high, side `CE` then `PE`, window newest first): NIFTY at 5 minutes `WEEK` 1, `WEEK` 2, `MONTH` 1; BANKNIFTY `MONTH` 1, `MONTH` 2 and `WEEK` 1 only for windows that end on or before 2024-11-20; offsets -`IndexOffsets` to +`IndexOffsets` (10); the first `StockCount` (20) shares of the targets, which come ranked by turnover (the mean close x volume of the last 20 daily bars, as 0175) and **frozen**: the ranked symbols are stored once in the app setting `options.backfill_stocks` the first time all gates are open (the first write wins), so the plan does not move with the nightly ranking; at 15 minutes, `MONTH` 1, offsets -`StockOffsets` to +`StockOffsets` (3). Windows are 30 days each on a **fixed grid** (1 January 2020 + 30 k days), the newest ending on or before the first day of the current month, back to the first whose end is after `Years` (5) years before that day: **60 or 61 windows** (61 on 2026-11-01). The grid does not move with the date, so a new month only adds windows at the new end and the oldest fall off; a key that is done stays done. The request of the oldest window starts no earlier than five years back (the key keeps the grid's day). With the defaults, 20 shares and 61 windows: 14,364 index keys (the spec's 15,372 less the BANKNIFTY weekly cut: 1,554 of its 2,562 weekly keys remain) and 17,080 stock keys, **31,444 requests**, about 8.7 hours at one a second. The expiry codes (1 nearest is assumed) and the offset limits per code are UNVERIFIED and are set from the probe before the full run.
4. **Rows (`RollingBarParser`, pure, never throws).** `data.ce` or `data.pe` (the one that matches the request; the other must be null) with parallel arrays `timestamp, open, high, low, close, strike, spot` and, when sent, `volume, oi, iv`. Arrays of different lengths, a body that is not the documented shape or both sides present are `bad_body`; a null side or `data: null` is an empty window (zero bars). Prices and strikes become integer paise (half away from zero); a zero or negative close, or a strike that is not a multiple of the underlying's strike step, is kept with flag `suspect` (bit 0); a bar outside 09:15 to 15:30 India time is dropped and counted; a bar with an unusable value (null, not a number, outside the integer range) is dropped and counted, never zero-filled. `timestamp` is read as Unix seconds, or milliseconds from 13 digits (UNVERIFIED); `iv` is stored as sent (UNVERIFIED unit). **Strike step:** P14-01 stores none, so the step is a constant of the target resolution: NIFTY 50 rupees, BANKNIFTY 100 rupees; shares have none known and are not checked. Rows insert with `ON CONFLICT DO NOTHING` on `(ts, underlying_id, expiry_flag, expiry_code, atm_offset, side, interval_minutes)`.
5. **The fetch log is the resume point.** `options.fetch_log` has one row per attempt of a key (a series and a window): key, attempt number, started and ended, outcome (`ok`, `empty`, `no_data`, `rate_limited`, `timeout`, `server_error`, `bad_body`, `token_refused`, `not_subscribed`, `disk_stop`, `bad_request`, `store_failed`), HTTP status, Dhan code, bars kept, latency. The attempt row and its bars go in one transaction. A key is finished by `ok`, `empty` (an answer with no bar) or `no_data` (`DH-907`) and is never fetched again; a key with three failed attempts (`timeout`, `server_error`, `bad_body`) is **given up**, left and listed, and so is a key whose answer could not be stored three times (`store_failed`: an answer that can never be stored must not block the plan); a rate limit, a refused token, a missing plan, a disk stop and a `bad_request` are not the key's fault and do not count (a rate limit has the run-level breaker below). A failed attempt is tried again at once, up to three in all. A store that fails for one attempt is logged by type and counted as a gap (never as ok); a row with outcome `store_failed` and no bars is written if the store allows (if not, the request is counted in memory), so that the daily cap counts every request sent; the key stays open for the next night. **Run-level breakers** end the run with a reason instead of going on: three answers in a row that cannot be stored (`store_failed`, wait 5 minutes), five rate-limited answers in a row across keys (`rate_paused`, wait 15 minutes), five keys given up in a row (`too_many_failures`, ends the night), and `DH-905` (`bad_request`, the request itself is wrong, ends the night and is not an attempt of the key); `not_subscribed` and a finished plan also end the night. "The night" is keyed to the India date of the window's start (16:30), not to the date of the moment, because the window crosses midnight: an ended run does not start again at 00:00. The daily request cap stays per India day. The outcome-based exits (bad request, refused token, no plan, rate-limit pause) run before the store-failure handling, so such an answer that also cannot be stored does not go straight to the next key. **Reset of a given-up key (recorded, not implemented):** the fetch log is insert-only, so a later owner act will insert a `reset` row for the key and the resume query will count only failures after the newest reset. The unique index on (key, attempt) keeps one row per attempt.
6. **Failure handling.** `DH-904` or HTTP 429: a pause of 60 seconds and the spacing doubles for the rest of the **night** (up to 30 seconds), kept on the singleton job across runs and reset when the night (the India date of the window's start) changes; `DH-901`, 401, 403, 807, 809: `token_refused`, the run ends and nothing is sent until the token changes (a fingerprint of the credentials, never the token); `DH-902`, 806: `not_subscribed` ends the day; `DH-907`: `no_data`; `DH-905`: `bad_request`; 5xx, `DH-908`, `DH-909`, a network failure or an answer over 4 MB: `server_error`; a timeout (`TimeoutSeconds`, 15): `timeout`. No credentials at all: the run ends `no_token` and writes no row. The daily cap `MaxRequestsPerDay` (40,000) counts the requests of the India day from the fetch log (so a restart does not reset it) and ends the run `daily_cap`; the next India day goes on.
7. **Four gates, all default off, and an unreadable gate is a closed gate.** (a) the deployment flag `Options:Backfill:Enabled` (`Options__Backfill__Enabled`, compose `XD_OPTIONS_BACKFILL_ENABLED`, default false; a restart changes it); (b) the owner's stored switch, the newest row of `options.backfill_switch` (no row = OFF), changed by `PUT /api/options/backfill {enabled, reason, password}` with a **fresh password on every change, ON and OFF** (`OwnerAct`, no step-up window opened or used up), the actor taken from the session, one account event `OptionBackfillSwitched` (category `service`, detail `switch=<id> option_backfill=on|off`, never the reason), 401/423 from the password check and 400 `options.reason_invalid`; (c) the service `options-backfill`, **registered paused**, run by `xd-feed`, retries 0, no catch-up, notify on failure, "Run now" refused; (d) **the owner's acceptance of the probe result**, a row of `options.backfill_probe_ack` (no row = not accepted) written by `PUT /api/options/backfill/probe-acceptance {note, password}` (fresh password, actor from the session, event `OptionBackfillProbeAccepted`, detail `probe_ack=<id>`); this fourth gate is an addition to the spec's three (criterion 9 asked that the full run wait for the probe). With any gate closed or unreadable nothing reads the credentials, builds a request or sends (the supervisor's tests count credential reads at zero). `GET /api/options/backfill` returns the switch, its history, the acceptance, the progress (keys planned, done, empty, no data, given up, left, and the hours the left keys need at the current rate, counted in request time and not in nights) and the reasons it is not running; it returns no bar. The progress comes from the heartbeat the feed host writes (a plan against the fetch log, refreshed at most every five minutes and after a run).
8. **The night window.** The code (not the service schedule) runs the backfill only between **16:30 and 08:30 India time, every day**, end exclusive, so it never competes with the live feed, the chart reads and the chain recorder; the service's schedule is therefore "continuous" and the Services screen describes the window in words. A run that is open when 08:30 comes stops at the next key and the next night goes on where it stopped.
9. **Disk guard, its own cap plus the shared floor; the app deletes nothing.** Before each start and before every window (each fetch) `DepthDiskGuard.Check`: the stored size of `options.rolling_bars` above `Options:Backfill:MaxStoredGb` (3) ends the run `disk_budget` (a `disk_stop` row is written for the key it was about to fetch), free space below `Options:MinFreeGb` (20) ends it `disk_free`, a warning at 80 %. A disk stop holds until the backfill is next not wanted (the owner pauses the service, switches off, or the night ends) and the guard agrees at the next start. An unreadable free space leaves the size cap in force.
10. **Schema (migration `AddOptionBackfill`, raw SQL).** `options.rolling_bars` is a hypertable with 30-day chunks, compressed after 7 days (old chunks compress at the first policy run), segmented by `underlying_id, expiry_flag, expiry_code, side`, ordered by `atm_offset, ts`, **no retention policy**, no foreign key, checks on every coded column. **Deviations from the spec's column list:** the offset column is `atm_offset` (`OFFSET` is a reserved word); `volume` and `oi` are **nullable** (a field Dhan did not send is not a zero, as 0176 did for `oi`); `options.backfill_probe_ack` is a fourth table (decision 7d). `fetch_log`, `backfill_switch` and `backfill_probe_ack` are plain tables. `xd_app` is granted SELECT and INSERT table by table (`GrantTableToAppRole` then `MakeAppendOnlyForAppRole`); `xd_exec`, `xd_mcp_read` and `xd_mcp_sql` are granted nothing. `Down` drops the four tables.
11. **No trading use, no reader.** `IRollingBarStore` has no method that returns a bar (an architecture test lists its three methods); the fetch log is read only for the resume state and the daily count; only `RollingBarStore` names `options.rolling_bars` in SQL; no route returns bars; the Domain, `Simulation`, `Strategies*`, `Indicators`, `SimExport`, `SimReader`, `XDrishti.Execution` and the Application namespaces Planning, Learning, Portfolio, Execution, LiveTrading, Live, Selection, Research, Lab, Reporting, Paper, Depth, Ticks and OptionChain reference no backfill type, and the backfill code references none of the order, plan, live-session, chain or other recorder types; nothing in it is an active-set provider. With the backfill failing, no other service changes: it has its own loop, its own run record, its own heartbeat row (`xd-backfill`) and its own try/catch.
12. **Logs** `options.backfill.window|gap|given_up|disk_warning|disk_stop|token_refused|done` and the supervisor's (event ids 6941 to 6970) carry counts, ids and outcome words only; a test pins the range, the prefix and the absence of any secret, URL or symbol placeholder.
13. **The probe (owner-run, stores nothing).** `scripts/xd-probe-backfill.sh` runs `dotnet XDrishti.Feed.dll --probe-backfill` inside the running `xd-feed` container (it holds the vault key). It makes **at most five** requests: NIFTY `WEEK` 1 at ATM+10, NIFTY `WEEK` 2 at ATM+10, BANKNIFTY `WEEK` 1 in 2024-06 (at ATM, inside its weekly era), BANKNIFTY `WEEK` 1 in 2025-01 (after the weekly cut: empty or `DH-907`?), and the best-ranked share `MONTH` 1 at ATM+3, one window each, side `CE`, and prints what Dhan returned: outcome, HTTP status, Dhan code, the keys and array lengths, the first and last timestamp as sent, the first kept bar in India time, the strike against the spot, the IV range, the bars kept and dropped. It has no store (a test pins its constructor), prints no token, client id or URL, and does not depend on the deployment flag. The build and its tests made **no call to Dhan**; every shape above is UNVERIFIED until the table below is filled.

## Disk budget and requests
31,444 requests at one a second: **8.7 hours** (one night of the 16-hour window) and under the 40,000 daily cap. About 33 M rows at about 145 B raw each: **4.8 GB raw, about 1.0 GB compressed at the planning ratio of 5:1 (UNVERIFIED, 3:1 to 10:1)**. A night's uncompressed growth can reach the 3 GB cap before the compression policy runs; the guard then stops the run, which is resumable and expected (the owner resumes the service after the policy has run). Combined caps: depth 40, ticks 12, chain 4, backfill 3 = 59 GB plus the 20 GB floor = **79 GiB** free with everything on; the backfill alone needs 23 GiB; enlarging the VM disk to 160 GiB is the owner's act. `xd-backup` must exclude this table's data like the depth, tick and chain tables.

## Runbook (owner)
1. `scripts/xd-probe-backfill.sh`; read the output; fill the table below in this ADR; set the planner's offset limits (`IndexOffsets`, `StockOffsets`) from it.
2. `PUT /api/options/backfill/probe-acceptance` with `{note, password}`.
3. Check `podman machine ssh df -h /var` shows at least 23 GiB free; `export XD_OPTIONS_BACKFILL_ENABLED=true` and `deploy/xd-up.sh`.
4. `PUT /api/options/backfill` with `{enabled: true, reason, password}`; resume `options-backfill` on the Services screen. It runs from 16:30.
5. **Check:** `GET /api/options/backfill` (progress and any reason it is not running); the heartbeat row `xd-backfill`; Seq events `options.backfill.*` (6941-6970); `SELECT outcome, count(*) FROM options.fetch_log GROUP BY 1`; given-up keys: `SELECT ... FROM options.fetch_log GROUP BY key HAVING count(*) FILTER (WHERE outcome IN ('rate_limited','timeout','server_error','bad_body')) >= 3`.
6. **Switch off:** the same `PUT` with `enabled: false` and the password, or pause the service, or unset the flag and redeploy. **Stopped by the guard** (`disk_budget`, `disk_free`): free space or raise `MaxStoredGb`, then pause and resume the service.

## Consequences
- P14-04 reads `options.fetch_log` for coverage and the stitching checks; P14-08 and P14-11 read bars only through a reader slice of their own.
- "5 years back" slides: a month of delay loses the oldest month for good. Rolling series lose a held strike when the spot moves more than the offset window (P14-04 counts it). Index weekly history crosses the 2024-11-20 and 2025-09-01 rule changes; the epochs of P14-01 label them. No bid or ask exists in this data.
- The windows sit on a fixed grid, so the newest window may end up to 29 days before the first of the month; the plan gains one or two windows a month and loses the oldest, and the progress figures follow the plan.
- **Insert into compressed chunks:** every chunk of a five-year backfill is old, so the compression policy compresses it before later keys are written into it. Tested as `xd_app` (insert and select only) on the dedicated server: `INSERT ... ON CONFLICT DO NOTHING` into a compressed chunk works on this TimescaleDB, adds the new bars and skips the old ones, with no extra right. No decompression step is needed.

## Known limits (review, 2026-11-01)
- The acceptance row `options.backfill_probe_ack` is never stale, cannot be withdrawn, and is not tied to a particular probe result or to the offsets in force when it was written. A changed `IndexOffsets`, `StockOffsets` or plan after the acceptance is not re-checked; the owner's switch is the safety.
- A given-up key can only be fetched again after the later reset act described in decision 6; until then it is listed and left.
- The breakers use fixed numbers (3, 5, 5); only the settings of the table in doc 16 are configurable.
- **shortcut:** inserting into a compressed chunk decompresses the batches it touches; `timescaledb.max_tuples_decompressed_per_dml_transaction` (default 100,000) bounds that per statement, and one segment of a 30-day chunk is about 33,000 rows (a series' bars of one window group), so a statement stays far under it; the decompressed batches stay decompressed until the next compression policy run. A statement that did reach the limit would fail as a store failure (counted, then the key given up after three), never lose data.
- The ranked shares are frozen only when the ranking is complete (at least `min(StockCount, listed shares)` shares) and its newest daily bar is at most 7 days old (the freshness rule of P14-01); until then the plan follows the live ranking and nothing is frozen.
- The progress figures count the plan for today's date, so they can move by a window when a month starts.
