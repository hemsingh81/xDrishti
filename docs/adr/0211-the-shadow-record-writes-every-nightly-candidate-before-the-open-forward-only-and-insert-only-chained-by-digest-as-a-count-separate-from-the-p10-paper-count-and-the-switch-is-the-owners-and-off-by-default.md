# 0211 — The shadow record writes every nightly candidate before the open, forward-only and insert-only, chained by digest, as a count separate from the P10 paper count; the switch is the owner's and OFF by default

- **Status:** Proposed (built in CF-08 part A from the owner-Approved spec, 2026-11-03; the write side only, see "What is not built"). Becomes Accepted when the owner has read it. **Safety slice: yes (light)** (a new automatic writer; it starts paused, writes nothing until `paper.shadow.enabled` is ON, places no order, calls no broker, moves no ticket and changes nothing the plan or the P10 count reads).
- **Date:** 2026-11-05.
- **Relation to other ADRs:** extends the paper programme of [0116](0116-paper-fills-are-the-grading-replay-captured-per-armed-allocation.md) (P10-01; one replay path), [0119](0119-a-measurement-epoch-freezes-the-measured-configuration-changes-are-detected-classed-and-labelled-and-nothing-is-applied-or-blocked.md) (P10-05; the frozen fingerprint and epoch) and the plan record of [0083](0083-the-plan-record-insert-only-state-trails-owner-only-approvals-lapse-by-default-and-no-order-by-name.md) (P7-03; insert-only, the database clock stamps a decision); follows [0090](0090-grading-replays-each-ticket-through-the-simulator-on-its-own-session-and-stores-one-insert-only-grade.md) (one replay path, which part B reuses). It changes none of them. The grader, the summary and the switch endpoint are part B.

## Context
The P10 exit criterion counts only owner-approved, armed, primary, measured trades: about 43 to 58 in 12 weeks. A nightly plan holds many more candidates (primary, reserve, rejected by the fill) that the simulator could grade after the close, and which are evidence about the rules' edge, not about execution. To use them the record must be tamper-evident and free of hindsight: a candidate written after the open could have seen the outcome, and a selection rule that reads shadow outcomes of its own epoch would select on them.

## Decision
1. **A separate record, `paper.shadow_*`.** `shadow_entries` (one row per candidate), `shadow_sessions` (one row per session of a chain: `ok` or `gap`), `shadow_grades` (table and guards now, writer in part B) and `shadow_settings` (the switch, a fourth table the spec did not list: "an append-only audited row" needs a place). The runtime role has SELECT and INSERT only on all four (table-by-table `GrantTableToAppRole` and `MakeAppendOnlyForAppRole`; `PlanGrantsTests` lists the paper tables). A grade is its own row; a graded row is never rewritten (unique on `entry_id`).
2. **Every candidate, once, from the stored plan.** `WriteShadowHandler` takes the newest non-draft plan of a session that has not opened and turns every plan item of any group into a row with `counts_for_edge`. Levels (entry reference, stop, target) and the time rule are the plan item's stored values, or null; nothing is recomputed. The trade key is the simulator's `StrategyId|Symbol|Side|DecisionDate` (`SimTrade.Key`), built before the session: the decision day is the day before for a daily or longer timeframe and the session itself otherwise (the replayer's own rule, `TicketReplayer.IsDaily` and `Before`, now shared), so a shadow row and a paper entry of one ticket join. A candidate whose key an earlier one of the session has is left out, primary first, then reserve, then rejected, each by rank (unique on `(session_date, trade_key)`), and counted in the outcome.
3. **Which items count for edge (UNVERIFIED in the spec, resolved by reading `SelectionPlanBuilder`).** The plan record does store the held and not-eligible candidates and the candidates dropped in the merge (including `merged_duplicate` and the conflict codes) as `Rejected` items with reason codes, and marks every item that never reached the smart rules and the fill with the unavailable marker `smart_rules` (now the constant `SelectionPlanBuilder.SmartRulesNotRun`). Those items are recorded with `counts_for_edge = false`; primary, reserve and fill-rejected items count. This is slightly wider than the spec's two named cases (it also sets aside `conflict_*` drops, which never became candidates either); the owner can widen it by changing one predicate (`ShadowPlanFacts.CountsForEdge`).
4. **What the plan does not hold is null, never a guess (review fix 3).** The plan record has no feature vector and no model id (UNVERIFIED in the spec, resolved: it has neither), so `features`, `feature_version` and `model_id` are null in part A, and those rows are excluded from CF-10 and CF-12 scoring. `p_win` is read from the item's stored advisory note (`model P(win) 0.712, advisory only`, three decimals, the builder's own words) by one strict pattern, else null. `config_hash` is the newest full configuration snapshot (ADR 0119) and `edge_epoch` the paper epoch in force, both read without creating them; with none stored they are null. The row hash is the SHA-256 of the canonical JSON (fixed field order, four-decimal levels, numbers as invariant round-trip text, feature keys in ordinal order) and includes the plan id (review fix 2); the database id and `written_at` are not in it, since the database stamps the second after the hash.
5. **Forward-only, stamped by the database, before 09:00 India time (review fix 1).** `written_at` is set by a `BEFORE INSERT` trigger from one function, `paper.shadow_now()` (`clock_timestamp()`), so a direct insert cannot name its own time; only the migration role can replace the function (the tests replace it to fix the clock, the runtime role cannot). The entry trigger refuses a row whose `written_at` is at or after 09:00 India time (03:30 UTC) of its `session_date`, which covers "the session is today or earlier" because every later instant of an earlier session is past its cut-off; refuses a row older than its plan (`trading.plans.created_at`, see "Limits"); a row for a date other than its plan's; and a row whose session is not `ok`. The session trigger applies the same cut-off to an `ok` session and requires a `gap` to be a session that has opened. The application does the same arithmetic first (`ShadowCutoff`), so the database is the backstop and not the usual refusal. The cut-off is 09:00, before arming (09:10) and the open (09:15).
6. **Gaps, never back-filled.** A run records, for each trading session after the newest stored one that has opened, a `gap` row; a run asked for a past session writes no entry and, if the session is after the newest, a gap. An earlier session than the newest is never added. A first run has no history to be a gap in. The store port has no member that adds a row to an existing session (an architecture test pins its three members: head, read chain, write a whole session).
7. **Chained digests.** A session's digest is the SHA-256 of `previous|hash1,hash2,...` with the row hashes in ordinal order; a gap has no hashes. The session trigger requires a new session to be later than the newest and to carry the newest digest as its previous (under an advisory lock, so two writers cannot both link to the same head). `ShadowDigest.FirstBroken` recomputes the row hashes from the stored columns and the digests from those, and names the first session that does not match; a changed column, a deleted or inserted row and a removed session are all found, and so are changes made as the owner role (the test does that). The database owner can still rewrite a whole chain consistently; the weekly export of the last digest to the Reports export and to a file outside the database (review fix 4) and `xd paper shadow verify` are part B.
8. **The switch.** `paper.shadow.enabled` is the newest row of `paper.shadow_settings` (owner actor, a reason, database-stamped time; no row is OFF). With it OFF the handler reads nothing and writes nothing. The service `shadow-write` (daily 19:00, after the nightly plan at 18:30; paused until the owner enables it) is registered like the other automatic writers. The owner act that appends a row (fresh password, CSRF, audited) is part B.
9. **Edge count and wording.** `EdgeCount` (pure) is its own type: raw n, and an effective n per day as graded trades over the design effect `1 + (m - 1) * rho`, `m` the day's candidates, a day with none contributing nothing; rho is the placeholder 0.3 until CF-01 and says so. Hand numbers are unit tests: 240 trades at 6 a session is 96.0, 100 at 5 is 45.45, one a day is n, 60 effective take 25 sessions at 2.4 a session against 40 for 60 armed trades at 1.5. `ShadowWording` holds the fixed sentences ("modelled fills; no queue, no latency").
10. **No selection on shadow outcomes (criterion 7, review fix 5).** `IShadowResultReader` is a port only in part A, named by no use case. Architecture tests: no type of `Domain.Selection`, `Domain.Planning`, `Domain.Autonomy` or `Application.Planning`, `Selection`, `Autonomy` names a shadow namespace or the reader; `Domain.Paper` and `Application.Paper` (the counting types) name no shadow type; only `WriteShadowHandler` names `IShadowStore`. `IMlInfluenceGate` (review fix 5) does not exist in the code yet, so its rule cannot be written; it belongs to P12.
11. **Logs and security.** One count-only event per run (ids 5400 and 5401); an architecture test pins that the shadow log methods take only a logger and integers. No level, feature, symbol or strategy text is logged; no secret is involved.

## What is not built
- **Part B:** the grader (`GradeShadowHandler`, `ShadowGradeService`, same replay path as paper), `GetShadowSummaryHandler` and `GET /api/paper/shadow/summary`, the switch endpoint `PUT /api/paper/shadow/settings`, the verb `xd paper shadow verify|summary`, the weekly digest export, the `IShadowResultReader` implementation, and the Shadow tab of `/paper`.
- **Features, the champion model id and the feature version** in a row, until the plan record holds them.
- **Candidates the plan does not store:** none are known to be missing; if the pre-plan list ever holds more than the plan stores, they are not recorded.

## Limits
- **The plan's stored-at is the builder's clock.** `trading.plans` has no database-stamped column; `created_at` is the time the builder supplied. The "not older than its plan" guard is therefore a sanity check against a row that predates its plan, not a hardening against a writer that lies about the plan time. Adding a database-stamped column to the plan record is a change to the plan table and was left out.
- **The database owner can update or delete.** The tables are insert-only for the runtime role by grants (as `lab.test_ledger` and `workflow.approvals`), not by triggers, because the chain test and the reset of the integration database run as the owner. The chain digest and its copy outside the database (part B) are what makes an owner rewrite visible.
- **A session with a skeleton or empty plan is an `ok` session with no rows** and is not written again if a later plan version for it arrives: the first plan seen before the open is the one shadowed.
- **The fills are modelled** (touch is fill, no queue, no latency); the record is about the rules' edge and says so.

## Open owner questions
1. Is setting aside the `conflict_*` drops (not only `merged_duplicate`, held and not-eligible) right? 2. Switch `paper.shadow.enabled` on once part B can grade, or now? 3. Is a database-stamped column on `trading.plans` worth a migration of the plan table to harden the plan-time guard?

## Consequences
A new insert-only record and one paused service; nothing the plan, the tickets, the paper capture or the P10 count reads changes (a test compares the P10 reads byte for byte with and without shadow rows). With the switch OFF, which is the default, nothing is written and the only cost is one setting read per run.
