# 0126 — The P8 phase check reads three witnesses and is never MET on what it could not read

- **Status:** Proposed (spec [P8-17](../specs/P8-17-the-phase-check.md), built 2026-10-26; the spec is still Draft). Becomes Accepted when the owner has read it and recorded the stopwatch note below.
- **Date:** 2026-10-26.
- **Relation to other ADRs:** [0097](0097-the-p7-phase-check-ten-consecutive-scheduled-sessions-from-stored-plan-runs-and-never-met-on-fewer.md) and [0123](0123-the-paper-phase-check-judges-the-p10-exit-from-stored-records-with-its-caveats-in-the-label-and-reads-only.md) (the pattern: three outcomes, caveat in the label, limits always printed), [0080](0080-the-phase-check-exit-criteria-from-stored-records-and-never-met-on-thin-data.md) (supplied, never verified), [0100](0100-the-report-endpoints-read-the-stored-runs-through-one-query-model-with-an-evidence-block-and-net-only-by-the-owners-stored-confirmation.md)-era report endpoints (P8-06), [0103](0103-the-p6-phase-check-is-also-a-read-only-get-with-no-client-supplied-replay-time-and-plan-versus-actual-is-a-server-read.md) (the 4-interaction path).

## Decision
1. **Three witnesses, because each sees what the others cannot.** A test sees interaction counts on fixtures; the server sees the stored runs and real timings; only the owner's stopwatch measures "an answer in two minutes" as a person. The API container mounts no `data/`, so the bundle, the browser pass, the interaction result and the stopwatch note are read by a host script from files, never guessed by the server.
2. **Server check.** `GET /api/reports/phase-check` and `xd reports phase-check` (exit 0 whatever the verdicts): the pure `Domain/Reporting/ReportsPhaseCheck` over `ReportsPhaseFacts`; `EvaluateReportsPhaseCheckHandler` calls the nine built report handlers in process on the default set, each twice (cold, warm; the repeat is also the determinism probe), single-flight. Criteria 1 to 10 are numbered as in P8-00, each MET, NOT MET or NOT EVALUABLE with a detail line; a MET on a convention carries its caveat. The server passes the interaction result, the stopwatch and the bundle/browser files as null, so criteria 1, 7 and 8 are NOT EVALUABLE there, by construction.
3. **MET only on real evidence.** No stored run: criteria 1, 2, 3 and 9 are NOT EVALUABLE ("no stored run"); the overlap and mixed-basis probes (criterion 4) and the route scan (criterion 5) still run. A report that refuses to load is unread (NOT EVALUABLE), never evidence. A figure that breaks the state rule (a number outside value/provisional, a NaN, a missing reason) is NOT MET with its path. Criteria 6 and 10 are always NOT EVALUABLE here, naming the test or process that proves them.
4. **Read-only is checked on the route table.** `IEndpointCatalogue` (Application port, `NoEndpointCatalogue` default for the command-line host, `EndpointCatalogue` over `EndpointDataSource` in the API) lists every route under `/api/reports`, `/api/learning`, `/api/cells`, `/api/plans/notices`, `/api/changelog`, `/api/lessons`, `/api/hypotheses`, `/api/experiments`, `/api/exports`; a non-GET not on `ApprovedReportWrites` (empty; P8-18/19/20 extend it by commit) is NOT MET. The command-line host has no route table, so the local summary reads the committed OpenAPI contract for the same rule and says so.
5. **Interaction budget.** `src/features/reports/phase/whatWorksPath.test.tsx` walks the P8-08 path (click Reports, open Baskets, pick, Escape) with `countingUser` (`src/test/interactions.ts`) and fails above 4; the requests are matched to `backend/contracts/what-works-path.json` by operation id against the OpenAPI contract; a fifth interaction is a positive control. The backend timing test (`ReportsPhaseCheckApiTests`) reads the same manifest: p95 under 1 s over 20 calls after a warm-up on the seeded fixture; real-data times are reported, not asserted.
6. **The stopwatch is the owner's act, supplied, never verified.** `node frontend/scripts/p8-evidence.mjs stopwatch --seconds .. --interactions .. --basket .. --answer RANKED|NOTHING --date YYYY-MM-DD` records the owner's typed numbers with the commit into `data/p8-evidence/stopwatch.json`; it refuses missing or odd input and invents nothing. Three trials, each at most 120 s and 4 interactions, are needed; a trial over either limit is NOT MET. Procedure (the owner's): after the P8-16 pass, on the stack built from the commit under test, decide the basket first, a new tab, start the stopwatch on Enter at `http://127.0.0.1:8080/reports` (first trial after a hard reload), stop when the answer can be said aloud using only what is on screen ("In basket B, strategy S, timeframe T, exit E: lower bound x R, n = N" or "Nothing has enough evidence yet: the largest sample is N of M needed"); count your own interactions; three trials; do not rehearse and call it cold.
7. **Local summary.** `scripts/p8-phase-check.sh` runs the verb, runs the interaction test (recorded for this commit), and `p8-evidence.mjs summary` merges the server criteria with `bundle.json` (written by `npm run size` when `XD_EVIDENCE_DIR` is set; `scripts/check.sh` sets it), `browser-checklist.jsonl` (P8-16 format), `interaction.json` and `stopwatch.json`. Evidence recorded at another commit is accepted when `git diff --quiet <recorded> HEAD -- backend frontend` is clean, else stale (NOT EVALUABLE, "run again"); an absent file is NOT EVALUABLE. The rules live in `p8EvidenceCore.mjs`, tested by hand tables.
8. **Headline.** `P8 exit: MET` only when criteria 1 to 5, 7 and 8 are MET and none of the ten is NOT MET; any NOT MET is `NOT MET`; any gap among the seven is `NOT EVALUABLE (n of 7 need evidence)`; a report missing or repeating a counted criterion is `NOT EVALUABLE, malformed report`. No composite score.
9. Log ids 5255 (evaluated, counts and ms) and 5256 (a report could not be read). No migration, nothing stored.

## Consequences
- On the owner's machine today the headline is NOT EVALUABLE until the stopwatch note, the P8-16 pass and a run on real data exist; that is correct.
- **Deviations from the spec, for the owner:** (a) the spec says "n of 8" for the open count; the counted criteria are seven (1 to 5, 7, 8), so the code prints "of 7". (b) The spec's manifest names `GetReportRuns`; the built operation id is `ListReportRuns`, and the filter parameter is `basket` (not `baskets`). (c) Acceptance 2 asks for at most 12 page requests; the built Reports page makes 21 from the cold start to the picked basket (ten panels, then the same ten with the basket filter). The test ratchets the measured 21 exactly; bringing the page to 12 is roadmap row P8-17f, not done here. The browser checklist (criterion 8) needs a line for every screen listed in the committed `frontend/scripts/p8-built-screens.json`; a record counts only while `backend/` and `frontend/` have no uncommitted change. (d) Lazy per-route budgets are not measured by `npm run size`, so criterion 7 carries the caveat "only the guarded first load is measured".
- **Owner's stopwatch note (to be added):** date, commit, three trials (seconds and interactions), basket, answer kind. Not recorded: no stopwatch result is invented here.
- Not verified: the run on the owner's stored runs (about 2.1 years of data, an answer of "nothing has enough evidence yet" is expected); the cost of 18 report loads on a 500,000-trade population (single-flight, gated like the screens, owner-invoked only).
