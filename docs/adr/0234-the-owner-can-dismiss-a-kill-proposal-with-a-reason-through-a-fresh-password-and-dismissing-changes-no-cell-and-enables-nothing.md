# 0234 — The owner can dismiss a kill proposal with a reason through a fresh password; dismissing changes no cell and enables nothing

- **Status:** Proposed (approved by delegation, 2026-11-09). Becomes Accepted when the owner has read it. **Safety slice: no change to risk.** Dismissing leaves every cell exactly as it is, so it neither lowers nor raises risk. No order is placed or touched anywhere.
- **Date:** 2026-11-09.
- **Relation to other ADRs:** closes the open item of [0219](0219-a-firing-kill-rule-writes-a-proposal-and-a-notice-the-owner-or-an-automatic-setting-that-is-off-by-default-pauses-the-cells-only-the-owner-with-a-fresh-password-ever-re-enables.md) ("no route to dismiss a proposal"; the state `dismissed` existed in the table and nothing set it). It uses the owner-act mechanism of 0219 and [0212](0212-the-shadow-record-is-graded-after-the-close-through-the-one-replay-path-summarised-as-raw-and-effective-n-labelled-gross-unless-the-sheet-is-confirmed-and-switched-by-the-owner-with-a-fresh-password.md).

## Context
A kill proposal stays open until it is applied. An owner who has read it and judged it a false alarm had no way to say so: the bell kept showing it and the Decay tab kept offering it. The frontend owner-act UI needs the verb.

## Decision
1. **`POST /api/confidence/kill-proposals/{id}/dismiss`**, body `{ "reason": string, "password": string }`. A session, the CSRF token and **a fresh password for this act** (the same mechanism and rate limit as the kill switch and the re-enable). The actor is built from the session, never from a body. The password is required although dismissing lowers no risk, because it is a decision of the owner that closes an alarm; a stolen session alone must not be able to silence a kill proposal.
2. **One conditional update** moves the proposal `proposed -> dismissed` and records the owner, the time (database clock) and the reason (1 to 400 characters, trimmed). The first dismissal stands: dismissing again is a success with `alreadyDismissed: true` and the first actor and reason, and changes nothing. A concurrent loser reads the stored outcome.
3. **It changes nothing else.** `DismissKillHandler` has no dependency on the lifecycle, the changelog, the pause or re-enable handlers or the automatic setting (an architecture pin lists its dependencies). No cell is paused, re-enabled or touched; no switch is read or written. A dismissed proposal is closed: applying it is 409 `confidence.proposal_closed` (existing), and an applied proposal cannot be dismissed (409 `confidence.proposal_applied`). The daily evaluation may write a new proposal on a later day if the rule still fires (one per strategy, rule and day, unchanged).
4. **Storage (`AddKillDismissReason`).** One nullable column `dismiss_reason varchar(400)` on `confidence.kill_proposals`, a column grant of UPDATE on it to the runtime role (the other grants are unchanged: no DELETE, INSERT still excludes every decision column), and a check that ties it to the state (`(state = 'dismissed') = (dismiss_reason IS NOT NULL)` and not blank). The existing check already forbids `auto` from deciding anything but `applied`, so an automatic dismissal is refused by the database. Raw SQL, no EF entity, the model snapshot is unchanged. Down drops the check and the column.
5. **Read.** `GET /api/confidence/kill-proposals` items gain `dismissReason` (null unless dismissed). The existing apply, re-enable and kill-settings routes and the list already carry what a screen needs (proposal numbers, cells, state, actor, decided time, the switch and thresholds), so no other field was added.

6. **A dismissed proposal still counts as the last firing** of its rule: the decay report reads the newest proposal of the rule in any state (`LatestAsync`), so the 20-new-trades wait before the rule may fire again applies after a dismissal too.
7. **Apply racing a dismissal.** Apply pauses first and then compare-and-sets. If the owner dismisses in between, the proposal stays `dismissed`, the paused cells stay paused (the safe direction) and apply answers 409 `confidence.proposal_dismissed_during_apply` naming them; it is never reported as applied (the automatic run counts it as failed).
8. **Pre-deploy check:** the check constraint needs existing rows to agree; before deploying run `SELECT count(*) FROM confidence.kill_proposals WHERE state='dismissed'` (expected 0: nothing could set that state before this change), else the migration fails on those rows.

## Refusals (the frontend contract)
403 `auth.step_up_required` (no password), 401 `auth.invalid_credentials` (wrong), 423 `auth.locked`, 429 `auth.rate_limited`, 403 `auth.csrf_invalid`, 401 (no session), 400 `confidence.reason_invalid`, 404 `confidence.proposal_not_found`, 409 `confidence.proposal_applied`, 409 `confidence.decision_refused` (the record refused it; nothing changed). On apply: 409 `confidence.proposal_dismissed_during_apply`.

## Consequences
The bell notice is derived from open proposals, so a dismissed proposal leaves it. The next day's run may propose again. Tests: unit (owner, reason, idempotent, no cell change, apply after dismiss), integration (401, CSRF, step-up, 400, 404, 409, double dismiss, the database checks).
