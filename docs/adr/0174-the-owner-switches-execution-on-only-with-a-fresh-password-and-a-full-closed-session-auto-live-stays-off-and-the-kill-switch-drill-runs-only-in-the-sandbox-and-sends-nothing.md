# 0174 — The owner switches execution on only with a fresh password and a full closed session, auto_live stays off, and the kill-switch drill runs only in the sandbox and sends nothing

- **Status:** Proposed (built from the Approved specs P12-05, P12-07 and P12-10, which deferred these two items for lack of an endpoint, 2026-11-01). Becomes Accepted when the owner has read it. **SAFETY decision: the first write route to the global execution switch, and the first composition of the drill.**
- **Date:** 2026-11-01.
- **Relation to other ADRs:** [0161](0161-the-kill-switch-is-an-insert-only-halt-record-that-only-ever-makes-the-system-stricter-ended-only-by-the-owner-or-by-a-named-automatic-clear-and-composed-nowhere-that-can-send.md) (the drill service, until now composed nowhere), [0163](0163-an-account-moves-up-the-mode-ladder-one-step-on-stored-evidence-by-an-owner-act-with-a-cooling-off-and-down-at-any-time-and-no-mode-built-here-can-send.md) (the mode source stays closed; only `assisted` is storable), [0167](0167-auto-live-sends-only-inside-an-owner-chosen-limits-sheet-that-the-database-proves-for-every-entry-an-empty-sheet-allows-nothing-and-no-action-happens-without-its-row.md) (the raise timing reused), [0168](0168-the-execution-screens-read-model-is-get-only-derived-from-insert-only-rows-and-says-unavailable-rather-than-zero.md), [0091](0091-auto-approval-is-an-option-behind-an-owner-setting-default-off-a-new-approval-kind-the-database-checks.md).

## Context
P12-07 criterion 13 (`GET/PUT /api/execution/settings`) and P12-05 criterion 10 (`POST/GET /api/execution/drills`) were not built: no write route to `execution.settings` existed, so `execution_enabled` read OFF forever, and the drill had no protection snapshot in any host. P12-10 (criteria 7 and 9) deferred the matching controls. Four database checks and four readers took the newest settings row regardless of its `effective_from`, so a raise waiting for its cooling-off would have been read at once.

## Decision
1. **Settings writes, the two switches only.** `PUT /api/execution/settings {executionEnabled, autoLiveEnabled, reason, password}`. Session, CSRF, the actor from the session, a reason of 1 to 300 characters and a **fresh password on every change** (stricter than the spec, which asks it only for a raise). Switching `execution_enabled` from OFF (in force) to ON is a raise: the `Live:Writes:Enabled` gate is asked before the password, and it takes effect at 09:00 India time of the next trading day after one full closed session. OFF (or ON while ON is in force) is in force at once; an OFF row supersedes a raise still waiting. The `values` object is carried over unchanged by the database; no key of it can be changed here.
2. **`auto_live_enabled` stays OFF.** `autoLiveEnabled: true` is 409 `execution.auto_live_locked` before anything else, the store writes the column as the literal `false`, and the trigger refuses an ON row from every role but the table owner. Turning it on later needs a new decision and a migration.
3. **Database.** Migration `AddExecutionSwitchWrites`: `xd_app` gains INSERT on `execution.settings` (and its sequence); `xd_exec` still has SELECT only. Trigger `execution.check_settings` (every role but the table owner, i.e. migrations and fixtures, who own the trigger anyway), with `search_path` pinned to `pg_catalog, pg_temp` and every catalog name qualified, so a temporary table named like a catalog cannot make the runtime role look like the owner: one advisory lock, then the row's id drawn (id order is commit order), `changed_at` from the database clock, auto_live refused, owner actor and reason, values carried over, an early raise refused (not before 09:00 India time of the next calendar day), anything else stamped in force at once, SHA-256 snapshot hash stamped. A CHECK `ck_exec_settings_auto_live_off` keeps `auto_live_enabled` OFF for every role including the owner; the decision that allows auto_live drops it. UPDATE, DELETE and TRUNCATE refused for every role. The four checks that read the switch (`check_promotion_request`, `check_mode_trail`, `check_ticket_outcome`, `check_ledger_entry`) are rewritten from their catalog text, one phrase each, to read the row in force; the migration fails if the phrase is missing. `check_limits` and `check_mode_trail` drew their id before their per-account lock; they now draw it after the lock, the same way. Every trigger that judges a row against a row read after its lock (`check_settings`, `check_limits`, `check_mode_trail`, `check_ledger_entry`) refuses (23514 `execution.isolation_refused`) unless the transaction is READ COMMITTED: at REPEATABLE READ or SERIALIZABLE the read after the lock would use the transaction's first snapshot, so a writer could, for example, switch execution back ON against a stale ON row with no cooling-off. No code of ours uses another isolation level. The three rewritten functions have their `search_path` pinned to `pg_catalog, pg_temp` and their new calls qualified with `pg_catalog.`. The readers in `xd-api` and `xd-exec` read the row in force too. Down first writes an OFF row as the owner when a switch-on is still waiting, because after Down the readers take the newest row whatever its time (fail closed).
4. **The drill.** `POST /api/execution/drills {accountId, password}` (session, CSRF, fresh password) refuses 404 for an unknown account and 409 `execution.drill_refused` while any halt is in force; otherwise it leaves a `drill` command row with an empty payload and an audit event. `xd-exec` answers it with `DrillRunner`, registered **only** in the sandbox send composition (environment `sandbox` AND `Execution:SendEnabled`); everywhere else the command is answered `refused` / `execution.drill_unavailable`. The runner judges flatness on the sandbox order book and positions read now (GET only) plus our own record; an unreadable side is never flat (`refused:no_snapshot`), any non-zero broker position, working order, or intent not in the final set of the API's open-intent count (rejected, cancelled, failed, reconciled; so planned and closed count) is `not_flat`. The drill itself is P12-05's: a cancel halt of its own, an entry sent through a sender whose transport refuses everything, the permission table checked, its halt cleared in a `finally` that covers every step after the halt is raised, a row in `execution.drills`. `GET /api/execution/drills` lists the drills and the latest 20 requests with their answers.
5. **Audit.** Account events `ExecutionSettingsChanged` (category autonomy) and `ExecutionDrillRequested` (category service); log ids 6780 to 6784 (ids and codes only, never the reason text).

## Consequences
- Nothing here can send an order, store `semi_auto` or `auto_live`, or open the mode source. Switching execution on opens only the `execution switch` fact of the `manual_live` → `assisted` gate, whose sandbox-suite fact still has no source.
- In the owner's deployment (environment `none`) a drill is answered `execution.drill_unavailable`: the drill evidence the ladder needs exists only after a sandbox run.
- The rules of the settings trigger do not bind the table owner (`xd_owner`); that role can switch any trigger off, so the control is the runtime role.
- If the drill's own clear (`AutoClearAsync`) throws, the drill's `cancel` halt stays active: it fails closed (no new entries, no drill row) and the owner releases it by hand.
- **Shortcut:** the database floor for switching execution on is 09:00 India time of the next calendar day; the API asks for the stricter next trading day after one full closed session, which the database has no calendar to prove. Upgrade: a trading-days table readable by the trigger.
- `TEMPORARY` is still granted to `PUBLIC` on the database (`deploy/db/init/10-roles.sh` unchanged): revoking it was not shown safe for every role and fixture, and the pinned search path closes the shadowing route for this trigger. A test fails if any function of schema `execution` names a catalog relation without the pin and the `pg_catalog.` prefix; today only `check_settings` names one.

## Not built (owner decisions)
- Editing the `values` keys (needs a risk direction for every key; most have none in `ExecSettingRegistry`, and the registry is not visible to `xd-api`).
- Turning `auto_live_enabled` on by any route.
- A drill in environment `none` judged from our own record only, or a drill against the live broker (refused by design).
- Review (third pass, 2026-11-01): the READ COMMITTED guard of `check_ledger_entry` is proved by the structural test only, not by a behavioural insert at REPEATABLE READ; and no test runs the migration's Down (the exact text restore and the order of RESET against the reverse rewrites are correct by reading). Both are owed as tests.
