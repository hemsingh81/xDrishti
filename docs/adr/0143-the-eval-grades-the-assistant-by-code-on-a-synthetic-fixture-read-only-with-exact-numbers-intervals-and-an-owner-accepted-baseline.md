# 0143 — The eval grades the assistant by code on a synthetic fixture read through a separate read-only tool endpoint, with exact numbers, honest intervals and a baseline only the owner accepts

- **Status:** Proposed (written in P9-09 under the owner's delegation; the spec was treated as Approved). Becomes Accepted when the owner has read it. **SAFETY decision: it decides what a model run may touch (fixture data only) and who may call a run accepted (the owner).**
- **Date:** 2026-10-27.
- **Relation to other ADRs:** [0005](0005-local-llm-runtime-and-models.md) (the model is configuration, chosen by this eval), [0136](0136-the-local-model-server-runs-in-a-container-on-the-gpu-the-pick-is-qwen3-30b-a3b-with-the-thinking-mode-off-gpt-oss-20b-is-the-alternate.md) (model and mode), [0137](0137-the-assistants-tools-run-in-a-separate-read-only-mcp-service-on-views-and-two-database-roles.md) (the tool endpoint and roles), [0138](0138-the-assistant-endpoint-runs-the-tool-loop-in-the-application-streams-events-marks-figures-not-found-in-the-tool-results-and-stores-every-turn-insert-only.md) (ground only against tool results), [0140](0140-the-briefing-text-is-phrased-by-the-model-from-app-built-facts-and-a-deterministic-guard-rejects-any-figure-symbol-or-claim-it-cannot-verify-the-fixed-format-text-is-the-fallback.md) (the text guard), [0141](0141-a-strategy-draft-is-text-the-model-wrote-for-the-owner-to-read-the-lab-validator-and-four-checks-decide-if-it-is-offered-and-only-the-owners-confirm-with-a-switch-and-a-fresh-password-stores-a-version-or-starts-a-quick-test.md) (the draft pipeline).

## Context
"The assistant is good enough" must be a recorded fact with numbers, not a feeling, and it must be re-checked whenever the model, the runtime or a prompt changes. The questions need known answers; the owner's stores are small and change daily. A model run must never touch the owner's data or any switch.

## Decision
1. **A synthetic fixture with hand-worked answers.** `eval/fixture/fixture.json` (fake symbols EVA..EVH2, two runs of 24 and 16 trades, one plan, two holdings, one cell, learning rows) is the whole world of the eval. Its SHA-256 is the `fixture_hash`. The 30 data questions and their expected values (exact fractions, rounded only when grading) are checked in under `eval/sets/`. A model-free test feeds the fixture trades to the P8-05 report engine and asserts every KPI answer equals the hand number within 1e-9; it says plainly that engine agreement is not independent proof of the engine and the hand numbers are the second derivation.
2. **Grading is code, never a model.** Numbers are exact after normalisation (at least the stated decimals, equal to the exact value rounded half away from zero to the printed decimals; no tolerance band). A correct answer with an extra, unrelated number in a sentence that carries the answer is a `conflicting_number`. Honest-state questions need a state phrase and no number for the withheld metric. Every figure must also be in a tool result, the question or the allowed list (`ungrounded_number`); the check is the eval's own tokenizer, independent of the assistant's, so the two can disagree and the disagreement is reported. A case passes only if correct and grounded; a missing tool-result audit makes grounding `not_evaluable` and the case cannot pass.
3. **Honest statistics.** Wilson 95 % intervals on every rate and an exact paired sign test on the discordant pairs of two runs over the same cases. 30 cases cannot separate 27 from 24 correct and the report says so; six one-way discordant pairs are the fewest for p below 0.05.
4. **Thresholds live in `eval/thresholds.json`**, read by `ThresholdTable` and reviewed in a pull request: data 27 of 30; plans raw 8, repaired 9 of 10, no escape, every symbol covered; ideas first shot 8, repaired 9 of 10, intent 0.85 with none below 0.60, both declines right; events precision 0.80 once 200 labelled rows exist (before that `not_evaluable`, shown, not blocking). The verdict is PASS only when data, plans and ideas pass; a failing set (events included, once evaluable) fails the run; a set that did not run makes it INCOMPLETE.
5. **The model run is an owner act and touches only the fixture.** The runner starts from the CLI only; nothing starts it. It reads the fixture database through its own read-only tool endpoint (`xd-mcp-eval`, the same image and the same two roles, its own bearer token), after a marker probe that compares the database's `eval_marker.fixture_hash` with the file's. It writes only audit rows with origin `eval` that hold fixture data, never a strategy, hypothesis, basket or setting, never flips a switch, never confirms or accepts, and the eval origin has no path to the draft-confirm, auto or accept handlers (an architecture test). A model that is down is `model_unavailable`, never a pass.
6. **A baseline is accepted by the owner only.** `xd eval accept` is refused unless the run is a gating `PASS`; a set that got worse needs a reason. There is no auto option: nothing is applied by it, and an automatic "passed" would defeat the point (the owner's standing rule on auto options covers things that need manual approval to be applied; this applies nothing).
7. **A fingerprint makes staleness visible without a model.** SHA-256 over the model file hash, runtime image digest, prompt versions and hashes, the sets, the thresholds, the fixture and the profile. A changed prompt version or model makes the accepted baseline stale.

8. **Where a run happens.** `xd eval run` is the owner's verb, run in a one-shot container (`xd-eval`, profile `eval`) on the internal network, because the model and the tool servers are reachable nowhere else. The container holds the database password of the runtime role, the model key and the eval token, and the repo's `eval/` folder read only. The turn is the assistant's own turn service, built by one factory over the eval tool catalog with temperature 0 and seed 1337 (the production runner and catalog are not touched); the conversation is audited with origin `eval` and actor `eval:<run id>` like every turn. The plan set calls the briefing writer and the guard of P9-06 (at most two attempts: the first is the raw reading, the second the repaired one); the idea set calls the drafter, the Lab validator and the four checks of P9-07 (at most three calls). Neither stores a briefing or a draft, and neither can reach the confirm, auto or accept paths: the eval namespace names none of them (architecture test), and the drafting tool is offered only to an owner chat turn.
9. **What is stored.** `ai.eval_runs`, `ai.eval_cases` and `ai.eval_baselines` are insert-only for the runtime role (grants test); a run and its cases are written in one transaction when the run ends, a run that stops (a model that goes down, Ctrl-C) is stored as it stands with status `model_unavailable` or `cancelled`, verdict INCOMPLETE and never gating; a run that cannot ask the first question stores nothing. A gating run needs two repeats or more, the builtin target and a completed status (a check of the table). The report is three files (`report.json`, `report.md`, `answers.jsonl`) built from the stored run; `scripts/xd-eval.sh run` writes them to `data/eval/<run>/`.
10. **Reading.** `GET /api/assistant/evals`, `/{id}` and `/status` only; no route runs, grades, accepts or compares. The assistant status takes its `evaluation` from the eval status: `passed` only while a baseline exists and the fingerprint matches, `failed` when the newest gating run is not PASS, else `not_yet_evaluated`. While the model server is not running its identity is unknown and is not compared (the status says so): a baseline is never called stale because a server is off.
11. **Answers of another assistant** (`xd eval grade`, target `hermes`) are graded by the same code from a file; grounding comes from the tool-call audit of each answer's `session_id`; a missing audit makes grounding not evaluable and the answer cannot pass. Such a run is never gating and cannot be accepted.
12. **The marker.** `ai.eval_marker` (one row, written last by the seeder as the database owner; no right for the runtime role) and the reviewed view `aiv.eval_marker` through which the eval tool endpoint proves what it reads. It is empty in every other database, so a probe of the production database finds none. The seeder (`xd eval seed`, run by `scripts/eval-db.sh`) refuses any database but `xdrishti_eval`, any database that already holds rows in the tables it writes, and a database seeded from another version of the fixture; it runs in one transaction.

## Cut or limited
- **DQ-24 and DQ-25 say "count each once, by its newest state".** Lessons and hypotheses are logs (one row per state change) and the tool filters rows, so "open" would count the opening row of a lesson that was dismissed later; the fixture has a lesson that moved (the spec's "closed" lesson is a dismissed one: closing needs a judged experiment the fixture does not have). The wording of the two questions names the rule; the expected numbers are the spec's.
- **DQ-15 is the unrealised return, not the XIRR.** The spec's table has "XIRR of EVH1: 21.0 %", which is true only on the fixture date (one year after the purchase): the portfolio tool values a holding at today's date, so the XIRR falls with every day after 2026-03-03. The question asks for the unrealised return of EVH1 in percent (21.0 %), which does not depend on the date; the expected number is the one of the spec.
- The 200 labelled announcements arrive with P15; the events set reports `not_evaluable`.
- The report engine answers `insufficient` below 30 trades, and the fixture groups hold 24, 16, 12 and fewer: through `get_report` these questions have no figure, so a correct answer must be computed from the stored trades (`run_sql`) or the engine's minimum is the thing under test. The oracle runs the engine with small minimums. UNVERIFIED how a real model behaves here.
- No real model was run for this ADR; every test uses scripted answers. UNVERIFIED on the owner's machine: the compose services of the eval and `scripts/xd-eval.sh` / `scripts/eval-db.sh` (the file parses with `compose config` and the rules are tested, but no container of the eval was started); the wall time of a run (about two hours at three repeats, from the spec); how a real model behaves on the 30 questions; the determinism of greedy decoding on the GPU (`stability` shows how far it holds).
- The model's identity in the fingerprint is the model file hash the server reports; the "runtime digest" is the build string it reports (the image digest is not exposed).
- The `get_report` tool answers `insufficient` for every fixture group below 30 trades: a model that wants a KPI figure has to compute it from the stored trades with `run_sql`. The fixture test checks that this is what the tool answers.

## Consequences
- A model, runtime or prompt change can be judged on the same 30, 10 and 10 cases and compared pairwise with the accepted run.
- 30, 10 and 10 cases cannot show small differences; the intervals say so. The fixture tests reading numbers correctly, not market judgement.
