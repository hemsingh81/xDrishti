# 0135 — The depth recorder stores the 20-level book of up to 50 shares about once a second, behind three gates, a disk guard and no reader

- **Status:** Proposed (built in P7-16 on the owner's delegation of the decision; the allow-list entry was accepted in principle by [ADR 0133](0133-new-broker-endpoints-enter-the-allow-list-in-the-commit-of-the-slice-that-uses-them-index-and-vix-history-needs-none.md)). Becomes Accepted when the owner has read it. **SAFETY decision: a new broker WebSocket on the allow-list, the Data account's token on a second connection, continuous disk growth.**
- **Date:** 2026-10-27.
- **Relation to other ADRs:** [0024](0024-live-feed-xd-feed-and-live-prices.md) (the live feed and its one socket), [0097](0097-the-p7-phase-check-ten-consecutive-scheduled-sessions-from-stored-plan-runs-and-never-met-on-fewer.md) (the pinned allow-list), [0128](0128-owner-act-capabilities-are-one-insert-only-log-with-a-generic-gate-by-name-off-by-default-and-switched-on-only-by-the-owner-with-a-fresh-password.md) and [0130](0130-the-owner-act-forms-are-endpoints-behind-a-capability-a-fresh-password-and-an-audit-row-over-the-existing-handlers-and-state-machines-and-apply-nothing.md) (the fresh-password pattern), [0091](0091-auto-approval-is-an-option-behind-an-owner-setting-default-off-a-new-approval-kind-the-database-checks.md) (the stored switch), [0083](0083-the-plan-record-insert-only-state-trails-owner-only-approvals-lapse-by-default-and-no-order-by-name.md) (no order).

## Context
Dhan offers no historical market depth, so a later phase (P13, order-book features) can only use depth that this system recorded itself, and six months must exist when it starts. Recording opens a second broker socket with the Data account's token and grows the database without bound, so it has to be off until the owner switches it on, bounded by a disk budget that stops the recording and not the machine, and unable to influence anything that decides or trades.

## Decision
1. **One exact allow-list entry.** `wss://depth-api-feed.dhan.co/twentydepth` with exactly the query keys `authType`, `clientId`, `token` (each once, any order, no `version`). `BrokerEndpoints.IsAllowedDepthSocket` is a second exact check beside the live feed's; `Describe()`, `PlanPhaseCheck.PinnedAllowList` (`WSS depth-api-feed.dhan.co/twentydepth?authType&clientId&token`) and the allow and refuse tests changed in the same commit. The 200-level host, other paths, ports, schemes, extra keys (including `version`) and the live feed's host stay refused on this check and the depth host stays refused on the live check. The connector builds the URL, checks it before any connection, and never logs it.
2. **Three gates, all off by default.** (a) The deployment flag `Depth__Enabled` (default false, restart to change; `deploy/compose.yaml` passes `XD_DEPTH_ENABLED`, default false); (b) the owner's stored switch `market.depth_recorder_switch` (insert-only, newest row decides, no row = OFF), changed by `PUT /api/depth/recorder` with a **fresh password on every change, ON and OFF** (`OwnerAct.AuthorizeAsync`, `StepUpCommand` with `Elevate: false`: the sign-in lockout and audit apply, an earlier step-up window neither counts nor is used up; the actor is `owner:<email>` from the session, never from the body) plus one account event `DepthRecorderSwitched` (category `service`; row id and state only, never the reason); (c) the service `depth-recorder`, registered paused. With any gate closed nothing reads the credentials, builds a URL or opens a socket: the supervisor checks the flag first, then the switch, then the service, and reads the credentials only after the disk guard, the day's set and all three gates.
3. **A window service of the `xd-feed` host, in its own loop.** `DepthRecorderService` (window 09:14-15:31 India time on trading days, retries 0, no catch-up, notify on failure) is an `IExternallyRunService`; `DepthRecorderSupervisor` (15 s looks) and `DepthRecorder` (the session) run in a second hosted service (`DepthService`) with their own try/catch, run record and heartbeat row `xd-depth`; the live feed's session, flush, active set, pre-open check and `xd-feed` health check (which reads only its own row) are untouched. "Run now", the pause marker and the live-feed health of the Services screen belong to the live feed alone (`ServiceRegistry.UsesLiveFeedMarker`); "Run now" of the depth recorder is refused (`services.read_only`).
4. **20 levels, one socket, at most 50 instruments, about once a second, change-only.** The set is fixed per day and stored in `market.depth_session_instruments`: today's armed tickets in rank order (at most `Depth:MaxArmed` 20), then the owner's `Depth:PinnedSymbols`, then the most liquid tracked shares by the mean of close x volume of the last 20 daily bars before the day (ties by symbol). It is built only from read-only ports (`IArmedTicketReader`, `IInstrumentSecurities`, daily bars); it is not an active-set provider and changes nothing. A bid and an ask packet become one row per instrument per `Depth:SampleMs` (default 1000) when a side changed and both were seen; prices become integer paise (half away from zero), quantities are clamped to `int.MaxValue` (flag), a side older than 5 s, a crossed book and a ladder out of order are flagged; the time is the receive time plus a monotonic millisecond counter (packets carry no exchange time). Only 09:15:00 up to 15:30:00 is stored.
5. **A hypertable in the existing database.** `market.depth_snapshots` (six `int4[20]` arrays, one-day chunks, compressed after 2 days, segment by instrument, order by time, **no retention policy**) written with `COPY`, one transaction per batch every `Depth:FlushSeconds` (5); a failed batch is retried with the next, rows unwritten for more than 30 s are dropped oldest first and counted, and the receive loop never waits for the database. All four depth tables are insert-only for `xd_app`.
6. **A guard that stops and never deletes.** Before each start and every 5 minutes: stored size above `Depth:MaxStoredGb` (40) ends the run `disk_budget`; free space of the file system the process runs on (`DriveInfo("/")`) below `Depth:MinFreeGb` (20) ends it `disk_free` (unreadable free space leaves the size cap in force and says so); a warning at 80 %. A stopped recorder stays stopped while the condition holds and until a look finds it not wanted (the owner's pause, the end of the window). The application deletes nothing; dropping chunks after P13 decides is the owner's SQL act. The run fails with a message, which raises the service-failure notice.
7. **No reader.** `IDepthStore` has no method that reads a snapshot (an architecture test pins the method list), no route reads depth, no hand-written frontend file mentions it, and the decision layers (Domain, Simulation, Strategies, Indicators, Planning, Learning, Portfolio, the live feed's own code) reference no depth type. P13 is the first consumer and starts with its own spec.
8. **Disconnect codes.** 806 (Data APIs not subscribed) ends the run `not_subscribed` and waits for new credentials; 805 (too many connections) is flapping; 802/803/807/808/809 are a refused token and wait for a changed token; flapping (more than 10 reconnects in 5 minutes) pauses attempts for 5 minutes; a crash waits 30 s. Reconnects use the live feed's back-off and limiter classes.

## Deviations from the spec text (decided while building)
- The switch endpoint has **no capability** (ADR 0128 names one capability per owner act; the spec lists the password only): the three gates and the password are the guard. Adding `depth_form` would be one line in `Capabilities.All` if the owner wants a fourth gate.
- The `market.depth_sessions` row is written when the **day is over** (first look after 15:31, or a new India day) with the reason of the day's last end and the counts summed over its runs, not at the end of every run: a restart, a refused token or a pause in the morning does not use up the day's single row (the primary key is the date). A day with a stored set and no end row at the next start (the process died, or was restarted before the day ended) is closed as `crashed`; that row then stands for the day (first wins).
- `gap_seconds` counts the time between the start (or a drop) and the next connection; a drop that is still open when the run ends is not added.
- The stored size is read with `hypertable_detailed_size` (readable by `xd_app`, tested); the free space is read inside the `xd-feed` container with `DriveInfo("/")` and describes the VM file system only if the container root is on it (UNVERIFIED until the first real run; the size cap alone is in force when it cannot be read).
- `gen-api` puts the two routes into the generated client types (`frontend/src/shared/api/schema.d.ts`); no hand-written frontend file and no screen exist.

## Consequences
- Nothing changes while the flag, the switch and the service are off: the host registers the supervisor, which beats `xd-depth` with the state word `disabled`, `switch_off` or `paused` and does nothing else.
- Owner acts before switching it on, in this order: check the VM disk (`podman machine ssh df -h /var`, at least 60 GiB free, or enlarge it); confirm in the Dhan account that the Data APIs plan includes 20-level depth (otherwise the first run ends `not_subscribed`, harmlessly); set `XD_DEPTH_ENABLED=true` (optionally `Depth__PinnedSymbols__0=NSE:...`) and run `deploy/xd-up.sh`; `PUT /api/depth/recorder` with the password; resume the service `depth-recorder` on the Services screen. Turning it off again needs the same password.
- `xd-backup`, when built, must exclude `market.depth_snapshots` data (`pg_dump --exclude-table-data`).
- The budget, byte order, sequence meaning and rate are estimates and assumptions until the pilot (five real sessions): bytes per row, compression ratio, packets per second and rows per instrument-day are measured with `hypertable_detailed_size`, `hypertable_compression_stats` and a count per instrument and replace the numbers of the spec (0.77 GB per day raw, about 38 GB per year at 5:1) here.
- A trade-tick stream for aggressive volume is not part of this slice (finding for the index: P7-16b "tick recording").
