# 0175 — Option contracts of a configured underlying list are kept from the master refresh in their own schema, with a dated lot history and dated rule epochs, never in the master list

- **Status:** Proposed (built in P14-01 from the owner-Approved spec, 2026-11-01, with the recommended answers). Becomes Accepted when the owner has read it. Not a safety decision: no broker endpoint, no token, no order, under 20 MB a year.
- **Date:** 2026-11-01.
- **Relation to other ADRs:** amends [0010](0010-instrument-master-sources-and-scope.md) (the master scope: option rows are still skipped by the master list and are now read once more for this archive), [0002](0002-config-and-strategies-in-app.md) (the underlying list is an app setting, not a file), [0045](0045-the-result-store-sim-runs-and-sim-trades.md) (insert-only rows for the runtime role), [0133](0133-new-broker-endpoints-enter-the-allow-list-in-the-commit-of-the-slice-that-uses-them-index-and-vix-history-needs-none.md) (not triggered: the scrip master is the file already fetched from `images.dhan.co`, `MasterDataEndpoints.DhanScripMaster`).

## Context
Every later option slice of P14 (chain recorder, expired-options backfill, cost model, expression simulator) needs to say which contract, which lot and which market rules were in force on a date, or say `unavailable`. Dhan's scrip master already lists every live option contract; the master list skips them (doc 06 §2.1) and today's `lot_size` of an instrument is overwritten daily, so the history is lost unless it is kept from now on. Spec: [P14-01](../specs/P14-01-option-contracts-lot-sizes-and-rule-epochs.md).

**Read in the real file (2026-11-01, `api-scrip-master-detailed.csv`, 204,521 rows):** the index rows of the default list are `NIFTY` (id 13), `BANKNIFTY` (25), `FINNIFTY` (27) and `MIDCPNIFTY` (442, "Nifty Midcap Select"), so their canonical symbols are `NSE:NIFTY`, `NSE:BANKNIFTY`, `NSE:FINNIFTY`, `NSE:MIDCPNIFTY` (the FINNIFTY and MIDCPNIFTY rows were added to the committed master sample, which now has 77 rows and 62 instruments); `OPTION_TYPE` is `CE`/`PE`; `STRIKE_PRICE` is rupees (`720.00000` for the RELIANCE 720 call, `147.50000` for a half-rupee strike); `EXPIRY_FLAG` is `W` or `M`; `SM_EXPIRY_DATE` is `yyyy-MM-dd`; `TICK_SIZE` is paise (5 or 1, as verified for shares, ISS-18); an index option's `UNDERLYING_SECURITY_ID` is the exchange's index token (26000 for NIFTY), not the id of the index row (13), so the underlying is matched by symbol. NSE option rows: 81,835 (12,201 `OPTIDX` on 6 indices, 69,634 `OPTSTK` on 218 shares). Underlyings carry different lots across expiries during a revision (AMBUJACEM: 1,200 for November and December, 1,350 from January).

## Decision
1. **One read, two outputs.** `DhanMasterParser.ParseAsync` takes an optional list of underlyings. The master list's rules are untouched (`InstrumentScope` unchanged; an option row still counts as out of scope); an NSE `D` row of `OPTIDX`/`OPTSTK` whose `UNDERLYING_SYMBOL` names a listed underlying is split and read by `OptionRowCollector`, every other option row is only counted (`skipped_not_listed`). An option row never adds a warning or a protected id to the master list's parse, so `market.instruments`, search and baskets get exactly what they got before. A file without `STRIKE_PRICE`, `OPTION_TYPE` or `EXPIRY_FLAG` reads no option and says so; the master list is imported as before.
2. **Row mapping (pure, `OptionScope` and `OptionRowCollector`).** Underlying: `CanonicalSymbol.ForIndex` for `OPTIDX`, `ForListed` for `OPTSTK`; an exchange test symbol is never kept. `strike_px` = rupees x 100 rounded half away from zero, above 0 and within `int4`; `side` `CE`/`PE`; `expiry_kind` `week`/`month` from `W`/`M`, else null; `lot_size_seen` a whole number from 1; `tick_px` whole paise or null. A row with an unreadable security id, expiry, strike, side or lot is counted `invalid` and dropped, never stored with a zero.
3. **Schema `options` (migration `AddOptionContracts`, raw SQL, no EF entity).** `contracts` (primary key **(security id, expiry)**, not the id alone; unique `(underlying_id, expiry, strike_px, side)`; foreign key to `market.instruments`; checks on every coded column), `lot_sizes` (identity id, `effective_from`, `lot_size > 0`, `source` in `circular|secondary|scrip_master`, `source_url`, `confirmed`, `recorded_at` stamped by the database; a check refuses `confirmed` unless the source is a circular with its address), `market_epochs` (primary key `(code, effective_from)`; a check refuses `confirmed` without an address). `Down` drops the schema.
4. **Never deleted; the runtime role's rights are the minimum.** The import inserts a new (security id, expiry) and advances `last_seen_on` only of a stored row whose underlying, strike and side are the same as the file's; a contract missing from a later file (expired) keeps its row. `xd_app` reads all three tables, inserts into all three, may update only `contracts.last_seen_on` (a column grant) and can update nothing else, delete or truncate nothing. No other role (`xd_exec`, `xd_mcp_read`, `xd_mcp_sql`) has any right. A contract another security id already holds is counted `conflicting`, not an error.
4a. **Reused security ids (review, 2026-11-01).** Whether NSE reuses an F&O token after expiry is UNVERIFIED (the real file of 2026-11-01 has no repeated id). If a security id in the file names a different contract than the stored one, it is counted `reused_id` and reported as a run warning: with a new expiry it is stored as its own row (the key allows it) and the old row keeps its dates; with the same expiry and another underlying, strike or side it is neither stored nor advanced, so the stored history is never overwritten. A row already stored as itself (the new-expiry row an earlier reuse added) is advanced and not reported again. Later slices join on (`security_id`, `expiry`) or on (`underlying_id`, `expiry`, `strike_px`, `side`), never on the id alone. A (security id, expiry) twice in one file keeps one row chosen deterministically (lowest underlying, strike, side, lot) and the dropped ones are counted `conflicting`.
5. **Lot history.** Per listed underlying the lot "the file shows on the day" is the lot of its **nearest expiry on or after the refresh's India date** (most common at that expiry, ties to the smaller); during a revision the far months carry the new lot first, the near one is what trades that day, and the underlyings with more than one lot are counted in the log. When it differs from the newest `scrip_master` row (or there is none yet), one row is written with `effective_from` = the refresh's India date, `confirmed = false`. Every contract keeps the lot it showed when first seen (`lot_size_seen`).
6. **Lookups, pure.** `LotSizeLookup.InForce(rows, underlying, date)`: the row with the latest `effective_from <= date`; on the same date a confirmed row wins, then the one recorded last; none is `unavailable`. `EpochLookup.InForce(rows, date)`: per code, the latest row on or before the date. Both return the `confirmed` flag; nothing guesses.
7. **Seeds: every one unconfirmed.** The build agent did not open a circular, so **no seed is `confirmed`**. Lot seeds (written by the import once the underlying is in the master list, each once): NIFTY 75 from 2024-11-20 (secondary: Business Standard on the SEBI circular of 2024-10-01), NIFTY 65 and BANKNIFTY 30 from 2025-12-30 (secondary: Kotak Neo bulletin). Bank Nifty's lot before 2025-12-30 is not seeded (no dated source), so it reads `unavailable` before that date. Epoch seeds (in the migration): `weekly_index_one_per_exchange` and `min_contract_value_15_lakh` 2024-11-20, `upfront_premium` 2025-02-01 (Business Standard, SEBI 2024-10-01), `nifty_expiry_tuesday` 2025-09-01 (Business Standard), `index_lot_revision` 2025-12-30 (Kotak Neo), `stt_fo_raise` 2026-04-01 (Outlook Money). Confirming one is an owner act: an inserted `circular` row with the circular's address.
8. **The underlying list is the app setting `options.underlyings`** (a JSON array of canonical symbols in `platform.app_settings`, ADR 0002). Without a row, the next refresh builds the default once: the four indices `NSE:NIFTY`, `NSE:BANKNIFTY`, `NSE:FINNIFTY`, `NSE:MIDCPNIFTY` and the 30 F&O-eligible tracked shares with the highest mean turnover over their last 20 daily bars (the depth set's ranking, P7-16). It is **written once, with the actor `system:options-first-import`, only when all 30 are found and the newest daily bar of the ranking is at most 7 days old (about 5 sessions)**; with fewer the run uses what it found (logged) and the next refresh tries again; with stale bars it does the same and reports it as a run warning. **Owner acceptance point:** spec criterion 8 says the list is written into the setting "by the owner"; here the system writes the default once and records it as `system:options-first-import`, never as an owner act. The owner accepts it by reading this ADR or replaces it by writing the row (before the first refresh, to avoid the computed default). A stored row is used as it is and never recomputed; the owner changes it (no route in this slice; the screen is P14-16). A bare ticker gets `NSE:`, case is folded; an entry that is not a symbol is dropped and reported; a listed symbol that is not an active (not retired) index or share of the master list is a run warning (`unmapped_underlying` for its rows), never a crash; an empty list keeps no contract.
9. **Never fails the refresh; warnings only for real problems.** The setting is read before the download (no database work while the download stream is open); the contracts are saved after the master list. A problem reading the setting or saving the contracts is an error log (`options.step_failed`) and a run warning, and the refresh still succeeds. A run warning is written only for a real problem: an unreadable setting or entry, an unknown or retired underlying (with its `unmapped_underlying` rows), `invalid` rows, `reused_id`, `conflicting` rows, a file without the option columns, a stale ranking, a failed save. Option warnings come first in the run's list, so the cap of 50 stored warnings never drops them. A malformed option line or number never fails the master import (strike overflow is checked before multiplying; any arithmetic or format error in an option row counts it `invalid`). **Deviation from spec criterion "counts in `market.master_refreshes` warnings text":** a counts line on every refresh would raise the Services/Instruments "last refresh has warnings" chip after nearly every refresh, so the counts (kept, underlyings, new, seen again, conflicting, reused ids, lot changes, mixed lots, `skipped_not_listed`, `unmapped_underlying`, `invalid`) go to the log event `options.contracts_applied` instead; `market.master_refreshes` has no other text field and the schema is not changed for it. A normal option import leaves the run's warnings identical to a run without a list (tested). Logs `options.*` (ids 6901 to 6905) carry counts only.
10. **The first refresh reads the whole file.** `RefreshRules.Version` is 2, so the next refresh after deploy ignores the stored `ETag` and imports the unchanged file once. On a day the file is unchanged (`304`), `last_seen_on` does not move; a changed list takes effect at the next refresh that reads the file. Shortcut: the setting is read before the download on every refresh, also one that then finds the file unchanged or fails to download (one small read; the turnover ranking only while no list is stored); a default fixed on such a day is the same default.
11. **No trading use yet.** `Domain` outside `Options`, `Simulation`, `Strategies*`, `Indicators`, `SimExport`, `SimReader` and the planning, learning, portfolio, research, lab, paper and live code reference no option type; the store has no method that reads a contract; only `OptionContractStore` names the tables in SQL; no route reads them (architecture tests).

## Measured
- **Live contracts for the list (real file, 2026-11-01):** the four indices hold **8,979** (NIFTY 3,991, BANKNIFTY 2,328, FINNIFTY 1,058, MIDCPNIFTY 1,602); a share holds 107 to 572 (median 316), so 30 shares add about 9,500 and at most 13,978: **about 18,500, at most 22,957** live rows (the P14-00 estimate was 10 k). The exact count for the turnover list is in the first run's `options.contracts_applied` log event.
- **Parse time on the real file** (Release, best of 7, Apple M-series): 55 ms without a list, 62 ms with the four indices and the 30 shares with the most option rows (22,957 contracts): **+13.7 %** of the parse, under the 20 % budget; the whole run (download, sectors, save; about a minute) grows much less. The stream is still read once, front to back (a forward-only stream test).
- **Size:** about 20 k live rows, 50 to 70 k expired rows a year at about 250 B with the index: under 20 MB a year, no cap.

## Consequences
- P14-02/03/04 join on (`security_id`, `expiry`) or (`underlying_id`, `expiry`, `strike_px`, `side`); P14-07/08 read lots and epochs with the two lookups and must carry the `confirmed` flag into what they print.
- Until the owner confirms them against the circulars, every lot and epoch reads unconfirmed.
- The owner's list can be written before the first refresh (SQL or CLI now, the P14-16 screen later) to avoid the computed default.
