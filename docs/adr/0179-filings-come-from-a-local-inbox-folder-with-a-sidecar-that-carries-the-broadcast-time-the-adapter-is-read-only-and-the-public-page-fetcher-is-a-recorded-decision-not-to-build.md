# 0179 — Filings come from a local inbox folder with a sidecar that carries the broadcast time; the adapter is read-only; the public-page fetcher is a recorded decision not to build

- **Status:** Proposed (built in P15-01 from the owner-Approved spec, 2026-11-02, with the safer answers to the three open questions: no fetcher, the sidecar contract as written, a script that files local files only). Becomes Accepted when the owner has read it. Safety slice: it reads untrusted files and decides how the system may ever reach an exchange website; it sends nothing.
- **Date:** 2026-11-02.
- **Relation to other ADRs:** [0133](0133-new-broker-endpoints-enter-the-allow-list-in-the-commit-of-the-slice-that-uses-them-index-and-vix-history-needs-none.md) and [0097](0097-the-p7-phase-check-ten-consecutive-scheduled-sessions-from-stored-plan-runs-and-never-met-on-fewer.md) (allow-list rule and pin) are untouched: no host and no path is added. [0083](0083-the-plan-record-insert-only-state-trails-owner-only-approvals-lapse-by-default-and-no-order-by-name.md) (no order). P15-00 decisions D1 (the folder drop is the default source) and D3 (point in time by broadcast time).

## Context
P15 needs exchange filings (results, shareholding, board meetings, announcements) stored point in time by the time the exchange broadcast them. The exchange terms of use are unverified, the endpoints are undocumented and cookie-gated, and the system needs about 4,300 results files in five years, which a hand-filed folder handles. Reading a local folder and fetching from an exchange website are different acts.

## Decision
1. **One port, one local adapter.** `IFilingsSource` (`Application/Abstractions/Filings`): `ListAsync(FilingQuery)` returns `FilingListing { Accepted, Rejected, Problems, Truncated }`; `OpenAsync(FilingRef)` returns a read-only forward stream that never reads past the listed size, hashes what it hands out and throws `content_changed` as soon as more bytes than listed are read, or at the end when the SHA-256 differs from the listed one. `FolderDropFilingsSource` (Infrastructure) reads `Filings:InboxPath` and **never writes, moves or deletes** there (an architecture test scans its source for any write call). It holds no state, reads no sub-folder, follows no symlink, and parses no file bytes (a DTD or an entity in an XML file is only hashed).
2. **The sidecar carries the metadata, not the file name.** `<file>.meta.json` (UTF-8, at most 4 KB, schema 1, no unknown and no duplicate key): `symbol`, `kind` (`results`, `shareholding`, `board_meeting`, `announcement`), `period_end`, `broadcast_ts`, `source_ref`. The name carries no meaning. Pure rules live in `Domain/Filings` (`FilingSidecar`, `BroadcastRule`, `FilingNames`).
3. **The broadcast time needs an offset and is never guessed.** `broadcast_ts` is `ok` only with an offset or `Z`, from year 2000 on, and not more than 5 minutes ahead of the `TimeProvider` clock; it is stored as a UTC instant. Absent, `null`, a date without a time, a time without an offset, unparsable text, a time before 2000 or in the future make the file `unavailable` with a closed reason (`missing`, `date_only`, `no_offset`, `unparsable`, `before_2000`, `broadcast_in_future`); the file is still **listed**, so P15-02 can store and count it, and the date is never substituted. A `.csv` of `board_meeting` or `shareholding` is `row_level_ts` (the rows carry their times, P15-04); only there the symbol `*` is allowed.
4. **Rejections are listed, never silent.** Closed reasons: `no_sidecar`, `invalid_sidecar` (with the first problem as a code: `sidecar_too_large`, `invalid_json`, `duplicate_key`, `unknown_key`, `bad_schema`, `bad_symbol`, `bad_kind`, `bad_period_end`, `bad_source_ref`, `sidecar_empty`, `sidecar_not_regular`, `sidecar_unreadable`), `bad_name`, `bad_extension`, `too_large`, `empty`, `not_a_regular_file`, `unreadable`, `orphan_sidecar`. The order of checks opens nothing a reason does not need: a link or folder, name, extension, size (from the directory entry), sidecar, only then the hash.
5. **A loose or missing inbox is a problem, not data.** A mode wider than `0700` on a POSIX host gives no entries and the problem `inbox_permissions` (the owner runs `chmod 700`; the adapter never changes a mode); a missing folder is `inbox_missing`; a symlinked folder is `inbox_outside`. Reason: a world-writable inbox would let another local user plant a filing.
6. **Bounded and ordered.** Files are hashed by streaming; a file that changes size while read is `unreadable`; at most `Filings:MaxFiles` entries are examined per scan, names taken in ordinal order, and more is `truncated: true`. Accepted entries are ordered by symbol, kind code, period end, SHA-256 (all ordinal), so any directory order gives the same list.
7. **Settings `Filings:*`** (the default `InboxPath` is relative and resolves against the host's working directory, so P15-02 sets `Filings__InboxPath` explicitly, `/data/filings/inbox` in the container) (`ValidateOnStart`, registered in the Infrastructure DI root): `InboxPath` (`data/filings/inbox`), `MaxFileMb` (20, 1-200), `MaxFiles` (5,000, 100-50,000). Log event `filings.scan` (6981) carries counts and reason codes only.
8. **The owner's script files local files only.** `scripts/filings-drop.sh` copies a saved file to `<SYMBOL>_<kind>_<period_end>_<sha8>.<ext>` and writes the sidecar (both `0600`, folder `0700`), refuses what the adapter would refuse, and contains no network or interpreter command (a test greps it). A downloader would be the fetcher by another name.
9. **Decision: the public-page fetcher is not built, and nothing for it exists.** No code, host, allow-list row, setting or gate. The strings `filings.fetch` and `Filings:Fetch` appear nowhere in `backend/src` (architecture test); the key is only *reserved* in doc 16 as "not built, default false". The fetcher may be built only as a later slice (provisionally `P15-01b`) after the owner has read the exchange terms and says so in chat; that spec must carry the owner's written statement of what the terms allow, exact-path allow-list rows added with their use (pin and guard test), `filings.fetch.enabled` default false with a fresh-password switch and a paused service, one request per 3 seconds for the process, an honest `User-Agent`, `robots.txt` obeyed, 429 and `Retry-After` obeyed, no cookie reuse, no browser impersonation, no CAPTCHA handling, fetched bytes written only into the inbox with a sidecar whose `broadcast_ts` comes from the response body or is `null` (never the fetch time), and a disk cap with counts-only logs.
10. **Layering.** Only the filings code and the DI root reference a filings type (architecture test); the Domain types, the port and the adapter reference no `System.Net.Http`, `System.Net.Sockets`, `HttpClient`, `IHttpClientFactory`, `WebClient` or broker client, and the adapter's constructor takes only options, the clock and a logger.

## Consequences
- P15-02 ingests what the adapter lists and counts `unavailable` files; P15-04 reads the `.csv` drops. The compose mount of the inbox arrives with the first host that reads it (P15-02); no API, UI or migration changes here.
- The owner supplies the broadcast time by hand; a wrong time is a look-ahead error nothing here can detect (the script's help says to copy the time the exchange shows).
- Sidecars are manual work for about 4,300 files; a batch helper is a later convenience.
- `.pdf` and `.txt` are accepted and stored; nothing reads them before P15-08.

## Known limits
- A named pipe or device in the inbox reports length 0 and is rejected `empty` (as a filing) or `invalid_sidecar` with detail `sidecar_empty` (as a sidecar), and is never opened, because opening a pipe would block the scan (.NET exposes no file-type bit); a symlink or folder is `not_a_regular_file`. A sidecar that really is empty gets the same detail.
- Hard links are regular files and are accepted. Only someone who can already write the `0700` inbox can create one, which is the owner.
- There is a short window between the checks and the open in which a file could be swapped for a link; the open re-checks the size and the link state, and the hash proves content, but a local attacker able to write the `0700` inbox is already the owner.
- The directory listing is taken whole before the cap applies (names only), so an inbox of millions of entries costs memory; the 20 GB and 5,000-file limits make this theoretical.
- The exchange terms, any public endpoint's shape and the XBRL file sizes stay UNVERIFIED (P15-00).
