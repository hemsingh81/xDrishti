# 0023 — Trades from CSV or by hand are stored as transactions and rebuild a holding's lots with real dates

- **Status:** Accepted (owner, 2026-10-13: "approved as written", after the review below) — builds on [ADR 0012](0012-holdings-acquisition-dates-and-returns-model.md) (lots, owner-set dates, "a later helper may refine dates from trades"), [ADR 0013](0013-portfolio-import-with-settings-and-daily-refresh.md) and [ADR 0017](0017-trading-calendar-eod-schedule-quality-adjustments-and-csv-undo.md) §5 (applied corporate actions)
- **Date:** 2026-10-13

## Context
Dhan's holdings API has no purchase dates, so every lot carries the owner's first-import date (default 1 Jan 2025) or a hand-edited one. XIRR, the value history, the benchmark and the long-term-soon rule are only as good as those dates (ADR 0012, ADR 0020). Design doc 12 §1–§3 names the better source — the trades themselves, from a broker tradebook export (CSV) or entered by hand — and lists the domain model (immutable transactions → FIFO lots → positions). The holdings and lots tables exist; transactions do not. The broker's quantity and average cost are authoritative (ADR 0012), so trades can only **explain** a holding, never change what Dhan says is held.

## Decisions
1. **Transactions are stored; lots are derived from them on an explicit step.** `portfolio.transactions` holds each trade — account, instrument (when mapped), ISIN, trading symbol, exchange, `side` (`buy`/`sell`), India `trade_date` and optional time, `qty` > 0, `price` > 0, `charges` ≥ 0 (one total; informational here, counted in the net returns since P2-14, [ADR 0026](0026-dividends-entered-by-the-owner-and-charges-in-net-returns.md)), `source` (`csv` | `manual`), `batch_id`, `external_id`, who/when — and is **immutable except `voided_at/by`** (no DELETE for the app role; a mistake is voided, never edited). Importing or adding trades **does not touch lots**; the owner previews the effect and confirms **Rebuild lots** (per import, or per holding), so nothing the owner dated by hand is replaced without being shown.
2. **Reconstruction (pure, deterministic).** For one holding, from its **non-voided transactions of the same account and security** (matched by ISIN, else trading symbol, case-insensitive) and the broker's current quantity `Q` and average cost `A`: net = Σ buys − Σ sells; the **opening quantity** `P0 = Q − net`. If `P0 < 0` the file explains more shares than Dhan holds (or a sell is missing its buy): **not applied**, reported as `quantity_mismatch` with the numbers. Otherwise lots are rebuilt chronologically (same day: buys before sells; then by time, then file order): an **opening lot** of `P0` (date = the account's first-import date, or the day before the first trade when that is earlier, flagged *default date*), then each buy creates a lot, each sell consumes open lots **FIFO** and closes pieces at the sell price on the sell date (`estimated = false`). The opening lot's unit cost follows from the broker's average cost (amended after review, see below): `c0 = (A × (P0 + B) − BC) / P0`, with `B` the shares and `BC` the cost of all the buys of the trades on today's basis; when that is not positive the opening lot costs `A` and the rebuild says `costNote: opening_cost_fallback`; with `P0 = 0` there is no opening lot. Rebuilding replaces **all** lots of the holding (including lots added by syncs and hand-dated ones — the preview counts them) in one unit of work; lots made from trades have `source = trade`, are not flagged default and their dates are read-only (they come from the trades); the opening lot stays editable.
3. **Splits and bonuses.** A trade is converted to today's share basis with the instrument's **applied** corporate actions after its trade date (ADR 0017 §5: quantity × factor⁻¹, price × factor), so a 2021 purchase of a stock that split in 2023 matches Dhan's quantity; the preview says "adjusted for N corporate actions". Unapplied suggestions are not used; a mismatch caused by a missing corporate action surfaces as `quantity_mismatch` (the owner confirms the action on the Data screen and rebuilds).
4. **Trades for securities the account does not hold now** (fully sold, or not synced yet) are stored and listed ("12 trades for 4 securities not held") but **not applied**; if the holding appears later, *Rebuild lots* uses them. Closed positions are not created from trades in this slice.
5. **CSV import is generic, auto-detected and previewed first.** One file per request (UTF-8, ≤ 10 MB, ≤ 20,000 rows), header aliases case-insensitive and punctuation-insensitive (date: `date|trade date|trade_date|order execution time`…, symbol: `symbol|trading symbol|scrip|instrument`, ISIN, side: `trade type|side|buy/sell|transaction type`, quantity, price: `price|trade price|rate|avg price`, optional `exchange`, `trade id|order id|trade no`, `time`, charge columns `brokerage|charges|taxes` summed); dates `yyyy-MM-dd`, `dd-MM-yyyy`, `dd/MM/yyyy`, `dd-MMM-yyyy` (never `MM/dd`); numbers with `.` decimal and optional thousands commas. A file missing a required column is refused with the missing names and a **downloadable template**; rows for derivatives/commodity/currency segments or non-equity instruments are **skipped with reason counts**; bad rows are listed (line, reason) up to a limit and never imported silently; the preview shows counts, the securities matched/unmatched, the per-holding **reconstruction result** (lots before → after, realised P&L from real sells, mismatches) and nothing is stored until **Import**. Broker-specific profiles (Dhan, Zerodha…) are **not verified here**: they are added as profiles when the owner supplies a real export.
6. **Idempotent and undoable.** A trade's identity is `external_id` when the file has one, else a hash of (account, date, time, symbol, side, qty, price, line occurrence in the same file); importing the same file again stores nothing new ("N already imported"). A trade id is the identity **together with the trade date** (`t:yyyyMMdd:id`; exchanges number trades per day). Each import is a **batch** (`portfolio.trade_batches`: file name, SHA-256, counts, status); **Undo** voids every transaction of the batch and rebuilds the affected holdings from what remains (with no trades left a holding returns to one lot of `Q` at cost `A` dated by the first-import date, flagged default). Manual trades form no batch and are voided one by one.
7. **Not in this slice:** the Dhan trade-history and ledger sync (a later story reuses these tables with `source = broker`), cash flows/dividends, charges in cost basis or XIRR (stored only), brokerage-specific parsers, editing a transaction (void and re-add), positions/intraday P&L, creating closed holdings from trades.
8. **API** (session + CSRF, no step-up; audited): `POST /api/portfolio/trades/preview` (multipart: account id, file → report), `POST /api/portfolio/trades/import` (same body + `rebuild: true|false` → batch + the rebuild report), `GET /api/portfolio/trade-batches`, `POST /api/portfolio/trade-batches/{id}/undo`, `GET /api/holdings/{id}/trades`, `POST /api/portfolio/trades` (manual), `POST /api/portfolio/trades/{id}/void`, `POST /api/holdings/{id}/rebuild-lots` (preview with `dryRun=true`), `GET /api/portfolio/trades/template`.
9. **Screen:** a **Trades** entry on the Portfolio screen (button/drawer): import wizard (account, file, preview, import and rebuild), import history with Undo, **Add trade**; a **Trades** section in the holding drawer (the holding's transactions, void, *Rebuild lots* with its preview); the lot list marks `from trades` lots read-only.

## Review before approval (2026-10-13)
Gaps found in the first draft, settled here (the decisions above stand), after reading the lot model, grants and sync code:
- **Whole shares.** Lot and holding quantities are `long`: a transaction's quantity is a whole number (`bigint`); a trade whose quantity is not whole is a bad row, and a quantity that is not whole **after** the split/bonus conversion (e.g. a 3-for-2 bonus on an odd lot) makes that holding `quantity_mismatch` (reason `fractional_after_adjustment`) instead of rounding.
- **Replacing lots is allowed to delete.** The portfolio schema grants the app role DELETE on `holding_lots` (no append-only rule there), so a rebuild deletes the holding's old lots and inserts the new ones in **one unit of work** (the holding's `xmin` token guards a concurrent sync; retried once as the sync does); the audit records counts only. `holding_lots.source` gains the value `trade` (check constraint widened in the migration; still ≤ 8 characters).
- **"Nothing replaced without being shown" is enforced, not assumed.** The preview returns a `digest` of the resulting lot shapes per holding; **Import with rebuild requires that digest** and answers `409 portfolio.preview_stale` (with the fresh report) when holdings, lots, corporate actions or trades changed in between. The screen requires an explicit confirmation when hand-dated lots are replaced.
- **Ambiguous matches.** A security that matches more than one holding of the account (an NSE and a BSE row of the same ISIN) is `ambiguous` and not applied. Matching: ISIN first, else trading symbol (case-insensitive) within the account. A row whose security matches neither a holding nor a master-list NSE share/ETF falls into "unmatched securities" — stored, not applied — so a derivative or odd symbol that slips past the segment heuristics can never be applied as equity.
- **Opening-lot rules.** The opening lot has `source = import`, `uses_default_date = true` (editable); the first-import-date re-dating (P2-01b) **skips holdings that have trade lots**, and a hand edit of the opening lot's date must be before the earliest trade date (`400 portfolio.invalid`, field `acquiredOn`). A later sync that changes the quantity keeps its current behaviour; the next *Rebuild lots* recomputes `P0 = Q − net` with the new `Q`, and its preview shows **opening quantity before → after**, so a quantity change that the trades do not explain is visible, not silent.
- **Dedupe and Undo.** Uniqueness `(account_id, external_id)` applies to **non-voided** rows only (a partial unique index), so after an Undo the same file can be imported again; identical lines inside one file get an occurrence index, so two genuine identical trades are both kept and a re-import still adds nothing. Charges: a `total charges` column is used as is, otherwise brokerage/tax component columns are summed (never both).
- **Dates and times** are India time; a trade date after today (India) is a bad row.

## Amendments after the independent review (2026-10-13)
- **Opening-lot cost (decision 2).** Indian brokers' average cost `A` is a weighted-average-cost figure: a sale does not change it. The cost per share of the opening (pre-file) shares is therefore implied by `A` over everything ever bought, `c0 = (A × (P0 + B) − BC) / P0`, whether or not sales consumed the opening lot, and the pieces sold from the opening lot cost `c0` (consistent realised profit). The invariant "invested = `Q × A`" of the first draft is replaced by: **the open lot quantities add up to `Q`; with no sales in the file and an opening lot, invested = `Q × A` to within the rounding of `c0` to 4 decimals (±0.0001 × the opening quantity + 0.01); with sales the first-in first-out cost basis from the trades can differ from the broker's average-cost figure** (first-in first-out against the average-cost method differ by nature; without an opening lot the real buy costs stand). The rebuild block shows `openCostAfter`, `brokerCost`, `costDelta` and, for the fallback, `costNote`; they are part of the digest, and the screen says "cost basis differs from broker by ₹x".
- **Identity (decision 6).** A trade id alone is not unique across days: the identity is `t:yyyyMMdd:id`, also for the repeat check inside a file.
- **Undo.** Added `?dryRun`, the counts of lots it cannot restore and the list of holdings it could not rebuild (see Consequences).
- **Limits of the report.** A preview lists every held or master-listed security and at most 200 unmatched ones (`securitiesTotal`, `unmatchedListed`); the digest covers all.

## Amendments
- **Rebuild of one holding has no digest (frontend, 2026-10-13).** `POST /api/holdings/{id}/rebuild-lots?dryRun=false` re-computes the rebuild server-side when it is applied; the confirmation dialog's counts come from the dry run made when it opened, so a holding that changed in between is applied as recomputed (or answered `applied: false`), unlike the import, which refuses a stale preview.

## Consequences
- Returns, XIRR, the value history, the benchmark and the long-term-soon rule become exact for holdings whose trades are loaded; holdings without trades keep today's behaviour and flags.
- The broker stays authoritative for quantity and total cost; a file that disagrees is shown and not applied, so a wrong or partial export cannot corrupt the portfolio.
- Rebuilding replaces hand-dated lots, so it is always previewed and audited (counts, no per-lot data). **Undo derives, it does not snapshot:** it cannot bring back hand-dated or sync-added lots that an earlier rebuild replaced — the holding returns to one default-dated lot of `Q` at `A` (or to the shape of the remaining trades). The Undo dry run (`?dryRun=true`) and its counts (`handDatedLotsReplaced`, `syncLotsReplaced`, `notRebuilt`) say so before the owner confirms.
- Corporate-action handling depends on the owner having confirmed splits/bonuses on the Data screen; the preview says when it did.
- Broker-specific exports need a profile each; the generic format and template make the first import possible without guessing.
