# 0176 — The option-chain recorder stores five-minute index chains and a daily stock pass from two new allow-listed Data API endpoints, behind three gates, its own cap and no reader

- **Status:** Proposed (built in P14-02 from the owner-Approved spec, 2026-11-01, with the recommended answers). Becomes Accepted when the owner has read it and the five-session pilot (criterion 12) has filled the "Pilot" section below. A safety decision: two new broker endpoints, the Data account's token on a new HTTPS client, continuous disk growth.
- **Date:** 2026-11-01.
- **Relation to other ADRs:** follows [0133](0133-new-broker-endpoints-enter-the-allow-list-in-the-commit-of-the-slice-that-uses-them-index-and-vix-history-needs-none.md) (an allow-list row enters in the commit of the slice that uses it) and [0097](0097-the-p7-phase-check-ten-consecutive-scheduled-sessions-from-stored-plan-runs-and-never-met-on-fewer.md) (the pinned list changes in the same commit), copies the recorder pattern of [0135](0135-the-depth-recorder-stores-the-20-level-book-of-up-to-50-shares-about-once-a-second-behind-three-gates-a-disk-guard-and-no-reader.md) and [0173](0173-the-trade-tick-recorder-stores-last-trade-updates-of-the-depth-set-when-cumulative-volume-rises-on-a-second-quote-socket-behind-three-gates-its-own-cap-and-no-reader.md) (three gates, a fresh-password switch, a disk guard that deletes nothing, no reader), uses the reference data of [0175](0175-option-contracts-of-a-configured-underlying-list-are-kept-from-the-master-refresh-in-their-own-schema-with-a-dated-lot-history-and-dated-rule-epochs-never-in-the-master-list.md), and the fresh password of [0091](0091-auto-approval-is-an-option-behind-an-owner-setting-default-off-a-new-approval-kind-the-database-checks.md) and [0128](0128-owner-act-capabilities-are-one-insert-only-log-with-a-generic-gate-by-name-off-by-default-and-switched-on-only-by-the-owner-with-a-fresh-password.md). No order, no order-capable scope ([0083](0083-the-plan-record-insert-only-state-trails-owner-only-approvals-lapse-by-default-and-no-order-by-name.md)).

## Context
Dhan sells no history of the option chain's bid and ask, open interest, IV and Greeks. Every later P14 slice that prices a spread, a half-spread or a credit structure needs that history, and it can only be built forward in time, so the recording has to start early (D1, D13 of P14-00). The expired-options API (P14-03) gives candles, not the book.

## Decision
1. **Two exact allow-list rows, no wildcard.** `POST https://api.dhan.co/v2/optionchain` and `POST https://api.dhan.co/v2/optionchain/expirylist` are two `Uri` constants in `BrokerEndpoints.Allowed`, each with no query (not even `?`), a trailing slash, another case, host, port or scheme refused. `PlanPhaseCheck.PinnedAllowList` gains the same two lines in the same commit; `POST /v2/charts/rollingoption` and `/v2/charts/historical` stay refused (they enter with P14-03). The class summary gains one `<para>`; no existing line of the guarded files changed. The architecture test `The_xd_api_allow_list_files_are_byte_for_byte_the_committed_ones…` guards `BrokerEndpoints.cs`, `PlanPhaseCheck.cs` and `BrokerAllowListTests.cs` and tolerates only an empty diff against HEAD or a diff whose added lines are exactly the literal set of this slice (nothing removed or changed); after the commit the diff is empty and the guard is strict again, so any later edit must change that literal set in the same commit, with an ADR.
2. **One client, one throttle.** `DhanOptionChainClient` sends with the Data account's token and client id (headers `access-token`, `client-id`) through the existing credentials port; it logs nothing at all (no logger is injected), so no URL, token, client id or body can reach a log, and a reply carries only an outcome word, the HTTP status, a well-formed Dhan code (`DH-9xx`, or `80x`) and, for a success, the bytes for the recorder to read. `ChainThrottle` (a singleton) makes any two requests of the process, of either kind, at least `Options:Chain:SpacingMs` apart and never less than 3,000 ms; a larger spacing asked for after a rate limit applies to the very next request. **Rate limit, UNVERIFIED:** Dhan says "one unique request every 3 seconds"; whether that is per user or per (underlying, expiry) is unknown, so the strictest reading is built and the pilot may relax it in a later ADR, never in the settings (`SpacingMs` has range 3000 to 60000).
3. **What is asked and when (`ChainSlotPlanner`, pure).** Trading days only. Expiry lists once per underlying from 09:15. Slots every `IntervalMinutes` (5) from 09:20 to 15:30 (75). Each slot asks each index of `Options:Chain:IndexExpiries` (default NIFTY: the next 3 weekly and the next monthly **that is not among them**, so 4; BANKNIFTY: the next 2 monthly), 6 requests, 18 s of the 5 minutes. The stock pass (the other underlyings of `options.underlyings`, 2 expiries each) runs between the index slots from the first slot at or after 14:30, only while the next slot is further away than one spacing plus the timeout, and what is not asked by 15:25 is a `window_end` gap. A slot still running when the next starts is closed and its missing requests are `slot_overrun`; a slot already over when the recorder starts is never caught up; a restart in the middle of a slot runs the rest of that slot.
4. **Rows (`OptionChainParser`, pure, never throws).** One row per (slot `ts`, underlying, expiry, strike, side). The strike key (`"25650.000000"`) and every price become integer paise, half away from zero. A zero or missing bid, ask or last price is **null** with `no_bid` (1), `no_ask` (2) or `no_trade` (4), and the quantity goes with its price; an IV that is not a positive number, a delta outside -1..1, a negative gamma or vega, or any value that is not a finite number is null with `bad_greeks` (8) (a negative theta and a negative put delta are normal); a bid above the ask is `crossed` (16) and both are kept as sent. A missing field is null, never zero. Only the strikes within `StrikesEachSide` (30 for indices, `StockStrikesEachSide` 15) strikes of the one nearest the underlying's last price are kept. `oi`, `prev_oi`, `volume` and `prev_volume` are **nullable** (the spec had them not null): a field Dhan did not send is not a zero. A body that is not the documented shape is one `bad_body` gap; a chain with no strike is `no_data`.
5. **A failed request writes a request row and no snapshot.** `options.chain_requests` has one row per planned request: slot, kind, underlying, expiry, outcome (`ok`, `rate_limited`, `timeout`, `server_error`, `no_data`, `bad_body`, `token_refused`, `not_subscribed`, `slot_overrun`, `window_end`, `disk_stop`), HTTP status, Dhan code, rows newly stored, latency. Inserts are `ON CONFLICT DO NOTHING` on the primary key `(ts, underlying_id, expiry, strike_px, side)`, so a re-run of a slot inserts nothing; the request row of the re-run says `rows = 0`. The request row and the snapshots of one request go in one transaction.
6. **Failure handling.** `DH-904` or HTTP 429 doubles the spacing for the rest of the slot; three slots in a row with a rate limit end the run (`rate_limited`, failed, so the owner is told), and the supervisor waits 15 minutes. `DH-901`, 401, 403, 807, 809: `token_refused`, nothing is sent until the token changes (a fingerprint of the credentials, never the token). `DH-902`, 806: `not_subscribed` ends the day. `DH-907`: `no_data`. A timeout (`TimeoutSeconds`, 10) is `timeout` with no retry. 5xx, `DH-908`, `DH-909`, a network failure or an answer over 4 MB: `server_error`. No credentials at all: the run ends `no_token` and the supervisor waits. A store that fails for one request is logged by type, counted as a gap (never as ok), and the session goes on. A slot missed after the session started (a sleeping Mac) is written as `slot_overrun` for the pairs the cached expiry lists plan. **Shortcut:** the 15-minute rate-limit pause is held in memory; a restart of `xd-feed` inside it forgets the pause (the 3-second throttle still holds, and a repeated limit pauses again after three slots).
7. **Three gates, all default off, and an unreadable gate is a closed gate.** (a) the deployment flag `Options:Chain:Enabled` (`Options__Chain__Enabled`, compose `XD_OPTIONS_CHAIN_ENABLED`, default false; a restart changes it); (b) the owner's stored switch, the newest row of `options.chain_recorder_switch` (no row = OFF), changed by `PUT /api/options/chain-recorder {enabled, reason, password}` with a **fresh password on every change, ON and OFF** (`OwnerAct`, no step-up window opened or used up), the actor taken from the session (never from the body), one account event `OptionChainRecorderSwitched` (category `service`, detail `switch=<id> option_chain_recorder=on|off`, never the reason), 401/423 from the password check and 400 `options.reason_invalid`; (c) the service `option-chain-recorder` of the Services screen, a window service 09:14 to 15:31 on trading days, **registered paused**, run by `xd-feed`, retries 0, no catch-up, notify on failure, "Run now" refused. With any gate closed or unreadable nothing reads the credentials, builds a request or sends (the supervisor's tests count credential reads at zero). `GET /api/options/chain-recorder` returns the switch, its history and the reasons it is not running. The host is `xd-feed`: it alone of the background hosts holds the vault key the Data account's token needs (`xd-worker` does not).
8. **Disk guard, its own cap plus the shared floor; the app deletes nothing.** Before each start and before each slot `DepthDiskGuard.Check`: the stored size of `options.chain_snapshots` above `Options:Chain:MaxStoredGb` (4) ends the run `disk_budget` (the slot's planned requests are written as `disk_stop` gaps), free space below `Options:MinFreeGb` (20, the same default as `Depth:MinFreeGb`) ends it `disk_free`, a warning at 80 %. A disk stop holds until the recorder is next not wanted (the owner pauses the service, switches off, or the window ends) and the guard agrees at the next start. An unreadable free space leaves the size cap in force and is a note on the day's row.
9. **Schema (migration `AddOptionChainRecording`, raw SQL).** `options.chain_snapshots` is a hypertable with 7-day chunks, compressed after 7 days, segmented by `underlying_id, expiry`, ordered by `ts, strike_px, side`, with **no retention policy**, no foreign key, and checks on every coded column; `chain_requests`, `chain_sessions` (one row per day, written when the day is over; a past day with request rows and no end row is closed `crashed` at the next start) and `chain_recorder_switch` (the columns of `depth_recorder_switch`) are plain tables. `xd_app` is granted SELECT and INSERT table by table (`GrantTableToAppRole` then `MakeAppendOnlyForAppRole`); `xd_exec`, `xd_mcp_read` and `xd_mcp_sql` are granted nothing. `Down` drops the four tables.
10. **No trading use, no reader.** `IOptionChainStore` has no method that returns a row (an architecture test lists its five methods); only `OptionChainStore` names the table in SQL; no route returns snapshots (`GET /api/options/chain` belongs to P14-16); the Domain, `Simulation`, `Strategies*`, `Indicators`, `SimExport`, `SimReader`, `XDrishti.Execution` and the Application namespaces Planning, Learning, Portfolio, Execution, LiveTrading, Live, Selection, Research, Lab, Reporting, Paper, Depth and Ticks reference no chain type, and the chain code references none of the order, plan, live-session or other recorder types; nothing in it is an active-set provider. With the recorder failing, no other service changes: it has its own loop, its own run record, its own heartbeat row (`xd-options`) and its own try/catch.
11. **Logs** `options.chain.request|gap|slot|disk_warning|disk_stop|token_refused|paused` (event ids 6911 to 6940) carry counts, ids and outcome words only; a test pins the range, the prefix and the absence of any secret, URL or symbol placeholder.

## Disk budget
About 58,600 rows a day (6 index requests x 75 slots x 61 strikes x 2 sides = 54,900, plus 60 stock requests x 62 = 3,720), 14.5 M rows a year, about 185 B raw each: **2.7 GB a year raw, about 0.54 GB compressed at the planning ratio of 5:1 (UNVERIFIED, 3:1 to 8:1)**. The 4 GB cap is about 7 years at the planning ratio. With everything on, free space of 79 GiB is needed (depth 40, ticks 12, chain 4, backfill 3, floor 20): the owner's VM disk enlargement to 160 GiB is the recommended step; options alone need 27 GiB, ticks plus options 39 GiB, depth plus options 67 GiB. `xd-backup` must exclude this table's data like the depth and tick tables.

## Consequences
- The pilot (five sessions, owner-run) fills the table below; until then every shape in `docs/research/dhan-samples/optionchain-*.json` is UNVERIFIED.
- P14-04 reads `options.chain_requests` and `options.chain_sessions` for coverage and the 6.5 % parity rate; P14-07 reads half-spreads only after 60 sessions and only through a reader slice of its own.
- A sleeping Mac or an expired daily token loses those slots for good; each is a counted gap.
- Vendor IV and Greeks are a black box (model and rate unknown): they are stored as sent and labelled, never recomputed here.

## Known limits (second review, 2026-11-01)
- The allow-list guard (`ExecutionBoundaryArchitectureTests`) passes silently if `git` cannot start or exits non-zero, does not pin `git diff` output options (a user config with colour or an external diff tool could blank the diff), and reads stderr without a timeout; a later diff adding exactly the same lines a second time would also pass. Owed: `git --no-pager -c color.ui=never diff --no-color --no-ext-diff -U0 HEAD`, fail when `.git` exists and git exits non-zero.
- The no-reader architecture test lists assemblies by hand (a new `src` project would not be scanned), its `OptionChain.*` exemption is by name prefix only, and it has no positive control. Owed: build the list from `XDrishti.slnx`, limit the exemption by namespace, add a control.
- After a failed store write the request log still says `outcome=ok` and no gap line is logged, while the counts say gap. Slots skipped during a 15-minute rate pause get no `slot_overrun` rows.
- Recorder tests that end by `StopAsync` still rely on a 4 x 5 ms quiet poll, so they could in theory flake under load; the fix is to wait until the fake clock has a pending timer (`SettableClock.NextTimerDue`) before each advance.
