# 0097 — The P7 phase check: ten consecutive scheduled sessions from stored plan runs, and never MET on fewer

- **Status:** Proposed (spec [P7-18](../specs/P7-18-the-phase-check.md), approved under the owner's standing run instruction of 2026-10-22; built 2026-10-24). Becomes Accepted when the owner has read it.

## Context
The roadmap exit of P7 is "plans published 10 consecutive sessions unattended". It takes ten trading sessions of wall-clock time and the owner's switches (the services start paused and the selection builder is OFF), so it cannot be argued from a test. P7-00 question 10 asks what "published", "unattended" and "consecutive" mean; the owner's binding decisions say P7 places no order, is paper only, and has no auto-approval unless the setting is ON (default OFF). A check that echoed "a plan exists" would print MET on a handful of manual runs.

## Decision
1. **One pure function, three calls.** `PlanPhaseCheck.Evaluate` takes plain stored facts and returns the twelve acceptance criteria of P7-00, the ten sessions of the window, the setup and the limits. Each criterion is `MET`, `NOT MET` or `NOT EVALUABLE`; a MET that rests on something the check does not run carries a caveat in its label (as ADR 0080).
2. **The exit (criterion 1), as P7-00 Q10 recommends.** A session counts when a scheduled (not manual) `nightly` run published a plan row for it, **including the skeleton or empty plan**, which is reported separately as "plans with zero primary tickets" (and "skeleton") and printed in the MET label. A session with a manual attempt (published or failed) is not unattended; a session with a failed-closed attempt breaks the run **even if a scheduled retry published** (a bad-data or lapsed-token day is not an unattended success; gate and reason are listed). "Consecutive" is the trading calendar's sessions: the window is the last ten trading days ending at `--through`, a weekend or a confirmed holiday between two is not a session and does not break the run, a trading day with no run row is a gap and does. NOT MET when a fact is against the window; NOT EVALUABLE when nothing is against it but fewer than ten sessions have any history; MET only for ten counted sessions in a row (re-checked in code before it is printed: exactly ten sessions, distinct ascending dates, ending at the requested date). The caveat is part of the headline, the JSON `exitCriterion` and the log: all-empty plans read `MET (COUNT ONLY: all 10 plans are empty, no ticket was ever proposed)`; `exitVerdict` is the bare word.
3. **The window ends at the newest due session.** Before the `nightly` time plus ten minutes on the evening of the last closed session, with no row yet, that session is not yet due and the window ends before it; `--through` overrides (a later date than the newest planned session is refused).
4. **Stored records only; tests are referenced, not run.** Judged from records: ten sessions (1), fail closed (2: consistent rows, all six gates seen failing before MET), no order (4: the allow-list, below), honest evidence (6: no-order sentence, limits and per-ticket evidence on the stored plans), human in the loop (7: decisions before the cutoff, approvals backed by rows, no ticket left undecided long after the cutoff, auto approvals counted by actor kind and a fact against the workflow when dated before the first stored ON row; tickets that ever were approved, armed or triggered, including those that later expired, need an approve row; caps of 60 plans and 200 autonomy rows are printed), accounts (8: paper-only allocations), grading (9) and journal (11: counts and no double-linked fill). Never judged here: look-ahead (3), determinism (5), the live active set (10) and the process steps (12): NOT EVALUABLE with the names of the tests that prove them.
5. **The allow-list is read from the code and compared with a pin.** The Dhan allow-list is `BrokerEndpoints` in Infrastructure, not a config file. A read-only port `IBrokerAllowList` exposes its declared entries, derived from the single rule table `IsAllowed` uses (method, host, path, query keys only) and a probe `Allows(method, url)`. The Domain holds a pinned list of the eight entries and ten probe requests (orders, super and forever orders, positions, funds, kill switch, market-feed LTP) that must be refused. A difference or an allowed probe is NOT MET; changing the list is an owner-approved item and changes the pin in the same commit. The architecture tripwire is a test and is only named.
6. **The setup is part of the answer.** The state of the services (`nightly`, `eod`, `portfolio-broker-history` needed for the exit; `suggestions`, `review-cutoff`, `preopen`, `plan-expiry`, `weekly`), the owner's switches (builder `UseSelection`, open book `AssumedEmpty`, `autonomy.auto_approve_tickets`, `autonomy.promote_from_reserve`) and the **blockers**: which required services and needed switches are still off and what that stops. The autonomy switches are the owner's choice, not part of the exit, and are never blockers; the check turns nothing on.
7. **Limits are part of the report**, in the object and in every text: about 2.1 years of data and no hold-out; plans provisional (no cell Active before P10); market gate, events, results, ban and surveillance data have no source; the empty-plan risk; the pre-open quote format unverified; "unattended" read from the manual flag only (a code change or an owner action is not recorded); the Dhan token lapse; stored records only; a catch-up run counts as scheduled and hand-run eod or sync runs are not read; read caps; the Planning switches are read by the process that ran the check; nothing written.
8. **Read only.** `xd plan phase-check [--through DATE]` and `GET /api/plan-runs/phase-check` call one handler that only reads (a test lists every call on every store); the verb exits 0 whatever the criteria say. Log ids 4790 to 4791; no table, no migration.

## Consequences
- Today the exit can only read NOT EVALUABLE or NOT MET: the services other than `nightly`, `eod` and the sync are paused, the selection builder is OFF so any published plan is the empty skeleton, and the open book is unavailable. The check names those switches. Ten real scheduled sessions need the owner to switch them ON and ten trading days to pass without a manual run or a failed gate.
- A failed bad-data day sends the count back to zero; with a Data-account token that lapses about daily the exit may take more than ten calendar sessions (P7-00 risk 10).
- Ten empty skeleton plans would meet the count; the label says so ("10 of 10 plans have zero primary tickets, 10 of them skeleton"). Whether that is enough is the owner's call (P7-00 risk 1); this check does not decide it.
- The pinned allow-list makes any change to the broker endpoints visible in two places: `BrokerAllowListTests` fails and the phase check reads NOT MET until the pin is changed on purpose.

## First read on the owner's data (2026-10-24)
`scripts/xd.sh plan phase-check` against the local database: two run rows exist, both `failed_closed` at `selection-inputs`, both manual (started by a person for the planned session 2026-10-26); no plan is stored. The window (2026-10-12 to 2026-10-26, skipping 2026-10-17/18/24/25 weekends and the calendar's closed 2026-10-20) therefore reads: nine sessions with no history, one `manual_run` session, the exit **NOT MET** with a streak of 0; criterion 2 NOT EVALUABLE (one gate seen failing of six), 4 MET with its caveat (the eight pinned entries, ten probes refused), 6 to 9 and 11 NOT EVALUABLE (no plan, decision, grade or fill stored), 3, 5, 10 and 12 NOT EVALUABLE by design. The running stack and the host process both show the builder and open-book switches OFF and `suggestions`, `review-cutoff`, `preopen`, `plan-expiry` and `weekly` paused; `nightly`, `eod` and the portfolio sync are enabled. Nothing was fabricated and nothing was written.

## Alternatives considered
- **Count a session as good when a scheduled retry published after a failure.** Rejected: the owner's rule is that a fail-closed day breaks the run; a retry setting would otherwise hide bad data days.
- **Require at least one primary ticket per plan for a MET.** Rejected for the check (Q10 recommends counting empty plans): the count stays honest and the zero-primary share is printed beside it; the owner can decide to tighten it.
- **Run the architecture and unit tests from the verb.** Rejected: slow, environment dependent, and the check would then trust a fresh run of the code instead of a stored record; `scripts/check.sh` is where the tests run.
- **Read the allow-list from a file.** There is none: it is code. A port over the code with a pin was the smallest honest reading.
- **A stored record of each check.** Rejected: it is recomputed from insert-only records on demand; storing it would add a second place to disagree.
