# 0058 — Lab runs: the table that is the queue, the quick test, the run identity and the restart rule

- **Status:** Accepted (spec [P5-02](../specs/P5-02-lab-runs-job-run-record-and-quick-test.md), which the owner approved on 2026-10-22, questions 1 to 6 as recommended; built on 2026-10-22). The text of this ADR has not been read by the owner. Three points differ from the spec's wording and are listed under *Deviations*.
- **Date:** 2026-10-22.
- **Relation to other ADRs:** [ADR 0037](0037-simulation-conventions-and-the-two-stage-seam.md) (the run key), [ADR 0039](0039-an-engine-module-is-reached-from-an-adapter-in-infrastructure-never-from-application.md) (engine modules are reached through a port), [ADR 0041](0041-the-simulate-verb-the-export-library-and-the-pipeline-in-the-host.md) (the pipeline lives in the host; the export library is named by the API only), [ADR 0045](0045-the-result-store-sim-runs-and-sim-trades.md) (the result store, idempotent by run key), [ADR 0024](0024-live-feed-xd-feed-and-live-prices.md) (the hub), [ADR 0056](0056-stored-strategies-the-lab-tables-the-seed-and-loading-by-version.md) and [ADR 0057](0057-the-lab-api-validate-store-and-read-strategy-versions.md) (the stored versions the runs test).

## Context
The owner can store a strategy version (P5-01). The next step is to run it: a quick test of a stored version over a basket or a list of symbols, started from the API, carried out in the background, reporting progress, and recorded so that it can be read, cancelled, and found again. The result is trades and counts, never a verdict (P5-03 to P5-06).

## Decision
1. **`lab.lab_runs` is the record and the queue** (migration `AddLabRuns`, reversible). One row per run: the identity (key, strategy id, version, hash, universe, window, method, configuration hash, engine version), the state and stage, the progress, the keys of the simulation runs produced (`sim_run_keys text[]`, a soft reference to `research.sim_runs`: no foreign key across schemas), the counts, the located problems, the stage log, the labels, the error, the host that claimed it, the cancel flag and the times. The row has a foreign key to the stored version by hash. `xd_app` has SELECT and INSERT, UPDATE **by column** on the state columns only (`state, stage, progress_*, sim_run_keys, counts, problems, stages, error, host, cancel_requested, started_at, finished_at, updated_at`), and no DELETE or TRUNCATE; the migration does not call the schema-wide grant, so the append-only strategy tables are not loosened (a grants test pins both).
2. **States and moves** (`Domain/Lab`): `queued`, `running`, `succeeded`, `failed`, `cancelled`, `interrupted`. Legal moves: queued to running or cancelled; running to succeeded, failed, cancelled or interrupted; nothing leaves a final state. Every update that moves a run is guarded by the state it expects (`WHERE state = 'running'`), so a finished run never changes.
3. **Run identity** (`LabRunIdentity`): the SHA-256 of a fixed text of the strategy hash, the universe (label and the **sorted** instrument ids), the window, the method, the SHA-256 of the configuration text (`quick.years`, `quick.symbols`, the fills and the cost basis as `none` or `<sheet id>|<rates hash>`) and the engine version. A **partial unique index** on `key` where the state is queued, running or succeeded makes a second post of the same input the same run (`200` with that run, whoever races: twelve parallel posts leave one row, tested); a failed, cancelled or interrupted run frees the key, so starting it again is a new row with the same key.
4. **The quick test** (D2): the last `quick_test.years` (1) of stored data ending at the last stored session (the India date of the last stored bar), clipped to the first stored session, or the window posted; at most `quick_test.symbols` (30) instruments. A larger universe is cut to the first 30 of a **seeded shuffle of the sorted ids** (`QuickSample`: SplitMix64 written out, because the platform generator is not promised to be stable; the seed is the first eight bytes of the SHA-256 of the sorted ids and is stored in the run). The post resolves the basket or the symbols **once**; the run keeps the list, so a basket changed later changes nothing. The run is replayed by `RunSimulationHandler` with the stored version **by hash**, the first timeframe the verb would choose (the built-in's default, else 15m if declared, else the first), the modelled fills, `InstrumentIds` in ascending id order, the charge sheet named by `StrategyLab:CostSheetId` (default `default`) when it is stored and in force on the first day, otherwise gross. Then the run is stored by `StoreRunHandler` with the record text and the digests of `trades.csv` and `open_at_end.csv` made by the export library exactly as the verb makes them (`IRunRecordWriter`), so a Lab run and a verb run of one input are one stored run: the equality test runs the verb with `--store` and then the Lab run and finds the same key, one `sim_runs` row, and no conflict.
5. **Stages** (`LabRunner`): `validate` (the stored version and the universe are there), `compile` (`IStrategyChecker.Check`, the same read and compile as the validate endpoint under today's rules; warnings are kept and do not fail the run), `quick_test`. Each is logged with start, end and the number of problems. A failed validate or compile ends the run `failed` with the located problems and runs nothing, so no `sim_runs` row is written.
6. **A run is stored whole or not at all.** The replay is in memory until it is complete; the owner's cancel is seen between instruments (the handler checks the token after each) and once more just before the store is written; after that the store is allowed to finish. A cancel of a queued run is immediate; a cancel of a running one sets the flag, the job's watcher (every 100 ms; the database is asked every 500 ms) cancels the replay, and the job ends the run `cancelled` and sends the last event. A host stop leaves the run `running` (see 8).
7. **Progress** (`ILabProgress`, one port for the page, the CLI and the tests): `labRunProgress { runId, state, stage, done, total, message }` and `labRunFinished { runId, state }` on the existing hub `/hubs/events`, to every connected screen (the hub already needs the owner's session); a `ProgressThrottle` lets at most four progress events a second through per run (the last event, `labRunFinished`, is never throttled). The instruments done are reported by an optional `IProgress<int>` on `RunSimulationQuery`, the only change to the simulation use case. The progress is also written to the row (stage, done, total, stage log), so `GET /api/lab/runs/{id}` serves the same data and a missed event costs nothing (tested with the hub connected, and the GET after it).
8. **Restart** (D4): at the start of the host `LabRunDispatcher.RecoverAsync` makes every run that this host (`xd-api`) had `running` `interrupted`, sends its last event, and never resumes it; a queued run is still queued and is picked up. The owner starts an interrupted run again; that is a new row with the same key.
9. **Parallelism**: `strategy_lab.max_parallel_runs` (2) runs at once; the rest stay queued in the table and are claimed with `FOR UPDATE SKIP LOCKED` as slots free (two claimers never share a run). `LabRunDispatcher` (Application) holds the loop and is tested with a gated executor; the hosted service `LabRunService` in the API only calls it, and is off when `StrategyLab:RunWorker=false` (the integration tests drive `DrainAsync` themselves).
10. **API** under `/api/lab/runs`: `POST` (202 with the run and a `Location`; 200 with the run that holds the key; 422 `lab.invalid_input`, 404 `lab.not_found` for the strategy, version or basket, 409 `lab.no_data`), `GET` (filters `strategyId`, `state`, `limit` 1 to 200), `GET {id}`, `POST {id}/cancel` (202, 404, 409 `lab.not_cancellable`). The response of the post is the full run (a superset of the spec's `{ id, state, key }`). The labels of a run carry the exploration line, the cost basis, the window, the sample and the stored data range (D6); `verdict` is always null.
11. **Logs** `lab.run.queued|started|stage|finished|failed|cancelled|interrupted|crashed|dispatcher_failed` (ids 4439 to 4447): the run id, a key prefix, the stage, the code and counts, never a strategy text, a trade or a secret (a test scans the log of two runs for a strategy's words, for trade fields and for the owner's password and the vault key). An unexpected exception ends the run `failed` with the code `lab.run_crashed` and no message.

## Deviations from the spec
- **Hangfire is not used.** The spec said the worker references Hangfire; it does not (a comment in the project file only; no package is pinned or restored). Adding a job server with its own tables for one queue of one user would be a new dependency and a second place where state lives. The table is the queue and the dispatcher polls it (1 s; `StrategyLab:PollMilliseconds`). Retries are off by construction (a failed run is a result). If a second kind of background job ever needs a scheduler, Hangfire can be added then and the dispatcher replaced behind `ILabRunExecutor`.
- **The job runs in `xd-api`, not `xd-worker`.** The architecture test allows only the API project to reference the export library (`XDrishti.SimExport`), and a stored run needs the record text and the digests the library renders (ADR 0041). Rather than relax the rule or copy the renderers, the job is a hosted service of the API next to the data-job and refresh workers. It also removes the cross-process path to the hub: the progress port is called in the process that owns the hub, so neither `LISTEN/NOTIFY` nor polling is needed for progress (the spec's question 6 does not arise). The cost is that a long run shares the API's CPU and that a restart of `xd-api` is the "worker restart" of criterion 7. Moving the job to `xd-worker` later needs a record writer outside the export project and a notify path to the hub; the ports (`IRunRecordWriter`, `ILabProgress`, `ILabRunExecutor`) are where that change would go.
- **Settings are `StrategyLab:*` configuration** (`QuickYears`, `QuickSymbols`, `MaxParallelRuns`, `CostSheetId`, `PollMilliseconds`, `RunWorker`) with the defaults of doc 16, bound by the host into `LabSettings`; the database-held configuration of ADR 0002 does not yet exist for this section.

## Consequences
- The API contract and the frontend types are regenerated (`/api/lab/runs`, the two hub events and their types).
- The Lab module reaches the simulation only through its public handler and the three ports above; no engine type is named in the Lab code. The architecture tests stay green unchanged.
- `RunSimulationQuery` has an optional second argument; every other caller is unchanged.

## Honest limits
- **The quick test is exploration.** It runs on a sample of at most 30 instruments of whatever the basket holds (a seeded shuffle, not the most liquid: liquidity is a universe-layer idea that does not exist yet), over the last year of the stored data, in-sample, with no hold-out (ISS-19). Every run says so in its labels.
- **The sheet can change between the post and the job.** The cost basis is decided at the post for the key and again by the job for the run; if the owner stores or edits the sheet in those seconds the run may be costed differently from its key's basis. The run record has the sheet it used.
- **Not measured on the owner's data.** The 1 to 2 minutes of doc 11 §3 for 30 symbols and one year (criterion 12) is not measured here: the tests run on the invented three-day fixture, and the owner's database was not touched. The first real run on `data/` should be timed and the figure written here.
- **Progress after a restart.** A run interrupted by a restart keeps the progress it had last written; it is never shown as complete, but its numbers are those of a partial replay.
- The dispatcher polls once a second, so a posted run starts within about a second; there is no wake-up signal.
