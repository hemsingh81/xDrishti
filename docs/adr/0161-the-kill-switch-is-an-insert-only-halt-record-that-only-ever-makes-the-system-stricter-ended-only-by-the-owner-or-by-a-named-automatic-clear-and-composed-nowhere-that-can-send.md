# 0161 - The kill switch is an insert-only halt record that only ever makes the system stricter, ended only by the owner or by a named automatic clear, and composed nowhere that can send

- **Status:** Accepted (decided in P12-05 under the owner's standing run instruction; spec [P12-05](../specs/P12-05-kill-switch-and-halts.md)).
- **Date:** 2026-10-30.
- **Relation to other ADRs:** builds on ADR 0155 to 0160 (`IHaltSource` and `IHaltRequests` were the ports; `SquareOffService`, `ProtectiveGuard` and the alarms are used as they were); follows ADR 0151 (the P11 halts are advice and stay a separate, read-only matter). The xd-api allow-list and `Infrastructure/Brokers/BrokerEndpoints*` are not touched; no other project references Execution; `deploy/` is untouched; no call to Dhan was made.

## Context
A halt must stop new entries at once, never block a protective or reduce-only action, survive a restart, and be ended only on purpose. The owner's limits stand: nothing may become able to send, live is refused everywhere, an unreadable halt source means halted, and clearing is an owner act with a fresh password.

## Decision
1. **One record, insert-only, two ends.** `execution.halts` plus exactly two places where a halt ends: `halt_releases` (the owner's act, written by `xd_app`, the only INSERT that role holds on a halt table) and `halt_auto_clears` (written by `xd_exec`, only for the codes that may clear themselves). A halt is active while it has neither. Every table of the slice refuses UPDATE, DELETE and TRUNCATE for every role including the owner. Triggers enforce what a database can: the owner actor, the halt exists, not already ended by the other door, a freeze is never released, an exit_all only when the positions are flat, a drawdown halt only with a 20-character review. The broker's switch is never asked for a code that clears itself (check constraint).
2. **Permission is a table, not an opinion.** `HaltRules.Permits` is the spec's 25 cells; the effective state is the strongest active halt of the system and the account. A halt only removes permissions. Under `freeze` the two protective actions remain, flagged as needing a fresh broker read. An unknown level permits nothing.
3. **The gate reads the record every time.** `HaltService` is both the request door (`IHaltRequests`) and the gate (`IHaltSource`): any halt reads as `Halted` for the entry gate (stricter than per-account), an unreadable record as `Unreadable`, and both block entries. No cache, so the next read after a commit sees the halt; the second gate check inside the send path (already there) turns an entry caught in its write-ahead into `halted_before_send`. A request below its trigger's own level is raised, never lowered; the owner's button cannot come through the system door.
4. **Start is cheap and carried out by xd-exec; release is not.** The API leaves a command row (session and CSRF, no password; exit_all needs the step-up window because it realises losses); `xd-exec` records the halt, and a halt it cannot write is not answered so it is retried. The API's release checks `Live:Writes:Enabled` before the password, then a fresh password, the actor from the session and every rule, and answers all refusals together (409). The audit carries ids and codes and no free text.
5. **Clearing is never automatic by accident.** Only seven codes may clear themselves, by a quiet period or a number of good reads; a bad or `unavailable` reading restarts the count, so an unreadable source can never clear a halt. The two codes that wait for the readiness fact of P12-11 clear nothing yet.
6. **Cancel and exit-all reuse what exists.** At `cancel` the enforcer cancels working entries (three attempts, a second apart, each judged by the book, then an `exit_failed` alarm) and never touches a protective leg. At `exit_all` it runs `SquareOffService` with the square-off clock forced for the halted accounts, so the flatten is the same reduce-only, re-priced, stop-last sequence already tested, not a second copy. At `freeze` it does nothing.
7. **Kill switch and drill, built as ports and fakes.** The broker's switch is a port with no implementation, called at most once per halt and only when flat; a failed or unknown answer is recorded and never repeated. The drill builds its own sender with a refusing transport and proves that the gate stops an entry before the transport, in how many milliseconds, that the table still lets a stop through, and that it can clear its own halt; it refuses on any position, working order or other halt.
8. **Composed: only what can only make things stricter.** The halt store, `HaltService` and the `halt` command are composed in the record composition. `IHaltSource` stays `ClosedHaltSource`; the enforcer, drill, coordinator and `IBrokerKillSwitch` are composed by no host; tests pin this (service provider and source text).
9. **Settings.** Ten registry settings, all inside compiled ranges, `exec.broker_kill_switch_on_halt` default false: drawdown 8.0, disaster 3.0, feed loss 15 s, runaway 6 in 10 s, reject burst 5, crash loop 3, clock skew 2,000 ms, index 9.0 percent, outage 60 s. `exec.broker_pnl_exit` is not added (nothing reads it).
10. **Not built, owed.** The Dhan kill-switch and P&L-exit calls (UNVERIFIED, canary C3), the evaluator loop and host composition, the drill endpoints, the P11 live halts as a `no_halt` input, `day_marks` writing, release of a freeze (needs `break_resolutions`, P12-06), the screen (P12-10). Shortcuts: the halt de-dup is check-then-insert in one statement (two writers could both insert the same halt; the effect is a duplicate, never a weaker one; upgrade: a partial unique index over active halts); the cancel retry is tick-based, its three-attempt budget is in memory (a restart resets it) and a retry is another cancel judged by the book, not a lookup (upgrade: persist the tries, use `LegLookup` once verified). Review fixes: a throwing kill-switch call is recorded `failed` and never repeated; only `loss_cap`/`disaster_loss` may ask `exit_all` and only `reconciliation_break`/`oversold` `freeze` through the system door; the drill clears its own halt in a `finally`; a halt command that keeps failing is retried at once, then after 2, 4 ... 30 s with a log line (failure class only), never given up.

## Consequences
A halt is a tested row and a tested loop, with a negative control (a gate checked once is caught on every seed). Because the entry gate's source is still closed and nothing else is composed, nothing new can send; turning the real source on is a later, deliberate step with the mode ladder.
