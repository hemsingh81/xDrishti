# 0129 — A replay job started from the screen rebuilds one stored run with one field changed, runs the existing experiment path one at a time, and never applies anything

- **Status:** Proposed (spec [P8-18](../specs/P8-18-tweak-and-re-run-from-the-ui.md) Part B, approved by the owner on 2026-10-26; built 2026-10-26). Becomes Accepted when the owner has read it. **SAFETY slice: it starts a CPU-heavy job and writes research state from a screen.**
- **Date:** 2026-10-26.
- **Relation to other ADRs:** [0128](0128-owner-act-capabilities-are-one-insert-only-log-with-a-generic-gate-by-name-off-by-default-and-switched-on-only-by-the-owner-with-a-fresh-password.md) (the capability and the fresh password), [0072](0072-experiments-same-entries-purged-folds-an-honest-rule-and-an-append-only-ledger.md) (the judge and the ledger, unchanged), [0076](0076-the-hypothesis-loop-one-knob-checked-on-stored-runs-a-state-table-and-nothing-applied.md) (nothing is applied), [0058](0058-lab-runs-the-quick-test-the-run-identity-and-the-restart-rule.md) (the queue pattern), [0100](0100-the-report-endpoints-read-the-stored-runs-through-one-query-model-with-an-evidence-block-and-net-only-by-the-owners-stored-confirmation.md) (the default report set), [0083](0083-no-order-is-placed-before-phase-12-an-architecture-tripwire.md) (no order).

## Context
`xd learn experiment` judges two stored runs; making the candidate run was a separate verb. The owner asked to do both from the Learning area. Each judged replay is a permanent trial that raises the bar of every later one for 30 days, and each stored candidate is permanent storage, so looking must cost something and must never change anything.

## Decision
1. **A job, not a second simulator.** `research.experiment_jobs` is the queue (claimed with `FOR UPDATE SKIP LOCKED`, interrupted at the next start, never resumed, retried or scheduled). The runner has four stages: `prepare` (the baseline's request rebuilt with ONE field changed), `replay` (`RunSimulationQuery`), `store` (`StoreRunCommand`, `created_by = experiment:<job>`), `compare` (`RunExperimentCommand`, the owner from the session at the start as actor). The judge, the folds, the hold-out and the trial count are those of ADR 0072.
2. **The request is rebuilt from the stored record and proven.** `ReplayBaselineReader` reads every field from the record (schema 6 only), the fill rules must rebuild to the stored text, and `ReplayPlanner` compiles the strategy without reading a bar and requires the definition hash to equal the baseline's (a stored strategy by its hash; a built-in by its id with the exit read from its definition). A baseline made with an exit override of a stored strategy, or anything that does not reproduce, is refused with the reason (`experiments.baseline_not_rebuildable`), never guessed. A test proves that the unchanged rebuild is the baseline's run key.
3. **Only entry-neutral knobs.** `ReplayKnobCatalogue`: an exit parameter that the baseline's exit has as one plain number (FIXED_RR, PARTIAL_BE, PARTIAL_TRAIL, ATR_TRAIL; the ranges of the strategy compile; t2_rr above t1_rr) and slippage upward. A strategy `parameter` is refused (it may change which entries exist); a cheaper or equal slippage is refused with the rule 3 sentence. Refused before anything is queued.
4. **Bounded cost.** One active job (partial unique index on the active states, backed by a lock in the insert), three jobs in 24 hours counting failed and cancelled (`Experiments:MaxJobsPerDay`, 1 to 10), 60 minutes (`MaxMinutes`, 1 to 240; out of range stops the host), cancellation between instruments and once more before the store (nothing stored, not a trial), a visible queue state. The identical input returns its job (queued, running or succeeded) instead of a second one.
5. **Never applies.** The job namespace may use only the run store (through the store command), the experiment ledger (through its command), the job store, read ports and the simulation query; an architecture test lists the stores it may not touch and bans members named apply, activate, promote or publish. A table checksum test hashes every configuration-bearing table before and after a full job. The result card ends with "Nothing was changed. Applying a change is your own separate act."
6. **Four layers of gate.** The endpoint asks the capability `experiments_ui` BEFORE the password (an off start neither counts toward the lockout nor says anything about the password), then the password typed again for this start (`OwnerAct`), then the handler asks the gate again, then the database trigger refuses an insert while the newest capability row is not on. Cancel is the safe direction: session and CSRF only.
7. **Replay time is measured, not invented.** The wall time of the candidate replay (`TimeProvider`), the instrument count and whether a Lab run ran meanwhile are stored and printed; the "under 10 minutes" target is judged only at exactly 214 instruments, else "not comparable". The preview says "not_evaluable" until a job measured one.
8. **Failure is honest.** A refusal after the store (for example `experiments.assumptions_differ`) ends the job `failed` with the ledger's code; the stored candidate stays; no experiment row exists, so no trial. A host stop is `interrupted`; a timeout is `failed` with `experiments.timeout`.
9. **Candidate runs are marked.** The default report set (`RunSelection`) leaves out runs whose `created_by` starts with `experiment:` (note "experiment candidate"); they stay selectable by name.
10. **Audit and surface.** `AccountEventType.ExperimentJobStarted` and `ExperimentJobCancelled` (kind and instrument count, never a value). `ApprovedReportWrites` lists exactly `POST /api/experiments/` and its cancel, so the P8 read-only check names them. Hub events `experimentProgress` (at most 4 a second) and `experimentFinished`. Log ids 4905 to 4914. The UI is one lazy panel of the owner-acts feature.

11. **A job is never stranded.** The watcher (progress, stop flag, heavy-job probe) logs a failed look and looks again; the runner always reaches `FinishAsync` (three tries) and, if the store still fails, the dispatcher marks the job `interrupted` (as a restart would) so the one-active index never blocks a new start. An interrupted job's card says a candidate run may be stored and an experiment may be on the ledger.
12. **A capability switched off between the handler's check and the insert** is refused by the database trigger (23514) and answered as 403 `capabilities.off`, not as a failure.

## Consequences
- With the capability off (the default after deploy) nothing can start; the preview is read only and works regardless.
- On today's data every result is at best Inconclusive; the screen says it before the start.
- The stored candidate runs are permanent and the trial count is global: three starts a day is a deliberate friction.
- **Limit:** the replay time is for this machine and this moment.
- **Limit:** "owner" is a string with a database check; a process holding `xd_app` could write a job row only while the capability is on (the trigger), and cannot apply anything because nothing applies.
- **Limit:** a baseline that was made with an exit override of a stored strategy cannot be replayed from the screen; run it again by the verb.

## Alternatives considered
- **A new `method` of the Lab run.** Rejected: a Lab run is a strategy-version test with gates; this is a baseline-versus-candidate judgement.
- **Hangfire or the services framework.** Rejected: a service is scheduled work; this is on demand, for one owner.
- **All three knob kinds.** Rejected: a `parameter` can change entries and burn a trial on `entries_added`.
- **A queue longer than one.** Rejected: bounded cost, one machine.
