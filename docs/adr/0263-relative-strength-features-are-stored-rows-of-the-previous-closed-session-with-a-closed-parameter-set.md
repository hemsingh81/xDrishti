# 0263 — Relative-strength features are stored rows of the previous closed session, with a closed parameter set

- **Status:** Proposed (spec [BK-09](../specs/BK-09-relative-strength-features-and-sector-strength.md), approved 2026-11-03; built 2026-11-11). Becomes Accepted when the owner has read it.
- **Date:** 2026-11-11.
- **Relation to other ADRs:** [ADR 0108](0108-a-lag-on-a-feature-call-and-a-warning-for-comparisons-that-cannot-be-true.md) (the one-session lag of feature reads), [ADR 0033](0033-weekly-monthly-timeframes-calendar-features-and-the-market-context.md) (date-driven features read strictly before the date), [ADR 0081](0081-four-swing-strategies-as-stored-text-only.md) (stored text only), [ADR 0207](0207-a-strategy-version-is-pre-registered-the-ledger-counts-every-extra-look-and-a-locked-hold-out-is-fixed-at-the-first-post-and-read-once-by-an-owner-unlock-with-enforcement-and-the-honest-count-as-the-owners-switches.md) (trials and pre-registration), [ADR 0255](0255-derived-baskets-are-pure-versioned-and-point-in-time.md) and [ADR 0257](0257-the-basket-profile-runs-its-risk-figures-on-a-daily-rebalanced-equal-weight-index-whose-weights-come-from-the-previous-sessions-membership.md) (the basket stack this builds on).

## Context
Strategies and reports need a share's relative strength inside a basket, against the Nifty 50, and its sector's rank, without look-ahead and without free parameters (every free parameter is a grid search by accident and counts in the multiple-testing factor).

## Decision
1. **Pure kernels in `Domain/Market/Strength`:** `RelativeStrengthRank` (volatility-adjusted momentum R/v with a 21-session skip, percent rank with ties at the average, at least 10 voters, zero volatility not evaluable, an ex-date in the window excluded and counted as `corporate_action_unresolved`, the `BreadthCalculator` rule), `IndexRelative` (20 sessions against the Nifty 50, percentage points) and `SectorStrength` (equal-weight mean of the members' window returns, at least 5 members with the full window, ranks 1..k with ties on the lower rank). Only closes up to the day are read; a property test proves cutting or replacing later bars changes nothing.
2. **Sector return is the mean of member window returns,** which is what acceptance criterion 5 states by hand (+3.0 %), not the compounded daily-rebalanced index of BK-06. The two differ by rebalancing; the buy-and-hold reading is cheaper and is the one BK-06 already uses for a hold.
3. **Stored, insert-once rows.** `market.relative_strength_daily` (the momentum rows per share, basket, lookback and skip; the index-relative row uses the empty basket id, lookback 20, skip 0, the score in percentage points, no foreign key on the basket) and `market.sector_strength_daily`. A day that has rows is never rewritten; the runtime role has insert and select only. The day is written in one transaction.
4. **The daily step** (`ComputeRelativeStrengthHandler`) runs as a post-step of the data job after the context and breadth steps, is OFF by default (`Market:RelativeStrength:Enabled`), catches up the missing sessions (default 5, convergent by primary key) and logs counts only (events 7420, 7421). The sector universe is the union of the members of the pre-registered baskets as of the day, not the whole tracked set. The membership basis is `dated` when the basket has changes on at least two days, else `single_snapshot` (as the profile of BK-07).
5. **Closed parameters in the DSL.** `mom_rank(basket, lookback, skip)`, `rs_vs_index(n)`, `sector_rs(window)` are date-driven catalog features (`IndicatorParameter.Allowed` is the closed set): the basket is a quoted name of a pre-registered basket (Nifty 50, Nifty 100, F&O stocks, Most liquid; the stored basket is found by the name, with the "NSE ", "List: " or "Derived: " prefix of the system baskets), the lookback 126 or 252, the skip 21, `rs_vs_index` 20, the sector window 21, 63 or 126. Anything else is a compile error that names the allowed values. The frame reads the newest stored row strictly before the date (`RelativeStrengthDays.Before`), so a read on day D is the row of the previous session and no second shift is applied. An unknown (insufficient, unavailable) is NaN, so the condition is false and the existing per-condition unknown counter counts it. The catalog `tf-1` of the learning side is untouched; the three names are refused for mirroring (a rank has no opposite side).
6. **`RS_ROTATION` is stored text** (swing, 1D, BUY only, at the close, one `FIXED_RR`, hold 5, stop `swing_low` 5, `mom_rank("Nifty 100", 126, 21) >= 0.67 and sector_rs(63) <= 3`). Seeded as a version like the other built-ins; not Active, not read by selection. The thresholds 0.67 and 3 are fixed; changing either is a new variant.
7. **Read endpoint** `GET /api/market/relative-strength?basket=&asOf=` (newest 500 rows, tag Market).

## The run (criteria 6, 7 and 11)
8. **Lab runs read the stored rows.** A strategy that names one of the three features gets, once per instrument, its rows (momentum and index-relative) and its sector's rows with `as_of` from 14 days before the window to the day before the window end (`RelativeStrengthRunReader`), as `FrameOptions.RelativeStrength`. The frame reads the newest row strictly before each date, so a decision on day D sees the previous closed session. A run given none (the engine called without rows) is refused; an instrument whose replay has no rows is skipped with `no_relative_strength`. A comparison run (several exits in one scan) does not read them yet and fails closed.
9. **The run records what it read.** `SimulationRun.RelativeStrength` holds the hash and count of the rows, the session the members are as of (the window end), and per basket the id, name, the `params_hash` of the newest version of a derived basket (none for an index or manual basket) and the basis (`dated` or `single_snapshot`). The hash and the date are a line of the run key (`rstrength`), so other rows are another run; the run label prints the basket ids, "members as of", the basis, the parameter hash and the `feature_unknown` count. No other run has the line, so every other key is unchanged.
10. **`feature_unknown` is its own counter** (`ScanCounters.FeatureUnknown`): the steps at which a condition that names one of the features was not true because a feature was unknown. A known low rank is plain false and is not counted. Unknown is never a pass.
11. **Trials.** A Lab run of `RS_ROTATION` is a ledger row like any other (ADR 0207); a run over another basket has another plan hash and is a `replan` row. The count enters `MultipleTesting.Factor` only when the owner's `CountInFactor` switch is on. Pre-registration of the version stays the owner's act.

## Decisions recorded with the build
- **"Liquid-100" is the derived basket "Most liquid"** (BK-03, stored as "Derived: Most liquid"); the pre-registered baskets are Nifty 50, Nifty 100, F&O stocks and Most liquid. The spec's open question 1 is answered this way until the owner says otherwise.
- **`EqualWeightIndex` (BK-06) is not reused for the sector return.** Acceptance criterion 5 states the sector return as the plain mean of the members' window returns (+3.0 % from +4, +2, +6, 0, +3), which is the equal-weight buy-and-hold return over the window. The daily-rebalanced index compounds the daily means and would give another number for the same members; the plain mean is also one pass over the members instead of a daily loop. The profile of BK-06 keeps the rebalanced index for its own figures.

## Consequences
- The step is off by default, so until the owner turns it on a run of `RS_ROTATION` finds no rows and trades nothing (every step is a `feature_unknown`).
- The trade-card and ticket builders (`TicketBuilder`) do not read the rows; a stored strategy that names the features is not explained there.

## Honest limits
- Two to three years of history: a 252-session lookback has about one year of valid ranks (`short_history` before that). A basket of today's members flatters momentum (survivorship); the basis says so.
- Sector equal-weight returns of a small set are noisy; rank flips near ties are common.
- The pre-registered basket names are the ones the system baskets carry today; the liquid basket is the derived "Most liquid" one.
