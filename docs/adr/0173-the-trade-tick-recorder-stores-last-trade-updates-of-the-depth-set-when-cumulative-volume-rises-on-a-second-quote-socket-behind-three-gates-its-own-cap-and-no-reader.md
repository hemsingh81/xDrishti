# 0173 — The trade-tick recorder stores the last-trade updates of the depth set when cumulative volume rises, on a second Quote socket, behind three gates, its own cap and no reader

- **Status:** Proposed (built in P7-16b from the owner-Approved spec, 2026-10-31, with the recommended answers). Becomes Accepted when the owner has read it. **SAFETY decision: a further broker WebSocket with the Data account's token (socket 3 of Dhan's 5), continuous disk growth.** No new allow-list entry.
- **Date:** 2026-10-31.
- **Relation to other ADRs:** [0024](0024-live-feed-xd-feed-and-live-prices.md) (the live feed, its allowed endpoint and parser), [0133](0133-new-broker-endpoints-enter-the-allow-list-in-the-commit-of-the-slice-that-uses-them-index-and-vix-history-needs-none.md) (allow-list rule; not triggered: no new endpoint), [0135](0135-the-depth-recorder-stores-the-20-level-book-of-up-to-50-shares-about-once-a-second-behind-three-gates-a-disk-guard-and-no-reader.md) (the depth recorder this mirrors), [0091](0091-auto-approval-is-an-option-behind-an-owner-setting-default-off-a-new-approval-kind-the-database-checks.md) and [0128](0128-owner-act-capabilities-are-one-insert-only-log-with-a-generic-gate-by-name-off-by-default-and-switched-on-only-by-the-owner-with-a-fresh-password.md) (fresh-password switch), [0083](0083-the-plan-record-insert-only-state-trails-owner-only-approvals-lapse-by-default-and-no-order-by-name.md) (no order).

## Context
P13's aggressive-volume feature (`vol_delta_5m`) needs a trade stream aligned with the recorded book; Dhan offers no historical ticks and its feed sends only the latest trade's fields per update (no individual trades, no sequence number). Recording opens another broker socket with the Data token and grows the database, so it must be off until the owner switches it on, bounded so it stops the recording and not the machine, and unable to influence anything that decides or trades. Spec: [P7-16b](../specs/P7-16b-trade-tick-recording.md).

## Decision
1. **A second connection to the already-allowed live-feed host, Quote mode only.** `TickFeedConnector` holds its own `DhanFeedConnector` (own packet counts): `wss://api-feed.dhan.co` with the four query keys, checked by `BrokerEndpoints.IsAllowedWebSocket` before any connection. `BrokerEndpoints` and `PlanPhaseCheck.PinnedAllowList` are unchanged. It subscribes with request code 17 only, in messages of at most 100. It is not the live feed's socket, not an active-set provider, and never touches `Live:MaxWsInstruments`. Socket 3 of 5 (live, depth, ticks).
2. **Parser, additive.** `FeedPacket.LastQuantity` (uint16 from bytes 13-14 of a quote; null when zero) and the cumulative volume read as uint32 (signedness UNVERIFIED). The live feed never reads `LastQuantity`; its mapping is unchanged (one parser test's expected record gained the new field).
3. **Change-only on cumulative volume.** `TickSampler` (pure) writes a row only when the cumulative volume of an instrument rose since its last stored row in the run; the first usable packet of a run and the first after a reconnect are `baseline` (bit0); a lower volume is written with `volume_down` (bit2); an earlier exchange trade time sets `ltt_back` (bit3); a last quantity of 65,535 sets `ltq_capped` (bit1); an unchanged volume is counted (`unchanged`) and not written; ticker, previous-close and other packets are counted and ignored. Prices become integer paise half away from zero: float32 resolves a paisa only below 167,772.16 rupees, above it the paise value may be off by a few paise, accepted. Only receive times 09:15:00 <= t < 15:30:00 India time are used; a packet outside does not move the state, so the first one inside is the baseline.
4. **Row shape.** `market.trade_ticks(ts, instrument_id, rx_mono_ms, rx_seq, ltt_epoch, ltp_px, ltq, cum_vol, flags)`: receive time, monotonic ms since the run started, a per-run packet counter (the only order inside a millisecond), the raw int32 exchange time (zone UNVERIFIED, not converted), paise, last quantity, cumulative volume, flags. No aggressor, side, bid or ask; P13 classifies volume deltas against the depth snapshot at or before the receive time.
5. **Budget (estimate until the pilot).** About 130 B raw a row; planning 2 stored rows/s per instrument (range 0.5 to 5): 2.25 M rows and 0.29 GB raw a session, 72 GB a year raw, at a planning compression of 8:1 (UNVERIFIED, range 5:1 to 15:1) about 9 GB a year. The pilot replaces these numbers here.
6. **Separate cap, shared free floor.** `Ticks:MaxStoredGb` (12) on `market.trade_ticks` ends a run `disk_budget`; the free floor is the depth recorder's `Depth:MinFreeGb` (20) and ends it `disk_free`; warning at 80 %; checked before each start and every 5 minutes with `DepthDiskGuard.Check`; a stopped recorder stays stopped until the condition clears and a look finds it not wanted; **the app never deletes data**. Both recorders on need 72 GiB free (40 + 12 caps + 20 floor) or a larger VM disk.
7. **The day's set: the depth set, own copy.** The depth recorder's stored set of the day is copied when it is there by the first look at or after 09:14:30 India time; otherwise one is built with `DepthRecordingSet.Build` from the same `Depth:*` inputs (armed, pinned, liquid). Either way it is stored in `market.tick_session_instruments` with `source` `depth_set` or `built`, fixed for the day. The tick code holds no depth store and **never writes a depth table** (a written `depth_session_instruments` row without a depth end row would forge a depth `crashed` day).
8. **Three gates, own switch and service.** (a) `Ticks__Enabled` (default false; `deploy/compose.yaml` passes `XD_TICKS_ENABLED`, default false); (b) `market.tick_recorder_switch` (insert-only, newest row decides, no row = OFF), changed by `PUT /api/ticks/recorder {enabled, reason, password}` with a fresh password on every change ON and OFF (`OwnerAct.AuthorizeAsync`, `StepUpCommand` with `Elevate: false`), the actor from the session, one account event `TickRecorderSwitched` (category `service`, row id and state only); 401/423, 400 `ticks.reason_invalid`; `GET /api/ticks/recorder` returns the switch, its history and the not-running reasons; (c) the service `tick-recorder` (window 09:14-15:31 India time, trading days, registered paused, retries 0, no catch-up, notify on failure; "Run now" refused). With any gate closed nothing reads the credentials, builds a URL or opens a socket; an unreadable gate counts as closed.
9. **Own loop, own heartbeat.** `TickService` is a third hosted loop of `xd-feed` (beside the live feed and the depth recorder), with `TickRecorderSupervisor` (15 s looks), `TickRecorder` (the session), its own run record and heartbeat row `xd-ticks`. Writes: `COPY`, one transaction per batch every `Ticks:FlushSeconds` (5); a failed batch is retried with the next; the queue holds at most 50,000 rows; rows unwritten for more than 30 s are dropped oldest first and counted; the receive loop never waits for the database. Failures: back-off and limiter of the live feed; a reconnect resubscribes the set and makes the next row of every instrument a baseline; the hole counts in `gap_seconds`; more than 10 reconnects in 5 minutes or 805 pause attempts 5 minutes; 806 ends `not_subscribed`; 802/803/807-809 wait for a changed token. One `market.tick_sessions` row per day when the day is over (ADR 0135's rule); a past day with a tick set and no row is closed `crashed`.
10. **No reader.** `ITickStore` has no method that reads a tick (pinned by an architecture test), no route reads ticks, `Domain`, `Simulation`, `Strategies*`, `Indicators`, the decision layers, the live feed's code and the depth code reference no tick type. Logs `ticks.*` (ids 5341 to 5370) carry counts and ids only.

## Deviations from the spec text (decided while building)
- The set rule is applied by waiting: before 09:14:30 with no depth set stored the recorder waits (state `waiting_set`, nothing read or opened); from 09:14:30 it builds. A depth set stored later the same day does not change the stored tick set.
- A quote with no volume (zero) or a price that does not fit `int4` paise (above about 21.4 million rupees) is counted as unusable and not written.
- The connector test subscribes 50 instruments (the most the day's set holds; the local test server reads messages up to 4 KB); the batching of 100 is tested in the recorder.
- No capability, as ADR 0135: the three gates and the password are the guard.

## Consequences
- Nothing changes while any gate is off: the supervisor beats `xd-ticks` with `disabled`, `switch_off` or `paused` and does nothing else.
- Owner acts before switching it on: `podman machine ssh df -h /var` shows at least 72 GiB free with depth also on (or 32 GiB with ticks alone), or enlarge the VM disk; set `XD_TICKS_ENABLED=true`, run `deploy/xd-up.sh`; `PUT /api/ticks/recorder` with the password; resume `tick-recorder` on the Services screen.
- `xd-backup`, when built, must exclude `market.trade_ticks` data (`pg_dump --exclude-table-data`).
- **Pilot (owner-run, five real sessions, recorded here):** packets/s, stored rows per instrument-day, share of packets with a volume change, bytes per row and compression ratio (`hypertable_detailed_size`, `hypertable_compression_stats`); `median(ts - to_timestamp(ltt_epoch))` within 5 s (else the LTT is IST-shifted and P13 converts with the offset); the sum of positive `cum_vol` steps per instrument-day matches the EOD bar's volume within 1 % on days without gaps.

## Known limits (build review, 2026-11-01)
- The existing parser test `DhanFeedPacketParserTests` gained `LastQuantity: 25` in one expected record (record equality makes this unavoidable); no other existing parser test changed.
- At the 50,000-row cap the newest row is dropped; the 30-second rule drops the oldest. Both are counted in `dropped_rows`.
- If cancellation arrives while a COPY commit is in flight, the batch stays queued and the final flush can send it again; `trade_ticks` has no key to catch the duplicate (rare; consumers must tolerate a repeated row).
- `TickRecorderSupervisor` is a near copy of `DepthRecorderSupervisor` by design (independent recorders); a shared base for the gate and run lifecycle would stop the two drifting.
- `xd-feed` keeps `mem_limit: 256m` with a third socket and a 50,000-row queue: watch memory in the first pilot sessions (runbook).
- The architecture tests' list of areas that must not use tick types omits `Application.Execution`, `Application.Accounts` and `Application.Platform`, and exempts the whole `Infrastructure.Brokers` namespace; narrow both later.
- The Services page shows the tick recorder's switch together with the depth recorder's (same two files as in the amendment to ADR 0135); the tick recorder has no other screen.
