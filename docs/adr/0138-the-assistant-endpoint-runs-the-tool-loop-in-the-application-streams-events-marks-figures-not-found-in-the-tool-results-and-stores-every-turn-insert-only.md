# 0138 — The assistant endpoint runs the tool loop in the application, streams events, marks figures that are not in the tool results, and stores every turn insert-only

- **Status:** Proposed (written in P9-03 under the owner's delegation of 2026-10-26; the specs were treated as Approved). Becomes Accepted when the owner has read it. **SAFETY decision: a streaming endpoint that sends the owner's questions to a model and tool results back to it, stores prompts, and an owner-only settings change.**
- **Date:** 2026-10-27.
- **Relation to other ADRs:** [0136](0136-the-local-model-server-runs-in-a-container-on-demand-with-the-measured-qwen3-30b-a3b-as-default-two-pinned-alternatives-and-a-status-the-api-reads-over-http-only.md) (the model server and `IChatClient`), [0137](0137-the-assistants-tools-run-in-a-separate-read-only-server-under-two-database-roles-that-can-select-only-from-reviewed-views-and-the-switch-lives-in-the-database.md) (the tool server, `ai.settings`; item 12 asks this slice for the owner act), [0091](0091-auto-approval-is-an-option-behind-an-owner-setting-default-off-a-new-approval-kind-the-database-checks.md) (owner-only settings with the password in the body), [0128](0128-owner-act-capabilities-are-one-insert-only-log-with-a-generic-gate-by-name-off-by-default-and-switched-on-only-by-the-owner-with-a-fresh-password.md).

## Context
P9-01 gave the API a model it can ask, P9-02 a tool server that can only read reviewed views. P9-03 is the part that connects them for the owner: a question goes in, the model's tool calls and answer stream back, every number of the answer is checked against what the tools returned, and the whole turn is kept so that it can be replayed. The assistant is OFF by default; the model never sees anything but tool results from the reviewed views; the endpoint writes nothing but its own audit rows.

## Decision
1. **The loop is the application's, not a library's.** `AssistantTurnService` (Application) runs the loop over two ports: `IChatModel` (one streamed completion; the adapter over `Microsoft.Extensions.AI`'s `IChatClient` lives in `Infrastructure/Ai` and offers the tools as declarations only, with **no** function-invoking wrapper) and `IToolCatalog` (the MCP client in `Infrastructure/Ai`, a stateless client per operation, the list cached for 60 seconds). Reason: the budget, the discard of preface text, the audit row per call, the cumulative cut of results and the cancellation are the product's rules and must be testable with a scripted model; the member names of `FunctionInvokingChatClient` in 10.11.0 would otherwise be unverified code on the safety path. The Application layer references no model or tool library (architecture test).
2. **One door.** `IAssistantTurnRunner.BeginAsync` makes every refusal first (off, invalid, unknown conversation, model not ready, tool server down, nightly running, busy, too long) and stores nothing for a refusal; a session then holds the single turn slot and `RunAsync` runs the loop. The chat endpoint, the evaluation (P9-09) and later jobs use it; `origin` (`chat`, `eval`, `job`) is stored; all obey the same switches. Nothing else in the code reaches the model for question answering.
3. **Off means nothing is called.** No `ai.settings` row, or `enabled` false: `409 assistant.disabled` before any call to the model, the tool server or the store (the status endpoint does not ask the tool server either). The deployment flag `Assistant__Llm__Enabled` stays a second, independent switch.
4. **The settings change is the owner's act, with the fresh password only where exposure grows.** `PUT /api/assistant/settings` needs the session and the CSRF token; the actor is `owner:<email>` from the session and any actor in the body is ignored. A pure rule classifies the change: turning the assistant or the portfolio context on, or raising the budget of tool calls, needs the password in the body **on every such change** (verified like the other owner acts with `Elevate:false`: the step-up window is neither opened, extended nor used up; a wrong password counts toward the sign-in lockout); switching off or lowering needs none, so the owner can always switch it off. The handler checks the rule again against the newest row (a race cannot raise exposure without the password). This closes ADR 0137 item 12. No capability gate is added: the settings row is the gate and chat can only write its own audit rows.
5. **The stream.** `POST /api/assistant/chat` answers `text/event-stream` (events `turn`, `status`, `tool_call`, `tool_result`, `token`, `iteration_discard`, `ping`, `done`, `error`; the data is the camelCase JSON of the event). Text produced in an iteration that ends in a tool call is announced by `iteration_discard` (the server cannot know earlier whether it is a preface). Refusals are ordinary problems before the stream starts. `ping` every 15 seconds of silence. Rate limit 10 per minute per session cookie. The phase `tool` of `status` is declared in the contract but not sent: `tool_call` already says it.
6. **Budgets.** Tool calls per turn: the setting (1 to 12, default 6); a call beyond it gets `tool.budget_exhausted` as its result and is not made; a model that still asks afterwards ends the turn with `tool_limit`; a tool not in the catalog gets `tool.unknown`. History: the last 6 messages, an assistant message carrying one line that names its calls and never their results (so an old figure is not "this turn's tool result": intended). Tool-result text per turn: 10,000 characters, later results cut to 1,500 and marked. Prompt: system, schemas and question must fit 8,000 less 3,000 for results estimated at 3.5 characters per token, else `422 assistant.too_long`. `max_tokens` 900, temperature 0.2 (reasoning, not a measurement: an option; P9-09 may change it), turn timeout 180 seconds.
7. **Grounding: mark, do not block.** A pure check (`Domain/Assistant/Grounding`) reads the figures of the answer (not dates, times, list numbers, `[n]`, timeframes, identifiers, years) and looks for each in the numbers of the tool results of the turn and the owner's question (never the arguments of the model's own tool calls: a figure it invented and echoed there would pass): equal after normalisation, within half a unit of the figure's last printed digit, or equal after ×100 for a percent; the sign is ignored; a plain integer (a count) must be exact, or match a source with decimals after rounding. A difference the model computed itself is in no source and is flagged: derived numbers come from `calc` (P9-05). The unmatched figures are returned as spans and stored; the answer is never changed. It reads digits only: spelled-out numbers and numbers inside quoted text pass, and a right number used for the wrong thing passes; it narrows the problem, it does not close it. Briefings (P9-06) fall back to deterministic text instead of marking.
8. **The audit is insert-only and written in pieces.** Migration `AddAiAudit`: `ai.prompts` (once per hash), `ai.conversations` (with `origin`), `ai.messages` (unique `(conversation_id, seq)`), `ai.tool_calls` (unique per `(conversation, turn, call_index)`, the result envelope at most 64 KB, injection flags from the envelope), `ai.model_calls` (calls outside chat, no content). The schema is re-granted and `UPDATE`/`DELETE` taken away again from all six `ai` tables including `ai.settings`; the view `ai.account_labels` is closed again to `xd_app`. The tool server's two roles get nothing on the new tables. The user's message and the calls are written as they happen; the assistant's message once, at the end (a crash leaves a turn that the read shows as "no answer stored"). A cancelled turn stores the text so far with `finish_reason 'cancelled'` and `not_checked`; the audit is written even when the client has gone.
9. **Cancellation.** A client that goes away cancels the turn's token (the connection to the model server closes), the turn stores what it has, and only then is the single turn slot released.
10. **The proxy.** Caddy compresses everything except `/api/assistant/chat` and routes it through a handler of its own with `flush_interval -1`; `CaddyfileTests` read the file and `scripts/check-proxy.sh` runs the real proxy image against a stream with a 2 second gap.
11. **Logging.** Event ids 6060 to 6066: ids, counts, codes and statuses; never a message, a prompt, an argument, a result or an exception text.

12. **Retention and ids.** No retention in v1 (about 20 KB a turn): when size matters, add a purge as a SECURITY DEFINER function run by the owner; `xd_app` can never delete. Conversation and tool-call ids are not scoped to a session (single owner).

## Consequences
- Added: the package `ModelContextProtocol` 2.3.0 (the client, already a dependency of the server package), six `ai` tables in one migration with a `Down` that drops the five new ones, the routes of tag `Assistant`, the prompt file `system.v1.txt`, a Caddy handler.
- The loop code is ours: a change of the model library cannot change the budget or the audit; the cost is that tool-call parsing of streamed updates relies on the adapter delivering whole `FunctionCallContent` items (the OpenAI adapter of 10.11.0 does).
- The tool server must be reachable for a turn; with the assistant on and the tool server down the answer is `503 assistant.tools_unavailable`, never a model answer without tools.
- Not built here: any tool beyond P9-02's four (P9-05), the screen (P9-04), `calc` (so a derived number is always flagged for now), the golden schema file of all 16 tools (the estimate is tested on the four built).

## Not verified in this build
- No real model was run: the model is a scripted fake in every test; the tool-call streaming of the real `llama.cpp` through the OpenAI adapter, the 200 ms first event and the 2 second cancellation against a real model are unmeasured.
- The Caddy stream check ran against a local Python upstream through the proxy image; it was not run against the running stack (nothing was deployed or switched on).
- The stack was not touched: `xd-llm` and `xd-mcp` were not started and the assistant was not switched on.
