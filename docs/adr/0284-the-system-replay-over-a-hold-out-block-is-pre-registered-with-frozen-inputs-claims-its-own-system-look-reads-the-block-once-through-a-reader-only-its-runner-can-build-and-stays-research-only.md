# 0284 — The system replay over a hold-out block is pre-registered with frozen inputs, claims its own system look, reads the block once through a reader only its runner can build, and stays research only

- **Status:** Accepted (owner, 2026-11-13, in chat: "Consider my approval and you do due diligence also consider mostly things should be in auto mode with best default values"; spec [SR-03](../specs/SR-03-pre-registered-system-replay-over-a-hold-out-block.md) Approved).
- **Date:** 2026-11-13.
- **Relation to other ADRs:** Builds on [0283](0283-the-hold-out-is-a-chain-of-fixed-blocks-released-by-an-owner-act-or-the-auto-option-and-every-cut-follows-the-block-in-force.md) (the `system` kind, the per-kind slot, the horizon, the seal steps) and [0272](0272-the-system-replay-is-research-only-fenced-from-evidence-and-hindsight-labelled-and-runs-the-live-pieces-over-as-of-facts-in-memory.md) (the replay fence and clamp; this is the one sanctioned read past the clamp). Uses the baseline arm and comparison of [0279](0279-the-replay-baseline-takes-every-candidate-at-equal-risk-a-sweep-queues-one-run-per-start-and-a-replay-trade-chart-reads-through-the-hold-out-clamp.md) and the defaults of [0282](0282-auto-mode-defaults-follow-the-owners-instruction-of-2026-11-13-on-where-no-evidence-is-lost-and-no-risk-is-widened.md).

## Context
SR-01 and SR-02 never read a hold-out block, so every replay figure is "data seen before". SR-03 gives the system one pre-registered, once-only, net-of-costs look at a block it has never read.

## Decision
1. **Registration (insert-only).** `research.replay_holdout_registrations` stores canonical JSON and its SHA-256 (`config_hash`): the target block, the selection arm's parameters (scope, capital, profile, checked sheet id, version rule `start`, mode `frozen`), both arms, the rates hash of the sheet, the whole settings snapshot and its hash, the resolved scope hash, the strategy versions by hash, the engine version and the pass rule. The target is the earliest block of the chain whose start is after today (the stored blocks plus the one after the newest); block 1 and a block that has begun are never targets (422 `replay.registration_invalid`: `no_future_block`, `gross_choice`, `sheet_missing`, `sheet_unchecked`, `scope_empty`, `scope_over_memory_cap`, `bad_rule`). The newest registration stored for a block is the one; older ones read `superseded`.
2. **Frozen inputs.** The run uses the stored snapshot and versions, never today's. Drift is only a missing or changed input (a version by hash, the scope's members and the memory cap, the statistics snapshot as of the block start, which must have been created before the block began, the sheet, which must still be `checked`, with the same rates hash) or a stored block that does not end where the registration said: 409 `replay.registration_drift` before the claim. A changed engine version is not drift; the result is labelled `engine_changed`.
3. **The look.** The `system` look is claimed through HO-01's insert-only store (subject `system-replay:<registration id>`, version 1), burned even if the run is abandoned; a second run is 409 `replay.holdout_used`. The horizon (registered before the block's start) and a free slot are checked first; a refusal there stores nothing and reads nothing (a deviation from "stored re-used": nothing is burned for a look that could not count). The block must be the block in force and sealed (409 `lab.holdout_filling`).
4. **The reader.** `HoldOutBlockReader` lets the replay's `ClampedBars` read up to the block end and no further. It can be built only from a `HoldOutClaim`, which can be made only from a stored, fresh `system` look; only `HoldOutSystemRunner` builds either (architecture test). Every other replay path keeps the training clamp.
5. **Execution.** The owner act (`POST /api/replay/holdout-registrations/{id}/run`, fresh password, 202) and the auto step only claim the look. `HoldOutSystemRunLoop` (hosted in `xd-api`, off with `Replay:RunWorker=false`, waiting while a queued replay runs) runs each claimed registration with no result, both arms in memory in their own scope, and stores the result. The reader's end is the stored block's end, never the registration's computed one; the claim refuses as drift when they differ. A database, timeout or I/O failure leaves the claim without a result and is retried (at most 5 times, counted in memory); any other failure, or the fifth, is stored `run_failed` with the reason (a verdict word of its own: `inconclusive` stays for an unavailable figure of the rule). A stop leaves the claim and the run resumes at the next start. The queued replay job and this loop never run together. *Deviation from the spec text:* the two arms are not stored as `replay_runs` rows (that would put block prices in the replay reads); their figures and the comparison are in the result row, and `runIds` are the stable ids of the two arm results.
6. **Verdict.** All net: pass needs at least 30 closed trades, CAGR above 0, maximum drawdown within the registered limit (default 15 %) and an arm comparison that is not `baseline_better`; fewer than 30 trades, a gross basis, an unavailable figure or `too_little_history` is inconclusive; otherwise fail. Pure (`SystemReplayVerdict`).
7. **Automatic by default (ADR 0282).** `replay.holdout.auto_register` and `replay.holdout.auto_run`, rows of the insert-only `research.replay_holdout_settings` seeded ON (`system:default`, reason `ADR 0282`); a name with no row reads OFF, an unreadable table reads unavailable and nothing acts. Changing either is a fresh-password `PUT /api/replay/settings`. Seal step 40 (`SystemReplaySealStep`) claims, as `auto`, the look of the sealed block in force and registers, as `auto`, for the block after it when none is registered (the sheet checked most recently, the Auto scope, the replay defaults). `SystemLookSlot` keeps a block in force while its newest registration has no result (auto release waits). A bell notice names a drifted registration and a missing checked sheet.
8. **Research only.** The result tables are named by one store; no evidence reader reads them (architecture test). The card shows the rule first and the hindsight label. No order, no `XDrishti.Execution` reference.
9. **Migration `AddReplayHoldOutRegistrations`** creates the three tables (insert-only grants per table); `Down` refuses while a registration exists. The two seed rows are sealed as AM-01a's: the shape check admits `system:default` only with reason `ADR 0282` and ON, and a trigger refuses that actor from `xd_app` and for a switch that already has a row. The result verdict admits `run_failed`. `ICostSheetStore` gains `ListCheckedAsync` (most recently checked first, by the date in the checked note).
10. **Ledger.** The claim appends one `system_replay` trial-ledger row per strategy version, keyed by the look (SHA-256 of the look id), with no figure.
11. **Auto steps record their authority.** An auto run keeps the id and time of the `auto_run` switch row that allowed it with the look; a registration stored on or after the block start is never the newest and holds no slot.

## Consequences
- The first fresh system look is block 3 (read about 2027-11-05). Until then the card shows the registration and its rule only.
- A scope over the memory cap registers nothing; the owner narrows the scope or raises `Replay:MaxWindowMb`.
- A registration whose input drifted keeps its block in force until the owner restores the input or releases the block with the forfeit; the stalled-block notice says why.
