# 0232 — The shadow digest is copied outside the database; a switch-on over missed sessions needs an acknowledgement (409 `paper.shadow_gap`); a graded row always has its gross R; the summary carries the sequential line

- **Status:** Proposed (built as the CF-08 and CF-09 leftovers, 2026-11-09). Decided under the owner's delegation (research, configurable, best default, log in the ADR); approved-by-delegation, becomes Accepted when the owner has read it. **Safety slice: no** (read and report paths and one refusal; the switch stays OFF and no order is placed).
- **Date:** 2026-11-09.
- **Relation to other ADRs:** closes the "What is not built" items of [0212](0212-the-shadow-record-is-graded-after-the-close-through-the-one-replay-path-summarised-as-raw-and-effective-n-labelled-gross-unless-the-sheet-is-confirmed-and-switched-by-the-owner-with-a-fresh-password.md) (digest outside the database, the 409, the null-gross minor) and the "line on the shadow summary" item of [0213](0213-the-paper-edge-series-gets-a-sequential-failure-test-that-flags-a-probable-failure-early-with-the-odds-stated-and-never-passes-anything.md). Changes none of 0211 to 0213.

## Context
Review fix 4 of CF-08 asked that the chain digest leave the database so that a database owner cannot rewrite the chain and its only copy together. The contract also listed a 409 `paper.shadow_gap` without saying when. CF-09 D7 wanted the sequential line on the shadow summary. Round 2 of the CF-08 review left a graded net row with a null `r_gross` silently dropped in the gross view.

## Decision
1. **The digest log.** A weekly service `shadow-digest` (Saturday 11:00 India time, paused at start, nothing exported while `paper.shadow.enabled` is OFF) recomputes the chain (`ShadowDigest.FirstBroken`); a chain that does not verify is not copied and the run fails with `paper.shadow_chain_broken`. Otherwise it appends one line to `shadow-digest.log` in the folder `Shadow:DigestFolder` (`week`, `last_session`, `digest`, `sessions`, `gaps`, `written_at`). Append only (one `FileStream` in append mode, one buffer, flushed to disk), and a head already on the newest line is not written again. **Every line ends with `prev=` and the SHA-256 of the whole line before it**, checked on every read; a torn last line (no newline) is a problem and nothing is appended after it. **The log is checked against the chain** before every export and by `xd paper shadow verify` (non-zero exit): every logged (last session, digest) must equal that session's stored digest, so a database owner who recomputes the digests is found; a mismatch or a logged session the chain lacks fails the run with `paper.shadow_digest_diverged` and writes nothing. A missing or empty log fails the same way when the run history holds an earlier successful export. **Known limit (shortcut):** cutting lines off the *end* of the log leaves a valid chain and a valid prefix, so tail truncation is not detected locally; only an offsite copy of the newest line shows it. **Writability:** the folder is probed (create, write, remove a file) when the owner switches the record ON (409 `paper.shadow_digest_unwritable`, no row) and on every run (the run fails); whether the container's uid can write the host folder is **unproven against the running stack**. *Researched basis:* the usual tamper-evidence pattern for a hash chain (certificate transparency, signed-tree-head logs) is to publish the head to a party the writer cannot edit; a plain append-only file on a separate volume or backup mount is the smallest form of that. The Reports export was **not** used: it is capability-gated, reads research tables only and every kind calls a screen's handler, so a paper kind would widen it for no gain. The folder defaults to `data/shadow-digest` (git-ignored `data/`); the owner should point it at a disk the database role cannot write. The file is evidence to compare with `xd paper shadow verify`, not authentication.
2. **409 `paper.shadow_gap`.** Turning the record ON when more trading sessions have opened since the chain's newest session than `Shadow:MaxResumeGapSessions` is refused with 409 (no row is appended) unless the request carries `acknowledgeGap: true` (an accepted gap is audited as `gap_acknowledged missed=N`); the message says how many sessions would become gap rows (never back-filled). A first start (empty chain) and turning OFF are never refused. *Researched basis:* a silent gap in forward evidence is the one thing the owner cannot repair later, so the refusal sits at the only moment the owner is present; the acknowledgement is a plain field because the owner's fresh password is already required. **`Shadow:MaxResumeGapSessions` defaults to 0** (range 0 to 60): any missed session needs the acknowledgement; a higher value only loosens that and is a deliberate owner choice.
3. **Gross R is never null on a graded row.** Migration `AddShadowGradeGrossCheck` adds `CHECK ((status = 'graded') = (r_gross IS NOT NULL))` to `paper.shadow_grades` (the grader already writes it that way; the table was empty and the switch OFF). Down drops only that constraint.
4. **The sequential line on the shadow summary.** `GET /api/paper/shadow/summary` gains `sequential` (`available`, `note`, `edgeState`, `behaviouralState`, `line`): the system-scope answer of CF-09, the same line as `xd paper sequential`, also printed by `xd paper shadow summary`. A flag only, never a pass; `available: false` with a note when no shadow edge series exists. The `/paper` phase tab already has the line through `GET /api/paper/sequential`.
5. Settings are the configuration section `Shadow` (`DigestFolder`, `MaxResumeGapSessions`), validated at start. Neither can turn the record on.

## Consequences
New port `IShadowDigestSink`; handler `ExportShadowDigestHandler`; service `shadow-digest`; request field `acknowledgeGap`; summary field `sequential`. `scripts/gen-api.sh` regenerated.

## Not built
The Reports-export kind (decision 1); an offsite push of the log (the owner copies or mounts it). The `/paper` Shadow tab is a frontend slice built separately.
