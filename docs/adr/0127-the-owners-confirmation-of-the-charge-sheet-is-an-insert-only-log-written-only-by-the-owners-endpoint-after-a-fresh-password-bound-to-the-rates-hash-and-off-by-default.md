# 0127 — The owner's confirmation of the charge sheet is an insert-only log, written only by the owner's endpoint after a fresh password, bound to the rates hash, and off by default

- **Status:** Proposed (spec [P8-23](../specs/P8-23-charge-sheet-confirmation-writer.md), approved by the owner on 2026-10-26; built 2026-10-26). Becomes Accepted when the owner has read it. **SAFETY slice: an owner act.**
- **Date:** 2026-10-26.
- **Relation to other ADRs:** [0100](0100-the-report-endpoints-read-the-stored-runs-through-one-query-model-with-an-evidence-block-and-net-only-by-the-owners-stored-confirmation.md) decision 6 (net only by the owner's stored confirmation; this is the writer it left to a separate slice, and it moves the storage from a settings row to a table), [0099](0099-the-report-engine-is-a-pure-core-with-one-population-rule-six-honest-states-and-a-ranking-by-the-credible-lower-bound.md) (the hook), [0044](0044-the-cost-choice-the-stored-charge-sheet-the-cost-sheet-verbs-and-the-bill-check.md) (the stored sheet and its rates hash; ISS-25), [0122](0122-the-backtest-versus-paper-report-is-computed-on-read-from-a-point-in-time-reference-and-a-composition-matched-band.md) and [0123](0123-the-paper-phase-check-judges-the-p10-exit-from-stored-records-with-its-caveats-in-the-label-and-reads-only.md) (the paper comparison and phase check wait on the fact), [0091](0091-auto-approval-is-an-option-behind-an-owner-setting-default-off-a-new-approval-kind-the-database-checks.md) (the owner-act pattern: fresh password, insert-only rows, database checks), [0117](0117-the-audit-log-screen-is-a-read-model-over-the-six-insert-only-stores-merged-by-keyset-in-memory-with-pattern-redaction.md) (the audit screen gains a seventh source), [0083](0083-no-order-is-placed-before-phase-12-an-architecture-tripwire.md) (nothing here touches an order).

## Context
A figure is "net" only if the owner confirmed the stored charge sheet (ISS-25, ADR 0100). The only source, `IChargeSheetConfirmationSource`, read a settings row that nothing could write, so no report could be net and the paper phase check (P10-06) could never read MET. ADR 0100 refused to write it from the read-only slice and left the owner's act to a separate one. A settings row also cannot carry the history the owner asked for (who, when, a revoke as another row): it is edited in place.

## Decision
1. **The confirmation is an insert-only log.** Table `workflow.charge_sheet_events`: `kind` (`gate_on`, `gate_off`, `confirm`, `revoke`), the sheet id and the SHA-256 of its rates on a confirmation or revoke, the India date of a confirmation, the actor (`owner:%`, a database check), the reason, the time. One table, one lock: the newest capability row is the switch (no row means OFF), the newest confirm-or-revoke row is the confirmation. `xd_app` has SELECT and INSERT only, granted on this table alone (no schema re-grant). The settings key of ADR 0100 is gone from the code and a hand-written row is not read.
2. **The standing rule (Domain, `ChargeSheetStandings`).** A confirmation stands only if the newest confirm-or-revoke row is a confirmation AND the stored sheet it names still has exactly the confirmed rates hash. A different hash is `stale`, a sheet no longer stored is `sheet_missing`, a revoke is `revoked`; none is "confirmed". `ChargeSheetConfirmationStore` (the report source) applies the rule on every read, so a later change of the sheet's rates is never silently still valid. One confirmation is in force: confirming another sheet supersedes the first; the history keeps both.
3. **The owner's act.** `POST /api/charge-sheet/confirmation` `{sheetId, ratesSha256, reason, password}`, `POST .../confirmation/revoke`, `PUT /api/charge-sheet/capability`, and `GET .../confirmation` for the status. Each write needs a session, the CSRF token, the sign-in rate limit and **the password typed again for that act**, verified with the sign-in lockout rules and audit without opening, extending or using up the step-up window (`OwnerAct.AuthorizeAsync`, shared with the autonomy switches). The actor is `owner:<session e-mail>`, never from the body. The body carries the hash the owner was shown, never a "confirmed" flag; the handler compares it with the stored sheet now (409 `chargesheet.rates_changed`).
4. **The capability is OFF by default and gates confirming only.** Switching it on or off is an owner act with a password. While it is off a confirmation is refused (403 `chargesheet.capability_off`) by the handler, by the store under the lock and by the database trigger. A revoke is always allowed (it can only make figures gross) and switching off does not revoke. **No setting, job, service, rule or verb confirms anything**: the capability only allows the owner to; the write port has one user (the handler) and the act command one caller (the endpoint module), both pinned by architecture tests.
5. **Idempotent under the lock.** The store takes the lock the insert trigger takes, re-reads, and writes nothing when the log already says the same (the same confirmation again, a revoke with nothing to revoke, a capability already in that state); the answer says `changed: false`. Two confirmations at once make one row. The database stamps id (after the lock, so id order is commit order), time and the India date; a chosen value is overwritten.
6. **The paper fact reads the same confirmation.** The production `ICostConfirmationFact` is `StoredCostConfirmation` (Infrastructure, over `IChargeSheetConfirmationSource`): the confirmed day for the confirmed sheet id only, else null. The Application registers `NotConfirmed` with `TryAdd` (default and test default); the Infrastructure `Replace`s it. The ADR 0100 list of Application readers of the source is unchanged. So E3 and E4 can be evaluated and a real MET of the paper check is reachable, and every "never MET on unconfirmed evidence" test stands.
7. **Audit.** A seventh audit source (`chargesheet`, category `configuration`, kinds `chargesheet.confirm|revoke|gate_on|gate_off`) over the same table: actor, time, sheet, the first 12 characters of the hash, the reason (redacted as every free text). Log events 4950 to 4952 carry row ids, kinds and codes only.
8. **The verb.** `xd charge-sheet show [--sheet ID]` reads; `confirm` and `revoke` refuse (exit 1) and point to the Settings screen: the terminal has no password check and the verb's actor `cli:xd` is not an owner.
9. **The screen.** Settings, tab "Charge sheet", one lazy component: the state in words, the sentence of what confirming means, the stored sheet with its full rates hash and what it was checked against, the history, a reason and a password box, three acts. Confirm is disabled until a sheet is shown, confirming is on, and a reason and password are typed; the password is cleared after every try. A wrong password does not end the session (the shared client lists the three paths as password checks). It lives on Settings because Reports and Paper are read-only screens guarded by tests that forbid any write call and any import of another feature.

## Consequences
- The owner can make reports net and let the paper check be evaluated, by an act that is audited, bound to the rates and revocable. Nothing changes for any existing report number until the owner acts; after the migration the database holds no row, the capability is off, and every figure is gross.
- A sheet's rates are part of the binding, so editing the sheet (`scripts/cost-sheet.sh load --replace`) makes the confirmation stale at once: the owner confirms again at the new hash.
- **Limit:** a paper trade records the sheet id, not the rates hash it was costed with. After a change of rates and a new confirmation, earlier paper trades of that id count as confirmed at the new rates.
- **Limit:** the system records that the owner said the sheet is right, not that it is. Checking against bills is P3-03f's `check`.
- **Limit:** "owner" is a string with a database check (as in P7-12). A process holding `xd_app` could insert an owner row only while the capability is on; the controls are the single writer behind session, CSRF, rate limit and password, the insert-only grant and the trigger.
- The audit screen reads seven stores; `AuditSource.ChargeSheet` has ordinal 6.
- Measured: first-load JavaScript 197.8 KB to 197.9 KB gzip (the three password-check paths and two query roots); the card is a lazy chunk of 6.6 KB (about 2.4 KB gzip).

## Alternatives considered
- **Keep the settings row.** Rejected: updated in place, no history, no revoke as a row.
- **A flag on the request or a "confirmed" setting.** Rejected: ADR 0100's rule that a caller must not be able to make a report net by saying so; the body carries a hash to compare, never a verdict.
- **Confirm from the terminal.** Rejected: no fresh password; the actor would not be an owner.
- **Confirm by name only.** Rejected: the store overwrites sheets in place.
- **Refuse an unchecked sheet.** Rejected: the owner's judgement is theirs; the screen says it is unchecked.
- **The step-up window instead of a password per act.** Rejected: the window is not used up by an act and would let one password cover many.
