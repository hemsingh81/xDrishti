# 0181 — The results calendar keeps each meeting row with its own intimation time, counts days in trading sessions to an event session, and answers "unavailable" for an instrument with no entry

- **Status:** Proposed (built in P15-04 from the owner-Approved spec, 2026-11-02). Becomes Accepted when the owner has read it. Safety slice: no (local files and its own tables; no network, no broker, no order). It produces a number (`days_to_results`) but **no decision path reads it yet**.
- **Date:** 2026-11-02.
- **Relation to other ADRs:** [0179](0179-filings-come-from-a-local-inbox-folder-with-a-sidecar-that-carries-the-broadcast-time-the-adapter-is-read-only-and-the-public-page-fetcher-is-a-recorded-decision-not-to-build.md) (the `row_level_ts` csv entries this loads), [0180](0180-the-point-in-time-filing-store-keeps-immutable-envelopes-and-answers-what-was-known-at-an-instant-from-the-broadcast-time-plus-a-lag-and-nothing-else.md) (the envelope table, the visibility rule and the supersede chain this reuses), [0033](0033-weekly-monthly-timeframes-calendar-features-and-the-market-context.md) (the date comes from the caller), [0087](0087-pretrade-checklist-pure-unavailable-never-passes-and-an-owner-only-confirm-despite.md) (`unavailable` never passes), P15-00 risk 8 (look-ahead through the calendar).

## Context
Pre-trade checks and the loss tag want "how many sessions until this company reports". A results date learned *after* the question's instant would let a backtest avoid a results day it could not have known, so the date has to carry the time the exchange made it public, and a missing date must never be read as "far away". No code sets `DaysToResults` today.

## Decision
1. **Each calendar row carries its own intimation time.** The owner drops a board-meeting csv (`symbol,period_end,meeting_date,purpose,status,intimation_ts`) and a shareholding csv (`symbol,period_end,category,pct,pledged_pct,broadcast_ts`); the sidecar names the kind and symbol `*`, the rows carry the time. Every row is one envelope (`kind board_meeting`, `broadcast_ts` = the intimation instant, to the microsecond) plus one `filings.calendar` row in one transaction; a shareholding (symbol, period) group is one envelope plus up to four `filings.shareholding` lines. A blank, date-only, offset-less, future or unparsable time is `unavailable` with the P15-01 reason: stored, counted, never dated, never used. No migration: the tables of ADR 0180 already have the columns.
2. **The envelope hash is the hash of the canonical row text**, not of the file: instrument id, period, values and time to the microsecond (or `unavailable:<reason>`), never a file name, line number or ingest time. The same row in two files, at any line, with the same instant spelt in another offset, is one envelope, so reloading a file inserts nothing. (The spec said the file hash is the base; a hash that includes the file would make the same row in two files two rows, which contradicts its own criterion.)
3. **The group is (instrument, period, purpose) and holds row envelopes only.** A file envelope of the same instrument, kind and period (a PDF or XML that P15-02 stores) is another group: `FilingStore` groups only envelopes with no calendar or shareholding row, the two row stores and `ShareholdingRows` only envelopes that have one. They share the advisory lock key (`FilingStore.GroupLockKey`) so writers are still serialised. A refusal of the unique supersede index is mapped to `bad_supersede`, never thrown.
   The group: A later intimation supersedes the stored current row of the group (`supersedes` set at load, linear chain, enforced by the ADR 0180 trigger); an equal time with other content is `ambiguous_order` and not stored; an earlier time is stored unlinked and counted `out_of_order` (visible by its own time, hides nothing later). The decision reuses `PointInTimeRule.Decide` on the stored rows of the same purpose, under the envelope group's advisory lock, so an `other` meeting never supersedes a `results` one and every writer of a group is serialised. Inside one file, rows that share a time but not content are refused together (the outcome never depends on line order) and a file loads in chain order.
4. **Days are counted in trading sessions to an event session.** `ResultsDays` (pure): the `results` rows visible at t (`intimation + lag <= t`, the lag of ADR 0180), the current one per period end by the point-in-time rule, cancelled ones dropped; the **event session** of a row is the first trading day on or after its meeting date (a Saturday or holiday meeting counts on the next session, the conservative reading because the reaction is then); candidates are those with an event session on or after the India date of t; the earliest wins; `days = TradingDaysBetween(date(t), event session)`. A decision at 23:00 IST still counts that day as today. A reschedule replaces the earlier date only from its own visible time.
5. **No entry is `unavailable`, never zero, never an estimate.** Closed reasons: `no_entry` (no visible `results` row, or only rows without a time), `only_cancelled`, `no_upcoming_entry` (every event session past). No date is ever inferred from last year's.
6. **Ports, no decision use.** `IResultsCalendar` (`DaysToResults` single and batch, one query, and the agenda for the route) and `IShareholdingAsOf` are named only by their implementations and the route's read handler; architecture tests pin that the decision areas, the checklists, the simulation, strategies, learning, planning, selection and the execution service reference neither them nor any filings type. P15-05/06 amend the test, naming the new caller. Wiring `days_to_results` into the two checklists is P15-06's, behind a default-off setting.
7. **Loaders.** `LoadCalendarHandler` and `LoadShareholdingHandler` (one use case each) read the `row_level_ts` entries through `IFilingsSource` (hash re-verified at the end of the stream, strict UTF-8, bounded by the listed size, at most 20,000 rows, a bad header rejects the file), reject per row with a closed reason and line and column (`bad_row`, `unknown_instrument`, `ambiguous_symbol`, `inconsistent_ts`, `out_of_range`, `ambiguous_order`; also `too_many_rows`, `bad_encoding` for a file that is not UTF-8, `bad_supersede`, `content_changed`, `unreadable`); a row timed in the future is `bad_row` (column `intimation_ts` / `broadcast_ts`), so nothing that depends on the clock is stored; the first 50 rejects of each file are kept with line, reason and column (never a cell) in the per-file result and the first 10 appear in the run line, and count loaded, duplicate, revisions, out of order, unavailable time and `sum_off`. Logs and the run line carry counts and codes only. They run inside the existing `filings-ingest` run, after the file ingest (no new service, paused by default, "Run now" allowed); each loader call is wrapped in the service: one that throws or fails is logged by exception type only, marks the run failed and never stops the other loader or any other service. Different instruments are stored by 8 parallel workers (one transaction and one lock per row); the rows of one instrument stay in order. A 4,300-row csv loads in about 2 s on the test container.
8. **Shareholding.** All rows of a (symbol, period) share one time (same state and instant to the microsecond), else the group is `inconsistent_ts`; a category twice in a group is refused on every line; a blank `pct` is stored `unavailable` and no number; a pct outside 0-100 refuses that line `out_of_range`; a group of all four categories that is off 100 by more than 1.0 point is stored and counted `sum_off`, never corrected; a later group of the same key supersedes the earlier from its own time. `IShareholdingAsOf.Latest` returns the current visible group and the group exactly one quarter earlier by period end (else none), or `unavailable/no_entry`.
9. **Route.** `GET /api/calendar/results?from&to&asOf` returns the visible upcoming meetings with an event session in the range (default: the India date of `asOf` and the next 59 days; at most 120 days; `asOf` default now, an offset required, not before 2000-01-01): symbol, instrument id, period end, meeting date, event session, days, `intimatedAt`, `revision` (1 plus the visible rows of the same instrument and period with an earlier time, so it never depends on load order), at most 2,000 rows (`truncated`), and `instrumentsWithoutEntry` (count and the first 300 symbols: the tracked instruments with no visible, not cancelled, not past results meeting at `asOf`, whatever the range). 400 `calendar.invalid_query` for a bad range, a bad or offset-less `asOf` or an unknown parameter; an empty list is not an error. No file content, no estimate.

## Consequences
- P15-05 can read `days_to_results` and the shareholding for any instant without a look-ahead path; P15-06 wires the event filter behind its own setting.
- The architecture allow-lists change deliberately: `filings.calendar` and `filings.shareholding` are written only by `CalendarStore` and `ShareholdingStore`; `result_facts` stays for P15-03.
- `IFilingInstruments` gained `TrackedAsync` (the tracked list for the instruments-without-entry count).

## Known limits
- As complete as the owner's files; an instrument with no row stays `unavailable` and is listed.
- A hand-typed intimation time is trusted (ADR 0179); a wrong one weakens the guard, a blank one is unavailable.
- Results sometimes come out after the meeting day; the event session is a lower bound for the broadcast and P15-06's windows add margin.
- Rows of the same group with equal time and other content in two different files: the first loaded wins, the second is `ambiguous_order` (a file-order dependence that only a conflict can show).
- The trading calendar knows only the confirmed holidays; a future holiday not yet confirmed is a session in the count.
- The agenda reads every stored results row up to the cutoff (a few thousand rows over five years); no paging.
