# 0056 — Stored strategies: the `lab` tables, the seed of the built-ins and loading by id, version or hash

- **Status:** Accepted (spec [P3-02d](../specs/P3-02d-stored-strategies-lab-tables-and-the-seed-of-the-built-ins.md), which the owner approved on 2026-10-22, questions 1 to 8 as recommended; built on 2026-10-22). The text of this ADR has not been read by the owner.
- **Date:** 2026-10-22.
- **Relation to other ADRs:** [ADR 0002](0002-config-and-strategies-in-app.md) (strategies live in the database, defaults ship embedded and are written on first start), [ADR 0036](0036-the-typed-strategy-model-and-the-compile-of-its-sections.md) (the model whose parameters and quantities this uses), [ADR 0039](0039-an-engine-module-is-reached-from-an-adapter-in-infrastructure-never-from-application.md) (the engine is reached from an adapter; Application sees strings and numbers), [ADR 0045](0045-the-result-store-sim-runs-and-sim-trades.md) (insert-only tables, the grants test), [ADR 0055](0055-the-strategy-file-its-schema-and-the-content-hash.md) (the file, the canonical text and the hash).

## Context
The three built-ins were C# builders reached by id, which made "seeded in the database" (ADR 0002) untrue and left no place for an own strategy. P5 (library API, Lab runs) and the nightly scanner need a strategy to be a stored, unchangeable text with a hash, runnable by id and version exactly as a built-in is.

## Decision
1. **Two insert-only tables (D1 to D3, migration `AddLabStrategies`).** `lab.strategies` (id with the model's pattern, style, `built_in`, `created_at`; no latest-version column, because the runtime role cannot update) and `lab.strategy_versions` (`(strategy_id, version)` key, `schema_version`, `hash char(64)` unique, `source_text` at most 262,144 bytes and kept byte for byte, `canonical_json` as `text` so the hashed bytes are the stored bytes, `parent_hash` pointing at the unique hash, a note of at most 500 characters, `created_at`). A unique index on `lower(id)` keeps two ids that look alike out (owner question 6). `xd_app` can SELECT and INSERT and nothing else (`MakeAppendOnlyForAppRole`); a later `lab` migration that re-grants the schema must call it again for both tables. `Down` drops both tables and then the schema without CASCADE, so a later table in `lab` makes it fail and remove nothing. A grants test runs as `xd_app` on a throw-away server.
2. **The store port (D4).** `IStrategyStore` in `Application/Abstractions/Research` over plain records; `StrategyStore` in Infrastructure with raw SQL on the pooled data source. An append is one transaction: the same hash again is the same row (`Created = false`, whatever the expected version); otherwise the family is created if new, the version is `max + 1`, an expected version that differs is `lab.version_exists`, and the parent defaults to the previous latest version. A lost race on the hash re-reads the row; a lost race on the version or the family starts again (up to 24 rounds: eight writers need eight at worst). No lock, no serialisable isolation. The store checks that the hash is the SHA-256 of the canonical text and the sizes, judges nothing else, and refuses an append to a built-in family (`lab.builtin_readonly`) unless the call is the seeder's (one `Seed` flag in place of the spec's two, `BuiltIn` and `AllowBuiltIn`: a family is a built-in exactly when the seeder created it).
3. **The seed (D5).** Three embedded resources (`Seed/Strategies/*.yaml`), written by `xd-api migrate` after the migrations (`StrategySeeding.SeedAsync`), the one place first-start data is written. Each text is read and compiled by the engine on every declared timeframe (`ISimulationEngine.Describe`); one that does not pass is logged at error level and not stored (owner question 3). Idempotent by hash; a release that ships a different text for an id makes it the next version, the old version stays, and the parent is the previous latest (owner question 4). `lab.seed.strategy`, `lab.seed.refused`, `lab.seed.failed`, `lab.store.appended` log id, version and a hash prefix, never a text.
4. **`rr` becomes a parameter of the model (D6, owner question 1, option A), and the built-in hashes change once.** The three builders now declare `rr` and write `rr: [rr]` in their exit (`Quantity.Named`), so the effective parameters of a run record (which already held `rr`) are a fact of the text and a stored strategy takes `--param rr=3` like any declared parameter. The canonical text of each built-in changes, once:

   | Strategy | Hash before | Hash after |
   |---|---|---|
   | `ORB` | `9c1141cf1835d03a0b25b280bbab9b2a7367db8e13ec7568cb0083ca9db14e03` | `0ba11bc69d2f1cfa24d8801f78f8fcc111415b39fa1454a1a09e59eeebf8574c` |
   | `VWAP_PULLBACK` | `7c1c2493b220e3c343c50960b08a623d48be346e198c7bc233710aaccbe7cca9` | `82f2d536dd1f8879c36620226ae00466fcca73f65a129e110ed276595f23a401` |
   | `BASE_BREAKOUT` | `c41e6a82171fbef80953512750c2eec2a300c461893d6ff627a936956b585374` | `68c445de513df1e644de3dcae920629c0cf131ad6a6e26d8a2107dbffd7d074b` |

   Runs stored before this change keep their keys (insert-only); runs after it have new keys for the same trades. The record's `schema`, the engine version and the trades are unchanged; the golden run record and the two golden definitions were regenerated, and the pinned hashes in the tests are those above. `BASE_BREAKOUT` is now at the model's limit of four parameters. The builders stay as the test oracle: a test reads each seed and requires it equal to the builder's definition and hash (D6), and requires the stored path to give the run record of the built-in path.
5. **Loading by id, version or hash (D7, D8).** `SimulationRequest` gains `StrategyVersion` and `StrategyHash`. `RunSimulationHandler` resolves in the store first: a hash names a version; an id names the latest version (owner question 5), or the one asked for; an id that is not stored but is a built-in still runs the engine's built-in (the oracle path, kept for the tests); anything else is refused with what exists (`simulation.unknown_strategy` naming the stored ids and the built-ins, `simulation.unknown_strategy_version` naming the versions, `simulation.unknown_strategy_hash`). The handler hands the text and the stored hash to the new port method `PrepareStored`; the engine reads the text, refuses it with `strategy_store.hash_mismatch` if it does not give the hash (a changed row, or a reader that reads an old text differently; nothing runs), substitutes the given values for the declared parameters (an undeclared name is `simulation.unknown_parameter`) and prepares it through the same `StrategyPreparation` path as a built-in, so the run record carries the same fields. The version number is not in the record or the key (owner question 7): a run names its version by its hash, and `GetByHashAsync` finds the number. The verb prints `strategy <id> version <n>, hash <hash>` as its first line for a stored strategy.
6. **Layers.** The reading of the text is done in the simulation library, which now references the strategy file library (`StoredStrategies`: `Inspect` and `Prepare`, pure, no package of its own); Infrastructure's adapter stays thin and still references only Application and Simulation; Application names no engine or file type. This is the one change to an architecture rule: the allowed project references of the simulation library gain `XDrishti.Strategies.File`, and the lists of its public types, of the Application research port and of the types allowed to do I/O in the adapter's namespace gain the new names. The rules that matter (no package in the simulation library, YAML package only in the file library, Application sees no engine type, the adapter does no I/O and holds no state) are unchanged and still enforced.
7. **Verb flags.** `--strategy <id>`, `--strategy-version <n>` with it, `--strategy-hash <64 hex>` instead (it needs `--timeframe`, because the verb does not read the text to find the default timeframe).

## Consequences
- P5-01 can serve the library over `IStrategyStore` and map `lab.version_exists`, `lab.builtin_readonly`, `lab.id_clash` and `strategy_store.invalid`; P5-02 keys a Lab run by the hash.
- `--param rr=…` works on a stored built-in; `--exit FIXED_RR:rr=…` still replaces the exit of any strategy.
- A release that changes a built-in's text adds a version; old runs point at old hashes and stay valid.

## Honest limits
- The parsed definition is not cached by hash (the spec suggested it): the text is read once per run, not per instrument, so the saving is a few milliseconds a run and a static cache would be state in a library that has none.
- `simulate --list-strategies` still prints the C# table of the built-ins; it does not list stored custom strategies (that is the library API of P5-01), and the value ranges of the built-in parameters (`Min`/`Max` in the C# table) are not enforced for a stored strategy: the compile judges the values.
- The default timeframe of a stored custom strategy is 15m unless `--timeframe` says otherwise; the verb does not read the text for it.
- Only a hash mismatch, a size and an id/style/hash format check guard the table; the store trusts the caller that read and compiled the text.
- A superuser or the migration role can still change rows; the grants are the guard, there is no trigger.
