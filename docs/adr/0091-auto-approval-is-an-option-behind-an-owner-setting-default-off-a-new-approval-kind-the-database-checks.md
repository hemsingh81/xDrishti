# 0091 — Auto-approval is an option behind an owner setting (default OFF), a new approval kind the database checks

- **Status:** Proposed (spec [P7-12](../specs/P7-12-autonomy-and-auto-approval.md), approved under the owner's standing run instruction and the owner's binding instruction of 2026-10-23; built 2026-10-23). Becomes Accepted when the owner has read it.
- **Date:** 2026-10-23.
- **Relation to other ADRs:** [0083](0083-the-plan-record-insert-only-state-trails-owner-only-approvals-lapse-by-default-and-no-order-by-name.md) (its owner-only rules and three safety reviews are kept; this ADR adds a second kind beside them and lifts only "the approval kind is `owner`"), [0087](0087-pretrade-checklist-pure-unavailable-never-passes-and-an-owner-only-confirm-despite.md) (unavailable never passes), 0086 (nightly), 0002 (config in the database).

## Context
The owner decided (2026-10-23): whatever needs manual approval must also be able to run automatically, controlled by a setting (ON = no manual approval, OFF = manual, default OFF); P7 places no order; paper accounts only; promotion from the reserve is a setting too; no learning change is applied automatically. ADR 0083 had made the owner the only kind of approval and written that raising it was a new migration.

## Decision
1. **A pure rule.** `AutoApprovalPolicy.Decide(ticket, checklists, settings, context)` returns Approve or Decline with every reason. Approve needs: switch ON in a stored row; primary and Proposed; before the cutoff; lower bound of the shrunk cell win rate at least the threshold (default 0.58); no unavailable input on the ticket; for every allocated account one complete unconfirmed checklist with all 14 checks Pass (it accepts only `ChecklistResult`, which cannot carry a confirmation); the daily cap (default 3) not reached. Decline leaves the ticket to the owner, whose manual path is unchanged; at the cutoff an undecided ticket still lapses.
2. **Settings are an insert-only table**, `workflow.autonomy_settings`: a complete snapshot per row (two switches, threshold 0.50 to 0.99, cap 1 to 20), actor `owner:...`, reason, and the database-stamped time and SHA-256 hash of the canonical text `autonomy:v1|auto=..|reserve=..|min_p_win=0.xxx|max_per_day=n`. The newest row is the highest id (the insert trigger draws the id after taking the exclusive lock, so id order is commit order; ordering by the stamped time was rejected because a backwards clock step could make an older ON row look newest); no row means everything OFF. `AutonomyChange.Create` (Domain) is the only constructor of a change and refuses a non-owner actor; the handler appends against the row the caller saw (else conflict); the endpoint takes the actor from the session and requires a FRESH password in the body for every change. The step-up window is not used: it is not consumed by use, so a session that stepped up for something else could flip the switch. The password is verified server-side by the step-up handler with `Elevate: false` (same lockout and audit, no window opened, extended or closed).
3. **A new approval kind `auto`** in `workflow.approvals`: actor exactly `rule:autonomy` (never `owner:`), decision approve only, no modifications, no confirmation, with `settings_id`, `settings_hash` (a composite foreign key to the settings row) and `policy_version`; an owner row must have none of those. The ticket move into Approved still needs the approval row and the state/chain/composite keys of ADR 0083. Modify and reject stay owner-only (an `auto` row cannot be anything but approve).
4. **The database decides, in the approval trigger**: the referenced row must be the NEWEST row and have the switch ON; the item must belong to that plan, be primary and still proposed (newest event); the plan must be published or in review; the count of auto approvals for that planned date must be below the row's cap (a per-date advisory lock serialises it); the cutoff is the existing `decided_at < cutoff` check on the database clock. A shared advisory lock on the settings (taken here) and an exclusive one (taken by the settings insert trigger) make a settings change and an auto approval mutually exclusive. The event trigger adds: an event backed by an auto approval is from Proposed, by the rule, on a primary item.
5. **One writer.** `PlanStore.AutoApproveAsync` (behind `IAutoApprovalStore`) takes the plan lock then the item lock, the same order as an owner's decision, so of an owner decision and an auto approval on one ticket one is written and the other is stale; the unique "a state is left once" index backs it without the lock. `IPlanStore.MoveItemAsync` is untouched.
6. **The pass** (`AutoApprovePlanHandler`) reads the switch first and returns at once when OFF. It has no actor argument. It is not called by anything yet; the cutoff service must call it before the cutoff. `ApplyReviewCutoffHandler` is unchanged, so OFF is exactly as before.
7. **Reserve promotion** (`ReservePromotion.Select`, pure): OFF never promotes; ON it applies the same terms as the auto rule. The pre-open check will add its own database gate when built.
8. **Evidence.** `plan_items.p_win_lower` (nullable, 0 to 1) holds the lower bound the rule reads; the selection builder fills it from the cell statistics.
9. **No order.** Nothing in this ADR places, modifies or cancels an order; the no-order tripwire is unchanged.

## Consequences
- Today no ticket can be auto-approved even with the switch ON (the checklist inputs are not wired and the builder lists unapplied inputs as unavailable); this is by design and tested. The machinery becomes live as those slices land.
- `Down` of the migration fails while an auto approval exists, because the old shape only knows the owner.
- The strings `owner:` and `rule:autonomy` are conventions enforced by checks, not identities; a process holding the runtime role could write either. The architecture rule and the review of the single writer are the control.
- `p_win_lower` is trusted (range-checked only). `ReservePromotion.Select` does not check plan state or the cutoff: P7-11 must add its own database gate. The checklist source wired in P7-10 must not return partial lists silently (the rule declines them, but the source must be honest).
- The settings are not in `platform.app_settings` (overwrite in place, no history); the others of Q14 may still be.

## Alternatives rejected
- Reusing `app_settings`: overwritten rows cannot show what was on at a past moment, which the database check needs.
- Letting the rule act as the owner (an `owner:` actor): rejected by the owner's instruction; the auto kind is separate and visibly distinct.
- A confirmable check counting as a pass for the rule: it would let an unavailable input through.
