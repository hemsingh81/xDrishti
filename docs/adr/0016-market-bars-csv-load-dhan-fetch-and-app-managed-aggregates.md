# 0016 — Market bars: load the CSV folder, fetch from Dhan's Data API, aggregate in the application

- **Status:** Accepted (owner, 2026-10-12: "analyse data/stocks_csv … create a Data & import page … load all data from stocks_csv, then from the Data API, then aggregate on all time frames … manual refresh … highlight the last tick datetime … keep it simple") — amends [ADR 0008](0008-broker-credentials-vault-and-connection.md) (endpoint allow-list) and design doc 05 §4/§9 (continuous aggregates)
- **Date:** 2026-10-12

## Context
`data/Stocks_CSV` holds 214 files `<SYMBOL>_1m.csv.gz` (≈ 41 M one-minute bars, 2024-04-01 → 2026-04-30; columns `time` (epoch seconds, UTC, bar start), `open`, `high`, `low`, `close`, `CE Breakout Level`, `PE Breakout Level` (always empty), `Volume`; 375 bars per normal session, 60 on the Muhurat session; 39 rows with an open outside the minute's high–low range, all first bars of a day). The owner has the Dhan Data API plan (₹499/month: intraday and daily chart data, live feed, …). Design doc 05 plans hypertables and TimescaleDB continuous aggregates; the runtime role `xd_app` has plain DML only and cannot refresh continuous aggregates it does not own.

## Decision
1. **Storage:** `market.bars_1m` hypertable (instrument, bar-start instant UTC, OHLC, volume, source `csv|dhan`), compressed after 7 days; `market.bars_agg` for every derived timeframe (5m, 10m, 15m, 30m, 1h, 1D, 1W, 1M), keyed (instrument, timeframe, bucket start); `market.bar_coverage` (first/last bar, count, source mix per instrument, maintained by every job); `market.data_jobs` (one row per run with phases, progress and counts) and `market.csv_files` (file name, size, modified time, rows, loaded at). Prices are raw (adjustments come with P1-10).
2. **One pipeline, three phases, one button:** *CSV* (load new or changed files of the mounted folder) → *Dhan* (fetch 1-minute bars after each tracked instrument's last bar, ≤ 90 days per request, throttled) → *Aggregate* (rebuild the touched ranges of every timeframe). Each phase can also be requested alone. It runs in the API as a background job like the instrument refresh, one at a time, and an interrupted run is marked failed at start-up.
3. **Precedence:** Dhan bars overwrite CSV bars for the same minute; CSV never overwrites Dhan. Rows are never silently dropped: rejected rows are counted and listed with the reason in the job.
4. **Row rules:** a row whose high/low do not contain open and close (the opening bar when the open is the pre-open price) is **repaired** (high = max, low = min over open/high/low/close) and counted as repaired; unparseable rows, non-positive prices, negative volume and duplicate minutes are rejected; zero-volume minutes are kept; special sessions (Muhurat) are kept.
5. **Symbols:** `<SYMBOL>` ↦ `NSE:<SYMBOL>` in the instrument master (shares/ETFs, not retired); unknown or ambiguous symbols are listed and skipped, never guessed; instruments that have bars from CSV files are tracked automatically (P1-05), but only when they have never had a tracking row (see the consequences).
6. **Aggregation in the application, not continuous aggregates:** set-based SQL upserts per instrument and touched date range, run as `xd_app`, idempotent and testable against an independent reference. Rules from design doc 05 §4 (09:15 IST anchoring, 1h buckets 09:15…14:15 plus the partial 15:15–15:30, daily bucket = IST date, week starts Monday, month = calendar month, bucket stores bar count and a completeness flag).
7. **Dhan Data API access:** a new allow-listed endpoint for the broker client, `POST https://api.dhan.co/v2/charts/intraday` (and nothing else new — still no order, position or fund endpoint). The token is the access token of the account with the primary **Data** role; if it is missing or expired the Dhan phase is skipped with a clear reason and the page says to reconnect.
8. **Mounting:** the CSV folder is mounted read-only into `xd-api` (`data/Stocks_CSV` → `/data/csv`, `Data__CsvFolder`).
9. **Not in this decision:** scheduled EOD fetch and gap detection (P1-12), data-quality checks (P1-14), corporate-action adjustment (P1-10), official daily candles, live feed.

## Consequences
- The page can show, for every instrument, the first and last bar (the "last tick" time) and how far behind it is.
- Aggregates are only as fresh as the last job; they are rebuilt for the touched range at the end of every run.
- The first CSV load is large (≈ 41 M rows); it is resumable per file and runs in the background with progress.
- Without a holiday calendar (P1-11) "behind" is judged against the last weekday session; holidays will refine it.
- The Dhan client (built 2026-10-12, [doc 05](../design/05-data-and-brokers.md) §6) adds to decision 7 only the one allow-listed endpoint (`POST /v2/charts/intraday`, no query): 15 s per request, one request at a time through a shared throttle, **one** retry after 2 s on 429/5xx/DH-904 and none on other 4xx; 401/403 (or DH-901/DH-902) end the phase. Dhan's documentation does not say which time base or time zone `timestamp` uses, so it is read as Unix seconds (milliseconds when it has 13 digits) and **proven from the data** before anything is stored: bars far from the period asked for, an India/UTC offset of 5 h 30 min, or end-of-minute stamps fail that instrument with a message naming the suspicion — nothing is shifted or guessed — and the overlap with the stored bars (0.05 %) remains the final proof. The minute that is still running is not stored.
- **A CSV file with a wrong clock is refused as a whole** (review fix, 2026-10-12). The CSV path has the same session/alignment proof as the Dhan fetch, as a streaming check over every accepted bar of the file (a shift of 5 h 30 min, bars outside every session, end-of-minute stamps), before the merge: nothing is stored and the reason names the suspicion. Times later than one day from now are rejected (`timeInFuture`), the range stays 2000–2100, and a file whose times are mostly out of range (milliseconds) fails instead of "loading" zero bars. The 60-bar Muhurat session, Saturday special sessions and the 39 repaired opening bars of the real files are unaffected (checked on all 214 files).
- **Per-file work is bounded:** `Data:Csv:MaxRowsPerFile` (5 000 000), `Data:Csv:MaxBytesPerFile` (1 GiB, counted after decompression) and `Data:Csv:MaxSpanDays` (3 700, about 120 monthly chunks); a file over a limit fails with the setting named. The real files are about 200 000 rows and two years.
- **Automatic tracking never undoes an untrack:** after a load only instruments that have bars from CSV files and **have never had a tracking row** (active or not) are tracked; an instrument the owner untracked stays untracked even when its file changes or is forced. The set comes from the instruments that have bars after the job (files loaded now or earlier), so a tracking that failed is retried by the next run even when all files are unchanged. (Decision 5 amended.)
- **A job ended elsewhere is not overwritten:** progress and final state are written only while the job is still `running` in the store; a worker still busy after recovery or the 12-hour rule failed its job learns that (zero rows updated), stops reporting and stops at its next file or instrument.
- **Chunk privileges** of the hypertable are checked, not assumed: `xd_app` has no DELETE/TRUNCATE on ordinary or compressed chunks, including chunks created later (TimescaleDB copies the hypertable's privileges to every chunk); tested in `DataTableGrantsTests`. Log event ids of this module are 3301–3315 (the first block collided with the instrument source's); the architecture tests now assert that every `[LoggerMessage]` event id is unique across the solution.
- **Residual risk of the missing DELETE (noted in the independent review, 2026-10-12).** `xd_app` has no DELETE on the bars, but it has `UPDATE` (the merge upserts) including the `source` column, so with the app's credentials the source of Dhan bars could be rewritten to `csv` and [ADR 0017](0017-trading-calendar-eod-schedule-quality-adjustments-and-csv-undo.md) §6's `market.undo_csv_bars` would then remove them. The protection against deleting market data is therefore only as strong as the application's own handling of `source`; this is accepted for a single-owner local system (design doc 05 §9).
