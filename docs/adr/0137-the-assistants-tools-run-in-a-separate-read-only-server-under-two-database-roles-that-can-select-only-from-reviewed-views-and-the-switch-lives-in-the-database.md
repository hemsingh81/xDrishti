# 0137 — The assistant's tools run in a separate read-only server under two database roles that can SELECT only from reviewed views, and the switch lives in the database

- **Status:** Proposed (written in P9-02 under the owner's delegation of 2026-10-26; the specs were treated as Approved). Becomes Accepted when the owner has read it. **SAFETY decision: a new container, two new database logins and the views that decide what the model may read.**
- **Date:** 2026-10-27.
- **Relation to other ADRs:** [0136](0136-the-local-model-server-runs-in-a-container-on-demand-with-the-measured-qwen3-30b-a3b-as-default-two-pinned-alternatives-and-a-status-the-api-reads-over-http-only.md) (the model server, `back` network, file secrets, profile `ai`), [0005](0005-local-llm-runtime-and-models.md), [0091](0091-auto-approval-is-an-option-behind-an-owner-setting-default-off-a-new-approval-kind-the-database-checks.md) (the settings-snapshot pattern copied by `ai.settings`), [0045](0045-the-result-store-sim-runs-and-sim-trades.md) (insert-only grants the views must not bypass), [0128](0128-owner-act-capabilities-are-one-insert-only-log-with-a-generic-gate-by-name-off-by-default-and-switched-on-only-by-the-owner-with-a-fresh-password.md) (switches OFF by default, owner acts).

## Context
The assistant (docs/specs/P9-00) answers questions about the owner's stored data with tools. Tools must run under a database role that cannot write and cannot see secrets, accounts, sessions or settings, in a process that has no write code at all. `xd-api` runs as `xd_app` (DML on every table by default privileges), and the init script that creates `xd_app` runs once per volume, so a new role must come from a migration. A model-supplied SQL text is untrusted; the privilege, not a parser, has to be the boundary.

## Decision
1. **A separate container `xd-mcp`** (profile `ai`, started with `scripts/xd-ai.sh`, never by `xd-up.sh`): four read tools `list_tables`, `describe_table`, `run_sql`, `lab_validate` over MCP Streamable HTTP, stateless, bearer token per client (`ModelContextProtocol.AspNetCore` **2.3.0**). Network `back` only, no published port, `read_only`, `cap_drop: [ALL]`, `no-new-privileges`, 512 MB, three secrets (its two passwords, its token) and none of the application's. The host has no `DbContext`, no command handler, no store and no database driver reference (architecture test, with a planted violation proving the rule fails). Tools are `AIFunction`s with their own JSON Schema (`additionalProperties: false`, bounds, pattern) so that a bad argument is `tool.invalid_arguments` naming the property instead of the SDK binder's exception; every tool carries the read-only annotations. Deviation from the spec text: the spec's attribute style (`[McpServerToolType]`) cannot give that error, so one base class and one `ToolSpec` per tool are the single source of schema and check.
2. **Two roles, not one.** `xd_mcp_sql` (only `run_sql`) and `xd_mcp_read` (typed tools, the catalog and the switch read). Both are created `NOLOGIN` by migration `AddAiReadAccess` (no superuser, no create, no inherit, no membership), with role-level `default_transaction_read_only = on`, `lock_timeout 1s`, `idle_in_transaction_session_timeout 10s`, `work_mem 16MB`, `temp_file_limit 64MB`, `search_path aiv`, `statement_timeout` 5 s / 10 s, `CONNECTION LIMIT` 3 / 6. Their only table privilege is `SELECT` on the views of schema `aiv` (and `ai.settings` for the read role); they have no `USAGE` on any application schema and no right on any sequence; the only function they may execute among the `SECURITY DEFINER` ones is `ai.context_allows`. A test proves this from the catalog over every relation, sequence and function of the database, and as the roles (writes, DDL, `COPY ... TO PROGRAM`, `lo_import`, `pg_read_file`, `DO` blocks that try to reach a secret all fail). Rejected: `SET ROLE` inside one connection (`set_config('role', ...)` from a SELECT can undo it); one role plus a SQL parser.
3. **Views, not table grants.** 35 views in schema `aiv` (28 of class C1, 7 of class C2 for the owner's portfolio), each listing its columns by name, owner-executed (`security_invoker` false) so the roles need no base-table right. Left out for good: every secret, token, client id, order id, broker security id, account number, the actor of an event (it can be `owner:<e-mail>`), the strategy text body, feature arrays and JSON documents; `bars` reads the daily and intraday aggregate, never the 1-minute table. The account id becomes the account **label**, through one helper view `ai.account_labels` (so no `aiv` definition names the accounts schema) that nobody but the owner can read. A manifest in code (`Domain/Assistant/DataManifest`) lists every view and column with class, kind, unit and meaning; integration tests compare it to the live database both ways, check every column name against `secret|token|password|passwd|client_?id|account_?(no|number)|pan|phone|email|dp_?id|demat|address`, check the kind against the database type, and check every view definition against the tables it must not reach. Every C2 view carries `WHERE ai.context_allows('portfolio')` and is a `security_barrier` view, so a function written into a query cannot see a row before the predicate removes it.
4. **`xd_app` has no access to `aiv`.** The init script grants `xd_app` DML on every table the owner creates in every schema, and a simple view is auto-updatable: without a revoke `xd_app` could UPDATE or DELETE base rows through a view and bypass the insert-only grants of `research.*`. The migration ends with `REVOKE ALL ... FROM xd_app` on the views and the schema (and from PUBLIC) and does not call the schema-usage helper for `aiv`; every later migration that creates a view in `aiv` must end the same way, and a test checks every relation of `aiv` found in the catalog.
5. **The switch is in the database.** `ai.settings` (insert-only for `xd_app`, a trigger stamps the id after a lock, the database time and the SHA-256 of the canonical text of **every value column**; a test flips each value column in turn and fails on a column the hash ignores) and `ai.context_allows(key)` (`SECURITY DEFINER`, fixed `search_path`; `assistant` is the newest row's `enabled`, `portfolio` is `enabled AND portfolio_context`; no row or any other key is false). The views follow the newest row at once, with no restart. Every tool call first reads the switch; when it is off the call ends with `assistant.disabled` and nothing else is queried. Turning it on is an owner act of P9-03; this slice only reads.
6. **`run_sql` is bounded by privilege first.** `BEGIN READ ONLY`; `SET LOCAL statement_timeout`; the text as a `NO SCROLL` cursor (it refuses `SELECT INTO` and data-modifying statements); a fetch of one row more than asked for (the cut is the server's); `ROLLBACK`; the call is also stopped half a second after the timeout whatever the database does. A lexical pre-check (one statement, `select`/`with`, 4,000 characters, no comment, ASCII outside quoted text, balanced parentheses, a list of refused keywords; literals, quoted identifiers and dollar quotes are skipped) is there for readable errors, **not** for safety; tests run the runner with the pre-check bypassed (a smuggled second statement, `SELECT INTO`, a data-modifying CTE, `set_config('role', ...)`) and show nothing changes.
7. **One runner enforces the contract.** `ToolRunner` is the only place for the switch, argument validation, the time limit, the row cap (200), the cutting of cells (300 characters), the 6,000-character fit (rows dropped from the end, the total kept), the 64 KB bound and the log event. Only cells of columns the manifest marks as text are cleaned (control, zero-width and bidirectional characters out, `<` and `>` escaped, injection-like patterns counted, the text still delivered) and scrubbed (PAN shape, JWT shape, 32 or more base64 characters, 9 or more digits: `[redacted]`); run keys, hashes, identifiers, amounts and every number pass untouched. For `run_sql` the decision is by the output column name (a name the manifest knows as structured stays structured, a name it does not know is text when the database type is a string type), except a column whose every cell has the shape of a SHA-256, which is a hash under another name. Tests: a real 64-hex run key, a SHA-256 and 12,345,678,901 pass unchanged with `redactions` 0.
8. **Provisioning.** Passwords cannot be read by a migration. `xd-api migrate` runs, after the migrations and the strategy seeding, a role step as the database owner: both password files present and non-empty (`AiRoles__ReadPassword`, `AiRoles__SqlPassword`, from `xd-migrate`'s secrets) give both roles `LOGIN` and a `scram-sha-256` password (passed as a parameter, quoted inside the server); otherwise the roles stay `NOLOGIN`, migrate succeeds and event 6020 says why. The step is idempotent and logs no password. `xd-up.sh` writes three secret files from the Keychain (`xdrishti/db/mcp-read`, `xdrishti/db/mcp-sql`, `xdrishti/mcp/token`), generated on first use and never replaced; `xd-api` also gets the token and the URL for P9-03. To rotate: change the Keychain item, run `xd-up.sh`, restart `xd-mcp`.
9. **Transport.** `/mcp` needs `Authorization: Bearer <token>` (SHA-256 of both sides compared in constant time, every configured token examined, an empty token never matches, 401 with the same answer whether the header is absent or wrong); the host name must be `xd-mcp` (framework host filtering); a body over 64 KB is 413; more than 60 calls a minute per client is 429; every path except exactly `/health` (any casing) needs the token and passes the same body and rate gates (a rule naming `/mcp` would miss `/MCP`, since routing ignores case); `/health` is anonymous, says only ok or unavailable, and the container health check is `dotnet XDrishti.Mcp.dll --healthcheck`. No CORS, no cookie authentication, no session. An unauthorized request is logged at Debug only. Logs (events 6020 to 6035) hold the tool, a hash of the arguments, the number of rows, the time and the status, never a query, an argument value, a row or a token.
10. **Review hardening (migration `AddAiReadAccessHardening`).** The roles are members of PUBLIC, so PUBLIC's rights are theirs; three were taken from PUBLIC and given back to `xd_app`: `TEMPORARY` on the database (no temp tables), `USAGE` on schema `public` (the role-level REVOKE of the first migration was a no-op), and `EXECUTE` on the `pg_advisory*` lock functions (except `pg_advisory_unlock_all`, which the driver calls when a pooled connection is reset and which frees only the caller's own locks). The pre-check also refuses dollar quoting and any `$` that is not a positional parameter (a tag inside a name such as `a$x$` hid semicolons from the scan), and the function families `pg_advisory*`, `set_config`, `dblink*`, `lo_*`, `pg_read_*`, `pg_ls_*` and a few server-control ones (`pg_sleep` stays: the time limit is tested with it). The runner prepares the cursor command first and stops unless the driver counts exactly one statement. A database refusal reaches the model as the SQLSTATE and a fixed text, never the server's message (it can quote a cell). A text cell is read through a bounded text reader (300 characters plus one), so a huge value is never held; a bytea cell is reported as `[bytea]`. Residual: an array or other large non-text value is still read whole.
11. **What the roles can still see.** The definitions in `pg_catalog` and `information_schema` that every login sees: names of schemas, tables, columns and functions of the whole database, and the statistics views PostgreSQL shows to all. They cannot read any row of any of them but the `aiv` views (tested), so the cost is that the model could learn that `accounts.broker_secrets` exists, not what it holds.
12. **For P9-03 (settings endpoint).** `xd_app` may insert any `ai.settings` row; the table only requires `changed_by LIKE 'owner:%'`. Nothing in the database proves the owner acted. The endpoint of P9-03 must therefore require the owner's fresh password and write the actor itself, as the other owner acts do; this slice writes no row.

## Consequences
- The model can read exactly the columns of the 35 views, and only after the owner's database row says so; the worst a hostile prompt can cause is a misleading answer and 6 calls (budget of P9-03), never a write.
- A new view needs a migration (with the two revokes), an entry in the manifest and a passing manifest test; a new value column of `ai.settings` needs a replaced trigger function in the same migration.
- Typed tools (P9-05) will need a few report-source tables for `xd_mcp_read` beyond the views; that grant is a decision of that slice, with its own test.
- `list_tables` sizes are the planner's estimates of the base tables, not counts.
- Added: the package `ModelContextProtocol.AspNetCore` 2.3.0 (and its dependencies), an image target `mcp`, a compose service, three secrets, the migration `AddAiReadAccess` (with a `Down` that drops views, functions, table, schemas and, when nothing else depends on them, the roles).

## Not verified in this build
- The stack was **not** brought up with `xd-mcp`: nothing was started or switched on. Compose parses (`compose config`) and the static rules pass; the image build, the container health check, the `xd-ai.sh start --tools-only` path and the Keychain items were not exercised against the running stack. The first `scripts/xd-ai.sh start --tools-only` after `deploy/xd-up.sh` is that test.
- `list_tables`'s `approxRows` of a table never analysed is 0.
- The SDK is pinned at 2.3.0; its option names were read from the package's XML documentation and exercised by the contract tests (`tools/list`, a call, 401, 413, 429, the host header) against the real host with a real MCP client.
