# 0136 — The local model server runs in a container on demand with the measured Qwen3-30B-A3B as default, two pinned alternatives, and a status the API reads over HTTP only

- **Status:** Proposed (written in P9-01 under the owner's delegation of 2026-10-26, "model and GPU: check yourself and do the best"). Becomes Accepted when the owner has read it. **SAFETY decision: a container with GPU device access and a new secret.**
- **Date:** 2026-10-27.
- **Relation to other ADRs:** [0005](0005-local-llm-runtime-and-models.md) (the runtime and model choice, amended by this ADR, not edited), [0003](0003-local-stack-compose-and-secrets.md) (secrets as files), [0128](0128-owner-act-capabilities-are-one-insert-only-log-with-a-generic-gate-by-name-off-by-default-and-switched-on-only-by-the-owner-with-a-fresh-password.md) (switches OFF by default).

## Context
P9-01 must decide what really runs on this Mac and pin it. Facts read on 2026-10-27: Mac16,7, Apple M4 Pro, 51,539,607,552 bytes (48 GB) unified memory (`sysctl`); Podman machine `podman-machine-default`, libkrun, 10 CPUs, 24,576 MiB, 120 GiB disk, rootless (`podman machine inspect`); host swap 24.8 of 25.6 GB used (`sysctl vm.swapusage`, 2026-10-27); VM memory 23,962 MB total, 19,399 MB available with the stack running.

## Decision
1. **Runtime: container, not host-native.** The measured speed (P0-15) is 71 to 88 % of native Metal for generation and 56 to 73 % for prompt reading, every speed threshold passes, and the container keeps the model server inside the compose stack: internal network with no route out, file secret, read-only model mount, one start/stop path. Host-native would need the API to reach the host (`host.containers.internal`), which widens the network boundary of `back`, and a host process outside the compose hardening. Native Metal (llama.cpp b11530, `scripts/llm-setup.sh`) stays the documented fallback: an endpoint change only (`Assistant__Llm__BaseUrl`). Rejected: krunkit/Vulkan variants other than the one measured (not measured here), the RamaLama CLI (publishes on all interfaces).
2. **Image pin.** `quay.io/ramalama/ramalama:0.25.0@sha256:d60dfda3113e127071d2b2679921c763d0eb7a0733596f68bf93a4ef1ca1216e` (created 2026-09-25, 1,021,677,557 bytes on disk, image id `829aa6d2e660`; pulled earlier, checked again here with `podman image inspect`). Inside it (run with `--network none`, 2026-10-27): Fedora 44, `llama-server --version` prints "version: 0.4.1-dev (build 1, commit b29c606)" built with GNU 16.2.1 for Linux aarch64 (a dev build string; the upstream llama.cpp build number is **UNVERIFIED**). Flags checked in `--help`: `--api-key-file` (env `LLAMA_ARG_API_KEY_FILE`), `--chat-template-kwargs` (env `LLAMA_ARG_CHAT_TEMPLATE_KWARGS`), `--no-webui`, `--jinja`, `--slots/--no-slots`. `curl` and `bash` are present, `wget` and `nc` are not (the health check uses `curl`). The server rejects an empty `LLAMA_ARG_CHAT_TEMPLATE_KWARGS` at start ("attempting to parse an empty input") and accepts `{}`, `null` and the thinking-off object, so compose defaults it to `null`; `xd-ai.sh` exports the real value.
3. **Hardening result (M5, partly).** With `--read-only --tmpfs /tmp --cap-drop ALL --security-opt no-new-privileges`, uid 1000 can open `/dev/dri/renderD128` (mode 0666) and can read the model folder (virtiofs, world-readable files). So the service runs as `user: "1000:1000"`, not root; `group_add: keep-groups` is not supported by this remote Podman client and is not needed. **UNVERIFIED:** that Venus/Vulkan really initialises under this user and read-only root: that needs a model load, which this build did not run. If it fails on the first start, the fallback in the spec applies (root with `cap_drop: [ALL]`, no egress), recorded as an exception in doc 17.

   **Default stays `main`**, because it is the one model measured here for speed, memory and 10/10 tool calls and it is already on disk. The pick between the three belongs to the P9-09 evaluation (a candidate is only promoted by measured answers). Nothing newer was found that fits: the official Qwen GGUF list has no Qwen3.5/3.6 model (searched 2026-10-27), Qwen3-Next-80B does not fit 48 GB, and the one web comparison found (indirect, a blog) favoured gpt-oss-20b for clean tool calls without testing the Instruct-2507 GGUF under llama.cpp, so it is not evidence either way.
5. **Where the files live.** `~/Library/Application Support/xDrishti/models` (the P0-15 folder, `XD_MODELS_DIR`) and `data/models-llm/` (git-ignored through `data/**`; filled by `scripts/fetch-model.sh`, which asks y/N, resumes, checks size and SHA-256 and deletes a file that does not match). `scripts/xd-ai.sh start` mounts whichever folder holds the chosen file, read-only, and loads it with `-m` (never `-hf`, so the server never downloads).
6. **On demand and OFF.** The service has profile `ai`, `restart: "no"` and is not started by `deploy/xd-up.sh`; the owner runs `scripts/xd-ai.sh start|stop|status`. A missing model file is reported as `model_missing` (exit 2, with the command that gets the file), never as an answer. The API has a deployment flag `Assistant__Llm__Enabled` (compose `XD_ASSISTANT_LLM`, default false): while false it makes no request to the model server and the status says "switched off in this deployment". No hosted service exists in this slice, so there is nothing to register paused; the later chat endpoint (P9-03) is behind the owner's `ai.settings` switch, default OFF.
7. **Status over HTTP only.** `GET /api/assistant/llm-status` asks `/health` (no key), `/v1/models` and `/props` (key); the API holds no container socket. States `ready`, `loading`, `down`, `misconfigured`; the detail is a fixed sentence. `model_missing` is a state of the start script, because the API cannot see the host folder and a missing file shows as `down`.
8. **Not measured in this slice** (all need the model loaded and the stack under load; recorded as owner/next-session work, not claimed): M1 peak memory (so `mem_limit: 8g` stays a placeholder: the benchmark's VM peak was 5.3 GB), M2 five cold-start load times with memory samples, M3 effect on API and worker (so P9-00 D13, no chat during the nightly run, stays), M4 prompt-cache effect, the explicit `LlmSmokeTests`, and M5's GPU initialisation under the non-root user.

## Consequences
- The first `scripts/xd-ai.sh start` is also the first real test of items 3 and 8; its result is appended to doc 17 and to this ADR.
- The API's package set moves to `Microsoft.Extensions.*` 10.0.13 (needed by `Microsoft.Extensions.AI` 10.11.0) and adds `Microsoft.Extensions.AI` and `.OpenAI` 10.11.0 and `OpenAI` 2.14.0. The Dockerfile's `runtime` base image (used by the worker) is still 10.0.12; the app brings its own `Microsoft.Extensions.*` assemblies, so this was left alone.
- Nothing leaves the Mac: `xd-llm` is on `back` (internal) only, publishes no port and holds no secret but its own key.
