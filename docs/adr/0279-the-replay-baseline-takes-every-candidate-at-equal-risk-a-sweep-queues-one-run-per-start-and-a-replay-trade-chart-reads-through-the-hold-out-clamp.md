# 0279 — The replay baseline takes every candidate at equal risk, a sweep queues one run per start, and a replay-trade chart reads through the hold-out clamp

- **Status:** Proposed (spec [SR-02](../specs/SR-02-replay-baseline-arm-start-date-sweep-and-chart-link.md), approved 2026-11-12 as the coordinator's recommendation under the owner's standing instruction). Becomes Accepted when the owner has read it.
- **Date:** 2026-11-12.
- **Relation to other ADRs:** extends [ADR 0272](0272-the-system-replay-is-research-only-fenced-from-evidence-and-hindsight-labelled-and-runs-the-live-pieces-over-as-of-facts-in-memory.md) (the fence, the labels, one replay at a time are all kept); the paired day bootstrap of ADR 0216; the research fence of ADR 0243; the P8-11 trade chart (ADR 0125).

## Decision
1. **The baseline arm** (`arm = baseline`, frozen mode only) takes every candidate the session found, with no filter, ranking, smart rule, cluster, sector or max-positions cap, under the same capital, profile, costs, scope, versions and cells. Each of the n candidates risks r = min(risk per trade, (total-risk limit less open risk) / n) of equity; the quantity is the live `PerAccountAllocator`'s (risk, capital per trade, free cash). Headroom at or below 0 blocks every candidate as `total_risk`, and a daily loss at or past the profile's limit (the pre-trade checklist's rule, `figures.DailyLossPct >= limit`) stops every new candidate (reason `total_risk`, detail `daily_loss`; the closed list of eight block reasons is unchanged).
   **Live limits and the baseline.** Applied to both arms: risk per trade, capital per trade, free cash, total-risk headroom, daily loss, positive equity, one position per symbol. Applied to the selection arm only, by design (they are the choosing): the selection filters, ranking, smart rules, market gate, equity throttle, cluster cap, max positions and entries per day, per-sector and basket caps, correlation, size scaling and the liquidity pool. A symbol already open, or a second cell of a symbol in the same session, is not doubled (blocked as `capital`, detail `already_held`). Fills and exits use the same `TicketReplayer` path; a `data_missing` session takes nothing in either arm. The label `baseline_no_selection` says it is "no choosing among the system's candidates, not random stocks". Random-k and learning-mode baselines are deferred.
2. **The arm is part of the parameters** (so of the input hash) but is left out of the stored text when it is `selection`, so every run stored before SR-02 keeps its hash and can resume. The column `replay_runs.arm` repeats it.
3. **The comparison** is `ReplayPairComparison.CompareArms`: the same paired day bootstrap and bars as frozen versus learning (the selection run in the "learning" slot), seeded apart (`sr02|...`). Answers: `selection_better`, `baseline_better`, `no_measurable_difference`, `too_little_history`; n, informative days and P are always shown. It stays realised-only (`shortcut`). A baseline request makes a selection run and a baseline run with one `pairId`; `GET /pairs/{id}` answers `selectionVsBaseline` (and `frozen`, `learning` and the old answer fields are then null).
4. **The sweep**: 2 to 12 distinct start dates with one end date E (default the last readable session), frozen, selection arm. All runs are stored `queued` in one transaction with one `sweep_id` (table `research.replay_sweeps`, insert-only) and created one microsecond apart, so the existing job claims them oldest first, one at a time, in date order. Each run is one `system_replay` look in the trial ledger written at the start ("this sweep adds N replay looks"). A start needs at least 126 sessions up to E and frozen cell statistics as of the start; otherwise the whole sweep answers 422 naming each bad date. 409 `replay.busy` while any replay is active, and a single replay started while a sweep has queued runs is busy for the same reason. The read gives per-start CAGR, max drawdown, final equity, trades and whether the run beat the benchmark, and the spread (min, median, max of CAGR and max drawdown, share with CAGR above 0, share beating the benchmark) over the completed starts. Cancel stops the run in flight after its session and cancels every queued run; the ledger rows stay.
5. **A frozen snapshot per freeze date.** `ReplayFacts` kept one frozen snapshot for the instance; the runs of a sweep are prepared on one instance, so it now keeps one per freeze date (each start reads its own).
6. **The chart** `GET /api/replay/runs/{id}/trades/{tradeNo}/chart` returns the P8-11 `chart` block (bars, coherence), markers (entry, stop, exit) and limits. The instrument is the symbol's member of the universe as of the entry session; bars come through the replay's clamped reader and `TradeReplayWindow`, so a window past the clamp is cut at it and says so; more than 5,000 bars is refused (422). The bars are as stored (not adjusted by later actions; stated in the limits). The exit price is not stored: it is derived as entry + gross result / (quantity x side), exact for gross figures, and the view says `exitPriceDerived`.
7. **The fence stays.** The sweep table joins the write list of `ReplayStore` (the only code that names it); no evidence reader may name it; nothing reaches evidence; no order is referenced.

## Consequences
- Migration `AddReplaySweeps` (Down included): `replay_sweeps`, `replay_runs.arm` (check), `replay_runs.sweep_id` (FK), and a replaced guard trigger that keeps both fixed after the insert. The runtime role has SELECT and INSERT on the sweep table.
- A sweep of 12 starts averaging 300 sessions over 100 instruments is about 53 minutes of engine time, and 12 more looks in the ledger; the look count and "data seen before" stay first on screen.
- The baseline uses the same cell set as the selection arm, so it measures the value of choosing among the system's candidates, not of the cells.
- `GET /pairs/{id}` changes shape for the frontend: `frozen` and `learning` can be null (a baseline pair).
