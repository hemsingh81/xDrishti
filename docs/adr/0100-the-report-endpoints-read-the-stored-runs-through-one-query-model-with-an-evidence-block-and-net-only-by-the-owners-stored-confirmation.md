# 0100 — The report endpoints read the stored runs through one query model with an evidence block, and a report is net only by the owner's stored confirmation

- **Status:** Proposed (spec [P8-06](../specs/P8-06-report-read-endpoints.md), approved: the P8-00 questions it touches answered as recommended, read-only build; built 2026-10-24). Becomes Accepted when the owner has read it.
- **Date:** 2026-10-24.
- **Relation to other ADRs:** [0127](0127-the-owners-confirmation-of-the-charge-sheet-is-an-insert-only-log-written-only-by-the-owners-endpoint-after-a-fresh-password-bound-to-the-rates-hash-and-off-by-default.md) (the owner's act that writes the confirmation), [0099](0099-the-report-engine-is-a-pure-core-with-one-population-rule-six-honest-states-and-a-ranking-by-the-credible-lower-bound.md) (the engine these endpoints serve, and the hook for the stored confirmation), [0045](0045-the-result-store-sim-runs-and-sim-trades.md) (the stored runs and trades; the reader pattern), [0044](0044-the-cost-choice-the-stored-charge-sheet-the-cost-sheet-verbs-and-the-bill-check.md) (the stored charge sheet; ISS-25), [0053](0053-the-same-entries-comparison-and-the-mae-mfe-diagnostics.md) (the comparison that gives a run its exit), [0083](0083-no-order-is-placed-before-phase-12-an-architecture-tripwire.md) (nothing here touches an order).

## Context
P8-05 built the report engine as a pure core; nothing could reach it. The exit of P8 ("what works, in which basket, on which timeframe, with which exit") needs the stored simulation runs readable over HTTP, with the honest rules of the engine intact: no number for a non-value, no trade counted twice, no report called net on anyone's say-so. The plan (P8-00, risk 2) asked for a spike first, because exit and style are not trade columns, the fill of `basket_ids` was unverified and the size of the trade table was unknown.

## Decision
1. **Where the facts live (the spike, [P8-06](../specs/P8-06-report-read-endpoints.md)).** Trades, windows, the costed flag and the closed or open state are columns of the result store. **Style** is that of the stored strategy (`lab.strategies.style`). **Exit** is the candidate id of the stored comparison the run belongs to, and is *not recorded* for any other run and for a run in comparisons that disagree. The **basket** is on the trade (none for a list of instruments, the one basket for a basket run; the column is an array, so several are storable), and the first stored trade of a basket run names the universe of the run. The sources are printed with the labels (`stored strategy`, `stored comparison <key>`).
2. **A port, a streamed projection.** `IReportTradeSource` (Application/Abstractions/Reporting) lists the runs and streams the closed trades of chosen runs; the Infrastructure implementation reads 13 columns with a plain reader (no change tracker), the filters (strategy, timeframe, side, symbol, basket, dates) as statement parameters, and interns the repeated strings. It lives in `Infrastructure/Research` because only that namespace may name the result tables (ADR 0045); the architecture rule that keeps the adapters of that namespace honest names it. It only reads.
3. **One query model.** `ReportQuery` (lens, filters, metric, run set, basis, page) is parsed from the query string against whitelists; every unknown name, bad run key, date, limit or cursor is 422 `reports.invalid`, all problems together, a rejected value echoed cut short and without control characters. The same query serves all nine endpoints (`/runs` takes none): `/summary`, `/groups`, `/pivot` (a lens of exactly two dimensions), `/equity`, `/distribution`, `/insights`, `/what-works` (added to the plan's list because the exit question needs it and the engine has it) and `/trades`. The URL is the view.
4. **The run set is explicit or the default.** Named runs must exist (404 `reports.not_found`). Otherwise: for each strategy and universe the newest run, among the runs costed the way the newest run of all is, so gross and net never mix; every run left out is listed with the reason, and the evidence says the set was the default. The engine's refusals pass through with their codes: 409 `reports.run_overlap` and `reports.mixed_basis`, 422 `reports.double_count`, `reports.dimension_unavailable` (regime, account).
5. **Evidence and the six states on the wire.** Every answer carries `ReportEvidenceView`: basis, n, dates, the runs used with their facts (the Data used panel), the limits (the engine's and this slice's: closed trades only, how many open trades were left out, where style and exit come from, what a basket run carries), the unavailable inputs, duplicates dropped, and what the owner confirmed for a net report. A figure is a `MetricView` (state, a number only for value and provisional, the reason). A thin group has no equity points and no distribution bins; a pivot gap is `empty`; the empty store gives `empty` everywhere and reads no trade. "Nothing has enough evidence yet" is a 200.
6. **Net by the stored confirmation only (SAFETY).** `ChargeSheetConfirmation` has exactly one source: `IChargeSheetConfirmationSource`, which reads the settings row `reports.charge_sheet_confirmation` (`{"sheet_id","rates_sha256","confirmed_on"}`) and returns it only when the row parses, the rates hash is present and 64 lower-case hex, the sheet is *stored* and **the stored sheet's rates hash is still the confirmed one**: the cost sheet store overwrites a sheet in place, so a confirmation of a name would silently cover other rates; a confirmation of rates the sheet no longer has is "not confirmed". Anything else is "not confirmed". `basis=net` is a request that the loader allows only with that value *and* only over runs whose stored sheet id **and rates hash** (`costs_rates_sha256` of the run header) are the confirmed ones (else 422 `reports.net_unavailable`, naming the run and the difference), and never over an empty run set (422 `reports.net_unavailable`, not an empty "confirmed" report); without it the answer is 422 `reports.net_not_confirmed` with the reason, and `/runs` says net is `unavailable` with the reason. The evidence of a net report prints the sheet, the first 12 characters of the rates hash and the date. No query parameter, header or body is read for it: the parameter records have no such field, and architecture tests fail if any request, query, command, body, input, filter or params type of Application, Infrastructure or Api carries a confirmation or a flag named for one, if the Api names the confirmation type or its source at all, or if any Application type but the loader and the runs list reads the source. The integration tests send `confirmed=true`, `chargeSheetConfirmed=true`, `sheet_id=...`, `rates_sha256=...` and two confirmation headers with `basis=net`: 422 while nothing is stored, and with a stored confirmation the answer is the stored one whatever the request names. **Nothing in this slice writes the confirmation**; the owner's act of confirming the sheet (a verb in the pattern of `cost-sheet`, with the owner's own decision, writing the hash of the rates it shows) is a separate slice. Until then every report is gross.
7. **Read only.** The module maps GET and nothing else; no command handler, no write SQL (architecture tests read the sources); session-protected; no export, no job, no order-named member (the tripwire stays green).
8. **Answers are bounded, never cut, and so is the work after the read.** The engine takes the cap as an argument (`GroupBy`, `Pivot`, `Equity`, `Distribution`, `FindWhatWorks`) and its single pass over the trades stops at the first group past it, before any figure, equity point, bin or pivot cell is built; a pivot whose grid (rows times columns) is larger than the cap is refused before its cells are laid out. Caps: 2,000 groups, 10,000 pivot cells, 200 distributions, 40 curves, 2,000 "what works" cells; over the cap the answer is 422 `reports.invalid` ("the lens has more than N groups; at most N are returned at once"), because a cut answer would read as the whole. What is **not** bounded by these caps: the pass that finds the groups (it reads the whole population, at most once), which is bounded by the ceiling of decision 11; the trade list pages at most 1,000 trades.
9. **The engine gained what the endpoints need**, pure and tested by hand tables and a seeded property: the equity and drawdown series (one point per exit date, none for a thin group), the R distribution (bins of half an R from -4 to 6 with open ends), a slice of the trades in the order of the exits, and a faster population build (one array sort per order instead of two LINQ sorts, no string per trade in the signal check, one pass for the evidence), which took the population rule on 500,000 trades from about 700 ms to about 380 ms without changing a result (all 2,963 domain tests unchanged).
10. **Log events** 4800 `reports.loaded` (kind, runs, trades, basis, ms) and 4801 `reports.refused` (kind, code): no trade, symbol, strategy or figure.
11. **The load is bounded (memory).** (a) *Ceiling:* the closed trades of the runs used, from the run headers and before any filter, may not exceed `ReportLoader.MaxClosedTrades` = 500,000; above it the answer is 422 `reports.too_large` (count and ceiling in the message) and no trade is read. The ceiling is the size at which one request was measured (section below). (b) *Gate:* a process-wide `ReportGate` (a `SemaphoreSlim(1)` held by the loaded report until its handler has built the answer) lets one report at a time hold a population in memory; a request that waits honours its cancellation token, and a refusal or an error releases the gate. (c) The runs list takes no population and needs no gate.
12. **A trade-list cursor belongs to its report.** The cursor is `o<offset>.<hash>`, the hash being eight hex characters of the used run keys and the number of trades; a cursor from a report with other runs or another number of trades, or a forged one, is 422 (the hash does not cover the filters and is not a security boundary: two reports with the same runs and the same trade count but different filters share it, a known limit) `reports.invalid` instead of paging through a list that changed under it. There is no stored state between pages: **every page recomputes the population** (the measured cost below applies to every page).
13. **Each endpoint declares only the parameters it uses** (`ReportFilterParams` for summary and insights, `ReportLensParams` for groups, equity, distribution and what-works, `ReportPivotParams`, `ReportTradesParams`), so the contract does not advertise a lens, a metric, a limit or a cursor where it is ignored. Strategy, symbol, exit and basket match exactly and case-sensitively, and the operation summaries say so. `openAtEndLeftOut` counts the open trades of the whole runs from their headers, before any date, symbol or basket filter, and the limit line says so.
14. **Curve and summary agree.** The point of an exit date carries the running R at the end of the date and the deepest fall reached at any exit of that date, so the deepest point of the curve is the maximum drawdown of the group whatever the order of trades within a date (a seeded property and a hand pair, a loss then a win on one date, pin it).

## Measured (the plan's UNVERIFIED target of 1 s p95)
One synthetic gross run of **500,000 closed trades** (1,250 instruments, a buy and a sell on each of 200 days: `StoredRunFixtures.Synthetic`), stored in a scratch database on the local TimescaleDB container (Podman, same machine as the test process), the machine otherwise idle. Each sample is the use case plus the JSON of its answer, in a scope of its own like a request, 20 samples after one warm-up; **the HTTP hop, the session check and a network are not in it**. Measured 2026-10-24 by `ReportsPerformanceTests` (explicit: `-explicit only`, `XD_REPORT_SAMPLES=20`).

| Report | median | p95 | largest | answer |
|---|---|---|---|---|
| summary | 882 ms | 981 ms | 985 ms | 3.6 KiB |
| groups by strategy and side | 917 ms | 1,000 ms | 1,076 ms | 5.0 KiB |
| groups by month | 915 ms | 1,012 ms | 1,034 ms | 10.8 KiB |
| pivot instrument by month (1,250 x 7 = 8,750 cells) | 1,330 ms | **1,434 ms** | 1,462 ms | 991.5 KiB |
| equity, whole population | 882 ms | 1,017 ms | 1,027 ms | 22.2 KiB |
| distribution, whole population | 859 ms | 952 ms | 981 ms | 3.7 KiB |
| insights | 930 ms | 1,022 ms | 1,035 ms | 3.8 KiB |
| what works | 899 ms | 1,007 ms | 1,030 ms | 5.9 KiB |
| trades, a page of 100 | 864 ms | 974 ms | 978 ms | 35.8 KiB |
| runs list | 24 ms | 29 ms | 30 ms | 0.8 KiB |

**The target of 1 s p95 (UNVERIFIED in the plan) is not reliably met on a run of 500,000 trades.** Eight of the nine reports sit at 0.95 to 1.02 s p95 (four at or under 1 s, four a few percent over), the pivot of two wide dimensions is 1.4 s. Each request holds the whole population in memory (see Memory below). Where the time goes (three rounds on the same run): listing the runs 25 ms; streaming and building 500,000 trade records 450 to 700 ms (the first round is the cold one); the population rule 370 ms (it was 700 to 1,000 ms before the sort and the signal check were rewritten, see decision 9); one grouping 25 to 55 ms; the JSON of the answer is small. A first measurement taken while other work ran on the same machine gave p95 up to 1.9 s, so the figures vary with load. The cost grows with the number of trades read; it was not measured at other sizes (the 20,000-trade run of the always-on test is checked for its figures, not its time). On the owner's real data the size is unknown: the database was not queried. **Nothing was hidden to reach these figures; no cache was added.** If the screens need under a second on a run this large, the follow-up is a stored pre-aggregation (per run and group, insert-only), a separate decision.

### Memory (the container has `mem_limit: 1g`, `deploy/compose.yaml`)
The first version of this ADR quoted "about 530 MiB" from the managed heap at the end of a test that still held its 500,000-trade fixture; that figure was not a per-request peak and is withdrawn. The test now builds the fixture in a helper that returns only a count, collects the heap, then samples the working set and the committed managed heap every 10 ms while ONE request runs (`ReportsPerformanceTests`, `report-memory` lines), on the same run of 500,000 trades:

| | peak working set above the idle process | peak committed managed heap above idle | allocated during the request |
|---|---|---|---|
| one request (workstation GC, the test host's mode) | **+155 to +160 MiB** | +161 to +163 MiB | 353 MiB |
| six requests fired at once, with the gate | +311 to +315 MiB | +317 to +325 MiB | 2,181 MiB (six times one) |

One request therefore holds about 160 MiB (about 320 bytes a trade) at its peak, 16 % of the container's gigabyte; the live population is smaller than that, the rest is the arrays the build holds at once and garbage not yet collected. With the gate the six at once ran one after the other (6.4 to 11.9 s, six times one request) and peaked at about twice one request, because the garbage of the finished ones is not yet collected, not three or six times: without the gate six populations could be live together, about 1 GB. **Not verified:** the API runs server GC in a container with a hard heap limit of 75 % of the limit (750 MiB); a test process with server GC on this many-core machine commits far more heap before it collects (+611 MiB for one request) and cannot show the container's behaviour, and the idle size of `xd-api` in production was not read. The ceiling of 500,000 keeps one request at the measured peak above whatever the API already holds; if the API's steady size leaves less than that, the ceiling is the constant to lower.

### Reading the p95 table
With 20 samples the 95th percentile is the 19th, the **second largest** sample (the largest is shown beside it); it is a rough guide, not a tail estimate. The samples exclude the HTTP hop, the session check and any network, and a request that waited at the gate. A second run taken while the machine was loaded by other work (load average about 28) gave medians of 1.0 to 2.4 s and p95 from 1.1 to 4.2 s with the same code, so the table above is for an idle machine and nothing more.

## Consequences
- The exit question can be asked of the stored research over HTTP, and the likely answer on this data (nothing has enough evidence yet) is an ordinary 200.
- Every report reads the whole population of its runs into memory and groups it; there is no stored pre-aggregation. That is simple and exact, and the cost is the figures above, growing linearly with the trades. **If the owner's data or the screens need it faster, a stored pre-aggregation (per run and group, insert-only, in the pattern of the cell snapshots) is the named follow-up; it is a separate decision, not part of this slice.** The owner's real size is not yet known (not queried).
- Two basket runs of one strategy over baskets that share an instrument hold the same signal (P8-05's rule) and cannot be added together; the screens will have to say so and offer the runs one at a time. Two explicit lists of instruments of the same size and label are not told apart (the header does not keep the members) and can be refused as one universe.
- The style and exit labels exist only where a stored strategy or a stored comparison gives them; most real runs will show `not recorded` for the exit, and "which exit" will be answerable only over compared runs.
- The `reports.charge_sheet_confirmation` row does not exist on the owner's database; net stays unavailable until the owner's act is built. **Update 2026-10-26 ([ADR 0127](0127-the-owners-confirmation-of-the-charge-sheet-is-an-insert-only-log-written-only-by-the-owners-endpoint-after-a-fresh-password-bound-to-the-rates-hash-and-off-by-default.md)):** the act is built, and the confirmation lives in the insert-only table `workflow.charge_sheet_events`, not in a settings row (a settings row can be edited in place); `IChargeSheetConfirmationSource` reads the newest confirm-or-revoke row and applies the same rule of this decision 6 (stored sheet, same rates hash). A hand-written settings row is no longer read.

- Every page of the trade list and every report recomputes its population (about 0.9 s on 500,000 trades); there is no stored state between pages.
- A request waits at the gate behind a large report; a page that fires several reports on a large run is served one after the other.
- A run set above 500,000 closed trades is refused whole (`reports.too_large`), even when a filter would leave few trades, because the ceiling reads the run headers and the filter is applied in the store.

## Alternatives considered
- **A confirmation flag or sheet id in the query ("net=confirmed").** Rejected: it lets a caller make a report net by saying so.
- **Write the confirmation in this slice (a verb or an endpoint).** Rejected: a write, an owner decision (SAFETY), and the slice is read only.
- **Cache the loaded populations.** Rejected here: hundreds of megabytes held in memory for a single-owner tool, and a stale-data question the immutable store does not need.
- **Group in SQL.** Rejected: the engine owns the rules (population, shrinkage, states); a second implementation in SQL would drift. A stored pre-aggregation is the right place for speed.
- **Cut an oversized answer to the cap.** Rejected: silent truncation reads as completeness.
- **A separate endpoint per lens, or a POST body for the query.** Rejected: one GET model keeps the URL the view (Back works, a link reproduces it) and keeps the read path free of any body.
