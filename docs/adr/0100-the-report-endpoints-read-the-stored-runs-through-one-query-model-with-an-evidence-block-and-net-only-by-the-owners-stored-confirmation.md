# 0100 — The report endpoints read the stored runs through one query model with an evidence block, and a report is net only by the owner's stored confirmation

- **Status:** Proposed (spec [P8-06](../specs/P8-06-report-read-endpoints.md), approved: the P8-00 questions it touches answered as recommended, read-only build; built 2026-10-24). Becomes Accepted when the owner has read it.
- **Date:** 2026-10-24.
- **Relation to other ADRs:** [0099](0099-the-report-engine-is-a-pure-core-with-one-population-rule-six-honest-states-and-a-ranking-by-the-credible-lower-bound.md) (the engine these endpoints serve, and the hook for the stored confirmation), [0045](0045-the-result-store-sim-runs-and-sim-trades.md) (the stored runs and trades; the reader pattern), [0044](0044-the-cost-choice-the-stored-charge-sheet-the-cost-sheet-verbs-and-the-bill-check.md) (the stored charge sheet; ISS-25), [0053](0053-the-same-entries-comparison-and-the-mae-mfe-diagnostics.md) (the comparison that gives a run its exit), [0083](0083-no-order-is-placed-before-phase-12-an-architecture-tripwire.md) (nothing here touches an order).

## Context
P8-05 built the report engine as a pure core; nothing could reach it. The exit of P8 ("what works, in which basket, on which timeframe, with which exit") needs the stored simulation runs readable over HTTP, with the honest rules of the engine intact: no number for a non-value, no trade counted twice, no report called net on anyone's say-so. The plan (P8-00, risk 2) asked for a spike first, because exit and style are not trade columns, the fill of `basket_ids` was unverified and the size of the trade table was unknown.

## Decision
1. **Where the facts live (the spike, [P8-06](../specs/P8-06-report-read-endpoints.md)).** Trades, windows, the costed flag and the closed or open state are columns of the result store. **Style** is that of the stored strategy (`lab.strategies.style`). **Exit** is the candidate id of the stored comparison the run belongs to, and is *not recorded* for any other run and for a run in comparisons that disagree. The **basket** is on the trade (none for a list of instruments, the one basket for a basket run; the column is an array, so several are storable), and the first stored trade of a basket run names the universe of the run. The sources are printed with the labels (`stored strategy`, `stored comparison <key>`).
2. **A port, a streamed projection.** `IReportTradeSource` (Application/Abstractions/Reporting) lists the runs and streams the closed trades of chosen runs; the Infrastructure implementation reads 13 columns with a plain reader (no change tracker), the filters (strategy, timeframe, side, symbol, basket, dates) as statement parameters, and interns the repeated strings. It lives in `Infrastructure/Research` because only that namespace may name the result tables (ADR 0045); the architecture rule that keeps the adapters of that namespace honest names it. It only reads.
3. **One query model.** `ReportQuery` (lens, filters, metric, run set, basis, page) is parsed from the query string against whitelists; every unknown name, bad run key, date, limit or cursor is 422 `reports.invalid`, all problems together, a rejected value echoed cut short and without control characters. The same query serves all nine endpoints (`/runs` takes none): `/summary`, `/groups`, `/pivot` (a lens of exactly two dimensions), `/equity`, `/distribution`, `/insights`, `/what-works` (added to the plan's list because the exit question needs it and the engine has it) and `/trades`. The URL is the view.
4. **The run set is explicit or the default.** Named runs must exist (404 `reports.not_found`). Otherwise: for each strategy and universe the newest run, among the runs costed the way the newest run of all is, so gross and net never mix; every run left out is listed with the reason, and the evidence says the set was the default. The engine's refusals pass through with their codes: 409 `reports.run_overlap` and `reports.mixed_basis`, 422 `reports.double_count`, `reports.dimension_unavailable` (regime, account).
5. **Evidence and the six states on the wire.** Every answer carries `ReportEvidenceView`: basis, n, dates, the runs used with their facts (the Data used panel), the limits (the engine's and this slice's: closed trades only, how many open trades were left out, where style and exit come from, what a basket run carries), the unavailable inputs, duplicates dropped, and what the owner confirmed for a net report. A figure is a `MetricView` (state, a number only for value and provisional, the reason). A thin group has no equity points and no distribution bins; a pivot gap is `empty`; the empty store gives `empty` everywhere and reads no trade. "Nothing has enough evidence yet" is a 200.
6. **Net by the stored confirmation only (SAFETY).** `ChargeSheetConfirmation` has exactly one source: `IChargeSheetConfirmationSource`, which reads the settings row `reports.charge_sheet_confirmation` (`{"sheet_id","confirmed_on"}`) and returns it only when the row parses and names a *stored* cost sheet; anything else is "not confirmed". `basis=net` is a request that the loader allows only with that value *and* only over runs costed with that very sheet (else 422 `reports.net_unavailable`); without it the answer is 422 `reports.net_not_confirmed` with the reason, and `/runs` says net is `unavailable` with the reason. No query parameter, header or body is read for it: `ReportQueryParams` has no such field, and architecture tests fail if any request, query, command, body, input, filter or params type of Application, Infrastructure or Api carries a confirmation or a flag named for one, if the Api names the confirmation type or its source at all, or if any Application type but the loader and the runs list reads the source. The integration test sends `confirmed=true`, `chargeSheetConfirmed=true`, `sheet_id=...` and two confirmation headers with `basis=net`: 422. **Nothing in this slice writes the confirmation**; the owner's act of confirming the sheet (a verb in the pattern of `cost-sheet`, with the owner's own decision) is a separate slice. Until then every report is gross.
7. **Read only.** The module maps GET and nothing else; no command handler, no write SQL (architecture tests read the sources); session-protected; no export, no job, no order-named member (the tripwire stays green).
8. **Answers are bounded, never cut.** Over 2,000 groups, 10,000 pivot cells, 200 distributions, 40 curves or 2,000 "what works" cells the answer is refused (422 `reports.invalid`) with the count and what to do; the trade list pages at most 1,000 trades. A cut answer would read as the whole.
9. **The engine gained what the endpoints need**, pure and tested by hand tables and a seeded property: the equity and drawdown series (one point per exit date, none for a thin group), the R distribution (bins of half an R from -4 to 6 with open ends), a slice of the trades in the order of the exits, and a faster population build (one array sort per order instead of two LINQ sorts, no string per trade in the signal check, one pass for the evidence), which took the population rule on 500,000 trades from about 700 ms to about 380 ms without changing a result (all 2,963 domain tests unchanged).
10. **Log events** 4800 `reports.loaded` (kind, runs, trades, basis, ms) and 4801 `reports.refused` (kind, code): no trade, symbol, strategy or figure.

## Measured (the plan's UNVERIFIED target of 1 s p95)
One synthetic gross run of **500,000 closed trades** (1,250 instruments, a buy and a sell on each of 200 days: `StoredRunFixtures.Synthetic`), stored in a scratch database on the local TimescaleDB container (Podman, same machine as the test process), the machine otherwise idle. Each sample is the use case plus the JSON of its answer, in a scope of its own like a request, 20 samples after one warm-up; **the HTTP hop, the session check and a network are not in it**. Measured 2026-10-24 by `ReportsPerformanceTests` (explicit: `-explicit only`, `XD_REPORT_SAMPLES=20`).

**The target of 1 s p95 (UNVERIFIED in the plan) is not reliably met on a run of 500,000 trades.** Eight of the nine reports sit at 0.95 to 1.02 s p95 (four at or under 1 s, four a few percent over), the pivot of two wide dimensions is 1.4 s, and the managed memory after a run is about 530 MiB (each request holds the whole population). Where the time goes (three rounds on the same run): listing the runs 25 ms; streaming and building 500,000 trade records 450 to 700 ms (the first round is the cold one); the population rule 370 ms (it was 700 to 1,000 ms before the sort and the signal check were rewritten, see decision 9); one grouping 25 to 55 ms; the JSON of the answer is small. A first measurement taken while other work ran on the same machine gave p95 up to 1.9 s, so the figures vary with load. The cost grows with the number of trades read; it was not measured at other sizes (the 20,000-trade run of the always-on test is checked for its figures, not its time). On the owner's real data the size is unknown: the database was not queried. **Nothing was hidden to reach these figures; no cache was added.** If the screens need under a second on a run this large, the follow-up is a stored pre-aggregation (per run and group, insert-only), a separate decision.

## Consequences
- The exit question can be asked of the stored research over HTTP, and the likely answer on this data (nothing has enough evidence yet) is an ordinary 200.
- Every report reads the whole population of its runs into memory and groups it; there is no stored pre-aggregation. That is simple and exact, and the cost is the figures above, growing linearly with the trades. **If the owner's data or the screens need it faster, a stored pre-aggregation (per run and group, insert-only, in the pattern of the cell snapshots) is the named follow-up; it is a separate decision, not part of this slice.** The owner's real size is not yet known (not queried).
- Two basket runs of one strategy over baskets that share an instrument hold the same signal (P8-05's rule) and cannot be added together; the screens will have to say so and offer the runs one at a time. Two explicit lists of instruments of the same size and label are not told apart (the header does not keep the members) and can be refused as one universe.
- The style and exit labels exist only where a stored strategy or a stored comparison gives them; most real runs will show `not recorded` for the exit, and "which exit" will be answerable only over compared runs.
- The `reports.charge_sheet_confirmation` row does not exist on the owner's database; net stays unavailable until the owner's act is built.

## Alternatives considered
- **A confirmation flag or sheet id in the query ("net=confirmed").** Rejected: it lets a caller make a report net by saying so.
- **Write the confirmation in this slice (a verb or an endpoint).** Rejected: a write, an owner decision (SAFETY), and the slice is read only.
- **Cache the loaded populations.** Rejected here: hundreds of megabytes held in memory for a single-owner tool, and a stale-data question the immutable store does not need.
- **Group in SQL.** Rejected: the engine owns the rules (population, shrinkage, states); a second implementation in SQL would drift. A stored pre-aggregation is the right place for speed.
- **Cut an oversized answer to the cap.** Rejected: silent truncation reads as completeness.
- **A separate endpoint per lens, or a POST body for the query.** Rejected: one GET model keeps the URL the view (Back works, a link reproduces it) and keeps the read path free of any body.
