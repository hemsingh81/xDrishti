# 0162 - Reconciliation only makes the system stricter: the poll is the truth, the stream is the speed, and nothing here can send or open a socket

- **Status:** Accepted (decided in P12-06 under the owner's standing run instruction; spec [P12-06](../specs/P12-06-order-update-stream-and-reconciliation.md)).
- **Date:** 2026-10-30.
- **Relation to other ADRs:** builds on ADR 0155 to 0161 (the `Leg` rank rule, `LegLookup`, `IBrokerReads`, the alarms, `HaltService`, the insert-only pattern and the owner-act pattern of the halt release are used as they were); follows ADR 0025 and ISS-01 (the trade history API is a second witness only). The xd-api allow-list and `Infrastructure/Brokers/BrokerEndpoints*` are not touched; no other project references Execution; `deploy/` is untouched; no call to Dhan was made and no socket was opened.

## Context
After a crash, or while the broker and we disagree, the question is whether our picture of the money is true. The owner's limits stand: nothing may become able to send, live is refused everywhere, an unreadable input never counts as agreement, and the layer that finds a disagreement may only make the system stricter and never repair a number to make it fit.

## Decision
1. **The poll is the truth, the stream is the speed.** Dhan documents the order-update socket, its login and fields, but no heartbeat, no replay of missed messages and a malformed sample. So the leg state and protection come from the poll (order book, trade book, positions while exposed) at 5 s busy and 30 s idle; the stream only makes it faster. `streams_alive` is true only while the last good poll is at most 15 s old and no gap fill is owed (after every connect and at the start one poll must complete first); the stream alone never makes it true. A poll the broker could not answer is not a poll.
2. **No socket exists in this slice.** The client (`OrderUpdateFeed`) runs over `IOrderUpdateTransport`; only an in-process fake exists, and a source scan pins that the project names no WebSocket or TCP client. `StreamEndpoint.Resolve` never names or returns the documented live host: for sandbox it returns an address only when the configured host is exactly the pinned sandbox host of `ExecutionEndpoints` (no port, user, path, trailing dot or look-alike); live and none get nothing. Dhan documents no sandbox socket, so by default the stream does not run.
3. **A tolerant reader, never a guess.** The parser reads `"name": value` pairs wherever they stand (the sample is not valid JSON), names case-insensitively, first non-empty value wins, unknown names ignored. An unknown status, product, side, order type or leg number, an impossible quantity or garbage is `Unreadable`: dropped, counted, and a poll is asked for. Only the mapped fields leave the parser (no remarks, no client id, no token). The login message is built exactly as documented and carries the token nowhere else.
4. **Apply once, never backwards.** An update is applied once per (order, status, traded quantity, time); the rank rule is the domain `Leg.Apply` (a lower status or any change after a final one is counted and ignored; the filled quantity never decreases). 2,000 seeds of duplicated, delayed and reordered updates give the in-order result; a version without rank is caught on far more than 10. Our prefix with no leg is reported for the reconciliation, never invented.
5. **Two fill sources, one authoritative.** The stream's cumulative quantity and average price drive the leg and protection at once (provisional); the trade book's rows with their exchange trade id become the `fills` rows within a poll (`IFillWriter`, idempotent by trade id); the reconciliation compares the two.
6. **The comparison is a pure function.** `Reconciler.Compare` reads its input and returns breaks; it has no way to correct anything (our side is a read-only port with two methods, and a test hashes our books and the event log before and after a run with breaks). Order status class and quantities (grace `exec.recon_grace_s`), broker orders with our prefix against legs (stop and target legs of our super order matched by parent, leg number and recorded order id before anything is unknown), trades against fills by exchange trade id (quantity exact, price to four decimals; a missing one is a break at its second sighting), the sum of a leg's fills against its cumulative quantity, positions in the instruments we manage against our book plus the explained foreign trades. A foreign working order in a managed instrument is a conflict; a foreign trade explains a position. A trade of our order without an exchange trade id is `unavailable`. A break's key holds the broker's figure, so an accepted break stays quiet only while the figure is the same.
7. **Freeze, do not fix.** `BreakService` stores the run and its new breaks (one row per open key; the run counts repeats) and asks for a freeze of that account only, on every run with a break so a lost request is made again; the halt record does not stack it. A foreign conflict asks for `entries` through a new halt trigger `foreign_conflict` (owner release) and raises a critical alarm; it could not go through `reconciliation_break` because the halt service raises a request to its trigger's level. An unreadable broker, an unreadable record, unreadable settings or an exhausted read budget is an `unavailable` break: the run is never clean (a check constraint refuses an unreadable run with no break). Only a clean, readable end-of-day or final run moves closed intents to reconciled. Alarm codes `recovery_slow`, `journal_gap`, `foreign_conflict` are added.
8. **Resolution is the owner's, by append.** The owner's row is written by `xd_app` (its only INSERT on these tables), after `Live:Writes:Enabled` and a fresh password, with the actor from the session; the trigger `check_break_resolution` checks the break exists, is unresolved and that `dismiss_foreign` is for a foreign conflict only; `xd_exec` has SELECT only. For `accept_broker` on an intent-linked break the engine (`BreakAdoption`, idempotent) appends one owner event naming the break; legs, fills and positions are not rewritten and the break stays in the history. The freeze is released through the existing halt release only when its trigger is `reconciliation_break`, the account has at least one break and every break has a resolution (the trigger `check_halt_release` and `HaltReleaseRules` agree); a freeze of any other cause stays unreleasable here. The trigger reads the breaks without a lock (rows are insert-only, so a lock on existing rows cannot keep out a new one): a break inserted at the very moment of a release is not seen by it. This is contained because `BreakService` records the break before asking for a freeze and asks again on every run that finds a break, so a release that raced a new break is followed by a new freeze. The audit is a log line with ids and codes and no free text.
9. **Recovery reads before it writes.** The host starts `recovering`. `RecoveryService` has a lookup, the read-only reads and the reconciliation, and no sender (a reflection test pins the constructors; every test broker logs its writes and recovery makes none, over 500 seeds of crash points at the four points of the send protocol in the states open, filled, protected and closing). It looks unknown legs up twice, 2 s apart, but writes what it found only after the order book, trade book, positions and funds have all been read; an unreadable broker changes no leg and keeps the host recovering, with the alarm after 120 s. An account with no break and no unknown leg is ready, one with a break is frozen, and the host leaves `recovering` only when every account is one or the other. This is stricter than the written order of steps 3 and 4.
10. **The real protection snapshot exists and is not wired.** `PollProtectionSource` builds the P12-04 snapshot from the last poll, our open intents and the halts, and answers null (never an empty snapshot) when the streams are not alive, no poll has completed or a record cannot be read. `IProtectionSource` stays the closed default.
11. **Settings and composition.** Six numeric settings (`exec.poll_busy_s` 5, `exec.poll_idle_s` 30, `exec.recon_interval_s` 60, `exec.recon_grace_s` 30, `exec.stream_backoff_max_s` 30, `exec.recovery_max_s` 60), none enabling anything, out-of-range values make the run unavailable. Only the three Pg classes are registered in the record composition; the services, the feed and the protection source are composed by no host (tests over the service provider and the source text), `IBrokerOrders` stays registered nowhere, `IHaltSource` and `IExitSendPolicy` stay closed.
12. **Not built, owed.** The real WebSocket transport and stream loop; the schedulers (poll, continuous, 15:45 eod, 16:30 final) and host composition; `GET /api/execution/stream` (the status lives in the memory of `xd-exec`; it moves to P12-10 with the screen; `StreamStatusView` exists); a database writer for leg adoption in recovery; the stored-trades source for `journal_gap` (`xd_exec` has no portfolio grant; the check is pure and the alarm exists); `legDetails` flattening in `DhanReads` (the matching rule exists); `buyQty`/`sellQty`/`productType` in the position comparison; LISTEN. Shortcuts: the open-key de-dup is read-then-insert (one writer assumed; the effect of two would be a duplicate row, never a missed break); the last-session choice of `PgReconOurSource` is the account's latest intent date.

## Consequences
Nothing new can send or open a connection, and every disagreement found makes the system stricter and waits for the owner. The costs are false freezes (a lagging trade book can freeze a session; better than a missed one) and an owner who must resolve each break by hand, with the password, behind the live-writes gate. Everything about the stream and the trade-book fields stays UNVERIFIED until a sandbox or live canary compares real messages with the parser.
