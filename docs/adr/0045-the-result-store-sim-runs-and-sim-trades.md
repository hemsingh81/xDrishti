# 0045 — The result store: `research.sim_runs` and `research.sim_trades`

- **Status:** Accepted (owner, 2026-10-19: "All six, recommended answers" on [P3-10](../specs/P3-10-the-result-store-sim-runs-and-sim-trades.md): opt-in `--store`, typed trade columns, plain tables now, keep every run and delete by hand, the record and not the labels, no reader of the whole record yet).
- **Relation to other ADRs:** completes [ADR 0037](0037-simulation-conventions-and-the-two-stage-seam.md) Amendment 2 ("the Lab will store it"; Amendment 9 records the decision), builds on [ADR 0039](0039-an-engine-module-is-reached-from-an-adapter-in-infrastructure-never-from-application.md) (a port and an adapter), [ADR 0041](0041-the-simulate-verb-the-export-library-and-the-pipeline-in-the-host.md) (the export library, the verb, "files stay the audit copy") and [ADR 0044](0044-the-cost-choice-the-stored-charge-sheet-the-cost-sheet-verbs-and-the-bill-check.md) (a `test-` sheet is never stored). Amends none.
- **Date:** 2026-10-19 (built the same day; migration `AddResearchResultStore`, no API change).

## In short
- **A finished run can be kept exactly as it was and read back.** `scripts/simulate.sh … --store` writes the export files first and then stores the run: one row in `research.sim_runs` (the facts a query filters by as typed columns, the whole record without its trades as canonical text) and one row per trade in `research.sim_trades` (every field of `SimTrade` as a typed column, the baskets as `uuid[]`), in one transaction.
- **The run key is the idempotency key.** The same run again is a no-op (`already stored`); another record under a stored key is `store.run_conflict`, logged at error as a corruption signal, nothing written, exit 3.
- **Insert-only for the runtime role.** `xd_app` can read and insert; it can neither update nor delete a stored result, and it cannot create objects. A stored run is removed by the owner as `xd_owner`.

## Decisions
1. **D1 — header as columns plus the canonical text; trades normalised.** `sim_runs` has the filterable facts as columns and `record_json` (type `text`, not `jsonb`: jsonb keeps neither key order nor number spelling, so the hash of what was written could no longer be checked) with `record_sha256`. `sim_trades` has one row per trade of both lists (`open_at_end` is a column and part of the key, so statistics can leave the open trades out), every field a column: the trigger bar flattened, the six enums by lower-case name with a `CHECK` on the closed set, the costing flattened into 24 nullable columns that are all null or all present (a generated `CHECK`, and `costs = 'charged'` if and only if `cost_quantity` is present), `numeric` without a scale for money, `double precision` for prices and R. The sheet id of a costing is the run's `costs_sheet_id` and is put back on read. 61 mapped columns and four keys: the 65 of the spec.
2. **D2 — keys and indexes.** `sim_runs`: identity `id`, unique `run_key char(64)` with a hex `CHECK`, and `ix_sim_runs_strategy_created (strategy_id, created_at DESC)`. `sim_trades`: primary key `(run_id, open_at_end, ordinal)` (the record's order), unique `(run_id, trade_key)` (the join of P4's same-entries comparison), foreign key to `sim_runs` without cascade. No other index until a measured query needs one.
3. **D3 — plain tables, no hypertable, no compression.** Measured (see *Consequences*): a 200,000-trade costed run is 110.6 MiB of table and 21.9 MiB of indexes. **Trigger to revisit:** `pg_total_relation_size('research.sim_trades')` above 2 GB or any measured query slower than a second; then one migration makes it a hypertable on `trade_date` (primary key extended by the time column) with compression by `run_id`; the row model and the port do not change.
4. **D4 — the write.** One transaction on one connection: `INSERT … ON CONFLICT (run_key) DO NOTHING RETURNING id`; if a row comes back, a binary `COPY` of the trades in record order from the lists the record holds, then `SELECT count(*)` equal to the trades of the run, else rollback with `store.write_failed`, then commit. A key that is taken is compared (record digest, trades digest, both counts, engine version, schema versions): equal is `AlreadyStored`, anything else `store.run_conflict`. Two concurrent stores of one key give one `Stored` and one `AlreadyStored`. Cancellation rolls back.
5. **D5 — the digests come from the in-memory run.** The verb makes the canonical record text with `SimExportJson.WriteRecord` (the run object of `run.json` without `trades` and `open_at_end`, the same converters, the same bytes) and the trades digest as `SHA-256(sha256(trades.csv) ":" sha256(open_at_end.csv))` over the hashes the folder writer took of the very bytes it rendered, never from files read back. The handler recomputes the SHA-256 of the record text before the write; the adapter compares the trades digest and never serialises. The export library stays Api-only.
6. **D6 — validation before the database** (`store.run_invalid`, a field error each, at most 20): a null run; a run key that is not 64 lower-case hex; record schema other than 5 or a trade schema other than 4; a record text whose hash is not the digest given; lists that hold more trades than the record counted in the window; two trades with one key; a costed trade in a gross run, a gross trade in a costed run, a costing with another sheet id than the run's; and **a run costed by a `test-` sheet** (a synthetic sheet is never stored).
7. **D7 — privileges.** `GrantSchemaUsageToAppRole("research")`, then `MakeAppendOnlyForAppRole` for each of the two tables (the order the helpers document). **Standing rule for later research migrations:** the other research tables of doc 03 §5 are not all insert-only, so a later migration either grants per table (`GrantTableToAppRole`) or, if it re-grants the schema, calls `MakeAppendOnlyForAppRole` again for these two; a standing test (`ResearchGrantsTests`, on a dedicated throw-away server where the role `xd_app` exists) checks every table of the schema and fails if it is forgotten.
8. **D8 — retention.** Keep every stored run; nothing expires. Removal is the owner's, as `xd_owner` (doc 17 gives the order: trades first, then the header). A `SECURITY DEFINER` function is the later slice if removal becomes routine.
9. **D9 — reversibility.** `Down` drops `sim_trades`, `sim_runs` and then `DROP SCHEMA research` without `CASCADE`: with another object in the schema it fails and, the migration being one transaction, removes nothing. `Down` destroys stored runs; every run can be re-run from the stored bars and its key says whether the result is the same.
10. **D10 — events 4415 to 4418** (`store.started`, `store.completed`, `store.conflict` at error, `store.failed` at error): the run key's first 12 characters, counts, figure names, codes and milliseconds; never a trade, the record text, the definition or a sheet.

## Decided in the build
- **The model of `sim_trades` is declared from the one column list** (`TradeColumns`): `SimTradeRow` carries the four keys as properties and the 61 mapped columns are shadow properties generated from that list, so the model, the migration, the copy, the reads and the generated checks cannot drift. A test compares the list with the properties of `SimTrade`, `Bar`, `TradeCosting` and `LegCharges`.
- **The count check of the validation** compares the lists with the record's `TradesInWindow` (which includes the open-at-end trades) rather than with `Fates.Trades`, which cost-skipped trades could make unequal to the list in a costed run (UNVERIFIED for the engine; the weaker check cannot refuse a real run).
- **`SimExportJson.WriteRecord`** takes the converters of `Write` and drops the two members by a type-info modifier on the same generated serialiser, so a member added to the record is written by both.
- **Two architecture rules were extended, not relaxed:** the list of the research port gained `IRunStore` and its values, and the "adapter does no I/O" rule of the research namespace excludes the result store's adapter types, which `ResultStoreArchitectureTests` pins (with sentinels).

## Consequences
- **Measured on the test container** (200,000 costed trades, `RunStoreSizeTests`): the transaction took 3.5 s (57,000 rows a second, copy 3.4 s); `sim_trades` is 110.6 MiB (580 bytes a trade) plus 21.9 MiB of indexes (primary key 6.0 MiB, unique trade key 15.8 MiB), 132.4 MiB in all, within a factor of 1.5 of the 120 MB and 20 MB estimated; a filtered page of 1,000 rows took 53 ms; the whole stream ran at 67,800 rows a second, below the 100,000 the spec hoped for (a loose bound, not a gate).
- **Handed on.** The join of P4, the screens and filters of P5, the aggregates of P7, the reader of the whole record from its text and a delete function; the owner's disk headroom for about 20 large runs (about 3 GB, UNVERIFIED on his machine).
- **Until the migration is applied** (`deploy/xd-up.sh` runs `xd-migrate`), `simulate --store` exits 3 and names the migration `AddResearchResultStore`; the export files are kept.

## Alternatives considered
- **One `jsonb` document per run or per trade.** Not queryable by trade, too large to parse for a page, and jsonb loses the spelling the hash needs.
- **A hypertable now.** The unique key must contain the time column, a run spreads over every chunk its years touch, and the extension's behaviour for inserts into compressed chunks at this version is unverified; it pays only past a few gigabytes.
- **Granting `DELETE`.** App code must not be able to alter or remove a stored result.
- **Storing the labels.** They are derived from the record and the engine's verification state at export time; storing them would freeze `engine not verified` on a run P3-08 later verifies.
