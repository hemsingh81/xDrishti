# 0219 — A firing kill rule writes a proposal and a notice; the owner, or an automatic setting that is OFF by default, pauses the cells; only the owner with a fresh password ever re-enables

- **Status:** Proposed (built in CF-12 part 12b from the owner-Approved spec, 2026-11-03). Becomes Accepted when the owner has read it. **Safety slice: yes** (it is the first state change of the confidence programme: an automatic demotion path behind a setting, and the only door that raises a paused cell's risk again). Demotion lowers risk; re-enable raises it and is never automatic. No order is placed or touched anywhere in this part.
- **Date:** 2026-11-06.
- **Relation to other ADRs:** completes the safety half of CF-12 after [0218](0218-the-decay-monitor-the-kill-rule-evaluations-and-the-loop-report-are-read-only-evidence-with-every-input-that-has-no-source-yet-unavailable-and-no-consumer.md) (the read-only evidence, whose calculators this part uses unchanged); uses the lifecycle of [0073](0073-the-learning-changelog-and-the-cell-lifecycle-the-log-is-the-state.md) (P6-08) and the owner-act mechanism of [0212](0212-the-shadow-record-is-graded-after-the-close-through-the-one-replay-path-summarised-as-raw-and-effective-n-labelled-gross-unless-the-sheet-is-confirmed-and-switched-by-the-owner-with-a-fresh-password.md) (a fresh password per change, the actor from the session, a switch stored append-only with its id in commit order); follows the architecture-pin pattern of [0217](0217-a-model-may-influence-a-decision-only-through-one-gate-whose-predicate-needs-an-unspent-hold-out-forward-evidence-no-calibration-alarm-and-the-owners-switch.md) (scans with sentinels). The CF-09 failure boundary is the proposal-only input of [0213](0213-the-paper-edge-series-gets-a-sequential-failure-test-that-flags-a-probable-failure-early-with-the-odds-stated-and-never-passes-anything.md).

## OWNER QUESTION FIRST: the lifecycle gains an eighth legal move, Paper to Paused (edits P6-08)
The P6-08 table (doc 09 section 7, ADR 0073) had seven moves, and its only way into `Paused` was `Active -> Paused`. Nothing is `Active` until live exists (P7+), so a kill rule could pause no cell at all. The spec asks for "all cells of the strategy move `Paper/Active -> Paused`", so this part adds **`Paper -> Paused`**: it needs no fact (it lowers risk) and, like every move but the owner's approval of a candidate, one evidence id. `Paused -> Paper` is unchanged (it needs the claimed fact `Recovered`). **Re-enable never goes to Active**: Paper to Active still needs the paper days, the band and the owner. The change is in `CellLifecycle` (pinned by its test, now eight moves and seven that need evidence), the state diagram of doc 09 and a test that a Paper cell can be paused and that the pause can be reverted. **Do you accept the eighth move?** If not, the kill rules can still be proposed but nothing could execute them until a cell is Active.

## Context
The spec (D2, D3, AC5, AC6) asks that a failing strategy can be stopped, manually or, if the owner chooses, automatically; that re-enabling is an owner act with a fresh password and never automatic; and that the CF-09 failure boundary may only ever create a proposal. The approvals rule of the project adds that anything with manual approval must also be able to run automatically behind a setting that is OFF by default, that the automatic decision is recorded as automatic (never as an owner approval) with the setting snapshot, and that an input that is `unavailable` never counts as a pass.

## Decision
1. **A firing rule writes a proposal and a notice (`ProposeKillHandler`).** For one strategy and one India day it reads the decay report (the same verdicts as `GET /api/confidence/decay`, so the proposal and the read agree) and writes one row of `confidence.kill_proposals` for every rule that **fires** (`KillDecision.MakesProposal`: a rule that is not evaluated, held or holding never does), with the rule, its figure and limit, the trades, the words with the numbers, the Paper or Active cells it would pause, the SHA-256 of the decay and kill settings and the length of the series. Not written: a second proposal for a rule that already has an open one, a proposal when no cell is Paper or Active, and anything when the strategy was already evaluated today (`confidence.decay_checks`, one insert-only evaluation per strategy and day with the four verdicts, written after the proposals so that a failure leaves nothing recorded and the next run repeats it). A unique key on (strategy, rule, day) makes the insert idempotent in the database too. The bell notice is **derived on read** from the open proposals, and from the proposals the automatic setting applied in the last three days (a resolved notice, so an automatic pause is never silent), the P8-15 way: `IBellNoticeSource` is a neutral port in `Abstractions.Planning`, `GetPlanNoticesHandler` merges every source, and `KillProposalNotices` is the one source; Planning names no kill type. The wait of review fix 3 is now enforceable: a proposal records the length of the series when it fired, and the decay report reads the newest proposal of the rule in the same epoch to give `held` until 20 new trades.
2. **Applying (`ApplyKillHandler`): demote first, then compare-and-set.** The actor is `owner:...` (the signed-in owner, the endpoint builds it from the session, no password: the safe direction) or `auto`. For each cell the proposal names that is still Paper or Active the handler asks `PauseCellCommand` (a changelog row with the rule, the numbers, the settings hash and the evidence id `kill-proposal:N`); a cell already Paused is skipped, so a repeat or a concurrent call writes no second row; a pause that fails for another reason stops the call and leaves the proposal `proposed`, so a retry pauses the rest. Then **one conditional update** moves the proposal `proposed -> applied` (actor, decided time, the switch row); the call that loses it returns the stored outcome (`alreadyApplied`). An applied proposal applied again is a no-op, a dismissed one is 409 `confidence.proposal_closed`.
3. **The automatic path (`confidence.kill.auto`, default OFF, no row means OFF).** The owner changes it only through `PUT /api/confidence/kill-settings`: a session, the CSRF token and **a fresh password on every change, ON and OFF alike** (the shadow switch's mechanism; the step-up window is neither opened nor used up). A body without a password is **403 `auth.step_up_required`** (nothing is checked or counted), a wrong one is the sign-in 401 or 423 with its lockout. The switch is `confidence.kill_settings` (append-only; the id is drawn after an advisory lock so the highest id is the last to commit, the pattern of `paper.shadow_settings`), not a configuration value (`Confidence:Kill` has no such key). When it is ON the same daily run applies the open proposals as actor **`auto`**: the changelog row carries `auto`, `BeforeRef = kill-switch:{row}`, the settings hash and the reason with the rule and numbers; the proposal records `auto` and the switch row. It is never recorded as an owner. **The CF-09 failure boundary is `ProposalOnly`: the handler refuses it for `auto` (403 `confidence.proposal_only`), the daily run never offers it, and the database refuses to record it as decided by `auto`**. That last guard is about the **proposal record only**: a check that `auto` never decides a proposal-only rule or a dismissal, and a trigger that an automatic decision needs the newest switch row to be ON and to be the one recorded. It does not stop a cell from being paused: the pause is a changelog row, which the database cannot tie to the switch, so the handler's own checks are what keep `auto` off the boundary. When the record refuses a decision (the switch was turned OFF between the check and the update) the store answers `Refused` and the handler returns 409 `confidence.decision_refused` instead of throwing; the cells it had already paused stay paused, which is the safe direction, and the proposal stays open. Also: the runtime role can insert only an open proposal (INSERT is granted on the proposal's own columns, never on state, actor, decided time or the switch row), and the automatic run applies only the open proposals that were made today or whose rule still fires in today's report (an older proposal whose rule no longer fires stays for the owner); an apply that fails or throws is counted, logged and tried again by the next run (the same day's re-run applies the proposals of today), and one strategy that throws does not stop the others. The owner can apply that proposal by hand.
4. **Re-enabling (`ReEnableCellHandler`) is only ever the owner's.** `POST /api/learning/cells/{key}/re-enable` (the key is the URL-encoded cell key): a session, the CSRF token and a fresh password in the body (403/401 as above). `Paused -> Paper` only, recorded by the lifecycle's own recorder with the facts the owner states (owner approved, recovered); the actor is the session. It refuses a non-owner actor (`auto` among them), a cell that is not Paused (409 `confidence.cell_not_paused`), a bad key (422) and a missing reason. When a kill proposal paused the cell (found from the evidence of the pause that put the cell where it is, followed back through revert rows to the one first made; if the evidence names a proposal that cannot be read back, the answer is the same 409 and never a pass) the strategy's kill rules are evaluated again and **every rule that fired must `hold` now and no rule may fire or be held; a rule that cannot be evaluated, or a report that cannot be read, is not a pass: 409 `confidence.rule_not_cleared`** (the spec calls this problem `confidence.rule_cleared`; it is returned when the condition is NOT cleared, so it is named to read as what it says). A pause that no kill proposal made has no condition to clear, and says so. The CF-11 gates R and S are not built, so **every answer carries a visible warning that they were not checked**, never a silent pass. A revert is a correction, not a lifecycle move, and `RevertChangelogHandler` now refuses a row whose evidence names a kill proposal, so the pause is lifted only by this act. **The lifecycle recorder itself refuses `Paused -> Paper` for such a pause** unless the command carries `OwnerReEnable`, which is an `init` property (not a constructor argument) that only `ReEnableCellHandler` sets: an architecture test reads the IL of every production assembly and asserts that the only caller of `set_OwnerReEnable`, whether by an object initializer or a `with` expression, is that handler, with a sentinel of each form as a positive control: the owner's CLI verb `xd learn lifecycle --to paper` is refused for a kill pause with a message that points to the re-enable act, and still works for a pause that no kill proposal made (the origin of the pause is followed back through revert rows, so a restored pause is still a kill pause). This keeps the spec's D3 meaning: re-enable of a kill pause is only through the owner act with a fresh password.
5. **`PauseCellCommand` is the one door of the automatic path to the lifecycle.** It carries no target state and no fact; `PauseCellHandler` builds `RecordCellTransitionCommand` with `CellState.Paused` and is the only automatic caller of it. Everything else that moves a cell is out of reach of the automatic path.
6. **The service `decay-monitor`** (`DecayMonitorService`, daily 18:00, must follow `shadow-grade`, starts paused, registered with the other scheduled services and run by the API host that runs them all). `EvaluateDecayHandler` lists the strategies that have a shadow edge candidate in the current paper epoch, asks `ProposeKillCommand` for each, and reports the counts; one failing strategy does not stop the others and records nothing for itself. **Deviation from the first reading, no epoch:** with no paper epoch yet the run does not stop; the epoch is null, exactly as the decay report reads it, so the shadow rows that carry no epoch (written before the first epoch) are the series that is evaluated, and the rows of an epoch are not. (The first draft returned early without an epoch, which left a series the report can read unmonitored.) It reads shadow outcomes only through the one reader, like the other display use cases (the pin of the shadow architecture test lists it).
7. **Settings `Confidence:Kill`** (`StressMultiplier` 1.5, `DrawdownFactor` 2): bound and range-validated at start. Demotion lowers risk, so a value that makes a rule fire sooner is the safe direction, and **only those are claimed to be tighten-only, in both directions**: the multiplier may only go up (1.5 to 3) and the factor only down (1 to 2); a value outside them stops the host (tests refuse 1.49, 3.01, 2.01, 0.99, 0 and NaN). The trailing 100 trades and the 20 new trades between firings are **fixed**, not settings, because a different number is a trade-off in either direction and not a tightening (fewer trades judge on thinner evidence, more judge later). `KillRules.CostStress` takes the multiplier as an argument (default 1.5) and the decay report passes the setting.
8. **Enforcement (`KillArchitectureTests`, each scan with a sentinel it must catch).** (a) The **closure of everything the automatic path can reach** (the service, the run, the proposal and apply handlers, found from the IL: what the code names and, for a named contract of the solution, every class that implements it) does not contain the re-enable, a revert, the CLI verb or any other changelog writer; the only type in it that builds the lifecycle command is `PauseCellHandler`, and the only one that appends to the changelog is the lifecycle's recorder; the source of `PauseCellHandler` names `CellState.Paused` and no other state. Sentinels: a type holding the re-enable contract reaches the handler; a type that builds the command and appends reaches both detectors. (b) Who may name the re-enable is pinned (its handler, its route, the registration and the JSON context); the switch has one writer (the owner's handler), the proposals two (propose and apply), each contract has one implementation, in Infrastructure. (c) Planning, Selection and Autonomy (Domain and Application) name no kill type, port, setting or proposal (a sentinel that reads a proposal is caught); the bell reaches the notices only through the neutral port. (d) None of the kill types depends on the execution plane, live trading, accounts or autonomy. (e) The routes are the pinned few; the two acts that raise or allow risk use the fresh-password step and the apply route uses the session's owner. The 12a assertions that 12b legitimately changes were rewritten (the consumers are the ones named; the endpoint file of 12a stays GET only), and the `OwnerMoves` pin of `RevertChangelogHandler` was updated here (this is the ADR it asks for).
9. **Storage (`AddDecayAndKill`).** Schema `confidence`: `kill_settings` (append-only), `decay_checks` (append-only), `kill_proposals` (insert, plus a column grant of `state`, `actor`, `decided_at`, `auto_setting_id` and a trigger that allows one move from `proposed`); the runtime role has no DELETE or TRUNCATE anywhere. Raw SQL, no EF entity, so the model snapshot does not change; Down drops the schema only. Tests: up and down on a scratch database, the grants, every refusal listed above on the real role.

## What the owner sees
`GET /api/confidence/kill-proposals` lists the proposals (rule, numbers, cells, state, actor) with the setting (OFF by default) and the thresholds beside them; the bell shows an open proposal; nothing is paused until the owner applies it or switches the automatic setting ON. The Learning screen tabs and the `xd learn` verbs are part 12c.

## Deviations and interpretations (proposals, for the owner)
- **The eighth lifecycle move** (see the owner question above).
- **The P8 read-only rule gains one approved write.** The re-enable route is under `/api/learning`, a prefix the P8 phase check guards as GET only, so `POST /api/learning/cells/{key}/re-enable` is added to `ApprovedReportWrites` (the route is the owner-approved CF-12 spec's). The other routes of this part are under `/api/confidence`, which is not guarded. Without the entry the P8 phase check would say NOT MET.
- **Re-enable returns to Paper, never Active**, and for a pause that no kill proposal made there is no kill condition, so only the lifecycle's claimed `Recovered` fact applies. The spec says "Paused -> Paper/Active"; the table allows only Paper.
- **The 409 is named `confidence.rule_not_cleared`**, not the spec's `confidence.rule_cleared`, so that the name reads correctly (a rename of a code that nothing used yet).
- **The kill switch has its own table `confidence.kill_settings`**, a third table beside the spec's two, stored like `paper.shadow_settings`. No account-audit cross-index event is written for it (the shadow switch has one): the row has the actor, reason and time; an `AccountEventType` for it is a small follow-up.
- **`dismissed` exists in the schema but nothing sets it**: the spec lists no route to dismiss, and the UI is 12c. A rule that stops firing leaves its open proposal open; the owner applies it (it pauses nothing that is no longer Paper or Active) or it waits for the dismiss verb of 12c.
- **A proposal covers the cells that are Paper or Active when it is written**; a cell that becomes Paper later is not in it.
- **The "20 new trades since it last fired" wait** is read as since the newest proposal of the rule in the same epoch, in any state (carried over from 12a's reading).
- **Concurrent auto and manual apply:** the changelog rows record who paused each cell, the proposal records who won the final update; if both race, they can differ (each row is true). Marked `// shortcut:`.
- **Kill rule (b) drawdown stays `not_evaluated`** on the edge series (12a: a shadow row has no cell in the reader), so it never proposes; the proposal path for it is built and tested with a scripted report. The frozen thresholds are proposals of the spec.
- **The service runs in the API host** with the other scheduled services (their definition says `xd-api`); the Worker project only runs heartbeats. The brief said "in the Worker"; registration is the way `shadow-grade` is.
- **`UNVERIFIED` answered:** "Paused for all cells of a strategy" is the intended meaning of paper size zero: a Paused cell fails the selection's `cell_state` filter (rank 0), so it is never a candidate; nothing else reads the state yet, so this is a record of intent until paper data and live exist. "Is the P10-04 band code able to give the percentile at any n" stays as ADR 0218 answered it.

## Consequences
A failing forward edge is now told to the owner with the rule and the numbers, can be stopped by one click or, if the owner decides, by the daily run, and can only come back by the owner's act with a fresh password after the condition has cleared. The CF-09 failure boundary never acts by itself. Nothing ranks, sizes, plans, approves or orders differently: only the state of cells moves, and only toward less risk unless the owner re-enables. Parts 12c (screens and verbs), CF-11 (the gates the re-enable warns about) and 10d (rollback) remain.
