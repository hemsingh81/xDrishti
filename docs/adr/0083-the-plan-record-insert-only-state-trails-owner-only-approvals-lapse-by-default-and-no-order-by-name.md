# 0083 — The plan record: insert-only state trails, owner-only approvals, lapse by default, and no order by name

- **Status:** Proposed (spec [P7-03](../specs/P7-03-plan-record-and-state-machines.md), approved under the owner's standing run instruction of 2026-10-22; built 2026-10-23). Becomes Accepted when the owner has read it.
- **Date:** 2026-10-23.
- **Relation to other ADRs:** [ADR 0073](0073-the-learning-changelog-and-the-cell-lifecycle-the-log-is-the-state.md) (the log is the state), [ADR 0078](0078-lessons-a-finding-a-linked-fix-and-a-result-read-from-the-stored-experiment.md) (append-only record with a lock per subject). The first ADR of P7 is 0082 (written by another slice); this one is the plan record.

## Context
P7 turns stored evidence into a proposed plan for the next session and records what the owner decides. Doc 04 section 4.2 gives the ticket diagram; doc 19 section 5 says v1 places no orders. Before any pipeline or screen exists, the record, its transition tables and the rule that nothing can place an order must exist and be tested, because everything later (review, arming, grading) writes into them.

## Decision
1. **Six insert-only tables.** `trading.plans` (immutable header, unique `plan_key`, `(for_date, version)`), `plan_items` (primary, reserve, rejected with reasons, levels as text, evidence as columns), `plan_item_allocations` (size per Trading account, paper mode only for now), `plan_events` (the trail), `plan_runs` (one row per pipeline attempt) and `workflow.approvals` (the owner's decisions). `xd_app` has SELECT and INSERT only (`MakeAppendOnlyForAppRole`, a grants test on a dedicated server). New schemas `trading` and `workflow`.
2. **The state is the newest event.** No state column. A move locks the plan or item (advisory lock in the transaction), checks that the newest state is the one the caller saw, and inserts; of two concurrent moves one wins. The database also holds the legal pairs of both tables in a check on `plan_events`, and a test compares the check with the Domain tables on every pair, so the two cannot drift.
3. **Pure tables.** Tickets: 10 states, 13 moves. Plans: 8 states, 11 moves. Into Approved, Modified and Rejected only the owner moves; every other move is a service's. The plan state is bounded by its tickets. A rejected candidate is not a ticket and has no moves.
4. **Lapse is the default.** At the review cutoff every undecided ticket lapses; the plan is Approved only if the owner approved a ticket. There is no top-N arming and no promotion from the reserve. These are the safe defaults of P7-00 questions 3 to 5; changing them is the owner's decision and a new migration and ADR.
5a. **The database enforces it.** An item event into approved, modified or rejected must name an approval row, any other event must not (check); the approval's actor must start with `owner:` (check) and its kind is `owner`; composite foreign keys tie an event and an approval to an item of the same plan and an event to an approval of the same item and plan; a state is left at most once (partial unique indexes). The store throws if an approval is missing, extra or of another decision than the move. The first write endpoint must set the actor from the authenticated identity, never from a request body (a typed actor can replace the `owner:` prefix then).
5c. **The database holds on a direct insert too.** An approval names the state it backs (generated `state`), and an event's `to_state` must equal it (composite foreign key), so a reject approval cannot back an approved event. Every event carries `prev_event_id`: exactly the first event of an item starts at `proposed` (of a plan at `draft`) with no previous event, and every later one continues from the previous event's `to_state` (composite foreign key; lane 0 is the plan). A `BEFORE INSERT` trigger on `plan_events` (`trading.check_plan_event`, owned by the migration role; the runtime role has INSERT only; dropped in `Down`) enforces the plan rules from the newest event of each ticket (approved needs an approved ticket and none open; rejected and lapsed need none open and none approved; armed needs an armed ticket; in review needs a decision) and refuses events on rejected-group items. An approval's `(plan_id, cutoff)` is a foreign key to `(id, review_cutoff)` of the plan, so the cutoff is the plan's own; `decided_at` is stamped by the database clock by a `BEFORE INSERT` trigger on `approvals` (a direct insert cannot back-date an approval before the cutoff; the store reports the refusal as after the cutoff) and the store reads application time after taking its locks. `review_cutoff` must fall on `for_date` in India.
5b. **Consistency and the cutoff.** Ticket moves take the plan lock, then the item lock; a plan move recomputes the ticket facts in SQL under the plan lock, so a plan is never Approved or Armed without a live approved or armed ticket. A plan is Approved only as a consequence of owner ticket approvals (each backed by its approval row); the cutoff handler's plan move is a service move that can only follow one. The review cutoff is stored on the plan (derived from the session calendar by the pipeline), and an owner approval or modification at or after it is refused by the store and by a check on `approvals` (rejection is allowed); decisions are accepted only while the plan is Published or InReview.
5. **Approvals are the owner's only.** `workflow.approvals.kind` has a check `= 'owner'` and the `ApprovalKind` enum has one member; there is no system, rule or automatic kind in this slice. An approval row is written in the same transaction as the ticket move it records, with actor, reason, optional confirmation reason, modifications (required for modify) and the cutoff.
6. **No order by name.** An architecture test scans every type and member name of the shipped assemblies for `PlaceOrder`, `SubmitOrder`, `ModifyOrder`, `CancelOrder` in any casing (underscores ignored) and for create/send/post/execute/buy/sell with order or trade, the API route templates for order routes, and the referenced assemblies for broker or order-routing libraries; it is proved to fail on a planted member and type. It is a tripwire, not a guarantee and not the barrier: the barrier is that no broker write endpoint is on the allow-list and no order-capable credential exists (doc 19 section 5). Every plan carries the sentence that armed is watched, not an order, as data, pinned by a test.
6a. **Grants stay narrow.** A later migration must not call `GrantSchemaUsageToAppRole` for `trading` or `workflow` (it would give UPDATE and DELETE back); an architecture test fails on it. A new table there is granted on its own and made append-only.
7. **Surface.** `GET /api/plans` and `/{id}` are read only. The write handlers exist for P7-10 and P7-11 and are not exposed. Log ids 4650 to 4653. Migration `AddPlanRecord` with `Down`.

## Consequences
- **Decay:** the plan rules hold at the moment of the plan move. A plan that is Approved or Armed stays so if its last approved ticket is later invalidated or expires; the tickets carry the live state. The trigger sees committed rows only, so a direct writer that skips the store's plan lock can still race it.
- **"Owner" in the database is the actor prefix plus the kind**; any code holding `xd_app` can write it. The control is that no path or endpoint does (architecture tests, GET-only endpoints); the first write endpoint must take the actor from authentication. The database does not require a published plan before item events, nor bound `review_cutoff` to the calendar session beyond the date: P7-08 derives it.
- **Lock keys** are 32-bit `hashtext` values: a collision only makes two moves wait for each other. Correctness does not rest on the lock: the continuity indexes, the chain keys and the trigger are in the database.
- **The migration id `20261023102010` was never applied outside tests**; `AddPlanRecord` was edited in place (now `20261023112357`) while unmerged.
- **Tripwire gaps (not a guarantee):** the name scan does not match `SquareOff` (a legitimate exit reason of the simulator; the route scan has `square-off`), nor names built from other words, strings, reflection or a library not on the denylist; an order sent through a generic HTTP call to an allow-listed host is not caught by any scan. The barrier is the host allow-list and the absence of an order-capable credential.
- Every later P7 slice writes into tested tables and tested state rules; the pipeline, review and arming add no new way to approve.
- The trail answers "what did the system propose and what did the owner decide" from rows alone (the Decisions report of P7-13 reads it).
- Allocations to a manual-live account are refused by the database until a later migration relaxes the check on the owner's decision.
- **Shortcut:** the actor is a string with the `owner:` prefix, checked in the handler and in the database; it is only as trustworthy as the caller that builds it (see 5a). The rule is by name, so it stops the obvious order method, not a determined bypass.
- Not verified: behaviour on the owner's machine; no plan has been published by a pipeline yet.
