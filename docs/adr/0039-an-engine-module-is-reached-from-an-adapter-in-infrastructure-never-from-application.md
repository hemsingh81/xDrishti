# 0039 — An engine module is reached from an adapter in Infrastructure, never from Application

- **Status:** Accepted with spec P3-04a (the owner approved the spec that requests this rule, 2026-10-18: "approve P3-03a and P3-04a"; the text of this ADR is the build's record of it and has not been read by the owner separately). It refines, and does not supersede, the dependency rule of [doc 03 §4](../design/03-target-architecture.md), which drew the engine modules beside Infrastructure.
- **Relation to other ADRs:** [ADR 0002](0002-config-and-strategies-in-app.md) (strategies are data, so the use case that runs one must not be tied to the code that evaluates it); [ADR 0037](0037-simulation-conventions-and-the-two-stage-seam.md) (Amendment 3 records the decisions of P3-04a about the universe, the reads and the refusals; this ADR records the layering that carries them).
- **Date:** 2026-10-18 (built the same day)

## In short
- **Application references Domain only.** It never names `XDrishti.Simulation`, `XDrishti.Indicators` or `XDrishti.Strategies`.
- **A use case reaches an engine through a port** declared in `XDrishti.Application/Abstractions/<module>` whose signatures use Domain values only, and **an adapter in `XDrishti.Infrastructure/<module>` implements the port** over the engine module. Infrastructure is the only project that references the engine module (the compiled adapter is `internal`, stateless, with no I/O and no clock).
- **The sequence is handler → port → adapter → engine.** The handler reads through its own ports (bars, instruments, baskets, actions, calendar), hands the values to the engine port and keeps the answer; the engine stays pure.
- **An architecture test enforces it**, with a sentinel for each rule (`ResearchLayeringArchitectureTests`).

## Context
Doc 03 §4 said `Domain ← Application ← (Infrastructure, Brokers.*, engine modules) ← hosts`, which draws the engine modules (Indicators, Strategies, Simulation, Learning, Planning) at the level of Infrastructure. That left two readings: an engine module that Application may reference (it is pure, so what harm), or an engine module reached through Infrastructure. P3-04a needed the second, for three reasons found in the review of its first draft:
1. **`backend/CLAUDE.md` makes one use case one handler and puts every I/O behind a port in `Abstractions/`.** The orchestration of a simulation run (validate, prepare, resolve the universe, read one instrument at a time, apply the guard against adjusting a CSV-adjusted series twice, assemble the record) is a use case. It belongs in Application, where the Strategy Lab (P5), walk-forward (P4) and the scanner (P7) will reuse it. The first draft put all of it in an Infrastructure adapter named after the use case; that makes the orchestration of every later consumer an Infrastructure matter.
2. **The engine modules change for their own reasons** (a new indicator, a new rule of the language, a new fill model) and Application should not recompile or retest with them. A port that names Domain values only is the seam: `InstrumentReplayInput` and `InstrumentReplay` live in `XDrishti.Domain.Research` for that reason.
3. **Where the strategy comes from will change** (P3-02c and P3-02d store strategies as text): the port changes then (a strategy spec with id, text and parameters, not the built-in id it takes today) and only the adapter and the factory behind it follow.

## Decision
1. **Application references `XDrishti.Domain` among the projects and nothing else** (project file and compiled references). No type of Application depends on `XDrishti.Simulation`, `XDrishti.Indicators` or `XDrishti.Strategies`.
2. **The port** `ISimulationEngine` (with its opaque handle `IPreparedStrategy`) is in `XDrishti.Application/Abstractions/Research`. `EngineVersion`; `Prepare(strategyId, parameters, evaluationTimeframe, fills)` giving a `Result` with field errors that carry a path and a code; `Replay(strategy, input)` giving `InstrumentReplay`. Pure and synchronous; a caller error throws; a handle the engine did not make throws `ArgumentException`. The namespace holds interfaces only and mentions no engine type.
3. **The adapter** `SimulationEngineAdapter` is in `XDrishti.Infrastructure/Research`: `internal sealed`, no constructor parameters (a singleton; the prepared strategy belongs to a run and no scoped service is injected into it), no field, no I/O, no clock, no logging. It is a thin map from the port to `BuiltInStrategies.Prepare` and `InstrumentReplayer.Replay` of `XDrishti.Simulation.Replay`. It names no type of the strategy model, the indicators or the compiler; the one type of `XDrishti.Strategies` it touches is the located problem (`LocatedProblem`), which it turns into a `FieldError`.
4. **Project references.** Infrastructure references `Application` and `Simulation` and nothing else of the engine modules (`Strategies` is reached transitively; the compiler warm-up rule of doc 03 §4.2, which looks for a *direct* reference to `Strategies`, is unaffected and is still met by `XDrishti.Simulation` and `XDrishti.Api`). Nothing in `src/` but Infrastructure references `XDrishti.Simulation`; test projects may. The `Dockerfile` already copies the project file of every project Infrastructure needs.
5. **The handler** takes ports (interfaces), a `TimeProvider` and a logger, and nothing else; it is `internal sealed` (the `LayerDependencyTests` handler rule). It reads a clock only through `TimeProvider`, to time the phases for the log.
6. **Where the built-in strategy factory lives.** `BuiltInStrategies` (id and parameter names to `OrbV1`) stays in `XDrishti.Simulation.Replay`, beside the replay, so the adapter needs no strategy-model type; it gained `BuiltInStrategies.Prepare`, which builds and prepares in one step, for that reason. The registry of P3-04b reuses the same factory.

## Consequences
- **Tests.** `ResearchLayeringArchitectureTests` (in `XDrishti.Architecture.Tests`) reads the project files and the compiled assemblies: Application references `Domain` only and no type of it depends on an engine module; the port namespace holds exactly the two interfaces and names no engine type; Infrastructure references exactly `Application` and `Simulation`; no other `src` project references `Simulation`; the `Dockerfile` copies the three engine project files; the handler is `internal sealed` and takes interfaces and `TimeProvider` only; the adapter is `internal sealed`, stateless and free of I/O and clock (the IL of the adapter and of the handler is scanned for wall-clock, file, network and environment reads, with a sentinel), and depends on the strategies library only through `LocatedProblem`. Each rule has a sentinel (a type in the test project that does what the rule forbids) or a reading that proves the scan finds what it looks for.
- **Cost.** One more hop for every engine call, and a value type in Domain for everything the port's signatures use (`InstrumentReplayInput`, `InstrumentReplay`, `StrategyRecord`, the counters). That is the price of an Application that can be built and tested with no engine project, which `XDrishti.Application.Tests` does (a fake engine).
- **Later engine modules** (Learning, Planning) follow the same pattern: a port in `Abstractions/<module>`, an adapter in `Infrastructure/<module>`, the only reference to the engine project in Infrastructure.
