# 0156 - The execution record lives in schema `execution`, written only by the role `xd_exec`, with checks by trigger, and the container sits in profile `live` on its own network

- **Status:** Accepted (decided in P12-01b under the owner's instruction to build P12; spec [P12-01b](../specs/P12-01b-execution-record-role-and-container.md)).
- **Date:** 2026-10-29.
- **Relation to other ADRs:** continues ADR 0155 (skeleton and pure state machine); uses ADR 0083 (insert-only trails, chain keys) and the role pattern of ADR 0137 (login set by `xd-api migrate` from a secret file).

## Context
ADR 0155 left everything that needs a database, a role or a container for this slice. The owner asked for it with hard limits: still no broker call, no start of the container by a plain `xd-up.sh`, nothing created in the Keychain by an agent, every setting OFF.

## Decision
1. **Schema `execution`, raw SQL migration `AddExecutionRecord`, not mapped in the EF model.** Nine tables: `intents`, `events`, `legs`, `fills`, `intent_state`, `positions`, `commands`, `command_results`, `settings`. The other tables of the criterion-10 list (broker calls, checks, alarms, halts, drills, reconciliation) are created by the slices that own them. Only the service writes the record and it uses plain Npgsql in `XDrishti.Execution/Persistence`; the API reads with one query in Infrastructure. The EF model, `xd-migrate` and the architecture pins are therefore untouched.
2. **Checks by trigger and constraint.** `execution.legal_move(from, to)` holds the 23 pairs (a test compares all 196 with the Domain table); a check constraint uses it. `check_event` locks the intent's state row, requires `seq = last + 1` and `prev_event_id = last id`, a state event to start from the current state, refuses `open>cancelled` after a fill and a fill above the quantity. `project_event` moves `intent_state` (state, seq, filled quantity) in the same statement, so the projection cannot drift; a test rebuilds it from the events for 200 random intents and compares it to the live row, in C# and in SQL.
3. **Role `xd_exec`.** Created NOLOGIN by the migration (when the migrating role may), given a login by `xd-api migrate` from the secret file `ExecRole__Password` (empty or absent = the role is set NOLOGIN, failing closed even after an earlier login; nothing starts the service without the owner). Grants: INSERT on `events`, `intents`, `fills`, `command_results`; INSERT and UPDATE on `legs`, `intent_state`, `positions`; SELECT on the rest of the schema; sequence usage; its heartbeat row (`platform.service_heartbeats`) is the only write outside the schema. No DELETE, TRUNCATE or UPDATE of an insert-only table. A connection limit of 6 and short statement timeouts. **Read grants outside the schema** are the plan, approval, account (without secrets), live quote, instrument, calendar and holdings tables. **Decided against the spec text:** `accounts.broker_secrets` and `accounts.broker_connections` are NOT granted now: nothing reads them before the broker adapter, and a vault read with no user is only risk; P12-02 adds those two grants with its adapter. `auth.sessions` is not granted (as specified). **Amended by [ADR 0171](0171-a-live-broker-token-reaches-the-execution-service-only-as-a-per-account-same-day-sealed-hand-over-with-its-own-key-for-the-readiness-reads-first.md):** `xd_exec` also reads (SELECT only) `accounts.exec_token_handover`, the sealed same-day token hand-over; still nothing on `accounts.broker_secrets`.
4. **`xd_app`:** SELECT on every execution table, INSERT on `commands`, nothing else; the default privileges are revoked table by table and for sequences. `ExecGrantsTests` lists every table and fails on a new one or a wider grant, so a later migration that re-grants the schema is caught. The owner-act tables (mode trail, limits, day unlocks) and their actor-kind triggers belong to P12-07.
4a. **Two guards after review.** `xd_exec` holds UPDATE on `intent_state`, so a BEFORE INSERT/UPDATE trigger (`guard_projection`) refuses any write that is not inside the trigger chain (`pg_trigger_depth() < 2`): the event triggers pass, a direct statement is refused (tested). The grant on `platform.service_heartbeats` is table-wide, so a row guard trigger (`guard_heartbeat`) lets `xd_exec` write only `service_name = 'exec'` (tested).
4b. **`Down` leaves the role `xd_exec` and its CONNECT grant on purpose** (cluster-wide, owns nothing once the schema is dropped; a later Up reuses it); it removes the schema, the heartbeat trigger and the outside grants.
5. **The service refuses any other role.** `ExecDatabaseOptions` fails start-up unless the connection string's user is `xd_exec`; the health probe applies the same rule.
6. **Command plane by polling.** A 500 ms poll of commands without an answer; the primary key of `command_results` makes a second answer impossible. The spec's `LISTEN` is not used: polling meets the one-second bound and avoids a long-lived connection. The only known kind is `ping` (done); every other kind is refused `execution.command_unknown`. No endpoint writes a command in this slice, so the API has no write route here.
7. **Heartbeat and status.** Row `exec` every 10 s (state always `recovering` until P12-06; details: environment, settings hash, commands answered), stamped by the database clock. `GET /api/execution/status` is read only: `down` for no row, an unknown state word or a beat older than 30 s (an unknown word never reads as healthy); environment `none` and the settings hash only while fresh; every account's gate is closed with `no_mode_answer` until the mode ladder (P12-07); `halts` is empty and `entriesBlocked` is always true until the halt store (P12-05).
8. **Container.** Dockerfile target `exec`; compose `xd-exec` in profile `live`, network `exec` (internal; `xd-db` joins), no egress, no published port, one secret (`db_exec_password` as `Database__Password`), 256 MB, hardened, health check = heartbeat younger than 45 s, environment `none` unless `XD_EXEC_ENVIRONMENT`. `xd-up.sh` creates the Keychain item `xdrishti/db/exec` and builds and starts the profile only with `--exec`; without it an empty secret file is made once so that compose still resolves. `xd-migrate` also mounts the password file (to set the login), so the boundary rule (g) now reads: the file in `xd-migrate` and `xd-exec` only, the role name and `exec` network membership (with `xd-db`) as stated; `ExecComposeRulesTests` pins it with a planted violation per rule.
9. **Boundary test.** Npgsql is allowed in `XDrishti.Execution` (Persistence only; Domain and Application stay free of it); EF Core, Infrastructure, ASP.NET Core and HTTP stay forbidden. Still no broker code, no HTTP client, and the `xd-api` allow-list is unchanged.
10. **Event ids** 6601 to 6605 (host), 6610 and 6611 (role provisioning).

## Consequences
The order record exists, is protected from every other role, and the service can run, heartbeat and answer a ping, with no way to reach a broker. Joining `exec` changes the `xd-db` service definition, so the next `xd-up.sh` recreates the database container: a brief whole-stack outage (the named volume persists). `legs`, `fills` and `positions` have no writer until P12-02; the projection check covers `intent_state` (state, seq, filled quantity). `LISTEN` can be added later without a schema change if latency ever matters.
