# 0247 — Learned setting changes are bounded steps on a short allow-list, kept in an insert-only log and applied at the next start

- **Status:** Accepted by delegation (owner instruction in chat 2026-11-09: research best practice, choose the best, validated setting with the best default, record it here). Built in AU-10.
- **Date:** 2026-11-09.
- **Relation to other ADRs:** Applies [0242](0242-few-visible-settings-and-learned-changes-tighten-automatically-while-loosening-needs-the-owners-password.md) and [0246](0246-the-settings-catalog-has-one-descriptor-per-key-five-essential-settings-and-an-undeclared-direction-loosens-both-ways.md); [0244](0244-one-auto-switch-runs-the-chain-and-only-suggests.md) owns the Auto switch (AU-17 builds its store; here it is only read). ADR 0220 (model promotion) is unchanged.

## Context
ADR 0242 fixed the rule: learning may tighten by itself, anything else needs the owner's fresh password. Left open: which keys, how far one change may move, how many per week, where the change lives, when it takes effect, how a pair of keys that limit each other is checked, and what happens when a stored change would stop the host.

## Decisions
1. **Allow-list (nine keys).** `CostStress:TierABps`, `TierBBps`, `TierACutCrore`, `TierBCutCrore`, `RangeFraction`, `MinTurnoverCrore`; `Decay:Sigmas`; `Readiness:ExpectancyR`, `TStatistic` (all under `Confidence:`). Each has a declared direction that the existing validators or an ADR call tighten-only (ADR 0230 for the cost keys, which it says measured paper fills should replace), and a measured source can inform it. A key with direction `none` is never learnable; `Loop:Level` is not on the list; no stored switch (Auto, kill, readiness, model, live, execution) is on it. A test pins the list against the descriptors.
2. **Bounded step.** An automatic change moves a value by at most `Learned:MaxStepPercent` (default 10, range 1..25) of the value it replaces, never past the descriptor bounds. Best practice for adapting a safety threshold from noisy evidence is a rate limit and a trust region, so one week's evidence cannot jump a gate and the next week can step again from new evidence. A loosening is stored as asked (it is only ever a proposal).
3. **Weekly cap.** At most `Learned:WeeklyCap` automatic changes in a trailing 7 days (default 3, range 0..10; 0 turns automatic application off). The rest stay proposals. One variable per change (one key per row, and one piece of evidence per key per run), once per evidence hash.
4. **Evidence.** Out of sample only, never from sealed hold-out data, never unavailable (a missing figure, hash or reference is a skip, not a pass). The evidence source port has one implementation today that reports nothing, so until a measured source is added the weekly run changes nothing. The same holds for the empty-plan probe of criterion 9: it cannot tell, so no notice is raised and no number is invented.
5. **The log.** `config.learned_setting_changes`, insert-only for the runtime role except the state and decision columns. The database refuses: an automatic decision of anything but a tightening made by learning, an automatic decision while `auto.enabled` is not stored as true, a loosening decided by anything but an owner, a decided row decided again, any change to what was proposed, any delete. Each row keeps a settings snapshot (Auto, cap, step, the values of the allow-listed keys) and its hash, and the evidence reference and hash. An auto decision is recorded as `auto`, never as an owner approval.
6. **Applied at the next start.** The host reads the newest applied value of each key once while it builds its options and lays it over the configured value. The running values do not move meanwhile (the options are singletons, and a hot reload would let a decision change a gate in the middle of a plan). The view says so.
7. **A learned change must not stop the host.** At start each value is tried on its own: it is used only if its key is on the allow-list, an automatic value is not looser than the configured one, and the options still pass every validator with it; otherwise it is left out with a warning. If the log cannot be read the configured values stand. The check at proposal and at approval uses the same validators over the whole candidate (so the pairs that limit each other, such as hold-out against ladder bar, high against mid multiplier, tier B against tier A, building against usable against ready, are checked together) and a candidate that fails is refused and saved nowhere.
8. **Undo.** Undoing an applied change is one step: a new row puts the old value back and the first row becomes `undone`. Undoing a tightening is a loosening and needs the password at any Auto state; undoing an owner loosening puts the tighter value back and needs only the session. This amends doc 09's one-click Revert for that case only.
9. **Passwords.** The endpoint reads the row to see whether the act loosens (the stored direction or the descriptor's, whichever is less safe; an unknown key or unreadable value loosens) and asks for a fresh password for THIS act (neither opens nor uses a step-up window); the handler refuses without the proof as well. Dismissing is the safe direction and needs none.
10. **Essential rows (criterion 11).** `GET /api/settings/essentials` gives value, default, whether it is the default, who changed it and when. `notices.failure` is stored in `platform.app_settings` (the failure notices of the services honour it; turning it OFF needs the password). A reset to default needs the password and is offered for `notices.failure`, `auto.enabled` and `suggest.scope`. `chargesheet.gate` shows who and when (from its own log) but is switched only by its own owner act, which an architecture test pins as the single place that names the act (its default is Off, so the screen calls that act with Off); `risk.profile` has no single default (profiles belong to accounts), so no reset and no who/when is recorded for it.
11. **Service.** `learned-settings` runs after `weekly`, starts paused, recovery class `LatestOnly`.

## Consequences
Nothing changes in production until the owner turns Auto on (AU-17) and a measured evidence source exists; until then the allow-list, the log, the endpoints and the guards are in place and tested. The nine keys and their directions are for the independent reviewer to confirm key by key.
