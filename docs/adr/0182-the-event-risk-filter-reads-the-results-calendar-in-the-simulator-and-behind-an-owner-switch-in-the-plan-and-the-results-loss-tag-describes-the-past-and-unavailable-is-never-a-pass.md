# 0182 — The event-risk filter reads the results calendar in the simulator and, behind an owner switch, in the plan; the results loss tag describes the past; "unavailable" is never a pass

- **Status:** Proposed (built in P15-06 from the owner-Approved spec, 2026-11-02). Becomes Accepted when the owner has read it. **Safety slice: yes** — it changes which entries a research run takes and, when switched on, which candidates the plan selects. It places, sizes, moves and cancels no order, and no setting here allows one.
- **Date:** 2026-11-02.
- **Relation to other ADRs:** [0037](0037-simulation-conventions-and-the-two-stage-seam.md) (amendment 10: engine `sim-7`, run-record schema 7), [0071](0071-automatic-loss-tags-pure-rules-over-the-closed-trade.md) (the tags describe the past), [0082](0082-selection-core-filters-with-unavailable-merge-and-a-deterministic-rank.md) and [0087](0087-pretrade-checklist-pure-unavailable-never-passes-and-an-owner-only-confirm-despite.md) (`unavailable` is never a pass), [0174](0174-the-owner-switches-execution-on-only-with-a-fresh-password-and-a-full-closed-session-auto-live-stays-off-and-the-kill-switch-drill-runs-only-in-the-sandbox-and-sends-nothing.md) (the switch pattern: fresh password every change, insert-only decision rows, pinned `search_path`), [0180](0180-the-point-in-time-filing-store-keeps-immutable-envelopes-and-answers-what-was-known-at-an-instant-from-the-broadcast-time-plus-a-lag-and-nothing-else.md) and [0181](0181-the-results-calendar-keeps-each-meeting-row-with-its-own-intimation-time-counts-days-in-trading-sessions-to-an-event-session-and-answers-unavailable-for-an-instrument-with-no-entry.md) (the visibility rule and `days_to_results` this reads), [0083](0083-the-plan-record-insert-only-state-trails-owner-only-approvals-lapse-by-default-and-no-order-by-name.md) (no order).

## Context
Four consumers want "how many sessions until this company reports": a strategy that names `not_event_day`, the plan selection (`exclude.results_within_days`), the plan's pre-trade check, and the loss tag. Each must say `unavailable` for an instrument with no calendar entry and take its non-pass path; none may guess a date. In the live paths nothing may change until the owner says so, and the owner's "auto" option (CLAUDE.md) must be recorded as auto and never run on missing evidence.

## Decision
1. **One pure window rule.** `ResultsWindow` (Domain): a candidate is *inside* iff `0 <= days <= N` sessions; a non-value answer, or a negative number, is `Unavailable`, never `Outside`. `EventDayFilter` applies it to a snapshot with N = the side's `max_hold_sessions` (0 for an intraday side): **no position is open across a results event**. The simulator, the selection and the checklist share it (the checklist only takes `DaysOrNull`; its rule `d > 3` and limit 3 are unchanged).
2. **The simulator reads an immutable snapshot, never a port.** `EventCalendarSnapshot` (Domain) holds the stored `results` meeting rows of the run's instruments with an intimation time, cut to whole microseconds, plus the lag; the run handler takes it with **one** read before the walk (cutoff: end of the window's last India date minus the lag) and hands it to every replay. A decision at instant `t` asks `ResultsDays.Compute` over the rows of its instrument, so a meeting intimated after `t` does not exist at `t` (reschedules and cancellations act from their own times). Blocked and unavailable entries become no-trades `EventBlocked` and `EventUnavailable` **before the walk and before the position gate**, so they open no position and occupy no gate; they are counted in `WalkCounters`, `RunFates` (identities hold: fates still add up to the candidates) and the run record. **Names:** the stored fields are `EventBlocked` and `EventUnavailable` (`event_blocked` and `event_unavailable` in the JSON of the record and the export); they are the spec's `event_filter_blocked` and `event_filter_unavailable`. `calendar_rows`, `calendar_sha256` and `evf_version` are `EventFilterRecord.CalendarRows`, `CalendarSha256` and `EvfVersion` (`event_filter` in the record JSON). A run that names the filter with **no calendar row at all** is refused `simulation.filter_not_available` ("no results calendar rows for the window (P15-04)") before any bar is read; so is a run whose calendar read failed. An instrument handed no snapshot is skipped `event_calendar_unavailable`. `min_turnover` stays refused with a message that no longer mentions the calendar.
3. **Run identity.** A run that names the filter records `EventFilterRecord(calendar_sha256, calendar_rows, lag_minutes, evf_version)` and its key text has the line `events=<sha256>|<lag>|<evf-1>`; the definition (which names the filter) and the snapshot hash and the lag each change the key. A strategy that does not name the filter has no such line, reads no calendar, and its trades equal the `sim-6` trades (differential test; the goldens differ only by the engine label and, in the run record, the schema number and key).
4. **Plan, behind a default-OFF switch.** `PlanEventFilter` reads the effective switch; OFF (or an unreadable table) changes nothing and the calendar is not asked. ON: one batched `IResultsCalendar.DaysToResults` per plan build at `t = max(build instant, start of the plan's India date)` supplies `PlanCandidate.ExcludedByEvent` (true inside N, false outside, null unavailable) and the checklist's `DaysToResults`. A required `event` filter holds a candidate with no entry (an owner may list `event` as optional, then it is a printed caveat); `events` leaves the "not applied" list only while the filter ran; the basis prints `events: N=2, 187 of 214 instruments with an entry, 27 unavailable`. A calendar read that fails answers `unavailable` for everyone and throws nothing into the plan. **The execution checklist (`ExecChecklist.Results`) is unchanged and stays `unavailable`**: `xd_exec` gets no grant on `filings`, `XDrishti.Execution` references nothing of it (architecture test); how the money-path service would receive such a fact is a separate decision.
5. **The switch is an insert-only history.** `filings.event_filter_decisions` (migration `AddEventFilterDecisions`, granted table by table: `xd_app` SELECT and INSERT, the identity sequence, nothing for `xd_exec` or the read roles): `enabled`, `results_within_days` 0-10, `approval` manual/auto, `decided_by` owner/auto, `actor`, `reason`, `setting_snapshot` jsonb, `verdict_ref`, `changed_at`. Checks: `owner` ⇔ `actor LIKE 'owner:%'` and no verdict reference; `auto` ⇔ `actor = 'auto:event-filter'` and a verdict reference. A `BEFORE INSERT` trigger (no `SECURITY DEFINER`, pinned `search_path`, READ COMMITTED) takes an advisory lock, stamps `changed_at` from the database clock, and holds an automatic row to its limits: approval `auto` in force, window and approval copied, turn-on only from off and never right after an owner OFF, turn-off only of a filter an automatic row turned on. The newest row is the switch; no row or an unreadable table is OFF. `GET`/`PUT /api/selection/event-filter`: every change (ON and OFF) needs the session, the CSRF token and a **fresh password** (`StepUpCommand`, no elevation), the actor comes from the session, a reason of 1-300 characters without secrets (`selection.reason_invalid`), a window of 0-10 and approval manual/auto (`selection.invalid_setting`), 401/423 from the step-up, 403 `selection.owner_only`, 409 `selection.stale`; one account event `EventFilterSwitched` (category `selection`) names the row and never the reason. The paper-account configuration snapshot lists the three `smart_rules.event_filter.*` values, so the configuration identity changes with them (turning it on is classified protective: `risk_down`).
6. **The auto option is a pure rule over a stored verdict.** `EventFilterAutoDecision.Decide(verdict, state, ruleVersion)`: with `approval = manual` nothing happens; with `auto`, only a verdict `KEEP` **for the current rule version with a reference to its evidence** turns the filter on; `DROP`, `INCONCLUSIVE`, `NOT_EVALUABLE`, another rule version, an unknown word, no verdict and `unavailable` change nothing (counted `auto_not_applied` with a closed reason); an automatically enabled filter turns itself off when the newest verdict of the current version is an explicit non-KEEP; a filter the owner turned on is never turned off by it; **a filter the owner switched off (an owner OFF row directly after an ON row) stays off: the auto path may not turn it on again until the owner turns it on or sets approval manual** (an owner row that is off after an off row, such as the one that arms `approval = auto`, is not an owner OFF; the pure rule says `owner_off`, the trigger refuses the row, and the cross-check test covers it); an unreadable verdict neither turns it on nor off; it never changes N or the approval (setting `approval = auto` is itself a fresh-password owner act). `ApplyEventFilterAutoHandler` records the row as `decided_by auto`, `actor auto:event-filter`, with the settings snapshot, the verdict state and rule version and the verdict reference. `IEventFilterVerdict` has no implementation before P15-10; the registered default answers `unavailable`, so the auto path cannot fire. A test cross-checks the trigger against the pure rule on every state and both actions, with two mutants of the rule that must disagree with the database.
7. **The loss tag `news_results` (rule version `lt-3`).** `LossTagKind.NewsResults` is appended last (stored counts keep their order) and is decided before `NormalVariance`. A loss is tagged when an event instant of its instrument lies in `[entry, exit]`, both ends inclusive: the broadcast time of a stored `results` filing, or, for a current, not cancelled calendar meeting **with no results filing for its period**, 09:15 India time of its event session (detail ends `; basis: calendar`). `LossTagger.Tag` keeps its two-argument form, which means "events not supplied": no tag, counted `news_results_unavailable`, never "no news". An instrument with neither a filing nor a meeting is absent from the events (unavailable), not an empty list; the `news_results` line leaves `NotBuilt` only when events were supplied and no loss lacked data; otherwise it reads "events not supplied" or "no filings data for N instruments". The growing-tag detector compares the new kind only when events were supplied. The tag describes the past from data known after the trade; an architecture test keeps `LossTagKind`, `LossTagger`, `EventInstant` and `ResultsEvents` out of the simulator, strategies, indicators, ML code, execution, selection, planning and the learning feature code.
8. **Logging** carries counts, ids and closed codes only (`selection.event_filter.switched|auto_applied|auto_not_applied|excluded|unavailable`); never a password, a reason text or a file.

## Consequences
- `SimulationEngine.Version` is `sim-7`, `SimulationRun.CurrentSchemaVersion` 7. **A stored run of schema 6 is still readable with its own label and is not re-labelled; the experiment-job baseline reader replays only the current schema, so a sim-6 run must be run again to be a baseline.** The oracle comparison is rerun in the same suite and the label is verified for `sim-7`: the walker, the gate and the costing are unchanged; the two new counters are always 0 in the oracle (dry-read table rows 40 and 41, "SPEC ONLY"); the filter has its own hand table.
- The architecture allow-lists change deliberately: the run, the plan, the switch and the loss tag are the only Application areas that name a filings type (exact sets in `EventFilterArchitectureTests`), `Domain` has three such types, the simulation two.
- The snapshot read is one call per run; the per-decision check is a dictionary lookup plus `ResultsDays.Compute` over the handful of rows of one instrument.

## Known limits
- **Fail closed after a passed meeting (owner-accepted).** An instrument whose last meeting has passed and whose next meeting is not yet intimated is `unavailable` (`no_upcoming_entry`), never a guess from last year's date. With the filter on, the simulator and the plan therefore take an entry only between an intimation and its meeting. The plan basis and `GET /api/selection/event-filter` count these instruments apart from `no_entry` (`no_upcoming_entry_for_instruments`). **P15-10 must read protocol F with this in mind and must report the share of entries lost to `no_upcoming_entry`**; the simulator's `EventUnavailable` fate does not yet split the two reasons (the share is derived by P15-10 from the snapshot).
- Coverage is the owner's file coverage. An instrument without an entry is held by a required selection filter (the safe default), which can empty a plan; the basis prints the counts so the cause is visible. In a long window most past decisions can be `unavailable` (a meeting is known only from its own intimation), so a filtered run can take few entries.
- A meeting date is a lower bound for the broadcast (results may come later the same day or next); the window uses sessions, the loss tag prefers the filing's broadcast.
- Removing results-window trades removes the largest winners too (P15-00 risk 7); the 50 % review flag and the tail test are P15-10's. If protocol F says DROP the code stays and nothing turns it on.
- The plan is asked at the start of its India date when built the evening before: rows are those ingested by the build, so nothing later can be in them, but a row inside the last `lag` minutes counts as known.
- The execution service has no event check; the plan check warns the owner before the ticket exists.
