# 0147 — The compliance record is one insert-only, owner-written store for the static-IP, SEBI and Dhan read-policy enquiry

- **Status:** Accepted (decided in P11-05 under the owner's delegation of 2026-10-28; spec [P11-05](../specs/P11-05-static-ip-and-sebi-recheck-runbook.md)).
- **Date:** 2026-10-28.
- **Relation to other ADRs:** [0008](0008-broker-credentials-vault-and-connection.md) and [0009](0009-dhan-consent-flow-only.md) (Dhan consent flow), [0091](0091-auto-approval-is-an-option-behind-an-owner-setting-default-off-a-new-approval-kind-the-database-checks.md) and [0130](0130-the-owner-act-forms-are-endpoints-behind-a-capability-a-fresh-password-and-an-audit-row-over-the-existing-handlers-and-state-machines-and-apply-nothing.md) (the fresh-password owner act), [0135](0135-the-depth-recorder-stores-the-20-level-book-of-up-to-50-shares-about-once-a-second-behind-three-gates-a-disk-guard-and-no-reader.md) (an insert-only owner record with a deployment gate), doc 19 §5 and doc 01 Q6.

## Context
Whether P12 can start depends on facts outside the system: does the home line give a static public IPv4 that Dhan will whitelist, what the SEBI retail algo rules and the exchanges' circulars require of a personal self-built system, and whether Dhan's whitelist also limits today's read-only calls. The lead times (an ISP, Dhan's reply, a 7-day lock after an IP is set) are the owner's, and the P11 phase check needs something it can read. The circular texts were not opened when the runbook was written (nseindia.com timed out), so every fact is a vendor or broker summary.

## Decision
1. **One store, `trading.compliance_records`, insert-only** for the runtime role (`MakeAppendOnlyForAppRole`), with kinds `static_ip`, `sebi_recheck`, `dhan_ip_read_policy`, each with its own outcome set, checked in the Domain and again by the table. P12-11 and the P11 phase check read this table; nobody makes a second store. The latest record per kind (newest id) is the current answer; none for a kind is `empty`, never "no change".
2. **The record never holds an address, client id or token.** `summary` and `isp` are screened (IPv4, IPv6, a whole word of 7 to 12 digits, a whole word of 24 or more URL-safe characters); `sources[]` has its own pattern (an `https://` URL with a named host, or a circular id `(SEBI|NSE|BSE)/...`); dates are typed. The table cannot screen text, so the application is the barrier and the migration says so.
3. **The write is an owner act with two gates.** The deployment setting `Live:Writes:Enabled` (environment `Live__Writes__Enabled`, compose variable `XD_LIVE_WRITES_ENABLED`, default OFF) is asked first, so a closed gate neither counts toward the sign-in lockout nor says anything about the password (403 `live.capability_off`); then the owner's password typed again for this save (`Elevate: false`: no step-up window opened or used). The actor is built from the session. The setting is a deployment setting, not a database capability: the spec named an option, and it cannot be switched on from the app it guards. The audit event `ComplianceRecorded` carries the kind, the outcome and the decided date, never the text.
4. **The overdue notice is derived on read** and merged into the plan notices of the bell (kind `compliance_recheck_overdue`, route `/live?tab=compliance`, no command): one per kind whose newest record has a review date before today (India date). A newer record of the kind resolves it; a kind with no record has none.
5. **No outbound call.** The system sends nothing to Dhan, the ISP or any site; the runbook is the owner's. An architecture test pins that the compliance code has no HTTP client and no broker port.
6. **The runbook lives in `docs/research/p11-static-ip-and-sebi-runbook.md`**; every question and check has a "who answers" column, a why-line and a place for the answer with date and source; facts without a primary source are marked `UNVERIFIED`. A test reads the file.

## Amendments made while building (spec P11-05, "Amendments at build")
- `ComplianceView` carries `writesEnabled` so the screen can hold the New record button back and say why; the actor column is `varchar(100)` like the other owner tables (the spec said 64, which would refuse an owner with a long address); the list `limit` is 1 to 200 (default 50); `whitelistedAt` cannot follow `decidedOn`; the static-IP fields are refused on the other two kinds (also a table check); `lock_ends_on = whitelisted_at + 7` is a table check; a source URL must name a host (no IP literal, no user info).
- The Live screen did not exist (P11-04A is not built): this slice adds the route `/live`, a sidebar entry and the tab strip with the Compliance tab alone.

## Consequences
- The owner can write the three records once the answers arrive; until then every kind reads `empty` and the phase check's compliance criterion is NOT EVALUABLE.
- The 24-character token screen also refuses a hyphenated compound of 24 or more letters; the owner splits it with a space.
- Rejected: storing the IP (personal network data); a database capability for the gate (a switch inside the app it guards); an automated message to Dhan (the system sends nothing on the owner's behalf); only a markdown note (the phase check could not read it).
- Limit: the record is the owner's note. The system verifies nothing at Dhan or the ISP, and a static address does not protect against the router's address changing after a hardware swap.
