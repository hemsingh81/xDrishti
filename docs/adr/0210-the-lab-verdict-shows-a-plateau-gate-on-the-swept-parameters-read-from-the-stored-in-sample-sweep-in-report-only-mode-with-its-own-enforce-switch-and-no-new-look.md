# 0210 — The Lab verdict shows a plateau gate on the swept parameters, read from the stored in-sample sweep, in ReportOnly mode with its own Enforce switch and no new look

- **Status:** Proposed (built in CF-07 part C from the owner-Approved spec, 2026-11-03; the plateau gate only, see "What is not built"). Becomes Accepted when the owner has read it. **Safety slice: no** (research-side numbers; no order, no broker, no network, no simulation; with `Enforce` off the verdict outcome, the six gates and their reasons, the limits, the evidence, the run key and the keys of the stored runs are unchanged).
- **Date:** 2026-11-05.
- **Relation to other ADRs:** completes the CF-07 family of [0208](0208-the-lab-verdict-shows-a-random-entry-null-beside-the-sign-flip-in-report-only-mode-and-the-null-is-one-look-in-the-ledger-with-enforce-the-owners-switch.md) and [0209](0209-the-lab-verdict-shows-a-placebo-set-and-a-mirror-gate-beside-the-random-entry-null-in-report-only-mode-and-the-placebo-set-is-a-second-null-look-in-the-ledger.md) (same block, same mode rule, same development window), reads the sweep of [0062](0062-robustness-sensitivity-monte-carlo-by-year-and-a-sign-flip-baseline.md) (P5-05), and follows [0207](0207-a-strategy-version-is-pre-registered-the-ledger-counts-every-extra-look-and-a-locked-hold-out-is-fixed-at-the-first-post-and-read-once-by-an-owner-unlock-with-enforcement-and-the-honest-count-as-the-owners-switches.md) on what a look is and on the hold-out.

## Context
An edge that exists only at one value of a parameter and collapses one step either side is the optimiser's, not the market's (spec CF-07, D4). The robustness stage already runs a one-at-a-time sweep (each swept parameter at the declared value times 0.8, 0.9, 1.1 and 1.2, plain runs of the first candidate exit, costed, over the run's whole window) and stores for every point its trades and its mean net R, and judges each parameter `stable | fragile | no_base_edge | inconclusive` with a looser rule (every valid point above 0 and at least half the base) that decides nothing. Nothing tested the neighbourhood of the declared value against a stated share of the base, nor reported where the plateau is. The programme rule (CF-00) holds: a new test is report-only beside PASS/MARGINAL/FAIL until the owner turns an enforce setting on; `unavailable` is never a pass; the settings that produced a figure are stored with it.

## Decision
1. **It reads the stored sweep; nothing is simulated.** The sweep already stores, per point, the parameter, the value, the trades and the mean net R (or the engine's refusal), and the base run likewise. The only thing the stored sweep does not carry is the declared value of each parameter (the base point has no parameter), so `LabPlateau.Read` is given the strategy's declared parameters and the sweep schedule by the runner and nothing is added to the sweep's own document. `LabPlateau` depends on no port and no simulation (an architecture test).
2. **The gate** (`PlateauGate`, pure, Domain), for one swept parameter. The curve is the swept points plus the declared value (the base run), in value order. A point is valid when its run was not refused and has a finite mean net R. (a) the base must be above 0, else `no_base_edge` and a fail; (b) the two points next to the declared value in that order each keep at least `Retention` (0.70) of the base mean (`neighbour / base >= 0.70`, with a tolerance of 1e-9 so that 0.14 over 0.20, exactly 70 % in arithmetic, passes); (c) the median of the mean net R over all valid points of the parameter, the declared value included, is above 0. All three hold: `plateau`, pass. Otherwise `spike`, fail, and the reason names which of the three failed with the percentages. The criterion-7 numbers are unit tests (base 0.12 with 0.05, 0.10, 0.11, 0.04: 83.3 % and 91.7 %, median 0.10, pass; base 0.15 with neighbours 0.02: 13.3 %, fail; the research example 5/10/15/20/30 with 0.02/0.11/0.12/0.10/0.01: pass, centre 15, smoothed 0.1100 against 0.0833 at 10 and 0.0767 at 20).
3. **Unavailable is never a pass.** A parameter is `inconclusive` (status `unavailable`) when the base run has no result, when it has fewer than `MinPoints` (3) valid points counting the declared value, when the declared value has no swept point on one side (so the two adjacent points do not exist: a sweep with every step above or below 1), or when a point immediately next to the declared value gave no result (it ran no trade or the engine refused it). That last rule is deliberate: skipping a dead neighbour and judging the next one out would hide a cliff. The gate over all parameters passes only when every swept parameter passes; any fail makes it a fail; otherwise any unavailable parameter, or a strategy that sweeps no parameter, makes it `unavailable`. The settings `MinPoints` counts the declared value, so the least is the declared value and one point either side.
4. **The plateau centre is reported, not applied.** It is the value, among valid points that have two valid neighbours in the curve, maximizing the mean of its own mean net R and its two neighbours' (a tie goes to the lower value), with that smoothed mean. The declared value is never changed by this gate: moving to the centre is a new strategy version, a new pre-registration and a new trial.
5. **The window and the hold-out.** The sweep ran over the run's whole window (`template.To`). When that window reaches the hold-out block (an explicit window may; `LabHoldOutGuard.Cut` shortens only a default one), the stored sweep points depend on hold-out sessions, and the gate is `unavailable` with the reason, shows no parameter row, and reads none of those figures. When it does not (every default window, and an explicit one that ends before the block), the sweep is development-window data and is read as stored. No new type here names a hold-out type (an architecture test). The sweep itself is unchanged, so an explicit window that reaches the block still runs its sweep as it did before this ADR (this is the existing behaviour, now visible as the reason the gate is unavailable).
6. **No new look in the ledger.** CF-06 counts a look as a test run on the data that could be selected on (ADR 0207); the random-entry null and the placebo set are new walks, hence a ledger row each. The plateau gate runs nothing: every point it reads is a sweep point that already has its own ledger row (kind `sweep`, one per point, ADR 0062) and its own variant statistics. Reading the same points again with a stated rule does not add data looked at, so it adds no row and no `TrialCounts` input; the migration is not touched. If the owner later wants the gate itself counted as a trial (a test of 3 conditions on the same points), it is one more `null`-kind row beside the two; that is a decision of the count, not of this slice.
7. **Modes, settings and Enforce.** `Confidence:Plateau`: `Mode` (Off or ReportOnly, default ReportOnly; Gate is not a mode), `Enforce` (default false), `Retention` (default 0.70; 0.50 to 0.95), `MinPoints` (default 3; 3 to 5, because a sweep has at most four steps and the declared value). `Enforce` with `Mode` Off stops the host at start, as the nulls do. The spec (D5) names a switch of its own for the plateau (`confidence.plateau.enforce`) beside `confidence.nulls.enforce`, so it is **not** folded into the nulls' Enforce: `LabPlateau.Apply` caps a PASS at MARGINAL when its own `Enforce` is on and the gate is a fail or unavailable, adds the limit "capped at MARGINAL by the plateau gate (fail) (enforced)", sets `Capped` in the plateau member, and never raises or changes a MARGINAL or FAIL and never touches the six gates. Both switches cap at the same level, so with both on a PASS becomes MARGINAL once (the second sees a MARGINAL and leaves it). The text and SHA-256 hash of the values are stored with the member.
8. **Where it lives.** The member `plateau` of the `nulls` block (spec, Contract), computed by the runner inside the nulls stage (no stage of its own, no progress steps) from the robustness block just produced. Because it is a member of that block it is computed only when `Confidence:Nulls:Mode` is not Off; with the nulls off there is no block and no plateau, and `Plateau:Enforce` with `Nulls:Mode` Off stops the host at start (an enforcing switch with nothing computed). A plain full run has no sweep and no block, as before.
9. **API and report.** `nulls.plateau`: `mode`, `enforce`, `settings`, `settingsHash`, `retention` (the threshold), `minPoints`, `comparison` (`>=`), `status`, `reason`, `capped`, `basis` and `parameters` (`param`, `declared`, `validPoints`, `baseMeanR`, `lowerValue`, `lowerRetention`, `upperValue`, `upperRetention`, `median`, `centreValue`, `centreMeanR`, `reading`, `status`, `reason`, `points`: `value`, `declared`, `trades`, `meanR`, `retention`, `error`), null in a document stored before it or with `Mode` Off. The sensitivity label now reads "in-sample sweep, one parameter at a time, ..." and the plateau `basis` says "in-sample sweep"; the report warns `plateau` on a fail or an unavailable gate (naming the parameters that failed, and "report only" unless enforced), lists the basis among the honest limits, and the HTML report gains "Chance: plateau (in-sample sweep)". The contract is regenerated (`scripts/gen-api.sh`); the Lab screen does not read the new member, so no frontend code was added.

## What is not built
- **The Lab screen block** "Chance and plateau" (React): the member is in the contract and the report; the always-loaded bundle has 1.0 KB of headroom, so the block waits for a lazy-loaded screen.
- **The `nulls` and `draws` fields of `POST /api/lab/runs`.**
- **Swing strategies and exits other than a fixed target** in the random-entry null and the placebo walk.
- **The instrument-roll basket question** (ADR 0209): rolls go over the instruments that have an out-of-sample trade, not the universe.
- **A minimum number of trades per sweep point.** The spec asks for none; a point with a handful of trades is valid here, and its trade count is shown in the row. The plateau is read on the first candidate exit only, in-sample, one parameter at a time: interactions between parameters are not seen.

## Open owner questions
1. Is 70 % retention the bar, and should a sweep point with few trades count? 2. Should a dead neighbour (no trade) be a fail instead of unavailable? (It is unavailable now, which is a miss for any consumer.) 3. Should the plateau gate be counted as a look in the ledger? 4. When `Plateau:Enforce` goes on (an owner act).

## Consequences
Robust runs gain one pure computation over data already in memory: no walk, no ledger row, no new stage. A fresh install shows the gate, which reads `unavailable` for any strategy that sweeps no parameter or whose neighbours of the declared value ran no trade, and reads a pass or a fail otherwise. Because the sweep is in-sample over the whole window the gate says something about the shape of the optimum, not about out-of-sample performance, and it is labelled so. With every default (`Enforce` off) the stored verdict differs from the old one only by the new member and the new words of the sensitivity label.
