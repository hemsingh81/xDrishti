# 0233 — A same-time-of-day relative volume feature (`rel_volume_tod`) and an owner-invoked, bounded repair of old bar holes that is off by default; the budget guard stays opt-in and the rising/falling lint stays deferred

- **Status:** Proposed (built 2026-11-09 as the small open issues ISS-23 and ISS-29, with decisions on ISS-16 and ISS-26). Decided under the owner's delegation (research, validated setting with the best default, log in the ADR); approved-by-delegation, becomes Accepted when the owner has read it. **Safety slice: no** (no order, no switch; the repair writes only bars that were missing and is off by default).
- **Date:** 2026-11-09.
- **Spec:** none separate. The slice is approved by delegation from the owner's 2026-11-08 instruction (small open issues, research, best default, log in an ADR); this ADR is the record.
- **Relation to other ADRs:** adds one name to the catalog of [0031](0031-streaming-indicators-and-the-feature-frame.md) and the rules language of [0034](0034-the-rules-expression-language-lint-and-compiler.md); uses the gap vocabulary of [0017](0017-trading-calendar-eod-schedule-quality-adjustments-and-csv-undo.md) and the allowed Dhan Data API read of [0016](0016-market-bars-csv-load-dhan-fetch-and-app-managed-aggregates.md) (no new endpoint); records decisions on ISS-12's leftovers (ISS-16) and on [0037](0037-simulation-conventions-and-the-two-stage-seam.md) Amendment 1 (ISS-26).

## Context
- **ISS-23.** `rel_volume(n)` divides by the previous n bars of the timeframe, so on 15m the 09:30 bar meets yesterday's afternoon bars, while doc 07 promises a same-time-of-day measure. Changing `rel_volume` would change every strategy that uses it (ORB, BASE_BREAKOUT) and their run keys.
- **ISS-29.** The gap backfill looks only `Data:Gaps:LookbackSessions` (at most 250) back, so a 2024 hole (KALYANKJIL 2024-04-23, 10:52 to 10:57) cannot be repaired. The row also named a flaky frontend test.
- **ISS-16 and ISS-26** were open decisions (a guard for timing budgets; a lint for `rising`/`falling` runs).

## Decision
1. **`rel_volume_tod(n)` is a new catalog name; `rel_volume(n)` is not touched.** Volume divided by the mean volume of the bars at the same time of day (the same start minute) in the previous `n` sessions; the current bar is never in the mean, nothing after it is read. `n` is a whole number of sessions, 1 to 250, default 20 (the usual best practice of 20 sessions, the same default as `rel_volume`; 250 bounds the memory, 375 slots of 8 bytes per session at 1m). Intraday timeframes only (1m to 1h; refused on 1D, 1W, 1M, where `rel_volume` over days is already the same-time-of-day measure). Continuous: a lag may reach into the day before, since each value is defined by the time of day. **Unavailable (NaN, so never true) until `n` sessions have been seen at that time of day**, for a bar outside 09:15 to 15:30, and while the mean is 0; first ready bar is `n * barsPerSession + 1`. A missing bar of a session is skipped and the ring reaches one session further back (stated, tested). A session is the calendar date\'s occurrence of the slot, not a calendar lookup: a short session (a Saturday special session, a Muhurat session) fills only the slots it has, and a bar outside 09:15 to 15:30 is not ready and not remembered (a stated shortcut). Volumes are whole numbers, so the sums are exact; the step allocates nothing. Mirror: same row as `rel_volume` (direction-neutral); the mirror table is pinned again with its version left at `mirror-1` because no existing row changed (a new name only; a run that does not use it has the same key and result). A strategy that does not use the name is byte-identical. The compiler warm-up reads it once.
2. **The repair of old bar holes: `POST /api/data/instruments/{id}/repair-holes` with `{from, to}`.** Owner-invoked only (a session, the CSRF token and a **step-up** are needed, because the write has no undo and changes evidence hashes; nothing schedules it, no service calls it). **Off by default:** `Data:Repair:MaxSessions` is 0, validated 0 to 60; a positive value is both the switch and the bound (409 `data.repair_disabled` while 0). The window must be closed trading sessions, reversed or open windows or more sessions than the setting are 400 `data.invalid`. The handler counts the missing minutes of the window per the trading calendar, asks the **existing** Dhan Data API read (the same `IIntradayBarSource` port, windows of at most 90 days, only for the days with holes), and stores **only the minutes that are missing**. The merge is **insert-only** (a new store method: a staged bar for a minute that has a stored one is dropped, never updated), and the whole read, fetch and merge **holds the one data-job slot** (a data job with the step `dhan` is registered for it, ended when done): another job running, or a second submit, is 409 `data.job_running`, so no other writer can race it. Bars that fail the bar checks are counted (`rejected`) and not stored; a store failure is a result (`data.repair_store_failed`), nothing is changed. Each repair is **audited** (account event `BarHolesRepaired`: actor, instrument, window, missing and inserted counts) and logged. **Repaired bars change the bars hash of the window: stored runs stay intact but stop being reproducible from the bars, and their trade cards fail the BarsSha256 check; a re-run gets a new key.** The gap records (`market.bar_gaps`) are not updated by the repair: the next gap pass inside the lookback re-counts, an older record stays as it was. Minutes the broker does not return stay missing and are reported (`missingAfter`). When bars were added, a data job with the steps `aggregate` and `quality` for that instrument is started (its id is returned, or none while another job runs; the repair does not fail for that). No order, no new external endpoint, no token in the answer or the log. Why a setting of 60 as the upper bound: one window is at most 90 calendar days, so the repair stays at a few requests; a longer stretch is several calls.
3. **The flaky frontend test (ISS-29's second half) is not reproduced and needs no change.** `/api/live/status` has been in the default handlers of `frontend/src/test/server.ts` since P2-10a, and `test/setup.ts` already records any request that escapes the mock and fails the test with its URL; `AddTrade.test.tsx` passes (22 of 22). If it shows up again the setup names the URL.
4. **ISS-16: no timing assertion in the gate; the budgets stay in the explicit benchmarks and the opt-in scripts.** A wall-clock budget (1 µs a step, 3 ms a compile, 20 ms the first compile) fails on a loaded machine and the gate must not flake (the project already carries this lesson); an allocation count is stable and already guards the zero-allocation claim of the frame, the evaluation and, since this ADR, `rel_volume_tod` (the allocation test lists it). The timing budgets are run before a release on a quiet machine (`scripts/bench-coldstart.sh`, the explicit benchmarks, engineering README section 3). The open minor findings (the 20 ms bound is six times the measured value; the warm-up does not cover the first `Step`) stay recorded in ISS-16, which remains **Open (accepted gap, opt-in script)**.
5. **ISS-26 stays deferred.** The trigger (a built strategy with a `rising`/`falling` run, or a sweep over its count) is not met: no built-in strategy (the fifteen in `Seed/Strategies`) writes `rising` or `falling`, and the 28 to 37 percent non-frame share of ORB and VWAP_PULLBACK does not measure such a run. No lint was built; the row records the check of 2026-11-09 and the trigger stays as written.

## Consequences
Catalog 60 to 61 names (45 non-date-driven); `GET` surfaces that list the catalog (the grammar sheet) show the new name by themselves. New setting `Data:Repair:MaxSessions`, new error codes `data.repair_disabled` and `data.repair_fetch_failed`, one endpoint (`scripts/gen-api.sh` regenerated). Docs: doc 07 section 5 (the Volume row) and doc 11 (the rolling table), roadmap rows ISS-16, ISS-23, ISS-26, ISS-29.

## Not built
A repair that overwrites a stored bar that differs from the broker's; a scheduled or automatic repair; a repair across several instruments at once; a Data screen button (the endpoint is for the owner's CLI or API client); a timing assertion in the gate; the `rising`/`falling` cost lint.
