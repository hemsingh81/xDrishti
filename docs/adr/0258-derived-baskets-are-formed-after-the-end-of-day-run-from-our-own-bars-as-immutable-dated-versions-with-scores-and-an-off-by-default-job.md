# 0258 — Derived baskets are formed after the end-of-day run from our own bars as immutable dated versions with scores, by an off-by-default job

- **Status:** Accepted (spec BK-03, approved by the owner 2026-11-03). **Safety slice: YES** (a scheduled job that writes rows; no network, no order, no trading configuration touched).
- **Date:** 2026-11-11.
- **Relation to other ADRs:** [0255](0255-derived-baskets-are-pure-versioned-and-point-in-time.md) (the engine this job calls), [0254](0254-index-baskets-are-stored-read-only-system-baskets-fed-by-an-off-by-default-guarded-fetch-of-nse-index-lists-with-forward-only-dated-membership.md) (stored system baskets, dated membership, `baskets.system`), [0240](0240-missed-days-are-recovered-by-one-dependency-ordered-pass-and-each-service-declares-how-it-can-be-recovered.md) (recovery class `LatestOnly`).

## Context
The fourteen derived baskets of ADR 0255 are pure functions. Something has to feed them our own bars after the end-of-day aggregation, store what they answer so that a simulation or report can read exactly what was published on any past date, and do it without ever reaching the network or an order.

## Decision
1. **One job, off by default.** The service `derived-baskets` (`Schedule.AfterService("eod")`, `MustFollow = ["eod"]`, `LatestOnly`, starts paused) carries out `RefreshDerivedBasketsCommand`. `Baskets:System:Derived:Enabled` defaults **false**: the handler returns `baskets.derived_disabled` before it asks the calendar, the bars or the store anything, and the run ends as `skipped: disabled`. A run takes a database advisory lock (`baskets.derived_running` 409 for refresh-now; the scheduled run ends as skipped). Each basket has its own switch in `market.derived_definitions` (all **off**); a missed run is not replayed, the next one forms the then-latest version.
2. **A version is a dated, immutable record.** `market.basket_versions` holds `as_of` (the last closed session), `effective_from` (the **next session from the trading calendar**, never a fixed weekday offset), the parameters and their SHA-256, `universe_size`, `member_count`, `below_threshold`, the named exclusions as json and the provenance (`derived` live, `recomputed` backfilled). `market.basket_member_scores` holds `(instrument, score, rank)` for the members and the next 20 non-members by rank (setting `ScoresKeptBeyondMembers`), plus `is_member` and `sessions_held`, so the next run's buffer and dwell take their incumbents from the previous version and the UI can say why. Both tables and the parameter sets are **insert-only** for the runtime role. The unique index `(basket_id, as_of, params_hash, coalesce(formed_at, '-infinity'))` makes a second run for the same date and parameters write nothing (`unchanged`).
3. **Members are ordinary dated `basket_members` rows** (`provenance = derived`, `source_kind = 'version'`, `source_ref` = the version): `valid_from` is the start of the India date of `effective_from`, and leavers get `valid_to` = that same start, so `members(asOf)` works unchanged (a row with `valid_to = D` is not a member on D). One transaction per version writes the version, the scores, the closes, the opens, the basket's revision and the audit event `BasketMembershipChanged` (counts only): a failure leaves no partial version and the previous membership stays served. No approval is requested (informational).
4. **Same effective date, new parameters.** The newer version wins: the older version's open rows for that date are closed with zero length (`valid_to = valid_from`) and the older version stays readable. A version is never written behind a newer published one (the run reports `behind_published_version`).
5. **Universe `U(D)` is read from our own bars on D**, retired instruments with a bar that day included, never from today's tracked set: one query for the whole window, shared by every basket of a run. Prices are the applied corporate actions' adjustments (an action on or before the date the owner's CSV files reach is not applied twice); an unresolved suggestion in the window marks the instrument `corporate_action_unresolved`. The Nifty 50 for baskets 5 and 14 comes from the context source.
6. **Parameters are owner data.** `PUT /api/baskets/system/derived/{id}/params` (step-up) stores a **new immutable parameter set** (never an edit), validated by `DerivedParams` ranges, selects it, and can switch the basket; the audit event `DerivedBasketChanged` carries the old and new hash and the setting snapshot. A basket this build cannot form cannot be switched on (`baskets.invalid`): **13** (needs BK-05's dated ban and ASM/GSM lists: a missing flag is not a pass) and the intraday **4** and **12**.
7. **Backfill is an owner act** (`POST /api/baskets/system/derived/backfill`, step-up): one `recomputed` version per due date of a closed range from bars cut at each date, with **closed** windows (the last ends where the next due version would take effect). Only a range that ends before the first published (`derived`) version, at most `MaxBackfillDays` (400) trading days, and never over an existing version (`baskets.backfill_overlap` 409, existing dates counted as already there). The answer states that adjustments are today's restated series.

## Consequences
- The refresh reads 260 daily bars of every share once per run (not per basket) and the engine does the rest; no instrument list is logged (`basket.derived`, block 3520: counts and outcome only).
- Versions are kept for ever (the point-in-time record); about 420 000 score rows a year.
- A version written after the close of D takes effect on D+1: the night's plan still expands the previous members (noted in the spec's review, not changed here).

## Known limits
- **No live 1-minute bar hook exists** (`bars_1m_live` is not built), so the 09:20 and 09:30 intraday freezes (acceptance criterion 6) are **not built**: baskets 4 and 12 are never due here and cannot be switched on. Owner question in the spec review.
- Basket 13 stays disabled until BK-05 supplies the flags.
- The settings `DailyRunAfter` (an event, not a clock) and `IntradayFreezeTimes` of the spec have no key: the first is the `after eod` schedule, the second belongs to the unbuilt freeze.
- **shortcut:** the backfill runs inside the request (a bounded number of evaluations of one basket) and answers 202 with the finished run, not a run id to poll; the services framework has no parameterised manual run. It holds the run lock meanwhile, so a scheduled run meeting it **fails** (not skips) and the service's three retries form the day's version once the lock is free; only a manual refresh is skipped.
- A backfill over dates that already hold `recomputed` versions under another parameter hash is refused (`baskets.backfill_overlap`); the same hash skips existing dates and seeds the buffer from the stored version before them. Dates with no universe are counted in the answer.
- Basket 14's cluster number is stored in the member's `score` column (members only) to rebuild the previous clustering for the stability figure.
- Refresh now forms only baskets that are due on the as_of (a weekly or monthly basket is not formed on another day); the manual flag only names the actor.
- `PUT .../params` writes owner data (parameter sets, the switch) even while `Baskets:System:Derived:Enabled` is off; nothing runs until the setting is on.
- Backfilled versions are `recomputed`: retroactively restated adjustments make them differ slightly from what was knowable on the date.
