# 0184 — The results XBRL parser reads untrusted files through one hardened reader, stores facts per span and basis with `unavailable` for every field the file does not carry, and is labelled synthetic until real filings pass

- **Status:** Proposed (built in P15-03 from the owner-Approved spec, 2026-11-02). Becomes Accepted when the owner has read it. Safety slice: no (local files and its own tables; no network, no broker, no order, no decision reader). The parser does read untrusted XML, so it is built as a security-sensitive parser.
- **Date:** 2026-11-02.
- **Relation to other ADRs:** [0179](0179-filings-come-from-a-local-inbox-folder-with-a-sidecar-that-carries-the-broadcast-time-the-adapter-is-read-only-and-the-public-page-fetcher-is-a-recorded-decision-not-to-build.md) (files are untrusted, no fetcher), [0180](0180-the-point-in-time-filing-store-keeps-immutable-envelopes-and-answers-what-was-known-at-an-instant-from-the-broadcast-time-plus-a-lag-and-nothing-else.md) (the store, the supersede chain, the visibility rule and its "consolidated and standalone are for P15-03" limit), P15-00 decisions D3 (point in time) and D4 (XBRL is the source of truth for numbers).

## Context
P15-05 needs reported revenue, profit and EPS per quarter, year to date and year, for each basis, as the market could have known them. The numbers come from the exchange XBRL file the owner stored (P15-02). Three things can go wrong silently: a hostile or broken file hurting the process, a number guessed where the file is silent, and a restatement of one basis hiding the other.

## Decision
1. **One hardened reader.** `SafeXml.Create` is the only place an `XmlReader` is made for a filing (an architecture test pins `XmlReader.Create` to that file and bans `XmlDocument`, `XDocument.Load`, resolvers and DTD-parsing modes in the shipped source): `DtdProcessing.Prohibit`, `XmlResolver = null`, `MaxCharactersFromEntities = 0` (moot with the DTD prohibited), comments and processing instructions dropped, `MaxCharactersInDocument` bounded. Around it (`XbrlFileReader`): the file is read up to `Filings:MaxFileMb` (20) and refused above it (`too_large`), bytes that are not valid UTF-8 are `invalid_encoding`, an empty file `empty`, any `<!DOCTYPE` or `<!ENTITY` is `dtd_prohibited` before an XML reader sees the bytes, an `xsi:schemaLocation` attribute is `external_reference` (a `link:schemaRef` is read past and never fetched), more than 64 levels `too_deep`, more than 200,000 elements `too_many_elements`, anything else that is not well-formed `not_xml`. Every refusal is a `rejected` parse row with that closed reason and no fact. Tests point every external reference at a local listener and assert it was never contacted.
2. **A pure parser.** `ResultsXbrlParser` (Domain) reads an `XmlReader` it is given and creates none; it is the same code for the tests and the service. A fact is read as filed: no scaling, no rounding, no correction. Facts are matched by element local name in the versioned `ResultsTaxonomyMap`; unlisted elements are not read.
3. **Rules.** Fields: `revenue`, `total_income`, `pbt`, `pat` (profit attributable to owners, else profit for the period, counted in the parse flags as `pat_from_profit_for_period`), `eps_basic`, `eps_diluted`, `exceptional_items`, and `audited` (unit `flag`, 1 or 0). Span from the context period: 80 to 100 days ending on the envelope's period end is `q`; from 1 April and longer than 100 days is `ytd`, or `fy` at 355 to 375 days; an instant, another end date or any other duration is skipped and counted `unknown_span`. Basis from a basis-axis member of the context, else the file's `NatureOfReportStandaloneConsolidated` marker; any other dimension (a segment) skips the fact (`dimension_skipped`). Units: `iso4217:INR` (`inr`), INR per `xbrli:shares` (`inr_per_share`); anything else is `unit_unknown`. Two different values for one field, span and basis are `conflicting_facts`; a text that is not a number is `bad_value`. For every (span, basis) seen in a file, all eight fields are stored; a field the file does not carry is `unavailable/not_in_file`. Sanity checks (`revenue > total_income`, EPS sign against the profit sign, basic EPS below diluted EPS for a profit) only count flags.
4. **Honest gaps instead of guesses.** (a) A stated rounding level other than actual/absolute/rupees (lakhs, crores, thousands) makes every money fact `unavailable/scale_unknown`; EPS is unaffected. Scaling is applied only when real fixtures show how values are scaled (spec rule), and not before. (b) A file with no readable basis marker stores no fact and its parse row is `no_facts/basis_unknown` (the fact table's basis column is closed to `consolidated` and `standalone`). (c) A file in a banking namespace stores no fact and its parse row is `no_facts/format_not_supported` until a bank filing is supplied. (d) A results envelope with no period is `no_facts/no_period`.
5. **Version label.** `ResultsParser.Version` is `xbrl-1-synthetic`. It becomes `xbrl-1` only after the owner's five real filings (with the PDFs for the hand values) pass criterion 1. Every row carries the version; a consumer reading facts passes it on, so P15-10 reports `fu-1` NOT_EVALUABLE "parser not checked against real filings" until the version is `xbrl-1`. The element names in the map are a starting list, UNVERIFIED against the real taxonomy.
6. **Tables (`ReshapeResultFacts`).** The P15-02 `filings.result_facts` was never written (a test pinned that). The migration first raises, changing nothing, when it has a row; then replaces it with `(filing_id, parser_version, field_code, span in q|ytd|fy, basis in consolidated|standalone, value, unit, state, unavailable_reason)`, primary key on all of the first five, `state = 'value'` exactly when `value` is set and a reason exactly when unavailable, and a foreign key to the parse row of the same version; and creates `filings.result_parses(filing_id, parser_version, outcome in parsed|rejected|not_xbrl|no_facts, reason, facts, flags jsonb, parsed_at)`. Both are insert-only for `xd_app` (`GrantTableToAppRole` + `MakeAppendOnlyForAppRole` per table); `xd_exec` and the read-only roles get nothing. `Down` restores the P15-02 shape and also refuses when either new table has a row. A later parser version adds its own rows beside the old ones.
7. **The parse step.** `ParseResultsHandler` (one use case, the only writer of both tables through `IResultFactsStore`) runs at the end of every `filings-ingest` run: each results envelope (dated or not) without a parse row for the current version is opened with the new read-only `IFilingFiles.OpenAsync` (hash checked first: a changed file is `content_changed`, a missing one `unreadable`; both are failures left for the next run) and parsed; a name that is not `.xml` or `.xbrl` is recorded `not_xbrl` and never opened. One filing is one transaction (the parse row, then its facts, `ON CONFLICT DO NOTHING`), so a crash leaves no half set; a second run parses nothing. A failure marks the run failed and stops no other step. Logs (`filings.parsed|parse_rejected|parse_flags|parse_failed`) carry counts, ids and codes only.
8. **Reading at an instant.** `IResultFactsAsOf.Facts(instrument, t)` takes the results envelopes visible at `t` by the ADR 0180 rule (lag included). For each (period end, span, basis) the facts come from the visible envelope with the latest broadcast time that carries that span and that basis (ties to the lower id). So a consolidated file chained as a revision of a standalone file by P15-02 hides nothing of the standalone facts, and a restatement replaces only what it restates, from its own time. The answer per field is `{state, value?, unit, reason?, filingId, broadcastTs}`; a field never seen is `unavailable/not_in_file`, never zero; an undated envelope's facts are never returned (counted). The granularity is the span and the basis, not the basis alone, so a restatement that carries only a quarter does not blank the year-to-date facts of an earlier file.
9. **API.** `GET /api/filings/{id}/facts` returns the parse outcome, the parser version, the stored facts and the parser's counts and sanity flags (`not_parsed` before the step has run); 404 `filings.not_found`; no file content and no path.
10. **No decision use.** `IResultFactsAsOf` is named only by its implementation and the registration; `IResultFactsStore` and `IResultsXbrlReader` only by `ParseResultsHandler`; no decision layer, pure library or the execution service references it. The P15-02 write allow-list names `ResultFactsStore` as the only writer of `result_facts` and `result_parses`.

## Consequences
- P15-05 can read per-basis facts as of an instant and must carry the parser version.
- Real fixtures may change the map, the basis marker, the scaling rule and the banking format; each is an ADR amendment and a new parser version, not an edit of old rows.
- The parse step adds one query per run (envelopes without a parse row) and one file read per new filing.

## Known limits
- Without the owner's five real filings the mapping is a guess and the version says so.
- An `xsi:schemaLocation` attribute is refused even though a real file might carry one; if real files do, the rule moves to "ignored, never fetched" with a new parser version.
- The text of a mapped element is kept only up to 64 KB (a longer one is `bad_value`); the XML reader itself still builds a text node whole, so one huge text node is bounded only by the 20 MB file cap.
- The 50 MB memory bound is measured and tested for the hostile files (all refused before any expansion). A good file of the full 20 MB holds its bytes (about 20 MB) plus the reader's text nodes; a text-heavy file of that size allocated about 150 MB in total (churn, not live memory) in a measurement, so the bound for a good file is the file cap, not 50 MB.
- File-level outcomes (`no_facts` for a bank file or an unreadable basis, `rejected`, `not_xbrl`) carry no fact rows. A newer such envelope therefore does not hide an older filing's numbers, and a field it would have carried reads as `unavailable/not_in_file` or as the older filing's value. The reason is on the parse row and `GET /api/filings/{id}/facts`, not in `IResultFactsAsOf`.
- Banking detection is by namespace (any namespace containing "bank"): broad, and safe (it only withholds facts). Revisit with real fixtures.
- The answer carries the parser version it was read for (`ResultFactsAnswer.ParserVersion`).
- A restated number is a new row from a new envelope; a parser fix is a new version beside the old rows, never an in-place change.

## Deviations from the spec
1. A file with no readable basis is file-level: parse row `no_facts/basis_unknown`, no fact rows (the basis column is closed to `consolidated` and `standalone`).
2. The banking format is file-level: parse row `no_facts/format_not_supported`, no fact rows.
3. The `pat` fallback to "profit for the period" is a parse flag (`pat_from_profit_for_period`), because a reason may exist only on an unavailable fact.
4. A stored file that cannot be opened (`content_changed`, `unreadable`) is a counted failure retried on the next run; nothing is stored for it.
5. The per-basis read is per (period, span, basis), not per basis alone.
6. A stated rounding level other than actual/rupees makes money facts `scale_unknown`; new closed reasons `empty`, `external_reference`, `nothing_mapped`, `no_period`; any name other than `.xml`/`.xbrl` is `not_xbrl`.
