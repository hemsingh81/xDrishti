# 0141 — A strategy draft is text the model wrote for the owner to read: the Lab validator and four checks decide whether it is offered, and only the owner's confirm, with a switch and a fresh password, stores a version or starts a quick test

- **Status:** Proposed (written in P9-07 under the owner's delegation of 2026-10-26; the spec was treated as Approved). Becomes Accepted when the owner has read it. **SAFETY decision: it decides what a model may cause in the strategy library and the Lab.** Built as slice 07a (core, job, confirm, panel) and slice 07b (chat tool `lab_propose_run`, auto option, CLI verb `xd assistant draft`).
- **Date:** 2026-10-27.
- **Relation to other ADRs:** [0057](0057-the-lab-api-validate-store-and-read-strategy-versions.md) and [0058](0058-lab-runs-the-quick-test-the-run-identity-and-the-restart-rule.md) (the Lab API and runs it uses), [0137](0137-the-assistants-tools-run-in-a-separate-read-only-server-under-two-database-roles-that-can-select-only-from-reviewed-views-and-the-switch-lives-in-the-database.md) and [0138](0138-the-assistant-endpoint-runs-the-tool-loop-in-the-application-streams-events-marks-figures-not-found-in-the-tool-results-and-stores-every-turn-insert-only.md) (the settings row and the owner's settings act), [0140](0140-the-briefing-text-is-phrased-by-the-model-from-app-built-facts-and-a-deterministic-guard-rejects-any-figure-symbol-or-claim-it-cannot-verify-the-fixed-format-text-is-the-fallback.md) (the same pattern of model text, deterministic checks, insert-only audit), [0128](0128-owner-act-capabilities-are-one-insert-only-log-with-a-generic-gate-by-name-off-by-default-and-switched-on-only-by-the-owner-with-a-fresh-password.md) and [0130](0130-the-owner-act-forms-are-endpoints-behind-a-capability-a-fresh-password-and-an-audit-row-over-the-existing-handlers-and-state-machines-and-apply-nothing.md) (fresh password per act).

## Context
The owner types a trading idea in English and wants a candidate strategy file. The library is immutable and every stored version enters the Lab's trial ledger, which tightens the gates for the whole family; a flood of stored guesses would harm the gates. A model is good at writing a first draft and bad at keeping numbers; it must never be the one who stores or runs anything.

## Decision
1. **The model's job ends at text.** It produces a JSON answer (decline or a YAML text, what it understood, the values it chose itself, what the language cannot say, the test the idea asked for). The Lab validator (`IStrategyChecker`) and the checks decide whether the text is offered. Nothing is stored as a strategy and no Lab job starts without the owner's confirm. The draft tools of the model are no write tools: `doc 14 §3` "no write tools except `lab_run`" becomes "no write tools"; `lab_run` is not offered to the model (P9-00 D9).
2. **Two entrances, one core.** The dedicated job (built) calls the model with no tools; the chat tool (slice 07b) would call the same core, `SubmitDraftHandler` (validator, then checks C3 to C6; it references no model port and no store).
3. **Checks.** C3 each assumption's YAML path exists with the stated value; C4 no `version`, an id of the right shape, at most four params; C5 every number in the explanation is in the idea or the text; C6 every number or clock time of the idea is in the text, in the requested test or in `not_expressed`. A finding is a repair reason; a text the validator accepts is `valid` even with findings, which are shown to the owner (so a clever check can never hide a valid text, and a bad one is never silent). Numbers are read by `DraftIdea` (a ratio such as 1:2 is matched by its second part; years and the 15 of "15-min" count).
4. **Repairs.** At most `MaxRepairs` (2) repair turns carrying only the located problems, finding codes and the failing text. The idea is data in a fenced block of the user message, never in the system prompt.
5. **Confirm.** The owner's confirm needs the session, the CSRF token, the switch `ai.settings.allow_draft_confirm` (asked first, so a switched-off act neither counts toward the sign-in lockout nor says anything about the password) and **the owner's fresh password on every call** (`OwnerAct.AuthorizeAsync`, `Elevate:false`; the step-up window is not used). The actor is the session's `owner:` identity, never a body field. The handler re-validates the text actually sent, refuses a taken id (`assistant.draft_id_taken`), requires the owner to pick exactly one of a basket and a list of symbols for the quick test (the idea's own window and baskets are text only), stores a normal version with the note `Assistant draft <id>; confirmed by owner`, starts a **quick** test only, and writes the one decision row. A second confirm returns the first result. Only `ConfirmDraftHandler` in the drafting namespace references `CreateStrategyCommand` and `StartLabRunCommand` (an architecture test).
6. **Discard** is a decision row; free of the password (the safe direction).
7. **Switches.** `Assistant:Drafts:Enabled` (false) and `ai.settings.enabled`; `allow_draft_confirm` false. Migration `AddAiWriteSwitches` adds four booleans to `ai.settings` (`allow_draft_confirm`, `auto_lab_quick_test`, `allow_proposal_accept`, `auto_accept_hypothesis`, all false; the last three are for slice 07b and P9-08) and replaces the `snapshot_hash` trigger: a row with all four false keeps the v1 text (old rows verify), a row with any true adds all four to the hashed text. Turning any of them on raises exposure (a fresh password); turning off is free. The settings endpoint takes four optional fields (absent = unchanged).
8. **Storage.** `ai.strategy_drafts` (one row per finished job, written once, id reserved at start) and `ai.strategy_draft_decisions` (one per draft, unique), insert-only for `xd_app`. The decision row already has `auto`, `settings_id`, `snapshot_hash` and a check that an auto decision is `system:auto-draft` with a snapshot, for slice 07b. A job in progress is held in memory; a crash loses it.
9. **Limits.** One model job at a time (the chat turn gate), `MaxPerDay` 20 per India date, an idea of 10 to 2,000 characters without control characters, a job timeout (default 360 s) ends `failed/timeout`; a model that is down or not ready ends `failed/model_unavailable`; an answer that never fits the schema ends `failed/answer_shape`.
10. **Quick test summary.** Counts and the run's own labels; no win rate, expectancy or verdict (a quick test is exploration).
11. **Log events** 6170 to 6178: ids, counts, codes, milliseconds; never the idea or the text.
12. **The chat tool (07b).** `lab_propose_run` is a local function in the turn loop (the tool server has no write code). Its arguments are the answer schema (YAML and the explanation fields); there is no idea argument: the server stores the owner's latest message of the turn verbatim. It calls the same core, stores one insert-only draft (`via = 'chat_tool'`) and answers `{draftId, status, problems, findings}` so the model can repair within its call budget. It is offered only in the owner's own chat turn (never eval, job or another actor) while drafting and the assistant are on, counts against `MaxPerDay`, and cannot reach the library or the Lab (architecture test). A chat-tool draft is never an auto candidate.
13. **The auto option (07b).** `ai.settings.auto_lab_quick_test` (false) is turned on only by the owner's `PUT /api/assistant/settings` with a fresh password; the other two inert switches stay refused (`assistant.setting_not_available`). `AutoDraftHandler` runs after a job's valid draft and acts only when: drafting and the assistant are on; the draft is from the dedicated job on an idea typed by an `owner:` session (a draft of the CLI or the chat tool never); it is valid with no finding and has no decision; the idea names exactly one existing, unarchived basket by exact name (case-sensitive, not inside a longer word); its id is free; fewer than 1 auto decision in the last hour and 3 on the India date (counted from the decision rows under the confirm lock, so concurrent drafts cannot pass together). It stores the text with the note `auto-confirmed`, starts a QUICK test only, and records the decision with `auto = true`, the settings row id and its `snapshot_hash`, actor `system:auto-draft`. A basket list that cannot be read is no pass; a quick test that cannot start is recorded with its code. It has no order port and places none.
14. **The CLI verb (07b).** `xd assistant draft "<idea>" [--show]` (actor `cli:xd`, draft only, waits for the job, no confirm option).

## Consequences
- Added: Domain `Assistant/Drafting`, Application `Ai/Drafting`, ports in `Abstractions/Ai/DraftPorts.cs`, `StrategyTextJson` in `Strategies.File` (the existing safe reader written out as JSON), infrastructure store, drafter, sheet builder; the prompt `draft.v1` in the prompt registry; migrations `AddAiWriteSwitches` and `AddStrategyDrafts` (with `Down`); five endpoints; the lazy `DraftPanel`.
- The sheet is generated from code (`IndicatorCatalog`, the model enums, two seeded examples) so a new indicator appears by itself.

## Not verified in this build
- No real model was run. Whether a 30B model writes a valid text in two repairs, how often it declines an expressible idea, and the 3 calls under 4 minutes figure are for P9-09 set C.
- The grammar-constrained `json_schema` output is not requested (the model port has no response-format field); the answer is always re-validated on our side, so the constraint would only save repairs.
- A real model calling `lab_propose_run` was not run; the API test of the auto option ends in a quick test that cannot start (the basket has no members), so a real auto run on data is not verified.
- Confirm against a real quick test (a basket with data) was not run end to end; the integration test confirms a draft and checks that an unstartable quick test still leaves the stored version and one decision.

## Deviations from the spec text
- Slice 07b: a draft of the CLI is not an auto candidate (only an owner session is); the owner's idea is the conversation's latest message of the turn for the chat tool; the inert switches `allow_proposal_accept` and `auto_accept_hypothesis` stay refused until P9-08.
- C5 and C6 use a draft-specific number reader (`DraftIdea`), not `TextGuard` with facts (the guard is built around briefing facts).
- A text with findings but accepted by the validator is `valid` (the findings are shown), not `invalid`.
- Application namespace is `XDrishti.Application.Ai.Drafting` (next to `Ai.Briefing`), not `Assistant.Drafting`.
- No hub event; polling is the contract.
