## Context
The simulator (P3-03) and the live engine must run the **conditions** of a rule — `rsi(14) > 55`, `crosses_above(close, vwap)`, `tf("1h").ema(20) > tf("1h").ema(50)`, `time >= "09:45"`, `regime() == "UP_LOW_VOL"` — over the `FeatureFrame` of [ADR 0031](0031-streaming-indicators-and-the-feature-frame.md) to [0033](0033-weekly-monthly-timeframes-calendar-features-and-the-market-context.md). The text comes from a person (later from an assistant) and lives in the database; four things are asked of the way it is read. It must be **safe** (never executed as code). It must **not read the future** — the main risk of [doc 19](../design/19-risks-and-compliance.md) — not even by a slip in the wording ("the previous value" of two features on different timeframes). It must be **fast**: a condition is evaluated for every closed bar, instrument and parameter set of a test. And its **errors must be fixable**: where, which rule, and what was probably meant.

## Decisions
The owner's answers of 2026-10-16 to the seven recommendations of the spec:
1. **Split.** This slice is the *expression language* — the text of one condition becomes a checked, compiled, evaluated predicate. The *strategy file* around it (the YAML sections, `params` of at most four, the `sell:` block and the automatic BUY → SELL mirror, the JSON Schema, storage in `lab.strategies`) is **P3-02b**. This slice receives the text, the evaluation timeframe and a `{name → number}` map, and nothing else. *(Note, 2026-10-18, P3 re-plan: P3-02b is split. P3-02b is the typed strategy model and the compile of its sections, with no YAML; the YAML file and the JSON Schema are P3-02c, storage and seeding P3-02d, the BUY → SELL mirror P3-02e; see the [roadmap](../design/18-roadmap.md).) *Built 2026-10-18: P3-02b is the typed model and the compile of its sections, [ADR 0036](0036-the-typed-strategy-model-and-the-compile-of-its-sections.md).)*
2. **Superpower** (one NuGet package, [doc 03](../design/03-target-architecture.md)), version pinned in `Directory.Packages.props` (3.2.1), with compiled expression trees; the alternative, a hand-written parser without a dependency, was not taken.
3. **Unknown is not true.** A condition whose data is not ready is *unknown*, not *false*: Kleene's three-valued logic, so `not (rsi(14) > 55)` cannot fire before RSI exists. A decision treats unknown as false.
4. **`time` is the close time of the evaluated bar**: the start of the last accepted 1-minute bar plus one minute (the bar 09:44 makes `time` = 09:45), so `time >= "09:45"` first holds on the 15-minute bar that *closes* at 09:45, not on the one before it.
5. **Lagged evaluation needs one timeframe.** `crosses_above`, `crosses_below`, `rising` and `falling` are refused when their operands sit on different timeframes (the "previous value" of the two would be different instants); the message gives the explicit form (`close > tf("1D").ema(20) and close[1] <= tf("1D").ema(20)`).
6. **Strict crossings.** `crosses_above(a, b)` is `a[0] > b[0] and a[1] <= b[1]` (a touch that does not pass is not a cross; equality at the previous bar counts as "not above yet"); `rising(x, n)` is strict at every step.
7. **The prerequisites come first**, inside this slice: `ContextFeature` / `ContextFeatureKind` become `DateFeature` / `DateFeatureKind`, `IndicatorInfo` gets `RequiresContext` and `RequiresExpiryDays`, and `FeatureFrame` gets `LastBarTime` — the follow-ups M18 of the P3-01c review, done before the first user of the names.

Design decisions of the spec, approved with it:

8. **A pure library `XDrishti.Strategies`** that references `XDrishti.Domain` and `XDrishti.Indicators` only (and Superpower), with four namespaces: **Syntax** (lexer, parser, immutable AST with source spans, canonical printer), **Binding** (names, types, catalog arguments; all internal), **Lint** (the look-ahead and timeframe rules and the codes) and **Compilation** (the plan, the delegate, the merge of several conditions). No I/O, no clock, no code made from text, no mutable static state, every class sealed (the three abstract bases of the syntax tree excepted); enforced by architecture tests.
9. **The grammar** is the one of [doc 11 §2](../design/11-strategy-lab.md): `or` < `and` < `not` < comparison (not chained) < `+ -` < `* /` < unary `-` < postfix `[k]` < primary; keywords `and or not true false`; numbers, double-quoted strings, no comments, free whitespace, case-sensitive. A subscript is only read after a reference.
10. **A closed vocabulary.** An identifier means, in this order, a strategy parameter (a number known when the condition is compiled), then a builtin, a constant or `time`, then a catalog feature. The dotted spellings are exactly `prev_day.open|high|low|close|volume`, `today.open|high|low`, `index.trend` and `index.adx` (mapped to the flat catalog names); everything else dotted is an error. Nothing else is ever looked up.
11. **Types:** `number` and `bool` are what a finished condition is made of; `time` (the keyword), `regime` (the function `regime()`) and `text` exist only next to a comparison. A condition must be `bool`.
12. **Errors are data.** A failed compile returns every problem it found — a stable code, a message that names the offending text, a source span with offsets, line and column, an optional suggestion, a severity — in source order, never an exception; at most 100 syntax problems are listed, then one that says there are more (Amendment 7). The library's `Result` carries one error, so `ParseResult` and `CompileResult` carry the list (the spec foresaw this).
13. **The look-ahead and timeframe lint** (table below), with the codes `strategy.lint.*`; the syntax problems have the codes `strategy.syntax.*`. *(Close-out, 2026-10-17: the meaning of one row, `lag_across_session`, was changed by [ADR 0035](0035-per-session-features-keep-the-history-of-the-session-only.md); see the table and Amendment 19. The code and the count of 16 lint codes are unchanged.)*
14. **Compile in two steps.** `ConditionCompiler.Compile` (parse, bind, lint) returns a `CompiledCondition`: exactly the features the text reads, the history depth, whether the frame needs a market context or expiry dates, the warnings. `Bind(frame)` resolves the handles and returns a `BoundCondition` whose `Evaluate` runs a delegate compiled from a `System.Linq.Expressions` tree built from the bound tree. `ConditionSet.Merge` unites the plans of several conditions (one frame for all).
15. **When to evaluate is the caller's business.** A bound condition is a pure function of the frame as it is *now*; the simulator evaluates at the steps where `frame.BarClosed(evaluationTimeframe)`.

### The lint rules
Each rule has a stable code `strategy.lint.<name>`; the messages are English sentences that name the offending text and may be reworded, the codes and spans are the contract. The full reference with examples is [doc 11 §2](../design/11-strategy-lab.md).

| Code | Severity | Rule |
|------|----------|------|
| `unknown_name` | error | an identifier or function that is not a parameter, builtin, constant, `time` or catalog feature; a dotted pair that is not one of the spellings; a regime name that is none of the nine; a builtin or parameter written with `tf(…)`. Suggestion: the closest names within edit distance 2 (case-insensitive; distance 1 for a text of one or two letters), at most five |
| `bad_arguments` | error | a wrong number, kind or range of arguments (the catalog's parameter names, ranges and defaults are quoted); an argument that is not a number known at compile time; a function or a feature with parameters written without parentheses (`rsi`; suggestion `rsi()`); a bad or repeated `source=`; a parameter or constant called like a function |
| `unsupported_timeframe` | error | `tf("…")` is none of `1m 5m 10m 15m 30m 1h 1D 1W 1M` (`"1d"` suggests `"1D"`), or the catalog does not support the feature on it (`vwap` on 1D, `prev_day_*` on 1W, a calendar or context feature on anything but 1m) |
| `negative_or_zero_lag` | error | a subscript or `rising/falling` count that is not a whole number of at least 1 (`close[0]`, `close[-1]`, `rising(close, 1.5)`). The span is the number, except for a subscript of zero (`close[0]`, `close[-0]`, `close[00]`, `tf("1h").close[0]`), where it is the whole subscripted feature (not only the `[0]`) and the suggestion is the feature without the subscript, so that the suggestion replaces its own span (Amendment 1) |
| `lag_too_deep` | error | the history needed (the largest lag read plus 1; the lags of `crosses_*` and `rising/falling` add to the lags inside) is above 256 |
| `lag_on_non_feature` | error | a subscript on a strategy parameter, a constant or `time` (on a call, a parenthesis, a literal or a second subscript it is the syntax problem `subscript_on_non_reference`) |
| `mixed_timeframes_in_lag` | error | the features under `crosses_*`, `rising` or `falling` are not all on one timeframe; the suggestion is the explicit form where one side is a plain reference on the strategy's timeframe. The calendar and context features are a clock of their own, the date: they are never lagged together with a bar feature, on 1m too (Amendment 4) |
| `time_on_daily` | error | `time` on a 1D, 1W or 1M strategy |
| `bad_time_literal` | error | a text compared with `time` that is not `HH:MM` within 09:15 … 15:30 (`"9:45"` suggests `"09:45"`) |
| `type_mismatch` | error | a value of the wrong type for its place (see *Types*); a parameter that is not a finite number |
| `constant_condition` | warning | a true/false part that reads no data (`1 < 2`, `crosses_above(1, 2)`, a parameter against a number); a bare `true`/`false` only when it is the whole condition; a bounded oscillator above 100 is *not* detected |
| `redundant_timeframe` | warning | `tf("15m").ema(20)` on a 15m strategy; suggestion `ema(20)` |
| `needs_context`, `needs_expiry_days` | information | the plan reports that the frame must be created with a `MarketContext` / the expiry dates; reported at the first feature that needs it, and only for a condition without errors |
| `shadowed_name` | warning | *added by the build* (Amendment 11): a strategy parameter with the name of a feature, builtin, constant or `time` wins, and says so |
| `lag_across_session` | warning | *added by the build* (Amendment 19); **meaning changed by [ADR 0035](0035-per-session-features-keep-the-history-of-the-session-only.md)** (the code is the same): a lagged read of a per-session feature (`vwap`, `or_high`, `or_low`, `today_*`, `prev_day_*`, `gap_pct`) from further back than a whole session holds, that is `k` bars of its timeframe `T` with `k · T` of at least the 375 minutes of a session (`vwap[75]` and `rising(vwap, 75)` on 5m, `rising(vwap, 7)` on 1h, `tf("5m").vwap[80]` on a 1D strategy). The frame keeps the history of such a feature for the current session only, so every bar that far back is in an earlier session, where the feature has no value: that part of the condition is never known, and unknown is not true. A shorter read that reaches before the first bars of a session is unknown on those bars only, by the rule of the frame, and is not warned; the strategy's own timeframe and a `time` check make no difference; a read on 1D is by position and is not warned. The message names the features, "up to N closed bars back" and the most a session holds. *First built as (Amendment 19, superseded):* a warning for any lagged read, on an intraday strategy, of a feature that has a value on its first bar, cleared by a `time >= "HH:MM"` check in the same chain of `and`s (`and time >= "09:45"` for one bar back on 15m; `rising(vwap, 3)` on 15m needed `time >= "10:15"`) |

## Why a condition cannot look ahead
The guarantee has three layers. The first is structural and is pinned by an architecture test and an audit of the expression trees, the second is the lint table, and the third is a property test that can fail — for what it can see, which is the feed of the frame, not the compiler (its limits are written below, with the layers that do guard the compiler).

1. **The language has no word for the future.** A compiled condition reads the world through exactly three doors of the frame: `frame[handle]` (the value as of the **last closed bar of the feature's timeframe**; for a per-session feature on an intraday timeframe also unknown from the start of a new date until its timeframe has closed its first bar of it, [ADR 0035](0035-per-session-features-keep-the-history-of-the-session-only.md)), `frame.At(handle, lag)` with a lag of 0 or more (the value `lag` closed bars of that timeframe ago) and, for `time`, `frame.Steps` and `frame.LastBarTime` (the minute that was just fed). A negative or zero subscript is refused when the text is read (`negative_or_zero_lag`), and the compiler only ever adds the non-negative offsets of the lagged builtins, so no lag is negative (`FeatureFrame.At` throws for a lag below 0: the future cannot be read at all). There is no syntax for a forming bar, a later bar or a value computed from them. A feature on a higher timeframe is whatever the frame says it is — the last *closed* bar (ADR 0031), a weekly bar only when its last session has closed (ADR 0033), a context value as of the previous session (ADR 0033). Two tests keep the library to these doors: an architecture test lists the only seven members of `FeatureFrame` the compiled library may reference (`get_Item`, `At`, `get_Steps`, `get_LastBarTime` to read; `HandleOf`, `get_HistoryDepth` and `Create` to bind), never `Step`, `Reset`, `BarClosed`, `TryLastClosed` or any other way to feed or peek at the frame, with a sentinel that proves the rule can fail; and `CompiledTreeTests` audits the expression trees of the written and of about 2,700 generated conditions on all nine timeframes: a tree can call only the public functions of `Kernel` and `Math.Abs/Min/Max`, gives the frame it was given to the three kernel functions that take one (`Value`, `ValueAt`, `CloseMinute`), holds nothing but numbers (no closure over a frame, a bar or a list), uses no member access, construction, invocation or indexing other than the handle array, and builds the lag of `ValueAt` only as a sum of non-negative whole numbers and the counter of a run — never a subtraction, a negation or a negative constant, so a lag is never negative. (The first build said "a feature is read at the lag written or further back, never nearer"; the audit does not prove that, only the shape. That a lag is *exactly* the one written is held by the interpreter oracle and the hand-calculated examples, see below and Amendment 14.) Hand-built trees (a call of `IsReady`, a lag of −1, a lag from a subtraction or a negation, another frame, a member access, a closure) show that each rule can fail.
2. **The lint refuses what would silently be wrong.** A lag that needs more history than the frame keeps (`lag_too_deep`), "the previous value" of features on different timeframes (`mixed_timeframes_in_lag`), a subscript on something that has no past (`lag_on_non_feature`) and a `time` on a bar that has no clock time (`time_on_daily`) are errors with a message and, where there is one, the correct form.
3. **A property test over the feed of the frame and the determinism of the chain** (`LookAheadPropertyTests`). For 240 seeds (40 on each evaluation timeframe 1m, 5m, 15m, 1h, 1D and 1W) and 1,200 random conditions (five to a seed, all in one frame, a market context on half of the seeds), the three-valued result and the decision of every condition at every closed bar of the evaluation timeframe is identical (a) when every later 1-minute bar is removed and (b) when every later bar is replaced by arbitrary values — prices of 1e12, 1e300, 1e-9 and 0, zero volumes, huge volumes —, for cut points at the closed bars (all of them when there are few, a sample with the first and the last otherwise) and a few minutes in the middle of a bar. On the seeds with a context the same runs also cut the context at the date of the cut: in (a) the context days dated at or after it are removed, in (b) they are replaced by changed ones (other prices, a VIX of 99.9, a breadth of 3), as the prefix property of the date lane in the Indicators tests does — a step on the date *D* reads the day before *D*, so the record of *D* and the later ones must not matter. The conditions are generated as a model, printed to text in several spacings and bracket styles, and go through the whole chain (parse, bind, lint, compile, bind to a frame, evaluate). **Negative controls** show that the property can fail: run through a feeder that gives the frame the first bar after the step before reading (`NextBarFeeder`), one that runs the frame on to the close of the slowest higher-timeframe bar before reading (`FormingBarFeeder`), or one that lets the date lane read the context record of the date itself (`SameDayContextFeeder`, modelled by moving every record one calendar day back), the same property reports violations on all six timeframes, for hand-written conditions and (for the first two) for the random ones, while the honest feeder reports none on the very same inputs.

**What the property proves, and what it does not.** It proves that, fed an honest series, the answer at a step depends on the bars up to that step and nothing later: it guards the *feed* and the *frame* (a closed value, a calendar or a context lookup that used a bar it had not been given) and the determinism of the chain (no hidden or static state). It cannot fail for a change in the *compiler*: a compiled condition is a pure function of the frame as it is at the step, and the frame holds only the bars up to the step, so whatever the compiled code computes, removing or replacing the later bars cannot change it. A compiler that read the wrong lag or the wrong clock (a `time` one minute late, a crossing whose previous value is the current one) passes the property and is caught by the other layers: the interpreter oracle (864 conditions compared at every step, and 288 more over the twelve per-session features since [ADR 0035](0035-per-session-features-keep-the-history-of-the-session-only.md)), the hand-calculated examples, the audit of the expression trees and the architecture test on the members of the frame, which exist for that reason (they were added after review showed that two mutations of the compiler passed all of `LookAheadPropertyTests`). The negative controls are three wrong *feeders*, not a wrong compiler: they show that the harness can see a leak in the feed. They stay feeders because `FeatureFrame` is sealed with a private constructor and the compiled code takes the concrete type, so a wrong frame wrapper would need an interface on the hot path (about 4.7 ns per condition, reasoned and not measured) and would catch nothing that the feeders do not (Amendment 14). The property also cannot by itself see a read of the *forming* bar that uses only past minutes, because a partial bar is a function of the minutes before it and truncation does not change it; the negative control `FormingBarFeeder` therefore models the leak as reading the bar in its final state before it closes. The forming bar is guarded where it is made — the frame never shows it (ADR 0031: the `CloseIndex` of every bucket against an independent reference, the frame-semantics tests, the prefix property) — and, in the library, by the two tests above: the compiled code reads the frame through `frame[handle]` and `frame.At` (and `Steps` and `LastBarTime` for `time`) and nothing else. It also does not cover look-ahead in the *data* (a restated close, ADR 0033).

**The compiler has a negative control of its own: the mutant control** (close-out, Amendment 14; `InterpreterOracleTests.Mutants`, test code only). It takes the real expression tree of every condition of the oracle corpus, changes it the way a faulty compiler would — a feature read one bar nearer than written, the previous value taken as the current one, a run that forgets the lag written inside it, `time` one minute ahead, `time` at the start of the bar —, compiles the changed tree and runs it through the same blocks and the same comparison as the main oracle test, after every 1-minute step, stopping at the first difference. The whole corpus is walked (nine timeframes, both flavours, six blocks: 108 blocks), because the run mutant is first noticed only in the ninth block. Measured: the oracle notices the five mutants after 1, 1, 9, 2 and 2 blocks, in the order above; the same wiring with nothing changed gives no difference over more than 1,000 comparisons, so a difference is the mutant's. The layers, and what each can see:

| Layer | What it can see | Where |
|-------|-----------------|-------|
| Truncation and perturbation property | the feed and the frame: a bar, a closed value or a context record that used the future; hidden or static state in the chain | `LookAheadPropertyTests`, with three wrong feeders as negative controls |
| Audit of the expression trees | a negative lag, a lag that is not a sum of non-negative terms, a call outside the kernel, a door of the frame other than the three, anything but numbers | `CompiledTreeTests`, with hand-built trees as negative controls |
| Interpreter oracle, hand examples, kernel tests | a wrong lag or a wrong clock in the compiler | `InterpreterOracleTests` (the corpus and the mutant control), `HandExamplesTests`, `KernelTests` |
| Architecture test | any use of a member of `FeatureFrame` other than the seven | `StrategiesArchitectureTests`, with a sentinel |
| Frame tests of the indicators library | the forming bar, which the frame never shows | `XDrishti.Indicators.Tests` (ADR 0031) |

**What no test of this slice covers: look-ahead through the caller.** A bound condition is a pure function of the frame as it is now (decision 15). The simulator and the live engine must evaluate only at the steps where `frame.BarClosed(evaluationTimeframe)`, and the truncation and perturbation property has to be run through the simulator's own feed loop, with a leaking feeder as its negative control (a requirement for the P3-03 spec).

## Security
No string is ever executed. Every identifier is checked against a closed vocabulary (the catalog, nine builtins, seven constants, `time`, and the strategy parameters, which are a map of numbers and so cannot carry text); the dotted spellings are three scopes (`prev_day`, `today`, `index`) with fixed members; `source=` is one of four prices. The only dynamic code is a `System.Linq.Expressions` tree **built from the bound tree** in one class (`ExpressionBuilder`) that calls a fixed list of the library's own functions (`Kernel`, plus `Math.Abs`, `Min` and `Max`), found by name once; the framework's `LambdaExpression.Compile` emits the IL for that tree, which the rule against `Reflection.Emit` in our own code does not cover and is not meant to. Architecture tests keep it that way: no `Reflection.Emit`, Roslyn, dynamic LINQ, CodeDom, `Activator`, `AppDomain`, assembly loading, file, network, database, clock or environment access (scanned in the compiled code, with negative controls proving the scans can fail), and no `System.Linq.Expressions` outside `ExpressionBuilder`. Literals are bounded (`1e400` and `1e-400` are problems), the text is at most 4,000 characters, the nesting at most 64 levels, and the parser and the binder check at every level that stack is left and end in a `too_deep` problem rather than a crash (the printer, the delegate builder, the lint visitors and the syntax records have no guard of their own and rely on the depth limit, Amendment 3). *(Corrected 2026-10-17: the first text said "every recursion checks that stack is left"; only the parser and the binder do.)* Fuzz tests feed the parser 6,000 random mixes of language and junk, 4,000 valid sources damaged by one character and every prefix of every valid source: nothing throws, hangs or breaks the contract (every problem has a span, a line and a column, in source order). The work of the recovery is bounded by a count, not by a clock: it parses the tokens at most 232 times and lists at most 100 problems (see *Consequences from the build*), and a test counts the parses for 18 shapes of the worst texts of 4,000 characters (22 since the close-out, Amendment 7). What it cannot do is protect the *meaning* of a valid condition — a wrong rule is the Lab's business (doc 11 §5), not the compiler's.

## Consequences
- The simulator and the live engine call one thing: `ConditionCompiler.Compile` → `ConditionSet.Merge` → `FeatureFrame.Create(plan.Features, …)` → `plan.BindAll(frame)` → `Evaluate` at the closed bars. **The frame is created from the plan's features**; if no condition reads a feature on the evaluation timeframe (a plan of `time >= "09:45"` alone has no feature at all) the caller must add one before it can ask `BarClosed` — the plan does not (P3-03). *(Note, 2026-10-18, P3-02b built: for a strategy the caller uses `StrategyCompiler.Compile`, creates the frame from `CompiledSide.Features` and calls `Bind`; the sentinel `close` on the evaluation timeframe is already in that list, so P3-03 does not add one; [ADR 0036](0036-the-typed-strategy-model-and-the-compile-of-its-sections.md).)*
- A bound condition belongs to the **layout** of its frame (the same features in the same order and the same history depth). `Evaluate` does not check which frame it gets, because that would cost time on every evaluation and would stop one strategy being reused across instruments; a frame of another layout reads other features **without an error**. Build every frame of a strategy from the same plan.
- Parsing and checking never pay for the delegate: it is built once, at the first `Bind`, whatever the number of frames, so an editor that only checks conditions pays 0.9 ms (warm) for ten of them and a test over ten thousand instruments compiles each condition once.
- The first compile of a fresh process costs about 38–41 ms, the JIT compiling about a thousand methods of the parser, the binder and the expression compiler (Amendment 2, closed by ISS-12). A host therefore runs the *compiler warm-up*, `CompilerWarmup.Run()`, once on a background thread when it starts, without delaying readiness: a `StrategyWarmupService`, an `IHostedService` that calls `Task.Run(CompilerWarmup.Run)` from `StartAsync`. That service belongs to the first host that references the library (P3-02b or the Lab API). *(Note, 2026-10-18, P3 re-plan: the service belongs to P3-03, the first project that references the library, `XDrishti.Simulation`; it lives in `XDrishti.Api` and must land in the same change, or the architecture rule fails. P3-02b adds no project that references the library, so it never needs the service.)* After the warm-up the first real compile takes 3–4.5 ms; a compile that arrives during it pays the rest. An architecture test fails when any `src` project other than the library references `XDrishti.Strategies` and no source file outside the library calls `CompilerWarmup.Run` (a textual check across `src`, not per project, and not that the call is in a hosted service); it is vacuous until a project references the library.
- **What a condition costs is bounded by its text; it is not constant** (Amendment 18). `and` and `or` may skip work, and `rising`/`falling(x, n)` is a loop of n steps, about 1.75 ns per value read on any data, so one long run costs more than the whole ten-condition set of the 0.3 µs target. The research of the close-out puts the worst case of one condition of the longest text the language allows (4,000 characters) at about 0.1–0.3 ms per evaluation. No cap was lowered and no cost lint was built; a lint that sums n × reads is the candidate if the simulator (P3-03) shows that evaluation matters, and the question is reopened when evaluation is above about 20 percent of a walk-forward run, or when a parameter sweep over a `rising`/`falling` count makes it a leading term.
- **The twelve per-session features keep the history of the session only** ([ADR 0035](0035-per-session-features-keep-the-history-of-the-session-only.md), 2026-10-17). `vwap`, `or_high`, `or_low`, `today_*`, `prev_day_*` and `gap_pct` on an intraday timeframe are unknown at every lag from the first 1-minute bar of a new India date until their timeframe has closed its first bar of it, and a lag that reaches before that bar is unknown: `vwap[1]` is unknown on the first bar of a session, `crosses_above(close, vwap)` from the second bar of the feature's timeframe, `rising(vwap, 3)` from the fourth. Unknown is not true (decision 3), so `not crosses_below(close, vwap)` is unknown on the first bar too. A strategy, the simulator (P3-03) and the live engine must expect a condition on these features to be unknown for the first bars of every session; a `time >= "HH:MM"` check is a trading rule now, no longer a device against reading two sessions.
- The error wording is English text for now; the codes, spans and suggestions are what a form builder or an editor (Monaco, a later UI story) reuses. Messages may be reworded without a new ADR.
- A condition with a syntax problem is answered with its syntax problems only; the name and lint problems appear once it parses.
- `rsi(14) > 100` (a bounded oscillator that can never be true) is not a `constant_condition`: only literals and parameters are constant. A wrong rule that compiles is for the Lab's checks.
- P3-02b writes the YAML around this: it hands each condition and the parameter map to `Compile`, turns `all:` / `any:` lists into `and` / `or`, and may use `ExpressionPrinter` for the canonical text of a condition (whitespace and redundant brackets removed) when it hashes a strategy. *(Note, 2026-10-18, P3 re-plan: the YAML is P3-02c; the spec of P3-02b (Draft, awaiting the owner's approval) has the typed model evaluate the entries of an `all:` / `any:` list at list level, one condition each, instead of turning them into one `and` / `or` text; see Amendment 3.)* *(Note, 2026-10-18, P3-02b built: that is what was built — each condition of a list is compiled and evaluated on its own and the lists are never joined (ADR 0036). The hash of a strategy is **not** taken from the printed text: `ExpressionPrinter` prints `rsi()` and `rsi(14)` differently although they are one feature, so a hash that must be equal for equal meaning is taken from the plan (the canonical `FeatureSpec`s and the bound tree); P3-02c decides it. P3-02b was split into P3-02b to P3-02e.)*

## Consequences from the build
What was learnt while building [P3-02](../specs/P3-02-rules-expression-language-lint-and-compiler.md); the deviations from the spec are listed under *Amendments* below.

**The prerequisites in `XDrishti.Indicators`.** The rename is mechanical (`DateFeature`, `DateFeatureKind`; the catalog names and behaviour are unchanged). `IndicatorInfo.RequiresContext` is true for exactly the ten names `index_trend index_adx index_vol_pct vix vix_pct vix_chg breadth regime_trend regime_vol regime`, `RequiresExpiryDays` for `is_expiry_day` only; `FeatureFrame.Create` reads the two flags instead of switching on the kind (the error fields and messages are unchanged), so a thirteenth date feature needs no edit in `Create`. `FeatureFrame.LastBarTime` is the epoch-second start of the last *accepted* 1-minute bar, 0 before the first step, unchanged by a skipped bar and cleared by `Reset`; reading it allocates nothing. Tests: 226 cases pin the flags for all 56 names (including the exact error when an option is missing, and that giving only the other option does not satisfy the requirement) and 54 cases pin `LastBarTime` (8 frame shapes, hand-calculated epochs, skipped bars, `Reset`, a 20-seed property), plus one allocation test; no existing assertion was weakened.

**The grammar as built** (the reference is [doc 11 §2](../design/11-strategy-lab.md)). The lexer is a Superpower tokenizer that never fails: what it cannot read becomes a token of an error kind with its own text, so every wrong place is reported. Only ASCII is part of the language outside strings; a full-width `＞`, a no-break space or an accented letter is an `unknown_character` problem with the code point, never silently its look-alike — and a look-alike with a clear meaning (`＞`, `&&`, `||`, `!`, `≥`, `×`) is reported once and then read as the token it stands for, so one mistake is one problem. A string in single or typographic quotes is one problem with the double-quoted string as the suggestion. Numbers are `digits [. digits] [e [+-] digits]` with a lower-case `e`; `.5`, `1.`, `1E5` and `55abc` are problems. Identifiers are letters, digits and underscores. A subscript is `[` an optional minus and digits `]` and follows a reference only (`close[1]`, `prev_day.high[1]`, `tf("1h").close[1]`; not `rsi(14)[1]`). `tf` is written `tf("1h").name` or `tf("1h").name(args)`; a bare `tf("1h")` is `bad_timeframe_qualifier`. A parenthesised node's span includes its parentheses.

**The parser is a hybrid.** The tokenizer and the small productions (names, literals, the `tf("…").` qualifier, a named argument, a subscript) are Superpower combinators. The recursive spine — an expression with its operators (precedence climbing), a parenthesised expression and the arguments of a call — is written as plain Superpower parser functions: nine combinator layers, one per precedence level, needed more than 1 MB of stack at 64 nested levels in a Debug build, the spine needs 512 KB in Release and 768 KB in Debug (including the 128 KB the runtime keeps in reserve), and every nesting level checks that stack is left. Superpower is not visible in the public API (an architecture test reads the signatures). **Recovery** wraps the parser in a loop: parse; at a failure explain it from the tokens around it (code, span, message), *repair the token list* (insert a missing value, delete up to the next safe restart, delete a broken subscript, close open brackets, fix the kind of a closing bracket) and parse again. The first problem is always exact; later ones are those of the repaired text — independent faults (a second unknown character, a trailing comma and a chained comparison, a missing operand and an unclosed bracket) are reported truthfully, a single typo gives one problem and not a chain: a follow-on failure right after a value the recovery supplied (`close <> 5`), at a comma it has just reported as having no argument (`rsi(,)`), at a `!` after a value that the lexical pass has already reported as an unknown character (`close ! 5`: the text has no `not` to blame) or at an end that a repair made (`close === 5`) is repaired without a second report. **Cost and bound.** Every attempt parses the whole token list again and builds the one array of tokens that Superpower reads, so k problems cost O(k·n) for n ≤ 4,000 tokens; before the bound a text of nothing but faults took 0.43–0.68 s and 1.5 GB (3,990 commas after `f(`), 0.13 s and 387 MB (3,999 `&`), 0.17 s and 435 MB (a long sum followed by 2,000 closing brackets). The recovery now stops after 100 problems (the lexical ones counted) or 232 parses (twice the problems plus 32), whichever comes first, and the parser lists the first 100 problems in source order followed by one `too_many_problems` for the rest of the text; the worst texts measured take 13–52 ms and 14–27 MB. A test counts the parses for 18 shapes of the worst texts, so no clock is involved. *(Close-out, Amendment 7: the first 100 problems **found** are listed, in source order. "Found" is not the order of the text: the lexical problems are found before the syntax ones and an unclosed bracket is found at the end of the text, so with 100 problems or more an earlier one may not be listed. The bound of 232 parses can also end a mostly damaged text with one or two problems listed, so the note no longer says "the limit is 100". Four worst-case shapes were added to the count: 22 in all.)* The copy of the token list that the recovery made before its first attempt is gone (it works on the list the lexical pass built).

**Limits.** Text longer than 4,000 characters: `too_long`, the span is the part beyond the limit. Nesting: `too_deep` in two places — before the parse (the brackets open at once plus the prefix operators pending may not exceed 64; the span is the token that goes over) and after it (the depth of the tree may not exceed 64: every call, prefix operator, subscript and each operator of a chain is a level, parentheses are none; the span is the whole condition) — so a chain of 64 `and` operators of single names passes and 65 do not, and 63 conditions of the form `rsi(14) > 55` joined by `and` pass and 64 do not (Amendment 3). *Why the tree check exists, measured in the close-out:* the length limit alone allows about 2,000 levels of a sum (`close>1+1+…+1` with 1,990 terms is 3,985 characters) and about 444 of `true and`; the printer and the delegate builder need about 0.5 KB of stack per level, the compile 0.6–0.9 KB and the parser spine 6–10 KB per bracket level, and the generated `Equals`, `GetHashCode` and `ToString` of the syntax records recurse too and cannot be guarded. That sum overflowed a stack of 512 KB, and the compiler could not even check it on one of 1.4 MB. At the limit of 64, print, merge, frame, bind and evaluate run on 64 KB (Release and Debug) and the compile on 192 KB. The number of conditions that fit is "about 60", not exactly 63: it depends on where a deeper condition sits in the chain.

**The binder.** Names resolve in the order of decision 10. The catalog is asked, not copied: the arguments of a feature become a canonical `FeatureSpec` and `FeatureFrame.Create` is run on a one-spec frame to get the catalog's own answers (ranges, whole numbers, `fast` below `slow`, an opening range of whole bars, a timeframe the feature cannot run on), whose field errors become problems at the argument, the timeframe or the feature they are about; messages quote the catalog's parameter names, ranges and defaults. Two spellings of one feature give *equal* specs (`rsi()`, `rsi(14)`, `rsi(14, source=close)`, and `highest(10)` with `highest(10, source=high)`), so the frame shares one instance. A feature argument and the count of `rising/falling` are *constants known at compile time*: a literal, a parameter, `MON … SUN`, or arithmetic, unary minus, `abs`, `min` and `max` of those (`rsi(rsi_len * 2)`); a division by zero is NaN and is refused. The calendar and context features are always read on 1m, whatever the strategy timeframe. `regime()` is compared with `==` and `!=` only, against one of the nine names (resolved to the code when the text is read) or a constant integer 1 to 9. The suggestion for a typo is the closest vocabulary entries by optimal string alignment distance (insert, delete, replace, swap two neighbours), compared case-insensitively, nearest tier only, ties broken by the smaller case-sensitive distance (`2m` suggests `1m` before `1M`), at most five; a property test checks one deleted, inserted or swapped letter in each of the 56 names plus the builtins against an independent edit-distance implementation. After an error the part becomes a `BoundInvalid` that keeps its bound operands, so the lint still finds the other faults of the condition: all binder and lint problems of a condition that parses are reported together, in source order. A `crosses_*`, `rising` or `falling` that cannot be bound (a type error in an operand, a count that is not a whole number) keeps its operands as the lagged ones of the call (`LaggedCall`), and a `time` compared with a bad text or with a number keeps the keyword, so the clock rules (`mixed_timeframes_in_lag`, `lag_too_deep`, `time_on_daily`) are still applied and fixing one fault does not make another appear. What is not kept is the arguments of a feature that cannot be bound (`rsi(time)`): they are the same fault.

**The compiler.** The bound tree has 17 internal sealed record node types behind an interface (so the library keeps its rule that no class is open for inheritance). `ExpressionBuilder` turns it into a `Decision` — a delegate over the frame and an `int[]` of handles (`handles[i]` is the handle of `Features[i]`), returning the numbers of `Truth` (1 true, 0 false, −1 unknown) — with two kinds of node: a *number* is an expression of type `double` (NaN when not ready), built *at an offset* (how many closed bars further back every feature in it is read, which is how `crosses_*` and `rising/falling` evaluate their operands at several lags while constants stay constants), and a *truth* is an `int` that calls the functions of `Kernel`. `Kernel` is the one place where each rule is written in plain code that a test can walk exhaustively: Kleene's tables, the six comparisons (unknown for a NaN), `crosses_above/below` (unknown if any of the four values is NaN), `between` (both ends included), the run state of `rising/falling` (a loop over the lags 1 to n, with no early exit on purpose: a run is atomic over NaN, a missing value anywhere makes it unknown even after a step has failed, so every step is read and the work is n times the reads whatever the data; Amendment 18), the division that is NaN instead of infinite, and `CloseMinute` for `time`. `and` and `or` skip the right side when the left one decides (an optimisation; the result is Kleene's). The delegate holds no frame and no handle, so one delegate serves every frame the condition is bound to.

**Semantics the spec left open, decided in the build.** The arithmetic of a NaN is NaN; only an exact zero divisor gives NaN, a quotient that overflows is ±infinity (a number), `inf − inf` is NaN (so unknown), `min` and `max` pass a NaN on. The lagged builtins are *atomic*: `crosses_*`, `rising`, `falling` and `between` are unknown if any of their values is NaN, even when the other values would already make the answer false. "Not ready" is NaN, relying on the `IIndicator` contract that `Value` is NaN exactly when not ready (a test pins `IsReadyAt` against NaN for every catalog feature at lags 0 to 2). `time` is unknown while `frame.Steps == 0` (not when `LastBarTime == 0`, so a real bar at epoch 0 is still a bar), is the India clock minute (the domain's `SessionClock.MinuteOfDay`, shared with the rest of the system, as are the session bounds 09:15 and 15:30 of `bad_time_literal`) and wraps at midnight. A condition that reads no feature binds to any frame.

**Superseded by [ADR 0035](0035-per-session-features-keep-the-history-of-the-session-only.md) (2026-10-17).** The paragraph below is what was built on 2026-10-16 and why; it is kept as history. The history of the frame no longer runs on across sessions for the twelve per-session features on the intraday timeframes (1m, 5m, 10m, 15m, 30m, 1h): the frame forgets it at the timeframe's first bar of a new India date and holds the feature unknown until that bar has closed, so `vwap[1]` on the first bar of a session is unknown and `crosses_above(close, vwap)` cannot compare two sessions. What no longer holds below: "by position" for these features; `IndicatorInfo.HasValueAtSessionOpen` (deleted, `RestartsEachSession` replaces it); the warning that asks for a `time >= "HH:MM"` check (`lag_across_session` now warns about a read that no session can hold, see the lint table); and the claim that the headline crossing is true on the first bar of a session. What still holds: `x[k]` is the value `k` closed bars of its own timeframe ago, a rolling feature (`ema(20)`) runs on across sessions, and so does everything on 1D.

**Lagged reads are by position, not by session.** `x[k]` is the value `k` closed bars of its own timeframe ago, and the history of the frame runs on across sessions ([ADR 0031](0031-streaming-indicators-and-the-feature-frame.md), decision 4; P3-01b criterion 2): a rolling feature wants that (`ema(20)` at 09:30 uses the previous day's bars). A feature that starts again at the session open and already has a value on its first bar does not: `vwap`, `today_open/high/low`, `prev_day_*` and `gap_pct` (from the second session on) — `IndicatorInfo.HasValueAtSessionOpen`, which is false for `or_high` / `or_low` of several bars because they are not ready until the range has closed, so a crossing against them is unknown on the first bars. For these, the read one bar back on the first bar of a session is the *previous session's last value*. The headline example `crosses_above(close, vwap)` is therefore true on the first bar of a session whenever that bar closes above its own typical price and the last close of the day before was at or below the last vwap of that day: a cross of two sessions. The final review found it (on a seeded random walk of 500 sessions the crossing was true on the first bar of about a quarter of the sessions, against a few percent at every other bar; a later scratch run measured 28.1 % of the first evaluations against 8.75 % of the other bars on 15m, [ADR 0035](0035-per-session-features-keep-the-history-of-the-session-only.md)); the same holds for `close > vwap and close[1] <= vwap[1]`, `rising(vwap, 1)` and `crosses_above(close, today_open)`. Pinned by a hand-calculated two-session example (`SessionBoundaryExamplesTests`: true at the first bar of the second session, `time >= "09:17"` removes it on 1m). The rule built (Amendment 19): the meaning of `x[k]` is unchanged and the lint warns, `lag_across_session`, naming the features, how far back, and the check that clears it. Reads `lag` bars of timeframe `T` back stay inside the session from the bar closing `(lag + 1) · T` minutes after the open (at most 15:30; none when `lag · T` is a whole session or more), and a strategy on timeframe `E` is affected when its first evaluation, `E` minutes after the open, comes before that: `E < (lag + 1) · T`. A strategy on 1D or longer evaluates at the end of a session and is not warned. The check is recognised when it is a lower bound of `time` (`>=` or `>`) in the top-level chain of `and` of the same condition and the first evaluation it lets through is late enough; under an `or` or a `not`, or as an upper bound, it is not. A check in another section of a strategy file is not seen (follow-up for P3-02b). The numbers are verified against the real frame by `LagAcrossSessionTruthTests` (28 combinations of strategy timeframe, feature timeframe and lag: the lint warns exactly when some evaluation of a second session reads the first, and no evaluation at or after the asked-for time does). **Known limits of the warning** (the stronger rule is ISS-13): (a) a *plain subscript* of an `or_high` / `or_low` of several bars still reads the previous session's range on the first bars (`close > or_high(30)[1]` on 15m at 09:30 compares with yesterday's high) and is not warned; (b) a 1D or longer strategy is exempt by timeframe, although a very long lag of an intraday feature (`tf("5m").vwap[80]`) lands in the previous session; (c) the `time` check is a clock check, the lag counts accepted bars: it assumes a complete 09:15 opening (a session whose first minutes are missing from the data, or an evening Muhurat session, is not protected).

1. **`x[0]` is refused.** The spec's *Meaning* said "`x[0]` is `x`"; its lint table said that a subscript that is not an integer in 1 … 255 is `negative_or_zero_lag`.    *Decided on research under the owner's delegation (2026-10-16/17); the owner may revert: kept as built.* The reason is not that the language needs "one spelling for the current value" — it has others (`vwap` and `vwap()`, `rsi()` and `rsi(14)` are equal), and that sentence of the first build is withdrawn. 3. **The nesting limit of 64 counts the depth of the tree.** The spec: "a source nested more than 64 levels … is refused with a problem". Built, two checks with the code `too_deep`: more than 64 brackets plus pending prefix operators open at once (before the parse), and a syntax tree deeper than 64 (after it), where each operator of a chain is a level, so a chain `a and b and …` is as deep as it is long: 63 conditions of the form `rsi(14) > 55` joined by `and` pass, 64 are refused. A hand-written condition does not come near; the limit protects everything that walks the tree (printer, binder, compiler).

   *Decided on research under the owner's delegation (2026-10-16/17); the owner may revert: kept as built, the limit stays 64.* The tree check is what makes the approved "never a stack overflow" true. The check before the parse bounds brackets and prefix operators, but a chain of operators is read in a loop and builds a left-deep tree that the printer, the delegate builder, the lint visitors and the generated members of the syntax records walk once per operator, and only the parser and the binder guard the stack (the measurements are under *Limits*). Exempting chains only moves the bound to the length limit of 4,000 characters; raising the limit has no user (nothing in the design documents needs more than about a dozen conditions in one chain); dropping the check breaks the guarantee. The cost is small: about 60 conditions in one chain. Built with the decision: the message of the tree check now says what counts and what fits ("Every function call, `not`, minus sign and subscript, and every operator in a row (`and`, `or`, `+`, `-`, `*`, `/`), adds one level, so about 60 conditions joined by `and` is the most one condition can hold. Split it into several conditions."); two tests record why the check exists (a sum of 1,990 ones, 3,985 characters, is refused for its depth; the deepest accepted chain, 63 × `rsi(14) > 55`, is printed, merged, framed, bound and evaluated on a thread with a stack of 256 KB — a coarse guard, which trips only when the limit is raised about fifteen times). For P3-02b: join the entries of an `all:` or `any:` list with parentheses, which add no level (fine up to about 60 entries), split at list level only beyond that (an `and` or `or` of decisions is exact, because unknown acts as false), and map the spans of problems back to the entries. *(Note, 2026-10-18, P3 re-plan: the spec of P3-02b (Draft) evaluates the entries of an `all:` / `any:` list at list level, one condition each, and never joins them; the advice to join with parentheses is replaced, and the limit of about 60 conditions is not reached by a list.)* *(Note, 2026-10-18, P3-02b built: the lists are evaluated at list level, so the limit of about 60 conditions is never reached by a list and there is no threshold at which to split; an `all` list of 100 conditions compiles, while the same 100 joined by `and` give `too_deep`, and a test shows both. The aggregate of the problems of many items has a cap of its own: 100 errors, then 100 warnings and notes, [ADR 0036](0036-the-typed-strategy-model-and-the-compile-of-its-sections.md).)* Revisit when a real strategy has more than about 30 conditions in one chain: then raise the limit together with stack guards in the walkers.
4. **The calendar and context features are a clock of their own in the lag rule.** *(The approved text was silent: it did not name dates, so read literally they counted as 1m features, and this amendment narrows that.)* They are read on 1m whatever the strategy timeframe, but they change once a *date*, and their previous value is the previous date, never the previous minute. So a lagged call (`crosses_*`, `rising`, `falling`) may read them among themselves and against constants (`crosses_above(vix, 20)`, `rising(vix, 2)`, `rising(vix - index_trend, 2)`; `regime() == 3` has no lag) and never together with a bar feature, on any strategy timeframe, 1m included, and also for `tf("1m")` bar features: `crosses_above(close, vix)` is `mixed_timeframes_in_lag` on 1m, 15m, 1D and the rest, and the message gives `close > vix and close[1] <= vix`, which lags the bar only. The alternative, letting a context feature mix with any timeframe, would make "the previous value" mean a previous date for one side and a previous bar for the other. *History:* the first build counted these features as timeframe 1m, which let the mix through on a 1m strategy (and `tf("1m")` on any); a review showed that `crosses_above(close, vix)` is then `close > vix and close[1] <= vix[1]`, where `vix[1]` stays the previous *date's* value all day: with the VIX at 50 yesterday and 30 today and the close at 25 yesterday and 40 all today, the "crossing" holds at every minute of today, while the explicit form holds at the first minute only (`HandExamplesTests` pins both). The rule was tightened. On a 1D strategy the previous date and the previous bar coincide, but the refusal is kept there too, so that one rule holds on every timeframe; the explicit form is available.

   *Decided on research under the owner's delegation (2026-10-16/17); the owner may revert: kept as built, with no exception for 1D.* The literal reading gives wrong answers (the example above: a "crossing" at every minute of a date). It is a wrong-answer problem, not a look-ahead one, since neither form reads a value that is unknown at the step. The refusal costs almost nothing: lags among date features alone (`rising(vix, 2)`, `crosses_above(vix, 20)`) stay legal and hold at every evaluation of the date; a mix without a lag (`close > vwap and vix_pct < 80`) stays legal; and the explicit form compiles. An explicit form exists only when one side is a plain reference on the strategy's timeframe, so a call such as `adx(14)` against `index_adx` has none. The first text said that on a 1D strategy the previous date and the previous bar coincide: that holds on complete data only. A daily bar whose closing minute (15:29) is missing closes at the first minute of the next date, and the pairing shifts (measured: with no 15:29 minute on one Wednesday, "the previous date" and "the previous bar" differ at two of the three later closes). The refusal stays uniform on every timeframe for four reasons: it is one rule, an exception would concern one timeframe of nine, no use of it was found, and relaxing a refusal later is additive (tightening it later would break stored strategies). Rejected alternatives: reading the date feature "as it is now" inside a lagged call (a level, which changes the meaning silently) and writing the date features into the history on every bar (which breaks day-over-day reads such as `index_trend[1]`). Built with the decision: when the date is one of the clocks and there is no explicit form, the tail "Compare on one timeframe.", which cannot be followed for a feature that has no other timeframe, is now "A calendar or context feature changes once a date, so compare it without a lag, or lag only the bar side by hand."; pin tests on a 1D strategy (`DailyStrategyDateLagTests`: complete data, and a missing closing minute).

18. **Two claims of the approved text are corrected, because the code does not make them true.**

    (a) *Approved (Goal): "decides in constant time".* **As restated in the close-out, an upper bound** (decided on research under the owner's delegation, 2026-10-16/17; the owner may revert): the work of a condition is bounded by its text and never grows with the history the frame keeps, the number of bars or the data; `and` and `or` skip the right side when the left one decides, so a bar can cost less than the bound; the only part that grows with the text is `rising`/`falling(x, n)`, a loop of exactly n steps over its operand that costs about 1.75 ns per value read, on any data, with no early exit on purpose (a run is atomic over NaN: a missing value anywhere makes it unknown, even after a step has failed), and allocates 0 bytes. Measured by the explicit benchmark `Evaluate_runs_by_count` (one run; see *Performance*): 444–449 ns for `rising(close, 255)`, 866–868 ns with two reads, 2.1–2.3 ns when `and` skips the run: one long run costs more than the whole ten-condition set of the 0.3 µs target, whose longest runs are `rising(close, 3)` and `falling(roc(5), 2)`.

    *What the first build said:* that a condition takes the same time on every bar and whatever the history, except `rising`/`falling`, with a scratch probe on a series "that rises all the way so that the run never breaks early" (14.5 ns for `rising(close, 3)`, 117 ns for `rising(close, 50)`, 452 ns for `rising(close, 255)` and 950 ns for `rising(rsi(14) + ema(20), 255)`, against 2.8 ns for `close > ema(20)`; no benchmark measured a long run). That was wrong in two ways: there is no early exit, so a rising series is no best case, and `and`/`or` can skip a run, so "the same on every bar" does not hold; and the figures for small n swing about two to one with the warm-up of the process, so the 14.5 ns, the 117 ns and the 2.8 ns are not repeated. *Decided:* no cap was lowered (255 is the history cap of 256, and the lint tables, the plans and the oracle pin it); no run counter was added to the frame (it would break the seven-member contract of the frame and work for a plain feature only); no early exit (it breaks the atomic rule and makes the cost depend on the data). A deterministic guard was added instead, `RunCostTests` (a run is one loop of exactly n steps with one read per feature in it per step, the tree does not grow with n, no run means no loop), beside the explicit benchmark, which asserts only absolute caps with a margin of four (n = 255 at most 2,000 ns, two reads at most 4,000 ns) and a loose linearity check (t(255) / t(50) between 3 and 8).

    (b) *Approved (Types): "Anything else is a type error naming both sides".* Built: a comparison names both sides; `and`/`or`/`not`, `+ - * /`, the unary minus and the arguments of a builtin name the operand that is wrong, the type the place needs and the type it has (`close + true > 1`: "The right side of `+` needs a number, but `true` is a true/false value"); the code, the span and the suggestion are unchanged. *Decided: kept as built, and one gap closed:* a number where a true/false value is needed (`rsi(14) and …`, `not rsi(14)`) now also gets the hint "Compare it with something, like rsi(14) > 55."; the hints for `time`, a regime and a text are unchanged; each wrong operand is reported on its own span, and both are reported when both are wrong (pinned by a theory over the operator × type matrix). The messages help more than the approved wording, which named both sides where only one is wrong.
