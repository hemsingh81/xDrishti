# 0293 — The day-by-day simulation is a stored cursor over the SR-01 replay and takes hold-out block 1's look automatically

- **Status:** Accepted (owner, 2026-11-14, in chat: SR-04 answers Q1–Q6 and open questions 1 (a) and 2; 3–4 as recommended). Spec: [SR-04](../specs/SR-04-day-by-day-simulation-with-live-playback.md).
- **Date:** 2026-11-15.
- **Relation to other ADRs:** Extends [0272](0272-the-system-replay-is-research-only-fenced-from-evidence-and-hindsight-labelled-and-runs-the-live-pieces-over-as-of-facts-in-memory.md) (SR-01, the engine reused) and the HO-01b chain ([0283](0283-the-hold-out-is-a-chain-of-fixed-blocks-released-by-an-owner-act-or-the-auto-option-and-every-cut-follows-the-block-in-force.md)); applies [0292](0292-features-that-wait-on-the-owner-are-removed-the-market-context-the-charge-sheet-and-the-pre-registered-hold-out-replay.md) decision 4 (block 1's look is automatic) and 5 (gross for ever) and the auto-option rule of [0282](0282-auto-mode-defaults-follow-the-owners-instruction-of-2026-11-13-on-where-no-evidence-is-lost-and-no-risk-is-widened.md).
- **Build state (2026-11-15):** parts A (backend: tables, cursor/phase service, endpoints, runner, restart resume) and B (the tape endpoint, parity) are built. Part C (the screen) is open.

## Context
The owner wants an XDhan-like simulation: one trading day at a time, learning only from data up to the day before, played minute by minute, settled, advanced; or run unattended. SR-01 already replays the whole system session by session as one job. Hold-out block 1 starts 2026-04-10, so SR-01 stops before it.

## Decision
1. **One engine.** A simulation is a stored session cursor over an SR-01 `ReplayPrepared`; settling a day is `ReplayDriver.StepAsync` of that session on the in-memory book (`SimDayBook`). No second engine and no copy of selection, sizing or ledger code: a day equals the SR-01 session with the same inputs (golden test), equity comes only from `PaperLedger`.
2. **Phases** `idle → settling → settled → (advance) idle | complete`, plus `cancelled` and `error`. Settle is a request the one hosted runner (`SimDaysRunner`, the SR-01 job pattern and yield rules, extracted into `ReplayYieldRules`) works; advance stores the settled day as an immutable snapshot and moves the cursor to the next trading session in one transaction. Auto-run repeats settle and advance through the same commands as the buttons; pausing is seen after the current day. **A manual Run day works in market hours** (coordinator decision, 2026-11-15): a settle asked while auto-run is off is stored as manual and the runner skips only the market-hours rule for it; low disk, data jobs, the incomplete backfill and a simulate-everything chunk still make it wait, and auto-run keeps yielding in market hours. Why the runner waits is stored on the run and shown in the status (`waiting`, e.g. `market_hours`). At most one run is active (a partial unique index).
3. **Restart and Continue.** The book is in memory. It is rebuilt from the stored days, each stepped with the end that was in force when it was settled and checked against its stored hash (`sim.diverged` otherwise); a day left `settling` is settled again from its start. Continue extends a complete run to the newest complete stored session; the old days are not recomputed (the last old day keeps its SR-01 "end of range": no entries for the day after it). `Sim:AutoContinue` (default OFF) lets a newer stored session extend a complete run by itself.
4. **Hold-out (open question 1, (a)).** A range that reaches the block in force's cut needs block 1's fresh strategy look. When it is stored, the run may read inside the block: the replay's clamp is widened for that run only (`IReplayFacts.ReadInsideHoldOut`, called only by the simulation; an architecture test pins it), and the days there carry `seen_holdout`. When it is not stored, the start (or Continue) takes it **automatically**, and only after every other check of the request has passed (the decision is pure; the claim is a separate step right after the run is stored, so a start that loses the one-active-run race spends nothing; a claim or ledger failure then cancels the run, and a look already claimed stays queued and recorded as auto) through the HO-01b claim of the seal service (`StrategyAutoLookStep.ClaimAsync`, the existing `holdout` Lab job, actor `system:sim-days`, mode `auto`, the hold-out settings hash in the unlock row and in the run's note; never an owner approval), under the existing auto option `Confidence:HoldOut:AutoUnlock`. Until the look is stored the end is clamped to the day before the block and its embargo and the note says why; an unavailable look (option off, filling block, no version passing every development row, a later block) never counts as taken. Every run and every Continue is a `system_replay` look in the CF-06 trial ledger; a Continue writes its rows (ids fixed by the run and the new end, so a retry writes nothing twice) before it extends the run, so a ledger failure extends nothing and a look is never lost. While a hold-out Lab job is queued or running no second claim is made (so `Sim:AutoContinue` does not search for candidates every minute). The evening seal step still never claims block 1. SR-01's own clamp is unchanged.
5. **Isolation and money.** The simulation writes only `research.sim_days_runs` and `research.sim_days_snapshots` (insert-only snapshots; a run updates only its moving columns; a trigger keeps what it was started with and keeps a cancelled or failed run final) and the trial ledger. No push endpoint, no order, no `XDrishti.Execution` reference. Costs are gross. Versions are today's active ones at the start (hindsight-labelled). Default mode `learning`; default capital `Sim:DefaultCapital` = 1,000,000; playback speed `Sim:DefaultSpeedSecondsPerMinute` = 10.
6. **A day** is the SR-01 session S: its picks are the plan made at the close of S, its trades are those entering or exiting on S (an exit after S is never shown).
7. **The tape (part B).** `GET /api/sim/days/{id}/days/{date}/tape?from=&to=` is a view of a settled day, never a second computation: it reads only the stored day (snapshot, or the settled cursor day), the closing equity of the stored day before it and the trades still open coming into it (one narrow store read, not the whole run), and the stored 1-minute bars of the instruments in play (held in, picked, or entered by `to`) of that day only, in one batched read through the replay's hold-out clamp and the high-water seam cut (a run inside block 1 widens the clamp only with its stored read-through, as settling does). Nothing after `to` is read or named. Events are `entry` and `exit` at their own minute; **there is no stop-move event**, because the replay never moves the stop. The **live board** at `to` (`SimTape.BoardAt`, pure, for the frontend to mirror) shows the open positions with entry, stop, last price (the close of the last bar up to the minute; null before the first) and running P&L; its **equity is realised-only**, as `PaperLedger` counts it (equity at the open plus the day's exits up to the minute), so at the last minute it equals the settled closing equity (parity test: any paging rebuilds the day's trades and equity). Errors: 404 `sim.not_found` / `sim.day_not_found`, 409 `sim.not_settled` / `sim.holdout`, 422 `sim.invalid`. A one-minute page of 50 instruments took 16–21 ms in the integration database (target < 200 ms).

## Consequences
- The hold-out block 1 look is taken by the first simulation that reaches it, if a strategy version qualifies; until then simulations stop at 2026-04-09 and say so.
- A Continue leaves a one-day gap of new entries at the old end (the price of never recomputing stored days).
- The risk limits are the seeded Standard profile (or one named at start), as SR-01; reading the paper account's own profile is open.

## Part C (2026-11-15)
The Day-by-day screen (`/simulation/days`) plays a stored day on a clock from the tape, mirroring `SimTape.BoardAt` in `simBoard.ts`. List endpoints `GET /api/sim/days`, `GET /api/sim/days/{id}/days` and `GET /api/sim/days/settings` are read-only projections. `hasNewSessions` on a complete run's status is true when newer complete sessions can be read, **or** when block 1's strategy look is still free: Continue is how that look is taken (it answers 409 `sim.nothing_new` with the note while the look runs, and extends the run once the look is stored). The status itself never claims the look.
