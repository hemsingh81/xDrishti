# 0207 — A strategy version is pre-registered, the ledger counts every extra look, and a locked hold-out is fixed at the first Lab post and read once by an owner unlock, with enforcement and the honest count as the owner's switches

- **Status:** Proposed (built in CF-06 part A from the owner-Approved spec, 2026-11-04). Becomes Accepted when the owner has read it. **Safety slice: light** (an irreversible record, the unlock; no order, no broker, no network; with every switch off no stored verdict outcome, gate or run key changes, except that a default Lab window now ends before the hold-out block, see 3).
- **Date:** 2026-11-04.
- **Relation to other ADRs:** extends [0059](0059-the-test-ledger-and-the-verdict-evaluator.md) (the ledger and the gates), [0062](0062-robustness-sensitivity-monte-carlo-by-year-and-a-sign-flip-baseline.md) (the sweep points are variants), [0067](0067-validation-harness-and-baselines-purged-folds-and-an-honest-eligibility-rule.md) (the ML hold-out now takes the shared start), [0206](0206-the-lab-verdict-shows-a-cost-stress-at-1x-1-5x-and-2x-and-a-fill-one-minute-later-test-beside-the-outcome-in-report-only-mode-and-enforce-is-the-owners-switch.md) (same switch rule: shown beside, decides nothing by default, settings recorded with the figure).

## Context
Without a written hypothesis, a frozen plan and a hold-out that is read once, every pass is a search result. The ledger counted distinct strategy hashes only, so the candidate exits of a full test, a changed universe, window or cost sheet, and a second look at the same hold-out were free.

## Decision
1. **Pre-registration (D1).** `lab.registrations` holds five plain-text parts per strategy version (counterparty, parameter signs, applicability, expected edge against cost, falsifier), written once by the owner session (`PUT /api/lab/strategies/{id}/versions/{v}/registration`, 409 `lab.registration_frozen` the second time, and also 409 `lab.registration_frozen` when a full or robust run has already frozen the plan of that version, because a registration written after the search began would not be before it), insert-only for the runtime role. `Confidence:Registration:Enforce` (default false): off, a full or robust run without one carries the warning `not_registered`; on, it is refused (422 `lab.not_registered`).
2. **Trial ledger and frozen plan (D2, D3).** `lab.plan_freezes` stores the plan hash (strategy hash, universe, window, cost sheet and its checked state, sweep plan, candidate exits, slippage preset, registration text hash) of a version's first full or robust run, and every later changed plan; a changed plan appends a `replan` row to `lab.test_ledger` (columns `trial_kind`, `extra_trials`; existing rows read `run` and 0). The first full test of a hash adds one look per extra exit candidate. `CountTrialsAsync` returns the parts; N = hashes + sweep points + extra exits + re-plans + nulls.
3. **Locked hold-out (D4).** The block is fixed once, at the first Lab post whatever its method (`EnsureAsync`), from the policy over the stored history (`Confidence:HoldOut`: 20 % share, at least 6 months), and never moves earlier. A **default** window always ends before the block start, enforcement on or off, so a development run never reads the hold-out; `Enforce` governs only the 422 `lab.holdout_touched` for an **explicit** window that reaches the block and the cap of a full or robust PASS at MARGINAL without a kept hold-out. The ML harness takes the same start (`HoldOut.Reserve(rows, months, fixedStart)`, from the stored block; no block gives the old rule bit for bit).
4. **One unlock (D5, D6).** `POST /api/lab/runs/{id}/holdout-unlock` (owner, fresh password verified without opening the step-up window) runs the frozen plan once over the block (the only reader of those sessions; an architecture test pins it) and stores an insert-only `lab.holdout_unlocks` row. The plan hash is recomputed from the run about to execute; if it differs from the version's first freeze the unlock is refused (`lab.holdout_unavailable`), and it fails closed: a version with no freeze at all is refused too ("this run has no frozen plan; post a full run (same explicit window, or a new run) and unlock that run"), and so is a cell whose chosen exit is no longer among the candidates (no fallback to the first candidate). The auto unlock runs after the run is stored as `succeeded`, because the unlocker reloads the stored run. The first look at a block is `fresh`; every later one is `reused_window`, shows its numbers, and cannot count toward a pass. Fresh is decided by the database (a partial unique index on `block_start` where not `reused_window`; a look that loses the race is stored as re-used), not by a read before the insert. A second look by the same version is 409 `lab.holdout_used`. Each stored look writes an account event `LabHoldOutUnlocked` (ids and state words, the mode `owner` or `auto`; the auto path is recorded as `auto` with actor `system:auto-unlock`, never as an owner approval). `Confidence:HoldOut:AutoUnlock` (default false) lets the unlock run by itself only when every development row of the verdict is a pass; an `unavailable` row never counts. One more row, `window_clear`, passes only when the run's window ends before the block starts (`run.To < block.Start`); a run whose explicit window reached the block cannot pass, so the auto path never unlocks it and it cannot burn the block's one fresh slot (the owner path is unchanged).
5. **Rule.** Hold-out expectancy at least 50 % of the development out-of-sample expectancy, above 0, with at least 30 trades; fewer trades is `inconclusive`. All numbers are `Confidence:HoldOut` proposals; the setting hash is stored with each look.

## Owner switches, UNVERIFIED against the database settings
- `CountInFactor` defaults **OFF**: the verdict keeps judging with the distinct-hash count and the honest count is shown beside it (`trials`). The tightening of the gates by the honest count (AC6) happens once, when the owner switches it on.
- `Registration:Enforce`, `HoldOut:Enforce` and `HoldOut:AutoUnlock` are configuration values like CF-01 to CF-05 (`Confidence:*` in the host settings), not yet rows of the versioned settings tables; the move to the database settings (UNVERIFIED) is the CF-00 follow-up.

## What is not built (CF-06 part B and follow-ups)
- The unlock is **synchronous** in the request. A queued `lab_runs` job with method `holdout`, progress and the run log are a follow-up.
- The UI: the registration form, the hold-out card on the report, the unlock button behind the step-up dialog, and their MSW tests are part B.
- The unlock is not routed through `OwnerActFlow` because that flow needs a capability switch and the unlock has none by spec; the audit row is written by the unlocker itself as the P7-12 handlers do.
- Two concurrent first posts can each store a hold-out block with a different start (the unique index is on the start); the earliest stored block is the one every reader sees, the later row is never read (marked `shortcut:` in the code; a single-row index is the follow-up).
- The missing or wrong password of the unlock answers 401 `auth.invalid_credentials` from the shared step-up check (counted toward the lockout), not the 403 the spec names; pinned in the integration test.
- A concurrent first full post of one hash can both add the extra exit looks (an over-count that only makes the luck bar stricter; marked `shortcut:` in the code).
- A longer block set by an owner act, and the `model` kind of unlock (CF-10).

## Consequences
Four new insert-only tables and two ledger columns (migration `AddLabRegistration`). A default Lab window is cut to end before the block and says so in the run's labels, which changes the key of a default-window run posted after the first block exists. The hold-out is spent by the first unlock of a block: later versions can look but cannot pass on it; only forward data refreshes evidence.
