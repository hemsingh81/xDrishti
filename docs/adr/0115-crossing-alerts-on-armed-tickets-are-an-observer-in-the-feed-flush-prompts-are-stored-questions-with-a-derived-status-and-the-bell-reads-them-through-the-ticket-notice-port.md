# 0115 — Crossing alerts on armed tickets are an observer in the feed flush, prompts are stored questions with a derived status, and the bell reads them through the ticket-notice port

- **Status:** Proposed (spec [P7-20](../specs/P7-20-price-crossing-alerts-and-post-trade-prompts.md), built 2026-10-26; the owner's Approved of the spec and of this ADR is still an owner act).
- **Date:** 2026-10-26.
- **Relation to other ADRs:** [0096](0096-the-pre-open-check-arms-only-approved-tickets-as-a-service-move-a-missing-input-invalidates-and-armed-tickets-join-the-feed-set-last.md) (Armed means watched), [0109](0109-plan-tickets-store-indicative-entry-stop-and-target-as-numbers-beside-the-text-rules.md) (numeric levels), [0093](0093-auto-journal-reads-the-stored-fills-matches-them-to-approved-tickets-by-account-instrument-side-and-day-and-stores-a-fill-grade-beside-the-plan-grade.md) (the match key), [0101](0101-plan-notices-in-the-bell-are-derived-on-read-from-the-stored-plan-record-with-a-route-and-no-command-and-nothing-leaves-the-app.md) (the bell: route only), [0022](0022-action-center-and-price-alerts.md) and [0024](0024-live-feed-xd-feed-and-live-prices.md) (P2-09 alerts and the feed).

## Decision
1. **Safety.** Alerts and prompts only. No order, no broker call, no ticket state move, nothing written to `plan_events`. `Planning:TicketAlerts:Enabled` defaults OFF; OFF means no observer is registered, no watched list is read, the bell source answers `[]` and reads nothing (exactly the null source it replaces), and the service `post-trade-prompts` (which starts paused anyway) stores nothing.
2. **An observer seam, not a dependency.** `ILiveTickObserver` (Application/Abstractions/Live); `LiveFlush` passes each flush's firm ticks to the registered observers after the prices are written, guarding every call (a throwing observer is logged, event 4894, and never costs a price). `TicketAlertObserver` is registered by `AddTicketAlertObserver(enabled)` only when the setting is true at start, keeps a watched-ticket cache (`WatchedCacheSeconds`, default 30) and stores at most one `stop_crossed` and one `target_crossed` per ticket (unique `(item_id, kind)`, `ON CONFLICT DO NOTHING`, mute checked in the same statement). Equality counts; a tick outside 09:15:00 to before 15:30:00 India time fires nothing.
3. **Data.** Migration `AddTicketAlerts`: `trading.ticket_alerts`, `trading.ticket_prompts`, `trading.ticket_notice_acks`, insert-only for `xd_app` (per-table grants, schema not re-granted); composite foreign keys tie a crossing and a prompt to a real item of its plan and a prompt to a real paper allocation; the acks table's check demands an `owner:` actor and the shape of each action.
4. **A prompt is a row plus a derived status.** Stored once per (ticket that was Armed, paper account) by the service at 16:45 (each run covers the last three trading days, so a missed run is made up). Its status is computed on read from `portfolio.transactions` (non-voided, any source) by the pure `PromptRules`: matched (`via = journal` when `journal_fills` links the trade to the ticket's entry, else `trade_on_record`), open, `expired_no_fill` after `PromptTradingDays` trading days, or `ambiguous` when two prompts share account, symbol, side and day and a trade fits (nothing is guessed; each names the other item).
5. **The bell reads through `ITicketNoticeSource`.** `TicketNoticeSource` (Application) replaces `NoTicketNoticeSource`. It emits `ticket_level_crossed` (warning, `crossing:{id}`, until the end of the next India day) and `post_trade_prompt` (info, `prompt:{id}`), route `/plans?plan={planId}`, counts and words only. An ambiguous prompt has its own text. Items the owner snoozed (until) or dismissed are not emitted. Owner acts live on the plan screen (`TicketAlertsEndpoints`: GET alerts, POST mute / snooze / dismiss; session and CSRF, actor from the session as `owner:<email>`).

## Resolved ambiguities (noted for the owner)
- **A matched prompt is shown as `resolved` in the bell** until the end of the day after its session (the port contract of P8-15b says "a matched prompt stays visible as resolved for a day"), while spec criterion 8 says a match "removes the prompt from the plan notices". Resolved items do not count in the badge, so the count closes by itself with no click; the bell keeps the line for a day. An `expired_no_fill` prompt is not a bell notice (it stays on the ticket card).
- **The watched cache is refreshed by its time, not by `NOTIFY active_set_changed`.** The change flag lives inside `FeedConnectionManager`; a second consumer would touch the connection code for a gain of at most 30 seconds, since tickets are armed at 09:10 before the 09:15 first firm tick. A mute is also checked in the insert itself, so it takes effect at once.
- **Names.** The service class is `TicketPromptsService` (id `post-trade-prompts`): the no-order tripwire reads a type name containing "posttrade" as an order verb.
- **Log ids 4890 to 4894** (the highest in use at build time was 4883; slices built in parallel should check `LogEventIdTests`).
- **Typed-in trades resolve a prompt but are not journaled or graded** (the journal reads broker rows only); stated on the prompt and in doc 12 section 8, raised as a finding.

- **The mute, snooze and dismiss endpoints stay live while the setting is OFF** (they are insert-only preferences; the feed, the read and the bell stay inert). The observer runs under a 2-second bound per flush; a failed refresh of the watched list is asked again after the cache time; a wick between two flushes, or inside a failed insert, can be missed (a crossing is retried only while the price is still beyond the level). `ListAcksAsync` reads the whole acks table (one row per owner click; a filter is a later change if it grows). A trade the journal linked to another ticket leaves this prompt open or expired, not ambiguous.

## Consequences
- With the setting ON and the database failing, the flush still writes prices and logs one line per failed call.
- A crossing is a last-traded print of a coalesced tick (a spike between two flushes is not seen); it is not protection: nothing rests at a broker.
- Not observed on a real morning; verified on fakes and a real database only.
