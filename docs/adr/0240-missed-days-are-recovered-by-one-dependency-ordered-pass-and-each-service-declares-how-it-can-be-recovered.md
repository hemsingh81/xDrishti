# 0240 — Missed days are recovered by one dependency-ordered pass, and each service declares how it can be recovered

- **Status:** Accepted (owner, 2026-11-09, in chat, as part of the AU programme). Pure planner built in AU-01 (see Amendment 1); the runner is AU-02.
- **Date:** 2026-11-09.
- **Relation to other ADRs:** Supersedes §4 of [0018](0018-services-framework-and-editable-schedules.md) (the reach and the once-per-start rule; the paused rule stays). Tightens [0097](0097-the-p7-phase-check-ten-consecutive-scheduled-sessions-from-stored-plan-runs-and-never-met-on-fewer.md). Keeps [0086](0086-the-fail-closed-nightly-pipeline-gates-one-row-per-attempt-a-null-builder-and-a-paused-service.md).

## Context
Catch-up runs once per start and, for daily jobs, only for the same India day (`CatchUpReach.SameDay`). A machine that sleeps for days is left with holes. Replaying everything naively would be wrong: a plan for a past day is meaningless and a decision-time capture cannot be made after the fact.

## Decision
1. Each service declares a recovery class. `Convergent`: one run closes all missed days (the end-of-day run). `LatestOnly`: one run for the latest closed session. `Dated`: one run per session, oldest first. `TimeBound`: never made up, reported as missed. Unclassified services fail a test.
2. One pass, started by start-up, wake or Data-account reconnect, runs steps one at a time in the topological order of `MustFollow` and `after`. A failure blocks its dependents only.
3. An item is unique per service and occurrence, so a pass after a crash is idempotent.
4. `nightly` is `LatestOnly` and runs only before its review cutoff, with all gates. Runs it publishes are flagged recovered and do not count towards the unattended streak of ADR 0097.
5. Reach is `Recovery:MaxSessions` (default 30, 1 to 250). Paused services are not missed.
6. Trigger `catch_up` is reused, so the `service_runs` check is unchanged.

## Consequences
The scheduler's own catch-up branch is replaced. The phase check of P7 gets stricter. Sessions beyond the reach need the existing Data backfill.

## Amendment 1 (AU-01 build, 2026-11-09; decided by delegation, owner rule "unsettled decisions: research, choose the best, record"; revised after the independent review)
Choices the spec left open, taken for the pure planner. The class of each service is pinned in `RecoveryClassTableTests`.
1. **Classes, with the facts read in the code.**
   - `Convergent`: `eod`, `history-eod`, `options-backfill`, `options-quality`, `shadow-grade` (each reads stored data and fills what is missing; UNVERIFIED for the last four beyond their descriptions).
   - `TimeBound`: `preopen`, `review-cutoff`, `shadow-write`, `paper-capture`, `live-estimates`, `live-capture`, `live-settle`, `live-feed`, `holdings-quotes`, the three recorders, and, after review, `readiness-snapshot`, `decay-monitor` and `ml-monitor`. The snapshot handler stamps its row with today's India date (a recovered run would write a misdated evidence row); the decay and model monitors evaluate the state as of today, are keyed "already checked today", and can propose or apply a kill or rollback, so a run on a stale reading must never happen.
   - `LatestOnly`: everything else, including `nightly`. `post-trade-prompts` looks back `CatchUpTradingDays` (3) trading sessions itself, so one run covers the last three; a missed session older than that is listed superseded although the run does not reach it (known limit, the Data side has no equivalent). Other `LatestOnly` rows are the AU-00 default, UNVERIFIED.
   - No service is `Dated`: with no baseline for "registered since" (item 4) a first run of a `Dated` service would replay the whole reach, so none may be added before AU-02 settles it (a test pins it).
2. **Order.** Kahn's topological order over `MustFollow` and `after`; of the ready services the lowest stage first, then by id. Stage 0 data, 1 learning (follows `eod`), 2 `nightly` and what follows it, derived from the chains. A cycle (a self-follow included) is `recovery.cycle`, naming the services on it.
3. **Occurrences.** One per India date: the first occurrence of the schedule that day, due when at or before now and no run of the service started at or after it. A service on an `after` schedule is due when the service it follows is, and only when every service on the chain is enabled with catch-up on; one that follows an unregistered service has none. Paused, disabled or catch-up-off services are skipped.
4. **Reach.** The `Recovery:MaxSessions`-th trading session back from the latest closed one. Older missed occurrences are `out_of_reach` back to the last run (at most 400 days). A service that never ran has no baseline, so it is missed for the whole reach; AU-02 decides whether a first start needs a "registered since" baseline.
5. **Dependencies.** A service that is not eligible, or was due and made no step (not recoverable, out of reach, or blocked itself), blocks what follows it by `MustFollow` or `after`, transitively: those occurrences are `not_recoverable: <service> did not run` and have no step. A `TimeBound` service keeps its own reason.
6. **Nightly.** One step for the latest session only when that session is the latest closed one and the review cutoff of the next session is strictly ahead; otherwise (or with no next session in the calendar) every occurrence is `not_recoverable: cutoff passed`.
7. **Weekly services.** A run on a weekly schedule (or one that follows it) with the `SameDay` reach is made up only within 24 hours of its time (the same rule as the services' own catch-up); later it is `not_recoverable`, since the run on a weekday fails or would describe a past week.
8. **Setting.** `Recovery:MaxSessions`, 1 to 250, default 30, validated at start-up; not in the visible settings. No reader until AU-02.
9. **Unclassified.** `ServiceConstraints.RecoveryClass` is nullable on purpose: a service that declares none fails the registry test and the planner refuses the plan (`recovery.unclassified`).

## Amendment 2 (AU-02 build, 2026-11-09; decided by delegation, owner rule "unsettled decisions: research, choose the best, record"; approved by delegation)
Choices the spec left open, taken for the runner and the triggers. Tests pin each.
1. **Baseline (settles Amendment 1 item 4).** The planner's "last run" of a service is the later of its latest run and its schedule row (`updated_at`: the first-start seed, a resume, an edit). A service with neither (no row, never run) counts from the start of the process. So a service never run, or paused for a long time and then resumed, is not reported missed for the days before it existed, and the first enablement or first start makes no surprise recovered run; a later wake in the same process finds what was missed since. Best practice for catch-up of a scheduler (cron-style "missed run" handling, Quartz misfire, systemd `Persistent=`): a missed run is measured from the last known good point, not from the beginning of time.
2. **Triggers.** `startup` (the scheduler's start-up, after the stored runs are closed and the first-start rows are seeded), `wake` (a scheduled time of an enabled catch-up service is found more than two minutes late when the scheduler looks: the existing wake detection), `broker_reconnect` (a successful `CompleteConnect` of a Data account) and an internal `resume` (below). All on by default: a pass only starts what the plan says is missed, never an order, and a paused service stays paused, so there is nothing to opt into. A request never waits for the pass and never throws.
3. **Debounce and stacking.** `Recovery:DebounceMinutes`, 1 to 120, default 10: a burst (a laptop waking, a network that flaps, a broker that reconnects) collapses to one pass, while one later in the day still runs; one pass already looks at everything missed. The window is counted from the last accepted trigger, in memory (a restart is itself a trigger and must run); a clock set back lifts it. A request while a pass runs is refused. Refused requests record nothing. Both settings are validated at start-up and are not in the visible settings.
4. **Attempts.** `Recovery:MaxAttempts`, 1 to 10, default 3: one attempt is one normal run with the service's own retries and timeout, so the retries stay bounded twice. A failed item is eligible again at the next trigger until the attempts are used, then stays `failed` and raises one notice per service per day (derived on read from the ledger like the other service notices). The plan for a retry counts from the start of the failed session, because a failed run is a run. A blocked or waiting item never ran and costs no attempt; it runs once what it follows has succeeded or the market hours are over.
5. **Blocking.** A failed step names itself as the blocker of the services that follow it by `MustFollow` or `after`: they become `blocked: blocked by <service>`, independent branches go on. A service that follows one whose latest item is `failed` or `blocked` for the same or a later session (used up its attempts in an earlier pass) is blocked as well, so a service is never run on top of a failure.
6. **One run per occurrence.** Before a step the runner waits for the service to be idle in this process (a scheduled run or a retry in progress), then looks at its latest run: one that succeeded at or after the occurrence's due time is the step's run (linked by `run_id`), so the scheduler and the runner never make two. A run-after chain started by a recovery step keeps the trigger `catch_up`, so a made-up run can never reach the unattended count as an `after` run.
7. **Market hours.** A service with `MustNotOverlap` that is due while the window is on a trading day is `waiting: market hours`; its dependents are `waiting` too. The runner remembers the instant the window ends (+1 minute) and the scheduler's next look after it asks for a pass with the internal trigger `resume`, which is not debounced (it is a continuation, not a new event) but is refused while a pass runs.
8. **ADR 0097.** `plan_runs.recovered` (default false) is set by the nightly run for the trigger `catch_up`, which only the recovery pass uses now that the scheduler's own catch-up is gone. The phase check reports such a session as `recovered_run`, it is not unattended and breaks the streak; a manual run keeps its own state.
9. **Ledger.** `platform.recovery_passes` and `platform.recovery_items` (unique on service and occurrence; the occurrence is the last session of the step, `yyyy-MM-dd`). The runtime role may read, insert and update, never delete. A pass writes its row only when it has steps. An item `running` when a new pass starts belongs to a process that is gone: it becomes `failed: interrupted` and is eligible again (it used the attempt); the pass becomes `interrupted`.
10. **No orders.** Nothing in the runner or the ledger names `XDrishti.Execution` or places an order (an architecture test pins it); it only starts registered services through the normal runner, whose own fail-closed checks (the six gates of `nightly`) apply unchanged. Decision-time captures are `TimeBound` in the planner and are never started.
11. **Review follow-ups (AU-02).** (a) A run with the trigger `catch_up` is no "run of the day" for the end-of-day service: it ignores the once-a-day rule, writes a `manual` data job (never a `daily` one) and, when the Data account cannot fetch, records no skipped `daily` job, so the scheduled 15:50 run is never blocked. (b) A trigger refused because a pass runs or the debounce is on is kept in memory as pending (no ledger row) and one trailing pass starts at the next scheduler look once both are over. (c) A step whose run was skipped (no connected account, source down) is `waiting`, costs no attempt, makes its dependents wait and is tried again at the next trigger (a reconnect included). (d) A run a pass starts does not start run-after dependents: each is a step of the plan, so `TimeBound`, paused, catch-up off, market hours and order are decided there. (e) Settings are read again before each step; the nightly step is planned again, so its cutoff is checked at the moment it would start. (f) When a later occurrence of a service is planned, its older open items become `superseded` (the state is in the check of the migration, which has not been applied anywhere yet), so a failed item cannot hold the baseline back for good. (g) An item that used up its attempts is never overwritten as blocked (its notice stays); a blocked item runs again once its blocker has succeeded. (h) A step that throws fails its item and the pass goes on.
12. **Existing rows and first deploy.** Plan runs written before this change read `recovered = false`, as they were not made up. The triggers have no switch: catch-up already existed per service (the `catch_up` setting of each schedule, default on), a paused service or one with catch-up off is never recovered, and a pass starts nothing that the planner does not find missed. On the first deploy the start-up pass finds nothing for a service that never ran (its baseline is the start) and makes up the missed sessions of every service that has a run or an owner-saved row; the owner sees these as `catch_up` runs in the history of each service.

## Amendment 3 (AU-03 build, 2026-11-09; decided by delegation, owner rule "unsettled decisions: research, choose the best, record"; approved by delegation)

Best practice for verifying a backfill (data-pipeline reconciliation, "trust but verify"): never take a job's exit status as evidence of its output; compare what is stored with what the source of truth says must exist (here the trading calendar), count by the cheapest bounded read, and fail closed on doubt.

1. **A step that succeeded is proved.** A service may declare an `IRecoveryProof`; after a successful step (the step's own run, or a scheduled run that made up the occurrence) the runner asks it for the step's sessions. Only `eod` declares one now. The proof is per tracked instrument and session: stored 1-minute bars (`IBarDayCounts`: the daily aggregate, the dirty range counted in the 1-minute table, never the whole history; one read per instrument for the range of the step) against `ExpectedMinutes` of the calendar, the `market.bar_gaps` record (`ListForAsync`, one read per instrument), whether the aggregates are built (one `ListDirty` read: a dirty range over the session means not built), and the last finished full quality run (it must have succeeded and finished at or after the start of the run). No new store, no scan of bar history.
2. **Per-session states.** `recovered` only when at least one instrument is evidence, none is missing, none is `unfillable` and the quality run is verified; `unfillable` when a gap record says no more can be had (it wins even if the count now reaches the expectation: a stale record is corrected by the next gap check, until then the session is never reported as recovered); `still_missing` otherwise (a count below the expectation, aggregates not built, quality unverified, or no evidence at all). A single missing instrument makes the session `still_missing`: the owner sees the counts (`instruments`, `complete`, `unfillable`, `missing`) per session. Before an instrument's first bar there is nothing to miss, and an instrument without any bar is not evidence (as the gap detection).
3. **Item state `partial`.** All sessions recovered: the item stays `succeeded`. Otherwise the item is `partial` (the run did succeed, the data is not complete): `reason` names the sessions not recovered by date and state, `detail` (new `recovery_items.detail jsonb`, migration `AddRecoveryItemDetail`, which also adds `partial` to the state check; its `Down` turns `partial` into `failed`) holds the per-session state, the quality verdict and the start of the proved run. A proof that cannot be read (a store failed) is `partial` too, with every session `still_missing` (fail closed, and retryable by the rule below). A partial item does not block the dependents in the pass (they are steps of their own), **and the services that read the bars decide for themselves through a real gate** (review of AU-03: the earlier claim that their gates already decide did not hold, because the fresh-data gate looks only at the newest bar, the quality gate never fails on missing minutes, and shadow grading and paper capture check nothing about completeness, so a grade over a hole would never be graded again). `IRecoveryDataGuard` reads the newest `eod` item; when it is `partial` it proves its sessions again now (never a stale answer) and gives a reason if a `still_missing` session at or after the one read remains. The nightly's `fresh-data` gate fails with that reason (the nightly is planned again by the next pass, before its cutoff); `shadow-grade` and `paper-capture` return `skipped` with that reason for a scheduled or catch-up run (a skipped run costs no attempt, makes a pass wait and tries again, and the next run grades or captures every candidate or ticket not done yet, so no grade is lost); the owner's own manual run is not held back. An `unfillable` session never waits (it is permanent).
   - **Re-proof.** Every pass, also one with nothing to run, proves its open `partial` items again (a later fetch, a refetch of the gaps or an owner run may have filled the hole); the item becomes `succeeded` when everything is recovered, else it stays `partial`. There is no attempt count: the proof is a read. One notice per service per day (`recovery_partial`, a warning) is raised while an item stays partial.
   - **Thin instruments (review).** One thin instrument must not make every pass partial. An instrument short by no more than `Data:Quality:MaxMissingPercent` (the quality check's own tolerance, default 1 %, already validated at start-up: no new setting) of the expected minutes is complete; an instrument whose gap record is `unfillable` after the successful fetch is served and counted in the detail. A real hole beyond the tolerance still makes the session `still_missing`. A session in which the unfillable instruments are not outnumbered by the complete ones is `unfillable`, never `recovered` (so an all-unfillable session cannot read as recovered). Shortcut: the "complete must outnumber unfillable" limit is a fixed rule, not a setting.
4. **Review follow-ups (AU-02).** (a) The "its scheduled run failed" short-circuit applies only to a run with the trigger `scheduled` or `after`; a failed owner run (`manual`) does not stop the pass from making the occurrence up. (b) A service that must not run in the market hours is judged by the real session of the day from the calendar (a special session has its own window), and resumes at the later of the minute after the close and its own `StartNotBefore`. Shortcut: `StartNotBefore` is applied only while the session is on; outside the market hours a pass starts the service at once (the scheduler's own rules apply to its scheduled run). (c) The cap on what an automatic end-of-day run asks for is pinned by tests for the normal close, a special session and a holiday.
