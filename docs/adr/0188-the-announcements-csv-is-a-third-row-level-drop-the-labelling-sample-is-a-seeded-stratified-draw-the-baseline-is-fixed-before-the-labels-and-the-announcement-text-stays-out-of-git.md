# 0188 — The announcements csv is a third row-level drop, the labelling sample is a seeded stratified draw, the baseline is fixed before the labels, and the announcement text stays out of git

- **Status:** Proposed (built in P15-07 from the owner-Approved spec, 2026-11-03). Becomes Accepted when the owner has read it. **Safety slice: no** — local files and its own rows; no model call, no network, no order, no setting.
- **Date:** 2026-11-03.
- **Relation to other ADRs:** [0179](0179-filings-come-from-a-local-inbox-folder-with-a-sidecar-that-carries-the-broadcast-time-the-adapter-is-read-only-and-the-public-page-fetcher-is-a-recorded-decision-not-to-build.md) (amended: a third row-level kind), [0180](0180-the-point-in-time-filing-store-keeps-immutable-envelopes-and-answers-what-was-known-at-an-instant-from-the-broadcast-time-plus-a-lag-and-nothing-else.md) (envelopes, visibility), [0181](0181-the-results-calendar-keeps-each-meeting-row-with-its-own-intimation-time-counts-days-in-trading-sessions-to-an-event-session-and-answers-unavailable-for-an-instrument-with-no-entry.md) (the row-loader pattern), [0143](0143-the-eval-grades-the-assistant-by-code-on-a-synthetic-fixture-read-only-with-exact-numbers-intervals-and-an-owner-accepted-baseline.md) (the eval, its sets hash and fingerprint), [0186](0186-the-p15-evaluation-protocols-f-x-p-and-l-count-each-trial-in-the-ledger-before-any-number-store-insert-only-verdicts-with-the-missing-quantity-named-and-feed-the-event-filter-only-through-the-verdict-port.md) (protocol L reads the labels).

## Context
Set D of the assistant eval needs 200 labelled announcements, and the LLM branch of P15 (P15-08) needs a baseline to beat. About 32,000 announcements a year cannot carry a hand-written sidecar each; no slice stored an announcement's category, subject or text; and `eval/sets/announcements.schema.json` does not allow an empty label, so the rows to label cannot be that file. The exchange terms are unverified (P15-00), so third-party text must not enter the repository.

## Decision
1. **A csv with text, one envelope per row.** Header exactly `symbol,broadcast_ts,category,subject,text`, UTF-8 RFC 4180, at most 20,000 rows; sidecar kind `announcement`, symbol `*`. `FilingSidecar.IsRowLevel` is true for `.csv` of `board_meeting`, `shareholding` and `announcement` (ADR 0179 amended). `AnnouncementCsv` (pure) rejects per row with line and column: `bad_row` (symbol, category 1-60, subject 1-300, text 1-4,000, a control character or a bidirectional override), `too_long` (never truncated); per file `bad_header`, `too_many_rows`, `bad_encoding`. A blank or invalid `broadcast_ts` is not a reject: the row is stored `unavailable` with the closed reason and counted. Unknown and ambiguous symbols reuse the P15-02 resolution. Text keeps its characters as given (CRLF to LF, ends trimmed): the spec asked for NFC, but the app runs with invariant globalization where `string.Normalize` does nothing, so a normalisation that varies by runtime was left out.
2. **The stored text and the hash.** The canonical text of a row is one JSON object with a fixed key order (kind, instrument id, time to the microsecond or `unavailable:reason`, category, subject, text). Its SHA-256 is the envelope's `content_sha256`, so the same row in two files, or on a rerun, is one row. `LoadAnnouncementsHandler` writes the text into the files store first (`IFilingFiles.CopyRebuildableAsync`), then stores the envelope (kind `announcement`, no period, so never grouped, never superseded) and its `filings.announcements` row in one batch (`AnnouncementStore`: one round trip, `ON CONFLICT DO NOTHING`, both rows or neither). The text file is rebuildable from the inbox csv, so it is written without a flush to disk per file and a file that does not hash to its own name (lost in a crash) is replaced by the right bytes on the rerun; every other copy keeps the durable rule of ADR 0180. 32,000 rows load in under 30 s (test); with a flush per file they took 96 s on the development machine. Logs and the counts line carry counts and closed codes, never a category, subject, text or file name. The loader runs in `filings-ingest` after the other loaders; the disk guard of the ingest applies. An announcement as a `.txt` or `.pdf` stays an ordinary envelope: no `filings.announcements` row, counted by `sample` as `without row metadata`, never sampled.
3. **The baseline is fixed first.** `eval/sets/announcement-baseline.json` maps exchange categories to `material` or `non_material`; a category not listed is `non_material`; names compare whole, ignoring case and spacing. The starting list is the spec's, the names UNVERIFIED and adjusted to the owner's files before the first sample. `AnnouncementCategoryBaseline.Predict` is a pure lookup. The file's SHA-256 goes into the sample, the manifest and, while the labelled set exists, the sets hash of the eval fingerprint; `import` refuses a baseline changed since the sample (`eval.baseline_changed`).
4. **The sample.** `AnnouncementSampler` (pure, version 1) draws 240 (200 main and 40 reserve) from state-ok announcements in an India-date range: half from baseline-material categories and half from the others (a half with fewer than its share gives all it has and the other half makes up the difference), within a half proportional across (category, India-year) strata with one place for every non-empty stratum when places allow; with more strata than places the strata whose hash ranks first get one place each. Every choice is the SHA-256 of seed and filing id (or stratum), never a position in the input, so any insert order gives byte-identical files. Fewer than 240 eligible rows is refused (`eval.too_few_announcements`, the count named). Each row records its stratum counts and the inclusion weight (eligible over sampled). Ids `a001` to `a200` are main, `a201` to `a240` reserve, in a fixed order.
5. **Files.** `sample` writes `data/eval/announcements/to-label.csv` (with the text, label blank) and `sample.json` (seed, range, baseline hash, strata, weights and a hash of each row's text columns; no text), folders 0700 and files 0600 through a temporary name. A sample that exists is never replaced by a different one (`eval.sample_exists`); the same sample again is a no-op. `import FILE` checks every id is from the sample and appears once, each row's text columns hash as at the sample, labels are `material`, `non_material` or `unsure` (case ignored), each `unsure` main row is replaced by the next reserve row which must then carry a definite label (an `unsure` reserve is passed over), and 200 definite labels remain (`eval.too_few_labels`); a refusal names the row, never a cell. It writes `data/eval/sets/announcements.jsonl` (the P9-09 schema, `source` `nse-announcement`, `category` the exchange category) and the committed `eval/sets/announcements.manifest.json` (ids, filing ids, row hashes, label-file hash, sampler version, seed, baseline hash, class counts; no text); the same file again writes nothing.
6. **Set D reads the file.** `EvalFileSet` gains the labelled file, the manifest and the baseline (null when absent). With the file valid and 200 rows or more set D reports `not_evaluable: no classifier yet (P15-08)`; absent or too short, the old state; invalid, the set fails with the line named (never the text). The sets hash includes the manifest, the label file's hash and the baseline only while the labelled file exists, so a baseline accepted before P15-07 is not made stale. `xd eval run --set events` no longer stops at "Nothing was run".
7. **Reporting.** `xd eval announcements show` prints the class counts, the label distribution per half, the baseline's precision on the sample (and weighted by the inclusion weights), says that precision on this sample is a stratified estimate, and prints the formula of the population-weighted precision that P15-08 will print. Without labels it says "waiting for labels".
8. **Where the text lives.** Only under `data/` (git-ignored). A test fails if a labelled-text file or a `text` key is under `eval/`, or if `.gitignore` stops covering `data/`. `scripts/xd-eval.sh announcements` mounts `data/eval`, the repo's `eval/` (for the manifest) and the filings store read-only for that verb only; the compose file is unchanged.
9. **Layering.** The announcement parser, store, candidates port, sampler, label checks and files port are named only by the loader, the three verb handlers, the eval's set-D reader and their implementations (architecture test). No migration: `filings.announcements` and its insert-only grants exist (ADR 0180); nothing is granted to `xd_exec` or the read roles.

## Consequences
- With the owner's csv and labels, set D has 200 rows to grade; until then it is `not_evaluable` and the verbs say they wait.
- `FilingFiles` gains `CopyRebuildableAsync`; the architecture test that pinned `overwrite: false` now pins the one replace path.
- A sample cannot be redrawn without the owner moving `data/eval/announcements/`.

## Known limits
- **The owner's labels are one person's judgement**; the definition in `eval/README.md` is the only guard. Precision on this sample is a stratified estimate.
- **Category names are UNVERIFIED**; an unknown category falls to `non_material`.
- **With more strata than places** (say 120 categories over several years) some strata get no row; `sample.json` lists them with `sampled` 0 and `show` counts them.
- **No Unicode normalisation** (invariant globalization): the same text typed in two normal forms is two rows.
- **A spreadsheet can mangle the labelling file** (a leading `=` in a subject is a formula to some tools, dates may be reformatted); a changed cell is refused, so edit only the label column in a text editor or export as csv UTF-8 without touching the others.
- **A crash right after a load** can lose the unflushed text files; the rerun rewrites them from the inbox.
