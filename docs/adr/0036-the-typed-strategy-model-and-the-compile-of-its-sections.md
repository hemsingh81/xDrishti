# 0036 — The typed strategy model and the compile of its sections

- **Status:** Accepted (owner, 2026-10-18: "yes to all recommendations" on the spec [P3-02b](../specs/P3-02b-typed-strategy-model-and-compile-of-its-sections.md); its open questions 1 to 6 are settled as recommended). Built the same day.
- **Relation to other ADRs:** Builds on [ADR 0034](0034-the-rules-expression-language-lint-and-compiler.md) (the language of one condition; Amendment 3 and Consequences get a dated note) and [ADR 0035](0035-per-session-features-keep-the-history-of-the-session-only.md) (the first evaluations of a session). Honours [ADR 0002](0002-config-and-strategies-in-app.md) (a strategy is stored text with a hash; the model is a stored contract). Hands the hash to P3-02c.
- **Date:** 2026-10-18

## Context
The simulator (P3-03) and the live engine must run a **strategy**, not a single condition: setup, trigger and invalidation lists, an entry, a stop, exits, time rules and filters. The old roadmap row "P3-02b: the strategy file around the language" mixed three things that have different risks: the typed model and what compiling it means, the YAML and the JSON Schema, and storage with its hash. This slice is the first: **a typed model and the compile of its sections, with no YAML and no storage**. Three forces shaped it. A strategy is stored and hashed (ADR 0002), so the names of the model are a contract that must not drift by accident. A mistake must be fixable: every problem needs a *path* in the model and, inside a condition, the span in the text the author wrote. And the 64-level limit of one condition (ADR 0034 Amendment 3) would be reached by an `all:` list of about 60 conditions if the list were turned into one `and` chain.

## Decisions
1. **The model, schema 1.** A new documented public namespace `XDrishti.Strategies.Model` in the existing project (no new project, no package): `StrategyDefinition` (schema, id, style, entry timeframes, sides, at most four `StrategyParam`s, `Buy` and `Sell` `SideRules`, `TimeRules`, filter names), `SideRules` (`setup`, `trigger` and `invalidate` `ConditionList`s of `all`/`any` condition texts, `EntrySpec`, `StopSpec`, candidate `ExitSpec`s, `OverlaySpec`s), `Quantity` (a literal or the name of a parameter) and the closed sets `Style`, `ListMode`, `EntryKind`, `StopKind`, `ExitPolicy`, `OverlayKind` (the filter names are two constants). Every model type is a sealed record, a readonly record struct or an enum, one public type per file. `StrategyDefinition.CurrentSchema` is 1. A snapshot test (`ModelSchemaSnapshot`, a C# raw string written by hand, no file I/O) pins every public type with its members, the enum values, the exit tables, the filter names and the problem codes (46; 47 since Amendment 1); renaming or removing one fails it with "a stored contract". The tables of the validator and of the tests are separate literals.
2. **Value equality, by hand.** A C# record compares a list by reference. The model records that hold lists (`StrategyDefinition`, `SideRules`, `ConditionList`, `ExitSpec`, `OverlaySpec`, `ExitParameter`) write `Equals` and `GetHashCode` through one internal helper (`ListEquality`) that compares element by element; a null list is not an empty list. The alternative, an immutable-list type of our own in every field, would have made every builder and test wrap its lists. Two definitions built twice from the same data are equal; the round trip of P3-02c and the seeding of P3-02d compare definitions.
3. **Lists are evaluated at list level and never joined into one text.** Every item of every list is compiled as its own condition with the context of the evaluation timeframe and the declared parameters. An `all` list is the Kleene AND of its items and an `any` list the Kleene OR (`ListFold`, the same functions the compiled conditions use). *Rejected:* joining the items with parentheses (which add no level) up to about 60 and splitting beyond, mapping the spans of the joined text back to the items. It needs a threshold, a span map, and type errors that mention an `and` the author never wrote. At list level there is no threshold: an `all` list of 100 conditions compiles while the same 100 joined by `and` give `strategy.syntax.too_deep` (a test shows both). The aggregate of the problems of many items has a cap of its own (decision 14).
4. **All sections are evaluated together at each closed bar of the evaluation timeframe, and `Fires` is the one definition of the entry condition.** This settles [doc 07](../design/07-strategies.md) §1 ("setup evaluated tonight") against the example of [doc 11](../design/11-strategy-lab.md) §2, which puts `time` and `rsi(…)` in `setup`. An entry is possible when `setup` is true, `trigger` is true and `invalidate` is not true. `SideEvaluation(Setup, Trigger, Invalidate)` has `Fires = Setup == True && Trigger == True && Invalidate == False` and `Invalidated = Invalidate == True`: unknown is not true (ADR 0034 decision 3), so an unknown invalidation neither fires nor invalidates. A side without a setup list has a true setup, one without an invalidate list a false invalidation. The simulator uses `Fires` and never combines the three truths itself; the latch ("once invalidated, no entry that day"), the counters and the decision-time trace are the simulator's. Every item is evaluated at every call (none is skipped) so that a run can count true, false and unknown per path. Which parts of a setup are knowable at the previous close, for the nightly shortlist, is the planner's business (P7).
5. **The sentinel feature.** `CompiledSide.Features` is THE list a frame is created from: the features of the conditions in the order of the model, then the stop's level and ATR, then those the exits read, then a `close` on the evaluation timeframe **when no feature is on it**. A frame cannot be created from an empty list and answers `BarClosed` only for a timeframe it has a feature on; a side of `time >= "09:45"` alone, or one that reads only `tf("1h")` features, has neither. The specs of the stop and the exits are built from `IndicatorInfo.DefaultSpec` and judged by the catalog through one shared internal `CatalogCheck` (extracted from `BindingScope`; the language did not change), so periods, whole numbers, whole bars of an opening range and timeframes are the catalog's rule, and equal specs are one feature. `Bind(frame)` checks the layout (`HandleOf(Features[i]) == i`, the history depth) and throws an `ArgumentException` that names the feature or the depth.
6. **The closed kind sets, accepted by the model and refused by name by the simulator.** Entry kinds `at_close`, `stop_above_high`, `limit_pullback`; stop kinds `fixed_pct`, `atr_mult`, `swing_low`, `swing_high`, `bar_low`, `bar_high`, `or_opposite`; exit policies `FIXED_RR`, `PARTIAL_BE`, `PARTIAL_TRAIL`, `ATR_TRAIL`, `STRUCTURE_TRAIL`, `EMA_TRAIL`, `PYRAMID`; overlays `time_stop`, `event_exit`; filters `not_event_day`, `min_turnover`. The model and the compile accept all of them; P3-03 runs only what it can and refuses the rest by name. The two filters are warnings at compile (nothing in P3 evaluates them: no results calendar, no liquidity data) and the simulator refuses a run whose filter list is not empty.
7. **`level` is not a stop kind of schema 1.** Doc 11 lists it, nothing defines it, and a computed price cannot be written in the language. A kind that can never compile would be pinned in a stored contract for nothing; P3-02c refuses `type: level` by name.
8. **Overlays.** `TIME_STOP` and `EVENT_EXIT` are not candidates: `exits` lists the candidate policies the Lab replays on the same entries (doc 08 §3), and `overlays` holds at most one of each kind, applied to every candidate (doc 16 `exits.overlays`). `SESSION_EXIT` and `MAX_HOLD` are always on and come from the time rules.
9. **Swing stops are N-bar extremes.** `swing_low` and `swing_high` are the lowest low and the highest high of the last `lookback` closed bars of the stop timeframe, the trigger bar included, not the last confirmed pivot (which is known only n bars late and may not exist). A pivot-based stop can be added later as a kind of its own. The optional `timeframe` of a stop (the evaluation timeframe by default; not for `fixed_pct`) reads the last closed day, today excluded, exactly as `tf("1D").lowest(n)` does.
10. **Time rules are the one place for windows, and a stored strategy is self-contained.** `first_entry` and `last_entry` (inclusive; 09:15 to 15:30 on the minute), `square_off` (intraday, required) and `max_hold_sessions` (swing, 1 to 5, required), in order `first_entry ≤ last_entry < square_off` (and, with `last_entry` absent, `first_entry < square_off`, reported at `square_off`); no entry time on a 1D evaluation timeframe (a daily bar has no clock time). Nothing is read from configuration: the numbers of the `styles` block of doc 16 are not defaults for a missing rule, so that the same text (and hash) means the same behaviour (NFR-3 of doc 02). `BoundSide.InEntryWindow` answers `first ≤ time ≤ last` with `time` read by the same function as the keyword (`Kernel.CloseMinute`), for the clock of the **step**; telling a late bar from yesterday's and a step that closed two bars is the scanner's (P3-03), because the library may not read `BarClosed`, `TryLastClosed` or `ClosedBarsAt`.
11. **The `invalidate` list is optional.** It is the `invalidation` row of doc 07 §1 ("cancel if…"); it covers "gap beyond trigger" (a condition on `today.open` against a level). "Stop level hit before trigger" cannot be written as a condition and is not covered.
12. **Style and timeframes (the author's proposal; the owner agreed).** An intraday strategy lists 5m to 1h and not 1D; a swing strategy lists 30m, 1h and 1D and not 5m, 10m or 15m (doc 07 §3 and §4); a swing strategy cannot list SELL (futures only, doc 07 §7). The rule is `style_timeframe_mismatch` / `swing_sell_unsupported`.
13. **`Side` is `XDrishti.Domain.Research.Side { Buy, Sell }`, not `Portfolio.TradeSide`.** `TradeSide` is a stored ledger fact with its own rule ("stored by name, never rename a value"); a research side has its own schema versions (the strategy model, the simulated trade). The two are mapped by name where a trade meets a ledger row. `Side` is the only public type added to the Domain; P3-03 adds `SimTrade` and `ExitReason` next to it.
14. **Problems are data with a path; the codes and the cap.** `strategy.model.*`, 46 codes in six groups (47 since Amendment 1) (`ModelCodes`, in `Compilation`, so that `Model` holds data only), plus the codes of the language unchanged, each as a `LocatedProblem(Path, Problem)`. A model problem has the span (0, 0, line 1, column 1): it has no text. Errors come first, in the order of the model (schema, id, style, timeframes, sides, params, then for the side compiled setup, trigger, invalidate, entry, stop, exits, overlays, then time rules and filters), at most 100, with one `too_many_problems` (an error) when some were dropped; warnings and information follow, at most 100, with one `too_many_problems` of severity information. The compile fails on errors only. A fault in a declaration (a repeated parameter, a bad name) is reported once and the parameter is still offered to the items as written, so it does not cascade. `side_rules_missing` and `sell_block_missing` are reported only by the compile of that side; the sell block's absence names P3-02e.
15. **Every parameter of a policy P3 does not run is provisional until P4 runs it.** The compile checks `FIXED_RR` (`rr`, a list of one to ten values in (0, 10]) and `PARTIAL_TRAIL` (`book_pct` in (0, 100), `t1_rr` in (0, 10], `trail_atr_mult` in (0, 20], optional whole `atr_period`, default 14, read on the evaluation timeframe) and only the *shape* of the other five candidates and the two overlays (a name `[a-z][a-z0-9_]*`, once; one to ten values, each a finite number or a declared parameter). A name or a range of a provisional parameter may change in P3-02b2 or P4 **without a new schema version** as long as no stored strategy uses it (the three built-ins use `FIXED_RR` only). The exit table is data (policy to parameter specs), so a new policy is a row. *(Amendment 1, 2026-10-19: P3-02b2 wrote the full tables of the other five candidates and the two overlays, accepted but still provisional until P4's spec; the shape-only check is gone.)*
16. **The hash is not taken from the printed text.** `ExpressionPrinter` prints `rsi()` and `rsi(14)` differently although they are one feature. The model keeps each item's text as written (`CompiledCondition.Source`) and no field that depends on a spelling; P3-02c takes the canonical text and the hash from the plan (the canonical `FeatureSpec`s and the bound tree). Until then the run record of P3-04 stores the definition as canonical JSON.

## Consequences
- **What exists.** `StrategyCompiler.Compile(definition, evaluationTimeframe, side)` → `StrategyCompileResult(Compiled, Problems)`; `CompiledSide` (items with their paths, entry kind, `StopPlan`, `ExitPlan`s, `OverlayPlan`s, `SessionRules` in minutes, filters, `Features`, `HistoryDepth`, `NeedsContext`, `NeedsExpiryDays`, `Warnings`, `Bind`); `BoundSide` (`Evaluate(frame, Span<Truth>)`, `InEntryWindow(frame)`; zero allocation, tested over 100,000 steps of a 20-feature frame with ten items). Internal seams, one sealed class each: `ModelChecks`, `TimeRulesCheck`, `StopCompiler`, `ExitCompiler` (with the table in `ExitTables`), `SideCompiler`, `QuantityReader`, `ProblemSink`, `ListFold`. The library still references only Domain and Indicators (and Superpower); the seven `FeatureFrame` members it may use are unchanged; no `src` project references it yet, so the compiler warm-up rule stays vacuous until P3-03 lands `StrategyWarmupService`.
- **Looking ahead through the side.** The truncation and future-perturbation property of ADR 0034 is run through `BoundSide.Evaluate` and `InEntryWindow` for 60 random sides (the three truths, `Fires` and the window are the same when later bars are removed or replaced; a feeder that reads the next bar is reported). It guards the feed through the new layer, as it does for a condition; look-ahead through the *caller* is P3-03's property.
- **Interpretation recorded.** The criterion "the problems of an item equal those of `ConditionCompiler.Compile` of the same text" is read as two sequences: the errors in the language's order and then the warnings and notes in the language's order, because decision 14 lists errors first for the whole strategy. A warning that the language would have put between two errors comes after them.
- **Warm-up.** `CompilerWarmup` also compiles 10 valid and 19 invalid strategy definitions (`WarmupStrategies`) and binds and evaluates the valid sides once; unit tests prove that between them they use every entry kind, stop kind, exit policy and overlay, both sides and both styles, and reach every group of codes. `CompilerWarmup.Outcome` gained the counts of strategy definitions compiled, bound and refused. Measured (Apple M4 Pro, Release, quiet machine, fresh process): the warm-up now takes **92–95 ms** (it was 60–63 ms; the budget is 150 ms); a warm `Compile` of the example side of doc 11 (4 items, 7 features) takes **0.19 ms** (budget 3 ms), the model checks and the merge adding **0.02 ms** to the compile of the four items (budget 0.5 ms); the first compile of that side after the warm-up takes **0.5 ms** (budget 20 ms; 19 methods left to JIT, 0.7 ms); process-cold it takes 34 ms (reported); `Evaluate` of a side of ten simple items takes **31 ns** per call (budget 0.4 µs) and `InEntryWindow` 15 ns. These are explicit benchmarks (`StrategyBenchmarks`) that `scripts/check.sh` skips; they are three more unguarded budgets and are named in ISS-12 and ISS-16 of the [roadmap](../design/18-roadmap.md).
- **Names of the build.** The model and the compile follow the sketch of the spec. Where the build chose: `ModelCodes` lives in `Compilation` (next to the compiler that reports it) and the two filter names are an internal list, so that the public namespace `Model` has only records and enums; a catalog problem about the timeframe of a stop that has no timeframe of its own is reported at `buy.stop`; the default period of the ATR of `PARTIAL_TRAIL` is part of the plan's values (`atr_period` 14); a null item of a list is the language's `strategy.syntax.empty`; the null lists of a hostile definition are read as empty rather than refused with an exception.
- **Hand-offs.** P3-03: uses `SideEvaluation.Fires`; counts a step where setup and trigger are true and invalidate unknown as `UnknownInvalidation`; refuses a side with overlays, filters, or any exit other than one `FIXED_RR` by name; reuses `Side`; owns the `StrategyWarmupService`, the scanner's stale and lost steps and the latch. P3-02c: reads YAML into this model, refuses `type: level` and any trail type other than ATR by name, writes `trail: { type: ATR, mult }` as `trail_atr_mult`, takes the hash from the plan. P3-02b2: the exit tables.
- **Tests.** `XDrishti.Strategies.Tests` 7,119 → 7,560 (441 new, one family per criterion of the spec; 9 explicit benchmarks, 4 of them new), `XDrishti.Architecture.Tests` 134 → 136, `XDrishti.Domain.Tests` +2 (`Side`). Last `scripts/check.sh`: 20,670 tests, 0 failed, 19 skipped (the explicit benchmarks among them).

## Amendments

### Amendment 1 (2026-10-19, P3-02b2): the exit tables of schema 1, ACCEPTED and PROVISIONAL until P4's spec
Decided by the owner on the spec [P3-02b2](../specs/P3-02b2-exit-policy-tables-of-schema-1.md) (2026-10-19, "All six, recommended answers"). It replaces the "shape only" part of decision 15. Schema 1, the records, the enums and the hashes of every definition that has ever been run are unchanged (`DefinitionJson` writes the records, not the compile); there is no new schema, no engine, run-record or `SimTrade` version, and no new ADR number.

**Status of the names.** Every table below except `FIXED_RR` is **ACCEPTED but PROVISIONAL until P4's spec**: P4 has no spec and no walker, so the break-even offset, whether a trail may move down, what activation means, a pyramid trail other than the ATR and the per-bar series of the features are not known. Nothing is stored before P3-02d, so a rename is free until the first stored use. The names that P4's spec confirms or changes become final by **Amendment 2** (the roadmap exit check: "final or renamed before any stored strategy uses them"). No claim of finality is made.

**The tables** (`*` required, `L` list of one to ten values, `W` whole, `(c)` the range and the whole-number rule come from the indicator catalog, so a failure is `feature_invalid`):

| Policy / overlay | Parameters | Reads on E |
|---|---|---|
| `FIXED_RR` | `rr`* L (0,10] | none |
| `PARTIAL_BE` | `book_pct`* (0,100); `t1_rr`* (0,10]; `t2_rr`* L (0,10], each above `t1_rr` | none |
| `PARTIAL_TRAIL` | `book_pct`*; `t1_rr`*; `trail_atr_mult`* (0,20]; `atr_period` W (c), default 14 | `atr` |
| `ATR_TRAIL` | `mult`* L (0,20]; `activate_at_rr`* [0,10]; `atr_period` W (c), default 14 | `atr` |
| `STRUCTURE_TRAIL` | `lookback_bars`* W (c) | `lowest(n, source=low)` (BUY) / `highest(n, source=high)` (SELL) |
| `EMA_TRAIL` | `length`* W (c) | `ema(n)` of the close |
| `PYRAMID` | `initial_pct`* (0,100]; `add_at_rr`* L (0,10] strictly increasing; `add_pct`* L (0,100], as many as `add_at_rr`, `initial_pct` plus the sum at most 100; `max_adds`* W 1 to the length of `add_at_rr`; `trail_atr_mult`* (0,20]; `atr_period` W (c), default 14 | `atr` |
| overlay `time_stop` | `min_progress_rr`* [0,10]; an intraday strategy gives `intraday_bars` W 1 to `ceil(375 / T)` (5m 75, 10m 38, 15m 25, 30m 13, 1h 7), a swing strategy gives `swing_sessions` W 1 to 5 and below `max_hold_sessions`; the field of the other style is `field_not_used` | none |
| overlay `event_exit` | `days_before_results`* W 1 to 10 | none |

**Rules.**
1. A failing row uses the existing codes: `field_missing`, `field_not_used`, `field_shape` (wrong count; also a non-whole value in `max_adds`, `intraday_bars`, `swing_sessions` or `days_before_results`), `value_out_of_range` (a bound, or a relation, at the value that breaks it), `feature_invalid` (a non-whole or out-of-range `atr_period`, `lookback_bars` or `length`: the catalog judges the feature) and `duplicate_exit`. Every field is reported; a relation is checked only among values that compiled.
2. The look-ahead rule for the exits. Every feature an exit reads is a plain feature on the evaluation timeframe (the exit tables have no expression-valued field, so there is no `tf()` and no lagged read). The values are **as of the closed bar**: a value computed at the close of bar *k* may move a stop or signal an exit only from the first minute after that close, never inside bar *k*; a feature that is not ready gives no update; `time_stop` and `event_exit` use only quantities known at entry. The compile cannot enforce what the walker does with the number, so **P4's spec must carry this as a property**: truncating all data after bar *k* changes no exit decision at or before *k*, and a negative control that uses bar *k*'s value inside bar *k* fails it.
3. **One new code**, `strategy.model.exit_not_evaluated` (a warning, one per candidate other than `FIXED_RR` and one per overlay, at `buy.exits[i]` or `buy.overlays[i]`): a model-time hint that nothing runs the policy yet. `strategy.model.*` has **47 codes**. The set of policies a simulator runs is the constant `ExitTables.RunBySimulator` (today `FIXED_RR`), which P4 edits together with the refusal in `Simulator.RefuseWhatItCannotRun`; a test in `XDrishti.Simulation.Tests` asserts that the warning and the refusal agree.
4. The model may describe more than the simulator can run: a correct table compiles and `Simulator.Create` refuses it by name (`simulation.unsupported_exit`, unchanged); a bad table is the compile's own problem.

**Reachable range.** Because the relations apply, two bounds of the spec's ranges are not reachable: `t1_rr` can be at most just below 10 (a `t2_rr` above it must still be at most 10) and `add_pct` and `initial_pct` can never reach 100 together with the other (their sum must be at most 100). The ranges stay as written (they are the sanity bounds of a single value); the relation is what refuses the pair.

**Dropped from doc 16.** `cap_total_risk_to_initial` (the cap of the total open risk at the initial 1R is the always-on rule of doc 08 section 4), `trail` of `PYRAMID` (the trail of the combined position is the ATR, written `trail_atr_mult` and `atr_period`, as `PARTIAL_TRAIL` writes doc 11's `trail: { type: ATR, mult }`) and `enabled` of the overlays (an overlay that is listed is on) are not parameters of schema 1 and are refused by name (`field_not_used`) with these explanations. Doc 16's single `time_stop` example with both `intraday_bars` and `swing_sessions` is not valid under the by-style rule and became two examples. `EMA_TRAIL` is a scalar `length`; the numeric fields that are lists are exactly `rr`, `t2_rr`, `mult`, `add_at_rr` and `add_pct`; relaxing a scalar to a list later breaks no stored text, the reverse does.

**Plumbing.** `StrategyCompiler` passes `definition.Style` and the raw `definition.TimeRules?.MaxHoldSessions` through `SideCompiler.Compile` into `ExitCompiler` (as an `ExitContext` with the side and the evaluation timeframe). `TimeRulesCheck` is **not** moved before the side, so the order of the problems of a definition is unchanged and the time rules are still reported once, after the side; the `swing_sessions` relation is checked only when the raw value is 1 to 5, otherwise the time rule's own problem stands. The relations are one internal static class, `ExitRelations`; `ParameterSpec` gained a whole-number flag and `ExitTables` an `OverlayChecked` table. `XDrishti.Strategies` makes its internals visible to `XDrishti.Simulation.Tests` (for the agreement test above).

**The tightening of criterion 11 of P3-02b, and the tests that changed.** The "shape only" rows for the five policies and the two overlays are replaced by these tables: a definition that compiled by shape with a name the new table does not have (`atr_mult`, `lookback`, `ema_len`, `minutes`) stops compiling, which is allowed because no stored strategy uses these policies (the built-ins use `FIXED_RR` only). Tests changed or replaced: the shape-only rows of `ExitTests`, the doc 11 example's warnings (`CompiledSideTests`: the two filter warnings and `exit_not_evaluated` at `buy.exits[1]`), `ModelSchemaSnapshot` (addition only), the warm-up sets (`WarmupStrategies`), the order test of `ProblemOrderAndFuzzTests` and four Simulation fixtures (`SimulatorSeamTests`, `SimulatorCreateTests`, `SwingCreateTests`, `ScannerSeamTests`) that used the provisional names. The golden files and run records are untouched.

### Amendment 2 (2026-10-21, P4-02 and P4-03): the tables of `PARTIAL_BE`, `PARTIAL_TRAIL`, `time_stop`, `ATR_TRAIL`, `STRUCTURE_TRAIL` and `EMA_TRAIL` are final
**P4-03** (spec [P4-03](../specs/P4-03-the-trails-atr-structure-and-ema.md), Approved 2026-10-19, "yes" to questions 1 to 7; built in [ADR 0051](0051-the-trails-atr-structure-and-ema.md)): the names `mult`, `activate_at_rr`, `atr_period` (`ATR_TRAIL`), `lookback_bars` (`STRUCTURE_TRAIL`) and `length` (`EMA_TRAIL`), their ranges, the feature each reads on the evaluation timeframe (`atr`; `lowest(n)` of the low for a buy and `highest(n)` of the high for a sell; `ema(n)`) and the absence of an activation for the last two are **no longer provisional**: a simulator runs them, and a rename would break a stored run. An activation or an offset for `STRUCTURE_TRAIL` or `EMA_TRAIL` would be a later optional name added by a further amendment.

**P4-02** ([P4-02](../specs/P4-02-partial-exits-and-the-time-stop.md) D13, built in [ADR 0050](0050-partial-exits-the-trail-from-t1-and-the-time-stop.md)) confirms the names and ranges of the tables of `PARTIAL_BE` and `PARTIAL_TRAIL` and of the overlay `time_stop` as Amendment 1 wrote them (`book_pct`, `t1_rr`, `t2_rr`, `trail_atr_mult`, `atr_period`, `min_progress_rr`, `intraday_bars`, `swing_sessions`; no rename), so their provisional status ends too. The break-even stop is the exact entry and `PARTIAL_TRAIL` has no break-even move (both the walker's rules, not parameters).

A simulator runs one value of each list parameter at a time (`rr`, `mult`, `t2_rr`); the lists stay in the model for the comparison of candidates (P4-05). The compile is unchanged: `ExitTables.RunBySimulator` holds `FIXED_RR`, the two partials and the three trails and `ExitTables.OverlaysRunBySimulator` holds `time_stop`, so `exit_not_evaluated` is no longer given for them. `PYRAMID` and `event_exit` keep the status Amendment 1 gave them until P4-04 and P4-07.
