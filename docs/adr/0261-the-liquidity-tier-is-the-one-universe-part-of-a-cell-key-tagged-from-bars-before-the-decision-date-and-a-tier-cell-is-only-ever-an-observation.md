# 0261 — The liquidity tier is the one universe part of a cell key, tagged from bars before the decision date, and a tier cell is only ever an observation

- **Status:** Proposed (spec [BK-11](../specs/BK-11-universe-cell-dimension-and-strategy-universe-link.md), approved 2026-11-03; first part built 2026-11-11). Becomes Accepted when the owner has read it.
- **Date:** 2026-11-11.
- **Relation to other ADRs:** [ADR 0193](0193-the-cell-key-gains-a-reserved-universe-part-and-an-expression-part-written-with-the-fewest-trailing-parts-so-every-stored-key-stays-byte-identical-and-only-cash-cells-reach-a-decision.md) (the reserved seventh part and the fewest-trailing-parts rule, widened here), [ADR 0064](0064-cell-statistics-bayesian-shrinkage-recency-weights-and-point-in-time-snapshots.md) (Beta shrinkage, insert-only snapshots), [ADR 0146](0146-a-regime-label-exists-only-where-the-stored-context-is-ready-it-is-read-before-the-decision-day-and-a-regime-cell-never-mixes-the-two-bases.md) (the pattern this follows), [ADR 0204](0204-a-cell-shows-a-shrunk-expectancy-pulled-toward-its-leave-one-out-parent-by-an-estimated-between-cell-variance-in-report-only-mode-and-gate-is-not-offered-until-the-lower-bound-is-validated.md) (report-only shrinkage), [ADR 0229](0229-conservative-slippage-prices-each-fill-by-the-liquidity-tier-on-the-entry-date-tier-c-and-an-unavailable-tier-are-excluded-and-counted-and-the-stress-request-field-defaults-on-for-robust-only.md) (the other, fixed-rupee liquidity tier).

## Context
The learning engine should be able to say that a setup works differently on highly liquid, middle and thinly traded shares, without multiplying cells and without a thin cell ever looking better than the same setup over all shares. The key already reserves a seventh `universe` part that accepts only `*` (ADR 0193).

## Decision
1. **One dimension, three values.** `CellId.Universe` accepts `*`, `liq_high`, `liq_mid`, `liq_low`. The canonical text is unchanged: six parts for universe `*` and cash (every stored key stays byte for byte), seven for a tier and cash, eight for any other expression with the universe explicit. `CellId.Parent()` drops the regime first, then the universe: one chain from the narrowest cell to the all-shares cell. `CellExplosionGuard` holds the bound (at most four times the plain cells; the key has exactly one extra part) and `AddApplication` refuses to start without it.
2. **The tier is the tercile by rank of the 20-session median traded value (close x volume),** per decision date among the tracked shares with at least 60 daily bars and a median; boundaries ceil(N/3) and ceil(2N/3), ties by instrument id. Fewer than 30 eligible shares: every ranked share is `unavailable` (no tier is invented). A share with fewer than 60 bars, or no session before the date, is `unknown`. Both are counted and stay in the `*` cell only. This is not the fixed-rupee A/B/C tier of CF-05 (ADR 0229): that tier prices a fill, this one conditions what is learned (owner question: use one meaning).
3. **No look-ahead.** The tier of a trade is built from sessions strictly before its decision date (`TierCandidates.At`, `UniverseTiers.Table`; the port `IUniverseSeriesSource` is asked for dates before the latest decision date only). A property test shows that appending later sessions changes no earlier assignment.
4. **Tier cells are stored beside the `*` cells,** by `xd learn cells --by-universe` (`ComputeCellStatsCommand.ByUniverse`, off by default), insert-only in the same snapshot; the `*` rows are identical with and without the split. The tier cell's prior is the posterior mean of its `*` cell. The key text holds the universe (the store already reads seven-part keys), so the key needs no column; the hold-out verdict does (point 7). The tier used by each trade is part of the snapshot key (a hash of the assignments), so another set of bars is another snapshot. The universe split reads only research runs (the cell statistics already do, ADR 0243). Tier cells get no CF-02 shrinkage figures.
5. **The parent-beats rule is a pure read-side function.** `CellChoice.Resolve(child, parent, minTrades, options)` returns the chosen cell, the reason (`child_better`, `no_better_than_parent`, `child_thin`) and both lower bounds; the parent's bound is that of the parent with the child's trades taken out (the exclusion method of the review fix). No stored row is relabelled. A thin child (fewer than `Learning:Universe:MinTradesChild` trades, or not `Enough`) is never read.
6. **A tier cell is an observation, never an applied restriction.** The selection, plan, paper, live and execution paths read the six-part cash cells only (`CashKey` in the store; the tier rows are left out of `ListLatestAsync`). `GET /api/cells/universe` lists the tier cells, `GET /api/cells/universe-links` lists each against its parent with `observation` true when the tier is read, has at least `learning.universe_link_min_trades` (100) trades and a stable hold-out. Nothing creates a hypothesis, changes a scan scope or places an order; a restriction is only ever a proposal for the existing hypothesis loop, by the owner's act.
7. **The hold-out is computed when the cells are computed and stored with the row** (`universe_verdict`, `universe_first_n`, `universe_second_n` on `research.cell_stats`, nullable, migration `AddUniverseControls`). The tier's trades are split at the median exit date (the rule of BK-07's `HoldOutStability`); in each half the tier's lower bound of the win rate must beat that of the rest of the parent in the same range (same prior, **unweighted** counts); a half under 30 trades is `insufficient`. The stored bounds and `CellChoice` use the recency-weighted counts, so the hold-out and the choice are two readings of the same cell, not one number (stated). It is not the locked hold-out of ADR 0207.
8. **Settings are stored owner settings** (precedent: BK-10): `learning.universe_min_trades_child` 30, `learning.universe_link_min_trades` 100 and `learning.universe_registered_baskets` (names, default the research note's seven plus a placeholder eighth, Nifty 500). Insert-only history `research.universe_settings_changes` (owner actor checked in the database), a fresh password for every change (`PUT /api/universe/settings`), one account event per change. A change names the `expectedVersion` it was read at (the newest change id, shown as `version`); the append checks it under an advisory lock in one transaction and answers 409 `learning.stale` otherwise (the guard of BK-10). A refused value is 400 `learning.invalid` through the shared problem mapping. No setting applies a restriction or places an order.
9. **Pre-registration.** A full Lab test of a strategy on a basket outside the registered list is refused (422 `lab.universe_not_registered`, a validation error the Lab maps to 422; the message names the list). A simulation of the basket alone is allowed. Whether a basket is registered is **not** in the run label or the run key (the list is mutable): the What-works ranking reads the list in force when the report is built and leaves out runs on unregistered baskets (every other report shows them). Baskets are registered by name with the system prefixes ignored (a stated shortcut: ids would need the default baskets to exist first).
10. **Run labels.** A basket run's universe label says `members as of the run date (single_snapshot, survivorship applies)`, the basket id and the parameter hash (`-`: the hash of a derived basket is not read here). The simulator replays the basket's members of the run date; reading `members(asOf = day)` per day (basis `dated`) is not built, so no run is ever described as point in time.
11. **Trials** are counted from the stored Lab tests: `GET /api/lab/strategies/{id}/universe-trials` gives k distinct baskets, the distinct tests (a repeat counts once) and k - 1 extra variants. It is an information breakdown only and feeds no factor or verdict; the honest count of looks (ADR 0207, CF-06) does, and already counts a new universe as a re-plan.
12. **Reports.** `ReportDimension.Universe` is refused with 422 `reports.dimension_unavailable` and the reason: the report engine stores no tier per trade; the tier cells are read from `/api/cells/universe`.

## Consequences
- The tier is relative to the tracked set (the owner's picks) as it is now: a share is in a date's set from its first stored daily bar. Delisted shares and shares tracked later are not in earlier sets (survivorship, stated).
- Tier effects may be sector or size effects; with few trades most tier cells say "not enough evidence" or "no better than all shares".
- Not built: per-day dated membership in the simulator, the `universe` report lens as an available dimension, and the automatic creation of a hypothesis from an observation (the proposer is unchanged; the owner creates the hypothesis).
