# 0267 — The tool server reads the two basket reports from the API with its own read-only token, accepted on exactly those two routes; the eval reads its own API over the fixture

- **Status:** Proposed (spec [BK-12b](../specs/BK-12b-basket-reports-for-the-assistant-via-the-api.md), approved 2026-11-11; built 2026-11-11). Becomes Accepted when the owner has read it.
- **Date:** 2026-11-11.
- **Relation to other ADRs:** closes the deviation of [ADR 0264](0264-the-assistant-reads-baskets-through-three-more-values-of-get-report-the-basket-screens-own-handlers-and-the-stored-context-row-with-no-new-tool-and-no-rank-unless-separated.md) ("Owner decision 2026-11-11"); [ADR 0137](0137-the-assistants-tools-run-in-a-separate-read-only-server-under-two-database-roles-that-can-select-only-from-reviewed-views-and-the-switch-lives-in-the-database.md) (the tool server and its two database roles, unchanged); [ADR 0262](0262-the-basket-profile-is-one-lazy-screen-over-two-read-only-endpoints-with-a-bounded-in-process-cache-and-a-rank-that-needs-separation.md) (the two endpoints and their cache); [ADR 0143](0143-the-eval-grades-the-assistant-by-code-on-a-synthetic-fixture-read-only-with-exact-numbers-intervals-and-an-owner-accepted-baseline.md) (the eval stack).

## Context
`get_report` answers `basket_profile` and `basket_ranking` through the two BK-07 query handlers. Those read bars, baskets, the benchmark and the calendar through ports that only the API implements; the tool server has no `DbContext` and its read role has no grant on those tables. The owner decided that the tool server reaches them **through the API** and that its database roles stay as narrow as they are.

## Decision
1. **A narrow service credential.** The API gets a second authentication scheme, `xd-service-read`, that checks a bearer token (`Api:ServiceTokens:Mcp`, secret file `mcp_api_token`) with SHA-256 of both sides in fixed time. It is **not** the default scheme, so the fallback policy (an owner session) still guards every route; only the policy `AssistantBasketRead` (an owner session **or** the service principal) lists it, and only `GET /api/reports/baskets/{id}/profile` and `GET /api/reports/baskets/ranking` carry that policy. The principal has one claim (`xd:service`), no owner, no session, no audit row; step-up, CSRF and every other policy refuse it. A wrong, empty or missing token, or no configured token, is the same 401 as any anonymous request (the session scheme writes it; the service scheme leaves the challenge alone). The host refuses to start when the token is shorter than 32 characters or equals the broker vault key, the hand-over key, the model key, `Assistant:Mcp:Token`, the owner password or the database password. A test enumerates every endpoint of the host with the token and no session: all answer 401 but the two.
2. **Not `mcp_token`, not the network, not the cookie.** `mcp_token` is the API's credential towards the tool server (one secret both ways could not be revoked alone); trusting the `back` network would let any container read reports; forwarding the owner's cookie would open write routes; read-only ports in the tool server were declined by the owner.
3. **Same interfaces, another implementation.** `XDrishti.Infrastructure.Ai.ReadOnly.BasketApi` holds `ApiBasketProfileHandler` and `ApiBasketRankingHandler`, implementing the two BK-07 `IQueryHandler` interfaces over one typed `HttpClient` (`BasketApiClient`); the tool server registers them with `AddAiBasketApi` (they live in the infrastructure namespace the tool server may use, because the architecture test forbids the tool server any other use of the application's messaging and reporting namespaces). `BasketReportReader` and its shaping are unchanged, so the model's body is what the in-process handlers would give; a test compares the two field for field over a real API host. The client's allow-list is a delegating handler: only a GET of exactly the two path templates on the configured host, so the token travels nowhere else.
4. **Fail closed.** A missing address or token, a transport error, a timeout (`Mcp:Api:TimeoutSeconds`, 8, range 1 to 9, inside the 10 s tool timeout), a status other than 200, 404 or 422, a body over `Mcp:Api:MaxResponseBytes` (2 MiB) or one that does not deserialize is `tool.unavailable` with "basket reports are not reachable now", never a partial body; 404 is `basket.unknown`; 422 is `tool.invalid_arguments` with the problem's title (or detail) as cleaned, cut, untrusted text. No retry. The body is read into the typed view, so a field the view does not name never reaches the model. Log event 6124 `mcp.api_call` (route name, status code, ms) carries no basket name, query or token.
5. **The eval has its own API.** `xd-api-eval` (profile `eval`) is the API image with `Api:ReportsOnly=true` over the fixture database as the runtime role: no hosted or scheduled service (the host removes every `IHostedService`), no broker key (the vault and hand-over keys are not required), only `ReportsEndpoints` mapped. It sits on `back` only, publishes no port, holds no Dhan or broker secret, and has its own token `mcp_api_token_eval`, shared only with `xd-mcp-eval`, whose `Mcp:Api:BaseUrl` is `http://xd-api-eval:8080`, never the production API (a compose lint test checks the host name as a whole word). The production `xd-mcp` points at `http://xd-api:8080` with `mcp_api_token`.
6. **No change to what the tool server can read from the database.** No migration; `xd_mcp_read` and `xd_mcp_sql` have exactly the grants of ADR 0264; an architecture test checks that the new folder has no `DbContext`, no command handler, no non-GET verb and names no route but the two.

## Decisions recorded with the build
- **Handlers are always registered.** The spec said "only when `Mcp:Api:BaseUrl` is set". They are registered always and answer the fixed `tool.unavailable` text without any call when the address or token is missing, which is what AC 7 asks for ("no BaseUrl/token: `tool.unavailable` with 'basket reports are not reachable now'").
- **The problem text is the title.** The API's 422 problems carry the reason in `title`; the client takes `detail` when there is one, else `title`.
- **A shared secret between the tool server's client token and its API token is refused at start** (`Mcp:Api:Token` must differ from every `Mcp:Tokens:*`).
- **Keychain items** `xdrishti/mcp/api-token` and `xdrishti/mcp/api-eval-token` are created on first use by `deploy/xd-up.sh` like the other tokens (32 characters); no owner act is needed beyond the next `xd-up.sh`, then a restart of `xd-api` and `xd-mcp`. An eval run needs `scripts/xd-eval.sh prepare` once more (it now starts `xd-api-eval` too).
- **The eval fixture is extended and the baseline must be re-run and re-accepted by the owner (owner decision 2026-11-11).** The synthetic fixture gains the Nifty 500 index (`NSE:NIFTY_500`, type `index`), 70 weekday sessions of straight-line daily closes (`bars` in `fixture.json`, seeded into `market.bars_agg`) for the index and five new shares, and three baskets of new shares only (EvalGamma = EVG1, EVG2, EVG3: A 100 to 110, B 50 to 45, C 200 to 250, so a hold of +8.3333 %; EvalTwin = the same three; EvalQuad = EVG1, EVG2, EVQ3, EVQ4, four members). No trade, plan line or holding names a new symbol, so the locked 30 data questions and their oracle are unchanged. The SHA-256 of the file (the `fixture_hash`) changes, so the accepted eval baseline reads as stale: **the owner re-seeds (`scripts/eval-db.sh reset`), re-runs the eval and accepts a new baseline; nothing here accepts one.** BQ-01 (EvalGamma against EvalTwin: not separated, no order), BQ-02 (hold 8.33 % and the 252-day figures insufficient), BQ-04 (Jaccard of EvalGamma and EvalQuad 0.4) and BQ-06 (EvalQuad, correlation insufficient, n = 4 of at least 5) carry the numbers the real API over the fixture gives (`EvalBasketGoldenTests` seeds the fixture, serves it with the reports-only host and reads it with the tool server's own client).
- **`not_evaluable`.** A basket question (BQ-, not the locked 30) whose `get_report` result carries `tool.unavailable` (no eval API) is graded with the code `tool_not_evaluable`: `AnswerGrade.NotEvaluable`, never `Passed`, whatever the answer says.
- **Reports-only is narrow.** It maps only the GET routes of `ReportsEndpoints` (no contract, docs UI or hub), and the host refuses to start with `Api:ReportsOnly` over any database but `xdrishti_eval`; a compose lint rule keeps the switch off `xd-api`. `xd-api-eval` uses the runtime role `xd_app` over the fixture database (a recorded shortcut: no separate read-only login).

## Consequences
- The assistant can read the two basket reports with the figures the screens show, without any new database grant. The attack surface added is one bearer token that opens two read-only GET routes of an already owner-only API.
- A rotation of `mcp_api_token` needs a restart of `xd-api` and `xd-mcp`.
- UNVERIFIED in a running container: that `xd-api-eval` starts under `Production` with `Api:ReportsOnly` and no broker secret (proved on the test host with the keys emptied and no hosted service, not under Podman), and its 300 to 500 MB.

Everything else here stands.
