# 0055 — The strategy file, its JSON Schema and the content hash

- **Status:** Accepted (spec [P3-02c](../specs/P3-02c-the-strategy-file-yaml-schema-and-hash.md), which the owner approved on 2026-10-22, questions 1 to 8 as recommended; built on 2026-10-22). The text of this ADR has not been read by the owner.
- **Date:** 2026-10-22.
- **Relation to other ADRs:** [ADR 0002](0002-config-and-strategies-in-app.md) (a strategy is a file you can import and export; schemas come from the backend's types), [ADR 0034](0034-the-rules-expression-language-lint-and-compiler.md) (the language: the text of a condition is the version), [ADR 0036](0036-the-typed-strategy-model-and-the-compile-of-its-sections.md) (the model, schema 1, which the file maps to one to one), [ADR 0037](0037-simulation-conventions-and-the-two-stage-seam.md) Amendment 2 (the run record carries the canonical JSON and its SHA-256; this ADR replaces the interim writer behind it, without changing a byte of the built-ins).

## Context
A strategy had a typed model and a compiler but no text a person could write, upload, download or diff, and its only canonical form was an interim writer inside the simulation library. P5 (validate, library, editor), the `xd` CLI and P3-02d (storage and the seed) all need a file, a schema for the editor and a hash that names a version by its content.

## Decision
1. **A new project `XDrishti.Strategies.File`** (Domain and Strategies, plus the YAML parser package YamlDotNet 16.3.0, pinned in `Directory.Packages.props`). `XDrishti.Strategies` keeps Superpower as its only package, and the Simulation library gains no package. Pure: reads a string, no file, network, clock, random or reflection (an architecture test pins it).
2. **Safe reading.** The parser's *events* are read into the library's own tree (`FileNode`: mapping, sequence, scalar, each with line and column); the library's object deserializer is never used. Limits, in one `FileLimits` record, are checked as events arrive: 256 KiB (by bytes, before parsing), depth 12, 5,000 nodes, 4,096 characters a scalar, 64 keys a mapping, 100 items a sequence. Refused by name: anchors and aliases, tags and merge keys, a second document, a duplicate key, control characters, a non-scalar key. A syntax error carries the parser's line and column. Any exception the parser throws on malformed text (other than out-of-memory and cancellation) is caught as `file.yaml_syntax`; the input is untrusted, so the filter is open (a 40,000-case fuzz run found plain framework exceptions).
3. **No implicit typing.** Every scalar is text and the field converts it: a number is `-?(0|[1-9][0-9]*)(\.[0-9]+)?([eE][+-]?[0-9]+)?` and finite (so hex, underscores, `.inf`, `+1`, `yes` are `file.bad_number`; a quoted number is `file.wrong_type`); a time is `HH:mm`, quoted or not; a quantity is a number or an unquoted parameter name (the words `yes no on off true false null inf nan` are never a name).
4. **The shape of the file (D1, D2, and the owner's answers to question 4).** The root has `strategy` and the optional `test` and `universe`; inside `strategy` the keys are the fields of the model. The rules of the BUY side sit directly under `strategy`, the SELL side under `sell:`; `overlays` is a key of a side; exit and overlay parameters are flattened (`{ policy: FIXED_RR, rr: [2.0] }`). `version` is read into the envelope and is outside the hash; `test` and `universe` are read, limited, reported as the warning `file.section_not_validated` and are outside the hash. `schema` is optional and must be 1. Any other key is `file.unknown_field`. The nested `trail: { type: ATR, mult: 2.0 }` of doc 11 is corrected to the model's `trail_atr_mult: 2.0` (question 3).
5. **Located problems.** `FileProblem(Path, Line, Column, EndLine, EndColumn, Code, Severity, Message)`; the path is the model's path (`buy.trigger[1]`, `exits[0].rr[1]`, `time_rules.last_entry`), so the problems of `StrategyCompiler` map straight through, and `FileReadResult.Locate(path)` gives the position of any field. All mapping problems of a file come in one pass, in file order. The reader does not compile.
6. **One table, three uses.** The key names and lexical rules are `FileShape`; the spellings of the enums are `StrategyNames` (public, in `XDrishti.Strategies.Canonical`); the parameters of each exit and overlay are a read-only view of `ExitTables` (`ExitParameterInfo`). The mapper, the writer and the JSON Schema generator read them. The schema (draft 2020-12, `urn:xdrishti:strategy:1`, `additionalProperties: false` everywhere) judges shape only and agrees with the mapper on what is a shape error; the ranges and the relations between fields are the compile's. It is generated once per process and pinned by a golden file (`XD_UPDATE_GOLDEN=1` rewrites it for review).
7. **The writer.** One fixed layout (block style, two spaces, keys in the order of the table, conditions and times double-quoted, other text plain when it is a plain word). `Read(Write(d)) == d` and `Write(Read(Write(d))) == Write(d)` on a seeded corpus of 500 definitions covering every stop, entry, policy, overlay, list mode and quantity form. A side with no section at all is not written and reads back as absent.
8. **The canonical text and the hash.** `CanonicalStrategy.Json(definition)` and `StrategyHash.Of(definition)` live in `XDrishti.Strategies.Canonical` (pure, so the file library and the simulation library both use them). It is the interim writer moved, byte for byte, with one change: **`params` and the parameters of an exit or overlay are written sorted by name (ordinal)**, because a YAML mapping has no order and the hash must not depend on it. The order of `exits`, of `overlays` and of the conditions of a list stays the author's. The text is taken from the model, never from the YAML, so comments, quoting, key order, flow or block style, `2` and `2.0`, the `version` and the omitted `test` and `universe` never reach it. A definition hashed before this change with unsorted exit parameters would get a new hash; none exists (only the built-ins have run, and they have one exit parameter). `rsi()` and `rsi(14)` still hash differently: the text is the version (question 5, ADR 0034). `DefinitionJson` in the simulation library is now one call to `CanonicalStrategy.Json`.
9. **No stored run is re-keyed.** (Amended by [ADR 0056](0056-stored-strategies-the-lab-tables-the-seed-and-loading-by-version.md) decision 4: the pinned hashes below are those at the time of this ADR; declaring `rr` as a parameter changed the three texts once, and the tests pin the new hashes.) The three built-ins declare one exit parameter (`rr`) and their parameters in name order, so the sorting changes none of their texts; a test pins the three known hashes (`ORB 9c1141cf…`, `VWAP_PULLBACK 7c1c2493…`, `BASE_BREAKOUT c41e6a82…`) and that a built-in survives write, read and hash unchanged.

## Consequences
- P3-02d can seed the built-ins as text and store `source_text`, `canonical_json` and the hash; P5-01 validates by `Read` then `StrategyCompiler`, serves `StrategyFileSchema.Json()` and checks `version` against the family.
- A person can write `rr` as a parameter name (`rr: rr`) once a strategy declares it; whether the three built-ins do is P3-02d's decision (its question 1), and it would change their hashes once.
- The model gained no field: `name`, `universe` and `test` are not part of schema 1.

## Honest limits
- The JSON Schema cannot reject a duplicate key (it is a YAML property) nor a value that depends on a parameter or on another field (a stop field its kind does not use, `book_pct: 500`); the compile does, and a test table says which mutation is judged by which.
- The in-item span of a compile problem inside a block scalar (`|`, `>`) is the whole scalar; the position table holds one range per path.
- A 256 KiB text is bounded by the limits but not benchmarked in `check.sh`; the explicit benchmark measures the example (median target 1 ms for read plus map).
- Allocation is bounded by the limits and asserted loosely (8 MiB on the attack set); the YAML scanner's own buffers are the library's.
