# 0265 — The loosening banner is computed on read from the stored change rows and hidden only by an insert-only dismissal, never in the stored plan or its hash

- **Status:** Proposed (spec [BK-10b](../specs/BK-10b-loosening-banner-on-the-plan-and-sizing-settings-forms.md), approved 2026-11-11; built 2026-11-11). Becomes Accepted when the owner has read it. **Safety slice: yes** (it displays a loosening and lets the owner hide it; hiding a warning is the less safe direction). It changes no quantity, limit, gate input or plan row and places no order.
- **Date:** 2026-11-11.
- **Relation to other ADRs:** [0259](0259-position-sizing-only-scales-down-by-volatility-capacity-and-basket-budgets-and-every-setting-is-an-owner-act-with-a-fresh-password.md) and [0260](0260-correlated-names-share-one-risk-cap-by-average-linkage-clusters-and-the-gate-can-read-a-baskets-own-breadth-both-off-by-default-and-every-change-an-owner-act.md) (the three change tables and the direction they store: this slice only reads `loosen`), [0115](0115-crossing-alerts-on-armed-tickets-are-an-observer-in-the-feed-flush-prompts-are-stored-questions-with-a-derived-status-and-the-bell-reads-them-through-the-ticket-notice-port.md) (insert-only dismissal, no password), [0219](0219-a-firing-kill-rule-writes-a-proposal-and-a-notice-the-owner-or-an-automatic-setting-that-is-off-by-default-pauses-the-cells-and-only-the-owner-with-a-fresh-password-ever-re-enables.md) (an automatic setting OFF by default, recorded as `auto` with the setting row, changed with a fresh password), [0091](0091-auto-approval-is-an-option-behind-an-owner-setting-default-off-a-new-approval-kind-the-database-checks.md) (an auto option behind an owner setting).

## Context
BK-10 and BK-08 store every change of a sizing limit, a basket budget, the cluster cap and the gate's breadth source with a `direction`, and left the "loosened since the last plan" banner, a dismissal state and the owner forms to this slice.

## Decision
1. **The banner is computed on read, never stored.** `GET /api/plans/{id}` and the plan list carry `loosenings`: one query over the three change tables (rows with `direction = 'loosen'`, the old value of a budget being the previous row of the same basket) minus the dismissed ones, then the pure rule `LooseningNotices.Shown` keeps those changed at or before the plan's `created_at`, oldest first. Nothing enters `trading.plans.basis`, `basis_flags_json` or `input_hash`: otherwise a dismissal before a build would change a plan's hash. An architecture test pins that the plan builder and the plan store name no type of the slice. If the loosenings cannot be read the plan is still returned with `looseningsUnavailable = true` and the screen says so.
2. **A dismissal is an insert-only owner act, no password** (as the other dismissals of the plan screen). `POST /api/plans/loosenings/{noticeId}/dismiss` (`sizing:{id}`, `budget:{id}`, `basket:{id}`): session and CSRF token, the actor from the session; one row in `trading.loosening_dismissals` (unique per change), one account event `LooseningDismissed`; a repeat adds nothing and answers 204; 422 for a malformed id or a change that did not loosen, 404 for an unknown one. A dismissal is of the change: it disappears from every plan read afterwards, older plans included; a newer loosening of the same key shows again.
3. **The automatic dismissal is OFF by default.** `plans.loosening_banner.auto_dismiss` is a stored, Advanced, not learnable setting (not on the ADR 0247 allow-list) in `trading.loosening_settings` (insert-only, id drawn after an advisory lock). `PUT /api/plans/loosening-settings` needs a session, the CSRF token and a **fresh password for every change, ON and OFF alike** (403 `auth.step_up_required` without one); `expectedVersion` guards a concurrent change (409 `plans.stale`). With it ON, after a plan is published (and only then, as a separate write whose failure is logged and leaves the banner shown) the loosenings that a published plan already showed, that is changed at or before the previous plan was built, are dismissed with the actor `auto`, the id of the setting row and its hash; a loosening no plan has shown is never dismissed. The database refuses an `auto` row whose setting row is not the newest, is OFF or has another hash, an owner row that names no owner, and a second row per change; `xd_app` can only select and insert.
4. **Forms.** Settings gets a Limits tab with the sizing settings, the basket budgets, the basket settings and the automatic dismissal: each submits to the existing PUT with the password typed for that change, shows the server's field messages, 409 as "changed elsewhere", the history newest first, and, from the direction the server stored, "This loosens a limit: it will be shown on the next plan until dismissed". The client has no direction rule.

## Consequences
The owner sees every loosening on every plan until they dismiss it; the only automatic hiding is an owner-chosen, audited option that is OFF. No limit, plan or order is touched by this slice.

## Deviations and interpretations (see the spec's build notes)
- The existing sizing, budget and basket-settings PUTs do not take an `expectedVersion`; they compare against the stored state inside the handler (409 `selection.stale`). The forms send the password and the values; the version guard exists on the new setting only.
- The automatic dismissal runs only inside `RunNightlyPlanHandler`, which is the one path that publishes a plan (scheduled and manual runs both go through it); a plan stored any other way would not trigger it. `// shortcut:` the plan read has no timing test (AC 11): it is one query over three small tables.
- A budget loosening's key reads `basket budget <name>`; its values read `20%` and `off`.

## Owner decision 2026-11-11

Given in chat. (1) Dismissing a loosening line needs **no password** (as built; the P7-20 dismiss pattern). (2) The auto-dismiss option is **kept, OFF** by default.
