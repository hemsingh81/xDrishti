# 0196 — The pairs study counts every candidate in the ledger before any test, walks pairs in a separate `pair-1` walker on the simulator's fills, and judges them by protocol S, where a gross DROP is valid and a gross KEEP impossible

- **Status:** Proposed (built in P14-13 from the owner-Approved spec, 2026-11-03). Becomes Accepted when the owner has read it. **Safety slice: no** (research over stored bars; nothing selects, plans or orders a pair, and no two-leg order path exists).
- **Date:** 2026-11-03.
- **Relation to other ADRs:** [0192](0192-the-pairs-core-is-a-pure-engle-granger-library-with-pinned-mackinnon-tables-a-benjamini-hochberg-rule-that-counts-unavailable-tests-and-a-signal-state-machine-that-never-trades-on-an-unavailable-z-and-no-reader-yet.md) (the core this study is the first reader of), 0059 (the test ledger, `VerdictEvaluator`, `MultipleTesting.Factor`), 0037 and 0038 (engine versions, the fill rules the pair walker reuses), 0042 and 0044 (the cost model), 0183 and 0186 (the shared extension record, hold-out once, ledger first).

## Decision
1. **Where the code lives.** The study's pure types are in `XDrishti.Domain.PairResearch` (`PairUniverse`, `PairFormation`, `FormationResult`, `PairTradeRule`, `PairCosting`, `PairTrial`, `PairQuarter`, `PairVariant`, `PairStudyOptions`, `ProtocolS` and their value types). It is **not** under `Domain/Pairs`: the core's architecture test pins that namespace (and its sub-namespaces, since the scan is by prefix) to System, `Common` and `Lab`, and the study needs the extension protocols, the cost model and the bars. `PairFamilies` (`pairs:intraday-1`, protocol `S`, version key `pairs-1`) is in `Domain/Learning/Extensions` beside `ExtensionFamilies`, in a list of its own: the P15 phase check keeps iterating `ExtensionFamilies.All` only. The loosened allow-list of `PairsArchitectureTests` is exact: `Domain.PairResearch` and, in the simulator, the type `PairWalker`; `PairResearchArchitectureTests` pins who may name a study type (the two handlers, the port, the store, the walker adapter, the verb, the walker) and that no decision area, host or the execution service does.
2. **Ledger first.** `xd pairs run` appends the six trading variants to `lab.test_ledger` before it reads anything. Then, per calendar quarter, it finds the candidates (same sector by today's label, return correlation >= 0.8 over the 252 sessions before the quarter, the 2,000 most correlated if more, ties by the symbols' ordinal order) and appends **every candidate** (family, ordered symbols, test definition; the hash does not depend on the window, so a pair re-formed in a later quarter is not a new look, while the run id does, so a new window is a new row with the same hash); only after the last append does it run the Engle-Granger test, Benjamini-Hochberg and the half-life, store the formation or walk anything. The correlation filter runs first on purpose: it is what *defines* the trial set (a pair is a trial because it is a candidate, and `y` is fixed by turnover), it forms no test statistic. A source-order test and a call-order fake pin it: 2,000 candidates + 6 variants = 2,006 trials, `Factor(2006)` = 3.74.
3. **Formation.** Benjamini-Hochberg at q = 5 % runs over **all** candidates of the formation (an unavailable test counts in `m` with p = 1); a rejected pair is then selected only when its half-life on the daily spread is in [1, 20] sessions and its hedge ratio is above 0 (the counts of both reasons are stored). The stored `detail` holds the counts, the exclusions, the selected pairs with `alpha`, `beta` and spread mean, the half-lives and the 50 smallest-p rows of the table (`FormationResult.Table()` prints all of it). A member with a gap in the window's daily closes is excluded and counted; a quarter with fewer than 252 sessions before it has no formation and says so. A session is a date on which at least half of the shares that have daily bars have one.
4. **The pair walker `pair-1`** (`Simulation/Walking/PairWalker`, with the same `Slip`, `TickGrid` and entry-limit code as the single-instrument walker; `SimulationEngine.Version` stays `sim-9`, the goldens are unchanged). Per 5-minute bucket the spread is taken from the last traded minute; the z-score is against the spread values of the previous `L` sessions only; the decision is at the bucket close and both legs fill at the next minute that holds a trade (at most 5 minutes later, before 15:15): the entry as a limit order at the bucket close with the entry limit percent, the exits at the open with the exit slippage. A pair opens only when `entry <= |z| < stop` (ADR 0192 asked for this; `PairSignal` is unchanged and the walker counts `BeyondStop`), never after 14:45, one position per pair, flat at the 15:15 decision. A leg with no bar in the delay: no entry (`leg_unfilled`); an exit takes the leg's next minute (`leg_late`) and, with none, the last close (`end_of_data`); a bucket without both closes is an unavailable z, which never opens and never closes by rule (counted). Every count is printed. The walker knows no cost type (the cost rule of `CostArchitectureTests` is not relaxed): its trades are gross, and `PairCosting.Apply` (Domain) charges the four fills through `CostModel.Leg` (intraday equity, the date of each fill) with the owner's sheet (`Pairs:CostSheetId`), else labels the trade `gross`; a date before the sheet's first schedule leaves the net unavailable (`costs_unavailable`), never zero.
5. **Sizing and R.** Y notional `Pairs:PairNotional` (default 1,00,000), X notional `beta` times it, whole shares (floor; a leg of 0 shares: `not_sizable`, counted). The rupee risk is the **nominal** notional times `(3.5 - |z at entry|) x sd(W)` (not the notional rounded to whole shares, so the R unit does not depend on a share price); `R` = net (gross when there is no sheet) rupees over it. Hand example: 100,000 x (3.5 - 2.0) x 0.004 = 600; +450 gross = 0.75 R.
6. **Protocol S** (`ProtocolS`, family `pairs:intraday-1`). Calendar quarters of the entry date are the folds (the quarter end of `CalendarFolds`); a quarter with >= 20 trades is evaluable. The last six months of the stored trades are the hold-out; the five trade dates before it are an embargo (dropped, counted). The verdict is over the pre-registered primary variant (e 2.0, L 5); the other five variants are reported in the grid with their trades and mean R, with N. NOT_EVALUABLE names `quarters n of 6`, `pair trades n of 300` and a bound that cannot be formed. KEEP needs: lower bounds (day blocks and 5-session blocks, 10,000 draws, seed 1337, one-sided 90 %) of the mean R at or above `0.05 R x Factor(N)`; mean R above 0 in two thirds of the quarters; the Lab's `VerdictEvaluator` with N returning PASS on the pooled trades; no pair at 25 % of the net profit or more; net of the owner's costs. DROP: not KEEP, minima met and the larger upper bound under 0.05 R (not widened); **a gross DROP is valid** (costs can only lower an absolute R, there is no comparator); **a gross result that would be KEEP is INCONCLUSIVE**. The Lab gates are the Lab's own defaults (`QualificationGates.Default`: 30 trades, 0.15 R, profit factor 1.2, 60 % positive folds, 10 R drawdown, 5 pp calibration); no threshold is invented. The Lab scales its trade, expectancy and profit-factor minimums by the factor of N, so at N = 2,006 it asks for more than the protocol's own 300 trades and 0.05 R; the protocol's rules are separate and both must hold. The calibration gate does not apply (no probability) and the evidence says `not applicable`. **Owner question:** are the Lab's gates, scaled by F, the right bar for pairs? The hold-out is read once, by `--holdout`, after a stored development KEEP: KEEP only when it has >= 100 trades, every trade is net, the mean is positive and its day-block lower bound is above 0; any gross or `costs_unavailable` hold-out trade makes it INCONCLUSIVE. **Owner question:** this hold-out pass rule is the implementer's conservative choice (the spec gives none); say whether to keep it. The development verdict never reads the hold-out: the evaluation cuts it first, from the primary variant's dates, and builds the grid, the formation counts, the turnover and the counts printed from development trades alone. A pooled result without a net profit fails with `no net profit; concentration not computable`.
7. **Evaluation reads the ledger first.** `xd pairs eval` refuses (`extensions.trial_not_in_ledger`) with nothing read when the primary variant is not a counted trial, takes N from the ledger, appends nothing (so a re-run stores the same record id and writes nothing), and judges only the stored trades of the current settings (a label `cfg:<hash>` of the notional, the charge basis and the fill rules; others are counted and printed). The record is the shared `research.extension_evaluations` row (protocol `S`, fold unit `quarter`, version key `pairs-1`), with the walker and fill-engine versions, the options hash and a hash of the trades in its inputs; the shared route `GET /api/research/extensions?family=pairs:intraday-1` lists it (its summary text names the family, so the contract is regenerated).
8. **Tables** (`AddPairResearch`, raw SQL, insert-only for `xd_app`, nothing for `xd_exec` or the read roles): `research.pair_formations(formation_id, family, quarter, window_from, window_to, candidates, tested, unavailable, selected, detail, created_at)` and `research.pair_trades(run_id, pair_key, ordinal, entry_ts, exit_ts, side, z_entry, z_exit, exit_reason, qty_y, qty_x, gross_inr, net_inr, r, labels)`. Ids are SHA-256 of the inputs (the formation: family, quarter, window, options and the closes; the run: variant, quarter, formation, both engine versions, the settings hash), so the same bars and options give the same rows and a second run writes nothing. A run always walks the **whole quarter** whatever `--from` and `--to` were typed (they only choose which quarters), so a run is a function of its quarter and runs never overlap. The formation window is built by the pure `PairWindow.Build` from points dated before the quarter start only (an instrument whose first bar is later, or any later point, changes nothing; a test pins the formation id). Each trade carries the labels `quarter:`, `formation:<16>` and `cfg:` (a hash of the options, the notional, the charge basis and the fill rules). The evaluation judges, per quarter, only the **latest stored formation** among those its trades carry and only trades of the current `cfg`; the rest are counted and printed as other settings or superseded formations. The variant trials are keyed on the span of the quarters the run touches, not on the dates typed. `z_exit` is **nullable** (the spec's column list does not say): a pair closed by the 15:15 square-off with no z-score has none, and the column must not hold a number for a non-value. The variant, the engine versions, the settings hash and the turnover are labels of the trade.
9. **Settings and verbs.** `Pairs:PairNotional` (10,000 to 10,000,000; default 100,000), `Pairs:MaxCandidates` (100 to 25,000; default 2,000), `Pairs:CostSheetId` (empty: gross, labelled). `xd pairs run --from --to [--variant e,L]`, `xd pairs eval --family pairs:intraday-1 [--holdout]`; exit 0 for any verdict, 1 for a refusal (an unknown cost sheet, a spent hold-out, a trial not in the ledger), 2 for a bad line.

## Honest limits (printed with every run and stored in every record)
- `ban_list: unavailable` (no source exists; never read as "not banned"); `sector: as of today` and `asm_gsm: as of today` (flagged shares are excluded; there is no dated history); asymptotic p-values; gross unless the owner's intraday charge lines are loaded (ISS-25); survivorship (today's F&O list for the whole history).
- With 2.1 years of bars there are about three quarters after the first formation: **NOT_EVALUABLE** until CF-04 Part B (5 years).
- Fills use `FillRules.Default` (0.1 % entry limit, default slippage); a run cannot yet choose others.
- Nothing is read by selection, planning, paper, live trading or the execution service; architecture tests pin the exact set of readers.
- The 2 s per formation and 1 minute per 50 pairs targets are UNVERIFIED and ungated.
