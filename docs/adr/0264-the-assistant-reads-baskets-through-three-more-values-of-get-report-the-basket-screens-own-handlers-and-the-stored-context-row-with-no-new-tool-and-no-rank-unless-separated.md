# 0264 — The assistant reads baskets through three more values of `get_report`: the basket screen's own handlers and the stored context row, with no new tool and no rank unless separated

- **Status:** Proposed (spec [BK-12](../specs/BK-12-ai-basket-tools.md), approved 2026-11-03; built 2026-11-11). Becomes Accepted when the owner has read it.
- **Date:** 2026-11-11.
- **Relation to other ADRs:** [ADR 0139](0139-the-ask-your-data-tools-reuse-the-report-engine-and-read-only-views-the-read-role-gets-column-grants-on-four-report-source-tables-and-calc-and-charts-take-no-number-from-the-model.md) (the tools, `IAiReportReader`, the schema budget, calc grounding), [ADR 0137](0137-the-assistants-tools-run-in-a-separate-read-only-server-under-two-database-roles-that-can-select-only-from-reviewed-views-and-the-switch-lives-in-the-database.md) (the read-only server and its roles), [ADR 0262](0262-the-basket-profile-is-one-lazy-screen-over-two-read-only-endpoints-with-a-bounded-in-process-cache-and-a-rank-that-needs-separation.md) (the two basket handlers and the separation rule), [ADR 0260](0260-correlated-names-share-one-risk-cap-by-average-linkage-clusters-and-the-gate-can-read-a-baskets-own-breadth-both-off-by-default-and-every-change-an-owner-act.md) (the stored context row), [ADR 0143](0143-the-eval-grades-the-assistant-by-code-on-a-synthetic-fixture-read-only-with-exact-numbers-intervals-and-an-owner-accepted-baseline.md) (the locked 30-question set).

## Context
The owner wants to ask "which basket held up best", "how correlated is my Banking basket" and get the numbers the basket screens show, each with its n or its honest state. A new tool per question costs schema tokens and gives a 30B model more to choose from wrongly; a model must also not be able to rank what the screen would not rank, and no class C0 data and no write may reach it.

## Decision
1. **No new tool.** `get_report`'s `report` gains `basket_profile`, `basket_ranking` and `basket_context`; `get_basket` is unchanged. Sixteen tools still. The schema budget is raised from 2,200 to 2,300 tokens (`ContextBudget.SchemaTokenLimit`), the golden schema file is regenerated, and the `get_report` description stays within 40 words (the older words "from stored simulation runs", "(value, insufficient, unavailable)" and "query:" were cut to pay for the new ones). The query keys `baskets`, `index` and `date` are added; a basket is an id or an exact name.
2. **The answer is the basket screen's view, reshaped, never recomputed.** `BasketReportReader` (Application/Ai, behind `IAiReportReader`) calls the `GetBasketProfile` and `GetBasketRanking` handlers and `BasketReportShaper` cuts their views: the same fields, a figure only as `{state, number, reason}` (a number only for a value; the engine's reason holds the n and the minimum), the evidence block as the tool evidence, a summary line "not enough data (reason)" for every headline figure that is not a value. The model's grounding rule is unchanged: a derived number must come from `calc` on grounded operands.
3. **Rank only when separated.** For a ranking that is not separated the `rsRank` fields and the `rankWindow` are removed and a note says "not separated: quote the returns and n, not an order". A basket with no value keeps its state and has no rank.
4. **Cut for the model, not for the screen.** The series are cut by the pure `SeriesSampler` (Domain/Assistant: first, last and the lowest and highest point of every series kept, at most 120 points, `sampled`, `step`, `points`, `total` stated). The envelope holds 6,000 characters (P9-00), so when the answer is still too long the series are cut further (60, 30, 16, 8 points) and the lists to 25 and 10 rows, always with a truncated flag and the total. The member lists (`excluded`, `shortMembers`, `noBar`) are cut at 50; contributions are only the top and bottom five; the correlation matrix, the index series, the rolling beta and the daily breadth series stay on the screen.
5. **Context is a stored row.** `basket_context(basket, date)` reads `market.basket_context_daily` through `IAiDataReader` under the read login, which gets column-level SELECT on exactly the 13 columns the report names (not `created_at`) and USAGE on schema `market` (migration `AddBasketToolAccess`, with `Down`; the SQL role gets nothing; no new view). A day without a row is `empty` with the newest earlier date; a future day or a bad date is `tool.invalid_arguments`; nothing is recomputed.
6. **Names are untrusted text.** A name is resolved against `aiv.baskets` (the active baskets, up to 500) by `BasketNameResolver`; an unknown or ambiguous name is `basket.unknown` with up to five near names, cleaned and escaped like any database text (an error message is not cleaned by the runner, so the reader does it). Names inside `data` are cleaned by the runner as before.
7. **Read only, no wider host.** The reader takes only a scope factory, `IAiDataReader` and the clock; the two data ports keep read verbs only (Architecture test). Log events are the existing `mcp.report` (6120): report name, status and time, never a basket name or symbol.

## Decisions recorded with the build
- **The tool server does not yet answer `basket_profile` and `basket_ranking` (deviation).** The BK-07 handlers read bars, baskets, the benchmark, the calendar and the stored context figures through ports that only the API host implements (EF over the application role). The `xd-mcp` host has no `DbContext` and the read role has no grant on those tables; the spec lists only the context table and two views. The reader therefore resolves the handlers when called and a host without them answers `tool.unavailable`; the rest of the assistant is unaffected, which is the spec's own wording for a missing BK-07. Wiring them needs read-only implementations of about eight ports and column grants on the bar and basket tables (or a second route to the API); that widens what the model's host can read and is the owner's decision. The context report works today.
- **Error code.** The spec's `tool.invalid_args` is the existing vocabulary entry `tool.invalid_arguments`.
- **Eval addendum is a separate file.** The eight questions are in `eval/sets/basket-questions.jsonl` (ids BQ-01 to BQ-08), not added to `data-questions.jsonl`, because P9-09 locks that set at 30 questions with a pass threshold of 27 (ADR 0143), and the fixture has no daily bars, no index and no four-member basket. The questions that need stored bars are written as honest-state questions on the current fixture (what the engine can truthfully say); the numeric golden answers (hold +8.3333 %, Jaccard 0.4) need a fixture extension and an owner decision on the threshold, and are not claimed here.
- **Metric objects have no `n` and `min` fields.** The BK-07 `MetricView` has `state`, `number` and `reason`; the reason carries the counts ("4 included, at least 5 are needed"). The summary text therefore says "not enough data" followed by the engine's reason, which holds the counts, not the metric's value.

## Consequences
- The model can quote the basket screens' figures with their states in the same envelope as the other reports; it cannot rank a board the screen would not rank, write anything, or read class C0.
- The profile answer is the largest of the tools; it is held under the envelope by cutting, with every cut stated in the answer.

## Owner decision 2026-11-11

Given in chat. The basket profile and ranking reports reach the assistant **through the API**: the tool server calls the API's read endpoints `GET /api/reports/baskets/{id}/profile` and `GET /api/reports/baskets/ranking`. The tool server's database role (`xd_mcp_read`) stays narrow; no grant on the bar or basket tables and no read-only copies of the eight ports. Built in [BK-12b](../specs/BK-12b-basket-reports-for-the-assistant-via-the-api.md); until then the deviation above stands.
