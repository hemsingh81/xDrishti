# 0132 — The PWA is an installable shell and an offline page behind a capability; its worker caches six static files and answers only failed page loads

- **Status:** Proposed (spec [P8-21](../specs/P8-21-pwa-installable-shell.md), approved by the owner on 2026-10-26; built 2026-10-27). Becomes Accepted when the owner has read it. **SAFETY slice: an offline cache and, later, network exposure.**
- **Date:** 2026-10-27.
- **Relation to other ADRs:** [0128](0128-owner-act-capabilities-are-one-insert-only-log-with-a-generic-gate-by-name-off-by-default-and-switched-on-only-by-the-owner-with-a-fresh-password.md) (the capability `pwa`, OFF by default, switched on only by the owner), [0124](0124-the-browser-runner-is-playwright-and-axe-over-the-installed-chrome-answered-from-the-msw-handlers-and-kept-out-of-check-sh.md) (browser runner), [0001](0001-foundation-stack-and-repository.md) (local-only).

## Context
The owner wants the app installable (Mac now, phone later). An offline cache is the classic way to show stale or sensitive data, and a phone path means exposing the stack. The slice had to decide what is cached, when the worker exists at all, and what is NOT done by an agent.

## Decision
1. **The worker answers one thing: a failed page load.** `public/sw.js` (plain JavaScript, about 80 lines, no dependency, not in the bundle) answers only a same-origin, plain GET navigation outside `/api /hubs /health /prototype /docs /assets` (decoded, case-folded, slashes collapsed; any other URL, method, mode, `Range` request or origin is left to the network: `respondWith` is not called). It calls `fetch(request)` and only when that rejects answers with the cached `/offline.html`. Its fetch answers are never stored. No push, sync, periodic sync or notification handler exists (a text test guards it).
2. **The cache is an allow-list of six static files** (`/offline.html`, `/manifest.webmanifest`, the four icons), written by one `cache.put` at install, each only if the response is 200, same-origin, not redirected, and not the SPA fallback page (an icon that came back as HTML is refused and the install fails). No application assets (hashed JS/CSS/fonts) and no `index.html` are cached: the proxy already serves them `immutable`, so the worker would add no speed, and a cached shell is the source of the "old page with new chunks" bug (spec D4, which is stricter than the brief of "static build assets"; the stricter rule is the one built and tested).
3. **Versioned by the build.** The cache is named `xd-offline-<hash>`, the hash being the first ten hex digits of a SHA-256 over those six files, stamped into `dist/sw.js` by a small Vite plugin (`closeBundle`). A changed file gives a changed worker file, so the browser installs the new worker, which deletes every older `xd-` cache at activate. `skipWaiting` and `clients.claim` are safe because the worker serves only the offline page.
4. **Capability gate.** The registration code is not in the entry chunk. `PwaGate` (in the lazy app shell, so only for a signed-in session) reads the capability `pwa`; only when the read has answered it loads `shared/lib/pwaControl` and: ON registers `/sw.js` (scope `/`, `updateViaCache: none`) when the page is idle; OFF unregisters every worker and deletes every `xd-` cache. A failed read counts as OFF (it never registers and removes any earlier worker: the kill switch fails safe); a read still in flight does nothing. The switch is not set in the running stack by this slice.
5. **Sign-out leaves nothing.** `endSession` (sign-out, expiry, any 401) calls `clearOfflineCaches()` (about 0.3 KB gzip of the entry chunk): unregister all workers, delete all `xd-` caches, never throws.
6. **The manifest and icons.** `manifest.webmanifest` (id, name, short_name, start_url, scope, display standalone, theme colour of `index.html`, background colour of the light theme, icons 192, 512 and a maskable 512; no shortcuts, share target, protocol handlers or related applications), `apple-touch-icon` 180; the PNGs were rendered once from `favicon.svg` by `frontend/scripts/gen-pwa-icons.mjs` with the installed Chrome (no image fetch, no build dependency). The manifest link in `index.html` is inert without a worker.
7. **Proxy.** One listener stays (`:8080`, published on `127.0.0.1` only). Added: `header /manifest.webmanifest Content-Type "application/manifest+json"` (Caddy has no built-in type) and `header ?Cache-Control "no-store"` on `/api/* /health/*` (default only: a response that sets its own value keeps it). The CSP is unchanged: the worker is covered by `script-src 'self'` (a worker falls back to it), the manifest by `default-src 'self'`; no `worker-src` was added. `CaddyfileTests` pin this.
8. **Not built here (decided, left to the owner and a later slice):** the second site `:8081`, `compose.phone.yaml`, `xd-up.sh --phone`, `scripts/phone-check.sh`, `Clear-Site-Data` on logout (a backend change that only matters over HTTPS, which does not exist yet; the JavaScript clearing is the mechanism) and the update snackbar (nothing app-related is cached, so a page load always fetches the current build). No listener, tunnel, certificate or LAN bind was added. The phone path is an **owner security act**; the runbook is in doc 17 "Phone access".
9. **Honesty about installing.** A browser installs a PWA only from a secure context: `localhost` on the same Mac counts, a phone needs HTTPS that the owner sets up herself. The switch's card on /owner-acts says so.

## Consequences
- After deploy the switch is OFF: no worker is registered, nothing is cached, behaviour is as before except the extra capability read in the shell and the inert manifest link.
- **Limit:** a service worker is security-relevant code; the allow-list tests (`serviceWorker.test.ts`, with hostile URLs) are the guard and a reviewer reads `sw.js` line by line.
- **Limit:** offline, a page load shows only the offline page; the Mac and `localhost` PWA is verified in a real Chrome (install, six cached URLs, offline page, clearing); the phone and a tunnel are not.
- Entry chunk grew by about 0.3 KB gzip (198.2 to 198.5 KB of 200).
