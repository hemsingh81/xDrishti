# 0057 — The Lab API: validate, store and read strategy versions

- **Status:** Accepted (spec [P5-01](../specs/P5-01-lab-api-validate-and-strategy-library.md), which the owner approved on 2026-10-22, questions 1 to 5 as recommended; built on 2026-10-22). The text of this ADR has not been read by the owner.
- **Date:** 2026-10-22.
- **Relation to other ADRs:** [ADR 0002](0002-config-and-strategies-in-app.md) (strategies live in the database), [ADR 0034](0034-the-rules-expression-language-lint-and-compiler.md) and [ADR 0036](0036-the-typed-strategy-model-and-the-compile-of-its-sections.md) (the located problems and the compile), [ADR 0039](0039-an-engine-module-is-reached-from-an-adapter-in-infrastructure-never-from-application.md) (engine modules are reached through a port), [ADR 0055](0055-the-strategy-file-its-schema-and-the-content-hash.md) (the file, the schema, the hash), [ADR 0056](0056-stored-strategies-the-lab-tables-the-seed-and-loading-by-version.md) (the tables and the store port).

## Context
The owner needs to send a strategy text and get back located problems or a stored, immutable, hashed version, to list and download what he has, and to start a new version from an old one. P3-02c and P3-02d built the file library and the store; nothing yet served them over HTTP. No run is part of this slice (P5-02).

## Decision
1. **Seven use cases in `Application/Lab`**, one internal sealed handler each, registered explicitly: validate, create, list, get (a family with its versions), get version, clone, schema. The Api host maps them in `LabEndpoints` under `/api/lab`: `POST /validate`, `GET /schema`, `GET|POST /strategies`, `GET /strategies/{id}`, `GET /strategies/{id}/versions/{n}`, `GET .../file` (attachment, `application/yaml`), `POST .../clone`. The owner session is the only identity; no step-up (the store is insert-only and idempotent by hash).
2. **A new port, `IStrategyChecker`** (`Application/Abstractions/Lab`), because Application may not name an engine module (ADR 0039): `Check(text)` returns every problem with severity and place, plus the description when no problem is an error; `Retarget(text, newId)`; `SchemaJson()`. `StoredStrategies.Check` in the simulation library does the work (read, then `Simulator.Create` on every declared timeframe, which compiles every side); `Infrastructure/Lab/StrategyChecker` only maps plain values. `Describe`/`Inspect` (errors only, used by the seed and the runs) are unchanged.
3. **Problems.** `{ path, code, message, severity, line, column, endLine, endColumn, start, length, suggestion }`. `path` is the model path; `line`/`column` locate the field in the file (a compile problem is located by its path, falling back to the nearest enclosing field); `start`/`length` are the item-relative span of ADR 0036 and exist only for a problem of the rules language. Warnings are returned and never refuse a text. The same problem from two timeframes appears once.
4. **Validate answers 200 whatever the text.** `{ valid, hash, id, style, version, timeframes, sides, problems }`; `valid` means no error. A text over **64 KB** (UTF-8, owner question 5) is not read: it is a problem with the code `lab.text_too_large`, in validate and in create. A body over 256 KB is refused by the transport (413). A `format` other than `yaml` is `400 lab.unsupported_format` (owner question 4).
5. **Create.** Valid text only (else `422 lab.invalid_strategy`, with the problems under `problems`, nothing stored). The id comes from the text. **Version numbers are the server's (owner question 2):** the text may omit `version` or carry the number the new version will get; any other number is `409 lab.version_exists` (checked inside the store's transaction, so it is race-free). The same content is the same row: `200` and nothing written; a new version is `201` with a `Location`. The optional `note` (500 characters) and `parentHash` (a stored version; default: the previous latest) go to the store; a parent that is not stored is `400 strategy_store.invalid`.
6. **Built-ins are read-only through the API.** The create handler never sets `NewVersion.Seed`, and the request type has no such field, so a body carrying `seed` or `builtIn` is ignored: a new family is never a built-in and an append to a built-in is `409 lab.builtin_readonly` (the store's `Forbidden` is turned into a conflict). Only `StrategySeeder` sets `Seed`. Read, download and clone work for a built-in. Tests pin both facts.
7. **Clone stores nothing.** It returns the stored text re-written at the fixed layout of the file with a new id (the request's `newId`; else the same id for an ordinary family, and `<ID>_COPY` for a built-in), plus the hash of the source as `parentHash`, to be posted with it. The clone has no `version` line, so it is accepted as the next version of its family or as version 1 of a new one.
8. **Reads.** The list is the store's family list (id, style, built-in, creation time, latest version, version count); the family read adds the versions without their texts (`ListVersionsAsync`, added to `IStrategyStore`); a version read returns the text byte for byte and `problemsFree` (whether it passes the rules of today); the file is that text, so the download re-posted to validate gives the same hash. `GetAsync` now asks the database for one id instead of listing all families (P3-02d reviewer minor).
9. **Failures** use the shared problem-details mapping with the codes `lab.invalid_strategy` (422, with `problems`), `lab.not_found` (404), `lab.version_exists`, `lab.builtin_readonly`, `lab.id_clash` (409). Logs: `lab.strategy.created`, `lab.strategy.versioned`, `lab.validate.rejected` (ids 4436 to 4438): id, version, hash prefix and counts, never the text.

## Consequences
- The page (P5-08a) and the CLI (P5-07) have their whole contract; the OpenAPI document and the frontend types were regenerated.
- `ISimulationEngine` is unchanged; the new port keeps the file library and the compile out of Application.
- A stored text that no longer reads under a later release shows `problemsFree: false` and cannot be cloned (409), but can be read and downloaded.

## Honest limits
- The documented example of doc 11 §2 is **not valid today**: it lists SELL with no `sell:` block (the mirror is P3-02e), declares two exit candidates (the simulator runs one), a `buffer_atr` on a swing-low stop and two filters that have no data. Validate says so, with locations. The tests use a valid two-sided strategy.
- `name` is not in the family list: the model has no name, the id is the name.
- The 64 KB limit is judged in the handler after the transport accepts the body (up to 256 KB), so a text between the two limits is a located problem, not a 413. The 413 itself is configured by `RequestSizeLimit` and not exercised by the in-process test host.
- Validate runs the compile for each declared timeframe on the request thread (about a millisecond when warm; the test pins 50 ms at the 95th percentile). There is no rate limit beyond the session.
- Hiding or archiving a family is not part of this slice (owner question 3).
- A seed that fails (`StrategySeeder`) is skipped as a failed `Result` and logged; a database exception aborts `xd-api migrate`.
