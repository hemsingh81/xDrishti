# 0273 — Pre-seam bars enter a run only for an instrument proven verified through a stored basis, with the switch off by default and the seam by date

- **Status:** Proposed (spec [CF-04d](../specs/CF-04d-source-aware-replay-of-backfilled-bars.md), approved 2026-11-12 as the coordinator's recommendation under the owner's standing instruction). Becomes Accepted when the owner has read it.
- **Date:** 2026-11-12.
- **Relation to other ADRs:** completes [ADR 0270](0270-the-dhan-one-minute-backfill-writes-only-before-each-instruments-first-csv-bar-through-a-resumable-chunk-ledger-and-pre-seam-bars-stay-out-of-every-run.md) decisions 7 to 10 (which kept every pre-seam bar out of every run until this slice) and uses [ADR 0271](0271-the-run-record-states-depth-per-instrument-and-the-survivorship-limit-from-its-own-stored-bars-and-only-for-a-run-that-rests-on-backfilled-history.md) (its `depth:` lines then appear by themselves); the omit-when-empty pattern of [ADR 0263](0263-relative-strength-features-are-stored-rows-of-the-previous-closed-session-with-a-closed-parameter-set.md); ADR 0017 §5 (the adjustment rule).

## Decision
1. **One switch, off.** `Data:History:Replay:AdmitVerified` (default false) in the existing `Data:History` section. With it off every record, key and label is Part B's byte for byte, and no admission fact is read (no scan).
2. **Verified is a pure Domain rule that fails closed** (`SeamVerification.Decide`). The first failing reason, in this order: `switch_off`; the probe is not `passed` (`not_probed` for `none`, `seam_unresolved` for `unresolved`, anything else is `not_probed`); the recorded seam is not both the current seam (the oldest stored CSV bar) and the high-water mark (`seam_moved`); a `planned` or `failed` chunk (`backfill_unfinished`); the continuity check never ran on a basis (`continuity_unchecked`; `seam_jump = false` is not evidence); `seam_jump`; the probe's or the check's basis is not the current one (`basis_changed`); a `dhan` bar between the seam date and the last in-span ex-date (`dhan_in_csv_span`). Trusting `probe_status` alone was rejected: it is never lowered after an action edit, and the continuity flag means the same whether or not the check ran.
3. **The basis** is the SHA-256 of `seam instant | ex-date:kind:numerator:denominator:onCsv` per applied action (`onCsv` = ex-date on or before the date the CSV is adjusted through). The probe writes `probe_basis` on a pass and clears it on a fail; the continuity check writes `continuity_basis`, `seam_jump` and `jump_pct` on every run, and `xd data backfill` runs it also when nothing is left to fetch (it is local and needs no Dhan connection). A CSV load that moves the adjusted-through date without crossing an ex-date keeps the instrument verified; adding, editing or undoing an action, or crossing an ex-date, means probing again and re-checking.
4. **A seam that moved earlier stays excluded** (`seam_moved`); the cut stays at the high-water mark. Repairing it is a later slice.
5. **Factor mode.** `AdjustmentFactors.SourceAware(seamDate, csvAdjustedThrough)` returns the same actions with `FactorAt` following `SourceAwareFactors` (a bar before the seam date takes every later action, a bar on or after it takes those after both its date and the adjusted-through date). The replay, walker, extractor and trade replay take it unchanged; `SourceAwareFactors` stays the oracle and a property test checks equality on every date 2021 to 2026.
6. **Three readers admit** and a test pins it: the run reader (`InstrumentInputReader`, shared with the cards, AU-12 and the Lab), the trade-feature extraction (so training sees the bars the run saw) and the trade replay, all through `SeamAwareBars.ReadForRunAsync`. Every other reader (the SR-01 replay, pairs, option re-mark and condors, planning, the assisted-check days and every daily SQL reader) keeps the high-water cut, so a pre-seam entry that needs a daily-table input is blocked by the existing rules.
7. **An admitted instrument does not raise `csv_adjusted_twice`**: under the CSV rule no in-span action touches a CSV bar, and a probe pass shows the CSV is on the adjusted-through basis. Every other instrument keeps the guard and `ack`.
8. **Pre-seam is by date everywhere.** The writer's guard drops every Dhan bar dated on or after the seam date (`beyond_seam`); `SeamAwareBars` and `market.backfill_cut` cut at India midnight of the high-water seam date. The seam day is a pure CSV day; the first CSV day is no longer dropped from the daily readers. Minutes on the seam date before its first CSV minute can only be repair bars and are treated like any repair bar in the CSV span.
9. **The key changes only where bars are admitted.** After the `i=` lines, one `seam=<id>|<seam date>|<basis sha256>` line per admitted instrument in run order; the instrument record gets `pre_seam {seam_date, basis_sha256}`, omitted otherwise. No schema version is bumped. The bars hash of an admitted instrument covers its raw pre-seam bars, so it changes by design; old runs keep their keys.
10. **Honesty.** With the switch on and an instrument of the run having a seam row, the run record gets `backfill_admission {admitted, excluded[{reason, count}]}` (omitted otherwise, never keyed) and the labels one line `backfill: pre-seam bars admitted for A instruments (source-aware); excluded for E (reason n, ...)`, reasons in ordinal order. `xd data history` shows `verified=yes` or the first reason per instrument (reported as if the switch were on).

## Consequences
- A wrong factor on a pre-seam bar would corrupt every result built on it, so everything unknown stays excluded and the switch is an owner act: run `xd data probe-seam`, then `xd data backfill` (it writes the continuity basis), then set the switch. Flip it between simulate-everything jobs, not during one.
- Per run, each instrument with a seam row costs the facts read (four small queries, one scan for the current seam and one for a `dhan` bar in the span, only when the switch is on and the cheaper reasons pass). If that is too slow, add a partial index on `(instrument_id, ts) WHERE source = 'csv'` and update `DataTableGrantsTests`.
- Migration `AddSeamVerificationBasis`: `probe_basis` and `continuity_basis` (`char(64)`, null) on `market.backfill_seams`, and `CREATE OR REPLACE` of `market.backfill_cut`; grants unchanged.
- The five-year 1-minute goal is met for an instrument only when it is verified and the owner has switched admission on; unverified instruments run as in Part B. Daily-table inputs have no pre-seam rows, so a strategy that needs one at a pre-seam entry is blocked (fail closed). The API and the History card are CF-04e.
- **The midnight cut changes behaviour even with the switch off.** A `dhan` repair minute dated on the seam date before the first CSV minute was excluded by the instant cut and is kept now (it is treated like every repair bar in the CSV span), and the seam-day daily bucket, which starts at India midnight, was dropped by every daily reader and is now returned. Both only affect an instrument with a seam row. Before the owner acts, list the instruments with such minutes: `SELECT b.instrument_id, count(*) FROM market.bars_1m b JOIN market.backfill_seams s USING (instrument_id) WHERE b.source = 'dhan' AND b.ts >= date_trunc('day', s.high_water_at AT TIME ZONE 'Asia/Kolkata') AT TIME ZONE 'Asia/Kolkata' GROUP BY 1;`. An instrument that returns rows has such minutes; they are repair bars and are covered by `dhan_in_csv_span` when it matters.
- **`shortcut:` `backfill_admission` is not keyed.** The run key holds the `seam=` lines and the bars hashes; the admission counts are in the record and the label only. The store's `ON CONFLICT DO NOTHING` keeps the older record when two runs share a key, so a re-run with different counts but the same admitted set shows the first one's counts.
- **Readers that follow a stored run** (the feature extraction, training through it, the trade replay, the trade cards) use the run's `pre_seam` record and not today's switch; see the spec's "As built".
