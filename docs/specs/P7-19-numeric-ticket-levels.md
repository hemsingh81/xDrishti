# P7-19 — Numeric ticket levels: entry reference, stop and target stored beside the text rules

- **Status:** Draft (written 2026-10-24; decisions below were researched under the owner's delegation; the owner's Approved is still needed before an agent builds it)
- **Phase / roadmap row:** P7 — Selection, accounts & nightly plan; follow-up of P7-04 and P7-11 (not a row of the original P7-00 table). Consumed by P7-20 (alerts) and P8-14 (ticket charts).
- **Design refs:** docs/design/10-trade-selection.md (ticket anatomy), 07 §1 and §2 (setup versus trigger), 11 (stops, exits), 13 (Trade Plan: entry / stop / target overlays), 19 §4 · ADR 0083 (plan record: insert-only, text-only levels), 0088 (ticket builder: levels indicative from the close), 0096 (pre-open: "the trigger and stop are text, so a price crossing cannot be evaluated"). New ADR: [0109](../adr/0109-plan-tickets-store-indicative-entry-stop-and-target-as-numbers-beside-the-text-rules.md).
- **Needs:** P7-03, P7-04, P7-09 (built). **Needed by:** P7-20, P8-14(d).
- **Size:** 2 agent-days (estimate; pure type 0.5, builder/mapping 0.5, migration + store + API 0.5, UI row + tests 0.5).
- **Safety:** no. It adds numbers to a stored record and shows them; it touches no order, credential, setting, approval or autonomy path, and no UI write. The no-order tripwire (ADR 0083) stays green.

## Goal
The plan ticket carries, as typed numbers, the indicative entry reference, stop level and target level that the ticket builder already computes and today flattens into sentences, so that alerts (P7-20) and charts (P8-14) can use them without parsing text; everything that is a rule rather than a level stays text, and nothing about the plan record's meaning changes.

## Verified facts (2026-10-24, code opened)
- `Simulation/Scanning/TicketBuilder.Draft` computes `entry = bars.Minutes[^1].Close` (the close of D), `Stop(...) -> (text, level)` and `Target(...) -> (text, rr, level)`. `TicketDraft` (Domain/Planning) already holds `StopLevel`, `IndicativeEntry`, `RewardRisk`; **there is no `TargetLevel` field**: the target level exists only inside `TargetText`.
- `SelectionPlanBuilder.Item(...)` builds `NewPlanItem(rank, group, symbol, side, strategyId, hash, Clamp(TriggerText,500), Clamp(StopText,500), Clamp(TargetText,500), Clamp(ValidityText,200), reasons, evidence, allocations)`: the numbers are dropped there. `Application/Abstractions/Planning/NewPlan.cs` declares the record; `PlanStore.cs:593` is the only other constructor call found.
- `trading.plan_items` (migration `AddPlanRecord`, config in `PlanConfigurations.cs`) has text columns `trigger_text`, `stop_text`, `target_text`, `validity_text` and checks `ck_plan_items_group`, `ck_plan_items_p_win_lower`, `ck_plan_items_shape` (`side IN ('BUY','SELL')`). Insert-only for `xd_app`; P7-03 assumption 17: no later migration may re-grant the schema (an architecture test fails on it).
- `PlanItemView` (Application/Planning/PlanView.cs) exposes `Trigger`, `Stop`, `Target`, `Validity` as strings and `Evidence`. `Input hash`: `SelectionPlanBuilder.Hash` includes `Trigger|Stop|Target` text per item; `plan_key` is `NightlyRules.PlanKey(forDate, BuilderId)`.
- Stop kinds in the builder: `FixedPct`, `AtrMult` (relative to the entry), `SwingLow/SwingHigh/BarLow/BarHigh` (a level read from a 1D-or-longer feature), `OrOpposite` (opening range, intraday: no number). A level is produced only when the feature is `Timeframe >= D1` and ready; otherwise the text says "level set on tomorrow's data".

## Scope
**In:** Domain `Planning.TicketLevels` (pure value type + factory), `TicketDraft.TargetLevel` and the mapping in `TicketBuilder`; `NewPlanItem` / `PlanItem` / `PlanItemView` gain an optional `Levels`; migration `AddTicketLevels`; `PlanStore` read/write; hash rule; `scripts/gen-api.sh`; a "Levels" row on the ticket card of `/plans` (P7-17); tests; ADR.
**Out:** any alert (P7-20), any chart (P8-14), any use of levels in grading, journal, selection, sizing or approval, changing a ticket's text, letting the owner edit a level (Modify stays "size down only"), levels for intraday-only stops, a level derived from tomorrow's data, backfilling stored plans.

## Acceptance criteria
1. Given a BASE_BREAKOUT-like fixture whose stop is `swing_low` and exit is a fixed 2R, when the builder runs, then the item carries `entry_ref_price` = close of D, `stop_level` = the swing low, `stop_anchor = 'level'`, `reward_risk = 2`, `target_level = entry + 2 x |entry - stop|` (BUY) and `levels_session = D`; the three texts are byte-identical to what P7-04 produced before this slice (golden test on the text).
2. Given a `fixed_pct` or `atr_mult` stop, then `stop_anchor = 'close_of_d'`; given `or_opposite`, an ATR not ready, or a missing lookback, then `stop_level`, `stop_anchor`, `target_level` and `reward_risk` are null while `entry_ref_price` stays set, and `unavailable` gains `levels:stop_not_numeric` (never a guess).
3. Given an exit that is a rule with no fixed target (trail, time stop, partials), then `target_level` and `reward_risk` are null and the text keeps the rule; `unavailable` already lists `target` where the exit did not match (P7-04), unchanged.
4. Given a SELL ticket, then `stop_level > entry_ref_price` and `target_level < entry_ref_price`; a BUY mirror. The database refuses the wrong orientation, a non-positive level, a target without a stop, a stop without an anchor, and `levels_session` without `entry_ref_price` (and the converse) on a direct insert.
5. Given a computed stop distance that is zero or more than 30 % of the entry (`TicketLevels.MaxRiskFraction`), then no stop or target is stored, `unavailable` gains `levels:implausible_stop_distance`, and the text is unchanged.
6. Given a plan stored before this migration (rows inserted without the new columns), then `GET /api/plans/{id}` returns the items with `levels: null`, the plan reads, approves, arms, expires and grades exactly as before (regression run of the P7-03, P7-10, P7-11, P7-13, P7-14 suites unchanged).
7. Given the same inputs, then two runs produce identical levels and an identical `input_hash`; the hash includes the numeric fields only when at least one is non-null (an item with no levels hashes exactly as before this slice).
8. Truncation property (extends P7-04 criterion 3): adding, changing or removing any bar after the close of D never changes the stored levels.
9. Given `PUT`/modify of a ticket (P7-10), then levels are unchanged and a modification never reads or writes them; the approval row's `modifications` JSON has no level key.
10. The card on `/plans` shows "Indicative levels, read at the close of {D}: entry {x} · stop {y} (level|from the close) · target {z} (RR {r})" using server numbers, or "Levels: rules only (see the stop and target text)" when `levels` is null; the pinned sentence "Indicative from the close of {D}, not tomorrow's price. No order is placed." is on the row. Plain text only.
11. `xd_app` still cannot UPDATE or DELETE `trading.plan_items` (`PlanGrantsTests` green); the migration does not call `GrantSchemaUsageToAppRole` for `trading`; `Down` drops only the six columns and the check.

## Contract
- **API:** no new route. `PlanItemView` gains `levels: TicketLevelsView | null` appended after `allocations` (existing fields, names and order unchanged, so existing clients keep working): `TicketLevelsView { entryRef: decimal, session: date, stop: decimal?, stopAnchor: "level"|"close_of_d"|null, target: decimal?, rewardRisk: decimal?, basis: string }` with `basis` fixed to "indicative from the close of the session; not tomorrow's price" (a server sentence pinned by a test, like `PlanWording`). Contract regenerated (`scripts/gen-api.sh`).
- **Data:** migration `AddTicketLevels` (append-only): on `trading.plan_items` add nullable `entry_ref_price numeric(18,4)`, `stop_level numeric(18,4)`, `stop_anchor varchar(12)`, `target_level numeric(18,4)`, `reward_risk numeric(9,4)`, `levels_session date`; check `ck_plan_items_levels` = shape of criterion 4 (written with `side`), and `stop_anchor IN ('level','close_of_d')`. No index (read through the item). Values are rupees, rounded half away from zero to 4 decimals when stored (the display rounds to 2). No change to grants.
- **Domain:** `TicketLevels` (record, `Create(side, entryRef, session, stop?, anchor?, target?, rr?)` returns `Result`), `StopAnchor` enum. `TicketDraft` gains `TargetLevel`; `TicketBuilder` fills it from the same expression as the target text (so number and text cannot drift; a test parses `0.##` of the number out of the text).
- **UI:** feature `plans` (P7-17): one row component `LevelsRow` inside the existing ticket card; no new route, no new dependency.

## Decisions (researched)
1. **Columns on `plan_items`, not a side table, not JSON, not parsed text.** Reason: levels are immutable properties of one candidate row, the table is insert-only and a nullable `ADD COLUMN` rewrites no stored row, the database can check orientation per side, and a read stays one query. Rejected: `trading.ticket_levels` side table (extra FK and join for a 1:1 record, nothing gained); a jsonb column (no checks, no typed comparison in P7-20's SQL); regexes over `stop_text` (the sentence is for humans and may be reworded; ADR 0027's rule "no code matches the text of a message"). Source: P7-03 assumption 17 and `PlanConfigurations.cs`.
2. **What is numeric and what stays text.** Numeric: the close of D (entry reference), a stop that reads 1D-or-longer data (`swing_*`, `bar_*`, `fixed_pct`, `atr_mult`), and a target only for a fixed reward-to-risk exit. Text: every trigger condition (intraday or clock parts are unknowable at the close, P7-04 4a), the validity window, trails, partials, time exits, the opening-range stop, and any level whose input is not ready. Reason: this is exactly what the builder can know without tomorrow's data; storing more would be invented precision. Source: ADR 0088 assumptions 4a, 5, 6 and the code above.
3. **A stop anchor is stored.** `level` (a market structure level that does not depend on where the owner enters) versus `close_of_d` (a percentage or ATR distance from the close of D, which moves with the real entry). P7-20 only calls the first a "stop level crossed" without qualification and labels the second "indicative, from the close". Rejected: one undifferentiated "stop" number (it would present an entry-relative stop as a market level). Source: `TicketBuilder.Stop`.
4. **Plan record semantics are untouched.** Texts, lifecycle, approvals, the cutoff, modifications ("size down only") and grading do not read the numbers; the item is still immutable and the plan is still idempotent by key. The numbers are a structured copy of what the text already says, labelled indicative. Alternative rejected: letting Modify change a level (would make an approved ticket differ from the proposed one and open a path to loosen a stop; ADR 0083 forbids loosening limits).
5. **Hash and key.** `plan_key` is unchanged. Levels join the per-item line of `input_hash` only when present, so an unchanged input without levels hashes as before. A re-run of the same date after this deploy therefore yields a new `version` of that date (a different input, never an edit, P7-03 assumption 7), which is the existing, tested behaviour. Rejected: excluding levels from the hash (two plans with different numbers would share a key).
6. **Backward compatibility.** Columns nullable, DTO field optional and appended; stored plans are not backfilled (the close of a past D is recomputable only by re-running a build, and a re-run is a new version; inventing it later would label history). A null `levels` is a normal state the UI and alerts handle.
7. **Plausibility cap 30 %.** A stop 30 % or more from the entry on a daily-bar strategy is more likely a data fault (unadjusted split inside the lookback, doc 05 corporate actions) than a plan; the number is withheld and `unavailable` says why. The 30 % is a code constant `TicketLevels.MaxRiskFraction` (owner-tunable setting not worth a settings home yet). Source: doc 19 §4 "bad data, wrong plan".
8. **How P8-14 uses it.** `PriceChart` draws horizontal price lines for `stop`, `target` and a dashed `entryRef` labelled "close of {session}", only for non-null values, with the caption from `basis`; where `levels` is null it shows the rule text and no line. Never a line from parsed text. P8-14's "structured flags" and "per-account standings" parts are independent of this slice.
9. **Grading and journal stay on their own simulated levels** (ADR 0090, P7-14 assumption 7: the plan grade's simulated entry and stop define 1R). Reason: the indicative close is not a fill; mixing them would silently change stored grades' meaning. Rejected: re-basing grades on these numbers.

## Risks and honest limits
- **Indicative, not tomorrow's price.** The entry reference is yesterday's close; a gap changes every distance. The pre-open check (ADR 0096) invalidates large gaps (0.5 x ATR) but a smaller gap still shifts a `close_of_d` stop. The row says so in a pinned sentence.
- Levels use the stored, adjusted-as-stored daily data, in-sample strategy definitions; they are not a recommendation. Cost, slippage and the real fill are absent.
- A trigger that is still text means the system cannot say whether the setup fired; a level number is not an order and not a protection ("armed means watched").
- Existing plans stay without numbers; the first plan with numbers is the first one built after the owner switches the builder on (the selection builder is OFF by default, ADR 0088).
