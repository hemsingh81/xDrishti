## Goal
A strategy is a text file the owner can write, upload, download and diff. The backend reads it into the `StrategyDefinition` of schema 1 (or says exactly where it is wrong), serves a JSON Schema for the editor, and gives every strategy one canonical text and one SHA-256 that do not change with white space, key order, comments or quoting. P3-02d stores that text and hash; P5 validates and runs it. This slice changes no simulation rule.

## What the code does today (read 2026-10-22)
- **No YAML anywhere.** `Directory.Packages.props` has no YAML or JSON-Schema package (`Superpower` 3.2.1 is the only parser dependency). `XDrishti.Strategies` may reference Superpower only; an architecture test pins the package set (`StrategiesArchitectureTests`), and it knows no file, clock or database. So the reader cannot live in it (roadmap row), and needs a new project.
- **The model** (`XDrishti.Strategies.Model`) is sealed records with value equality: `StrategyDefinition(Schema, Id, Style, Timeframes, Sides, Params, Buy, Sell, TimeRules, Filters)`; `SideRules(Setup, Trigger, Invalidate, Entry, Stop, Exits, Overlays)`; `ConditionList(Mode, Items)`; `ExitSpec(Policy, Parameters)` with `ExitParameter(Name, Values: Quantity[])`; `OverlaySpec`; `StopSpec(Kind, Timeframe, Pct, Mult, Lookback, Minutes, BufferAtr, AtrPeriod)`; `Quantity(Number | Param)`; `TimeRules(FirstEntry, LastEntry, SquareOff, MaxHoldSessions)`. A null section is "absent as written"; the compile decides if that is allowed. Limits: 4 params, 100 items per list, 1 to 10 values per exit list (`ExitParameter` summary), ids `[A-Za-z][A-Za-z0-9_]*` up to 64.
- **There is no `name`, `version`, `universe` or `test` in the model.** Doc 11's example has `version: 1`, `universe: {…}` and a `test:` block. They are not part of schema 1.
- **An interim canonical text exists:** `XDrishti.Simulation.Replay.DefinitionJson.Write(definition)` (internal; hand-written over a `StringBuilder`, snake_case member names, `FIXED_RR`-style policy names, `HH:mm` times, numbers by `CanonicalText.Number` (`R` format, `0` for zero), no white space, absent members left out, lists in model order, each condition parsed and printed again by `ExpressionPrinter`). `StrategyPreparation.MemberOf` puts it and `CanonicalText.Sha256Hex(json)` into the `StrategyRecord` of every run, so the strategy hash is already in every stored run key. Its header says it is interim "until P3-02c defines the canonical text".
- **The three built-ins are C# builders** (`OrbV1`, `VwapPullback`, `BaseBreakoutV1`, each `Create(...)`), reached by id through `BuiltInStrategies.Build/Prepare`, which also owns the closed list of verb parameters per id (including `rr`, which the builders write as a literal `Quantity.Of(rr)` in the exit and do **not** declare as a strategy param) and their ranges.
- **Located problems today** are `LocatedProblem(path, Problem(code, message, SourceSpan))` with paths such as `buy.trigger[1]`, `buy.stop.lookback`, `time_rules.last_entry`, `filters[0]`; the span is inside the condition text. There is no line or column of a file.
- Doc 11's example uses `trail: { type: ATR, mult: 2.0 }` for `PARTIAL_TRAIL`; the model's table for that policy is `book_pct`, `t1_rr`, `trail_atr_mult`, `atr_period` (doc 11 *model as built*, ADR 0036 Amendment 2). The example and the model disagree (see D4, question 3).

## Definitions

**D1. The file.** UTF-8 text, one YAML document, root mapping with one required key `strategy`. Optional siblings: `test` and `universe` (D2). Inside `strategy`, the fields of doc 11 §2 map to the model as follows (YAML spelling → model):

| File | Model | Notes |
|------|-------|-------|
| `schema: 1` | `Schema` | optional in the file, default 1 (the only schema); any other value is `file.unsupported_schema` |
| `id` | `Id` | required |
| `version: n` | not in the model | envelope field (D2) |
| `style` | `Style` | `intraday` or `swing` |
| `timeframes: [15m]` | `Timeframes` | codes `5m 10m 15m 30m 1h 1D` |
| `sides: [BUY, SELL]` | `Sides` | |
| `params: { name: number }` | `Params` | a mapping; **order of keys is not significant** (D8 sorts by name) |
| `setup`, `trigger`, `invalidate` | `ConditionList` | exactly one key, `all` or `any`, a list of strings |
| `entry: { type: at_close }` | `EntrySpec(Kind)` | `at_close`, `stop_above_high`, `limit_pullback` |
| `stop: { type: swing_low, lookback: swing_lookback, buffer_atr: 0.1 }` | `StopSpec` | `type` → `Kind`; a number or a parameter name for each `Quantity` |
| `exits: [{ policy: FIXED_RR, rr: [2.0] }, …]` | `ExitSpec` | `policy` → `Policy`; every other key is one `ExitParameter`, a scalar (one value) or a list (1 to 10 values) of numbers or parameter names |
| `overlays: [{ kind: time_stop, min_progress_rr: 0.5, intraday_bars: 6 }]` | `OverlaySpec` | same flattening; doc 16 spells overlays under `exits.overlays`, UNVERIFIED which spelling the owner wants (question 4) |
| `time_rules: { last_entry: "14:30", square_off: "15:15" }` | `TimeRules` | `HH:mm`; `max_hold_sessions` an integer |
| `filters: [not_event_day]` | `Filters` | names only |
| `buy:` / `sell:` | `Buy` / `Sell` | the sections above may sit directly under `strategy` (the BUY side, as in doc 11's example) or under `buy:`/`sell:`; **one spelling only** is written by the writer (D7): the `setup … overlays` keys at the top level are the BUY side, `sell:` is the SELL side. UNVERIFIED against the doc 11 example for a strategy with an explicit `buy:` (question 4) |

**No implicit typing.** Every scalar is read as text and converted by the field's own rule (the "Norway problem" and YAML 1.1 sexagesimal numbers such as `09:45` do not exist here): numbers must match `-?(0|[1-9][0-9]*)(\.[0-9]+)?([eE][+-]?[0-9]+)?` and be finite (so `0x10`, `0o7`, `1_000`, `.inf`, `.nan`, `+1`, `yes`, `on` are refused with `file.bad_number`); booleans do not occur in schema 1.

**D2. Envelope.** `version` is a positive integer (optional) and is **not part of the canonical form or the hash**: it is the family's counter, owned by the store (P5-01 question 2 recommends server-assigned; the text may carry it and the store checks it equals the next number or is omitted). `universe` and `test` are read as opaque trees (still under the limits of D3), **reported as the warning `file.section_not_validated`** with the path, returned in the parse result and **excluded from the hash**: they say how to test a strategy, not what it is (P5-00 D2 puts the test method into the Lab run identity). A key anywhere else that is not in the table of D1 is `file.unknown_field` (never ignored).

**D3. Safe reading.** The text is parsed by the **event-level parser of the YAML library** into the file package's own tree (`FileNode`: mapping, sequence or scalar, each with line and column, scalars with their raw text and whether they were quoted); the library's object deserializer is not used. Limits, each its own problem, values UNVERIFIED and set in one `FileLimits` record: text ≤ 256 KiB (checked **before** parsing, by bytes); depth ≤ 12; nodes ≤ 5,000; one scalar ≤ 4,096 characters (a condition is ≤ the language's own limit); a mapping ≤ 64 keys; a sequence ≤ the model's limits (100 conditions, 10 exit values). Refused outright, by name: anchors and aliases (`file.alias_refused`, which ends the billion-laughs class), tags and merge keys `<<` (`file.tag_refused`), more than one document, a duplicate key in one mapping (`file.duplicate_key`; the YAML library's default is to keep the last), a control character other than tab and newline, a byte-order mark followed by invalid UTF-8. A syntax error is `file.yaml_syntax` with the parser's line and column and a message in our words. The reader reads a string once; no file path, URL, include or `!!` construct is ever followed.

**D4. Mapping and the doc 11 example.** The mapper is table-driven (D6) and never throws on user input. For the one disagreement found, the spec follows the model: `PARTIAL_TRAIL` is written `book_pct`, `t1_rr`, `trail_atr_mult`, `atr_period`; the doc 11 example is corrected in the same change (question 3). A parameter name used in a `Quantity` position is resolved by the compile, not here (the mapper only knows "number or string").

**D5. Located problems.** One record in the file package, `FileProblem(Path, Line, Column, EndLine, EndColumn, Code, Severity, Message)`. `Path` is the model's path (`buy.trigger[1]`, `exits[0].rr[1]`, `stop.lookback`) so that the compile's problems map straight through; line and column come from a table `path → FileNode` built while mapping. A compile problem (`LocatedProblem`, with a span inside a condition) becomes a `FileProblem` whose range is the condition scalar plus the in-item span as `Offset` (for a quoted or block scalar the in-item span is exact only for a single-line plain or quoted scalar; UNVERIFIED for `|` and `>` blocks, so those get the whole scalar). Severity is `error` or `warning` (the compile's warnings such as `exit_not_evaluated` pass through). The reader reports **all** mapping problems of the file in one pass in file order, not the first; it does not compile (`StrategyCompiler` runs in P5-01's pipeline order: parse, map, compile for each declared side and timeframe). Codes are `file.*`, stable strings pinned by a test.

**D6. One descriptor table, three uses.** The file's shape is a closed table in the file package: per object its fields, YAML name, type (string, enum with members, integer with range, number-or-param, list of …, mapping of …), required or optional, and for the exit and overlay objects the parameter names and kinds taken from `ExitTables` (internal to `XDrishti.Strategies` today, UNVERIFIED how it is exposed; either an `InternalsVisibleTo` for the new project or a small public read-only view, the second preferred). The **mapper**, the **JSON Schema generator** (draft 2020-12; `$id` `urn:xdrishti:strategy:1`; `additionalProperties: false` everywhere; enums for kinds and timeframes; `minItems`/`maxItems`; ranges where the model has them; `x-xd-path` omitted) and the **writer** read it, so a field cannot exist in one and not in another. The schema checks shape only: the conditions are strings, and `StrategyCompiler` is the only judge of the rules, the cross-field relations (`first_entry ≤ last_entry < square_off`) and the ranges that depend on a parameter. The schema is produced by a function, golden-tested against a checked-in file `backend/tests/XDrishti.Strategies.File.Tests/golden/strategy-schema-1.json` (UNVERIFIED path), and served by P5-01 (`GET /api/lab/schema`); a schema change without a golden change fails the test.

**D7. The writer.** `StrategyFile.Write(definition)` returns YAML text in a fixed layout (keys in the order of D1's table, block style, two spaces, conditions as plain or double-quoted scalars as needed, `"HH:mm"` quoted, no comments, `\n` line ends, trailing newline). `Read(Write(d)) == d` for every definition the reader can produce, and `Write(Read(Write(d))) == Write(d)` (a fixed point). A download in P5-01 returns the stored text, not this; the writer exists for the seed (P3-02d writes it once into a resource, a test keeps them equal), for `xd strategy …` and for the tests.

**D8. The canonical form.** `CanonicalStrategy.Json(definition)` = the existing `DefinitionJson` output, moved into the file package's sibling that both the file package and `XDrishti.Simulation` can use (the Strategies project is the natural home, as it is pure: UNVERIFIED that `CanonicalText` (in `XDrishti.Domain.Research`) and `ExpressionPrinter` are reachable from there; both are today), with **two changes**: (a) `params` are written **sorted by name, ordinal** (a YAML mapping has no order, so the hash must not depend on it); (b) the envelope is outside. Everything else is kept byte for byte: no white space, snake_case, absent members omitted, lists in model order (the order of `exits` is the order of the candidates and the order of conditions in a list is the author's), numbers by `CanonicalText.Number` (so `2`, `2.0` and `2.00` are one number), each condition parsed and printed again by `ExpressionPrinter` (so extra brackets and white space do not change the text, while `rsi()` and `rsi(14)` still do: the text is the version, ADR 0002; question 5). The canonical text starts with `{"schema":1,"id":…`. It is taken **from the model, not from the YAML**, so comments, quoting, key order, flow or block style and `all` list spelling never reach it.

**D9. The hash.** `StrategyHash = CanonicalText.Sha256Hex(canonicalJson)`: 64 lowercase hex characters of the SHA-256 of the UTF-8 bytes. It names a strategy **version by its content** (the id is inside, so two families never share a hash; the `version` number and the envelope are outside, so re-numbering does not change it). Two files with the same hash are the same strategy.

**D10. Effect on the run records already made.** The run key includes the strategy hash (doc 11 §6), so D8(a) can change the hash of a built-in whose params are not already in name order, and therefore change the run key of the same run. The three builders declare `or_min` (ORB), `pull_atr` (VWAP_PULLBACK) and `base_len, base_pct, vol_x` (BASE_BREAKOUT, already in name order), so sorting changes none of their texts (read 2026-10-22). Criterion 8 pins that every built-in's canonical text and hash are **unchanged** by this slice. If they are, no stored run is re-keyed. If a built-in's hash changes (question 1 in P3-02d, which declares `rr` as a parameter), the change is that slice's, recorded in its ADR, and old runs keep their keys (insert-only; they were produced by the old text).

## Acceptance criteria
1. Given the doc 11 §2 example (corrected per D4, question 3), when read, then it yields a `StrategyDefinition` equal to the hand-built model of the same strategy, the warnings `file.section_not_validated` for `universe` and `test`, and no errors; and it compiles through `StrategyCompiler.Compile` for its `15m` BUY side with the feature list the P3-02b spec lists.
2. Given any definition `d` of a generator corpus (all kinds of stop, entry, exit policy with its parameter tables, overlay, list mode, style, quantity by number and by parameter name), when written and read again, then the result equals `d`, and writing again gives identical text.
3. Given the example, when the white space, key order, comments, number spelling (`2`, `2.0`), block versus flow style and the position of `version` change, then the canonical text and the hash are identical; when one condition is changed (`>` to `>=`) or one number, then they differ.
4. Given 12 mutations of the example (a misspelt key, a wrong type, a missing required field, an unknown policy, an out-of-range `book_pct`, an unknown timeframe, a list over its limit, an `all` and `any` together, a bad time, a negative number, a duplicate key, a field not used by its kind), then each is reported with its path, line, column and code, all in one pass, and the JSON Schema rejects every one that is a shape error (the others are rejected by the compile); a table says which.
5. Given inputs of an attacker (anchors and aliases including a nested "billion laughs" of 10 levels, a 10 MB text, depth 200, 100,000 nodes, a `!!python/object` tag, a merge key, two documents, a duplicate key), then each is refused with its own code, in under 100 ms, with allocations bounded by the limits (a test on the bytes allocated).
6. Given the generated JSON Schema, then it validates against the draft 2020-12 meta-schema, accepts the example and the writer's output for the corpus of 2, rejects the shape mutations of 4, and equals the golden file.
7. Given a number spelt `0x10`, `1_000`, `.inf`, `.nan`, `+1`, `1e999`, `yes`, or a quoted `"2"` in a number field, then each is `file.bad_number` or `file.wrong_type` at that scalar, and an unquoted `09:45` and a quoted `"09:45"` in a time field both read.
8. Given the three built-ins, when each is converted by `CanonicalStrategy.Json` and hashed, then the result **equals the text and hash that `StrategyPreparation` writes into the run record today** (pinned with the three known hashes), so no stored run is re-keyed (D10); a test fails if `DefinitionJson` and `CanonicalStrategy` differ on a corpus of 200 seeded definitions, except for the sorted `params`.
9. Given the file package, then an architecture test pins: it references only `XDrishti.Strategies`, `XDrishti.Domain` and the YAML package; `XDrishti.Strategies` still references Superpower only; no `System.IO`, clock, network or reflection over user input in the reader.
10. Given the benchmark of 1,000 reads of the example, then the median is ≤ 1 ms for read plus map (UNVERIFIED target; compile excluded) and the schema is generated once per process.

## Contract

- **Data:** none.
- **Library:** a new project `XDrishti.Strategies.File` (name UNVERIFIED) with `StrategyFile.Read(string text, FileLimits? limits) → FileReadResult(Definition?, Envelope, Problems)`, `StrategyFile.Write(definition)`, `StrategyFileSchema.Json()`, `CanonicalStrategy.Json(definition)`, `StrategyHash.Of(definition)`. - **UI/events/jobs:** none.

## Non-functional
Security: untrusted text, all limits before allocation, no object deserialization, no tags, no aliases, no file/network reach, no condition text logged beyond path and code. Performance per criterion 10; the read of a 256 KiB text is bounded by the limits. Observability: the reader logs nothing; P5-01 logs path-free counts. Determinism: same text, same result on every machine (no culture: all number parsing and printing by `InvariantCulture`).

## Test plan
Unit: the table of `file.*` codes (one case each); the mapper per object with good and bad inputs; the quantity rules (number or name); `all`/`any` shapes; the limits at the edge (limit and limit + 1); round trip and fixed point on a seeded generator of 500 definitions; hash stability under 10 syntactic perturbations of the example; hash difference under 20 one-token mutations; the three built-ins equal their current record text and hash; schema generation, meta-validation, golden file, agreement with the mapper on a corpus (every text the mapper rejects for shape is rejected by the schema and the reverse; a test-only JSON-Schema validator package, UNVERIFIED which). Properties: random bytes never throw; random mutation of the example never throws and always yields either a definition or at least one problem. Architecture: criterion 9. Benchmarks (explicit, not in `check.sh`): criterion 10 and 5. Edge cases: empty file, only `strategy:`, a root that is a list, CRLF, tab indentation (YAML forbids it: a located syntax error), non-ASCII in a condition (accepted, the language decides), a 4,096-character scalar.

## Open questions (for the owner; each with a recommendation)
1. **Where the reader lives.** A new project `XDrishti.Strategies.File` (depends on `Strategies`), or inside `Infrastructure`? Recommended: the new project; it is pure and testable, and the roadmap already says "outside `XDrishti.Strategies`". Infrastructure would make P5-01's validate depend on a database project.
2. **The YAML package.** Use the parser of an established library (event level only) or write a small YAML-subset reader? Recommended: the library's parser; YAML has enough traps (multiline scalars, flow collections, anchors) that a subset reader would be the larger risk, and the limits of D3 are applied on our tree.
3. **Doc 11's example.** Correct `trail: { type: ATR, mult: 2.0 }` to the model's `trail_atr_mult: 2.0` (doc change), or teach the reader a sugar for it? Recommended: correct the doc; one spelling per field, and the model's tables are final (ADR 0050).
4. **Sections and overlays.** (a) `universe` and `test` accepted and ignored with a warning (recommended: yes, so the doc 11 example reads verbatim) or refused until P5-03? (b) `overlays` as a top-level key of a side (recommended; matches the model) or as doc 16's `exits.overlays`? (c) BUY sections at the top level and `sell:` (recommended; matches the example) or `buy:`/`sell:` both?
5. **Equivalent spellings.** Keep "the text is the version" (`rsi()` and `rsi(14)` hash differently) or normalise default arguments? Recommended: keep; normalising needs the binder to print the resolved call, which is a language change (a new ADR), and a false "different" is harmless while a false "same" is not.
6. **`version` in the text.** Accepted and checked by the store (P5-01 question 2) or refused? Recommended: accepted, excluded from the hash.
7. **Limits.** Are 256 KiB and 100 conditions enough, or smaller? Recommended: as stated; a strategy larger than 256 KiB is not a strategy.
8. **Order of work.** P3-02c and P3-02d together (5 d) before P5-01/P5-02, as P5-00 question 1 recommends? Recommended: yes; P3-02d depends on D8 and D9 of this slice.
