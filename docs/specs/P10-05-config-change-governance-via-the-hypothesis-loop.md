# P10-05 — Config change governance: a fingerprint, measurement epochs, the frozen-during-measurement rule and the hypothesis queue

- **Status:** Draft (written 2026-10-24; decisions below were researched under the owner's delegation; the owner's Approved is still needed before an agent builds it)
- **Phase / roadmap row:** P10 — Paper trading, slice P10-05 of [P10-00](P10-00-paper-trading-plan.md)
- **Design refs:** docs/design/18 (P10 row: "config changes only via hypothesis loop"), 19 §3 ("Tweaking after every loss: changes only via hypothesis loop; versioned config"), 09 §5 (hypothesis loop), 09 §12, 09 §13 (guardrails), 16 (configuration), ADR 0002 (config in the app), 0073 (changelog, the log is the state), 0076 (hypotheses: accepting applies nothing), 0072 (experiments), 0091 (autonomy)
- **Needs:** P10-01 (epochs table and `IEpochGate`), P10-02; P6-08, P6-10 (built). ADR + design change: "doc 09 §5 and doc 18 P10: a measurement epoch freezes the measured configuration; any frozen change starts a new epoch" (next free ADR number at build time)
- **Size:** 3 agent-days
- **Safety:** yes. Owner-act verbs write epoch rows (they can restart the owner's own count); they are CLI only, with no UI write. The detector changes no setting, blocks nothing and writes only its own records. Spec Draft holds the build.

## Goal
The 60 paper trades are measured against **one** configuration. The system fingerprints the configuration at every capture, detects any change, classes it (restarts the count, only reduces risk, or irrelevant), starts a new epoch when the count must restart, keeps trades around a change out of the count, matches changes to accepted hypotheses where it can, and keeps accepted hypotheses waiting in a visible queue instead of being applied mid-measurement.

## Scope
**In:** pure `Domain/Paper` `ConfigFingerprint`, `ConfigComponent`, `ConfigClass`, `PaperConfigKeys` (the pinned classification), `ConfigDiff`, `EpochDecision`, `ChangeExplainer`; `Application/Paper` `FingerprintEpochGate` (implements P10-01's `IEpochGate`), `IConfigSnapshotSource` (reads the components through existing ports), `StartEpochHandler`, `ExplainChangeHandler`, `GetEpochsHandler`, `GetConfigHandler`, `GetQueueHandler`; Infrastructure store and the snapshot source; migration `AddPaperGovernance` (`paper.config_snapshots`, `config_changes`, `epoch_notes`, insert-only, with `Down`); endpoints; verbs `xd paper epoch show|restart|explain`, `xd paper config`, `xd paper queue`; frontend tab **Governance** (read only); `scripts/gen-api.sh`.
**Out:** blocking or reverting any change (the owner is the single operator; the rule is detection, labelling and the restart of the count), shadow replay of queued hypotheses (Findings), applying a hypothesis, a UI write, a fingerprint of the code revision (only the engine and schema versions are in it, see Decision 4).

## Acceptance criteria
1. **Fingerprint.** Given the same components in any read order, then the hash (SHA-256 of canonical JSON, keys sorted, invariant culture) is identical; changing any one value changes it; it contains no secret (a test scans the canonical text for token/key/secret/password names).
2. **Classification is closed.** `PaperConfigKeys` gives every component key a class `frozen`, `risk_down` or `free`. A reflection test fails when an options class of `Planning`, `Autonomy`, the smart rules or the selection settings, or a field of the risk profile / paper `TradingSettings`, has a property that is in neither the table nor an explicit `free` allow-list with a reason: a new setting cannot arrive unclassified.
3. **Direction matters.** Hand table (below): a raise of a risk limit, enabling a rule that adds trades, adding or re-activating a cell, a new strategy version or exit, a new cell-statistics snapshot, a new champion, a changed charge sheet, a changed capital, auto-approval ON, `UseSelection` or `UsePaperLedger` toggled: `frozen`. A lowered risk limit, a cell paused or retired, auto-approval OFF, a protective smart rule switched ON: `risk_down`. A schedule time, a theme, a notification choice: not in the fingerprint.
4. **Gate behaviour.** At each capture run the gate takes a snapshot and compares it with the previous one: equal -> the session's entries are `measured` in the current epoch; only `risk_down`/`free` differences -> same epoch, changes stored with effect `noted`, entries `measured`; any `frozen` difference -> a new epoch (kind `detected_change`, `started_on` = the next trading day after the session being captured, new fingerprint hash), the sessions captured in this run are `straddle` (stored, shown, **never counted**), and every change row names its key, class, before and after.
5. **No snapshot yet.** With no epoch the gate creates epoch `first` (so nothing is lost) and the owner may restart it after the pre-flight (`xd paper epoch restart`); with epochs but no snapshot (a first run after the upgrade) the snapshot is taken and no change is claimed.
6. **Owner restart.** `xd paper epoch restart --reason "<10 to 300 chars>"` writes an `owner_restart` epoch effective the next trading day; refused without a reason (`paper.invalid`) or when the newest epoch already starts that day. Never deletes or edits anything; the earlier epoch keeps its trades and reports.
7. **What does not reset.** Approving, modifying, rejecting, lapsing tickets; pausing or resuming services; code deploys that leave the engine and schema versions unchanged; a risk-down change; a capture catch-up with no config difference. A test per item.
8. **Explained or not.** For a changed `cells.eligible` entry the explainer looks for (a) an accepted hypothesis (newest row `accepted`) for that cell whose knob matches the change (parameter: the new version's stored parameter equals `CandidateValue`; exit: the new exit label equals it), accepted before detection and not already used, giving `hypothesis:<id>`; else (b) a `learning_changelog` row for that subject between the two snapshots, giving `changelog:<id>`; otherwise `explained_by` is null and the change is shown as **unexplained**. Settings, accounts and autonomy changes are never hypotheses: they are unexplained unless the owner attaches a note (`xd paper epoch explain --change <id> --reason ...`), stored in `paper.epoch_notes` and shown beside.
9. **The queue.** `GET /api/paper/queue` lists accepted hypotheses (newest row accepted) that no change row names as `explained_by`, with age, cell, knob, from, to, the stored experiment id, and the sentence `accepted means judged better offline; nothing was applied; applying it starts a new epoch`. The system never applies, proposes to apply, or reorders it.
10. **Preview before the owner acts.** `xd paper config` and `GET /api/paper/config` print every component with its class and current value, the last snapshot's hash, and the differences not yet captured, each marked `would restart the count` / `noted only`.
11a. **Refresh jobs are paused during an epoch.** `cells.snapshot` is `frozen`, so any run that stores a new cell-statistics snapshot, retrains or re-designates a model, or applies learning restarts the count. A pinned list `PaperConfigKeys.LearningWriterServices` (`cells`, `retrain`, and `weekly` if a later slice makes it run the P6 computing verbs; today `weekly` only writes the digest and no `cells` service exists) names such services by id. `xd paper config` and `GET /api/paper/config` show each one that is registered and enabled as a **blocker** (`enabled during an epoch: each run restarts the count`) and the Governance tab shows it. Test: with a fake enabled service whose id is in the list, the config view carries the blocker; a new snapshot key between two captures is a `frozen` change; with the service paused no change is produced. The owner pauses them in the pre-flight (P10-00).
11. **Failure and empty cases.** A component that cannot be read (a port fails) makes the snapshot `partial`: the gate writes no epoch change, logs `paper.config_unreadable`, the entries of that run are `measured` only if the previous snapshot is not older than the last full one by more than 3 sessions, else `straddle` (never claim stability from a blind read); no epochs yet -> empty states.
12. Read-only HTTP: every endpoint is GET; the verbs are the only writers, with actor `cli:xd`; `xd_app` can select and insert the three tables, not update or delete; the no-order architecture rule stays green; log ids 5240 to 5249 unique.

## Contract
- **API (GET only):** `/api/paper/epochs` -> `EpochView[]` { `id`, `kind`, `startedOn`, `endedOn` (the next epoch's start), `fingerprint` (short), `counted`, `straddle`, `riskDownChanges`, `unexplainedChanges`, `reason` }; `/api/paper/epochs/{id}` (adds changes and notes); `/api/paper/config` -> components, classes, last snapshot, pending differences; `/api/paper/config/changes?epoch=`; `/api/paper/queue`. 404 `paper.not_found`, 422 `paper.invalid`.
- **CLI:** `xd paper epoch show [--id]`, `xd paper epoch restart --reason`, `xd paper epoch explain --change ID (--hypothesis ID) --reason`, `xd paper config`, `xd paper queue`. Exit 0 report, 1 refused, 2 usage, 3 failure, 130 cancelled.
- **Components (key -> class when it changes):**
  - `cells.eligible` (sorted `cellKey@strategyHash` for each cell whose lifecycle state is at least the plan's minimum state, from the changelog replay; the state label itself is not in it, so Candidate to Paper bookkeeping is not a change): additions, new hash/exit `frozen`; removal (pause, retire) `risk_down`; `cells.snapshot` (key of the cell-statistics snapshot in force) `frozen`.
  - `planning.settings` (all `Planning:*`: builder, open book incl. `UsePaperLedger`, grading sheet id and capital, selection thresholds and minimum cell state): `frozen`.
  - `autonomy` (the four settings, the newest row hash): ON/raise `frozen`, OFF/lower `risk_down`.
  - `accounts.paper` (per paper account: enabled, mode, capital source and amount, risk profile id and its limits, overrides, styles, instruments): raise or add `frozen`; lowering risk per trade, entries per day, open positions, daily loss `risk_down`.
  - `smart_rules` (settings of doc 09 §14): switching a protective rule ON `risk_down`, OFF or loosened `frozen`.
  - `models.champion` (registry champion id): `frozen`.
  - `engine` (`SimulationEngine.Version`, `SimTrade.CurrentSchemaVersion`, canonical default fill rules, the charge sheet's content hash and id): `frozen`.
- **Data (migration `AddPaperGovernance`):** `paper.config_snapshots` (`id`, `taken_at`, `session_date`, `hash char(64)`, `components jsonb`, `partial bool`, `process text`, unique `(session_date, hash)`); `paper.config_changes` (`id`, `from_snapshot_id`, `to_snapshot_id`, `key`, `class check in ('frozen','risk_down','free')`, `before`, `after`, `effect check in ('new_epoch','noted')`, `epoch_id`, `explained_by text null`); `paper.epoch_notes` (`id`, `epoch_id`, `change_id null`, `hypothesis_id null`, `text`, `actor`, `created_at`). Insert-only via `MakeAppendOnlyForAppRole`.

## Non-functional
A snapshot reads about 10 existing ports once per capture run (milliseconds, no replay). The hash input is bounded (a few KB). Logs carry hash prefixes, keys and classes, never values of accounts or amounts.

## Decisions (researched)
1. **Q: How is "changes only via the hypothesis loop" enforced for one owner?** A: by **detection and consequence**, not prevention. The loop already ends at "accept records a verdict; applying is the owner's own act" (ADR 0076 point 6), so the system cannot see an intention, only a result. The fingerprint sees the result; a result with no matching accepted hypothesis is labelled unexplained; a frozen change restarts the count. Why: a block would be bypassed by editing a setting, and would punish a safety action. Rejected: refusing writes to frozen settings (the settings are in `IConfiguration` and the database; there is no single write path). Source: ADR 0076, 0002, doc 19 §3.
2. **Q: Freeze everything, or let the system keep learning during the measurement?** A: freeze, including the cell-statistics snapshot. Why: the exit criterion is a statement about one configuration; a statistics refresh changes the ranking and thresholds, so tickets before and after are different systems, and the band of P10-04 is defined from the snapshot at the epoch start. The cost (stale statistics for 12 weeks, no learning from paper results) is accepted: the data is 2.1 years and moves slowly; offline hypotheses and experiments continue and queue. Alternative rejected: a weekly automatic refresh counted as part of the system (turns "fixed system" into "system plus a learner", and nobody could say what the 60 trades measured).
3. **Q: What should not reset?** A: risk-down changes. Pausing a failing cell or cutting risk is the response doc 19 wants and must never cost the owner the count; the price is a labelled population censoring (shown on the review, the phase check and every MET label). Rejected: resetting on every change (makes safety actions expensive, which is how people stop taking them).
4. **Q: Code deploys?** A: the standing instruction deploys after every merge; resetting on each would make P10 impossible. The fingerprint holds the engine version, the trade schema version, default fill rules and the sheet hash, i.e. what changes the numbers; a code change that alters selection without touching them is not seen (stated limit, mitigated by the equivalence tests of P10-01 and the reviewer pass).
5. **Q: Which trades are set aside around a change?** A: the sessions captured in the run that first sees the change (`straddle`), because a ticket for session F is published the evening before and the change may fall either side. This costs at most one session per change on a daily capture. Never counted, never hidden.
6. **Q: Who may restart the count?** A: the owner, by CLI, with a reason; it is always allowed (a pipeline fix or a warm-up discard is legitimate). It is the escape valve and it is visible.
7. **Q: Process in which the settings are read?** A: the capture runs in `xd-api`, the process of the services, so the fingerprint is of that process's configuration (the same limit P7-18 prints); a container started with other values is not seen.

## Risks and honest limits
- Detection depends on the components listed; anything outside (data feed behaviour, the Dhan token state, the machine's clock) is not a config change here and appears as coverage in P10-06.
- A change and its reversal between two captures is invisible.
- Matching an accepted hypothesis to a change is by cell and value, not proof of intent.
- The owner can still tweak after every loss; the system makes each tweak cost the count and appear in the weekly review, which is the intended pressure.
- The explanation of `smart_rules` and `accounts` classes relies on stores whose reading shapes are UNVERIFIED (smart-rule settings home; risk-profile limit fields).
