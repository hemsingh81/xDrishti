## Goal
The owner's database holds one row per trading day with the NIFTY 50 high, low, close and the INDIA VIX close, written point-in-time by the end-of-day data job from bars the system already stores, and a reader that builds the `MarketContext` of ADR 0033 from those rows. Regime, `vix_pct`, `index_trend` are then real on the owner's data, and where they cannot be (too little history, a stale feed) they say `unavailable`, never a guess. The first acceptance item is a 0.5-day probe that finds out, on the owner's own Dhan account, what the allowed endpoint really gives.

## Scope
**In:** (1) the probe and its written result; (2) pure `ContextDayDerivation` (daily rows of the two indices to context records, with the rules below); (3) table `market.context_daily` and its migration; (4) a post-step of the data job (`ContextUpkeep`, warnings only, like `ICalendarUpkeep`) and the CLI verb `context refresh|coverage`; (5) the reader: `IContextFigures` (port, Domain values) and its adapter that builds and caches the `MarketContext`; (6) `GET /api/data/context` (coverage) and the notices `data_context_stale`, `data_context_gap`; (7) a bound on the age of a context read in `XDrishti.Indicators` (`ContextOptions.MaxAgeDays`); (8) the settlement of the six flagged deviations (Decisions D1 to D6) in ADR 0033 and doc 11.
**Out:** breadth and `sector_rs` (P3-01e); lifting the simulator's refusal `simulation.needs_context` and the expiry days (finding for the index); the daily-history endpoint and a CSV loader for index history (fallbacks C and D, separate slices if the probe calls for them); Bank Nifty and sector indices (ADR 0033 decision 7); intraday index features; any UI screen (the coverage endpoint is for P8-02/P8-16 to show).

## Acceptance criteria
1. **Probe (first).** Given the owner has connected Dhan and tracked NIFTY 50 and INDIA VIX, when `Update data` runs with `Data:Dhan:InitialDaysIndex` = 1800 (a temporary setting for this step), then `scripts/context.sh coverage` prints for each index: resolved instrument and Dhan `securityId`, first and last bar, days with bars, bars per day (min / median / max), days under 360 bars, the largest gap in sessions, price sanity (NIFTY above 5,000; VIX between 5 and 100), and the last 1-minute close against the aggregated 1D close; the agent writes the numbers into `docs/research/p3-01d-context-probe.md` with the date and states the **outcome O1 to O5** (D8). A failure code is quoted by its Dhan code only (`DH-9xx`), never the answer text.
2. **Derivation.** Given index and VIX daily rows (fixtures in the Test plan), then a record is produced for each session that has an accepted index leg and either an accepted VIX leg or a VIX leg that is `VixGraceSessions` sessions old; a session with a thin or missing index leg is skipped with a reason and a count; a session that is not a session of the calendar is skipped (`not_a_session`); nothing is written for a day whose bars are still being aggregated (a partial day, D9).
3. **Insert-only.** Given a date already stored, when the job runs again, then the stored row is untouched (`INSERT … ON CONFLICT DO NOTHING`, and `xd_app` holds no table-level UPDATE or DELETE on the table; column grants only by P3-01e: `ContextGrantsTests` fails if a later market migration adds a table-level grant).
4. **Same context from table and records.** Given N fixture days, when the reader builds the `MarketContext` from the table and a second one is built from the same `ContextDay` list, then all ten context values are equal at every date, and the values of the first k days do not change when later rows are added (prefix property, 20 seeds).
5. **Age bound (D6).** Given the context ends on day L, when a frame reads a date more than `MaxAgeDays` (default 7) calendar days after L, then the ten context features are not ready (NaN, a false condition), and at exactly 7 days they are ready; `MaxAgeDays` is validated 1 to 3650 (`indicators.context_options_invalid`).
6. **Staleness is visible.** Given the last context date is more than one trading session behind the last closed session, when the data notices are built, then `data_context_stale` (warn) appears with the days behind; `GET /api/data/context` carries `ageSessions` and `stale`; a context that is current raises nothing.
7. **Coverage is honest.** The endpoint prints days, first and last date, the first readable date of each family (`index_trend` after 55 days, `regime` after 265, `vix_pct` after 252 VIX days; first readable = the day after the Nth record), `vixDays`, `vixMissingDays`, the calendar span of the last 252 VIX days (D1), the first date on which `regime` has both parts (D2), the skipped days with reasons (first 50 and the total), and the sentence "derived from 1-minute bars; the official daily close can differ slightly".
8. **Missing prerequisites are named.** Given NIFTY 50 or INDIA VIX is not tracked, has no bars, or is not in the master, then no row is written, the coverage says `index_not_tracked` / `vix_not_tracked` with the fix ("track it on the Instruments screen"), and the job does not fail.
9. **Reader results.** `IContextFigures.AsOfAsync(date)` returns the figures of the latest record strictly before `date` with `AsOf`, `Basis` (`index_and_vix` or `index_only`) and nulls for not-ready values; before the first readable date, or past the age bound, it returns `unavailable` with the reason; it never returns a value dated on or after `date`.
10. **Docs.** ADR 0033 Amendment (no new number) records D1 to D6 as confirmed or changed; doc 11 §2 loses its "pending owner confirmation" marks and gains the age bound; doc 05 §9 describes the table; the roadmap row gets the probe result.

## Contract
- **Instrument resolution.** By canonical symbol in order `Data:Context:IndexSymbols` (default `["NSE:NIFTY"]`) and `VixSymbols` (default `["NSE:INDIA_VIX","NSE:INDIAVIX"]`), then by display name `Nifty 50` / `India VIX` ignoring case; type `index`, not retired, Dhan broker id in segment `IDX_I`. Doc 05/06 (symbol rules, `NSE:{SYMBOL_NAME}` with spaces as `_`) gives `NSE:INDIA_VIX` (ADR 0010 does not name it); `IndicesProvider` (live feed) lists `NSE:INDIAVIX` and finds it only through the display-name fallback (contradiction, finding). Security ids 13 (NIFTY 50) and 21 (INDIA VIX) appear in the repo's test fixture and in Dhan community reports and are **UNVERIFIED** against the owner's master; the probe prints the real ones.
- **Data.** Migration `AddContextDaily`. `market.context_daily`: `date date PK` (India date) · `index_instrument_id uuid not null` · `index_high`, `index_low`, `index_close double precision not null` · `vix_close double precision null` · `index_bars smallint not null` · `vix_bars smallint null` · `source text not null` (`derived_1m`) · `written_at timestamptz not null`. Checks: `index_low > 0`, `index_high >= index_low`, `index_close between index_low and index_high`, `vix_close > 0` (the rules of `MarketContext` validation, so a stored row can never be refused by it). Grants: `GrantTableToAppRole` then `MakeAppendOnlyForAppRole(Schemas.Market, "context_daily")`. P3-01e adds breadth columns and a column-level UPDATE grant.
- **Domain** (`XDrishti.Domain.Market.Context`): `DailyLeg(Date, High, Low, Close, Bars, Complete)`, `ContextDayRecord(Date, IndexHigh, IndexLow, IndexClose, VixClose?, IndexBars, VixBars?)`, `ContextDerivation.Derive(indexLegs, vixLegs, calendar, lastClosedSession, existingDates, options)` → `(Records, Pending, Skipped[(Date, Reason, Bars)])`, `ContextSkipReason` (`index_missing`, `index_thin`, `not_a_session`, `vix_pending`), `ContextCoverage.Of(...)`, `ContextFigures(AsOf, Basis, IndexTrend?, IndexAdx?, IndexVolPct?, Vix?, VixPct?, VixChg?, RegimeTrend?, RegimeVol?, Regime?, Breadth?)`.
- **Application:** `Abstractions/Market/Context`: `IContextBarSource` (reads the `1D` rows of `market.bars_agg` of the two instruments; columns `instrument_id, timeframe, ts, open, high, low, close, volume, bars, complete`), `IContextDayStore` (`ListAsync`, `InsertAsync`), `IContextFigures`. Handlers `RefreshContextHandler` (command) and `GetContextCoverageHandler` (query), `internal sealed`, registered in `DependencyInjection.cs`. `ContextUpkeep` is called by `ExecuteDataJobHandler` after the calendar step when the job ran `aggregate`, never fails the job (a warning on the reporter).
- **Infrastructure:** `ContextBarSource`, `ContextDayStore` (Npgsql, `COPY`-free: a few rows a day), `ContextFiguresAdapter` (the only project that names `MarketContext`; caches the built context by `(count, lastDate)`, rebuilds when the store changes; 1,300 days build in about 3 ms, ADR 0033 measured 5,000 in 12 ms).
- **Dhan phase:** `DhanFetchPlanner.Plan` takes the initial depth of a target of type `index` from `Data:Dhan:InitialDaysIndex` instead of `Data:Dhan:InitialDays` (365); nothing else of the planner or of `DhanIntradayChartClient` changes (it already builds `IDX_I` / `INDEX` bodies). The probe sets the value to what the account really gives (minus a week) before the first full fetch.
- **Library (`XDrishti.Indicators`):** `ContextOptions` gains `MaxAgeDays` (default 7); `MarketContext.TryAsOf` (public and the internal cursor overload) returns false when `date − day.Date > MaxAgeDays`.
- **API:** `GET /api/data/context` → `ContextCoverageView` (fields as criterion 7; read only; `ApiJsonContext`; `scripts/gen-api.sh`). No write endpoint.
- **Events/jobs:** runs inside every data job that aggregates, including the 15:50 `eod` run; idempotent; the first run after the probe back-fills every session still missing (about 1,100 records for 4.5 years). CLI `scripts/context.sh refresh|coverage` (host verb, same pattern as `cost-sheet.sh`; the database password from the Keychain; exit codes 0 / 1 refused / 2 usage / 3 failure).
- **Settings (defaults):** `Data:Context:Enabled` true · `IndexSymbols` · `VixSymbols` · `VixGraceSessions` 5 (1 to 30) · `MinDayFraction` 0.96 (of the calendar's expected minutes) · `Data:Dhan:InitialDaysIndex` 1825 (365 to 1825; applies to instruments of type `index` that have no bars) · `Indicators` `ContextOptions.MaxAgeDays` 7.
- **Log events** (`[LoggerMessage]`, next free ids at build time, `LogEventIdTests`): context refreshed (written, pending, skipped, last date); context prerequisite missing (which); context stale (sessions behind). No price, no token, no response text.

## Non-functional
Refresh ≤ 1 s for a day, ≤ 5 s for the 1,100-day back-fill; reader build ≤ 20 ms cold; no extra HTTP request beyond the bars the Dhan phase already fetches (42 requests, about 11 s at 4 per second, once). Dhan documents 5 requests per second and 100,000 per day for the Data APIs (read 2026-10-24 at <https://dhanhq.co/docs/v2/>). Security: nothing new leaves the host; the table holds no secret. Memory: the context is a few hundred KB.

## Test plan

- **Library:** `MaxAgeDays` boundary (7 ready, 8 not), a gap inside the history longer than the bound reads not ready and recovers on the next record, the frame and the extractor stay unchanged for in-bound reads, the existing 4,275 `Indicators` tests stay green except the test that pinned "reads the last day for ever" (replaced).
- **Integration (Testcontainers):** insert-only grants, `ON CONFLICT`, the post-step after a fake Dhan job, a tracked index with 375-bar days, the coverage endpoint, an index that is not tracked, the notice.
- **Architecture:** Application names no `Indicators` type (`ResearchLayeringArchitectureTests` unchanged); only `ContextFiguresAdapter` references `MarketContext`.
- **Hand fixture (grace 2, today = session 6):** sessions s1..s6; NIFTY legs s1..s6 complete; VIX legs s1 15.0, s2 missing, s3 16.0, s4 complete 375 bars 14.0, s5 missing, s6 missing. The age of a session is the number of sessions after it up to the last closed one (s6). Result: s1 written (VIX 15.0); s2 written with VIX null (age 4, grace passed); s3 (16.0) and s4 (14.0) written; s5 (age 1) and s6 (age 0) pending, not written. So 4 records, 2 pending, 0 skipped. Variant: if the s4 VIX leg has 340 of 375 bars (0.907, under 0.96) it is thin and is treated as missing (s4 waits or goes with a null VIX by the same grace rule); its 340 is listed in the skipped-leg evidence.
- **Probe-dependent tests** (run only if the probe gives O1): coverage of the owner's real data is an exit check, not a unit test.

## Decisions (researched)
**D1 — `vix_pct` window (ADR 0033 Amendment 1).** *Confirmed as built:* the 252 most recent days that have a VIX. A percentile rank is a statistic over 252 observations; "not ready on a gap day, never filled" is preserved. Added: coverage prints the calendar span of the window and warns when it exceeds 400 days. Rejected: the literal 252 calendar sessions (a gap would shrink the sample silently).
**D2 — `regime_vol` fallback (Amendment 2).** *Confirmed as built* (index percentile alone on any day where `vix_pct` is not ready): the alternative, regime not ready until both parts are, would leave `by_regime` empty for the first year of a VIX history of 2 to 3 years. Added: every output that carries a regime carries `Basis`; coverage prints the first date with `index_and_vix`; a regime cell must not mix the two bases without saying so (P6-02 obligation).
**D3 — the cursor (Amendment 5).** *Confirmed:* public `TryAsOf` is a binary search with no writes, so any number of frames share one context; the O(1) walk lives in each feature (proved by the 3-dates-per-step test). Rejected: a cursor in the shared context (mutable shared state).
**D4 — first partial week (Amendment 7).** *Confirmed:* `Complete` = every day that has bars is complete, which is the stored rule of doc 05 §4, so streaming and stored 1W agree. The first week of an instrument's data can be a partial week (the owner's CSVs start on a Monday or on Wednesday 2024-12-18); weekly values built from it sit inside the warm-up of any weekly feature of two or more bars, and `tf("1W").close` alone is the close of the days it has. The run labels already print each instrument's first bar. Rejected: marking the first partial period incomplete (it would make streaming and stored disagree and change approved P3-01c behaviour).
**D5 — exact thirds (Amendment 13).** *Confirmed* (100/3 and 200/3): the sketch approved with the spec shows them, doc 16 carries the exact doubles, and 33.3 / 66.7 leave a band [33.3, 33.33…) that is NORMAL and a score of exactly two thirds that is NORMAL, an asymmetry with no reason.
**D6 — past the last day (Amendment 14).** *Changed:* the library bounds the age: `ContextOptions.MaxAgeDays` = 7 calendar days (longest NSE closure plus a missing session). Reason: the pure library has no clock or calendar, but a stale regime that reads as ready is the dishonest case this system exists to avoid; one bound in `TryAsOf` protects the simulator, the extractor, the plan and the tests alike. This is the "maximum age in `ContextOptions`" that ADR 0033 named as the alternative. Rejected: leaving it to every reader (four consumers, four chances to forget). The plan's own bound (`GateMaxAgeDays` 4 calendar days) stays for the gate.
**D7 — source of the daily close.** The stored 1-minute bars aggregated to 1D (`derived_1m`), not Dhan's daily candles. Reason: no allow-list change, history up to 5 years through the endpoint the system already trusts (Dhan: intraday "last 5 years", 90 days per request, read 2026-10-24 at <https://dhanhq.co/docs/v2/historical-data/>), and the same precedence and gap machinery as every stock. Limit: NSE computes an index's official close from its constituents' closing prices, so the last 1-minute close can differ slightly from it (size UNVERIFIED; the probe compares the 15:29 close with a published close for ten dates by hand). Effect: only a trend flag within about 0.05 % of its average could flip.
**D8 — the probe's outcomes and the decided fallback for each.** O1 both indices give at least 1,100 sessions before 2024-04-01 with at least 96 % of days at 360 or more bars: build as specified. O2 NIFTY good, VIX missing, short or failing: build with `VixClose` null; `vix*` not ready; `regime_vol` index-only; the gate has no VIX figure (unavailable); source for VIX = fallback D (the owner downloads the India VIX history from NSE, a daily CSV loader slice; personal use, doc 19 §5). O3 neither index is served (a Dhan `DH-90x`, an empty answer, or `IDX_I` refused): fallback C below. O4 served but shallower than needed: build; regime and `vix_pct` become readable later (the coverage prints the dates); no fallback. O5 served with many thin days: the 0.96 rule is revisited with the numbers; if more than 2 % of days are thin, use C. Until the owner acts, the state is `unavailable` / `not_evaluable`, never a default.
**D9 — a partial day is never written.** A day is written only when the aggregate row of that date is final: the date is at or before the last closed session and its bars are at least `MinDayFraction` of the calendar's expected minutes (375, or the length of a special session); the running day never qualifies.
**D10 — the VIX leg waits, then goes without.** A date waits for its VIX leg up to `VixGraceSessions`; after that it is written with a null VIX. Reason: the table is insert-only (a restated close would move earlier percentiles), so a VIX that merely arrived late must not be lost; the wait is what makes insert-only safe.
**D11 — tracking as the mechanism.** The owner tracks the two indices; the existing Dhan phase fetches them, the aggregate phase builds their 1D rows, the quality checks cover them. Rejected: a private fetch path (duplicates the pipeline); automatic tracking (changes the owner's universe without a word). Cost: two index rows appear in "all tracked" lists; the build checks that no stock-only logic (breadth, baskets, plan universe, the quality gate's counts) takes them in (a grep and a test).
**D12 — fallback C, the allow-list change, spelled out as the owner's security act (not in this slice).** Dhan documents `POST /v2/charts/historical` for daily candles, "available back upto the date of its inception", body `securityId, exchangeSegment (IDX_I), instrument (INDEX), expiryCode, oi, fromDate, toDate` with dates `YYYY-MM-DD` and `toDate` non-inclusive (read 2026-10-24 at the page above; the timestamp base of the answer and the behaviour for an index are **UNVERIFIED**). The exact entry to add, in `BrokerEndpoints.cs`: a constant `DhanDailyChart = new Uri("https://api.dhan.co/v2/charts/historical")` and the row `(HttpMethod.Post, DhanDailyChart, null)` of `Allowed`, which prints in the phase check as `POST api.dhan.co/v2/charts/historical` (no query, exact path, HTTPS, default port, no redirects, same client limits as the intraday chart: 15 s, 16 MB). It touches: `BrokerEndpointsTests` and `BrokerAllowListTests` (allowed and the negatives), the negative in `DhanIntradayChartClientTests` that today asserts this very URL is refused, `PlanPhaseCheck.cs` (its expected list), doc 17 §3 (a new row), doc 05 §6, `deploy/README.md`, and an ADR (next free number at build time). The owner's Approved on that slice is the act; this spec being Draft is what holds it. A daily client would then write `source = 'dhan_daily'` rows through the same derivation.
**D13 — what the context is not.** One regime index (NIFTY 50) and the VIX (ADR 0033 decision 7); no sector indices; the context describes the market the owner's strategies trade in, not the owner's tracked set (that is breadth, P3-01e).

## Risks and honest limits
The probe may find that the intraday endpoint gives no index history (O3): then every regime feature stays unavailable until the owner decides on C or D, and P5's `by_regime` and P6-02 wait (as P6-00 risk 3 already says). Derived closes are approximate (D7). A tracked index adds two non-stock instruments to lists (D11). The stored table covers dates only from the first tracked day backwards to the probe depth; before that every output says `unavailable`. VIX of 1-minute bars is the last traded value of a computed index, not an instrument price. The simulator still refuses a strategy that reads the context (finding): this slice makes the data and the reader, not the use.

## Build notes 2026-10-27 (deviations from the sketch)
- `ContextSkipReason` has `index_missing`, `index_thin`, `index_invalid` (a leg the table would refuse is skipped, not written), `not_a_session` and `vix_thin` (evidence of a thin VIX leg; the day then waits or goes without). A day that waits for its VIX is listed in `Pending`, not as a skip, so `vix_pending` is not a reason code.
- `IContextDayStore` also has `StampAsync` (count and newest date: the cache key of the adapter) and `InsertAsync` takes the index instrument id (the table keeps which index a day came from). `IContextSettings` is its own port (the settings are `Data:Context:*`).
- `data_context_gap` is raised when sessions between the first and the last stored day have no record; `data_context_stale` when the newest day is more than one session behind the last closed one. Neither is raised while nothing is stored (a fresh install says nothing; `GET /api/data/context` names the missing prerequisite).
- A missing prerequisite (an index that is not tracked, or has no daily row) is logged and shown by the coverage, not added as a job warning on every update.
- `GET /api/data/context` also carries `gapSessions`, `enabled`, `indexSymbol`, `vixSymbol` and the source sentence; the verb is `context refresh|coverage` (`scripts/context.sh`).
- The probe-dependent tests are not run: nothing here depends on its outcome, and the owner's numbers go into the note.
