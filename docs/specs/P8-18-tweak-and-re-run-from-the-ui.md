# P8-18 — Tweak and re-run from the UI (start one replay job, judge it, never apply it)

- **Status:** Draft (written 2026-10-24; decisions below were researched under the owner's delegation; the owner's Approved is still needed before an agent builds it)
- **Phase / roadmap row:** P8 — Reports & UI, slice P8-18 of [P8-00](P8-00-reports-and-ui-plan.md) (Q3, Q1, Q2)
- **Design refs:** docs/design/09-learning-engine.md §12 (tweak & re-run, five honesty rules) · 04 §3-§4 (control plane vs services, human in the loop) · 13 §1c · 17 §2 (`xd-api` hosts the background services) · 19 §4 (automation over-reach, overfitting through repeated experiments) · ADR 0072 (experiments), ADR 0058 (Lab runs: queue table, dispatcher, hub), ADR 0083/0091 (owner-only acts, fresh password, auto never the owner)
- **Needs:** P6-11 (built: `RunExperimentHandler`, `research.experiments`), P5-02 (built: the queue/dispatcher/hub pattern), P3-10 (built: `IRunStore`), P8-03 (the Experiments tab that shows the result), P8-06 (the stored-run list for the baseline picker; until then a run key typed or pasted). An ADR at build time (next free ADR number at build time).
- **Size:** 4.5 agent-days (over the 1-3 d guide; see "Findings" in the report: split Part A, the capability gate, 1 d, from Part B, the job, 3.5 d)
- **Safety:** **yes.** It starts a CPU-heavy job from a screen, writes stored runs and a ledger row (a "trial" that raises the bar for every later experiment), and adds a write to a read-only phase. It stops for the owner: this spec being Draft is what holds the build. The setting that allows it defaults OFF.

## Assumptions (taken as the safest answer that still serves the goal)
1. **The UI can only do what `xd learn experiment` + `xd simulate --store` already do together**, through the same handlers (`RunSimulationQuery`, `StoreRunCommand`, `RunExperimentCommand`). No new rule, threshold or judge. ADR 0072 stays the judge; this slice is a job runner around it.
2. **No apply, anywhere.** There is no endpoint, command, button, DTO field or member named apply / activate / promote / publish in this slice. The result card ends with the judgement and the sentence "Nothing was changed. Applying a change is your own separate act." (P7-00 Q6, doc 09 §13 "no apply path exists").
3. **Only entry-neutral knobs are offered** (decision D3): `exit` parameters and `slippage` upward. Strategy `parameter` knobs stay verb-only until a strategy parameter carries a machine flag "does not change which entries exist" (none does today: `BuiltInParameterInfo` has name, default, note, range only; opened). Learning-side knobs of doc 09 §12 (history window, half-life, shrinkage prior, selection threshold, VIX gate) are not replays of the simulator and are out (ADR 0072 consequence 5).
4. **One job at a time, a hard daily limit, a time cap.** Each judged experiment is a permanent trial that raises the required improvement `0.02 + 0.006 sqrt(trials)` for 30 days, and each stored candidate run is permanent (insert-only). The UI therefore makes looking costly on purpose.
5. **The baseline must be a stored single-exit run** from `research.sim_runs`; the candidate request is rebuilt from the baseline's stored record with exactly one field changed. UNVERIFIED and settled by step 1 of the build (a 0.5 d spike inside this slice): that the stored record (`SimulationRun`: `Strategy`, `Options`, `Universe`, `Instruments`, `Fills`, `Costs`) carries every field `SimulationRequest` needs. If it does not, the slice stops and reports which field is missing; it does not guess.
6. **Capability gate (Part A).** A new insert-only table decides whether the owner has switched the UI write on. Absence of a row = OFF. This gate is reused by P8-19, P8-20 and P8-21 (they name their own capability only).

## Goal
The owner can pick a stored run, change one entry-neutral knob, start one replay from the Learning area, watch it, cancel it, and read the judgement of ADR 0072 with the replay time actually measured and printed, without anything in the trading configuration, plans, strategies, cells, models or autonomy changing.

## Scope
**In:** (A) `platform.capability_changes`, `GET /api/capabilities`, `PUT /api/capabilities/{name}`, `ICapabilityGate`, the shared fresh-password helper (extracted from `AutonomyEndpoints.ChangeAsync`, behaviour unchanged); (B) `research.experiment_jobs`, `POST /api/experiments`, `GET /api/experiments/preview`, `GET /api/experiments/jobs` and `/{id}`, `POST /api/experiments/jobs/{id}/cancel`, the dispatcher/runner, two hub events, the form (feature `owner-acts`, route `/owner-acts/experiment`, lazy), the result card, log ids, the ADR, docs, `scripts/gen-api.sh`.
**Out:** an apply/shadow/promote path (P10), `parameter` knobs, learning-side knobs, a queue longer than one, scheduling a job, a job started by the assistant (P9) or the command palette (P8-00 Q9), changing any cost sheet, deleting a stored run, a "run nightly / digest now" action.

## Acceptance criteria
1. Given the capability `experiments_ui` has no row or its newest row is OFF, when `POST /api/experiments` is called (valid body, valid password), then 403 `capabilities.off`, no job row, no run, no ledger row. *Integration.*
2. Given the capability is ON, when the owner posts a valid body with a wrong password, then 401 `auth.invalid_credentials` (counts toward the sign-in lockout, 423 `auth.locked` after the fifth) and no job exists; a correct password inside an open step-up window is still required and does not open or extend the window. *Integration, same cases as P7-12 criterion 4.*
3. Given a job is queued or running, when another valid post arrives, then 409 `experiments.job_active` naming the active job id; the identical input returns that job (200). Two posts racing leave exactly one active row (partial unique index). *Integration with a barrier.*
4. Given 3 jobs were created in the last 24 hours (`Experiments:MaxJobsPerDay`), when a post arrives, then 429 `experiments.daily_limit` with the time the oldest leaves the window; failed and cancelled jobs count. *Unit with a fake clock, integration.*
5. Knob rules (pure `ReplayKnobCatalogue`): kind `parameter` or an unknown name is 422 `experiments.knob_not_allowed`; slippage below the baseline's value (a cheaper assumption) is refused with the reason "a cheaper cost assumption cannot win (doc 09 §12 rule 3)"; an exit parameter outside the policy's declared range, a baseline that is a multi-exit comparison, a baseline that is not stored (404 `learning.run_not_found`), non-finite or unchanged values are refused before anything is queued. *Unit table + handler.*
6. Given the unchanged baseline request rebuilt from a stored record, when replayed with no knob change, then the run key equals the baseline's run key (determinism proof of `RunRequestFromRecord`; this is a test fixture check, not a user path). *Integration on a seeded two-instrument run.*
7. Happy path on a seeded fixture: the job goes queued, running (stages `prepare`, `replay`, `store`, `compare`), succeeded; the candidate run is stored once with `created_by = experiment:<jobId>`; the experiment is recorded once with the owner as actor (`owner:<email>` from the session, never from the body); the job row carries `candidate_run_key`, `experiment_id`, `replay_ms`, `compare_ms`; the hub received `experimentProgress` (at most 4 a second) and exactly one final `experimentFinished`. *Integration + fake clock + recording progress port.*
8. **Cancel.** Given a running job, when cancel is called, then 202, the replay stops at the next safe point between instruments, nothing is stored (no run, no ledger row, not a trial), the state is `cancelled`, the final event is sent; a queued job cancels at once; a finished job is 409 `experiments.job_not_cancellable`. *Integration.*
9. **Failure is honest.** Given the candidate has entries the baseline lacks (`experiments.entries_added`) or assumptions differ, then the job is `failed` with the ledger's own code and text, the stored candidate run (if any) stays, **no experiment row and no trial exist**, and the card says "judged nothing; not counted as a trial". A host stop mid-run is `interrupted` at the next start (never resumed); a job past `Experiments:MaxMinutes` (60) is `failed` with `experiments.timeout`.
10. **Replay time is measured and printed.** `replay_ms` is the wall time of the candidate replay only (`TimeProvider.GetTimestamp`), `compare_ms` is the ledger's; the card prints "Replay <m s> for <n> instruments over <from> to <to>, measured on this machine; other heavy jobs were running: yes/no". The P6 target "under 10 minutes on 214 instruments" is shown as met / not met only when the run holds exactly 214 instruments; otherwise "not comparable: N instruments". No elapsed time is ever invented before the first job: preview shows `not_evaluable` ("no replay time measured yet").
11. **Never changes configuration (proof, see Test plan).** After a full job, the content hash of every config-bearing table is unchanged, and only `research.sim_runs`/`sim_trades`, `research.experiments`, `research.experiment_jobs` and the audit rows have grown.
12. Preview (`GET /api/experiments/preview`) is read-only and tells the truth before the owner clicks: the next trial number, the required improvement, the usable folds, and `bestPossibleOutcome` = `Inconclusive` when fewer than 6 folds exist (today's data: about 3), with the sentence; the form needs a ticked box "I understand a run counts as a look and can at best be Inconclusive" when so.
13. UI: capability OFF shows the switch state read-only and a link to `/owner-acts` (no start control rendered); ON shows the form; the progress bar follows the hub and falls back to polling `GET /jobs/{id}` every 2 s when the hub is down; the card prints outcome, folds better of used, required improvement, totals after the gap, trials, replay time, limits. No control named apply anywhere. *Vitest + MSW.*
14. `scripts/gen-api.sh` run (OpenAPI + `hubContract.generated.ts`), log ids unique (`LogEventIdTests`), architecture tests green and unchanged, `scripts/check.sh` green.

## Contract
- **API (all behind session; writes need CSRF):**
  - `GET /api/capabilities` -> `{items:[{name, enabled, changedAt, reason?}]}` for the five whitelisted names `experiments_ui` (this slice), `learning_moves_ui` and `autonomy_form` (P8-19), `exports` (P8-20), `pwa` (P8-21); a name is a code constant, adding one is not a migration.
  - `PUT /api/capabilities/{name}` body `{enabled, reason, password}`. ON needs the fresh password (helper `FreshPasswordCheck`, `Elevate:false`, sign-in lockout and audit); OFF needs only session + CSRF (the kill switch is never slower than the switch). Actor = `owner:<session e-mail>`; each change also writes an `account_events` row `CapabilityChanged` (detail `name=exports on` or `off`). 404 `capabilities.not_found`, 422 `capabilities.invalid`, 401/423/429 as autonomy. Rate-limit policy `login`.
  - `GET /api/experiments/preview?baselineRunKey=` -> `ExperimentPreviewView {baseline{strategyId, from, to, instruments, costed, exit}, knobs[{kind,name,current,min,max,note}], nextTrial, requiredImprovementR, foldsAvailable, minFoldsForBetter:6, bestPossibleOutcome, replayEstimate: value|not_evaluable, jobsToday, jobsPerDay, limits[]}`.
  - `POST /api/experiments` body `{baselineRunKey, knob{kind:"exit"|"slippage", name, candidateValue}, holdOutMonths?, reason, password}` -> 202 `ExperimentJobView` (Location `/api/experiments/jobs/{id}`) or 200 for the same input. Errors: 403 `capabilities.off`, 422 `learning.invalid` / `experiments.knob_not_allowed`, 404 `learning.run_not_found`, 409 `experiments.job_active`, 429 `experiments.daily_limit`, 401/423.
  - `GET /api/experiments/jobs?limit=` (1-200, default 20) and `/{id:guid}` -> `ExperimentJobView {id, state, stage, done, total, baselineRunKey, knob, candidateRunKey?, experimentId?, errorCode?, errorText?, queuedAt, startedAt?, finishedAt?, replayMs?, compareMs?, instruments, otherHeavyJobsSeen, cancelRequested, limits[]}`. 404 `experiments.job_not_found`.
  - `POST /api/experiments/jobs/{id}/cancel` -> 202 (fresh password not needed: stopping is the safe direction); 409 `experiments.job_not_cancellable`.
  - The existing `GET /api/experiments` and `/{id}` are unchanged; the result card reads the ledger row for the judgement.
- **Hub:** client events `experimentProgress {jobId, state, stage, done, total, message?}` and `experimentFinished {jobId, state}` in `LiveHubContract` and `HubContractDocument` (the pattern of `labRunProgress`); same-origin and session rules unchanged.

Partial unique index on `((true)) where state in ('queued','running')` (one active job). Column-level `GRANT UPDATE` for `xd_app` on the state columns only (the pattern of `lab.lab_runs`; UNVERIFIED, read `AddLabRuns` first); no DELETE; a trigger refuses a change to a final state. Both migrations with `Down`; neither touches an applied migration.

## Non-functional
- Replay uses the engine's own cancellation between instruments (as `LabRunner`, `CancelEvery=5`); the API stays responsive (the job runs on the thread pool; a request never waits for it). Memory: the replay is in memory until complete, as the Lab (a 214-instrument run is the size of a full Lab test; UNVERIFIED on the owner's machine, which the measured job reports).
- Security: session + CSRF + capability + fresh password; owner actor from the session; text from the request (`reason`, names) is length-bounded, control characters refused, never logged. Logs carry job id, state, counts, ms, codes (block 4900-4919 proposed; `LogEventIdTests` decides at build time; the highest id used when last read, 2026-10-25, is 4801).
- Observability: the job row is the record; the audit row is `AccountEventType.ExperimentJobStarted | ExperimentJobCancelled | CapabilityChanged` (new values appended, detail `kind=exit instruments=214`, no value, no key).

## Decisions (researched)
- **D1 Reuse versus a new queue.** Chosen: a small sibling `experiment_jobs` table with the Lab's pattern (table is the queue, `SKIP LOCKED`, interrupted on restart). Rejected: a Lab `method` value (a Lab run is a strategy-version test with gates; this is a baseline-versus-candidate judgement, different identity, different report) and Hangfire/services framework (a service is scheduled work; this is on-demand, one owner). Source: `LabRunDispatcher.cs`, `ILabRunStore.cs`, ADR 0058, doc 04 §3.1.
- **D2 Start needs the fresh password.** Chosen: same as autonomy (every request, `Elevate:false`). Reason: a hijacked session could otherwise burn trials and fill storage; the owner's Q1 recommendation is "a password on every change and an audit row". Rejected: the 5-minute step-up window (not consumed by use, P7-12 assumption 8). Cancel needs none.
- **D3 Which knobs.** Chosen: exit parameters and upward slippage only. Reason: ADR 0072 compares the same entries and refuses added entries; a `parameter` can change entries and then the job would burn time and return `entries_added`. Cheaper slippage cannot win and still costs a trial, so the form refuses it up front (the ledger still records one if posted by the verb). Rejected: all three kinds (wasted trials).
- **D4 One job, 3 a day, 60 minutes.** Chosen for the reasons in assumption 4. The numbers are settings the owner may lower; raising the day limit above 10 or the time above 240 minutes is refused at start-up. Rejected: unlimited or queued jobs.
- **D5 Candidate runs are marked.** `created_by = experiment:<jobId>`. P8-06's default population ("newest run per strategy and universe") must **exclude** such runs by default and offer them in the picker labelled "experiment candidate", otherwise a stressed run would silently become the default Reports view. This is a requirement on P8-06 (see report); P8-18 adds the test against whatever the reader exposes.
- **D6 Replay time.** Measured, stored, printed with the instrument count and "other heavy jobs running"; the "< 10 minutes" claim is evaluated only at exactly 214 instruments. Source: P6-11 assumption 10 ("not measured"), P8-00 row P8-18.
- **D7 Capability store.** Chosen: an insert-only table with a code whitelist, newest row wins, absence = OFF, ON needs the password, OFF does not. Reason: it follows the autonomy pattern the owner already accepted (audited, snapshot hash, DB clock) and keeps a kill switch fast. Rejected: `platform.app_settings` (overwritten in place, no history, P7-12 assumption 7) and appsettings/env (needs a restart and an edit outside the app; also reasonable, but the owner asked that turning on be an authenticated act in the app).
- **D8 Hub events.** Two new events beside the Lab's, same throttle (4/s) and same-origin rule. Source: `HubLabProgress.cs`, `LiveHubContract.cs`.

## Risks and honest limits
- **On today's data every experiment is at best Inconclusive** (about 3 development folds, 6 needed, hold-out 6 months). The screen says so before the run and after it. A run is a look; the knob was picked by looking at the same history (ISS-19).
- The 30-day trial count sees only experiments recorded here; cancelled and failed jobs are not trials though they were looked at. Candidate runs are permanent storage.
- The replay time is for this machine and this moment; it is not a promise and not a measurement of the 214-instrument target unless the run has 214 instruments.
- "Owner" is a string in the database: code holding `xd_app` could write rows. The control is that the only writer is the endpoint (session, CSRF, password, capability) and the architecture/checksum tests; a compromised process is not stopped by the database (as P7-12).
- A hijacked session that also knows the password can start up to 3 jobs a day; it cannot apply anything because nothing applies.
- Rebuilding the request from a record may be impossible for old runs (schema versions before 6): those baselines are refused with a reason, not guessed.
