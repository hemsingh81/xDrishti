## Goal
One command measures whether the local model and the current prompts are good enough to be the assistant, and says so with numbers, intervals and a pass/fail against the thresholds of doc 14 §5. The same command re-runs on every model, runtime or prompt change, shows what changed against the last accepted run, and refuses to call a run "accepted" when a threshold fails. The result is also the basis for choosing between Qwen3-30B-A3B and gpt-oss-20b (ADR 0005) and for judging Hermes (P9-10).

## Acceptance criteria
1. **Fixture.** `eval/fixture/fixture.json` seeds an empty `xdrishti_eval` database to exactly the records of "The fixture" below; seeding twice changes nothing; its SHA-256 is `fixture_hash`. A model-free test recomputes the KPI answers with the P8-05 engine over the seeded trades and asserts each equals the hand-worked `expected` of the questions within 1e-9. The oracle uses the same P8-05 engine that `get_report` calls, so engine agreement is not independent proof of the engine; the hand numbers are the second derivation, and the test says so. The store keeps expected values as exact fractions (e.g. 1/6, 17/13) and rounds only when grading.
2. **Data questions.** The 30 questions are exactly those of the table below (ids, categories, expected). A scripted "perfect" answer set grades 30/30; a scripted answer set with each question's number changed in the last digit grades 0 numeric passes; a perfect answer plus one extra unrelated number in an anchored sentence fails with `conflicting_number`; honest-state questions fail if the answer gives any number for the withheld metric.
3. **Number grading is exact.** For `number` expectations the answer token must have at least `min_decimals` decimals and equal the expected value rounded half away from zero to the token's own decimals, or be numerically equal; no tolerance band. Tokens are normalised (`₹`, `%`, trailing `R` or `x`, Western and Indian grouping, unicode minus). Integer expectations need the exact integer token. Table tests: 45.83 accepts `45.83%`, `45.8%`, not `46%` (min_decimals 1), not `45.9%`; 0.1667 accepts `0.17`, `0.167`, not `0.16`.
4. **Grounding.** For each answer every numeric token must occur in the case's tool results (`ai.tool_calls.result` joined by `ai.eval_cases.session_id`; recomputed here, independent of P9-03's own `grounding_status`, and any disagreement between the two is reported), in the question text, or in `allowed_numbers`; else `ungrounded_number`. A case passes only if correct **and** grounded. Ungrounded tokens in an honest-state case are a hard fail of the set.
5. **Plans (set B).** Each of the 10 lines of `plans.jsonl` holds a stored `BriefingFacts` JSON; the runner calls the P9-06 pipeline with `UseModel` forced on and `MaxAttempts` 1 (raw) then 2 (repaired). Per case: `raw_pass` = guard ok on attempt 1; `repaired_pass` = guard ok within 2 attempts; `escape` = text accepted by the guard in which `IndependentNumberAudit` (a differently written tokenizer) finds a number absent from the facts; `covered` = every primary and reserve symbol present. The independent audit and the guard agree on 1000 generated texts (property test).
6. **Ideas (set C).** Each of the 10 lines of `ideas.jsonl` is graded by `DraftGrader` on the draft pipeline of P9-07 (the `draft` job with the real validator): `valid` (validate ok), `first_shot_valid` (valid before any repair), `intent` (assertions passed over assertions total), `decline_correct` for the two decline ideas. Assertion kinds are fixed (see format).
7. **Events (set D).** `announcements.schema.json` fixes the row format and `AnnouncementGrader` computes precision and recall of the `material` class with Wilson intervals; with no rows the set reports `not_evaluable: 200 labelled announcements arrive with P15` and does not block the verdict. Grader unit-tested on a synthetic 200-row confusion table (precision 0.80 exactly passes, 0.795 fails).
8. **Repeats and determinism.** Every case runs `repeats` times (default 3; request options temperature 0 and seed 1337; the server mode recorded as it is, `main` with thinking off per P9-01; `cache_prompt` off if the client can pass it, else left on and recorded; one request at a time). A case counts as passed only if all repeats pass (`pass^k`); `pass@1` and `stability` (share of cases whose normalised answers are identical across repeats) are reported. `--repeats 1` runs are marked `non_gating` and can never be accepted.
9. **Thresholds** are read from `eval/thresholds.json` (not code): data `pass >= 27 of 30`; plans `raw_pass >= 8 of 10`, `repaired_pass >= 9 of 10`, `escape = 0`, `covered = all`; ideas `first_shot_valid >= 8 of 10`, `repaired_valid >= 9 of 10`, `intent >= 0.85` with no idea below 0.60, `decline_correct = 2 of 2`; events `precision_material >= 0.80` once n >= 200. Verdict `PASS` needs data, plans and ideas to pass; events `not_evaluable` is shown and does not block. The report prints every rate with its Wilson 95 % interval and the line "30 cases cannot separate 27 from 24 correct".
10. **Fingerprint and staleness.** `fingerprint = SHA-256(model_sha256, runtime image digest, prompt versions and hashes from `PromptRegistry`, sets hash, thresholds hash, fixture hash, profile)`. `GET /api/assistant/evals/status` returns `{ baselineRunId?, baselineFingerprint?, currentFingerprint, stale, reasons[] }` where `reasons` names what differs (model, runtime, prompt X, sets, thresholds); with no baseline it says "no accepted eval run". A changed prompt version or model makes `stale = true` without any network call. P9-03's `GET /api/assistant/status` field `evaluation` (`not_yet_evaluated | passed | failed`) is fed from this: `passed` only while a baseline exists and `stale` is false, `failed` when the newest gating run is not `PASS`, otherwise `not_yet_evaluated`.
11. **Accept.** `xd eval accept <run>` (actor `cli:xd`) is refused (`eval.below_threshold` / `eval.non_gating`) unless the run is `PASS` and gating; if any set's pass count is lower than the current baseline's, `--reason "<text>"` is required and stored. At most one baseline row per run; the newest baseline is the current one.
12. **Compare.** `xd eval compare <run> [--baseline <run>]` prints per set: counts, discordant pairs `b` (baseline pass, now fail) and `c` (reverse), the exact two-sided sign-test p-value, and the sentence "with this many cases at least 6 discordant pairs, all one way, are needed for p < 0.05". It flags `regression` when a threshold now fails or `b - c >= 2` on data / `>= 1` on plans or ideas, and never blocks by itself (the gate is the thresholds).
13. **Target isolation.** The runner starts only after a probe: through the tool endpoint it reads `eval_marker.fixture_hash` from the connected database and compares it with the fixture hash; a missing or different marker aborts (`eval.wrong_database`) before any model call. The eval tool endpoint is a separate read-only instance (compose service `xd-mcp-eval`, profile `eval`, the same image and the same two roles `xd_mcp_read`/`xd_mcp_sql` of P9-02, which are cluster roles granted in `xdrishti_eval` by the same migrations, with its own bearer token `Mcp:Tokens:Eval`), not the production one. The eval database's own `ai.settings` row is seeded `enabled = true, portfolio_context = true` so the portfolio views return rows there; the owner's production switches are not touched, but the runner refuses to start while the production `ai.settings.enabled` is false (`eval.assistant_disabled`), because the turn runner honours it.
14. **Store.** `ai.eval_runs`, `ai.eval_cases`, `ai.eval_baselines` are insert-only for `xd_app` (grants test); the report folder `data/eval/<run-id>/` (git-ignored) holds `report.json`, `report.md`, `answers.jsonl`; logs carry ids, counts and ms (6190 to 6195, the E2 block of P9-00), no answer text.
15. `scripts/check.sh` runs all model-free tests (graders, statistics, fixture oracle, thresholds parsing, scripted-answer end to end); `scripts/gen-api.sh` run; Architecture.Tests green (Domain pure; the model reached only through the P9-03 pipeline, not directly).

## Non-functional
Wall time, UNVERIFIED on the owner's machine: data 30 x 3 x about 45 s, plans 10 x 3 x 25 s, ideas 10 x 3 x up to 3 calls, so roughly two hours for a gating run and about 40 minutes at one repeat. Graders: milliseconds. The fixture database is tiny (under 2 MB). No secret; eval answers hold only fixture data. The deterministic setting is the gate. A thinking-on Qwen run (temperature 0.6, top-p 0.95, top-k 20 per the Qwen3 card) would need a server mode P9-01 does not offer and is out; `gptoss` is always reasoning and is run as configured, its profile recorded.

## Test plan
Unit: `AnswerGrader` tables for every expected kind and the failure codes; number normalisation (Indian grouping, unicode minus, `1,23,456.50`, `R`, `x`); Wilson values (27/30 gives 0.744 to 0.965; 10/10 gives 0.722 to 1.0; 160/200 gives 0.739 to 0.850); sign test (b 6, c 0 gives p 0.03125; b 5, c 0 gives 0.0625); `ThresholdTable` parsing and verdicts; fingerprint sensitivity (each input changes it); staleness reasons; accept rules; `DraftGrader` assertions on two hand YAMLs. Property: independent audit versus guard agreement (1000 cases); grader never passes an answer that contains no digit for a number expectation. Integration (Testcontainers): migration, grants, seeder idempotence and hash, fixture oracle versus P8-05, the wrong-database abort, a scripted end-to-end run (a fake model returning the perfect answers) producing a `PASS`, accepted, then a changed prompt version making `status` stale. No test calls a real model.

## Decisions (researched)
**D1. Thresholds from doc 14 §5, made measurable.** *Answer:* data `>= 27/30` (90 %), events `>= 80 %` precision; briefing and ideas split into raw, repaired and escape counts (table in criterion 9). *Reason:* doc 14's "No numbers absent from input" is true by construction in the product (a guard plus a fallback), so the measured quantity is how often the model's own text survives (8/10 raw is the point below which the model adds nothing over the fixed text); "Valid DSL" is split into first-shot 8/10 (the same bar the Hermes PoC uses, doc 14 §6) and repaired 9/10. *Rejected:* 10/10 gates on 10 cases (a single flake blocks every model). *Source:* docs/design/14 §5, §6.
**D2. Exact-match grading, no model judge.** *Answer:* answers are graded by code: exact normalised numbers, set membership for text, state phrases for honest cases; no LLM-as-judge. *Reason:* the owner's rule is exact numbers; a judge model adds a second source of error and non-determinism; vendor guidance on LLM CI gates favours deterministic checks for structured outputs and fixed thresholds in config, and keeping a small maintained golden set (https://langfuse.com/resources/engineering/llm-regression-testing.md and https://oneuptime.com/blog/post/2026-08-31-llm-evaluation-ci-regression-gate/markdown, read 2026-10-24; vendor blogs, not standards). *Rejected:* a rubric judge; fuzzy numeric tolerance.
**D3. Small sets, honest statistics.** *Answer:* report Wilson intervals and an exact paired sign test, never a significance claim from 30 cases. *Reason:* at 27/30 the 95 % interval is 74 % to 97 %; the paired-comparison advice of Miller, "Adding Error Bars to Evals" (https://arxiv.org/pdf/2411.00640, read 2026-10-24), is to compare models on the same questions and look at the paired difference, which is what `compare` does. *Rejected:* bootstrap on 30 items as the headline (hides the small n).
**D4. A fixture database and a separate tool endpoint.** *Answer:* `xdrishti_eval` seeded from a file, read through `xd-mcp-eval`, with a marker probe. *Reason:* questions need known answers; the owner's stores are empty or mutable; running the real tool code against the real schema tests the real SQL path. *Rejected:* mocked tool results (would not test `run_sql` and the report tools); pointing at the owner's database (answers change daily).
**D5. ## Risks and honest limits
- 30, 10 and 10 cases cannot show a small difference or a high pass rate with confidence; the intervals say so. The fixture is small and synthetic: it tests reading numbers correctly, not market judgement.
- The questions were written by the same team that wrote the tools; a model tuned to them would pass without being good (no tuning is planned; the sets are not shown to the model except through the run).
- Intent assertions for ideas are mechanical; they cannot tell a sensible strategy from a literal one. The owner's own reading of ten drafts remains an owner act (recorded as a note on the run if made; absence is stated, not assumed).
- Greedy decoding on a GPU is not a determinism guarantee; `stability` shows how far it holds. A pass at temperature 0 does not predict behaviour at other settings.
- The data set grades the final answer text; a correct answer with a wrong chart or a missing table is outside it.
- Hermes answers are graded after the fact from a file and an audit join; if the tool-call audit is missing, grounding is `not_evaluable` and the Hermes result cannot pass (P9-10).
