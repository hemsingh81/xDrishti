## Goal
Everything the system has learned, planned and graded becomes readable in the app, honestly, on a phone and on a 4K monitor: a **Learning** screen (journey, lessons, plan versus actual, setups, tweak and re-run, autonomy), a **Reports** screen (Overview with auto-insights, basket comparison, pivot builder, lenses, filters, drill-down to the trade), exports and an installable shell. The phase exit is one question the owner can ask of the stored research and get an answer to in under two minutes: **what works, in which basket, on which timeframe, with which exit**, including the answer "nothing has enough evidence yet", which on about 2.1 years of replayed history is a likely and legitimate one. Like P3 to P7, P8 proves the machinery and its honesty rules; what the screens can *conclude* is bounded by the data (section "Honest limits"). **P8 builds no new way to change trading behaviour** (section "What P8 may and may not do").

## What P8 may and may not do
- **P8 may:** read stored records and show them; compute report aggregates **on the server** from stored simulated trades, plan grades and the journal (read only); add read endpoints; add lazy screens, a shared chart and honest-state kit, a bundle guard, an installable app shell (if the owner allows it, Q5), plan notifications in the bell derived from stored state (read only), and the P7 follow-ups that are screens or derived read models.
- **P8 may not (without the owner's own answer, section "Open questions", marker SAFETY):** add any control that changes an approval, an autonomy or auto-approval switch, a service or builder switch, a lesson / hypothesis / changelog state, or starts a job ("run now"); export data out of the app; send a push notification; cache sensitive data offline; open the app to the LAN. **Nothing in P8 places, modifies or cancels an order**, and the P7 architecture rule (no order-named member anywhere) stays as it is.
- The existing writes keep working unchanged: plan decisions on `/plans` (P7-17), Lab runs, Services controls, account actions. P8 does not widen them.
- The browser computes no statistic. Numbers come from the server's report engine (a deterministic pure core, as in P5 to P7); the browser formats, sorts and filters what it was given, and draws it. This is the same rule as doc 15 §6 ("numbers always come from the report engine").

## The seam (the decisions the slices share)
**Fact.** P8 sits on stored things: cell snapshots, models, experiments, lessons, hypotheses, changelog (P6), plans, grades, journal, digests, plan runs (P7), simulated trades and Lab results (P3 to P5), baskets and bars (P1, P2). It adds almost no new state (one stored counterfactual in P8-12, nothing else planned). Everything else is a read model and a screen.

**D1. Server-side numbers, honest-limits as fields.** Every report response carries an `Evidence` block: `basis` (gross R or net R after the stored charge sheet; "net" only if the sheet is the owner's, ISS-25), `population` (the run keys or plan ids behind the numbers), `dateRange`, `n`, `folds` where relevant, the list of `unavailable` inputs with reasons, and the `limits` strings ("about 2.1 years, replayed history, modelled fills, in-sample, no hold-out, members as of today"). The screens render these fields on every report; none of that wording is page prose (P6 risk 7, P7 risk 12). A test per report pins that a response without its evidence block fails to render.

**D2. One population rule, shared with P6.** A report is computed over an explicit **set of stored runs**, never over "all trades": default = for each (strategy, universe) the newest run on the stored charge sheet, listed in a visible **Data used** panel (run keys, window, costed or gross), with a picker to change it. A set that holds two runs for the same strategy and overlapping window is refused with the same error family as `CellDuplicate` (no double counting). Gross and net runs are never mixed in one number (`MixedBasis`).

**D3. Six states, one vocabulary, never green.** Every metric the API returns is one of `value`, `insufficient` (n below the stated minimum: 15 for insights per doc 15 §6, `min_trades` 30 for cells), `unavailable` (an input does not exist, with the reason, e.g. regime, events), `not_evaluable` (a rule needs more than exists, e.g. six folds, a champion, a fill), or `empty` (no records yet). The UI has one component per state (icon + word + reason; colour never alone) and **never draws a number for a non-value** (no zero fill, no 0 % bar, no empty chart that looks like "flat"). `not_evaluable` and `unavailable` are never styled with the `good` colour. This is the single most important rule of the phase.

**D4. One query model for lenses and filters.** One `ReportQuery` (lens, filters, metric, run set) with a server whitelist (422 `reports.invalid` for an unknown name, as `plans.invalid` / `learning.invalid`) and the same fields in the URL, so a link reproduces a view and Back works. Lenses: all trades, basket, instrument, individual trade, strategy / cell, sector, month, weekday, regime (`unavailable`), account (`unavailable` for simulated trades: a simulated trade has no account; accounts exist only on plan allocations and journal fills). Overlapping baskets: an instrument in several baskets appears under each, so per-basket totals are **not additive** and the screen says so (doc 06 §4). Basket membership is the one stored with the trade (`basket_ids`, as of the run), stated on screen; "current membership" is a later toggle, not the default.

**D5. Reading "which exit" and "which timeframe".** Timeframe is a trade column. Exit is a property of the run (label or policy), not of the trade: the report engine takes it from the run set (D2) and refuses to guess it. Where a run carries no exit label the exit lens says `unavailable: exit not recorded for run X`. The `What works` view ranks cells by the **credible lower bound** of expectancy, not the raw mean, shows n and the denominator ("looked at N cells; the best of N looks good by chance"), and uses the Lab's multiple-testing count where it exists. A cell below `min_trades` is shown as `insufficient`, listed after the ranked ones, never hidden.

**D6. Read-only by construction; writes are a separate, owner-gated slice each.** Screens P8-01 to P8-17 call GET only (plus the plan decisions that already exist on `/plans`). A test per screen fails if its feature folder imports a mutation or calls `POST`/`PUT`/`DELETE`. The write slices (P8-18, P8-19) are separate, stop for the owner, and each write needs the step-up the server already demands.

**D7. Bundle discipline.** Each screen is a lazy route (own chunk) as today; the heatmap / scatter / histogram / treemap chart types register in the lazy ECharts chunk only; Lightweight Charts (if the owner agrees, Q15) is a lazy chunk used by the trade replay and ticket charts only; no new dependency enters the entry chunk. P8-01 adds a guard (`npm run size`, called by `scripts/check.sh` after the build): entry + modulepreload chunks ≤ 200 KB gzip, and each lazy route chunk ≤ a stated budget, with the numbers printed. The budget baseline is the measured 195.3 KB, so a regression is caught the day it happens. P8-01 built the guard (ADR 0098): it holds entry + modulepreload to 200 KB (195.2 KB, 4.8 KB spare) and prints the larger always-needed first-paint total (205.1 KB with the app shell, landing route and CSS) without limiting it; under 3 KB of headroom it warns, and the first slice to hit the warning must first free space (preload path, entry split). Rule: eager code additions (nav entries, route definitions, tokens, `shared/lib`, `shared/ui` exports) spend the budget; lazy screens do not.

**D8. Exports leave nothing the owner cannot see.** If exports are allowed (Q4) they are a download of the table as displayed, built on the server from the same query, carrying the evidence block, with no account number, client code, balance or token, authenticated and logged as a count (kind, rows) never as content.

**D9. The PWA is a shell.** If allowed (Q5, Q7): a manifest, icons and a service worker that caches only the hashed static assets and an offline page. It never caches `/api` or `/hubs`, is cleared on sign-out and lock, and cannot show data while offline. The access path (LAN, TLS) is a deployment decision made before the slice, not inside it.

**D10. No invented scores.** Doc 13 / 09 list a "Learning health" 0 to 100 score from five parts and a "discipline score". No definition exists in code. P8 shows the parts that exist with their n and refuses to add a composite (Q12).

## Honest limits (read this before any P8 number)
- **Data: about 2.1 years** of 1-minute history (files from 2024-04-01 to 2024-12-18 to 2026-04-30), **no hold-out** (ISS-19), replayed history with **modelled fills** (ISS-18), survivorship as of today (ISS-22), costs net only if the stored charge sheet is the owner's (ISS-25, UNVERIFIED; otherwise every report is **gross** and says so). Every number on a report is a description of the past on data that shaped the rules, not a forecast.
- **A basket's result is a sum over its members as of the run**, overlapping baskets double-count by design, and a basket with a few instruments has a few hundred trades at most: expect `insufficient` cells to be the majority.
- **Looking at many cells and picking the best is a selection effect.** "What works" ranks by the credible lower bound, shows n and how many cells were looked at, and the sentence says the best of N will look good by chance; the Lab's trial ledger is the only formal count.
- **Provisional plans.** Plans were produced with cells that passed the gates, not paper-proven ones (P7-00 Q7); their grades are `simulated on plan prices`, not fills. **No graded real trade exists** (P10 / P11), so plan vs actual, execution gap, discipline and the live line of the journey are `not_evaluable`.
- **Many NOT EVALUABLE states are the correct display, not a defect:** no champion model (calibration, meta policy), no experiment, no context data (regime, market gate), no events data, no fills, no live trades, fewer folds than the minimum (about 5 or 6 quarterly windows, P6-00). Screens show them as such and the exit criterion does not need any of them to turn green.
- **The frozen-model comparison covers at most about one year**, and "no difference" is an ordinary answer.
- **Empty owner stores today** (no model, no experiment, no plan stored as last read): the first look at Learning and Plan screens on the owner's machine will be mostly empty states; the seeded fixtures, not the owner's data, prove the layouts.
- **Layout was never seen in a browser by an agent** for P2 to P7 (P7-17 said so); jsdom tests cannot assert 360 px or 4K layouts. Until the P8-16 checklist is run, "responsive" is a claim, not evidence.
