# P7-16 — Depth recording service: Dhan 20-level market depth recorded from the Data account, stored compressed, no trading use

- **Status:** Draft (written 2026-10-24; decisions below were researched under the owner's delegation; the owner's Approved is still needed before an agent builds it)
- **Phase / roadmap row:** P7 — slice P7-16 of [P7-00](P7-00-selection-accounts-and-nightly-plan.md) ("Start depth recording", SAFETY, Q9; first on the P7 cut line).
- **Design refs:** docs/design/20 §B (record our own depth; "start in P7 so >= 6 months exist by P13"), 16 (`feed_recorder`), 17 §1-2 (VM disk 120 GB, "revisit before tick data"), 03 §5 (`market.depth`), 19 §5 · ADR 0024 (live feed, allow-list), 0083 (no order by name). New ADR: **next free ADR number at build time**.
- **Needs:** P2-10, P7-11 (built). **Needed by:** P13-00 and its slices (sole consumer).
- **Size:** 4 agent-days (estimate).
- **Safety:** **yes** — a new broker WebSocket endpoint on the allow-list, the Data account's token on a second connection, continuous disk growth. Default OFF twice (configuration and a paused service). The owner's Approved on this spec and on the allow-list entry are the owner's acts; Draft holds the build. No order, no order-capable scope, no reader of the data.

## Goal
From the day the owner switches it on, each session's 20-level book of up to 50 chosen NSE shares is recorded about once a second, compressed, append-only and bounded by a disk budget that stops the recording rather than the machine, so six months exist when P13 starts. Nothing in P7 to P12 reads it.

## Acceptance criteria
1. Given the allow-list, then `wss://depth-api-feed.dhan.co/twentydepth` with exactly `authType, clientId, token` (each once, any order) is allowed and every other host, path, port, scheme, extra key (including `version`) or the 200-level host is refused before a connection opens; the live-feed rules and refused probes are unchanged; `PinnedAllowList` gains `WSS depth-api-feed.dhan.co/twentydepth?authType&clientId&token`.
2. Given constructed frames (marked UNVERIFIED), the parser decodes bid/ask packets of 332 bytes (little endian), walks stacked packets, and drops-and-counts (never throws) a wrong length, unknown code, segment other than `NSE_EQ`, NaN/negative/non-finite price and a truncated tail; code 50 goes through `FeedDisconnectReasons`; 806 ends the run `not_subscribed`, 805 `flapping`, 807-809 stop reconnects until the token changes.
3. Given a bid and an ask packet, the sampler emits at most one snapshot per instrument per `Depth:SampleMs` (1000), only when a side changed and both sides were seen; a side older than 5 s sets `stale_side`; prices become integer paise (half away from zero); a quantity above `int.MaxValue` is clamped (`qty_clamped`); best bid >= best ask sets `crossed`; levels beyond the book are 0/0/0; `ts` is receive time and `rx_mono_ms` the monotonic milliseconds since the run started, so a wall-clock jump is visible (packets carry no exchange time).
4. Rows are written with `COPY` in one transaction per batch every `Depth:FlushSeconds` (5); a failed batch is retried with the next; more than 30 s unwritten are dropped oldest first and counted; the receive loop and the live session are never blocked.
5. `DepthRecordingSet.Build` returns at most `Depth:MaxInstruments` (50) distinct instruments in the order armed tickets of today (rank order, at most `Depth:MaxArmed` 20), `Depth:PinnedSymbols`, then highest 20-session mean turnover (close x volume, before today) among tracked instruments; ties by symbol; unmapped symbols skipped and counted; stored at the start in `market.depth_session_instruments` with reason and rank; fixed for the day.
6. The recorder runs only when **all three** hold: deployment `Depth:Enabled = true`, the owner's stored switch ON (newest row of `market.depth_recorder_switch`; no row = OFF), and the service `depth-recorder` on (it starts paused). With any one off nothing reads credentials, builds a URL or opens a socket. `PUT /api/depth/recorder {enabled, reason, password}` checks the password **afresh on every change** (`StepUpCommand` with `Elevate: false`, sign-in lockout rules and audit, an earlier step-up window neither counts nor is used up), takes the actor from the session (`owner:<email>`, never the body), appends a row and an account event `DepthRecorderSwitched`; no session is 401, a wrong password 401/423, a body without a reason 400 `depth.reason_invalid`; turning it OFF needs the same password. `GET /api/depth/recorder` returns the switch, its history and the reasons the recorder is not running. On, the window is 09:14-15:31 IST on trading days; only snapshots stamped 09:15:00 <= t < 15:30:00 India time are written; one `market.depth_sessions` row is written at the end with the reason; a crashed process gets a `crashed` row at the next start.
7. Disk guard, before each start and every 5 minutes: stored size (`hypertable_detailed_size`) above `Depth:MaxStoredGb` (40) ends the run `disk_budget`; free space of the VM filesystem (statfs of the container root, verified at build; if unreadable the size cap alone applies and the Services row says so) below `Depth:MinFreeGb` (20) ends it `disk_free`; at 80 % a warning; a stopped recorder stays stopped until the condition clears and the owner resumes; **the app never deletes data**.
8. Token refused, feed dropped or machine asleep: reconnect with the existing back-off, resubscribe the day's set, the hole shows as `gap_seconds`; more than 10 reconnects in 5 minutes pauses attempts for 5 minutes and raises the service-failure notice; the live feed is unaffected in every case (separate session, own try/catch, own heartbeat row `xd-depth`; the `xd-feed` container health check reads only its own row).
9. Migration: `market.depth_snapshots` is a 1-day-chunk hypertable compressed after 2 days with no retention policy; `xd_app` can SELECT and INSERT but not UPDATE, DELETE or TRUNCATE any of the three tables (grants test); `Down` drops them; `market` is not re-granted.
10. **Never on the trading path.** The recording set is computed from read-only ports (`IArmedTicketReader`, `IInstrumentSecurities`, bars) and written only to the three depth tables; it is **not** an `IActiveSetProvider` and changes neither the live feed's set nor any ticket; a disk-guard stop, a failed connection or a crashed recorder changes nothing but the depth service's own run, row and notice (test: with the recorder failing, the pre-open check, arming, the active set and the live flush behave exactly as with it off). **No trading use** (architecture test): `Domain`, `Simulation`, `Strategies*`, `Indicators`, `Application/Planning|Learning|Portfolio` reference no `Depth` type or `depth_snapshots`; `IDepthStore` has no row-read method; no API route or frontend file mentions depth; the no-order tripwire is green.
11. Logs `depth.connected|disconnected|subscribed|flush|dropped|disk_warning|disk_stop|token_refused|flapping` carry counts and ids only, never URL, token, client id, symbol or price.
12. Pilot (owner-run, five real sessions, recorded in the ADR): bytes per row, compression ratio, packets per second and rows per instrument-day are measured with the queries below and replace the estimates in Decision 5.

## Non-functional
Ingest about 50 rows/s on average; parse load at an assumed under 1,000 packets/s (UNVERIFIED); `xd-feed` stays within 256 MB or the limit is raised to 384 MB per the pilot. One raw day is about 0.77 GB; two uncompressed days plus WAL are inside the free-space rule. The token is used on a second socket of the same host class (2 of 5); no new credential or secret file; the URL is never logged.

## Decisions (researched)
1. **20 levels, one socket, at most 50 instruments.** The documented NSE-equity path with 50 per connection; 200-level is one instrument per socket and would collide with the five-socket ceiling. Rejected: 200 levels (13x bytes, no P13 need), sharding over several sockets. Source: Dhan depth page, doc 20 §B.
2. **Set = armed tickets, then pinned, then most liquid.** P13 needs depth around the names the system plans; armed tickets appear only at 09:10 and change daily, so the liquid remainder keeps a continuous history. Fixed per day and stored. Rejected: a static list only; all 214 tracked names (20-level depth on illiquid names is empty).
3. **A hypertable in the existing database, not files.** Matches doc 03/20, queryable by P13, `bars_1m` already proves the compression pattern. Rejected: daily zstd files on a bind mount (a second system to index and back up; mount performance), moving the DB to the external SSD now (no evidence it is needed before P13; an owner act).
4. **Whole-book snapshot, six int4 arrays, at most once a second, change-only, receive time.** Raw updates are 332 bytes per side at an unknown, probably high, rate; one second keeps the shape (imbalance, spread, walls) at a plannable cost. **Sub-second dynamics and exact alignment with trades are not recorded**; timestamps are +/- a second or more. Rejected: every update; top-5 only (loses walls). `SampleMs` goes down to 500.
5. **Budget (computed).** 09:15-15:30 = 22,500 s x 50 instruments = 1,125,000 rows/day (upper bound, the book changes every second); about 248 sessions = 279 M rows/year; about 680 B/row (six 20-element int4 arrays plus overhead) = **0.77 GB/day, 190 GB/year raw**. Timescale compression of int arrays is UNVERIFIED; planning range 3:1 to 8:1 = **63 to 24 GB/year, planning figure 5:1 = 38 GB/year**; six months (about 124 sessions) = 19 GB; doc 20's "50-100 GB/year" is the same order. So `MaxStoredGb = 40` covers about a year at the planning ratio and always the six months P13 needs; `MinFreeGb = 20` leaves room for two uncompressed days, WAL and the rest of the database. If the pilot ratio is under 3:1, revisit `SampleMs` and the set size within the first month.
6. **Volume: `xd-db-data` inside the 120 GiB VM disk, protected by a guard.** The VM disk is a sparse file on a Mac with free space; enlarging it (`podman machine set --disk-size`, machine stopped) is a cheap owner act; moving to the external SSD is the P13 decision doc 17 leaves open. Rejected: a second volume or tablespace on the same disk (more parts, no safety).
7. **Stop at the threshold, never delete.** A deleting guard would destroy the data the phase exists to collect; a stopping guard costs only future data and notifies. No retention policy; dropping chunks is a manual owner SQL act after P13 decides. Rejected: `add_retention_policy`, rolling windows.
8. **Start/stop as a service, default OFF, three gates, the owner's switch needs a fresh password.** Deployment flag, the stored switch (password re-entered on every change, exactly as `PUT /api/autonomy/settings`, ADR 0091) and the paused-by-default service row. Reason: it opens a second broker connection with the Data token and starts unbounded disk growth, so a mis-click or a stolen session must not be enough. Rejected: service resume alone (no password in the services framework); a single switch.
9. **Window 09:15:00-15:30:00 only.** Pre-open and closing sessions are call auctions whose books behave differently; connect at 09:14 to lose no second. Revisit in P13-00.
10. **No consumer, no read path**, enforced by an architecture test: no model, filter or size may change on data nobody has validated; P13 is kept only if out-of-sample intraday expectancy improves.
11. **One exact allow-list row, not a looser guard.** Rejected: letting `IsAllowedWebSocket` accept two hosts by suffix.

## Risks and honest limits
- Data plan unknown: without depth rights Dhan answers 806 and nothing is recorded (harmless). Byte order, sequence and rate are unverified; fixtures are built from the documentation and must be replaced by sanitised captures (`docs/research/dhan-samples/depth20-bid.hex`, `-ask.hex`).
- **Lost seconds are lost**: a sleeping Mac, lapsed token or restart leaves holes (listed per session); six calendar months hold fewer than 124 full instrument-days.
- **No backup here and it is the only copy.** When `xd-backup` is built it must exclude `market.depth_snapshots` chunk data (`pg_dump --exclude-table-data`) or the nightly dump grows by GBs a week; losing the table costs waiting time, not capital.
- The VM disk is shared with bars, results, images and models; the guard protects the machine, not the other tenants. The recorded set is armed + pinned + liquid, not a market sample; features learnt from it describe those names.
- Pilot queries: `SELECT hypertable_detailed_size('market.depth_snapshots')`; `SELECT before_compression_total_bytes, after_compression_total_bytes FROM hypertable_compression_stats('market.depth_snapshots')`; `SELECT instrument_id, count(*) FROM market.depth_snapshots WHERE ts >= date_trunc('day', now()) GROUP BY 1`.
