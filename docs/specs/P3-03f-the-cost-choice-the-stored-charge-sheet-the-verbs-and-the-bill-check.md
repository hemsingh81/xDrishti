## Goal
The owner can load his charge sheet, see it, check it against his own bills, and run the simulator with it. A request names its cost choice in its type: a stored sheet with a capital and a profile, or gross by name; there is no third state and no zero-cost run by omission. A sheet that is unknown, or that begins after the window, refuses the run before any bar is read. The sheet is one row of `platform.app_settings`, versioned by id and embedded in every run record. The check reads the original report files line by line, compares each charge with the model and proposes rates from the bills (never stores them). The sheet and the check are the owner's; nothing in `src/` holds a rate.

## Definitions (decisions the tests pin)
Names of P3-03c are its: `CostSheet`, `CostSheetJson`, `CostContext`, `CostRecord`, `SizingProfile`, `CostErrors`, `TradeCosting`.

**F1 — The cost choice.** A closed type in `XDrishti.Application/Research`:
```csharp
public abstract record CostChoice
{
    public static CostChoice Gross { get; }                                                   // explicit, named; labelled "costs: none"
    public static CostChoice Sheet(string sheetId, decimal capital = 1_000_000m, string profile = "standard", decimal maxCostR = 0.10m);
}
```
Two sealed cases with private constructors; there is no state in which a gross choice carries a capital, and none in which a sheet choice lacks an id. `SimulationRequest` gains **`CostChoice Costs` as a required parameter, placed after `BasketId` and before the defaulted members**, so that every call site (the P3-04a handler tests, `RunSimulationDatabaseTests`, `RunSimulationBenchmarks`, the verb) stops compiling until it names its choice: a forgotten edit is a compiler error, not a runtime refusal. The default capital 10,00,000 and the profile `standard` are plan question Q4, taken on 2026-10-18 (the owner may revert); `max_cost_R` 0.10 is `selection.max_cost_R` of doc 16. **Validation** (extends P3-04a D1; failures are `simulation.invalid` with a `FieldErrors` entry per field, all of them listed, **one code only**): `costs` null (a caller that bypassed the type) is `costs: required`; `costs.sheet_id` empty or outside the id pattern; `costs.capital` not in (0, 10,000,000,000] or not finite; `costs.profile` not `standard` or `conservative`; `costs.max_cost_r` not in (0, 100] or not finite. There is no `costs_required` code: omission cannot be written. **Meaning of the verb flags** (rows of P3-04b2's table): `--gross` is `CostChoice.Gross`; `--costs <id>` with optional `--capital`, `--profile`, `--max-cost-r` is `Sheet(...)`; **neither `--gross` nor `--costs` is a usage error (exit 2)**, both is a usage error, and `--capital`, `--profile` or `--max-cost-r` without `--costs` is a usage error.

**F2 — The handler.** Order of operations (extends P3-04a D1): (1) validate, `Costs` included; (2) build `FillRules`; (3) `engine.Prepare`; (4) **only then**, for a sheet choice, `ICostSheetStore.FindAsync(id, ct)` once: absent is `simulation.cost_sheet_not_found` (not found); an id that starts with `test-` is never stored and so is not found; a sheet whose first schedule starts after `From` is `simulation.cost_sheet_not_effective` (validation, field `costs.sheet_id`: no trade of the window may lack rates, and a window that begins before the first date the owner vouches for is refused, not extrapolated); then `CostContext.Create` (its errors are passed through as `simulation.invalid`) and the `CostRecord`; (5) then any other port (the basket, the calendar, the bars). The handler gives the **same `CostContext` instance** to every `InstrumentReplayInput` and the `CostRecord` to `RunHeader`. A gross choice reads nothing and gives null for both. The start log line of P3-04a (D5) gains one argument, the sheet id or `gross` (an id; no rate, no capital). `Prepare` and the engine port do not change.

**F3 — The store.** Trading configuration lives in the database (ADR 0002); P3 writes no table and runs no result store (P3-04a, P3-10). A settings row is neither: the sheet is **one row of the existing `platform.app_settings`**, key **`research.cost_sheet.<id>`** (`AppSettingKeys.CostSheetPrefix`, the id lower-case from P3-03c D4), value the full canonical JSON of the sheet (`ToCanonicalJson()`, `checked` included). The roadmap row says "one validated JSON row"; **the value column holds 500 characters and a sheet of two segments with one schedule is about 600**, so this slice **widens `AppSetting.MaxValueLength` and the column to 8,000** with one migration `WidenAppSettingValue` (widening cannot lose data; the module that owns a key still checks its own values; the other keys are short and unchanged), which holds about twelve schedules (P3-03c D4 caps the canonical text at 8,000). Not chosen: one row per effective-dated schedule (no migration, but a sheet is then several rows to keep consistent and the hash and label would be of a recomposition). **Versioning:** a new set of rates is a **new id** (`dhan-2026-11`); an id is overwritten only by `cost-sheet load --replace` (F4); every run **embeds** the canonical text (without `checked`) and the rates hash (`CostRecord`), so an overwritten row can never change an old record, and the run key changes if the rates did. The port (`Application/Abstractions/Research`):
```csharp
public interface ICostSheetStore
{
    ValueTask<Result<CostSheet>> FindAsync(string sheetId, CancellationToken cancellationToken);   // costs: not found, or the stored text no longer parses (costs.sheet_invalid)
    ValueTask SaveAsync(CostSheet sheet, string actor, DateTimeOffset now, CancellationToken cancellationToken);   // collects the change; a `test-` id is refused
}
```
There is no `ListAsync` (no consumer). `CostSheetStore` is `internal sealed` in `XDrishti.Infrastructure/Research` over `AppSetting`, registered scoped in `DependencyInjection.cs` so that the handler resolves under `ValidateOnBuild`; the change is saved by `IPlatformUnitOfWork.TrySaveAsync`. The sheet is not a secret and is never logged in full.

**F4 — The verbs, the host, the script.** Three one-shot verbs: `cost-sheet load <file.json> [--replace]`, `cost-sheet show <id>`, `cost-sheet check <id> <report.csv> [<report.csv> …]`.
- **Dispatch and host.** `VerbDispatch.Of(args)` selects `CostSheet` only when `args[0]` is `cost-sheet`; `Program.cs` tests it first, before `--healthcheck`, `migrate` and `owner-reset` (which match anywhere in `args`), so `cost-sheet load migrate` or a file named `owner-reset` cannot select them; the host is the generic host of P3-04b2 (no arguments bound to configuration, no `AddApi`, no vault key, validated on build, not started, logs to stderr). If P3-04b2 has not merged, this slice creates the dispatcher and host in the shape that spec describes and P3-04b2 adopts them; the second to merge carries the join and its test. The container `owner-reset` mounts secrets and cannot read a host file, which is why these verbs run on the host through the script, never in a container.
- **The script** `scripts/cost-sheet.sh` (macOS, the style of `simulate.sh`): `source _env.sh`, reads `Database__Password` from the Keychain item `xdrishti/db/app`, exports `DOTNET_ENVIRONMENT=Development`, **resolves every argument that is an existing file to an absolute path before it changes directory** (it `cd`s to `backend/src/XDrishti.Api`, so a relative path would otherwise point nowhere), and runs `dotnet run -c Release --no-launch-profile -- cost-sheet "$@"`, returning the verb's exit code. No `set -x`, no echo of the password, no vault key or owner secret.
- **Exit codes** (as P3-04b2 D1): **0** done (a `check` with rows beyond the tolerance is still 0: it reports, it does not judge); **1** refused, nothing written: an invalid sheet (the problems on stderr, one `path: code: message` per line, at most 20), a `test-` id, an id that exists with other rates without `--replace`, an unknown id for `show` and `check`, a file over the size cap, an unreadable report; **2** the command line or configuration is wrong (usage on stderr); **3** unexpected (database unreachable, a concurrent write: the message is the exception type and its message cut to 300 characters, no stack on the console); **130** cancelled. Logs go to stderr; stdout holds only the result lines. Three `[LoggerMessage]` lines (loaded or updated, shown, checked; event ids after P3-04b2's 4405 to 4409, the next free ones, kept unique by `LogEventIdTests`) carry the sheet id, the rates hash and counts; never a rate, a bill, a name or a client code.
- **`load`.** Reads the file only after checking its length against a cap of **64 KB** (a larger file is refused before it is read); passes the text to `CostSheetJson.Parse` (which has its own 16,000-character and duplicate-property guards); refuses a `test-` id; finds the stored sheet with the same id: if its **rates hash differs, `--replace` is required** (exit 1 without it, with a message that names the old and the new hash); if the rates are the same and only `label`, `source` or `checked` differ, the descriptive fields are updated without `--replace` (this is how `checked` is written after a successful check without changing the key); then `SaveAsync` and `TrySaveAsync` (false is a concurrent write: exit 3). It prints the id, the rates hash, the label and `checked` or `unchecked`. **The actor** written to `UpdatedBy` is the literal `cli:cost-sheet`: a verb has no signed-in session (the column otherwise holds the owner's e-mail). **No audit event is written**: `AuditEventType` is the authentication trail and has no member for a settings write (adding one would be an account-context change out of scope); the trail of a load is the row's `UpdatedBy` and `UpdatedAt` and the log line with the id and the hash. If the owner wants an audit trail it is a later slice with its own enum member.
- **`show`** prints the canonical JSON, the rates hash and the label (`CostDescription.Label`).

**F5 — The check.** `cost-sheet check <id> <report.csv>…` reads the **original global transaction report files** (the 16-column Dhan CSV, one file per financial year) through `SheetLoader` and `GlobalTransactionReader.Read` and compares them with the model; it reads the stored sheet, never the stored transactions (a stored `Transaction` has one charge total, no bill number, no product, and a two-sided bill is two trades with the charges split by value; negative "Oth." lines and the ≥ 0 sum of P2-17 would also make a flat tolerance on totals misleading). **The reader is extended additively:** `GtrRow` gains a last member `GtrLines? Lines = null` with the seven values by column (Brokerage, GST, STT, SEBI Fees, Stamp Duty, Txn. Charges, Oth. Charges), filled by the same loop that sums them; `Charges` stays the rounded sum, every existing constructor call compiles and P2-17's tests pass unchanged (a test asserts that the importer's outputs are byte-identical before and after).
- **Classification of a row** (never guessed; a row that fits none is listed as *unclassified* and not compared): a row with both a buy and a sell quantity is a same-day round trip on one bill, **intraday equity** (two legs, buy and sell); a row with one side only, an equity or ETF on NSE, and a brokerage cell of 0 when the sheet's delivery brokerage rate is 0, is **delivery** (one leg); futures, options, commodity, currency and BSE rows are skipped with their reason (the importer's own classification, `BillTrades`). The local note counts 11 round-trip bill lines among 603 cash rows (UNVERIFIED): intraday is checked thinly, and the output says how many rows each class has.
- **Comparison.** For each classified row: the model's `CostModel.Leg` per leg (the bill's turnover is the row's buy value or sell value; the date selects the schedule; the DP charge is excluded because it is not on the transaction report), summed over the legs; compared **line by line** (brokerage, GST, STT, SEBI, stamp duty, Txn. charges) with the row's cells, and in total over the six. **Pass:** the total difference of the row is at most **0.05 rupee** (the roadmap's tolerance per bill). The per-line differences are reported (largest per line), not pass/fail. The "Oth." cell is compared with the model's `other` line only when the sheet's `other_pct` is above 0; **a negative "Oth." cell is a rounding or adjustment line, listed under *adjustments* with its count and sum and left out of the pass count**.
- **Output** (stdout): rows read, per class: rows, passed, beyond the tolerance, the largest total difference, the largest difference per line; the ten rows with the largest difference (date, class, difference only: **no bill number, no scrip name, no client code, no mobile, no e-mail, no quantity or value**, which the reader's metadata rule never stores or logs); the adjustments; and **the implied rates**: for each class and line, the minimum, median and maximum of `line / value` as a percent (SEBI per crore) over the rows where the line is above 0, with the row count — a **proposal only**, never stored and never turned into a sheet by the command; it is ISS-25's "derive the rates from the bills" option, with its limits stated in the output (rounding noise at small values, no effective dates, no brokerage cap or minimum, thin intraday evidence). Finally, one suggested string for the `checked` field, such as `check 2026-11-02: 24 delivery rows within 0.05, 3 intraday rows within 0.05`, for the owner to put into the sheet and `load`; **the command never writes it**.
- **What it cannot do** (stated in the output): it cannot check the rates of a class that has no rows; it checks what the bills show, so a rate that has never been billed (for example intraday on an exchange the owner never traded) is unchecked; the DP charge and account-level fees are not on this report.

**F6 — What the owner supplies for the sheet (the exact list; answer in one message).**
1. A sheet **id** and **source** (where and when he read it, for example "Dhan brokerage page, 2026-10-20").
2. The **first date for which he can vouch** for the rates (ideally 2024-04-01, the first stored bar) and **every date after it on which any line changed**.
3. For **each date** and **each segment** (*intraday equity*, MIS; *delivery equity*, CNC), **ten lines, each written even when it is 0**: brokerage as a percent of turnover per order; the cap in rupees per order; the minimum in rupees per order (0 if none); STT percent on the buy side and on the sell side; exchange transaction charge percent; SEBI fee in rupees per crore; stamp duty percent (buy side); any other percent charge on the bill ("Oth. Charges", 0 if none); the DP charge in rupees per delivery sale (0 for intraday).
4. Per date: the **GST percent**; whether GST applies to **brokerage + exchange + SEBI only**; and **how the bill rounds**: to the paisa **per order**, **per trade** or **per bill**, and with which rule: `half_away_from_zero` (.5 rounds away from zero), `half_even` (.5 rounds to the even digit) or `down` (the extra digits are cut).
5. Whether the **brokerage has a cap** (a broker with a percent and no cap cannot be written in this sheet: a cap of 0 means no brokerage at all, so tell us and we add a field), and whether it is charged **per order** or per trade; whether there is a **flat fee per order** besides the brokerage (for example an auto square-off fee), which the sheet cannot hold (limit `no_flat_order_fees`).

8. Confirmation that every instrument is **NSE cash equity** (or which are not; ETFs may carry other rates). Capital and `max_cost_R` only if he wants other numbers than 10,00,000 and 0.10.

## Acceptance criteria
Numbered, each testable. The handler is tested in `XDrishti.Application.Tests` with a fake engine and fake ports (a fake `ICostSheetStore` that counts its calls); the store, the migration, the verbs, the check and the end-to-end run in `XDrishti.Api.IntegrationTests` (Testcontainers; fixtures from `tests/Shared`; **the end-to-end sheet is an ordinary invented sheet `fixture-a`, not a `test-` one, with the numbers of the TEST sheet**); the reader extension in `XDrishti.Application.Tests`; the rules in `XDrishti.Architecture.Tests`. Nothing is read from `data/`.
1. **The cost choice is a type.** `CostChoice.Gross` and `CostChoice.Sheet(...)` are the only ways to build a choice; no value has a gross choice with a capital; a request with `Costs` null is `simulation.invalid` naming `costs`; a sheet choice with an empty or malformed id, a capital of 0, negative, NaN, infinite or above 10,000,000,000, an unknown profile, a `max_cost_r` of 0, 101, NaN or an infinity is `simulation.invalid` naming each field (all listed, one code); no port is read; `SimulationRequest` compiles only with a `Costs` argument (the call sites of P3-04a's tests carry `CostChoice.Gross`).
2. **Refusals before any bar.** An unknown sheet id is `simulation.cost_sheet_not_found`; a `test-` id is the same; a sheet whose first schedule is after `From` is `simulation.cost_sheet_not_effective`; in each, and in every earlier refusal of P3-04a, the call counts of the bar store, the basket, the calendar and the corporate-action queries are 0; the sheet store is read once per run, after `Prepare` and before any other port; for a gross choice it is not called; the same `CostContext` instance reaches every `Replay` call and the header carries the `CostRecord`; the start log line carries the sheet id or `gross` and no number.

- **Data:** the key `research.cost_sheet.<id>` in `platform.app_settings`; the migration `WidenAppSettingValue` (value column 500 to 8,000; use the `new-migration` skill); no new table, no grant (the verbs connect as `xd_app` like P3-04b2).

- **Events/jobs:** none; three one-shot verbs.

## Non-functional
- **Performance:** one extra settings read per run; the check is linear in the rows of the files (a few hundred per year); no budget asserted.
- **Security and privacy:** the sheet is the owner's configuration, not a secret; it is written only by the owner-run verb on the host, never logged in full, never in a URL; the report files hold personal lines and bills: the check prints only classes, counts, differences and rates, plants sentinels in its tests, reads nothing into the model beyond the numbers, and never stores a bill; the only secret in the process is `Database__Password`, which the verb's own code never reads.
- **Fail closed:** an absent choice cannot be written; an unknown sheet, a window before the first rate and a `test-` id refuse before any bar is read; a stored text that stops parsing refuses.
- **Observability:** three log lines (ids, hashes, counts); the output of `check` is the user-facing explanation.

## Open questions
Question 1 is plan question Q3 and blocks this slice's exit check; questions 2 and 3 are the owner's facts; question 4 records the split.
1. **Plan question Q3 — who supplies the sheet and how.** **Recommendation:** the owner gives the current Dhan sheet in the layout of F6 in one message, with the dates on which any line changed since 2024-04-01 and two or three of his bills; the bills are the **check** (`cost-sheet check`, which reads his original report files line by line) and not the source, because they show what was billed, not the cap, the minimum or the effective dates. If he prefers to derive the rates, `check` prints implied rates per class and line as a proposal, intraday only from a handful of bills; a sheet written from them is `unchecked` until the check passes against rows it was not derived from.
2. **How far back do the rates hold?** **Recommendation:** the owner states the earliest date he can vouch for (ideally 2024-04-01, with the dates of any change since); a sheet that starts later limits runs to windows from that date (refused before any bar is read), which costs data but is honest; applying the current rates backwards is his choice and must be written as a first schedule dated 2024-04-01, never done by the code.
3. **The DP charge, the flat fees, the brokerage cap and the rounding level.** **Recommendation:** the owner answers items 4 to 6 of F6 (rounding level and rule; whether brokerage has a cap and is per order; any flat per-order fee; the DP amount and whether it includes GST); until he does, the sheet is `unchecked`, a flat per-order fee other than the brokerage stays a stated limit and the DP charge is one flat figure per sale.
4. **Is the split accepted?** **Recommendation:** yes (recommended, the owner confirms): P3-03c is the pure half at about 2.3 agent-days, this slice the half that needs his sheet at about 1.6, together 3.8 (the first draft said 3.6).

**Decisions this draft takes (not questions; the owner may revert):** a required, closed `CostChoice` instead of an optional member with a runtime refusal (a forgotten call site is a compile error); one error code for a bad choice (`simulation.invalid`); the widening of the settings value to 8,000 rather than a row per schedule; the actor `cli:cost-sheet` and no audit event; the check reads the original files, not the stored transactions; `load --replace`; the 64 KB file cap; the check never writes `checked`.

## Risks
- **The sheet is late or partly known.** The exit check, the cost property of P3-08 and P3-09's net figures wait; real runs stay `--gross` and say so. Mitigation: P3-03c is complete without it.
- **The verbs conflict with P3-04b2's host.** Mitigation: the dispatcher test table of both slices includes both verbs; whichever merges second adopts the other's host; the script resolves paths itself.
- **The check's classification is a heuristic** (a one-sided bill with brokerage 0 is delivery; a two-sided bill is intraday): rows that fit neither are listed, not compared, and the implied rates carry their limits; a wrong class would show as a large difference, not hide.
- **Personal data in the report files.** The check prints no identifier; sentinel tests guard it.
- **A shared column is widened.** Additive; the owner module of each key still validates its values; the migration test.
- **A slipped unit or an old rate** passes the nets; the check against bills is the guard, and the label says `not checked against bills` until `checked` is present.
- **Merge conflicts** with P3-03c (the request and the handler are new here, but the record is P3-03c's) and with P3-04b2 (the dispatcher, the host, the parser table); the merge order and the join tests are the net.

**Deviations and readings (where the spec was ambiguous).**
- **A negative Oth. cell.** The spec says the cell "is listed under *adjustments* ... and left out of the pass count". It was read as: **the whole row** is an adjustment row, counted with its sum of negative cells and not compared, classed or used for implied rates. If the owner's reports carry a negative Oth. cell on many rows, the check would compare few rows; the alternative (compare the six lines of such a row and leave only the cell out) is a small change in `CostBillCheck.Run` and a decision for the owner once he has run it on his files.
- **`test-` ids.** The handler answers `simulation.cost_sheet_not_found` for a `test-` id **without asking the store**, so "the sheet store is read once per run" holds for sheet choices that can exist; the store also never finds one.
- **Unclassified rows:** a one-sided row whose exchange is not NSE, a one-sided row with brokerage while the sheet's delivery brokerage is 0, any one-sided row while the sheet charges delivery brokerage, and a date before the first schedule are listed (date and reason) and not compared. The spec named the first and the second cases only for delivery; the third is the "no guessing" rule applied to a sheet with delivery brokerage.
- **Implied GST** is a percent of the row's brokerage, SEBI and transaction cells (the spec's "line / value" is meaningless for GST); STT of an intraday row is on its sell value and stamp duty on the buy value; stated in the output.
- **Two existing architecture rules were narrowed** (the port list of `Abstractions.Research` has a third member; the "adapter does no I/O" rule of `Infrastructure.Research` excludes `CostSheetStore`): see ADR 0044. No rule was removed.
- **`CostChoice` case constructors are internal**, not private (an abstract base with a private constructor already closes the type).
- **The verb's namespace is `XDrishti.Api.CostSheets`** (folder `CostSheet`): a namespace `CostSheet` would hide the Domain type.
- **Tests that build a `simulate` command line** (`FakeVerb`) add `--gross` when a line names neither choice, because those tests are about other flags; `FakeVerb.RunRawAsync` and the cost-flag tests send a line as it is.
- **Size.** Not re-measured; the work was done in one session.
