# CF-04e — History API routes and card

- **Status:** Approved (coordinator's recommendation under the owner's standing instruction of 2026-11-11; every decision as recommended). Decisions taken: D1 to D9 below.
- **Phase / roadmap row:** CF programme, row CF-04e (P1 data / UI)
- **Design refs:** [CF-04](CF-04-history-backfill-to-five-years-daily-bhavcopy-and-corporate-actions.md) Contract "API" and "UI", AC 1, 5, 17, "Part B as built" · ADR 0270 (backfill), 0271 (depth lines), 0130 (owner-act forms), 0091 (fresh password per change) · docs/design/05-data-and-brokers.md §6.1
- **Needs:** CF-04 Part B (built, ADR 0270). **Independent of CF-04d** (source-aware replay, specced in parallel): CF-04e touches no replay code and never `SeamAwareBars.cs` or `SourceAwareFactors.cs`.
- **Size:** about 2 agent-days (backend read model, two routes, error mapping, audit 0.8; Data "History" tab 0.7; HTTP integration + Vitest/MSW tests 0.5).
- **Safety:** **YES.** An owner act starts network fetches (Dhan `/v2/charts/intraday`). Both routes stay refused while `Data:History:Backfill:Enabled` is OFF, and this slice gives no way to turn it on.

## Goal
The owner sees, on the Data screen, how deep the history of every tracked instrument is and where the 1-minute backfill stands (chunks, probe, seam), and can start the backfill or the seam probe from the web as a password-confirmed owner act — which, today, answers "off" because the switch stays OFF until CF-04d.

## Decisions (each as recommended)
- **D1 Switch read-only.** The card shows `Data:History:Backfill:Enabled` and why it is off; **no PUT route** in CF-04e. Reason: the owner's decision of 2026-11-11 (OFF until CF-04d is built), and the switch is deployment config, so an owner-act switch needs a stored switch layered under the flag (as P14-03, about +1 d) — a follow-up after CF-04d. *(Deviation from the roadmap wording "the switch as an owner act", recorded.)*
- **D2 Status codes.** 422 for `history.disabled`, `history.disk_low`, `history.calendar_missing`, `history.outside_window` (refusals with a reason, as the spec); 409 `history.run_active`; 404 `history.no_target`; the existing 409 `data.dhan_not_available` / `data.dhan_not_connected`. Done by a code-based branch in `ProblemResults` (Api only); the handlers and CLI exit codes are unchanged.
- **D3 Auth.** Fresh password for each act (`OwnerAct.FreshAsync`, ADR 0091/0130), CSRF, session; actor from the session; the sign-in rate limit (`LoginRateLimitPolicy`). Not the 5-minute step-up window: this act starts external fetches.
- **D4 Backfill runs as the service.** `POST .../backfill` checks in this order (ADR 0130: the switch FIRST, so an act that is off neither counts toward the sign-in lockout nor says anything about the password): session → switch (422 disabled) → fresh password → run active (409) → run window (422 outside_window) → `RunBackfillCommand(DryRun: true)` (calendar, disk; zero requests) → starts `history-backfill` through `RunServiceNowCommand` (manual trigger, background, run record, AU-12 sees the planned chunks). 202 with the run; 200 `started: false` when nothing is pending. Whole set only (one instrument stays a CLI act).
- **D5 Probe synchronous.** `POST .../probe` runs `ProbeSeamCommand` in the request (bounded: one request per chosen instrument), same order as D4 without the dry run, 200 with counts and lines. One probe at a time per process (409 `history.run_active`), and refused while the backfill service runs.
- **D6 Audit counts only.** New `AccountEventType.HistoryBackfillStarted` and `HistorySeamProbed`; detail e.g. `pending=23 estimatedRequests=23 runId=…` / `probed=20 passed=18 unresolved=1 noOverlap=1 failed=0 requests=20`, or `refused=<code>`. Audited only after the password passed (an OFF refusal comes before it and writes no row). No symbol list, no prices, no URL, no token.
- **D7 Read model as a new query.** `GetHistoryOverviewQuery` in a new file beside `ShowHistoryHandler` (CLI output unchanged), reusing `IFetchTargets`, `IBackfillStore`, `HistoryDepth` buckets and the coverage read that serves `firstBar` on `GET /api/data/instruments` (`historyFrom`). Daily (Part A) is reported as one span in the totals, not per instrument. No paging (tracked set ≤ about 500).
- **D8 Where the card lives.** A **"History" tab on the Data screen** (`?tab=history`, lazy chunk like Filings). The Services screen is unchanged: it already has the `history-backfill` card, and its "History" means run history.
- **D9 Window applies to both acts.** Outside `Backfill:RunWindow` both routes refuse 422 `history.outside_window` and name the next window start, instead of a silent skipped run.

## Scope
**In:** `GET /api/data/history`; `POST /api/data/history/backfill`; `POST /api/data/history/probe`; ProblemResults mapping; two audit event types; `ProblemDetailsSchema` code list; `scripts/gen-api.sh`; the Data "History" tab; tests.
**Out:** turning the switch on (D1); per-instrument backfill from the web; cancelling a run (Services already pauses); dry-run estimate on the web; the replay / `SeamAwareBars` / `SourceAwareFactors` (CF-04d); Services "Run now" password (risk 2); Data quality weekly `seam_jump` list.

## Acceptance criteria
1. **OFF refuses, zero calls.** With `Backfill:Enabled = false` (default), with a correct, a wrong or no password, both POSTs answer **422 `history.disabled`**; a counting `HttpMessageHandler` on the Dhan client records **0** calls; no `backfill_chunks`/`backfill_seams` row changes; no service run is started (run count unchanged); the password is not checked (failed sign-in count unchanged) and no audit row is written.
2. **Password after the switch** (switch ON): no session → 401; no password → 403 `auth.step_up_required` (nothing counted); wrong password → 401 `auth.invalid_credentials` (sign-in lockout → 423 `auth.locked`); every later check (409, 422 window/disk/calendar) runs only after the password passed. Missing CSRF → 403 `auth.csrf_invalid`.
3. **Run active.** Switch ON (test config), a `history-backfill` run in status `running`: backfill and probe POST → **409 `history.run_active`**, 0 Dhan calls. Two concurrent probe POSTs: exactly one 200, one 409.
4. **Window.** Clock 14:00 IST, window `20:00-06:00` → 422 `history.outside_window`, message names 20:00; clock 21:00 → passes this check; 05:59 passes, 06:00 refuses.
5. **Disk and calendar.** Fake free disk 6.97 GB for the 58,181,250-row estimate (needs 6.98 GB at 60 B × 2) → **422 `history.disk_low`** with both numbers; a planned range with 3 weekdays missing from Part A's ledger → **422 `history.calendar_missing`** naming the range and `3`. Both: 0 Dhan calls, no service run.
6. **Start.** Switch ON, in window, checks pass, 23 chunks pending → **202** `{ started: true, runId, chunksPending: 23, estimatedRequests: 23, estimatedRows }` with `Location` of the service run; a service run with trigger `manual` exists. With 0 pending → **200** `started: false`, no run.
7. **Probe.** Switch ON, fake source, 3 instruments (2 pass, 1 at 0.2× unadjusted) → 200 `{ probed: 3, passed: 2, unresolved: 1, noOverlap: 0, failed: 0, requests: 3, lines[3] }`; `market.bars_1m` row count and hash unchanged (CF-04 AC 10).
8. **Audit counts only.** Every audited detail matches `^[a-z_=0-9 .\-]+$` with no symbol, price, URL or token; length ≤ the column's max.
9. **GET shape.** Seeded: 4 instruments in states `done` (10/10 chunks), `partial` (4 done, 1 failed of 10), `seam_unresolved`, `seam_jump` (jumpPct 32.0) → each row carries `historyFrom`, `firstCsvBar`, `backfillStatus`, `chunks {done, failed, total}`, `probe {status, at, medianBps, withinMaxPct}`, `seamJumpPct`; totals `byStatus` sum to 4; depth buckets match `HistoryDepth`; `switch { enabled: false, editable: false, reason }`; `runWindow "20:00-06:00"`, `running`. Rows sorted by symbol (ordinal). GET needs a session, no password, makes 0 Dhan calls, `Cache-Control: no-store`.
10. **Card states.** Loading (`LoadingState`), error with retry (`ErrorState`), empty ("No tracked instrument has CSV bars yet." when 0 rows), OFF banner ("The 1-minute backfill is off. It stays off until source-aware replay (CF-04d) is built.") with **both buttons disabled** and the reason as their description; `seam_jump` and `seam_unresolved` rows show a text chip (not colour only) and the jump % / probe result; partial rows show a progress bar `done/total` with the failed count. Honest limits of CF-04 are printed under the table.
11. **Owner act in the UI** (switch ON fixture): button opens the password dialog; 422/409 problems show their message in the dialog; 202 shows "Backfill started" with a link to the Services run; the password field is cleared on close.
12. **Responsive and budget.** At 360 px no horizontal page scroll (the table scrolls inside or collapses to cards); the History tab is a separate lazy chunk; `npm run size` stays ≤ **200 KB gzip** with no eager additions beyond the tab name.
13. `scripts/gen-api.sh` clean; architecture tests green; no file of CF-04d changed (`SeamAwareBars.cs`, `SourceAwareFactors.cs`, replay code untouched).

## Contract
- **Auth:** session cookie + CSRF on all three; the two POSTs need `password` in the body (D3), rate limit `LoginRateLimitPolicy`; responses `Cache-Control: no-store`. Request bodies ≤ 1 KB (global limit applies).
- `GET /api/data/history` (`GetDataHistory`) → `{ switch: { enabled, editable: false, reason }, runWindow, inWindow, running, serviceId: "history-backfill", daily: { from, to } | null, totals: { instruments, byStatus: { none, planned, partial, done, seam_unresolved, seam_jump }, chunks: { done, failed, total }, depth: { under2, from2to3, from3to5, from5 } }, instruments: [ { instrumentId, symbol, historyFrom, firstCsvBar, backfillStatus, chunks: { done, failed, total }, probe: { status: none|passed|unresolved, at, medianBps, withinMaxPct }, seamJumpPct } ] }`.
- `POST /api/data/history/backfill` (`StartHistoryBackfill`) body `{ password }` → 202 `{ started: true, runId, chunksPending, estimatedRows, estimatedRequests, estimatedMinutes, text }` | 200 `{ started: false, … }`; errors 401, 403, 423, 429, 422 `history.disabled|disk_low|calendar_missing|outside_window`, 409 `history.run_active|data.dhan_not_available|data.dhan_not_connected`, 404 `history.no_target`.
- `POST /api/data/history/probe` (`ProbeHistorySeam`) body `{ password }` → 200 `{ probed, passed, unresolved, noOverlap, failed, requests, lines[] }`; same errors less `disk_low|calendar_missing`.
- **Settings:** none new; reads `Data:History:Backfill:Enabled`, `Backfill:RunWindow`, `Probe:*`.
- **Data:** no migration (two `AccountEventType` text values).
- **UI:** Data screen tab "History" (`?tab=history`), lazy; components under `frontend/src/features/data/components/history/`.

## Risks
1. **Switch turned on by deployment before CF-04d** (Keychain/compose edit): the routes would then fetch. Mitigation: the card says so; ADR 0270 owner act forbids it; CF-04d gates trust anyway (pre-seam bars stay out of every run).
2. **Services "Run now" needs no password** for `history-backfill` (fact 4), so the password on the new route is not the only door. Safe while OFF; follow-up after CF-04d: route `history-backfill` Run now through the same owner act.
3. **A CLI run is invisible to `history.run_active`** (fact 5): two runs could overlap. The chunk ledger is idempotent (CF-04 AC 6); the owner should not run both.
4. A large probe (many instruments with actions) can take minutes in one request; the card shows a spinner, the request has no client timeout.

## Shortcuts (accepted)
- No owner-act switch (D1); no web dry run; no per-instrument start; no cancel route; probe in the request (D5); daily span as one total (D7); no paging.
