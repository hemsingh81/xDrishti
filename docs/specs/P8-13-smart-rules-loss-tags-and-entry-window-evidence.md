## Goal
Show, for each smart rule and for the losses, what the stored records actually say and where they say nothing: how often each rule ran, was unavailable or moved a candidate on the stored plans; why trades lost (tag counts, R lost, growing tags) on the report population; what the entry-window and meta-labelling studies concluded when someone stored them; and for everything with no source, `not_evaluable` with the reason and the verb that would produce it.

## Scope
**In:** the **spike** (below); `GET /api/learning/smart-rules`, `GET /api/learning/loss-tags`, `GET /api/learning/entry-windows`, `GET /api/learning/meta-policy`; `--store` on `xd learn windows` and `xd learn policy` (kinds `entry_windows`, `meta_policy` in `learning_reports`); the extension of `CellLossTags` with R lost per tag; the **Smart rules** and **Loss tags** tabs of `/learning`.
**Out:** computing entry windows or the meta policy on a GET (they fit models over folds: jobs), applying a window, a threshold or a size multiplier (never automatic, ADR 0075/0069; the owner's act later), regime-based tags and gate evidence by VIX/breadth bucket (no context data until P3-01d/e), news/results tags (P15), execution gap and decision drag (P10/P11), a switch to turn a rule off, correlation matrices (needs the 60-day return table from the plan context; shown as a count of pairs checked and unavailable, not a matrix).

## The spike (first, 0.5 d, written into the ADR before any endpoint)
Question list, each answered from the owner's database and the code, with the number or the quote:
- **S1. What the stored plans say.** Count `trading.plans`, `plan_items` by group, and the distinct codes in `plan_items.reasons` and `plan_items.unavailable` (verified names from `SelectionPlanBuilder`: reserve reasons `gate_no_trade`, `gate_reduced_cut`, `same_bet_better_ticket`, `same_bet_open_trade`; flag codes `gate_*`, `throttle_*`, `correlation_*`, `rule_removed_half` in `Domain/Selection/SmartRules/SmartRuleCodes`). Fact to settle: does a plan row alone prove that a rule **ran** (as opposed to being unavailable)? If not, the "ran on N plans" column is `unavailable` and only "unavailable on N" and "moved K" are shown.
- **S2. Loss-tag cost.** Time `AnalyzeLossTagsHandler` on the owner's newest runs and on a synthetic 500,000-trade run (p50/p95 of five runs). Rule: p95 under 1 s means compute on read; otherwise the loss-tags view is stored as kind `loss_tags` by `xd learn loss-tags --store` (extra 0.5 d, same table) and the endpoint reads the newest.
- **S3. Champion and trainer.** Is there a champion model (`/api/models`)? If none (ADR 0080 said none), the meta-policy view is `not_evaluable: no champion` computed from the registry without running anything, and `--store` for it is built but untestable on real data.
- **S4. Entry-window cost and result.** Run `xd learn windows` once on the owner's data; record time and outcome (`not enough evidence` is likely at about 3 folds, ADR 0069).
- **S5. Run labels.** How P8-06 attaches style and exit to a run (the `CellSource` triple is how the verbs do it). Loss tags need `RunKey:Style:Exit`; reuse P8-06's run-set resolver verbatim, no second rule.
Outcomes and fallbacks: S1 no plans stored (likely: ADR 0097 found none published) -> the Smart rules tab ships with `empty` and the seeded fixture proves the layout; S2 slow -> store; S3 no champion -> as above; S4 slow (over 60 s) -> `--store` only, no change to the endpoint design; S5 unresolved -> loss tags take explicit `run=KEY:STYLE:EXIT` query parameters only and the tab says "choose runs" with the Data used picker of P8-08.

## Acceptance criteria
1. Given stored plans, when `GET /api/learning/smart-rules?plans=30` is called, then it returns per rule (gate, throttle, meta-labelling, entry windows, correlation) the plans read, plans on which the rule was unavailable (a code ending `_unavailable` or `correlation_partial` counted separately), candidates it moved to reserve (by reserve reason) and, per rule, an `outcome` metric that is `not_evaluable` with its reason and the verb when its evidence needs what does not exist (gate: VIX and breadth buckets need market context; throttle: real taken trades; meta: a champion and a stored policy; windows: a stored study; correlation: the pair table); no rule row ever shows a number for an outcome that is not computed. *`SmartRulesViewBuilderTests`, `SmartRulesApiTests`.*
2. Given a plan where a rule removed half or more of the candidates it saw (`rule_removed_half`), then the row says "flagged for review" (doc 09 §14) with the plan id and date; given none, no flag text. *`SmartRulesViewBuilderTests`.*
3. Given no plan stored, then `rules[]` has the five rows with state `empty`, "no plan stored yet (the nightly service is paused until the owner starts it)", and no digit. *`SmartRulesTab.test.tsx`.*
4. Given `plans` outside 1 to 60, then 422 `learning.invalid`. Same for an unknown `run` triple or a bad run key on loss tags (`reports.invalid` family: use `learning.invalid`, the module's code).
5. Given the report population (default of P8-06, or `run=KEY:STYLE:EXIT` repeated, 1 to 50), when `GET /api/learning/loss-tags` is called, then the answer holds trades read, losses, per cell the loss count, untagged count, counts per tag, **R lost per tag** (sum of negative R of the losing trades carrying the tag; tags overlap, so per-tag sums exceed the total, said in `limits`), the growing tags with the share now and before, the worst losses with their tags, the number of comparisons and the expected chance flags, the "not built" list verbatim from `LossTagReport.NotBuilt`, and the `Evidence` block. Two runs of one strategy over overlapping windows are refused as in P8-06 (`reports.run_overlap` is returned as the shared code). *`LossTagsViewBuilderTests`, `LossTagsApiTests`.*
6. Given hand trades (a gap through the stop of -1.8 R, a quick stop of -1.0 R, a normal-variance loss of -0.6 R carrying no other tag), then counts per tag, R lost per tag (-1.8; -1.0; -0.6) and the untagged count equal the table; a cost-only loss is untagged; the extension of `CellLossTags` changes no existing tag count (the existing P6-15 tests pass unchanged). *`LossTagAnalyzerTests` (existing) plus `LostRTests`.*
7. Given a cell with fewer than 60 losses, then "growing tag" is `not_evaluable: needs 60 losses (two windows of 30)` and its tag counts still show with n; a tag share is drawn with n beside it; a cell below the cell minimum is `insufficient`. *`LossTagsTab.test.tsx`.*
8. Given a stored entry-window study, when `GET /api/learning/entry-windows` is called, then it returns the newest (or `id`) with options, rows, range, used folds, per cell the status, the window as HH:mm to HH:mm, window trades and share kept, shrunk rate against the cell rate, lift, mean R inside and outside, folds held of evaluable and required, pooled out-of-sample lift, the reasons, the limits text and the `Evidence`; a proposal drawn with status other than `proposed` is labelled by its status (not enough evidence, no stable window, inconclusive); none stored is 404 `learning.entry_windows_not_found` and the tab shows `empty` with the command. Same shape for `GET /api/learning/meta-policy` (outcome, reasons, folds, pooled and recent totals with kept and skipped counts and mean R, the per-group thresholds, limits). *`ReportKindsApiTests`.*
9. Given `xd learn windows --store` or `xd learn policy --store`, then the report is stored once per distinct input hash (same pattern as P8-12: kind, sources, options, hold-out, training set, trainer recipe, champion id for the policy), the verb prints `stored as #N` or `already stored as #N`, and a `NoPolicy` outcome is stored like any other (it is a result). *`StoreLearningReportHandlerTests`.*
10. Given the feature folder, then GET only, no mutation import, server text rendered as text; the tabs show the `EvidenceBlock`, each number through the analytics kit and each chart with its table. *D6 test, markup test.*
11. Given the spike's outcomes, then each is recorded in the ADR with the number, and the endpoint set built matches the fallback table above. *ADR review, reviewer.*

## Non-functional
Smart rules: one read of the newest 60 plans' items (counts only): p95 under 300 ms on 60 plans of 40 items. Loss tags: p95 under 1 s on the seeded fixture and measured on 500,000 synthetic trades (S2 decides compute or store); no more than one page of `worst` (25). Memory: streamed rows, one pass. Security: GET only; no account number, no free text from a trader (symbols and codes only); logs carry counts and milliseconds.

## Decisions (researched)
1. **Stored for the heavy, computed on read for the cheap.** Entry windows (re-learn per fold) and the meta policy (re-fit per fold) are model fits: stored by the owner's verb into the P8-12 table, read by GET. Loss tags are a single pass of pure rules (ADR 0071: "pure rules over the closed trade") and the report engine already reads the same population: computed on read, bounded, unless S2 says otherwise. Alternative rejected: compute everything on read (hidden jobs on a GET, P8-00 D6); store everything (adds a stale-copy problem for the cheap one).
2. **Smart-rule evidence from the plan rows, with codes as the fallback.** The plan stores reserve reasons and unavailable codes per item (verified in `SelectionPlanBuilder`: `Applied(flagCodes, …)` puts the smart flag codes in `unavailable`); P8-14 adds structured flags. The tab reads `PlanView.flags` when present and the item codes otherwise, and says which. Rejected: matching the free-text `basis` (the fragility P8-14 removes).
3. **R35's outcome columns are `not_evaluable` today, by design.** "Equity with and without the throttle" needs real taken trades (none: P10/P11); "R by VIX/breadth bucket" needs market context (P3-01d/e not built); "R taken versus skipped" needs a champion; "R by entry hour" is P8-10's calendar report and is linked, not duplicated; a correlation matrix needs the 60-day return table at plan time. Printing these as states, with the command that will fill them, is the honest answer; inventing a proxy is not.
4. **R lost per tag is added to `CellLossTags`** rather than recomputed in the browser: the browser computes no statistic (P8-00), and the analyzer has the R of each tagged loss. Appending a field to a positional record is the smallest change; `RuleVersion` stays `lt-2` because no rule changes.
5. **Tags overlap:** shown as counts and R lost per tag, never as shares that sum to 100%; the share is "of the cell's losses", with n.
6. **No switch to turn a rule off in this slice.** Doc 09 §14 says switching off needs a password; that is a write from the UI (P8-00 Q2: not in P8). The tab points to the settings keys the owner already uses.
7. **A `NoPolicy` / "not enough evidence" result is stored and shown** like a finding: it is the likely answer on 2.1 years (ADR 0075/0069) and hiding it would read as "never run".
8. Sources: repo only (ADR 0069, 0071, 0075, 0085, 0092, 0099; specs P6-13/14/15, P7-06, P8-05).

## Risks and honest limits
- On the owner's machine the first view is mostly empty: no plan published (ADR 0097), no champion, no stored study, no context data. That is the correct display; the seeded fixtures prove the layouts.
- Loss tags describe, they do not explain (ADR 0071); thresholds are judgement defaults; MAE/MFE are whole-trade so event order inside a trade is unknown; growing-tag flags are expected by chance (the expected count is printed).
- Entry windows and the meta policy are optimistic where chosen on all development scores (ADR 0069/0075); only fold figures are out of sample; the screen shows the fold figures first.
- Counting codes on plan rows measures what the plan recorded, not what a rule would have done had its input existed.
- Many comparisons across cells: the printed chance-flag count is part of every loss-tag answer.
