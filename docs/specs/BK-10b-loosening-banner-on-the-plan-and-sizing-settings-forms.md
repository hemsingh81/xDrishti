No frontend form calls the three PUTs today (only `schema.d.ts` names them).
- **Size:** 2.5 agent-days (read-side banner and dismissal store 0.8, auto setting 0.5, plan screen banner 0.4, the three settings forms 0.5, tests 0.3)
- **Safety:** **yes (SAFETY, display of a loosening).** The slice changes no quantity, limit, gate input or plan row; it only shows, and lets the owner hide, the fact that a limit was loosened. Hiding a warning is the less safe direction, so: the banner shows every loosening until it is dismissed, a dismissal is insert-only and audited, the automatic dismissal is OFF by default and switched only by the owner with a fresh password, and it is recorded as `auto` with the setting snapshot (never as the owner). No order; no setting change by any rule, job, model or assistant.

## Goal
After the owner loosens a sizing limit, a basket budget, the cluster cap or the gate breadth source, the plan screen says so, with the old and new value, on every plan built after the change until the owner dismisses it; and the owner can make those changes from forms instead of raw API calls.

## Scope
**In:** (1) a pure `LooseningNotices` rule (which loosenings show on a plan); (2) an insert-only dismissal table and its handler; (3) the read-side banner on the plan view, never written into the stored plan; (4) the automatic dismissal setting `plans.loosening_banner.auto_dismiss` (default OFF); (5) the plan screen banner with a Dismiss control; (6) owner-act forms for the sizing settings, the basket risk budgets and the basket settings (P8-19 pattern); (7) tests; ADR.
**Out:** any change to how a setting is changed, validated or directed (BK-10/BK-08 own that); a banner for a `tighten` change; snooze; writing the banner into `trading.plans.basis` or `basis_flags_json`; a bell notice (follow-up if wanted); any order or order-shaped field.

## Definitions
- **Loosening:** a stored row with `direction = 'loosen'` in `selection.sizing_settings_changes`, `selection.basket_risk_budgets` or `selection.basket_settings_changes`. The direction is the one BK-10 (build notes: raising `sizing.vol_target.floor`, lowering `sizing.budget.min_fit`, disabling vol target or capacity, raising `sizing.capacity.pct`, raising or removing a budget) and BK-08 (raising or clearing `selection.max_cluster_risk_pct`, raising `selection.cluster_rho`, any change of `gate.breadth_source`) already record. This slice never recomputes a direction.
- **Notice id:** `sizing:{id}`, `budget:{id}` or `basket:{id}` (the change row id).
- **Shown on a plan:** a loosening whose `changed_at` is at or before the plan's `created_at` and that has no dismissal row recorded at or before the time of the read.

## Acceptance criteria
1. **Every loosening shows.** Given three `loosen` rows (one sizing, one budget, one basket setting) changed before a plan was built and no dismissal, when `GET /api/plans/{id}` is read, then `loosenings` holds three items, oldest first, each with notice id, source (`sizing`, `budget`, `basket`), key (for a budget the basket id and name), old value, new value, actor, changed at, and the sentence "Loosened since <date>: <key> <old> → <new> (by <actor>)."; a `tighten` row never appears.
2. **Next plan onward.** A loosening changed after a plan's `created_at` does not appear on that plan; it appears on the next plan built after it and on every later plan until dismissed.
3. **Plan hash unchanged (OFF identity).** Given no loosening (or every loosening dismissed), the plan built is byte-identical to a builder without this slice, `input_hash` included (the test pattern of `ClusterPlanTests.With_the_cap_off_the_plan_and_its_hash_are_identical_to_a_builder_without_the_port_even_with_other_settings_stored` and `SizingPlanTests.With_no_stored_setting_and_no_budget_the_plan_is_byte_identical_to_a_builder_without_the_port`). Given a loosening, the stored plan and its hash are **also** unchanged: the banner is computed on read and never enters `basis`, `basis_flags_json` or `input_hash` (otherwise a dismissal before a build would change a plan's hash).
4. **Dismissal is an insert-only owner act.** `POST /api/plans/loosenings/{noticeId}/dismiss` needs a session and the CSRF token; the actor is the session's owner (`owner:<email>`, as `TicketAlertsEndpoints.OwnerActor`; nothing from the body names it); no password, because the existing dismiss (`DismissPlanAlert`, P7-20) takes none. It appends one row to `trading.loosening_dismissals`, writes one account event `LooseningDismissed` (notice id, source, key, actor; after the row, a failure logged, as BK-10's `SizingChanged`) and answers 204. A second dismiss of the same notice adds nothing and answers 204. Malformed id 422 `plans.invalid`; unknown id 404 `plans.not_found`; id of a `tighten` row 422 `plans.invalid`; no session 401.
5. **Dismissed is gone everywhere, from then on.** After a dismissal the loosening is absent from `loosenings` of every plan read later, older plans included (a dismissal is of the change, not of one plan); the change row is never edited.
6. **A newer loosening shows again.** Dismissing `sizing:7` does not hide a later `sizing:9` of the same key.
7. **Auto option, default OFF.** `plans.loosening_banner.auto_dismiss` (`Stored` descriptor, tier Advanced, safer direction `none`, not learnable, not on the ADR 0247 allow-list): no row = OFF. `PUT /api/plans/loosening-settings` needs a session, the CSRF token and a fresh password for every change, ON and OFF alike (403 `auth.step_up_required` without one, the ADR 0219 mechanism); insert-only history `trading.loosening_settings` (id drawn after an advisory lock; account event `LooseningSettingsChanged`). When ON, a loosening already shown on at least one published plan is dismissed at the build of the following plan with actor `auto`, the id of the setting row in force and its hash; never recorded as an owner. When OFF nothing is dismissed automatically. A database check refuses an `auto` row whose setting row is not the newest one or is OFF. A loosening never shown on a plan is never dismissed automatically.
8. **Plan screen banner.** On the plan detail a non-empty `loosenings` renders one `Alert severity="warning"` block "Limits loosened since the last plan" above the smart-rule `PlanBanner` (prototype: the bold-lead `.banner warn` of the plan page), one line per item with its sentence and a **Dismiss** button (`AlertNoticeControls` style); with the auto setting ON the block says "Automatic dismissal is ON: each line hides after one plan". Text only, React-escaped, never colour alone. Empty: nothing rendered. Read error: the plan still renders and the block says "Loosenings could not be read" (never silently empty). Failed dismiss: message, the line stays.
9. **Settings forms (owner acts, P8-19 pattern).** Three forms: sizing settings (`sizing.vol_target.enabled`, `sizing.vol_target.floor`, `sizing.capacity.enabled`, `sizing.capacity.pct`, `sizing.budget.min_fit`), basket risk budgets (one row per basket, 1 to 100 or off) and basket settings (`gate.breadth_source` `tracked` or a basket, `selection.max_cluster_risk_pct`, `selection.cluster_rho`). Each submits to the existing PUT with the password and the `expectedVersion` it read; 409 shows "changed elsewhere, reload"; 400/422 show the server's field messages; the current value and history (newest first) are shown; after a change recorded `loosen` the form says "This loosens a limit: it will be shown on the next plan until dismissed" (direction from the response; no client-side direction rule).
10. **No new path changes a limit.** Architecture test: no type of this slice calls a sizing, budget or basket-settings change handler; the auto dismissal reaches only the dismissal store; no type of this slice names an order, `upsize`, `leverage`, `margin` or `multiplier`.
11. **Performance.** Reading `loosenings` for one plan is one query over the three change tables and the dismissals, under 20 ms with 10,000 change rows on the fixture; plan build time unchanged with the setting OFF and under 2 % higher with it ON.

## Contract
- **Domain (pure):** `Domain/Planning/LooseningNotices.Shown(loosenings, dismissals, planCreatedAt)`, `LooseningNotices.AutoDismissible(...)`, `LooseningNoticeId.Parse`.
- **Application:** the plan read handlers add `Loosenings` from `ILooseningSource` (`direction = 'loosen'` only); `DismissLooseningCommand/Handler`; `ChangeLooseningSettingsCommand/Handler` (fresh password through the existing step-up check); the plan builder calls the auto dismissal after the plan is published, only with the setting ON, as a separate write (a failure is logged and leaves the banner shown: the safe side).
- **Data:** migration `AddLooseningDismissals` with `Down`: `trading.loosening_dismissals (id bigserial, notice_source text check in ('sizing','budget','basket'), notice_id bigint, actor text, setting_id bigint null, setting_hash text null, created_at timestamptz default now(), unique (notice_source, notice_id))`, check `(actor = 'auto') = (setting_id is not null)` plus the trigger of AC 7; `trading.loosening_settings (id, auto_dismiss bool, changed_by, changed_at, hash)`; insert and select only for `xd_app`; grants test updated. Raw SQL, as the other owner-act tables.
- **API:** `GET /api/plans/{id}` and plan list items gain `loosenings: LooseningView[]` (empty when none; contract snapshot updated); `POST /api/plans/loosenings/{noticeId}/dismiss`; `GET` and `PUT /api/plans/loosening-settings` (`{ autoDismiss, password, expectedVersion }`; 403 `auth.step_up_required`, 401/423 wrong password, 409 `plans.stale`); rate limit `PlanDecisionRateLimitPolicy`; `scripts/gen-api.sh` in the same change.
- **UI:** `frontend/src/features/plans/components/LooseningBanner.tsx` in `PlanDetail`; the forms under the feature folder that hosts the P8-19 owner-act forms (`owner-acts` or `settings`; UNVERIFIED which). States: loading, empty, error, dismissing.
- **Events/jobs:** none new; the auto dismissal runs inside the plan build. Log events: loosening dismissed (source, id, actor kind), auto-dismissal count; never values or passwords; next free event id block at build time.

## Non-functional
See AC 11. Session and CSRF on every write; fresh password for the auto setting; the password never logged or echoed.

## Test plan
- **Unit:** `LooseningNotices` for AC 1, 2, 5, 6; every notice id form; `AutoDismissible` (never shown → no; shown once and ON → yes; OFF → no).
- **Application (fakes):** listing and order; idempotent dismissal; `tighten` refused; auto rows carry `auto` and the setting row; OFF identity of AC 3 with and without a loosening.
- **Integration (Testcontainers):** the database refuses an `auto` row with a stale or OFF setting and a second row per notice; no UPDATE/DELETE grant; PUT refusals without a password.
- **Frontend (MSW):** banner, dismiss, failed dismiss, error; each form's success, 409, 422 and loosen message.
- **Architecture:** AC 10.

## Open questions

1. Should dismissing a loosening need a fresh password? The existing dismiss pattern (P7-20) takes none, so none is asked.
2. Is "auto hides each line after one plan" the automatic behaviour wanted for a warning? It stays OFF unless the owner switches it on.
