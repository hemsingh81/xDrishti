# P7-16b — Trade-tick recording: last-trade updates of the depth set recorded from the Data account, stored compressed, no trading use

- **Status:** Approved (owner, 2026-10-31, with the recommended answers: third socket accepted; own 12 GB cap plus the shared 20 GB free floor; own switch and service; when depth is off, ticks are recorded on a set built the same way)
- **Phase / roadmap row:** P7 — finding "P7-16b trade-tick recording" of [JOURNEY](JOURNEY.md) (extra slices table: "P13 aggressive-volume feature has no source", 2 days); companion of [P7-16](P7-16-depth-recording-service.md).
- **Design refs:** docs/design/20 §B ("aggressive volume delta"), 17 §1-2 (VM disk 120 GB, "revisit before tick data"), 16 (`feed_recorder`) · ADR 0024 (live feed), 0133 (allow-list rule), 0135 (depth recorder), 0091/0128 (fresh-password switch), 0083 (no order). New ADR: **next free number at build time**.
- **Needs:** P2-10, P7-16 (built). **Needed by:** P13-03 (`vol_delta_5m`, sole consumer; P13-00 R2 and D10).
- **Size:** 2 agent-days (estimate).
- **Safety:** **yes** — a third broker WebSocket with the Data account's token, continuous disk growth. Default OFF three times. No new allow-list entry, no order, no order-capable scope, no reader of the data.

## Goal
From the day the owner switches it on, every last-trade update Dhan sends for the day's depth set is stored (receipt time, exchange trade time, price, quantity, cumulative volume), compressed, append-only and bounded by its own size cap and the shared free-disk floor, so P13 can derive aggressive volume against the recorded book. Nothing in P7 to P12 reads it.

## Verified facts
**Dhan (read 2026-10-31):** https://dhanhq.co/docs/v2/live-market-feed/ — `wss://api-feed.dhan.co?version=2&token&clientId&authType=2`; **5 sockets per user, 5,000 instruments per socket, 100 per subscribe message**, a sixth socket drops the first (805); little endian; 8-byte header (code, int16 length, segment, int32 security id; **no sequence number**). Ticker (code 2, 16 B): LTP float32, LTT int32 epoch. **Quote (code 4, 50 B): LTP float32, last traded quantity int16, LTT int32 epoch, ATP float32, cumulative day volume int32, total sell qty, total buy qty, day OHLC.** Full (code 8, 162 B): the quote fields plus OI and 5 depth levels. The page calls the feed "tick-by-tick event based" but **each packet carries only the latest trade's fields; individual trades are not listed** and no update rate is stated. https://dhanhq.co/docs/v2/annexure/ — request codes 15/16 ticker, **17/18 quote**, 21/22 full; 805, 806 not subscribed, 807-809 token errors.
**Code (read 2026-10-31):** `DhanFeedPacketParser` already parses code 4 (LTP, LTT, volume, OHLC; **LTQ is not read**; volume read as int32 and nulled when <= 0); lengths 16/50/16 and stacked packets were OBSERVED on 2026-10-14. The live feed (`FeedConnectionManager`, one socket, `Live:MaxWsInstruments` 200) subscribes **its active set** only: holdings and armed tickets in Quote mode, alerts and indices in Ticker mode. The depth set (`DepthRecordingSet.Build`: armed, `Depth:PinnedSymbols`, liquid by turnover) is stored in `market.depth_session_instruments` and is deliberately **not** an active-set provider (P7-16 criterion 10). `DepthRecorderSupervisor.RecoverAsync` closes as `crashed` any past day with a stored depth set and no `depth_sessions` row, so **another writer to that table would forge depth crash rows**. Depth tables: `GrantTableToAppRole` + `MakeAppendOnlyForAppRole` for `xd_app` (the `xd-feed` role); `DepthDiskGuard.Check(stored, free, maxStored, minFree)` is a pure function.
**UNVERIFIED until the pilot:** packets per second per instrument and the share that carry a new trade; whether LTQ and volume are signed (read here as uint16 / uint32); whether LTT is UTC epoch or an IST-shifted epoch (a 19,800 s offset passes the parser's one-day skew check); whether one update can cover several trades (conflation); whether depth sockets count toward the same five.

## Scope
**In:** `TickRecorder`, `TickRecorderSupervisor`, service `tick-recorder` (second hosted loop beside the depth loop in `xd-feed`, heartbeat `xd-ticks`); pure `TickSampler` (change-only rule, flags, paise); `ITickStore` (COPY writer, size read, **no row read**); additive `LastQuantity` on `FeedPacket` (parser reads it; the live feed ignores it); migration `AddTickRecording`; the owner's switch (`market.tick_recorder_switch`, `GET`/`PUT /api/ticks/recorder`); options `Ticks:*`; fixtures; tests; ADR.
**Out:** any read of ticks (P13); Full packets; inferring the aggressor or storing a book; instruments outside the day's set; derivatives, BSE, indices; recording outside 09:15-15:30; backups, export, screen; deleting data; any change to the live feed's set, socket or parser behaviour; allow-list changes.

## Acceptance criteria
1. Given the allow-list, then `BrokerEndpoints` and `PlanPhaseCheck.PinnedAllowList` are **unchanged** (pinning test green): the recorder opens `wss://api-feed.dhan.co` through `DhanFeedConnector`, whose existing `IsAllowedWebSocket` check runs before the connection; it subscribes with request code 17 only, in messages of at most 100 instruments.
2. Given constructed quote frames (marked UNVERIFIED), the parser sets `LastQuantity` from bytes 13-14 read as uint16 and reads volume as uint32; existing parser tests and the live feed's mapping are unchanged (the live feed never reads `LastQuantity`).
3. Given a stream of quote packets for one instrument, the sampler writes a row **only when cumulative volume rose** since the last stored row of that instrument in this run; the first usable packet of a run and the first after a reconnect are written with flag `baseline` (bit0); a volume below the last stored sets `volume_down` (bit2) and is written; an LTT earlier than the last stored sets `ltt_back` (bit3); LTQ of 65,535 sets `ltq_capped` (bit1); a packet with unchanged volume is counted (`unchanged`) and not written; Ticker, PreviousClose and unknown codes are counted and ignored; prices become integer paise (half away from zero; float32 resolves a paisa only below ₹167,772.16; above it the paise value may be off by a few paise, which is accepted and stated in the ADR).
4. Each row holds `ts` (receive time), `rx_mono_ms` (monotonic ms since run start), `rx_seq` (per-run packet counter, the only order within a millisecond, because Dhan sends no sequence), `ltt_epoch` (raw int32 as sent, not converted), `ltp_px` (paise), `ltq`, `cum_vol`, `flags`. No aggressor, side, bid or ask is stored.
5. The set is today's `market.depth_session_instruments` if stored by the first look at or after 09:14:30; otherwise `DepthRecordingSet.Build` with the same `Depth:*` inputs. Either way it is copied into `market.tick_session_instruments` with `source in (depth_set, built)`, fixed for the day. The tick recorder **never writes a depth table** (test: with the depth recorder off and ticks on, the next day's depth recovery writes no `crashed` row).
6. Three gates, all default off: deployment `Ticks:Enabled` (`XD_TICKS_ENABLED`, default false), the owner's switch (newest row of `market.tick_recorder_switch`; no row = OFF), and service `tick-recorder` (registered paused). With any gate closed nothing reads credentials, builds a URL or opens a socket; an unreadable gate counts as closed. `PUT /api/ticks/recorder {enabled, reason, password}` follows P7-16 criterion 6 exactly (fresh password on every change, ON and OFF; `StepUpCommand` with `Elevate: false`; actor from the session; account event `TickRecorderSwitched`, category `service`; 401/423/400 `ticks.reason_invalid`); `GET` returns the switch, history and the not-running reasons. Window 09:14-15:31 IST on trading days; only rows with receive time 09:15:00 <= t < 15:30:00 India time are written.
7. Writes: `COPY`, one transaction per batch every `Ticks:FlushSeconds` (5); a failed batch is retried with the next; queue capped at 50,000 rows, rows unwritten for more than 30 s are dropped oldest first and counted; the receive loop never waits for the database.
8. Disk guard, before each start and every 5 minutes, with `DepthDiskGuard.Check`: `market.trade_ticks` stored size above `Ticks:MaxStoredGb` (12) ends the run `disk_budget`; free space below the **shared** floor `Depth:MinFreeGb` (20) ends it `disk_free`; warning at 80 %; stopped stays stopped until cleared and resumed; **the app never deletes data**.
9. Failure: reconnects with `ReconnectBackoff`/`ReconnectLimiter`, resubscribes the day's set, the hole counts in `tick_sessions.gap_seconds` and the first row after it is `baseline`, so the volume traded in the hole shows as one jump and is never attributed to one instant; more than 10 reconnects in 5 minutes pauses 5 minutes and raises the service-failure notice; 806 ends `not_subscribed`, 805 `flapping`, 807-809 wait for a changed token; one `market.tick_sessions` row per day when the day is over (ADR 0135 deviation rule; unclosed past day = `crashed`). The live feed and the depth recorder are unaffected in every case (own session, try/catch, heartbeat row).
10. Migration: `market.trade_ticks` is a 1-day-chunk hypertable, compressed after 2 days (segmentby `instrument_id`, orderby `ts, rx_seq`), no retention policy; `xd_app` can SELECT and INSERT but not UPDATE, DELETE or TRUNCATE on all four tables (grants test); `Down` drops them.
11. **Never on the trading path; no reader** (architecture test): the set is read-only inputs and not an `IActiveSetProvider`; `Domain`, `Simulation`, `Strategies*`, `Indicators`, `Application/Planning|Learning|Portfolio` and the live feed's code reference no `Tick*` recorder type or `trade_ticks`; `ITickStore` has no row-read method; no route reads ticks; no-order tripwire green. With the recorder failing, the pre-open check, arming, active set and live flush behave exactly as with it off.
12. Logs `ticks.connected|disconnected|subscribed|flush|dropped|disk_warning|disk_stop|token_refused|flapping` carry counts and ids only, never URL, token, client id, symbol or price.
13. **Pilot (owner-run, five real sessions, recorded in the ADR):** packets/s, stored rows per instrument-day, share of packets with a volume change, bytes per row and compression ratio replace the estimates in Decision 5; `median(ts - to_timestamp(ltt_epoch))` is within 5 s (else the LTT zone is IST-shifted and P13 converts with the offset); the sum of positive `cum_vol` steps per instrument-day matches the day volume of the EOD bar within 1 % on days without gaps.

## Contract
- **API:** `GET`/`PUT /api/ticks/recorder` (as `/api/depth/recorder`; `ApiJsonContext`, `scripts/gen-api.sh`; problem codes `ticks.reason_invalid`, `auth.invalid_credentials`, `auth.locked`). No screen; the Services row and heartbeat show the state.
- **Data (`AddTickRecording`, insert-only):** `market.trade_ticks(ts timestamptz, instrument_id uuid, rx_mono_ms int8, rx_seq int8, ltt_epoch int4, ltp_px int4 check > 0, ltq int4 check >= 0, cum_vol int8 check >= 0, flags int2 check between 0 and 15)`, all not null, no foreign key, index `(instrument_id, ts DESC)`, hypertable as criterion 10. `market.tick_session_instruments(session_date, instrument_id, source, reason, rank, pk (session_date, instrument_id))`. `market.tick_sessions(session_date pk, started_at, ended_at, end_reason in (window_end, paused, disk_budget, disk_free, token_refused, not_subscribed, flapping, crashed), instruments, packets, rows, unchanged, dropped_rows, gap_seconds, stored_bytes, note)`. `market.tick_recorder_switch` = `depth_recorder_switch` columns.
- **Settings (`Ticks:*`, ranges, `ValidateOnStart`, doc 16):** `Enabled` false; `FlushSeconds` 5 (1-30); `MaxStoredGb` 12 (1-500). The set and the free floor come from `Depth:*`. Service `tick-recorder`: window 09:14-15:31 IST, trading days, first start paused, retries 0, no catch-up, notify on failure.

## Decisions (researched)
1. **A second connection to the live-feed host, not the live feed's packets.** The live feed subscribes its active set (holdings, armed, alerts), not the depth set's pinned and liquid names; reusing it would make the recording set an active-set provider, put recorder work in the live receive loop and tie recording to `Live:MaxWsInstruments` cuts, which P7-16 criterion 10 forbids for depth. A separate socket on the already-allowed endpoint needs no allow-list change (ADR 0133 is not triggered: no new endpoint), reuses connector, parser and back-off, and fails alone. Cost: socket 3 of 5. Rejected: tapping `FeedConnectionManager`; recording inside the depth socket (depth packets carry no trades).
2. **Quote mode (code 17), not Full or Ticker.** Quote is the smallest packet with LTQ and cumulative volume; Ticker has neither; Full adds 5 levels the depth recorder already keeps at 20 and multiplies packets with book-only updates.
3. **Store per update, change-only on cumulative volume; Dhan gives no individual trades.** Each packet is the latest trade's fields, so several trades between updates collapse into one; the **volume delta between rows is the trade volume**, LTQ only the last print. Keeping the raw cumulative volume makes the sum exact even across conflation and gaps (the pilot checks it against the EOD bar). Rejected: every packet (book-only updates waste disk), rebuilding trades from depth (P13-00 D10).
4. **No aggressor stored.** P13 classifies each volume delta from `ltp_px` against the depth snapshot received at or before the row's receipt time minus the lag (at or above ask = buy, at or below bid = sell, else tick rule), so the rule can change without re-recording. Limits: depth is once a second and receipt-timed, conflated trades may mix sides; `vol_delta_5m` is an approximation and P13 says so.
5. **Budget (computed; rates and compression UNVERIFIED).** Row about 62 B data + 24 B tuple header + about 40 B index = **about 130 B raw**. Rate planning figure 2 stored rows/s per instrument (range 0.5 to 5): 22,500 s x 50 x 2 = **2.25 M rows a session = 0.29 GB raw**; x 248 sessions = **72 GB a year raw** (range 18 to 181). Narrow numeric columns with delta encoding compress well in Timescale; planning ratio **8:1 UNVERIFIED** (range 5:1 to 15:1) = **9 GB a year** (range at 2/s: 14 to 4.8 GB; worst case 5/s at 5:1 = 36 GB). Six months (124 sessions) about 4.5 GB; P13's 10 months about 7.5 GB. **Combined with depth** (38 GB a year at 5:1): about 47 GB a year; caps 40 + 12 = 52 GB. Free disk during two uncompressed days: depth 1.5 GB + ticks 0.6 GB plus WAL, inside the floor.
6. **Separate size cap, shared free-space floor.** One cap for both would let the bulkier depth table starve ticks (or the reverse) and blur which recorder stopped; the free floor protects the machine, so one value (`Depth:MinFreeGb` 20) for both is right and each recorder stops itself. `Ticks:MaxStoredGb` 12 covers a year at the planning figure. Consequence: the switch-on precondition rises from 60 to **72 GiB free** (52 GB caps + 20 floor), or the VM disk is enlarged.
7. **Same set as depth, own copy.** Ticks are only useful against the book of the same names; copying the stored depth set keeps the day's coverage self-contained; writing `depth_session_instruments` itself would forge depth `crashed` rows. If depth is off, the same builder yields the same names.
8. **Three gates, own switch and service, fresh password**, as ADR 0135 decision 2: the owner can run depth without ticks; a mis-click or stolen session must not open a socket or grow the disk. Rejected: riding on the depth switch (couples two independent decisions).
9. **Raw LTT, receipt time primary.** The LTT zone is unverified and has one-second resolution; storing the raw integer avoids baking a wrong conversion into a year of rows.

## Risks and honest limits
- Packet rate, conflation and compression are unknown until the pilot; at 5/s and 5:1 the 12 GB cap is hit after about four months: revisit the cap or the set size in the first month.
- Lost seconds are lost: gaps keep total volume (cumulative field) but not its timing. A trade above 65,535 shares capped in LTQ is still exact in the volume delta.
- No backup and only copy: `xd-backup`, when built, excludes `market.trade_ticks` data (`pg_dump --exclude-table-data`).
- Pilot queries: `SELECT hypertable_detailed_size('market.trade_ticks')`; `hypertable_compression_stats('market.trade_ticks')`; `SELECT instrument_id, count(*), max(cum_vol) FROM market.trade_ticks WHERE ts >= date_trunc('day', now()) GROUP BY 1`.
