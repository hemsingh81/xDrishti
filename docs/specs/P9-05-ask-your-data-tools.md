## Goal
The owner's questions about expectancy by basket, today's plan, a cell's evidence, the portfolio, a basket or an instrument are answered by tools that return the numbers the app itself computes, with the evidence and the honest state of each, in the envelope of P9-00, within the row, byte and time limits, with nothing from classes C0 reaching the model.

## Scope
**In:** eleven tools on `xd-mcp` (`get_report`, `list_runs`, `get_plan`, `get_cell`, `get_portfolio`, `get_basket`, `get_instrument`, `search_notes`, `get_learning`, `get_system_status`, `calc`) and one local tool in `xd-api` (`make_chart`); read ports and adapters; migration `AddAiToolAccess` (column grants for the report source, any extra `aiv` view); manifest entries; golden tests on a seeded database; the golden schema file of all 16 tools used by P9-03's budget test.
**Out:** a net-basis report (needs `platform.app_settings`; v1 is gross only), trades list (`run_sql` covers it), regime and event data (not stored), a write of any kind, bars at 1 minute, order-book data, Hermes' token (P9-10), the eval questions (P9-09), embeddings.

## Acceptance criteria
1. **Envelope and limits.** Every tool returns the P9-00 envelope through P9-02's runner; arguments are validated against the schema of P9-00 (`additionalProperties:false`, ranges, patterns); wrong input is `tool.invalid_arguments`; rows default 50, max 200; the 6,000-character cut and the redaction apply; a tool does not catch the runner's timeout.
2. **`get_report`.** Given the seeded fixture (Test plan) and `report=groups`, `query={runs: "A,B"}` then the result is the P8-06 `groups` view for that run set: each metric `{state, number, reason}`, a group's `n`, the evidence (`Population`, `Limits`, `UnavailableInputs`, `DataUsed`) copied into `evidence`; `report=what_works` with no cell above the minimum returns the engine's "nothing qualifies" answer as `ok:true` with its counts; a run set that mixes gross and costed gives `ok:false` with the code `reports.mixed_basis`; overlap `reports.run_overlap`; an unknown dimension `reports.invalid` naming the field; `query` keys outside the parser's whitelist, more than 12 keys, or a value over 200 characters is `tool.invalid_arguments`; a `basis=net` in `query` gives `reports.net_not_confirmed` (v1 is gross; the answer says "net is not offered by the assistant yet"). The tool computes nothing itself: a test compares its numbers with the handler's output for the same query.
3. **`list_runs`.** `kind=sim` returns the P8-06 `runs` view reduced to `runKey, strategyId, window, costed, universe label, labels, isExperimentCandidate`, the default run set marked, the left-out runs with their reason; `kind=lab` returns `aiv.lab_runs` newest first (`state`, `method`, `strategy`, `verdict` where stored), at most `limit` (1..20, default 10).
4. **`get_plan`.** Given a stored plan for the date (default: the newest `for_date`) then the tickets with symbol, side, state (the newest event), `pWinLower`, expected R, the stored reasons and `unavailable` list, the numeric levels when P7-19 stored them (else the text and `levels: not stored`), the grade and fill grade when they exist; given no plan for the date then state `empty` with the date; the account label appears only when `portfolio_context` is on (else `accountLabel: unavailable (portfolio context is off)`); a date in the wrong format is `tool.invalid_arguments`. The words "buy" and "sell" appear only as the stored side; nothing says "recommend".
5. **`get_cell`.** Given `key` or `strategy+timeframe+side` then one row per window (`all`, `250d`, `60d`) with `n`, `wins`, win rate, the stored posterior fields and the state (`insufficient` with `n` below 30, P8-00 D3); no cell -> `empty`; ambiguous selector -> up to 20 cells listed with their keys and `notes: ["narrow the selector"]`.
6. **`get_portfolio`.** Given `portfolio_context` on and the seeded holdings then totals and groups (`none`, `bucket`, `basket`, `sector`, `account`) with invested, value, unrealised and unrealised %, computed in the tool from the `aiv` rows with the same rounding as the Holdings screen; XIRR: the pure `Xirr` lives in `Application/Portfolio/Returns`, which `Domain/Assistant/PortfolioFigures` cannot reference, so the figures function lives in `Application/Assistant` (not Domain) and calls `Xirr` over the view rows; if that is not done, XIRR is `xirr: {state:"unavailable", reason:"not computed by the assistant"}`; a holding held under the minimum days gives `insufficient` (doc 19 `min_days_for_xirr`). Given the context off then `ok:true`, `data:null`, a metric-shaped `unavailable: portfolio context is off`, and no row read. Account appears as its label; no client id, no cash or funds figure exists in any output.
7. **`get_basket` / `get_instrument`.** `get_basket(name)`: members as of now (symbol, name as untrusted text), counts, whether each member is tracked; unknown name -> `table.unknown`-style `basket.unknown`. `get_instrument(symbol, bars)`: master facts (segment, sector, lot size if stored), `tracked`, coverage (first and last daily bar, count, gaps count from `aiv.quality_results`), the last `bars` daily bars; unknown symbol -> `instrument.unknown`; both honest about "members as of today" (limit) in `evidence.limits`.
8. **`search_notes`.** Given a query then up to `limit` hits from lessons, hypothesis rationales, strategy-version notes, suggestions and the owner-typed fields that exist (hypothesis rationales, strategy-version notes, price-alert notes; the journal has no free text, so there is no journal source), ranked by `ts_rank` over `to_tsvector('simple', text)` with `websearch_to_tsquery('simple', @q)` (parameterised, never concatenated); each hit `{source, id, date, text(<=300), untrusted:true}`; hits from the context-gated source are absent, not empty-looking, when the context is off, and `notes` says which sources were searched; a query of only stop characters is `tool.invalid_arguments`; text with instruction-like patterns is delivered escaped with `injection_flags` counted (P9-02 AC 7).
9. **`get_learning`.** `lessons|hypotheses|changelog|experiments|models` newest first, at most `limit`, optional `status`; fields are the stored ones; no state moves; model rows carry the version and role but never the model bytes.
10. **`get_system_status`.** Returns the newest daily bar date, the newest plan date and state, the last nightly run (state, started, finished), each service's last run state, and the count of data-quality results by status from the latest run, each with `asOf`; a missing piece is `unavailable` with the reason, not omitted. It is the tool the prompt tells the model to call before saying "today" or "latest".
11. **`calc`.** `0.1+0.2` -> `0.3`; `1/3` -> `0.3333` (default 4 places); `round(2.675, 2)` -> `2.68` (away from zero); `(0.8-0.6)*100` -> `20.0`; `abs(-3)`, `min(2,5)`, `max(2,5)`; division by zero -> `calc.divide_by_zero`; any identifier, `^`, `**`, a string, more than 50 tokens or 200 characters -> `calc.rejected`; the parser is a small recursive-descent over `decimal`, no evaluation of text by the runtime; the result is text so no double rounding happens.
12. **`make_chart` (local to `xd-api`).** Given earlier calls #1 (ok, columns `basket`, `expectancyR`) and `x:{1,"basket"}`, `y:[{1,"expectancyR","Expectancy (R)"}]` then a chart spec `{kind, title, series:[{callIndex, column, label}], points:n}` is returned and stored with the turn; an unknown or failed call, a missing column, a non-numeric y column, more than 200 points, more than 4 series, a title over 80 characters or markup in a label gives `chart.bad_reference` naming which; the tool takes no number from the model; the UI draws from the stored rows (P9-04).
13. **Grants and sources.** `xd_mcp_read` gets column-level `SELECT` on exactly the columns the P8-06 reader reads from `research.sim_runs`, `research.sim_trades`, `research.sim_comparisons` and `lab.strategies` (`ReportTradeSource` LEFT JOINs it for the strategy name) (the list is taken from the reader and asserted by a test that runs the real reader as `xd_mcp_read` against the fixture) and nothing else outside `aiv` and `ai.settings`; `xd_mcp_sql` is unchanged; the manifest test of P9-02 still passes with any new view.
14a. **Structured fields survive the scrubber.** `get_report` and `list_runs` return the 64-hex `runKey`, `get_cell` its key, `get_plan` plan and ticket ids, `get_portfolio` amounts of any size untouched with `redactions` 0 (positive test with a real run key and a paise amount over 9 digits); the grounding check and the citation chips need them intact.
14. **No C0 data.** A seeded broker secret, client id, e-mail and PAN-like note are never present in any output of any tool (property test over all tools on the seeded database: the serialised envelopes contain none of the seeded strings).
15. **Budget.** The golden schema file of all 16 tools (P9-02's four, these eleven, `make_chart`) estimates at most 2,200 tokens; descriptions are at most 40 words each; each `get_*` on the fixture answers in under 1 s p95 (30 calls).
16. `scripts/check.sh` green; log ids 6120 to 6159 unique; migration `AddAiToolAccess` with `Down`; the tool count and names listed by `tools/list` equal the contract.

## Non-functional
`get_report` p95 under 1 s on the 4,000-trade fixture and under the P8-06 budget on large stored runs (it shares the report cache; a cold large run is bounded by the 10 s tool timeout and answers `tool.timeout`, never a partial number); `get_portfolio` under 300 ms for 500 holdings; `search_notes` under 200 ms for 20,000 rows (sequential scan; an index is a follow-up if it measures slower); memory under 100 MB per call besides the report cache. Security: parameterised SQL only; the portfolio tool reads the context switch before any portfolio row; no tool accepts a column or table name from the model except as a whitelisted enum or a validated report dimension.

## Test plan
Fixtures with hand-worked numbers (builders, Testcontainers, seeded through the same stores as P8-06): **reports** run A (ORB, basket B1, gross): 40 trades, 24 at +2.0 R and 16 at -1.0 R -> n 40, win rate 0.60, expectancy +0.80 R, total +32.0 R, profit factor 48/16 = 3.00; run B as P8-06's fixture; **portfolio** holding X qty 10, average cost 100, last 110 (invested 1,000, value 1,100, unrealised +100, +10.00 %), holding Y qty 5, average 200, last 180 (invested 1,000, value 900, unrealised -100, -10.00 %): totals invested 2,000, value 2,000, unrealised 0, 0.00 %; **cell** n 50, wins 30 (rate 0.60), a second cell n 12 (`insufficient`); **plan** two tickets, one graded; **notes** a lesson with an instruction-like sentence and a PAN-like string. Unit: `Calc` table (every AC 11 case and malformed input), `PortfolioFigures`, chart reference validation, description word pins. Integration: each tool on the fixture against the golden envelope; `get_report` equals the handler; the grants test (real reader as `xd_mcp_read`); context off/on for `get_portfolio`, `search_notes`, `aiv` views; empty database for every tool (each answers `empty` or `unavailable`, never an exception); the C0 property test; the 30-call latency check. End to end (scripted model, in-process `xd-mcp`): question "expectancy by basket" -> `get_report(groups)` -> answer "Expectancy is +0.80 R over 40 trades" grounded, and the same with "+0.9 R" flagged; "tomorrow's plan" -> `get_plan`; a cell with `insufficient` -> the answer says so and the check finds no figure. Edge cases: zero holdings, a holding with no last price (`unavailable`), a plan with levels null, a symbol with dots or an ampersand (`M&M`), a basket name with markup, 300 rows truncated, a Unicode query to `search_notes`, `calc` with 49 and 51 tokens.

## Decisions (researched)
**Reuse the report handlers, do not re-implement them.** One definition of expectancy, evidence and states (P8-00 D1/D3); a second SQL path in `xd-mcp` would drift. The cost is that the report source tables are readable by `xd_mcp_read` (column-level, explicit). Rejected: calling `GET /api/reports/*` over HTTP (needs a service credential into `xd-api`, a new auth path).
**Gross only in v1.** The net basis needs the stored charge sheet confirmation, held in `platform.app_settings` with other settings no assistant role may read (P9-00 D11); the owner's sheet is also not yet confirmed (ISS-25). A view exposing only the confirmation is a later, owner-visible decision. Rejected: reading the settings row.
**`query` object instead of re-declaring every report parameter.** The tool schema stays small (token budget) and cannot drift from the endpoint; the description lists the dimensions and the P8-06 parser rejects the rest. Rejected: a typed argument per filter (about 400 tokens of schema).
**Portfolio figures computed in a pure function over view rows**, not by the Holdings handlers, because those join account tables the roles cannot read; the function is checked against the screen's numbers on the fixture, so a divergence is a failing test. XIRR is reused if possible and otherwise reported `unavailable`: a wrong XIRR is worse than none (doc 19, short-hold XIRR).
**`calc` exists so derived numbers are possible and checkable.** P9-03's check cannot verify model arithmetic; the only way to state a difference is to fetch it.
**`make_chart` references tool columns instead of taking numbers.** Charts are the easiest place for a model to invent a figure; a reference cannot. It is local because it needs the turn's results, which the stateless tool server does not hold.
**Full text, not vectors, for notes** (P9-00 D5): a few thousand rows, English text, a deterministic and explainable ranking.
**Tool descriptions are part of the contract** and counted in the schema budget; the model is told in them to prefer `get_report` over `run_sql` for expectancy-style questions (the engine's honest states), and `run_sql` for shapes no tool covers.

## Risks and honest limits
1. Report answers inherit every limit of P8 (about 2.1 years, replayed history, modelled fills, gross R, in-sample cells, baskets as of the run); the evidence carries them and the prompt requires repeating them when ranking.
2. A model can choose the wrong tool or wrong filters; the answer shows the arguments in the chips so the owner can see it.
3. `get_portfolio` figures depend on stored last prices (live, quote or sync source and age are in the output); a stale price is flagged `asOf`, not repaired.
4. The tool set is wide for a 30B model with 2,200 schema tokens; if P9-09 shows wrong-tool errors, the response is fewer, broader tools, not more prompt.
5. Column-level grants for the report reader break if P8-06 later reads another column; the grants test fails then, which is intended.
6. `get_system_status` reads service run rows that may be sparse on a fresh install; it says `unavailable`.
