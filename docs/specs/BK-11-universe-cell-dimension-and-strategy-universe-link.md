## Goal
The learning engine can state, for a setup, whether it works differently on highly liquid, middle and thinly traded shares (for example "ORB, 15m, BUY, intraday, in the top liquidity tier"), shrunk toward the same setup over all shares, without multiplying cells beyond one new dimension of three values, and every simulation run records which basket (and which membership date) it ran on and counts toward the multiple-testing factor.

## Scope
**In:** (1) a **seventh `CellId` part `universe`** with values `*`, `liq_high`, `liq_mid`, `liq_low`; the parser accepts six parts (universe `*`) or seven; the P14 `expression` part, when it arrives, becomes the **eighth**; (2) the pure `UniverseTier` function and the tagger that assigns a trade's tier **as of its decision date**; (3) cell statistics for tiered cells, shrunk toward their `*` parent, used only when the child's credible lower bound beats the parent's; (4) run labels `universe_basket_id`, `universe_params_hash`, `universe_basis` (`dated|single_snapshot`) on simulation runs, and the trial counting for strategy × basket runs; (5) reports/pivot dimension `universe` (disabled with the reason when no tier exists); (6) doc 09 text change and ADR note.
**Out:** more than one new dimension; sector, volatility, momentum or index-membership as cell dimensions (Decision 2); learning that **applies** a restriction (the proposal path is P6-10, owner approves; nothing here changes a strategy's scan scope); free baskets as cell values (the dimension has three tiers, not 30 baskets); rewriting stored cell keys; changing `min_trades`; a UI beyond the existing Setups tab filters and the pivot builder entry.

## Acceptance criteria
1. **Key compatibility.** Given the stored key `ORB|15m|BUY|intraday|FIXED_RR|*` (six parts), then `CellId.TryParse` returns it with `Universe = "*"` and `Key` returns the same six-part text (stored keys are unchanged; no migration rewrites them); given `ORB|15m|BUY|intraday|FIXED_RR|*|liq_high`, it parses with `Universe = "liq_high"` and `Key` is the seven-part text; a universe other than `*`, `liq_high`, `liq_mid`, `liq_low`, a part with `|` or an eighth part (until P14 defines it) is rejected (`null`), as bad six-part keys are today.
2. **Parent link.** Given a tiered cell id, then `Parent()` returns the same cell with universe `*`; `*` has no parent; a regime-tagged cell's parent follows the existing rule first (regime then universe, documented as one order and tested), so there is exactly one chain from the narrowest cell to the strategy.
3. **Tier by hand.** Given tracked eligible shares on date D with median traded value over 20 sessions (rupees crore) ranked 1..300, then `liq_high` = ranks 1 to 100, `liq_mid` = 101 to 200, `liq_low` = 201 to 300 (terciles of the eligible count N, boundaries ceil(N/3) and ceil(2N/3)); a share with fewer than 60 daily bars on D has tier `unknown` and falls only in the `*` cell; with N below 30 eligible shares all tiers are `unavailable` (no tier is invented from a tiny universe). The tier boundaries are recomputed with data up to D - 1.
4. **No look-ahead (property).** The tier assigned to a trade is computed from bars up to the session before its **decision** date and the membership of the dated liquidity basket as of that date; appending later bars or later membership versions changes no past assignment (truncation property). Where no dated membership exists for the decision date the trade is tagged `unknown` (counted in the report), never with today's tier.
5. **Shrinkage and the parent-beats rule by hand.** Given a parent cell (`*`) with 200 trades and win rate 0.50, and a child cell `liq_high` with 22 wins in 30 trades, prior strength 20 toward the parent, then the child's posterior mean is (22 + 20 × 0.5) / (30 + 20) = 0.64 and its 5 % credible lower bound is about 0.53 (normal approximation 0.64 − 1.645 × 0.0672; the test checks the exact Beta quantile to 0.01) against the parent's about 0.44; the child's lower bound is higher, so selection-time consumers read the **child** cell. Given the child 16 wins in 30 (mean 0.52, lower bound about 0.40), the child's lower bound is not above the parent's, so consumers read the **parent**, and the child row says "no better than all shares". Given 29 trades, the child is "not enough evidence" and the parent is read.
6. **Both rows are stored.** The child and the parent snapshot rows are both written (insert-only, as in ADR 0064); the "which one a consumer reads" is a pure function `CellChoice.Resolve(child, parent, minTrades)` that returns the cell, the reason (`child_better`, `no_better_than_parent`, `child_thin`) and both lower bounds; no stored row is relabelled.
7. **Explosion guard.** Given the cell registry for the seeded fixture, then the number of cells is at most 4 × the number of six-part cells (one dimension of three plus `*`), and a startup check fails if a second universe-like dimension is added to the key (the key has exactly one extra part).
8. **Run labels.** Given `xd simulate --basket <id>` (or the Lab picker), then the run label stores `universe_basket_id`, `universe_params_hash` (null for manual baskets), `members_as_of` and `universe_basis`; for a rule basket with dated rows the simulator reads `members(asOf = day)` per day (basis `dated`); otherwise members as of the run date (basis `single_snapshot`, printed as "members as of <date>, survivorship applies"). A run whose basis is `single_snapshot` is never described in any view as point in time.
9. **Trials are counted.** Given a strategy tested on k distinct baskets (or tiers), then the family's variant count is increased by k − 1 from a base of 1 variant (k variants in total, so `Factor(k)`) for `MultipleTesting.Factor(variants)` (VERIFIED: `1 + PerDoubling × log2(variants)`), by hand k = 8 adds 3 doublings; the count is read from the run labels, not from the owner's memory; a repeated run of the same (strategy, basket, `params_hash`, window) counts once.
10. **Pre-registration.** The Lab refuses (422 `lab.universe_not_registered`) a strategy × basket comparison for a basket outside the registered list (default list of the research note's eight, stored as a setting, changed by owner act with password); a refusal message names the registered list. An unregistered basket can still be simulated alone, but its run is labelled `exploratory` and is excluded from What-works ranking.
11. **Strategy-universe link is a proposal.** Given a cell family where the best tier's lower bound beats the parent's in both halves of a hold-out (BK-07's `HoldOutStability`) with ≥ 100 trades in the tier, then the Setups view and `GET /api/cells/universe-links` list "ORB, 15m: stronger on liq_high (lower bound 0.53 vs 0.44, n 30/200)" as an **observation**, and the existing hypothesis proposer may create one hypothesis (one knob, one cell) "restrict scan scope to liq_high"; nothing is created without the owner's action and nothing is applied (the P6-10 states proposed → approved → … → accepted record a verdict only).
12. **Reports.** Given the pivot builder or `groups?lens=universe`, then the dimension `universe` is available when tiers exist and returns 422 `reports.dimension_unavailable` with the reason otherwise; cells under 30 trades are masked by the server as everywhere in P8.
13. **Regression.** All P6-01, P6-02 and P7 selection tests pass unchanged with universe `*`; `GET /api/cells` returns the same JSON for existing six-part cells (contract snapshot unchanged except an added optional `universe` property).
14. **Performance.** Tagging 20,000 trades under 2 s (one tier table lookup per instrument-day, loaded once); cell statistics for the seeded fixture with tiers within 1.5× the time without.

## Decisions (researched)
1. **One dimension, three tiers, default `*`.** Question: how can baskets condition learning without exploding cells? Chosen: a single `universe` part with three behaviour tiers (research §U3, §4 item 4). Reason: the child is shrunk toward its parent, and a child is used only if its lower bound beats the parent's, so adding a dimension cannot make a thin cell look better; more dimensions multiply cells faster than a few thousand trades can feed them (P6-00 already warns about regime × 9). Rejected: 30 baskets as cell values. Source: Harvey and Liu (backtesting haircut, snippet only, UNVERIFIED primary).
2. **The tier is liquidity.** Chosen: liquidity terciles from median 20-day traded value. Reason: liquidity is the one attribute that changes what a fill is and what range structure exists for breakouts; R-multiples already normalise for volatility, so a volatility tier mostly repeats the stop distance; momentum is a signal (BK-09), not a universe; sector has 20+ values; index membership has no history (forward-only, ISS-22). Rejected: a volatility tier, a sector dimension. The tier definition is the owner's to confirm (Open question 1).
3. **Terciles by rank on each date, not fixed rupee thresholds.** Reason: the boundaries follow the market (turnover grows with prices); a rupee threshold would be a number nobody can justify and would reclassify all shares when the market moves. Honest cost: a share's tier can change between dates; the trade keeps the tier at its decision date.
4. **Resolve at read time, store both.** Chosen: both rows are stored as snapshots and consumers resolve. Reason: the audit trail shows exactly what was known; relabelling a stored row would break the insert-only rule (ADR 0064).
5. **Universe is the seventh part, `expression` the eighth.** Reason: the P14 plan adds `expression` as an optional seventh part for the same reason; fixing the order now avoids two optional trailing parts of unknown order. This is a **design change to doc 09 and P14-00** (ADR note required); the P14 spec needs the one-word edit when it is next touched (not edited here).
6. **Pre-registered baskets only for comparison.** Reason: a grid of strategies × baskets is the cheapest way to fool oneself (research U2); eight baskets fixed in advance, every cell counted in N through the existing `Factor`. Rejected: counting only the winning cell (the standard error of data mining).
7. **The link is an observation and a proposal.** Reason: the repo's rule is that no learning change is applied automatically (P7-00 Q, doc 09 as-built text). Applying a scan-scope restriction narrows what the system trades, a change of behaviour that the owner decides through the hypothesis loop.
8. **Run labels carry the basis.** The member list a run used is part of its identity, so two runs on "Nifty 100" at different dates are different experiments (ISS-22 convention extended).

## Risks and honest limits
- Tier assignment depends on the dated liquidity basket; before it has history, tiers exist only from the first snapshot and earlier trades are `unknown` (counted).
- With 2 to 3 years of data, most tiered cells will be under `min_trades`; many "no better than all shares" answers are the expected outcome.
- Liquidity tiers also proxy for size and for sector mix; a tier effect may be a sector effect.
- The tier is relative to the tracked set (the owner's picks), not the market (ISS-22).
- The bound comparison is not a significance test; with several tiers × cells × strategies some children will beat parents by chance; the hold-out requirement for the link observation and the N count mitigate, not remove, this.
