## Assumptions (taken as recommended)
1. **The ledger exists; the research note says it does not.** Read in `Application/Abstractions/Lab/ITestLedger.cs` and `Infrastructure/Lab/TestLedger.cs`: `lab.test_ledger` is insert-only for the runtime role, one row per run (`strategy_id`, `version`, `strategy_hash`, `parent_hash`, `lab_run_id`, `method`, window, universe), sweep points appended with method `sweep` (P5-05), and `CountVariantsAsync(strategyId)` returns the **distinct strategy hashes of the family**. What is true in the research note: the count is per run **of a strategy text**, so (a) the candidate exits of a full test (default four, `FIXED_RR:rr=2|1.5|2.5|3`), (b) the timeframe/side cells walked, and (c) anything run through the ML harness are **not** counted; and there is no frozen plan, so a changed universe, window or cost sheet is not a new trial. This slice closes exactly those gaps and does not rebuild the ledger.
2. `MultipleTesting.Factor(n) = 1 + 0.25 * log2(n)` stays the multiple-testing rule (read in `Domain/Lab/MultipleTesting.cs`); it is heuristic and the Deflated Sharpe / PBO checks live in CF-03. This slice only makes `n` honest.
3. History today is about 2.1 years and the Lab has **no** hold-out (P5-06 honest limits); the ML harness keeps the last 6 months (P6-05, `HoldOut.Reserve`).
4. Thresholds are proposals in versioned settings (CF-00 home; model: the insert-only snapshot table of P7-12); each verdict stores the snapshot hash.

## Decisions (researched)
**D1. Pre-registration record.** A strategy version cannot start a `full` or `robust` run (a `quick` test is exploration and stays free) unless it has a registration: (a) who is on the other side and why they lose (forced seller, slow reaction, risk-transfer premium); (b) the expected sign of every parameter's effect; (c) instrument tiers and sessions it applies to; (d) the expected gross edge in bps and the cost it must beat; (e) a falsifier ("if out-of-sample expectancy is under X or the placebo scores within Y, retire"). Text fields, length-limited, plain text only (never rendered as HTML). *Why:* the SEBI base rate says a retail rule rarely has a tradable edge (about 71 % of intraday cash traders lost money in FY23), so a pass must be expensive and a mechanism must exist before the data is searched. *Rejected:* optional free text (becomes decoration); asking an assistant to write it (the point is that the owner commits). *Source:* confidence-edge-realism.md §0 and §2.2; [SEBI FY23 study via Business Standard](https://www.business-standard.com/amp/markets/news/over-70-intra-day-traders-incur-losses-during-fy23-reveals-sebi-study-124072401110_1.html).
**D2. What is frozen, and what a change means.** At the **first `full`/`robust` run** a `plan_hash` (sha256 of canonical JSON) is stored for: strategy hash, universe label **and** member-list hash (the label says "members as of today", ISS-22), window, cost sheet id and its version/confirmation state, the registered sweep plan (parameters, steps), the candidate exit flags, the slippage preset, and the registration text hash. A later run with a different `plan_hash` for the same strategy id is a **new trial** (ledger row with `trial_kind = 'replan'`), never a silent overwrite. Hand example (research §3 row 1): registering 3 parameters x 5 values is a joint grid of 5^3 = 125; registering 3 values each is 3^3 = 27. Factors: `1 + 0.25 x log2(125) = 2.7415` against `1 + 0.25 x log2(27) = 2.1887`. (The Lab sweeps one parameter at a time, up to 16 points, P5-05; the joint grid is shown only to explain why the registered plan size, not the lucky subset, is what is counted.)
**D3. A trial is a look, so count looks.** `N` for the factor = distinct strategy hashes (today's count) **plus** one per extra exit candidate per hash first run (`candidates - 1`) **plus** one per `replan` row **plus** one per null row (CF-07) **plus** the sweep points (already hashed variants). Hand example: 3 edits of a strategy (3 hashes), each full-tested with 4 exit candidates, plus one sweep of 16 points: today `N = 3 + 16 = 19` and `f = 1 + 0.25 x log2(19) = 2.0620`; with the new rule `N = 3 + 3 x (4 - 1) + 16 = 28` and `f = 1 + 0.25 x log2(28) = 2.2018`; the 0.15 R expectancy gate is `0.15 x 2.0620 = 0.3093` today and `0.15 x 2.2018 = 0.3303` after. Research check: 64 trials give `1 + 0.25 x 6 = 2.5` and a 0.15 R gate of 0.375 R. The verdict uses the **ledger total at judgement time**, not the count the caller supplies. ML trials (models registered per feature version, `ChampionRule` already requires `requiredTrials`) and Lab trials stay two ledgers with two factors; a strategy that feeds a model is not double counted here (UNVERIFIED how the two families are joined; open question 4).
**D4. One locked hold-out, fixed once, shared with the ML harness.** Length `max(6 months, 20 % of the stored history)`, proposal. Today 2.1 years = 25.2 months: 20 % = 5.04, so **6 months** apply and development has 19.2 months; quarterly folds start 9 months in (read: `SelectionOptions` defaults `MinTrainMonths = 9`, `TestMonths = 3`, `EmbargoSessions = 5`, `MinTrades = 30`), tests at months 9-12, 12-15, 15-18 give **3 folds**, fewer than the 6 needed for a pass, so every verdict stays at most MARGINAL (existing cap, P5-03). With 5 years (CF-04) = 60 months: hold-out 12, development 48, `(48 - 9) / 3 = 13` folds. The hold-out start is a stored date; it never moves earlier, and one date serves strategies **and** models (P6-05 reads it instead of computing its own six months; the option already exists as an argument). Sessions on or after it are cut from every Lab simulation window (the same refusal as `validation.holdout_touched`, new code `lab.holdout_touched`). *Why:* one hold-out per dataset means a model and a strategy cannot peek through each other. *Rejected:* a per-strategy hold-out (the owner would hold many overlapping ones and forget which was burned); a rolling hold-out (every roll leaks the old one into development).
**D5. One unlock per strategy version, a second look is a new trial and cannot pass.** `POST /api/lab/runs/{id}/holdout-unlock` (owner act, fresh password, CSRF, audit row, like P7-12) runs the **frozen plan** once on the hold-out range as it stood at the unlock, stores the result, and writes an insert-only `lab.holdout_unlocks` row. Until then the report shows only "hold-out: kept, not yet used". A different version of the same family may unlock again but its row is marked `reused_window` and the result **cannot count toward a pass** (it counts as a trial and shows its numbers); only data after the hold-out end (forward data, CF-08) can refresh evidence. Hold-out pass rule (scorecard row 12): expectancy at least 50 % of the development out-of-sample expectancy **and** above 0, with at least 30 hold-out trades (proposal), otherwise `inconclusive` (not pass). Hand example: development OOS +0.20 R; hold-out +0.12 R = 60 %: pass; +0.10 R = 50 %: pass (at least); +0.08 R = 40 %: fail; +0.12 R on 22 trades: inconclusive. *Source:* confidence-edge-realism.md §3 row 2, §4 row 12.
**D6. Auto option (CLAUDE.md approvals-auto rule).** The unlock is an owner act. A setting `confidence.holdout.auto_unlock` (default **OFF**) lets the system run the unlock once the development part of the scorecard (CF-11 rows 1 to 11 and 14) is all pass; the row is recorded as `auto` with the setting snapshot, never as an owner approval. Turning the setting ON is an owner act (fresh password). `unavailable` inputs never count as a pass. No setting allows any order.
**D7. Enforcement.** `confidence.registration.enforce` (default OFF): OFF, a run without a registration only carries the warning `not_registered` and the report row reads fail; ON, `full`/`robust` are refused with 422 `lab.not_registered`. Same shape for `confidence.holdout.enforce` (a `full`/`robust` result with no hold-out kept reads fail and caps nothing until ON, then caps at MARGINAL). Turning either ON is an owner act with a fresh password.

## Goal
Before any strategy is tested for real, the owner has written down why it should work and what would kill it; every look at the data is counted; the last months of data are kept unseen and opened once, and the Lab says so in every report.

## Scope
**In:** Domain `Registration` (fields, validation, `PlanHash`), `TrialCounter` (pure, D3), `HoldOutPolicy` (length, start, folds estimate), `HoldOutResult` (D5 rule); Application handlers `RegisterStrategyHandler`, `GetRegistrationQuery`, `UnlockHoldOutHandler`, extension of `StartLabRunHandler` (registration check, window clamp, `plan_hash`) and of the verdict path (N from the ledger); Infrastructure stores and migration `AddLabRegistration`: tables `lab.registrations` (insert-only, versioned per strategy version), `lab.plan_freezes`, `lab.holdout_unlocks`; new `trial_kind` column on `lab.test_ledger` (default `'run'`); endpoints below; report rows; Lab screen fields and a "Registration" tab; settings; ADR; docs 11 and 16; `gen-api`.
**Out:** the shuffled/placebo nulls (CF-07); deflated Sharpe and PBO (CF-03); effective sample size and power (CF-01); the readiness scorecard that reads these rows (CF-11); forward shadow evidence (CF-08); the data backfill (CF-04); point-in-time universe (ISS-22); benchmark comparison (a later slice; research §2.2 second row).

## Acceptance criteria
1. Given a strategy version with no registration, when a `full` run is started with `registration.enforce` ON, then 422 `lab.not_registered`; with it OFF the run proceeds and the report carries `not_registered` (integration, both settings).
2. Registration validates: all five parts non-empty, length limits, no control characters; stored with sha256; a second registration for the same version is refused (409) because the record is frozen; a new version needs its own (unit, integration).
3. `PlanHash` is deterministic and sensitive: changing any one of strategy hash, universe member-list hash, window, cost sheet version, sweep plan, exit flags, slippage preset changes it; changing only the order of parameters in the input does not (property test).
4. A second full run with a different `plan_hash` appends a ledger row `trial_kind = 'replan'`; with the same hash it appends nothing new for the plan (idempotent per run id, as today).
5. **Trial counter by hand:** 3 hashes x (4 - 1) extra exits + 3 + 16 sweep = **28**, `f = 2.2018` (to 4 places); today's rule gives 19 and `2.0620`; the factor of 64 is 2.5 exactly; of 125 is 2.7415 and of 27 is 2.1887 (unit).
6. The verdict's `variantCount` is read from the ledger at judgement time; a test appends rows between two judgements of the same evidence and the gates tighten (integration).
7. **Hold-out sizing by hand:** 25.2 months of history gives hold-out 6 (20 % is 5.04), development 19.2, 3 folds; 60 months gives hold-out 12, development 48, 13 folds; 12 months of history gives hold-out 6 and development 6 (below the 9-month start): `no_folds` (unit).
8. Every Lab simulation window ends before the hold-out start; a request whose window reaches it is clamped and says so, or refused with `lab.holdout_touched` when the window is explicit (integration); the ML harness reads the same date (P6-05 test updated, not weakened).
9. Unlock: the first call runs once and stores the result; a second call for the same version returns 409 `lab.holdout_used` and the stored result unchanged; an unlock for another version of the family is allowed, marked `reused_window`, and the pass flag is false whatever the numbers (integration). Without a fresh password: 403; wrong password counts toward the lockout as in P7-12.
10. **Hold-out rule by hand:** dev +0.20 R with hold-out +0.12 R (60 %) pass; +0.10 R pass; +0.08 R fail; +0.12 R on 22 trades inconclusive; hold-out negative fail; NaN fail (unit).
11. `auto_unlock` OFF (no row = OFF): the unlock never runs by itself; ON: it runs once when the dev rows are all pass, recorded `auto` with the snapshot; with any `unavailable` row it does not run (integration).
12. The report shows registration state, the trial count with its parts (distinct hashes, extra exits, replans, sweep points), the factor, the hold-out state (kept / used / reused) and never the hold-out numbers before the unlock (unit on the builder; HTML escapes the registration text, as P5-06 AC5).
13. Logs carry no registration text, strategy text or trade; Architecture tests green; migration has a `Down`; runtime role has insert and select only on the three new tables (a grants test like `ResearchGrantsTests`).

## Contract

Problems: 404 `lab.not_found`, 409 `lab.registration_frozen`, 409 `lab.holdout_used`, 422 `lab.not_registered`, 422 `lab.holdout_touched`, 403 step-up. Types added to `ApiJsonContext`; `gen-api`.
- **Data:** `lab.registrations(strategy_id, version, rationale jsonb, text_hash char(64), created_at, actor)`; `lab.plan_freezes(strategy_id, version, plan_hash char(64), first_run_id, created_at)`; `lab.holdout_unlocks(strategy_id, version, unlocked_at, mode 'owner'|'auto', setting_hash, reused_window bool, result jsonb)`; `lab.test_ledger.trial_kind text not null default 'run'`. Settings `confidence.registration.*`, `confidence.holdout.*`. Migration `AddLabRegistration`.
- **UI:** Lab screen: a Registration form on the strategy version (five fields, frozen after the first full run), a hold-out card on the report (state, never numbers before unlock), an unlock button behind the step-up dialog (the owner-acts pattern of P8-18/P8-19). Loading, empty and error states per frontend/CLAUDE.md; status not by colour alone.
- **Jobs:** none new; the unlock runs on the Lab dispatcher as a `lab_runs` job of method `holdout` (idempotent by run key).

## Non-functional
Registration and ledger reads are single-row. The hold-out run is one plain pass of the frozen plan on a short window. Deterministic: same input same bytes. Security: owner session, CSRF, fresh password for the unlock and for turning an `enforce` or `auto_unlock` setting ON; all settings changes append-only with actor, reason, DB-clock time and hash.

## Test plan
Unit (Domain): `Registration`, `PlanHash`, `TrialCounter`, `HoldOutPolicy`, `HoldOutResult` hand tables and properties. Unit (Application): handlers with fakes; the clamp; `auto` path. Integration: all endpoints, the two enforce settings, grants, the ledger `replan` row, idempotence. Frontend (MSW): form, frozen state, unlock dialog, error states. Architecture: new Domain types free of I/O; no code reads hold-out rows outside the unlock handler (a search-based test on the reader port).

## Risks
With 2.1 years the hold-out leaves 3 folds, so nothing can PASS until CF-04: the spec makes that visible, not better. A hold-out opened by accident (a dashboard that reads sessions after the start) burns it: the single reader port and its test are the guard. The factor grows with honest counting and may make a good idea unprovable on short history; that is the intended behaviour (research §4 hand example).

## Review fixes 2026-10-27
1. **Trial counter wiring (cross-spec).** D3 and AC5 count "plus one per null row" (CF-07 AC9): N = distinct hashes + extra exits + replan rows + null rows + sweep points. `TrialCounter` **replaces** `ITestLedger.CountVariantsAsync` at `Application/Lab/LabFullTest.cs:106`; `Infrastructure/Lab/TestLedger.cs:32` counts distinct hashes only, so a null row carrying an existing hash would add nothing there.
2. **Hold-out start (replaces the "never moves" wording of D4).** The start is fixed at first use as `max(6 months, 20 %)` of the history then stored. A longer hold-out after CF-04 is a **new** hold-out start, set once by owner act with a fresh password; the old block becomes development and is recorded as `burned`.
3. **Unlocks.** `lab.holdout_unlocks` takes `kind = 'strategy' | 'model'` (CF-10 uses `'model'`). Any unlock marks the shared block seen: the first use is `fresh`, every later one `reused_window` and cannot count toward a pass.
4. **Rule wording (D5, AC10):** pass = at least 50 % of development OOS **and** above 0 **and** at least 30 trades.
5. **Deadlock with CF-11 rows 2, 3, 6 (D6).** Before the unlock those rows use development OOS only, labelled "pre-hold-out"; after the unlock they are recomputed on OOS plus hold-out. The `auto_unlock` precondition uses the pre-hold-out values.
