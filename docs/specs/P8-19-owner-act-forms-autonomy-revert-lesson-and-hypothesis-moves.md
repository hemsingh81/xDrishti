- **Status:** Approved (owner, 2026-10-26); built 2026-10-26 ([ADR 0130](../adr/0130-the-owner-act-forms-are-endpoints-behind-a-capability-a-fresh-password-and-an-audit-row-over-the-existing-handlers-and-state-machines-and-apply-nothing.md)). - **Phase / roadmap row:** P8 — Reports & UI, slice P8-19 of [P8-00](P8-00-reports-and-ui-plan.md) (Q1, Q2, Q8)
- **Design refs:** docs/design/09-learning-engine.md §5 (hypothesis loop), §10 (lessons), §13 (autonomy, "password re-entry", "one-click Revert") · 04 §4.1 ("Only you"), §4.2 · 13 §1c · 19 §4 (automation over-reach) · P7-12 (autonomy) · ADR 0073 (changelog: the log is the state), 0076 (hypotheses), 0078 (lessons), 0091 (auto-approval option)
- **Needs:** P8-18 (the capability gate and the shared fresh-password helper, built there), P8-03 (the Lessons / Experiments / Hypotheses tabs that link to the forms), P8-04 (the Autonomy tab). P6-08, P6-10, P6-16, P7-12 are built and are the only logic used. An ADR at build time (next free ADR number at build time).
- **Size:** 4 agent-days (backend endpoints 1.5 d, forms 2.5 d; the report suggests splitting them)
- **Safety:** **yes.** Write actions from the UI, including the autonomy switches that let a rule approve tickets. None of them places an order (P7 and P8 place none), applies a learning change or edits a strategy, but they change records the plan reads. They stop for the owner. Every switch defaults OFF.

## Assumptions (the safest answer that still serves the goal)
1. **No new rule.** Every move is an existing, built handler: `ChangeAutonomySettingsHandler`, `RevertChangelogHandler`, `LinkLessonHandler`, `CloseLessonHandler`, `DismissLessonHandler`, `MoveHypothesisHandler` (all opened). The slice adds endpoints, a password check in front of them, a capability gate and forms. The state machines (`LessonLifecycle`, `HypothesisLifecycle`, `CellLifecycle.RevertRefusals`) are the only authority; the UI shows `NextStates` that the views already carry and never computes a transition itself.
2. **Fresh password on every request**, for all six writes (Q8: "a password on every change and an audit row"), through the helper extracted in P8-18 (`FreshPasswordCheck`, `Elevate:false`): same sign-in lockout counters and audit, the 5-minute step-up window neither opened, extended nor consumed.
3. **Actor from the session**, `owner:<e-mail>`, never from the body. `cli:xd` can never be produced by the web. The handlers' `IsOwner` accepts `owner:` and `cli:xd`; the endpoint builds the first only. An e-mail that makes the actor longer than 100 characters fails validation with 422 `learning.invalid` (the handlers' own limit); stated, not worked around.
4. **What stays verb-only** (decision D2): propose a hypothesis, start it (attaching the candidate run), judge it (a judgement is a trial that raises the bar), open lessons (`xd learn lesson` scan), designate a model, record a cell transition, run any learning job, change a service schedule or the selection builder (Q2: they stay on the Services screen). The web can only **approve, reject, expire and accept** hypotheses, **link, close and dismiss** lessons, **revert** the latest cell transition, and **change the autonomy settings**.
5. **Revert is a new row**, never an update or a delete (P6-08). It can only restore a less trusted state: the domain refuses restoring Active and refuses un-retiring.
6. **Gate.** Two capabilities from P8-18's store, both default OFF, both enforced on the server: `learning_moves_ui` (lesson, hypothesis, revert endpoints) and `autonomy_form` (the existing `PUT /api/autonomy/settings`, which today has no UI caller; gating it is an additive change, and its P7-12 tests seed the capability ON). Turning either ON needs the fresh password; turning OFF does not.

## Goal
The owner can record the moves that today need the terminal (link, close, dismiss a lesson; approve, reject, expire, accept a hypothesis; revert the latest cell transition) and change the autonomy settings from one screen, each with a reason and a fresh password, each leaving an insert-only audit row, none able to apply a change, place an order or turn anything on by default.

## Scope
**In:** endpoints below; `FreshPasswordCheck` reuse; the capability checks; the optional `expectedSettingsId` on the autonomy body (additive, see 9); `AccountEventType` values appended (`LessonMoved`, `HypothesisMoved`, `ChangelogReverted`, `AutonomySettingsChanged`); feature `owner-acts` forms and routes; read-only screens (P8-03/04) gain plain links; ADR; docs.
**Out:** the verb-only list (assumption 4), editing or deleting any record, "revert" of an autonomy row as a special endpoint (it is the same PUT with the old values, step 8), bulk moves, an apply button, push or e-mail about a move.

## Acceptance criteria
1. Given the capability for an endpoint is OFF or has no row, when any of the six writes is called with a valid body and password, then 403 `capabilities.off`, no row anywhere. Given `GET` of the same resources, they behave as before. *Integration, one case per endpoint.*
2. Given a wrong or missing password, when any write is called, then 401 `auth.invalid_credentials` (a missing password is the same 401) and the sign-in lockout advances; the fifth wrong one is 423 `auth.locked`; a correct password inside an open step-up window is still required and the window is unchanged. *Integration; the same matrix as P7-12 criterion 4, run for all six.*
3. Given a body that names an actor, a state or an autonomy level, then it is ignored: the row's actor is `owner:<session e-mail>`, the hypothesis move uses `AutonomyLevel.Supervised` as a constant. *Integration.*
4. **Lessons.** The matrix over every (from, to) pair of `{open, linked, closed, dismissed}`: only open->linked (`POST /api/lessons/{id}/link` with `fixKind` hypothesis|experiment and `fixId`), open->dismissed, linked->closed, linked->dismissed succeed; every other pair is 409 `lessons.move_refused` with the domain's sentence ("A closed lesson cannot move: closed is final."); an unknown fix is 404 `lessons.fix_not_found`; close without a recorded experiment on the fix is 409 `lessons.move_refused` ("The linked fix has no recorded experiment yet; judge it first, or dismiss the lesson."); an unknown lesson is 404 `lessons.not_found`; a move racing another is 409 `lessons.stale`. *Application + integration.*
5. **Close takes no number.** The body of close has `reason` and `password` only; a body that adds `beforeMeanR` or `result` changes nothing; the stored result is read from the fix's stored experiment (`improved` only when it was Better, otherwise `no_measurable_change`), shown as an ordinary result. *Integration.*
6. **Hypotheses.** `POST /api/hypotheses/{id}/move` with `to` in `approved|rejected|expired|accepted`; `proposed`, `running`, `judged` or anything else is 422 `learning.invalid` ("running and judged have their own commands"). The matrix over all (from, to): legal pairs of the table succeed (proposed->approved|rejected|expired; approved->rejected|expired; running->expired; judged->accepted|rejected|expired), illegal ones are 409 `hypotheses.move_refused`; accept needs a stored experiment with outcome Better, else 409 with "Only a Better experiment can be accepted."; the success text is the handler's ("Nothing was changed; applying it is your own act"). *Application + integration.*
7. **Revert.** `POST /api/changelog/{id}/revert`: succeeds only for the latest row of the cell, kind `transition`, and appends a row of kind `revert` pointing at it; a revert of a revert, a non-latest row, a designation, a restore to Active, and un-retiring are 409 `changelog.not_revertible` with every reason listed; unknown id 404 `changelog.not_found`; stale 409 `changelog.stale`. After it, `GET /api/changelog/cell-state` shows the restored state, and the table still has every older row byte-identical. *Integration.*
8. **Autonomy.** The form posts the existing body to `PUT /api/autonomy/settings` (switches, `minPWin` 0.5-0.99, `maxAutoPerDay` 1-20, reason 1-500, password). With nothing stored both switches show OFF. Re-using an old row is a fresh PUT with its values prefilled (a new row, password again), never an edit. Error codes `autonomy.owner_only`, `autonomy.values_invalid`, `autonomy.reason_invalid`, `autonomy.stale` are shown verbatim. The text beside the switches says "No setting lets anything place an order; an automatic approval only makes a ticket Approved". *Vitest + existing integration cases.*
9. **Stale form.** Given the form was loaded at settings id N and another change made id N+1, when it submits with `expectedSettingsId: N`, then 409 `autonomy.stale` and nothing is written; a body without the field behaves as P7-12 (current id read at submit). *Application + integration.*
10. **Audit.** Every successful write leaves (a) its own insert-only row with actor, reason, state change and database time (lesson/hypothesis/changelog/autonomy tables, already so), and (b) one `account_events` row of the new types with a detail such as `lesson=12 open->linked` (ids and state words only; **no reason text, no e-mail beyond the actor column, no numbers from the evidence**). A refusal writes no row of kind (a); wrong passwords are already audited by the step-up handler. Row (b) is written after (a) in its own transaction: if (b) fails the move stands, the failure is logged by id, and a test proves (a) cannot exist without actor and reason. *Integration.*
11. **Default OFF and no leaks.** A fresh database returns `{enabled:false}` for both capabilities; with both OFF, the rendered Learning and Plans screens contain no control that writes, only the read-only state and a link to `/owner-acts`. The shared write-path guard of P8-18 (criterion 15: case-insensitive; `post`, a variable-method `fetch`, `sendBeacon`; allowed writer features `owner-acts` and `exports` only) is part of this item and must pass, and the six paths appear only in `features/owner-acts` and the generated schema. *Vitest scan with positive controls + MSW.*
12. `scripts/gen-api.sh` run; problem codes are in the OpenAPI summaries; log ids unique; architecture tests unchanged; `scripts/check.sh` green.

## Contract
- **API (session + CSRF; fresh `password` in every body; rate-limit policy `login`; all return the handler's outcome DTO):**
  - `POST /api/lessons/{id:long}/link` `{fixKind, fixId, reason, password}` -> `LessonMoveOutcome {id, state, text}`.
  - `POST /api/lessons/{id}/close` `{reason, password}`; `POST /api/lessons/{id}/dismiss` `{reason, password}`.
  - `POST /api/hypotheses/{id:long}/move` `{to, reason, password}` -> `HypothesisMoveOutcome`.
  - `POST /api/changelog/{id:long}/revert` `{reason, password}` -> `ChangelogOutcome {id, subject, fromState, toState}`.
  - `PUT /api/autonomy/settings` as built plus optional `expectedSettingsId` (long). `GET /api/autonomy/settings` unchanged.
  - Codes: `capabilities.off` 403; `auth.invalid_credentials` 401; `auth.locked` 423; `auth.rate_limited` 429; `learning.invalid` 422; `lessons.*`, `hypotheses.*` (`not_found` 404, `move_refused` 409, `stale` 409, `fix_not_found` 404), `changelog.*` (`not_found` 404, `not_revertible` 409, `stale` 409), `autonomy.*` as P7-12.
- **Data:** no new table. The capability store is P8-18's. `AccountEventType` gains four values (stored by name; appended at the end; no migration, the column has no check, verified by reading `AccountEventType.cs`: UNVERIFIED for the database constraint, the build's first step reads the migration). The `ChangeAutonomySettingsCommand` gains the optional expected id.
- **UI:** feature `frontend/src/features/owner-acts/`, lazy routes `/owner-acts` (switches and the autonomy form), `/owner-acts/lesson/:id`, `/owner-acts/hypothesis/:id`, `/owner-acts/revert/:changeId`. Each form: the current state, the legal next moves from `NextStates` only (a move not listed is not rendered), a reason box (1-500, counter), the password field (`autocomplete="current-password"`, cleared after every submit), the consequence sentence ("Nothing is applied", "Revert only restores a less trusted state"), the server's problem text. Match the dialog shell of P1-16a. The read-only screens link with a plain anchor (no mutation import). No navigation entry.
- **Events/jobs:** none.

## Non-functional
Latency: a move is one read and one insert (under 200 ms, excluding the password hash, whose cost is the existing one). The password hash is checked once per request. Logs carry ids, state words, codes (block 4920-4939 proposed; `LogEventIdTests` decides); never a reason, an e-mail or a password. Responses carry `Cache-Control: no-store`.

## Test plan
- **Unit/application:** exhaustive matrices for lessons (16 pairs) and hypotheses (49 pairs, 7 states) from the pure tables; revert refusal reasons; expected-id compare; the actor builder; the new event details contain no free text (property over random reasons).
- **Integration (Testcontainers):** each endpoint x {capability off, wrong password, locked, valid}; chain races (two moves at once -> one row, one 409); append-only grants as `xd_app` (no UPDATE/DELETE on the learning tables, unchanged); audit rows; the step-up window unchanged after each call; autonomy cases of P7-12 re-run with the capability seeded ON and one with it OFF.
- **Proof that nothing else moves:** the table checksum technique of P8-18 around each write: only the one target table and `account_events` grow; plans, tickets, approvals, strategies, cost sheets, services, cells' stats do not change. An architecture test: the handlers behind these endpoints are not changed (their source hashes are pinned in the test as a reminder that this slice adds no logic), and the endpoints file calls only `ICommandHandler<...>` of the six commands.
- **Frontend (MSW, clock pinned):** every form for off, on, wrong password (field cleared), 409 text, success; only legal moves rendered for each state; accessibility (labels, focus after error, no colour-only state); markup in server text; the password never appears in the DOM after submit or in a query cache (a scan of `queryClient` state).
- **Real browser:** one lesson through link and close on a seeded database, one revert, one autonomy change ON then OFF, with the screens read in the Browser pane.

## Decisions (researched)
- **D1 Which writes.** The six above. Reason: they are the "Only you" and "Proposed -> you confirm" items of doc 04 §4.1 whose logic is built and whose effect is a record, not a change in trading (accept and close say so). Rejected: the full set including propose/start/judge (a judgement is a trial; start attaches a run: both belong with the replay job of P8-18 or the verb), and any "apply".
- **D2 Verb-only list** as assumption 4. Source: ADR 0076 (judge counts as a trial), doc 09 §13 ("Always asks you").
- **D3 Fresh password every time.** Chosen over the 5-minute step-up window because the window is not consumed by use and would let one password cover many moves; the autonomy PUT already works this way. Source: P7-12 assumptions 8; P8-00 Q8.
- **D4 One `move` endpoint for hypotheses, verbs for lessons.** Lessons have three different bodies (link needs a fix); hypotheses have one shape. Rejected: one URL per hypothesis state (more routes for the same code).
- **D5 Audit shape.** The domain rows are the primary audit (they are insert-only, carry actor, reason and time, and are what the machines read); the account event is a cross-index for the audit screen (P8-22). Rejected: one transaction across the research database and the accounts unit of work (no shared unit exists; adding one is a larger change than the risk it removes) and writing reasons into events (free text in a feed that is displayed widely).
- **D6 Autonomy gated by its own capability.** The switches let a rule approve tickets; the extra layer costs one extra password once. Rejected: no gate (the endpoint already exists, but the owner asked that anything that can run automatically be a deliberate act) and gating through `learning_moves_ui` (a lesson link is not the same risk).
- **D7 Stale protection.** `expectedSettingsId` is additive and optional so P7-12 callers do not break; the form always sends it. Rejected: ETag headers (nothing else here uses them).
- **D8 Revert wording and scope.** The form says what the revert will change (cell, from state, to state) and that published plans are not changed; it is limited by the domain to less trusted states. Source: `CellLifecycle.RevertRefusals`, ADR 0073.

## Decisions at build time (2026-10-26; gaps of the spec, the safer option each time; [ADR 0130](../adr/0130-the-owner-act-forms-are-endpoints-behind-a-capability-a-fresh-password-and-an-audit-row-over-the-existing-handlers-and-state-machines-and-apply-nothing.md))
- **D9 The gate is asked three times, not in the handlers.** The six handlers are also the command line's: gating them would gate the owner's terminal. The endpoint asks the gate before the password (a switched-off act says nothing about the password), then `IOwnerActRunner` asks it again and calls the one handler, then writes the audit row. There is no database layer (no table is added; the rows are the existing insert-only logs); an architecture test pins that one module names the five commands and one flow runs every write.
- **D10 The gate covers the existing autonomy PUT.** As the spec says (assumption 6); the P7-12 tests that use the PUT seed `autonomy_form` ON.
- **D11 `expectedSettingsId` 0 means nothing stored.** The view has `id: null` while no row exists, and the field is a number; the form sends 0 then. Absent keeps the P7-12 behaviour.
- **D12 The audit detail names the target state only** (`lesson=12 link to=linked`, `hypothesis=3 to=approved`), because the handlers' outcome carries the state after; reading the state before would add a second read in the endpoint. The revert detail has both states.
- **D13 One lazy route `/owner-acts/:kind/:id`** (`lesson`, `hypothesis`, `revert`; the revert id is the changelog row id) instead of three: the first-load script has under 2 KB of room and each route definition is eager.
- **D14 The revert link is drawn on the newest transition row of one cell's own changelog only.** The server alone decides whether the row can be reverted and lists every reason; a row that is not a transition (a designation or a revert) gets the server's sentence and no form (no password for a certain refusal).
- **D15 The sign-in rate limit applies as for every password-checked act** (10 a minute per address). A refusal there is a 429 with its words, never a sign-out. There is no OFF-direction shortcut in this slice (no move is a kill switch); turning a capability OFF stays the switches page, which is never limited.
- **D16 Statuses.** A refused input of the learning moves is 422 `learning.invalid` (also an unparseable `to` word, raised by the endpoint after the password so a wrong body costs nothing before it); the autonomy `PUT` keeps its 400 `autonomy.values_invalid` and `autonomy.reason_invalid` as built (the spec's 422 is for `learning.*`). The server's sentence is the `title` of the problem; the screen shows it with its code, as text.
- **D17 A success keeps the screen.** After a move the form stays mounted and shows the server's sentence; the record is read again, so the moves it lists change under it. A second try on a final record is a 409 shown as such.
- **D18 The Learning and Autonomy screens keep no write control.** They show a plain link to the form while the switch is ON, and the words with a link to `/owner-acts` while it is OFF (the `useCapability` hook is the one allowed import; `readOnly.test.ts` still holds).

## Risks and honest limits
- A form makes accidental clicks possible: the reason is required, the password is required, the consequence sentence is shown, and the move list is the legal list only. There is no undo of a lesson move (closed and dismissed are final); the history keeps both rows.
- "Owner" and "rule" are strings in the database (P7-12 limit): a compromised process holding `xd_app` could write rows; the control is that the only writer is the endpoint behind session, CSRF, capability and password.
- Turning `auto_approve_tickets` ON still approves nothing today: the checklist inputs are not all wired (P7-12 honest limits). The form says so beside the switch, from the server's own text.
- The audit cross-index row can be missing if its write fails; the primary row cannot.
- A password typed into a page on an untrusted device is a risk of any web form; this is why the access path is a private tunnel (P8-21) and not the open LAN.
