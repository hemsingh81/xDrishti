# P10-01 — Paper fill capture: an armed ticket becomes a timed, priced paper trade with no order

- **Status:** Draft (written 2026-10-24; decisions below were researched under the owner's delegation; the owner's Approved is still needed before an agent builds it)
- **Phase / roadmap row:** P10 — Paper trading, slice P10-01 of [P10-00](P10-00-paper-trading-plan.md)
- **Design refs:** docs/design/04 §4.2 (ticket states), 09 §9 (graded on fills), 10 §8, 15 §1 ("graded on fills"), 18 (P10 row), 19 §3, §6; ADR 0037/0038 (fill rules), 0042/0044 (costs), 0083 (plan record), 0090 (grading), 0093 (journal), 0096 (arming, expiry), 0024 (live feed: last price only)
- **Needs:** P7-03, P7-07, P7-10, P7-11, P7-13 (built); ADR: one new ADR "paper fills are the grading replay, captured per armed allocation" (next free ADR number at build time)
- **Size:** 3 agent-days
- **Safety:** yes (light). A new automatic writer service. It places no order, calls no broker, moves no ticket and changes no setting; it starts **paused** and switching it on is the owner's act. The spec being Draft is what holds the build.

## Goal
Every ticket the owner approved and the pre-open check armed ends up, once its session's official 1-minute bars are stored, as a **paper trade per paper account**: entry and exit instants (minute), filled prices, quantity actually allocated (after the owner's size-down), exit reason, R, and rupees gross and net of the stored charge sheet. No order exists anywhere; the record says so.

## Scope
**In:** pure `Domain/Paper` (`PaperEntry`, `PaperExit`, `PaperSkip`, `SkipCodes`, `PaperPnl`, `PaperWording`); the **single replay path** (extraction of the per-ticket replay out of `GradePlansHandler` into `TicketReplayer`, used by grading and capture); `Application/Paper` `CapturePaperFillsHandler`, `PaperCaptureService` (service id `paper-capture`), `IEpochGate` (`ResolveAsync(sessions, ct)` returns the epoch id and the `measure_status` of each session; default `SingleEpochGate`: one epoch `first`, every session `measured`; P10-05 replaces it), `IPaperStore`; Infrastructure `PaperStore`, records and configurations; migration `AddPaperCapture` (schema `paper`, tables `epochs`, `epoch_accounts`, `entries`, `exits`, `skips`, `capture_runs`, all insert-only for `xd_app`, with `Down`); `GET /api/paper/entries`, `GET /api/paper/capture-runs`; verbs `xd paper capture [--date]`, `xd paper epoch show`; tests; `scripts/gen-api.sh`.
**Out:** the ledger and open-book view (P10-02), epochs beyond the single default one (P10-05), reports (P10-03/04), owner-entered fills, live-feed recording, any ticket state move, any order, a screen.

## Acceptance criteria
1. **One code path.** Given an armed ticket with a stored grade, when it is also captured, then the paper entry price, exit price, exit reason and the replay run key equal the grade's (`EntryPrice`, `ExitPrice`, `ExitReason`) and `r_sim` equals the grade's R. Both handlers call `TicketReplayer`; a test fails if `GradePlansHandler` or the capture handler constructs a `RunSimulationQuery` itself. The existing P7-13 tests pass unchanged (behaviour-preserving extraction).
2. **Only armed tickets.** Given tickets that are proposed, modified, rejected, lapsed, invalidated, or approved-but-never-armed, then no entry is written for them. A ticket that has an `armed` event in its trail (even if it later expired) is captured, once per paper allocation (account).
3. **Entry never before arming.** Given a replay entry minute that starts before the ticket's armed instant (`plan_events.at` of the `system:preopen` row), when captured, then no entry is written and a skip `entered_before_armed` is stored; the database also refuses an entry with `entry_at < armed_at` (check).
4. **Quantity is the owner's.** Given an allocation of 100 shares reduced by an owner modification to 60, when captured, then `qty_allocated = 100`, `qty = 60`, and gross and charges are computed on 60. Given an unreadable stored modification, then the pair is skipped `modification_unreadable` and nothing is written (never the larger size).
5. **Rupees by the same pure charge function.** Given a stored charge sheet in force, then `charges` is the sum of `CostModel.Leg` for the entry and exit orders at the account quantity on the dates of the fills (segment by style as the replay does: swing is delivery), and `net_pnl = gross_pnl - charges`. With no sheet configured, `charges`, `r_net` and `net_pnl` are null and `cost_basis` is `gross, no charges`; a configured sheet that is not stored fails the run `paper.sheet_missing` and writes nothing.
6. **Open and closed.** Given a swing entry whose replay is still open at the end of the stored bars, then an entry is written with no exit; a later run writes the one exit when the replay closes it. An exit is never written twice (unique) and an entry is never changed. If a later replay shows a different entry for a stored one, nothing is overwritten, the pair is logged `paper.integrity` and the capture run counts it (surfaced by P10-06).
7. **Pending is not written.** Bars not yet reaching the session, a refused or skipped replay, a flagged decision or fill day, an unmapped symbol: nothing is stored in `entries`/`exits`/`skips`; the pair is counted in `capture_runs.pending` of that session's row (outcome `partial` when `pending > 0`) and the next run tries again (the rules of ADR 0090 point 5 apply unchanged). Final facts are stored as skips: `not_triggered`, `not_gradable` (with the reason), `dropped_by_sizing`, `legs_not_supported`.
8. **Idempotent.** Running twice for the same session writes nothing new (unique `(plan_item_id, account_id)` on entries and skips, unique `entry_id` on exits).
9. **No look-ahead.** The capture for session F reads bars only up to the last closed session; a session that is not past is refused (`paper.invalid`); the replay's own no-look-ahead properties (P3-08) stay green because the replay is unchanged.
10. **Reserve and auto are labelled, not hidden.** Each entry stores `ticket_group` (`primary`/`reserve`) and `approval_kind` (`owner`/`auto`). Both are captured; P10-04/06 decide what counts.
11. **No order, no state move.** The capture touches no `plan_events` row; the architecture rule of ADR 0083 (no order-named member) and the Domain namespace rules stay green; `xd_app` can select and insert the six tables but not update, delete or truncate.
11b. **Coverage rows.** A run writes one `capture_runs` row for every trading session from the epoch's first session up to the last closed session that has none yet, **including sessions with no armed ticket** (`seen = 0`, outcome `done`), so "captured through" and the stale-book rule of P10-02 are testable from that table alone.
12. The service starts paused, runs daily at 17:00 India time after `eod` (must follow `eod`; starts not before 16:30; catch-up same day), and before `nightly` (18:30). A failed run is visible on the Services screen with its reason.

## Non-functional
One replay per armed ticket (at most 50 armed a session, `PreOpenRules.MaxArmedTickets`) plus the tail replay for daily triggers, as grading; budget 3 minutes for a full session on the owner's data (UNVERIFIED: grading was not timed either). Reads only stored bars; no external call; no secret. Logs carry ids, counts and codes, never a price, symbol or account. Time through `TimeProvider`; dates India.

## Decisions (researched)
1. **Q: Where do paper fills come from: the live minute feed, the owner entering them, or both?** A: **the grading replay's own simulator over the official 1-minute bars the `eod` run stores, captured after the close, for armed allocations only.** Why: (a) the repo has **no live minute bars**: `xd-feed` writes only the last price per instrument every 2 s into holdings and the unlogged `market.live_quotes`, emptied each window (ADR 0024 decision 3 "No price history, no live bars"; `bars_1m_live` of doc 05 §5 is in no migration, checked 2026-10-24); recording them would be a new feed writer and storage (a SAFETY slice) for bars that are less complete than the official ones; (b) the backtest the exit compares against used the official bars and the same rules, so paper and backtest differ only by the days and the human steps; (c) one code path means paper cannot drift from the simulator that produced the cells (the failure ADR 0090 already rejected for grading). Rejected: owner-entered fills for the measured set (look-ahead and cherry-picking risk, 5 to 10 minutes a trade of the owner's time, and a hand-typed price is not evidence); live-tick simulation (nothing recorded to simulate on). Real hand trades the owner makes anyway stay in P7-14's journal as a separate basis and are never counted. Source: ADR 0024, ADR 0090, doc 05 §5, repo check.
2. **Q: Does paper add anything over P7-13 grades?** A: yes, and the spec says what: it restricts to tickets that were really approved and armed (so the operating chain is tested), uses the owner's size, keeps entry/exit instants and rupee P&L per account, and starts a forward-only record the plan cannot back-fill. It does **not** add execution realism: fills are modelled (touch is fill, no queue, no latency; `FillLimits.NotModelled`). Stated on every response. Source: ADR 0038 decision 11.
3. **Q: Move tickets Armed to Triggered to Closed?** A: **no.** `plan-expiry` (15:40) moves Armed tickets to Expired before the EOD bars exist, and Expired is final in `TicketLifecycle` (13 moves, pinned by exhaustive tests and a database trigger). A post-hoc "Triggered" would carry the wrong time and need a lifecycle change with three safety reviews behind it. The paper trade is its own record; views say "Expired = the watch window ended; whether it triggered is in the paper record". Rejected: reordering expiry after EOD (keeps armed instruments in the feed for hours for no benefit). Source: `TicketLifecycle.cs`, ADR 0096.
4. **Q: Which R is the trade's R?** A: the replay's (`RNet` when charged else `RFilled`), exactly as grading and the cells use, stored as `r_sim`; rupees use the account quantity. R is size-independent, so one signal has one R whatever the number of accounts. Source: `TicketGrader`, P8-05 count-once rule.
5. **Q: Entry before arming?** A: set aside (`entered_before_armed`), because a paper trade the system could not have been watching is not a trade it could have taken. With a 09:10 arming and a 09:15 open this fires only when arming is late. Source: ADR 0096 point 11.
6. **Q: Legs (partial exits, pyramids)?** A: a trade with `Legs` is skipped `legs_not_supported`; production runs have none (SimTrade note). Revisit with P4 exits in live use.

## Risks and honest limits
- Fills are the simulator's: no slippage beyond the modelled ticks, no partial fills, no rejections. Paper cannot validate execution; P11 does.
- The capture is after the close, so a "live" mismatch (a halted or circuit-locked stock) appears only as the bars show it.
- Entries are written for the replay's first qualifying trade; a strategy that fires twice in a session is captured once (as graded).
- The look of an armed ticket's price alert is not tested (price-crossing alerts are P7-20).
- Symbol to instrument uses the non-archived baskets as grading does (first match wins; an instrument removed from every basket is pending).
- Not measured on the owner's data; no armed ticket has existed yet.
