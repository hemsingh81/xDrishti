# P12-12 — The phase check: 30 semi-auto sessions with zero reconciliation breaks (a read-only measurement)

- **Status:** Approved (owner, 2026-10-31: run the roadmap loop in build order; written 2026-10-24, decisions researched under the owner's delegation). The measurement is built now; its verdict stays NOT EVALUABLE until real semi-auto sessions exist.
- **Phase / roadmap row:** P12 — Execution service, slice P12-12 of [P12-00](P12-00-execution-service-plan.md) (id only); the exit criterion of the roadmap row: "30 semi-auto sessions with zero reconciliation breaks"
- **Design refs:** docs/design/18-roadmap.md (P12 row) · 20 §A (reconciled state, "mismatch ⇒ freeze") · 19 §4 · ADR 0080 (the P6 phase check: MET / NOT MET / NOT EVALUABLE, limits always printed), ADR 0097 and spec P7-18 (the pattern: stored records only, never MET on thin data, caveat in the label, exit code 0) · P8-00 D3 (honest states)
- **Needs (build order of the group: P12-07, P12-11, P12-08, P12-09, P12-10, P12-12; this slice is last):** P12-06 (`recon_runs`, `recon_breaks`, `break_resolutions`; its criterion 10 defines a clean session), P12-07 (`mode_trail`), P12-08 (`confirm_tickets`, `ticket_outcomes`), P12-01 (`intents`, `events`, `legs`, `environment`), P12-04 (alarms), P12-05 (halts, drills), P12-11 (`day_states`), P7-18 (the pattern, `IBrokerAllowList`). Feeds the gate `semi_auto -> auto_live` of P12-07 and the phase-done step.
- **Size:** 2 agent-days (estimate) plus wall-clock time (see Risks).
- **Safety:** no (read only: nothing is written, no setting is read to be changed, no order and no broker call); the output gates a later safety decision (`auto_live`), so it is built to never over-claim. The spec being Draft holds the build.

## Assumptions
1. **Read only, stored records only.** The check recomputes from insert-only rows each time; there is no stored verdict (a second place that can disagree). It runs no test and calls no broker.
2. **Per account.** The criterion is evaluated per Trading account in `semi_auto`; the phase exit is MET when **at least one** account is MET, and the report lists every account. The `auto_live` gate of P12-07 reads the per-account verdict.
3. **Live only.** A session counts only for intents whose `environment` is `live`. Sandbox sessions (P12-02: third-party descriptions say it fills at 100 with no quotes) prove wiring, not reconciliation against real fills; they are listed and never counted.
4. **"Break" is P12-06's word.** A break is any `recon_breaks` row (`position_mismatch`, `trade_missing`, `trade_extra`, `order_mismatch`, `fill_mismatch`, `unknown_xd_order`, `foreign_conflict`, `unavailable`) of the account's session, from any run kind (`continuous`, `eod`, `final`, `recovery`), **resolved or not**: a resolution (`accept_broker`, `dismiss_foreign`) explains it but never erases it from this count (P12-06 criterion 10).

## Goal
Say, from what is stored, whether an account has completed 30 consecutive counted semi-auto sessions, each with a human-confirmed order sent, both end-of-day reconciliations readable, and not one break; show every fact against it; never print MET on fewer, never count a session that cannot be proved clean.

## Scope
**In:** pure `Domain/Execution/PhaseCheck` (`ExecutionPhaseFacts`, `SessionClass`, `AccountStreak`, `ExecutionPhaseReport`, `ExecutionPhaseCheck.Evaluate`, the wording); Application `EvaluateExecutionPhaseCheckHandler` (read only) over a port `IExecutionRecordsReader` (adapter in Infrastructure over the mapped `Exec...Row` tables); verb `xd exec phase-check [--account ID] [--through DATE]` (a verb of the API host like `xd plan phase-check`); endpoint `GET /api/execution/phase-check`; the panel on the Modes tab (P12-10's page); contract; ADR.
**Out:** any table or migration; running tests; changing a mode or a setting; judging look-ahead or determinism (tests do); the profit of the strategy (P10/P11 reports); the decision to move to `auto_live` (the owner's two-step act, P12-07).

## Acceptance criteria
1. **Session classes (per account and trading day, in this order).**
   `out_of_mode`: the effective mode at 09:00 IST was not `semi_auto`, or a `mode_trail` row took effect after 09:00 and up to 16:30 IST. Not counted, not a break, but a demotion row in that span is a fact printed against the window.
   `broken`: mode `semi_auto` the whole session and any of: one or more `recon_breaks`; no `eod` or no `final` run, or either with `readable = false`, on a day that had a live order sent or a position carried (an `unavailable` run is not clean); a `protection_breach`, `flatten_started` or `oversold` alarm; a halt of trigger `reconciliation_break`, `protection_breach` or `oversold`.
   `idle`: mode `semi_auto`, no live entry sent, no position carried in, no working order, no break, and the account either `ready` or `not_ready` at the 09:10:30 mark (P12-11). Not counted, does not break.
   `counted`: mode `semi_auto` the whole session, at least one live entry sent after a `confirmed` ticket outcome, both runs present and readable, zero breaks, no alarm or halt above, the day's end flat or every carried position reconciled in the `final` run. *`SessionClassTests` (one case per clause, plus the precedence).*
2. **Streak and verdict.** From the account's window start (the effective date of the newest promotion row to `semi_auto`; a later demotion row or a promotion row starts a new window) to `--through`: `counted` adds 1, `broken` sets the streak to 0, `idle` and `out_of_mode` leave it. Verdict: **MET** when the streak at `--through` is 30 or more; **NOT MET** when the window holds a `broken` session and the streak is under 30 (the criterion has been violated since the window began; the report names the break and the date); **NOT EVALUABLE** otherwise (nothing against it, fewer than 30 so far, or no semi-auto window, or the reconciliation tables are empty). It is never MET on fewer than 30 counted sessions; before it prints MET, the code re-checks that the 30 final counted sessions are distinct, strictly ascending, in one window and each `counted` (anything else is NOT EVALUABLE, "malformed window"). *`ExecutionPhaseCheckTests`.*
3. **Hand table with the target lowered to 3 for the test** (the constant is 30): D1 counted (streak 1), D2 idle (1), D3 counted (2), D4 broken by a resolved `position_mismatch` (0), D5 counted (1), D6 `not_ready` day with a carried position and an unreadable `final` run, broken (0), D7 counted (1), D8 counted (2), D9 idle (2), D10 counted (3): MET at D10, label "MET (3 counted sessions since D7; 2 broken sessions earlier in the window, D4 and D6; 2 idle sessions)". At D9 the verdict is NOT MET (a broken session in the window, streak 2 of 3). With D4 and D6 clean it is NOT EVALUABLE at D9 ("2 of 3 so far"). *same.*
4. **Boundaries.** 29 counted → NOT EVALUABLE ("29 of 30, 1 more needed"); exactly 30 → MET; a break in session 31 after MET at 30 → as of the later `--through` the verdict is NOT MET (MET is an as-of statement; the report prints the date it first held). A session whose mode row takes effect at 09:00:00 exactly is in mode; at 09:00:01 it is `out_of_mode`. *same.*
5. **Environment.** An intent with `environment = 'sandbox'` never makes a session `counted` and never `broken`; a window with only sandbox activity reads NOT EVALUABLE with "sandbox sessions are not counted: n". *`EnvironmentTests`.*
6. **Human-confirmed only.** A live entry counts only if its intent has a `ticket_outcomes` row `confirmed` (actor `owner:`) that precedes `submitting` by at most 30 s (P12-08); a live entry without one (should be impossible) makes the session `broken` with reason `unconfirmed_entry` and is printed. *`ConfirmedEntryTests`.*
7. **The window end.** Default `--through` = the last closed session whose `final` run is due (16:30 IST plus a 10-minute grace; before that on the evening, the newest session is "not yet due" and the window ends the day before); an explicit date is taken as given (a non-trading date takes the session on or before it; a date after the newest recorded session is refused, problem `execution.invalid`). *`WindowEndTests`.*
8. **Per-session line** (in the object and the text): date, class, orders sent, tickets issued/confirmed/skipped/expired/refused, runs (`eod`, `final`: present, readable), breaks (count, kinds), alarms and halts by code, `day_state` at 09:10:30, minutes from the first ticket to its tap (median, `insufficient` below 5 tickets). *`ExecutionPhaseCheckTests`.*
9. **Facts printed beside the verdict (never part of it):** protection coverage (entries whose broker-side stop was confirmed within `exec.protect_deadline_s`, n of N; `empty` with no entries); kill-switch drills in the window (count, last date and result; the ladder gate needs one at most 30 days old); `not_ready` days at 09:10:30 (count, share); maximum sends per second seen (against the limit of 2 and the exchange threshold of 10); demotions in the window; double-submit attempts refused (P12-08 `alreadyDecided`); `algoId` present on n of N live legs; foreign orders listed; per-fill slippage as n and `insufficient` below 30 fills (the report is P11-03's). *`FactsTests`.*
10. **Boundary fact.** The data-side broker allow-list of `xd-api` still declares no order endpoint (read through P7-18's `IBrokerAllowList`, compared with its pin); a difference is printed as NOT MET for this fact and does not change the streak. *`BoundaryFactTests`.*
11. **Limits always printed**, in the object and every text, in all three outcomes (list under Honest limits). *`LimitsTextTests`.*
11a. **Canary precondition.** A live session counts only after the canary protocol has been recorded: `exec.canary_pending` OFF in the settings snapshot in force that day, which the owner turns off only after recording C1 and C2 (P12-00). A live session before that (quantity capped at 1) is `out_of_mode` for this measure and is printed as "canary session"; the report shows the recorded C1/C2 dates or "not recorded". *`CanaryTests`.*
12. **Deterministic text; exit code 0** whatever the verdict (a report, not a gate); 1 refused (bad `--through`/`--account`), 2 usage, 3 failure, 130 cancelled; the text keeps a reason on one line and prints `exitVerdict` as the bare word next to the labelled `exitCriterion`. *`ExecutionPhaseCheckOptionsTests`.*
13. **Read only.** A test lists every call on the records port and fails on anything that is not a read; running the check twice gives byte-identical output; no log line carries an account name, symbol or price. *`EvaluateHandlerReadOnlyTests`.*
14. **Endpoint.** `GET /api/execution/phase-check?through=&accountId=` returns `ExecutionPhaseCheckView { report, text }` on an empty database (NOT EVALUABLE, "no semi-auto window"), on a fixture of 31 sessions (MET), with one break (NOT MET), and refuses a later date with 422 `execution.invalid`; session required; never a token, client id or balance. *`ExecutionPhaseCheckApiTests`.*
15. **Panel.** The Modes tab shows per account the verdict chip (kit `VerdictChip`), "n of 30 counted sessions since <date>", the per-session table (class as icon + word), the last break with its kind and date, and the limits; `NOT EVALUABLE` and `NOT MET` are never green; the panel has no button that writes. *`PhaseCheckPanel.test.tsx` (MSW).*
16. Log ids 6750 to 6759 unique; `scripts/gen-api.sh` run; `scripts/check.sh` green; architecture tests unchanged.

## Contract
- **API:** `GET /api/execution/phase-check?through=YYYY-MM-DD&accountId=` → `ExecutionPhaseCheckView { report: { through, exitVerdict, exitCriterion, needed: 30, accounts: [ { accountId, name, windowStart, mode, verdict, streak, counted, idle, broken, outOfMode, firstMetAt?, lastBreak?, sessions[], facts{}, label } ], boundary, limits[] }, text }`; 422 `execution.invalid`. Read only.
- **CLI:** `xd exec phase-check [--account ID] [--through YYYY-MM-DD]`, `scripts/xd.sh exec phase-check`.
- **Data:** none, no migration. Reads the tables named in Needs through `IExecutionRecordsReader`; new indexes only if a plan needs `(account_id, session_date)` on `recon_runs` and `recon_breaks`.
- **UI:** panel on `/execution?tab=modes`.
- **Events/jobs:** none (an owner's read; not a service).

## Non-functional
Reads: one query per table per account for the window (at most 200 sessions); p95 under 300 ms for 60 sessions; a verb or an occasional page, not a polling target. Logs (ids 6750 to 6759): date, verdict word, counts.

## Test plan
Unit: classes, streak and boundaries (hand tables above); a property over 2,000 random session lists: the streak equals a reference implementation that rescans, the verdict is never MET with fewer than `needed` counted, an added break never turns NOT MET into MET, an added idle session never changes the verdict (negative control: an implementation that counts idle sessions is caught on at least 10 seeds). Integration (Testcontainers): the reader over fixture rows from P12-01/06/07/08 builders (31 clean sessions; a break on day 17; an unreadable `final` run; a sandbox-only history; a demotion on day 12 and re-promotion). API and CLI parsing. Frontend (MSW): the panel in each verdict. The real-data read is by `scripts/xd.sh exec phase-check` and is reported, not asserted.

## Decisions (researched)
- **D1. "30 sessions with zero breaks" means 30 consecutive counted sessions, and a break restarts the count.** Question: 30 sessions in total each clean, or 30 in a row? Answer: in a row, ignoring idle days. Reason: a break leads to a fix, and a fix changes the machinery that the earlier clean sessions were evidence for; the P7 exit uses the same strictness (a fail-closed day breaks the run, ADR 0097). Rejected: any 30 clean sessions out of the window (lets a break be averaged away).
- **D2. A session counts only if something happened and was proved.** An idle day proves nothing about reconciliation, so it is neither counted nor held against the account; a day with orders or a carried position but an unreadable or missing end-of-day run is broken ("unavailable is not clean", the owner's rule, P12-06 D8). Rejected: counting no-trade days (30 idle days would pass with no evidence at all).
- **D3. Resolved breaks still break.** Resolution explains; it does not make the day clean (P12-06 criterion 10). Rejected: only unresolved breaks count (the owner could clear the measure by clicking).
- **D4. Live environment only, human-confirmed only.** `semi_auto` means a person tapped; an entry without a confirmed outcome contradicts the mode, so the day is broken and printed. Sandbox is wiring evidence (P12-02 D7).
- **D5. A verdict is "as of" a date.** The report prints when it first held, and the later `NOT MET` after a later break does not rewrite the date; the phase-done step records the as-of date. Rejected: a stored, sticky MET (a second record to disagree with the rows).
- **D6. Extra facts are printed, not scored.** No composite "readiness score" (P8-00 D10); protection coverage, drills, not-ready days and slippage appear with their n beside the verdict because the criterion alone says nothing about them. The roadmap's single criterion is kept as the verdict.
- **D7. Per account; one account is enough for the phase.** The owner's live trading may be one account; `auto_live` is promoted per account on its own record (P12-07).
- **D8. Same shape as the P6 and P7 checks.** Three outcomes, caveat in the label, limits always printed, exit code 0, a verb and an endpoint over one handler, so the habit of reading a phase check is the same everywhere (ADR 0080, 0097).

## Risks and honest limits (printed in every outcome)
- **Calendar time.** Thirty counted sessions need at least thirty trading days with a human-confirmed live order and a clean day; the plan produces zero tickets on many days (filters, provisional plans, the four Soft checks without a source until P7-06 and P15, which keep `semi_auto` on explicit owner confirmation), so the real time may be several months. The roadmap's six weeks for P12 are build time, not this wall-clock; stated here and in the findings of the index.
- Zero breaks proves our records agree with the broker's data, not with the exchange's, and not that the strategy makes money (P10/P11 reports); a clean run shows the plumbing held.
- The count depends on P12-06's break definitions and its freeze behaviour; a loose definition makes the criterion easy, a strict one hard. Foreign (hand-typed) orders on the same account can create breaks; the runbook recommends trading by hand in another account on execution days (P12-06 risks).
- "Human-confirmed" is read from a database row that `xd_app` writes after the session and password checks; a compromised API process could forge it (the limit of P12-07 D10).
- Sandbox is excluded; the first live days therefore carry real money at the owner's chosen size (a one-share canary is the owner's first act, P12-00).
- Stored records only; the continuous runs are a view at a resolution of `exec.recon_interval_s` (default 60 s) so a break that appears and disappears between runs is not seen; hand-run or console actions at the broker are not recorded unless the reconciliation sees their effect; read caps (200 sessions) are printed when reached.
- Nothing is written, no test is run; look-ahead, determinism and the state machine are proved by tests, not by this check.
