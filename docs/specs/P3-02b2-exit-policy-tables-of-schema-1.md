## Goal
The five candidate exit policies and the two overlays that the strategy model already accepts by shape alone get their **parameter tables** (accepted, provisional until P4's spec: D17): the names, which are required, scalar or list, whole or not, the range of each value, the relations between values, the features each reads and on which timeframe, and the problem codes of a failing row. After this slice a stored strategy may use any of them, **but the tables are ACCEPTED and still PROVISIONAL until P4's spec** (D17): P4 has no spec and the walker (the break-even offset, whether a trail may move down, what activation means, a pyramid trail other than the ATR) does not exist, and nothing is stored before P3-02d, so a rename is free until the first stored use; the names P4 confirms become final by ADR 0036 Amendment 2 (the roadmap exit check, "final or renamed before any stored strategy uses them", allows exactly this); a definition with a wrong name, a missing field or an out-of-range number is refused by `StrategyCompiler.Compile` with a located problem, and a correct one compiles to an `ExitPlan` (or `OverlayPlan`) that carries the numbers, the defaults and the features P4's walker will need. **The simulator does not run any of them in this slice** (D2): a correct definition still reaches `Simulator.Create` and is refused there as `simulation.unsupported_exit`, exactly as today.

## Scope
**In:**

2. **What the shape-only check cannot express**, added to the table machinery as data or as one small relation check per policy (D11): a whole-number flag, a relation between two parameters of one policy (`t2_rr` above `t1_rr`; `add_at_rr` increasing; `add_pct` as long as `add_at_rr`; `initial_pct` plus the sum of `add_pct` at most 100; `max_adds` at most the length of `add_at_rr`), and three facts from outside the policy that the overlays need (the style, the minutes of E, `max_hold_sessions`): `ExitCompiler` receives the side, the style and the evaluation timeframe, and the `max_hold_sessions` as written. **Plumbing (verified in `StrategyCompiler.cs`): `SideCompiler` is constructed with `(sink, declared)` and compiled with `(rules, side, tf)` and has neither the style nor the session rules, and `TimeRulesCheck.Check` runs after the side (line 59 against line 45).** So `StrategyCompiler` passes `definition.Style` and the *raw* `definition.TimeRules?.MaxHoldSessions` through `SideCompiler.Compile` into `ExitCompiler`; it does **not** move `TimeRulesCheck` before the side (that would change the order of the problems, P3-02b criterion 27), and the time rules are still checked and reported once, where they are now. ## Definitions
Numbered so that the criteria and the later P4 spec can cite them. "E" is the evaluation timeframe of the compile; "T" the minutes of E (5, 10, 15, 30, 60; 1D only for a swing side); a value that names a declared param is resolved to its number before any range or relation is checked (P3-02b criterion 12). Names are lower case with underscores, as in doc 16. A *scalar* takes exactly one value, a *list* one to ten (`ExitTables.MaxListValues`). "Whole" means an integer value; "catalog" means the range and the whole-number rule come from the indicator catalog (`feature_invalid`), as `atr_period` does today.

**D1. The code of a failing row is one of the existing ones, by rule.** A missing required field is `field_missing` at `buy.exits[i].<name>`; a name the policy does not have is `field_not_used`; the wrong count of values (a list where a scalar is wanted, none, more than ten, a name given twice) is `field_shape`; a number outside its bounds is `value_out_of_range` at the field (at `<name>[j]` for the *j*th value of a list); a period, lookback or length the catalog refuses is `feature_invalid` with the catalog's message; **a relation between two values of the policy is `value_out_of_range` at the value that breaks it** (the one rule that P3-02b already gives for `add_pct`); a list whose length must equal another's is `field_shape` at the list that is wrong; a policy or an overlay twice is `duplicate_exit`. **A non-whole value in a whole-number field that does not feed a catalog feature (`max_adds`, `intraday_bars`, `swing_sessions`, `days_before_results`) is `field_shape` at the field**, as the roadmap row asks; `atr_period`, `lookback_bars` and `length` feed a catalog feature, keep the catalog's `feature_invalid` as `atr_period` has since P3-02b (criterion 11) and as the stop fields do, so that one rule judges one feature (open question 5 asks whether to change that). The checks run in the order of the table, so the problems of one exit come in a fixed order; a first error in an exit does not stop the checks of its other fields (every field is reported), except that a relation is checked only when all the values it compares compiled.

**D2. The model may describe what the simulator cannot run.** The compile accepts a correct table for every policy and overlay and says nothing about the simulator; `Simulator.Create` refuses a side whose exits are not exactly one `FIXED_RR` with one `rr` value, or that has an overlay, as `simulation.unsupported_exit` at `buy.exits` / `buy.overlays[i]` (verified in `Simulator.cs`, `RefuseWhatItCannotRun`), after the compile has succeeded. Hence: a **bad** table is a compile problem (`strategy.model.*`, reported by every host that compiles, including `Simulator.Create`, which returns the compile's problems unchanged when the compile fails: `Simulator.cs` line 80 is the call; the exact path of the report is UNVERIFIED and the test of criterion 13 reads it); a **good** table that P3 cannot run is the simulator's named refusal. This is the rule of P3-02b scope item 6, unchanged. The only warning the compile adds is D14.

**D3. `PARTIAL_BE` (doc 08: "Book x% at T1, stop to breakeven, rest at T2").** Reads no feature.
| Parameter | Shape | Required | Whole | Range |
|-----------|-------|----------|-------|-------|
| `book_pct` | scalar | yes | no | (0, 100) |
| `t1_rr` | scalar | yes | no | (0, 10] |
| `t2_rr` | list | yes | no | each in (0, 10], **each above `t1_rr`** |

Names are doc 16's (`book_pct`, `t1_rr`, `t2_rr`); doc 08's "x, T1, T2" is their prose. `t2_rr` is a list so the Lab can compare targets (doc 16: `t2_rr: [2.0, 3.0]`); a scalar can be written as a list of one. The range of `book_pct` and `t1_rr` is the one `PARTIAL_TRAIL` already has, so that two partial exits cannot disagree on what a percentage is. Break-even is the entry price: whether it includes costs (a stop at entry plus the round-trip cost) is P4's walker rule, not a parameter in schema 1.

**D4. `ATR_TRAIL` (doc 08: "Chandelier/ATR trail after activation: period, multiple, activate_at").** Reads `atr(atr_period)` on E.
| Parameter | Shape | Required | Whole | Range |
|-----------|-------|----------|-------|-------|
| `mult` | list | yes | no | each in (0, 20] |
| `activate_at_rr` | scalar | yes | no | [0, 10] (0: trailing from the entry) |
| `atr_period` | scalar | no (14) | yes | catalog (as `PARTIAL_TRAIL`) |

`mult` is doc 16's name; it is not `trail_atr_mult` because the policy name already says ATR, and it is a list because doc 16 gives a list (`mult: [2.0, 3.0]`). `activate_at_rr` is **required**, not defaulted to doc 16's 1.0: a stored strategy is self-contained (P3-02b, *Names*), and a default that lives in the compiler would change the meaning of an old hash if it were ever changed. `atr_period` is the one default, because the catalog owns it, and it is written into `ExitPlan.Values` (D12) so that the plan, and the run record that stores it, show it.

**D5. `STRUCTURE_TRAIL` (doc 08: "Trail beyond prior swing / previous candle: lookback").** Reads `lowest(lookback_bars, source=low)` on E for BUY and `highest(lookback_bars, source=high)` for SELL, the same N-bar extremes as the `swing_low` and `swing_high` stops (P3-02b open question 4: a pivot is known n bars late and may not exist; an N-bar extreme is always ready after N bars).
| Parameter | Shape | Required | Whole | Range |
|-----------|-------|----------|-------|-------|
| `lookback_bars` | scalar | yes | yes | catalog (`lowest`/`highest` `n`: 1 to 10,000) |

The name is doc 16's (`lookback_bars`), not the stop's `lookback`: UNVERIFIED which spelling the owner prefers (open question 2). "Previous candle" is `lookback_bars` 1. The extreme includes the bar that just closed (ADR 0031: the catalog's `lowest` includes the current bar); whether the walker trails under the extreme of the *last closed* bar, which is the only look-ahead-safe reading, is D13 and P4's rule.

**D6. `EMA_TRAIL` (doc 08: "Exit on close beyond EMA: length").** Reads `ema(length)` of the close on E.
| Parameter | Shape | Required | Whole | Range |
|-----------|-------|----------|-------|-------|
| `length` | scalar | yes | yes | catalog (`ema` `n`: 1 to 10,000) |

The name is doc 08's. It is a **scalar** (doc 08 says "length"; doc 16 does not list `EMA_TRAIL`): a list can be allowed later by relaxing the shape of one row, which breaks no stored text, whereas a scalar cannot be recovered from a stored list. Open question 3 asks the owner. It is an *exit on the close beyond the EMA* (a signal at the close of an E bar, not a stop that rests): that is the walker's meaning (P4); the compile only declares the feature.

**D7. `PYRAMID` (doc 08 §4: initial 50 %, adds at +1R and +2R of 30 % and 20 %, max adds 2, "move stops so total open risk is at most the initial 1R").** Reads `atr(atr_period)` on E (for the trail of the combined position).
| Parameter | Shape | Required | Whole | Range |
|-----------|-------|----------|-------|-------|
| `initial_pct` | scalar | yes | no | (0, 100] |
| `add_at_rr` | list | yes | no | each in (0, 10], **strictly increasing** |
| `add_pct` | list | yes | no | each in (0, 100]; **as many values as `add_at_rr`**; `initial_pct` + sum of all `add_pct` at most 100 |
| `max_adds` | scalar | yes | yes | 1 to the length of `add_at_rr` |
| `trail_atr_mult` | scalar | yes | no | (0, 20] |
| `atr_period` | scalar | no (14) | yes | catalog |

Doc 16's `cap_total_risk_to_initial: true` and `trail: ATR_TRAIL` are **not parameters of schema 1**: the risk cap is the *rule* of doc 08 §4 and is always on (accepting `false` would be another policy, and a boolean has no place in `ExitParameter`, whose values are numbers or param names); the trail of the combined position is the ATR, written `trail_atr_mult` + `atr_period` exactly as `PARTIAL_TRAIL` writes doc 11's `trail: { type: ATR, mult }` (P3-02b hand-off (d), which P3-02c implements). A definition that gives `cap_total_risk_to_initial` or `trail` gets `field_not_used` whose message says the rule is always on, or that the trail is `trail_atr_mult`. A pyramid that uses a different trail (a structure or EMA trail of the combined position) is not in schema 1 and would be a new row. The sum is taken over **all** values of `add_pct`, not over the first `max_adds`: the list is what is written, `max_adds` can only lower the number used, so the rule does not depend on a second field. `max_adds` may be below the length (try fewer adds without rewriting the lists).

**D8. Overlay `time_stop` (doc 08 §5: "e.g. below +0.5R after 6 bars" intraday, "after 2 sessions" swing).** Reads no feature.
| Parameter | Shape | Required | Whole | Range |
|-----------|-------|----------|-------|-------|
| `min_progress_rr` | scalar | yes | no | [0, 10] |
| `intraday_bars` | scalar | **intraday strategy only** | yes | 1 to `(375 + T − 1) / T` (integer division) |
| `swing_sessions` | scalar | **swing strategy only** | yes | 1 to 5, **below `max_hold_sessions`** |

Exactly one of the last two is given, decided by the **style** of the definition: an intraday strategy gives `intraday_bars` (a `swing_sessions` is `field_not_used`) and a swing strategy `swing_sessions` (an `intraday_bars` is `field_not_used`), so a stored time stop is never ambiguous. The upper bound of `intraday_bars` is a session of 375 minutes (09:15 to 15:30) in whole bars of E rounded up, the formula of the roadmap row: 5m 75, 10m 38, 15m 25, 30m 13, 1h 7. `swing_sessions` at or above `max_hold_sessions` could never fire before `MAX_HOLD` leaves, so it is `value_out_of_range` at `swing_sessions` (a time stop of N sessions leaves at the close of session N, the same moment `MAX_HOLD` N would; "below" keeps the overlay meaningful). Doc 16's `enabled: true` is not a parameter: an overlay that is listed is on (P3-02b open question 5); `enabled` is `field_not_used`.

**D9. Overlay `event_exit` (doc 08: "Exit before results: days before").** Reads no feature (needs the results calendar, P15).
| Parameter | Shape | Required | Whole | Range |
|-----------|-------|----------|-------|-------|
| `days_before_results` | scalar | yes | yes | 1 to 10 |

The bound 10 is a sanity bound of this spec (a fortnight of trading days is not "before results"); doc 16 has 1. `enabled` as in D8. It compiles with the warning of D14.

**D10. The two tables already checked** are not changed: `FIXED_RR` (`rr`, list, each in (0, 10]) and `PARTIAL_TRAIL` (`book_pct`, `t1_rr`, `trail_atr_mult`, optional `atr_period`). `PARTIAL_TRAIL` stays provisional with the rest (D17; it gains the `exit_not_evaluated` warning); `FIXED_RR`, the policy the simulator runs, is the only one whose names are not provisional.

**D11. Relations and outside facts.** Relations are checked after the fields compile and only among the values that compiled (D1): `PARTIAL_BE` `t2_rr[j] > t1_rr`; `PYRAMID` `add_at_rr[j] > add_at_rr[j-1]` (reported at `add_at_rr[j]`), `add_pct` length equals `add_at_rr` length (at `add_pct`), `initial_pct + sum(add_pct) <= 100` (at `add_pct`, the message gives the sum), `max_adds <= add_at_rr.length` (at `max_adds`); `time_stop` the style rule, the `intraday_bars` bound from T, and `swing_sessions < max_hold_sessions` (the raw `definition.TimeRules.MaxHoldSessions`, passed down by `StrategyCompiler`; the time rules are checked *after* the side, so the compiled `SessionRules` does not exist yet; when the value is absent, not whole or outside 1 to 5 the bound is not checked, the time rule's own problem is reported once by `TimeRulesCheck`; with `max_hold_sessions` 1 no `swing_sessions` can be valid, since the range 1 to below 1 is empty, and the time stop is reported at `swing_sessions` with a message saying so: a swing strategy that holds one session has nothing to time out). The parameters of the stop and the other exits are not compared with these (an `ATR_TRAIL` and a `PYRAMID` may both be candidates).

**D12. The features and the plan.** Each ATR-reading policy (`ATR_TRAIL`, `PYRAMID`) builds `atr` from `IndicatorInfo.DefaultSpec(E)` with `P1 = atr_period`, exactly as `PARTIAL_TRAIL` does; `STRUCTURE_TRAIL` builds `lowest(n, source=low)` for BUY and `highest(n, source=high)` for SELL; `EMA_TRAIL` builds `ema(length)` of the close; all on E and all checked by `CatalogCheck` (a period or length the catalog refuses is `feature_invalid` at `atr_period`, `lookback_bars` or `length`). They go into `ExitPlan.Reads`, are merged into `CompiledSide.Features` after the stop's and in `Exits` order, and are deduplicated by the canonical spec (an `ATR_TRAIL` and a `PYRAMID` with the same `atr_period` share one `atr(14)`; a `STRUCTURE_TRAIL` with `lookback_bars` 5 and a `swing_low` stop with `lookback` 5 share `lowest(5, source=low)`). `ExitPlan.Values` carries every parameter by name as numbers, **defaults included** (`atr_period` 14 when not written). The side (BUY or SELL) is passed to `ExitCompiler` for the choice of `lowest` or `highest`. No overlay reads a feature.

**D13. The look-ahead rules for the exits.** (a) **Timeframe:** every feature an exit policy reads is a plain feature on E, never `tf()` of another timeframe and never a lagged or subscripted read: the exit tables have no field that takes an expression, so the language's look-ahead lint (ADR 0034) has nothing to rule on; the rule is structural and tested (criterion 9). (b) **As of the closed bar:** `ExitPlan.Reads` are values *as of the closed bar of E*; the plan contract is that a value computed at the close of bar *k* may move a stop or signal an exit only from the first minute after bar *k*'s close (never inside bar *k*), because at that minute the value is first knowable. The compile cannot enforce what the walker does with the number, so the rule is written here, in doc 08 §2 and in ADR 0036 Amendment 1, and **P4's spec must carry it as a property** (truncating all data after bar *k* does not change any exit decision at or before *k*; a negative control that uses bar *k*'s value inside bar *k* fails it, the pattern of ADR 0037's seam properties). (c) **Readiness:** a feature that is not ready (the ATR before bar 14 of the data) gives no trail update; the compile does not guess a minimum history for the exits (P4 decides whether the entry is walked, or the policy waits). (d) **Entry-time knowledge:** `time_stop` and `event_exit` use only quantities known at the entry (the number of bars or sessions since the fill, the progress in R, the results date): none reads a bar after the position closes.

**D14. The new code.** `strategy.model.exit_not_evaluated`, **warning**, path `buy.exits[i]` or `buy.overlays[i]` (and under `sell`), **one per exit policy or overlay that no simulator runs yet**: every candidate except `FIXED_RR` and every overlay (`PARTIAL_BE`, `PARTIAL_TRAIL`, `ATR_TRAIL`, `STRUCTURE_TRAIL`, `EMA_TRAIL`, `PYRAMID`, `time_stop`, `event_exit`); the message names the policy and says that nothing runs it yet (P4; for `event_exit` also that the results calendar, P15, is missing). The name follows `filter_not_evaluated` (`<thing>_not_evaluated`, snake case, declared once in `ModelCodes` with the `strategy.model.` prefix). **How it differs from the simulator's refusal:** the warning is a *model-time hint* on the located exit, given to every host that compiles (the Lab editor, a future validator), whether or not a simulator is ever asked; `Simulator.Create`'s `simulation.unsupported_exit` is the *run-time refusal*, one problem at `buy.exits` or per overlay, and stays unchanged. The warning list of the compile is a list of what the author should know; it never blocks. Which policies are "run" is one constant of the library (`ExitTables.RunBySimulator`, today `FIXED_RR`) that P4 edits when it builds a walker, together with the refusal in `Simulator.cs`; a test asserts the two agree (criterion 13). Warnings count in the cap of 100 like every other.

**D15. Error order.** The problems of the exits keep the order of P3-02b criterion 27 (exits, then overlays, each in list order, fields in table order); the new warning follows the errors, like every warning.

**D16. Schema 1 identity, hashes and goldens.** The records, the enums and `StrategyDefinition.CurrentSchema` do not change; a definition that compiled before and uses a name the new table does not have (`atr_mult`, `lookback`, `ema_len`, `minutes`) **stops compiling**: that is the provisional rule of ADR 0036 decision 15 and is allowed because no stored strategy uses these policies (the three built-ins use `FIXED_RR` only; storage is P3-02d). Everything else is byte-identical: `DefinitionJson` writes a definition from the records, not from the compile, so the canonical JSON of every definition that has ever been run, and therefore every run-record definition block and every golden file of the simulator, is unchanged; the engine `sim-5`, the run-record schema 5 and `SimTrade` schema 4 are not changed, there is no new event id (the last is 4414) and no new ADR number (the next free is 0045, unused). For P3-02c: the stored (YAML) spelling of every parameter in D3 to D9 is the name in the table; `trail`, `cap_total_risk_to_initial` and `enabled` are refused by name with the messages of D7 and D8; and a default written into `ExitPlan.Values` (only `atr_period`) is not part of the canonical text, so two definitions that differ only by writing `atr_period: 14` or omitting it are **different** definitions with different hashes and the same plan (the hash question of the printed `rsi()` against `rsi(14)` in the P3-02 Follow-ups, of the same kind, belongs to P3-02c).

**D17. Status of the tables and what is documented.** The tables are **ACCEPTED, PROVISIONAL until P4's spec**: P4 has no spec and no walker, so the break-even offset, the rule that a trail never moves down, what "activation" means, the pyramid trail other than the ATR and the per-bar series are not known; nothing is stored before P3-02d (storage), so renaming a parameter now is free. The names that P4's spec confirms (or changes) become final by **ADR 0036 Amendment 2**; the roadmap exit text "final or renamed before any stored strategy uses them" allows this. No claim of finality is made in the Amendment, doc 08, doc 16 or the snapshot comment; schema 1 is unchanged. ## Acceptance criteria
Numbered, each testable. The tables of the tests are literals written from the tables of this spec, not driven from `ExitTables`, so that a renamed parameter or a changed bound fails one of the two. Every parameter of every table has a **failing row** (exact code, path, severity) and a **near miss** (the value next to the bound, which compiles without that problem); the convention test over `ModelCodes` (P3-02b criterion 1 and *Test plan*) fails for any code without a failing example, so `exit_not_evaluated` has one.

1. **Valid examples.** Each of these compiles with no error on BUY and on SELL at E = 15m (`time_stop` also on a swing 1h strategy), with a plan that equals the figures: `PARTIAL_BE` `book_pct` 50, `t1_rr` 1, `t2_rr` [2, 3] (reads nothing); `ATR_TRAIL` `mult` [2, 3], `activate_at_rr` 1 (reads `atr(14)`, `atr_period` 14 in `Values`); `STRUCTURE_TRAIL` `lookback_bars` 3 (BUY reads `lowest(3, source=low)`, SELL `highest(3, source=high)`); `EMA_TRAIL` `length` 20 (reads `ema(20)`); `PYRAMID` `initial_pct` 50, `add_at_rr` [1, 2], `add_pct` [30, 20], `max_adds` 2, `trail_atr_mult` 2 (reads `atr(14)`); `time_stop` `min_progress_rr` 0.5, `intraday_bars` 6; `event_exit` `days_before_results` 1 (each of these but `FIXED_RR` also gives one `exit_not_evaluated` warning, D14). ## Open questions
To answer by number, as for P3-02b. Each has a recommendation first.
1. **Is the model allowed to describe exits the simulator cannot run (D2)?** The alternative is to refuse them at compile until P4, which would make the tables untestable end to end and contradict P3-02b scope item 6. **Recommendation:** yes; a correct table compiles, the simulator refuses by name (`simulation.unsupported_exit`), a bad table is a compile problem.
2. **The names.** Doc 16 and doc 08 disagree and the roadmap asks to settle them: `ATR_TRAIL` `mult` (doc 16) against `trail_atr_mult` (`PARTIAL_TRAIL`); `STRUCTURE_TRAIL` `lookback_bars` (doc 16) against `lookback` (doc 08 and the stop); `EMA_TRAIL` `length` (doc 08; not in doc 16); `activate_at_rr` (doc 16) against `activate_at` (doc 08); `PYRAMID` has no doc 16 name for the trail. **Recommendation:** doc 16's names where doc 16 has one (`mult`, `lookback_bars`, `activate_at_rr`, `t2_rr`, `add_at_rr`, `add_pct`, `max_adds`, `initial_pct`), doc 08's `length` for `EMA_TRAIL`, and `trail_atr_mult` + `atr_period` for the `PYRAMID` trail; doc 08 and doc 16 are edited to say so. The cost of a rename after this slice is a schema change, so this is the question to answer carefully; no stored strategy uses a name yet.
3. **Which numeric fields are lists (the Lab compares candidate values per policy, doc 08 §3)?** Here: `rr`, `t2_rr`, `mult`, `add_at_rr`, `add_pct` (doc 16 gives lists for exactly these) and scalars elsewhere (`length`, `lookback_bars`, `activate_at_rr`, `book_pct`, `t1_rr`, `initial_pct`, `trail_atr_mult`, `max_adds`). Relaxing a scalar to a list later breaks no stored text; the reverse does. **Recommendation:** as above; P4 relaxes a field when it needs to compare it.
4. **`PYRAMID`: drop `cap_total_risk_to_initial` and `trail` (D7)?** The cap is the always-on rule of doc 08 §4; the trail is the ATR written as `trail_atr_mult`. The alternative keeps a boolean and a policy name in the model, which the records cannot hold without a change of schema. **Recommendation:** drop them, edit doc 16, and refuse them by name with the explanation (D7). **This is an explicit precondition of Approving this spec** (it changes written config names, doc 16's `cap_total_risk_to_initial`, `trail` and the overlays' `enabled`): the owner answers it before the build starts.
5. **Which code for a non-whole value in `atr_period`, `lookback_bars` and `length` (D1)?** The roadmap row says `field_shape` for a non-whole value in a whole-number field of an exit; P3-02b criterion 11 says `feature_invalid` for `atr_period` 14.5 (the catalog's message). **Recommendation:** `feature_invalid` for the three that feed a catalog feature (one rule judges one feature, and the catalog's message names the range) and `field_shape` for the four that do not; the roadmap row is read as "the fields that are not catalog parameters". If the owner wants the row's literal reading, `atr_period` changes code (a change to an Approved criterion and its test) and the build cost is 0.1 day.
6. **`time_stop` by style (D8): exactly one of `intraday_bars` and `swing_sessions`, by the style of the definition, and `swing_sessions` below `max_hold_sessions`. This is a design change of doc 16's example** (one overlay with both fields), so it is the owner's call. The alternative accepts both and lets the walker choose, which makes a stored time stop mean two things. **Recommendation:** by style, strictly; with `max_hold_sessions` 1 a swing time stop cannot be written (AC7).
7. **`exit_not_evaluated` as a warning (D14).** The alternative is no warning, the simulator's refusal being the only signal. **Recommendation:** add it, one code; it mirrors `filter_not_evaluated` and tells the author at edit time.
8. **Should `Simulator.Create` name the unsupported policy (`buy.exits[i]`)?** Today one problem at `buy.exits` names `FIXED_RR`, not the policy the author wrote. **Recommendation:** not in this slice (it touches the Simulation project and its tests and is not needed by the tables); fold it into P4's first slice when the simulator starts running some of the policies and the refusal is rewritten anyway.
9. **A `PYRAMID` outside its stated use ("mostly 30m+ and swing", doc 08 §4)**: no compile check or warning. **Recommendation:** none; it is a trading judgement the Lab's evidence (P4) answers, not a model rule.
10. **Written together with P4 (the roadmap row).** P4 has one roadmap row and no spec, so "together with P4" cannot be literal and the tables cannot honestly be final. **Recommendation:** approve the tables here as **ACCEPTED, PROVISIONAL until P4's spec** (D17), from doc 08, doc 16 and the walker's needs as they are known (the features of D12 are what P4's per-bar series must carry); P4's spec confirms or renames them by ADR 0036 Amendment 2 before P3-02d stores any strategy that uses them.

## Risks
- **The names are guessed after all.** P4 may find a policy needs a field these tables lack (for example a trail that never moves down, a time of day, a different break-even offset). Mitigation: adding an optional field is additive; a required one is not, so the required set is the smallest doc 08 and doc 16 justify; D3 and D4 leave the break-even offset and the trail's monotone rule to the walker, as constants of P4, not parameters.
- **A hidden default.** `atr_period` 14 is a default in the compiler; a change to the catalog's default would change what an old hash means. It is the one default, written into the plan (D12) and pinned by a test; every behaviour number is required (D4's `activate_at_rr`).
- **Tightening an Approved contract.** Definitions that compiled by shape no longer do (D16), and the doc 11 example gains a warning. Mitigation: no stored strategy uses the policies; the edited tests are listed (*Contract*); the P3-02b text and ADR 0036 decision 15 announce it. The order of the problems for a definition that compiles today is unchanged: the time rules are not moved before the side (scope item 2) and a test asserts the same order for an unchanged definition (P3-02b criterion 27, D15).
- **A look-ahead that the library cannot see.** The compile declares the features, the walker uses them; a P4 walker that applies the close of bar *k* inside bar *k* would leak. Mitigation: D13(b) and the property P4's spec must carry; the library has no handle on it (UNVERIFIED how the per-bar series of the roadmap's open design point will be emitted).
- **Underestimate.** About 110 new table rows, the plumbing through three classes, the edited tests listed in *Contract* and five fixture sites: 1.6 days with the table machinery extending cleanly; if the relations need a new abstraction the slice reaches 1.9; still inside 1 to 3.
- **Per-session behaviour of the reads (UNVERIFIED).** The catalog marks `atr`, `ema`, `lowest` and `highest` as continuous across sessions (read in `IndicatorCatalog.cs`); whether an intraday `STRUCTURE_TRAIL` on the first bars of a session should reach into yesterday's bars is a trading question for P4, and ADR 0035's per-session features may be the better reading; the table does not decide it (the feature is the catalog's default spec).
