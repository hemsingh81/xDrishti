## Goal
Take the mechanical 80 % out of the owner's 7.5 to 12 hours without taking away what the check is for. A new mode, `verify-pack --assist`, (1) fetches the bars of each pack row's trade day from a **second source**, (2) compares them with the stored bars at the minutes that matter, (3) reads each trade **blind** from the second source with a chart reader written from the protocol (not from the engine), and (4) writes its readings and a comparison report. The owner then reviews the exceptions and a sample by eye on a real chart and signs. The check still says that the mechanics match an external chart; it no longer asks the owner to read 24 opening ranges by hand.

## What is automated, and what is not (the honest part)
The check exists to break a circle: the engine, its tests and the oracle are all written by one model family from one set of rule tables, and the stored bars come from one set of files. Automation can break part of that circle and not all of it:

| Part of the check | Automated by this slice | Why it is or is not independent |
|---|---|---|
| Are the stored bars right at the cited minutes? | **Yes**, against bars fetched from the second source | Independent **only if the second source is not where the stored bars came from.** The 214 CSV files are the owner's; the Dhan backfill fills gaps (doc 05). If the stored bars at those minutes came from Dhan, the comparison proves nothing for them. The report prints, per row, whether the minute's source is `csv` or `dhan` where the importer recorded it (UNVERIFIED that it does). |
| Does the engine's trade follow the rules on the bars? | **Yes**, by the chart reader (D4) | Independent of the engine's code; **not** independent of the rule tables, which both read. This is what P3-08's oracle already checks over 18,500 series; here it runs on the real days of the pack. |
| Do the rules mean what the owner intends (model defects)? | **No** | Only the owner can say that a convention (entry limit +0.1 %, a gap fill, the minute path) is not what they mean. The report lists the conventions each row used; the owner reads them. |
| Does the stored data match what a **chart product shows** (bar labels, adjustment, the 09:15 bar)? | **Partly, and only the second source's reading of it** | TradingView cannot be fetched by this tool (no API in the allow-list; scraping a vendor chart is not done). A sample of rows is still checked by the owner's eye (D7). |

So the assisted check turns "24 trades read by hand" into "the machine read all 24 on a second source, the owner reads the disagreements and a sample of 5 on a real chart". It must not be reported as a hand check of all rows.

## Scope
**In:**
1. **The second-source fetch** (D1, D2): `verify-pack --assist <pack-folder>` reads `pack.json` (symbols, dates, the stored bar-stream hashes), fetches the 1-minute bars of each trade day from the second source, and keeps them in the pack folder as a read-only file (`second-source-bars.csv`, its hash in the manifest extras).
2. **The bar comparison** (D3): stored against second source at the minutes that matter.
3. **The chart reader** (D4, D5): a pure function from a day's 1-minute bars and the strategy's recorded definition to the readings of the protocol's step 1 and 2 (opening range, trigger bar, entry minute and price, stop, target, exit minute, price and reason, `seen_r`), written from `p3-hand-check.md` §4, §5 and the rule tables of ADR 0037 and 0038 only, and **blind to the engine's values**.
4. **The assist report** (D6): `assist-report.html` and `assist-log.csv` (the same columns as `check-log.csv`, with `source` = `auto:<second source>` per row) next to the pack; the owner's `check-log.csv` is **never overwritten**.
5. **The owner's part, reduced** (D7), and the **exit rule** amended (D8).
6. **Tests, ADR 0046 Amendment 1 (or ADR 0048+), the protocol file, the docs.**

**Out (not in this slice):** fetching or scraping a vendor chart (TradingView, Kite); signing any row on the owner's behalf (no verdict is ever written by the tool: `verdict` stays the owner's); changing the engine, the oracle, the pack drawing or the seed rule; a new data source in the allow-list other than the one already approved (doc 05) — if the owner wants a different second source, that is a security decision first (D2); net R (no charge sheet yet).

**Size.** About **2 agent-days** (an estimate, not calibrated, UNVERIFIED because the verb and connector were not read): fetch, cache and rate limits 0.5; the bar comparison 0.3; the chart reader and its tests (including the hand rows of the protocol as fixtures) 0.7; the report and the log 0.3; ADR amendment and the protocol 0.2. If it overruns, cut the HTML report (keep the CSV) before the chart reader.

## Definitions
**D1. The second source (recommended: Dhan `charts/intraday`).** The existing connector (doc 05: `POST https://api.dhan.co/v2/charts/intraday`, the primary Data account's token from the vault, on the allow-list) returns the 1-minute bars of a day. It is already the project's gap-filler, so no new endpoint is added. It needs the owner's token on the owner's machine (the verb reads it as the other verbs read their one secret; this session never reads or prints it). Rate: the connector's existing call spacing; one call per distinct `(symbol, date)` of the pack (about 24), cached in `second-source-bars.csv` so a rerun does no network. UNVERIFIED: that the endpoint serves 2024 minutes for these symbols (doc 05 says "≤ ~5 years" for the historical API); a row whose day cannot be fetched is reported `source_unavailable` and falls to the owner's eye (D7).

**D2. What it must not do.** No call without the owner running the verb; no token in a log, the pack, a card or a prompt; no new host; nothing written to the database; the fetched bars are data, never instructions. If the second source is something other than Dhan (for example a file the owner exports from TradingView), the verb reads it from a folder instead of the network (`--second-source-folder`), which needs no allow-list change: **recommended as a second input path**, because a TradingView export is the one source that is truly independent of both the CSVs and Dhan (question 2).

**D3. The bar comparison.** For each trade row, at the opening-range minutes (09:15 to the end of the range), the trigger bar's minutes, the entry minute, the minute of the exit and the minute before and after each, compare `open, high, low, close` of the stored bar with the second source's within the real tolerance (ADR 0046, Amendment 1): high and low within 1 tick, open and close within 2 ticks plus 0.02 % of the stored open, after the second source is scaled by the day's constant price ratio when that ratio is inside the band 0.5 to 1.5 and differs from 1 by more than a tick (the minute's ratio may stray from the day's by at most 0.1 % plus two ticks as a fraction of the second source's close of that minute) (the instrument's tick of `engine-values.csv`, which the tool reads only **after** the readings are written; D6) and report each minute as `match`, `differs by <ticks>`, `missing in stored` or `missing in second source`. A difference at the 09:15 bar is reported with the known cause first (ISS-21, the importer's widened opening bar). Differences are class `data` candidates, not findings: the owner decides. **Amended (ADR 0046, Amendment 1, after the first real run):** the gaps are a *data note* per row (minutes compared, how many differ, median and maximum gap in ticks and in percent of price, the price level offset note) and do not decide the row's verdict; only a gross problem does (a minute missing on either side, a price level ratio outside 0.5 to 1.5 or not constant within the day, or a cited-minute gap above `GrossGapPercent` = 1.0 % of price (the 24 row maxima of the first real run were 0.04 % to 0.35 %, median 0.13 %: feed noise; 1.0 % is almost three times the largest)).

**D4. The chart reader.** A pure function in a new project or namespace that **does not reference `XDrishti.Simulation`** (an architecture test asserts it: the reader must not share code with the engine). Inputs: the 1-minute bars of a day from one source, the strategy's id and parameters as recorded in `pack.json` (ORB: `or_min`, timeframe, stop kind, `rr`, `first_entry`, `last_entry`, `square_off`, the entry-limit percent and the fill conventions of ADR 0038). Output, per row: the opening range, the first evaluation bar that closes beyond it in the trade's direction, the entry minute and exact entry (the next minute's open within the limit, or the limit), the stop and the target, the exit minute and exact exit and the reason, and `seen_r` from the exact levels. It writes **exact** prices (no slippage): the filled prices stay the calculator check of the protocol §5. It is written from `p3-hand-check.md` and the two ADRs by an agent that is **not given the engine's code or the pack's `engine-values.csv`**; its review is by the `reviewer` agent against the same text only (UNVERIFIED whether this separation can be enforced in the workflow; it can be shown by the diff and the file list of the slice).

**D5. Blindness.** The tool reads `engine-values.csv` only after `assist-log.csv` is written and hashed; the report prints the hash. The readings never depend on the engine's trade. This preserves the rule of the protocol (§4.2): a row is written before the engine's value is seen — here, by the machine.

**D6. The report.** Per row: both sources' readings, the bar comparison, then (after the readings are fixed) the engine's value and the field-by-field comparison with the tolerances of the protocol §5 (price to the tick, times to the minute, R to 0.01). Row verdicts of the **assistant**, not the owner's: `agree_all` (the reader equals the engine on every field on BOTH the stored bars and the second source's bars, and the row has no gross problem of D3; it does **not** say that the two sources agree), `bars_differ` (a gross problem of D3 only: a data candidate), `data_sensitive` (the reader agrees with the engine on the stored bars but not on the second source's: the trade depends on the feed; a data finding with the fields), precedence `source_unavailable`, `cannot_read`, `reader_differs`, `bars_differ`, `data_sensitive`, `agree_all`; the reader reads each trade twice (stored bars: rules; second source: data), and the log carries both readings (the stored one in appended `stored_seen_*` columns), `reader_differs` (reader on the STORED bars disagrees with the engine on a field: a model or implementation candidate, each with the field), `cannot_read` (reader found no trade where the engine has one or the reverse), `source_unavailable`. The report counts rows per verdict without percentages and **says that it is not a signed check**. `assist-log.csv` carries the reader's `seen_*` fields and `source`; its `verdict` column is empty.

**D7. The owner's reduced part (recommended).** The owner (a) reads every row that is not `agree_all` (expected to be few; UNVERIFIED), classifying each as data, model or implementation as in the protocol §7; (b) checks **at least 5 rows on a real chart (TradingView)**, chosen so that at least one is a Sell and one is `agree_all`, **picked by a fixed seeded rule from the `agree_all` rows** (not by the owner, so that the easy ones are not chosen) plus the rows with `bars_differ`; (c) reads the conventions list; (d) signs `check-log.csv`, rows `agree` or `disagree`, copying the reader's readings into the `seen_*` columns for the rows they accept (the log keeps `source` = `auto` for those and `owner` for the ones they read themselves). The spot-check lines (excluded and flagged days) remain the owner's, one chart lookup each.

**D8. The exit rule, amended (the owner's decision, question 1).** The protocol's rule (§7: every row signed; zero unexplained disagreements; zero open model or implementation defects; at least 5 rows against an external chart; the owner says P3 passes) stays, with two changes: a row signed on the strength of `source = auto` counts as signed, but it does **not** count as one of the "at least 5 rows against an external chart" (only the owner's own reading on a real chart does); and the record says how many rows were read by the machine and how many by the owner. UNVERIFIED power of the check: an assisted pass is weaker evidence than 20 owner-read trades only where the owner's eye is the only independent look at the **model**; it is stronger on **data and implementation**, because every row is read and not a sample of 5.

**D9. Rerun and evidence.** The assist files are written once per pack and per second-source hash; a rerun with the same inputs gives the same bytes; the pack's manifest records their hashes; a fix that changes the engine version voids the pack as in the protocol §8, assist files included.

## Acceptance criteria
1. **The reader on the protocol's examples.** A fixture set of at least 20 hand-computed days (buy and sell, a gap, a stop in the entry minute, a target, the square-off, a day with a hole, an empty opening range, a late trigger) gives the exact readings; each is computed by hand from the protocol and ADR 0037/0038 and committed with its derivation.
2. **Independence.** An architecture test shows that the reader project/namespace has no reference to `XDrishti.Simulation` or its types; a scan shows that no test of the reader reads `engine-values.csv`.
3. **Agreement with the engine on the oracle's series.** On at least 5,000 of the seeded series of P3-08 the reader's readings equal the engine's trade on every compared field (price, time, reason, `seen_r` to 0.01), except the declared differences; every difference is explained in the P3-08 log style.
   - **Amended 2026-10-20 (accepted by the builder, owner to confirm):** the oracle's series are walks over given candidates, so a chart reader cannot read them. The criterion is met by a substitute: 6,000 seeded invented opening-range days (12,000 side readings) read by both the real `Simulator` and the reader, every field compared, in `Api.IntegrationTests/Simulate/ReaderVersusEngineTests.cs`; 0 disagreements. It is a different evidence from the 18,500 oracle series.
4. **The fetch.** With a stub of the endpoint (a recorded response in the fixtures, never the live service in a test), the fetch builds `second-source-bars.csv` once per `(symbol, date)`, honours the call spacing, handles 401/429/empty/partial answers as `source_unavailable` for that row without failing the run, and never logs the token (a scan of the log and the files).
5. **The comparison.** A synthetic pair of stored and second-source days with planted differences (two ticks, a missing minute, a widened 09:15 bar; a one-tick difference is counted as noise, not reported as a difference) reports exactly the planted ones with the right words.
6. **Blindness and order.** The test run fails if `engine-values.csv` is read before `assist-log.csv` is written; the report prints both hashes.
7. **Nothing of the owner's is overwritten.** `check-log.csv` is byte-identical after `--assist`; `assist-log.csv` has an empty `verdict` column in every row.
8. **The real pack.** `verify-pack --assist` on `p3-check-1-ea89b084629b` runs end to end on the owner's machine (manual, the owner's token), writes the files, and the owner can open `assist-report.html`; the numbers of the run are not quoted outside the pack folder (roadmap, *What a P3 number means*).
9. **The record.** `docs/research/p3-hand-check.md` gains the assisted procedure (section 11), the amended exit rule and the fields "rows read by machine", "rows read by owner", "second source and its hash"; ADR 0046 gets Amendment 1.
10. `scripts/check.sh` green; a `reviewer` pass with no blocker or major; `scripts/build-docs.sh` run.

## Contract
- **API:** none. A new mode of the existing `verify-pack` verb: `--assist <pack-folder>` (with `--second-source-folder <dir>` as the offline path) and the script `scripts/verify-pack.sh --assist …`.
- **Data:** new files in the pack folder (`second-source-bars.csv`, `assist-log.csv`, `assist-report.html`) and their hashes in the manifest extras; no database access, no migration.
- **UI:** none beyond the static report.
- **Events/jobs:** none; one log line per mode run, no new event id beyond the family of the verb (UNVERIFIED: the numbering of event ids 4419 to 4422 in the roadmap leaves room).

## Non-functional
About 24 requests with the connector's spacing (UNVERIFIED seconds each; a few minutes in all); no secret outside the vault read the verb already uses; deterministic outputs for fixed inputs; read-only on the pack's existing files.

## Open questions
All six answered "yes to all recommendations" by the owner on 2026-10-19: each stands as the recommendation written in it.

1. **Do you accept the amended exit rule (D8)?** The machine reads all rows on a second source; you read the exceptions and at least 5 rows on a real chart (TradingView), and sign. Recommended: yes, with the honest limit that an auto-read row is not one of the 5 external ones. If you want the original protocol unchanged (every row read by you), this slice is not needed.
2. **The second source.** Recommended: Dhan `charts/intraday` (already allow-listed) **and** a folder input for a TradingView export you make yourself, which is the only truly independent chart source. Alternative: Dhan only (then the stored-bar comparison is weak for any minute the backfill supplied).
3. **Who reads which rows on a real chart (D7b).** Recommended: a fixed seeded rule picks them from the `agree_all` rows, plus every `bars_differ` row, so that the easy rows are not the ones checked by eye.
4. **Independence of the reader (D4).** Recommended: write it from the protocol and the ADRs only, in a project that cannot reference the engine, and review it against the same text. State plainly in the ADR that a reader written by the same model family can share a misreading of the rule tables, which is why the 5 rows on a real chart stay.
5. **The existing pack.** Run `--assist` on `p3-check-1` (nothing in it has been signed; the log's first-read hash `127e61cb…` is the evidence of the blank state) rather than drawing a new seed. Recommended: yes — the draw is unchanged and no trade of the window has been looked at by the owner; the assistant's readings are not the owner's reading.
6. **Build now or after P4 specs?** This slice only touches the verify tooling, not the walker; it can be built before P3 closes (it is a part of closing it). Recommended: build it now, as the fastest way to close P3.
