## Goal
Turn the **condition text** of a rule — `rsi(14) > 55`, `crosses_above(close, vwap)`, `tf("1h").ema(20) > tf("1h").ema(50)`, `time >= "09:45"`, `regime() == "UP_LOW_VOL"` — into something the simulator and the live engine can run over a `FeatureFrame`: parsed with precise errors, bound to the 56 catalog features, checked by a **look-ahead lint** that refuses what could read the future or mix timeframes in a way that gives a wrong answer, and compiled to a delegate (LINQ expression tree, never `eval`) that decides with **zero allocation** in time that does not grow with the history the frame keeps (the same on every bar, except `rising`/`falling(x, n)`, a loop of n steps: Amendment 18). A test proves the whole chain cannot look ahead. Still pure library code: no database, API, YAML or screens.

   - **Syntax** — lexer, parser (Superpower, version pinned in `Directory.Packages.props`) and an immutable AST with source spans; a canonical printer.
   - **Binding** — resolves every name against the `IndicatorCatalog` and the strategy parameters, types every node (number / boolean / time-of-day / regime name) and records which features, timeframes and history depth the expression needs.

2. **The expression language** (grammar and builtins in *Definitions*), including the DSL spellings `prev_day.high`, `today.open`, `index.trend` (mapped to the flat catalog names), `tf("1h").<feature>`, `close[1]`, and `regime()`.
3. **Three-valued evaluation** (true / false / unknown): an operand that is not ready (`NaN`, history not yet long enough, missing context) makes a comparison *unknown*; a decision treats *unknown* as *false*, but `not` does not turn it into *true*.
4. **Errors as data:** a failed compile returns a `Result` with a list of problems (code, message, source span, line/column, optional suggestion such as a close name), never an exception; all problems found are reported, not only the first.
5. Tests, benchmarks, an architecture test for the new project, ADR 0034 and the documentation (criteria below).

## Definitions (numbers and rules the tests pin)
These are the rules **as built**; the tests pin exactly these. Where a rule differs from the text the owner approved on 2026-10-16 — or settles a contradiction inside it — it names its Amendment below, and **⚠** marks the ones the owner is asked to confirm (Amendments 1, 2, 3, 4, 7, 14 and 18); the approved wording, where there is one, is kept in the Amendments, which also say what the owner is asked to confirm. The Definitions are the part a simulator or an editor author reads; the Amendments are the record of how they changed. The full language reference with examples is [doc 11 §2](../design/11-strategy-lab.md).

**Grammar** (precedence from loosest to tightest; keywords are lower-case: `and or not true false`):
```
or      := and ( "or" and )*
and     := not ( "and" not )*
not     := "not" not | compare
compare := sum ( ("<" | "<=" | ">" | ">=" | "==" | "!=") sum )?        -- not chained: a < b < c is an error
sum     := product ( ("+" | "-") product )*
product := unary ( ("*" | "/") unary )*
unary   := "-" unary | primary
primary := number | string | "true" | "false" | "(" or ")" | call
         | reference ( "[" ["-"] digits "]" )?                           -- a subscript only right after a reference; the lint decides which lags are usable (Amendments 1, 8)
reference := ident | "tf" "(" string ")" "." ident | ident "." ident    -- close, vwap, tf("1h").close, prev_day.high, today.open, index.trend
call      := ident "(" [ arg ( "," arg )* ] ")" | "tf" "(" string ")" "." ident "(" [ arg ( "," arg )* ] ")"
arg       := or | ident "=" ident                                        -- named argument: source=high
```
Numbers are decimal: digits, an optional fraction and an optional lower-case exponent (`55`, `0.5`, `1e-3`; `.5`, `1.` and `1E5` are errors, and so is a number the language cannot hold, `1e400`); strings use double quotes, with no escapes and no quote or line break inside; comments are not supported; whitespace (space, tab, CR, LF) is free; identifiers are letters, digits and underscores, not starting with a digit (upper case is read so that `MON … SUN` can be names; the binder refuses `RSI`, Amendment 8). Everything is case-sensitive. Only ASCII is part of the language outside strings: any other character is a problem that names its code point. **A text is at most 4,000 characters and nests at most 64 levels (the brackets and prefix operators open at once, and the depth of the tree, where every operator of a chain is a level: ⚠ Amendment 3).**

**Names.** An identifier resolves in this order: strategy parameter → builtin, constant or `time` → catalog feature (a feature qualified with `tf("…")` or written dotted is always a catalog feature). A parameter is a *number* known at compile time; used as a catalog argument (`rsi(rsi_len)`) it becomes part of the `FeatureSpec`, and a parameter that hides a feature, builtin, constant or `time` wins with a warning (`shadowed_name`, Amendment 11). A catalog feature is called with its parameters positionally in catalog order (`bb_upper(20, 2)`), with defaults for the trailing ones the catalog declares (`rsi()` is `rsi(14)`); each argument is a number known when the condition is compiled (a literal, a parameter, `MON … SUN`, or arithmetic, unary minus, `abs`, `min`, `max` of those); source-aware indicators take `source=close|open|high|low` as a named argument. A feature with parameters written without parentheses (`rsi`) and a function written without them (`abs`) are `bad_arguments`; a feature without parameters takes both `vwap` and `vwap()` (Amendment 9). DSL spellings: `prev_day.X` → `prev_day_X` (open, high, low, close, volume), `today.X` → `today_X` (open, high, low), `index.trend` → `index_trend`, `index.adx` → `index_adx` (every other dotted pair is an error; the other context names are written flat: `vix_pct`, `index_vol_pct`, `regime_trend` …).

**Timeframes.** An unqualified feature uses the *evaluation timeframe* given to the compiler (the strategy timeframe). `tf("1h").F` uses another one of `1m 5m 10m 15m 30m 1h 1D 1W 1M` (case as written; `1d` is an error with the suggestion `1D`). The value is always that of the **last closed bar** of the timeframe (the frame's rule). The catalog's refusals apply and become errors with the feature and timeframe named (`vwap` on 1D, `prev_day_*` on 1W …). The twelve calendar and context features are always read on 1m, whatever the strategy timeframe (`tf("1h").vix` is an error; `tf("1m").vix` is allowed). Only a catalog feature can be qualified: `tf("1h").crosses_above(…)` is `unknown_name`.

**Types.** `number` (double), `bool`, `time` (the keyword `time`, compared with a string literal of the form `"HH:MM"`) and `regime` (the function `regime()`, compared with one of the nine names, or with a constant integer 1..9) — the last two and a string literal exist only next to such a comparison. `and or not` take bool; arithmetic and ordering take number; `==`/`!=` take two numbers or two bools; `time` takes all six comparisons with a time string on either side; `regime()` takes `==`/`!=` only. A parameter must be a finite number. The whole condition must be bool. Anything else is a type error: a comparison names both sides, and every other operator and every builtin names the operand that is wrong, the type that place needs and the type it has (Amendments 9, 18).

**Builtins:** `crosses_above(a, b)`, `crosses_below(a, b)`, `rising(x, n)`, `falling(x, n)`, `between(x, lo, hi)` (inclusive), `abs(x)`, `min(a, b)`, `max(a, b)`, `regime()`, and the keyword `time`. Constants: `MON … SUN` = 1 … 7 (for `day_of_week`). `n` is a whole number of at least 1 known when the condition is compiled.

**Meaning:**
- `x[k]` (k = 1 … 255, an integer literal after a reference): the feature's value **k closed bars of its own timeframe ago** (frame `At(handle, k)`). **⚠ `x[0]` is refused** (`negative_or_zero_lag`, suggestion `x`; Amendment 1). *Approved wording: "`x[0]` is `x`".*
- Lagged evaluation: `crosses_above(a, b)` is `a[0] > b[0] and a[1] <= b[1]`; `crosses_below(a, b)` is `a[0] < b[0] and a[1] >= b[1]`; `rising(x, n)` is `x[0] > x[1] > … > x[n]` (n whole steps, strict), `falling(x, n)` the mirror. `a`, `b`, `x` may be any numeric expression: the expression is evaluated *at lag k*, i.e. every feature leaf is read with `At(handle, k + its own subscript)` and constants stay constants. The lags add up (`rising(close[200], 100)` reads 300 bars back, Amendment 10).
- **Lags are by position, not by session** (Amendment 19; the approved text was silent). The frame's history runs on across sessions (ADR 0031), so `x[k]` on the first `k` bars of a session is a value of the previous session. A rolling feature wants that (`ema(20)` at 09:30 uses the previous day's bars). A feature that starts again at the session open and already has a value on its first bar does not — `vwap`, `today_open/high/low`, `prev_day_*`, `gap_pct` (`IndicatorInfo.HasValueAtSessionOpen`; `or_high` / `or_low` of several bars are not ready at the open, so a crossing against them is unknown there): `crosses_above(close, vwap)` is true on the first bar of a session whenever that bar closes above its own typical price and the last close of the day before was at or below that day's last vwap, a cross of two sessions. The lint warns (`lag_across_session`) when a strategy on an intraday timeframe lags such a feature and names the check that clears it: `and time >= "HH:MM"`, 09:15 plus `(lag + 1)` bars of the feature's timeframe (`"09:45"` for one bar back on 15m); a lower bound of `time` in the top-level `and` chain of the same condition is recognised, one in another section of a strategy file is not.
- `time` is the **India clock time at which the evaluated bar closed**: the start of the last accepted 1-minute bar plus one minute (the bar `09:44` makes `time` = `09:45`); it is read from `FeatureFrame.LastBarTime`. A comparison of `time` with `"HH:MM"` is on whole minutes. `time` is unknown before the frame has accepted a bar and is refused when the evaluation timeframe is 1D or longer.
- `regime()` is the `regime` feature (1 … 9); `regime() == "UP_LOW_VOL"` is resolved to the code at compile time (the names are case-sensitive and exact).
- **Three-valued logic** (Kleene): *unknown* is the result of a comparison, `crosses_*`, `rising/falling`, `between` or `time` when any operand is not ready; `false and unknown = false`, `true and unknown = unknown`, `true or unknown = true`, `false or unknown = unknown`, `not unknown = unknown`. The lagged builtins and `between` are atomic: unknown if any of their values is not ready, even when another would already decide. A decision (`Evaluate`) returns *true* only when the result is *true*; *unknown* is false. Arithmetic with a not-ready operand is not ready (NaN); `x / 0` (an exact zero divisor) is not ready (NaN), never an exception; a quotient that overflows is ±infinity, a number (Amendment 12).
- **When to evaluate** is the caller's business (the simulator evaluates at steps where `frame.BarClosed(evaluationTimeframe)`); the compiled condition itself is a pure function of the frame as it is *now*.
- **Problems.** A bad condition is never an exception: the result carries every problem found, each with a code, a message, a span (offsets, line, column) and a severity. If the text does not parse, the problems are the syntax ones (`strategy.syntax.*`; the first is exact, the later ones best effort); if it parses, all binder and lint problems are reported together, in source order (Amendment 7). At most 100 syntax problems are listed: a text with more has its first 100 listed and one `strategy.syntax.too_many_problems` that covers the rest of the text (⚠ Amendment 7).

**Lint rules** (each has a stable code `strategy.lint.<name>`, a message that names the offending text, and a suggestion where one exists; all are errors unless marked warning or information):
| Code | Rule |
|------|------|
| `unknown_name` | an identifier or function is not a parameter, builtin, constant, `time` or catalog feature; a dotted pair that is not one of the spellings; a regime name that is none of the nine; a builtin or parameter written with `tf(…)` (suggestion: the names at the smallest edit distance found, if that is at most 2 — at most 1 for a text of one or two letters —, compared case-insensitively, at most five; the nearest tier only) |
| `bad_arguments` | wrong number, kind or range of arguments (the catalog's parameter names, ranges and defaults are quoted); an argument that is not known at compile time; a function or feature written without its parentheses; a bad or repeated `source=`. The span of too many arguments runs from the first surplus argument to the last |
| `unsupported_timeframe` | `tf("…")` is not one of the nine, or the catalog does not support the feature on it |
| `negative_or_zero_lag` | a subscript or `rising/falling` count that is not a whole number of at least 1 (`x[0]`, `x[-1]`, `rising(x, 1.5)`; ⚠ Amendment 1) |
| `lag_too_deep` | the history depth needed (the largest lag read plus 1, the lags adding up) exceeds 256 (the frame's cap) |
| `lag_on_non_feature` | a subscript applied to a strategy parameter, a constant or `time` (a subscript after a call, a group, a literal or another subscript is the syntax problem `subscript_on_non_reference`; use the lagged builtins, or write the feature twice) |
| `mixed_timeframes_in_lag` | a `crosses_*`, `rising` or `falling` whose feature leaves are not all on one timeframe: "the previous value" would mean different times; compare on one timeframe, or lag one operand explicitly. ⚠ The calendar and context features are a clock of their own, the date: lagged among themselves and against numbers, never together with a bar feature, on 1m too (Amendment 4) |
| `time_on_daily` | `time` used when the evaluation timeframe is 1D, 1W or 1M |
| `bad_time_literal` | a time string that is not `HH:MM` within 09:15 … 15:30 |
| `type_mismatch` | see *Types* |
| `constant_condition` (warning) | a true/false part that reads no data (`1 < 2`, `crosses_above(1, 2)`, a parameter against a number); a bare `true` or `false` only when it is the whole condition; `rsi(14) > 100` for a bounded oscillator is *not* detected (Amendment 11) |
| `redundant_timeframe` (warning) | `tf("15m").ema(20)` when the evaluation timeframe is already 15m |
| `needs_context` / `needs_expiry_days` (information) | the plan reports that the frame must be created with a `MarketContext` / expiry dates; these are not lint failures, and are reported only for a condition without errors |
| `shadowed_name` (warning) | a strategy parameter has the name of a feature, builtin, constant or `time` and wins (Amendment 11; not in the approved table) |
| `lag_across_session` (warning) | a lagged read (a subscript, or the lags of `crosses_*`, `rising`, `falling`) of `vwap`, `today_*`, `prev_day_*`, `gap_pct` or a one-bar opening range, on an intraday strategy whose first evaluation (`E` minutes after the open) comes before the read stays inside the session (`E < (lag + 1) · T` for the feature's timeframe `T`): the first bars of every session read the previous session. Not on 1D or longer; not when the condition holds `time >= "HH:MM"` (or `>`) late enough in its chain of `and`s. The message names the features, how far back and the check that clears it (Amendment 19; not in the approved table) |

## Acceptance criteria
**Syntax**
1. A table of ≥ 60 valid sources parses to the expected AST (hand-written expected trees): precedence and associativity (`a or b and c`, `not a and b`, `-x * y`, `a - b - c`, `a / b * c`), every literal form, the dotted DSL spellings, `tf("1h").ema(20)`, named arguments, nested calls and subscripts. A table of ≥ 60 invalid sources yields the expected problem code and exact span (empty text, unbalanced parentheses, unknown character, chained comparison `a < b < c`, a subscript on a call, missing argument, trailing comma, unterminated string, a number followed by an identifier …); every problem has line and column. **[As built: 98 valid and 108 invalid sources; Amendments 7, 8.]**
2. The printer is canonical and round-trips: for ≥ 500 generated ASTs `Parse(Print(ast))` equals `ast`, and the printed form of two sources that differ only in whitespace is identical. **[As built: 1,000 generated trees.]**

**Binding and typing**
3. Every catalog feature (all 56) can be written in its DSL form with its default arguments and binds to the `FeatureSpec` the catalog's `DefaultSpec` gives; a table pins the spec produced for ≥ 30 forms (positional arguments, defaults, named `source=`, `tf()` qualification, dotted spellings, parameters, `regime()`); two spellings of the same feature produce *equal* specs (so the frame shares one instance).
4. Unknown names, wrong argument counts or ranges, unsupported timeframes and type errors each give the documented code, quote the catalog's parameter names/ranges, and suggest the closest names; a typo in any of the 56 names (one deleted, inserted or swapped letter) yields the right suggestion (property over all names).
5. Parameters: `rsi(rsi_len)` with `rsi_len = 21` equals `rsi(21)`; an unknown or non-number parameter is an error; the parameter map is not mutated; compiling the same text with two maps gives two independent plans.

**Lint**
6. Every row of the lint table has at least one failing example (exact code, span, message text pinned) and one near-miss that passes; the three-way set of rules around lags (`lag_on_non_feature`, `mixed_timeframes_in_lag`, `lag_too_deep`) is exercised on every timeframe pair of {1m, 5m, 15m, 1h, 1D, 1W}; all problems of a source with several faults are reported together in source order. **[As built: 161 failing and 93 near-miss examples; the row `lag_across_session` was added, Amendment 19.]**

**Evaluation semantics**
7. The compiled condition equals an **independent tree-walking interpreter** (plain code in the test project, written from the Definitions, sharing nothing with the compiler) on ≥ 200 seeded random expressions × random frames (random bars over several sessions and weeks, every evaluation timeframe 1m … 1W, with and without a context), comparing the full three-valued result at every closed bar of the evaluation timeframe. **[As built: 864 conditions on all nine evaluation timeframes, compared after every 1-minute step, with a second interpreter over the bound tree; Amendment 14.]**
8. Three-valued logic: the Kleene tables of `and`, `or`, `not` are pinned exhaustively; no decision is ever *true* while an operand of its deciding comparison is not ready (property over the warm-up of every catalog feature on every timeframe, including `not (rsi(14) > 55)` and `rsi(14) < 45 or close > 0`); `x / 0` and a NaN operand never throw.
9. Hand-calculated examples (frames built from ≤ 12 bars): `crosses_above` / `crosses_below` including equality at the previous bar and at the current bar, the first bar after warm-up (history not ready → unknown), `rising(x, 3)` / `falling(x, 3)`, `between` at both ends, `x[1]` and `tf("1h").close[1]`, `day_of_week == TUE`, `regime() == "UP_LOW_VOL"` against a small `MarketContext`, and `time >= "09:45"` on a 15m evaluation timeframe (first true at the bar that closes at 09:45).

**No look-ahead (the point of the slice)**
10. **Truncation and future-perturbation property:** for ≥ 200 seeds, ≥ 1,000 random expressions in all, on evaluation timeframes 1m, 5m, 15m, 1h, 1D, 1W: the decision (and the three-valued value) at every closed bar of the evaluation timeframe is identical (a) when all later 1-minute bars are removed and (b) when all later bars are replaced by arbitrary values (including extreme prices and zero volume). A **negative control** proves the test can fail: the same property run through a deliberately wrong frame wrapper (reads the first bar after the step; reads the forming bar of a higher timeframe) is reported as a violation. **[As built: 240 seeds, 1,200 conditions, and on the seeds with a context the context days from the cut date on are removed or changed too; the negative controls are three feeders (the next bar, the forming bar, the context record of the date itself), not a frame wrapper, and the limits of the property are written in ADR 0034: it guards the feed and the frame, not the compiler, which is guarded by the oracle, the hand examples, the audit of the expression trees and the architecture test on the members of the frame; Amendment 14.]**
11. The plan lists exactly the features the expression reads (no more, no fewer, deduplicated) and the smallest sufficient history depth (the largest lag used + 1, at least 1); `FeatureFrame.Create(plan.Features, new FrameOptions { HistoryDepth = plan.HistoryDepth, … })` succeeds for every generated valid expression (it is accepted by the frame's own validation) and a plan that needs a context / expiry dates says so.

**Performance and structure**
12. Steady-state `Evaluate` allocates 0 bytes (the `AllocationProbe` of the P3-01c tests; a set of 10 conditions over a 20-feature frame, including a date change and a higher-timeframe close); targets: ≤ 0.3 µs per evaluation of a 10-condition set (benchmark reports the number), parse + bind + lint + compile of a 10-condition strategy ≤ 20 ms cold and ≤ 3 ms warm. **[⚠ As built: the 0 bytes (asserted in `scripts/check.sh`), 255–257 ns per set while the frame moves and a warm median of 2.5–2.7 ms (both asserted by the explicit benchmarks, which `scripts/check.sh` skips) are met; the cold figure is 39–41 ms and is NOT met (Amendment 2).]**
13. Architecture tests: `XDrishti.Strategies` references only `Domain` and `Indicators` (and Superpower); no I/O, no clock, no mutable statics, no use of `System.Reflection.Emit`, `Microsoft.CodeAnalysis` or `System.Linq.Dynamic`-style evaluation of text (the only dynamic code is `System.Linq.Expressions` trees built from the AST), all types sealed; the project is added to the solution, to `backend/Dockerfile` (COPY line) and to `Directory.Packages.props` with the exact Superpower version; the existing layer tests stay green. **[As built: three abstract bases of the syntax tree are the only classes not sealed; 21 new architecture tests; Amendment 16.]**
14. The prerequisites of item 0 are covered: renamed types, `IndicatorInfo.RequiresContext` / `RequiresExpiryDays` for exactly the 10 context-reading names and `is_expiry_day`, `FeatureFrame.LastBarTime` (0 before the first step, the start of the last *accepted* bar, unchanged by a skipped bar, cleared by `Reset`), no behaviour change elsewhere (the existing 4,000+ tests pass unchanged). **[As built: only the mechanical rename touched existing tests; four small details differ from the sketch, Amendment 15.]**
15. Docs: ADR 0034 (grammar, three-valued logic, the `time` convention, the lag rules, the project, Superpower), doc 11 §2 (the language reference with the grammar and the lint table), doc 03 (the project and its contents), the roadmap (P3-02 built; P3-02b next).

## Contract (public surface, sketch)
```csharp
public readonly record struct SourceSpan(int Start, int End, int Line, int Column);
public sealed record Problem(string Code, string Message, SourceSpan Span, string? Suggestion = null, ProblemSeverity Severity = ProblemSeverity.Error);

public sealed record CompileContext(Timeframe EvaluationTimeframe, IReadOnlyDictionary<string, double> Parameters);

public sealed class ConditionCompiler {
  public static Result<CompiledCondition, IReadOnlyList<Problem>> Compile(string source, CompileContext context);   // parse + bind + lint
}
public sealed class CompiledCondition {
  public string Source { get; }
  public IReadOnlyList<FeatureSpec> Features { get; }      // exactly what the expression reads
  public int HistoryDepth { get; }                         // 1 … 256
  public bool NeedsContext { get; }  public bool NeedsExpiryDays { get; }
  public IReadOnlyList<Problem> Warnings { get; }
  public BoundCondition Bind(FeatureFrame frame);          // resolves handles; throws only on a frame that was not created from these features
}
public sealed class BoundCondition {
  public bool Evaluate(FeatureFrame frame);                // unknown => false; zero allocation
  public Truth EvaluateTruth(FeatureFrame frame);          // True / False / Unknown
}
public enum Truth : sbyte { False = 0, True = 1, Unknown = -1 }

public static class ConditionSet { /// merges the plans of several conditions (one frame for all): union of features, max history depth
  public static CompiledPlan Merge(IReadOnlyList<CompiledCondition> conditions); }
```
(The exact `Result` shape follows the library's existing `Result` type; if it cannot carry a list of problems, a `CompileResult` record is used instead — decided in the build and recorded in the ADR.)

**As built (Amendments 5, 6):** `ConditionCompiler` is a static class and `Compile` returns `CompileResult(CompiledCondition? Condition, IReadOnlyList<Problem> Problems)` (on success `Problems` holds the warnings and the `needs_*` notes; `IsSuccess`, `Errors`); `ConditionParser.Parse(string)` returns `ParseResult(Expression? Tree, IReadOnlyList<Problem> Problems)`; `CompileContext` also has a constructor that takes only the evaluation timeframe (no strategy parameters; there is no constructor without arguments); `CompiledCondition` also has `EvaluationTimeframe`, `BoundCondition` has `Condition`; `CompiledPlan` (the result of `ConditionSet.Merge`) has `Conditions`, `Features`, `HistoryDepth`, `NeedsContext`, `NeedsExpiryDays` and `BindAll(frame)`. `Bind` throws an `ArgumentException` for a frame that lacks a feature of the condition **or keeps less history than it needs**; the delegate is built at the first `Bind`. Public types are in `XDrishti.Strategies` (`SourceSpan`, `Problem`, `ProblemSeverity`), `.Syntax` (the parser, the tree, the printer, `SyntaxCodes`), `.Lint` (`LintCodes`) and `.Compilation`; the binder, the bound tree, the linter and the expression builder are internal.

## Non-functional
- Performance: criterion 12; the evaluator is a compiled `Func<FeatureFrame, sbyte>`-style delegate over `int` handles resolved once at `Bind`, no boxing, no LINQ at run time. **As built:** `Decision(FeatureFrame, int[] handles) → int` (1 true, 0 false, −1 unknown), compiled once per condition at the first `Bind` and shared by every frame; the handles are the per-frame part (Amendment 6).
- Security: no string is ever executed; the only dynamic code is an expression tree built from the validated AST; every identifier is checked against a closed vocabulary (catalog, builtins, parameters); numeric literals are bounded; recursion depth is limited (a source nested more than 64 levels or longer than 4,000 characters is refused with a problem, never a stack overflow). **As built:** the 64 levels are the brackets and prefix operators open at once and the depth of the tree, where each operator of a chain is a level (⚠ Amendment 3).
- Privacy: tests use only invented series and invented strategy text; nothing is read from `data/`.
- Observability: none (pure library).

## Test plan

Families: syntax tables and printer round-trip; binding tables and the all-56-names test; lint table; interpreter oracle; Kleene tables; hand examples; truncation / future-perturbation property with its negative control; plan/dependency tests; allocation and benchmark. ## Open questions (1–7 answered 2026-10-16: recommendations approved; 8 still open)
1. **Split.** This slice is the *expression language* (text of one condition → checked, compiled, evaluated); the *strategy file* around it (YAML sections, `params` ≤ 4, `sell:` block, BUY → SELL mirror, JSON Schema) is **P3-02b**. **Recommendation:** split as written, so each slice stays reviewable and testable in isolation. OK?
2. **Parser technology.** Doc 03 names Superpower (a parser-combinator library, one NuGet package) with compiled expression trees. **Recommendation:** follow doc 03. The alternative is a hand-written parser with no dependency, which is also easy for a grammar this small; say so if you prefer no new dependency.
3. **Unknown is not true.** Three-valued logic: a condition whose data is not ready is *unknown*, not *false*, so `not (rsi(14) > 55)` cannot fire before RSI exists; a decision treats unknown as false. **Recommendation:** as written.
4. **`time` means the close time of the bar being evaluated** (a 15-minute bar covering 09:30–09:45 is evaluated at `time` = 09:45, so `time >= "09:45"` first holds on that bar, not on the one before it). **Recommendation:** as written; the alternative (the bar's start) would let a 09:45 rule act on a bar that closed at 09:30.
5. **Lagged evaluation needs one timeframe.** `crosses_above`, `rising`, `falling` and `x[k]` of an expression are refused when their operands sit on different timeframes (for example `crosses_above(close, tf("1D").ema(20))` on a 15m strategy): the "previous value" of the two operands would be different instants. The explicit form `close > tf("1D").ema(20) and close[1] <= tf("1D").ema(20)` is allowed and says what is meant. **Recommendation:** refuse, as written, with that suggestion in the message.
6. **Strictness.** `crosses_above(a, b)` is `a[0] > b[0] and a[1] <= b[1]` (a touch that does not pass is not a cross; equality on the previous bar counts as "not above yet"); `rising(x, n)` is strict at every step. **Recommendation:** as written.
7. **The two small frame/catalog prerequisites** (rename to `DateFeature`, flags on `IndicatorInfo`, `FeatureFrame.LastBarTime`) are done inside this slice as its first step. **Recommendation:** yes — they are the P3-01c review follow-ups and they must precede the first user of the names.
8. **Still open from P3-01c:** the six flagged build deviations of ADR 0033 (the `vix_pct` window, the `regime_vol` fallback, the cursor, the partial first week, the exact thirds, the end of the context) are waiting for your confirmation. This slice does not depend on them (it only uses the names), but if you revert one, the definitions in doc 11 change.

## Amendments (2026-10-16, from the build)
Deviations of the build from the text the owner approved; the guarantees of the acceptance criteria hold except where Amendments 2, 7 and 14 say otherwise. The Definitions above state the rules as built; this section is the record. Details and reasons are in [ADR 0034](../adr/0034-the-rules-expression-language-lint-and-compiler.md) ("Consequences from the build" and "Amendments").

**Amendments 1, 2, 3, 4, 7, 14 and 18 deviate from, narrow, or settle a contradiction in, text that the owner approved (all seven marked ⚠ *needs the owner's confirmation*).** The owner confirms them or they are reverted: 1 and 3 change approved wording, 2 misses an approved target, 4 settles a case the approved text left open, 7 narrows "all problems found are reported" (to one stage, and to 100 syntax problems), 14 replaces the approved negative control of criterion 10 and says what the property cannot see, 18 corrects two claims of the approved text that the code does not make true. The others resolve contradictions inside the spec in favour of the code, add behaviour the spec left open, or record how it was built; they change no behaviour the owner approved. The same list, with the same numbers, is in the ADR.
1. ⚠ *Needs the owner's confirmation.* **`x[0]` is refused.** *Approved wording (Meaning): "`x[0]` is `x`"*, while the lint table says a subscript that is not an integer in 1 … 255 is `negative_or_zero_lag`. Built: `close[0]` and `close[-1]` are `negative_or_zero_lag` (suggestion `close` for `close[0]`), so that the language has one spelling for the current value.
2. ⚠ *Needs the owner's confirmation.* **The cold-start budget is missed.** *Approved (criterion 12): "parse + bind + lint + compile of a 10-condition strategy ≤ 20 ms cold and ≤ 3 ms warm".* Measured in Release on an Apple-silicon Mac, three fresh processes: **cold 39–41 ms** (30–31 ms parse + bind + lint, 8–9.5 ms for the ten delegates; the build's own run gave 37 ms), warm median 2.5–2.7 ms (met). The cold figure is the first compile of a process (JIT of Superpower, the binder and the expression compiler); it is not asserted anywhere. Direction: `PublishReadyToRun` for the hosts or a lighter lexer, not tried; open in the roadmap issues log as ISS-12.
3. ⚠ *Needs the owner's confirmation.* **The nesting limit of 64 counts the depth of the tree.** *Approved (Non-functional): "a source nested more than 64 levels … is refused with a problem".* Built, `too_deep` in two places: more than 64 brackets plus pending prefix operators open at once (before the parse, the span is the token that goes over), and a syntax tree deeper than 64 (after it, the span is the whole condition; every call, prefix operator, subscript and each operator of a chain is a level, parentheses are none). A chain `a and b and …` is as deep as it is long: 63 conditions of the form `rsi(14) > 55` joined by `and` pass and 64 are refused, a chain of 64 operators of single names passes and 65 are refused.
4. ⚠ *Needs the owner's confirmation* (the approved text was silent). **The calendar and context features are a clock of their own in `mixed_timeframes_in_lag`.** They are read on 1m whatever the strategy timeframe, but they change once a *date* and their previous value is the previous date, never the previous minute. So a lagged call (`crosses_*`, `rising`, `falling`) may read them among themselves and against numbers (`crosses_above(vix, 20)`, `rising(vix, 2)`, `rising(vix - index_trend, 2)`; `regime() == 3` has no lag) and never together with a bar feature, on any strategy timeframe, 1m included, and for `tf("1m")` bar features too: `crosses_above(close, vix)` is refused on 1m, 15m, 1D and the rest (the message offers `close > vix and close[1] <= vix`, which lags the bar only). *History:* the first build counted them as timeframe 1m and so let `crosses_above(close, vix)` through on a 1m strategy, where `vix[1]` is yesterday's value all day and the "crossing" holds at every minute of a date (VIX 50 yesterday, 30 today, close 25 yesterday and 40 all today; the explicit form holds at the first minute only); a review found it and the rule was tightened. Kept on a 1D strategy too, where the previous date and the previous bar coincide, so that one rule holds everywhere.
5. **The result types** (foreseen by the spec): `ParseResult` and `CompileResult` carry the list of problems because the library's `Result` carries one error; `ConditionCompiler` is a static class; the single-condition plan is `CompiledCondition` and the merged one `CompiledPlan`, as in the sketch.
6. **Contract additions** (see the *Contract* note): `CompileContext(Timeframe)`, a constructor without the strategy parameters (there is no parameterless one), `CompiledCondition.EvaluationTimeframe`, `BoundCondition.Condition`, `CompiledPlan.Conditions` and `BindAll`; `Bind` also checks the history depth; the delegate is built at the first `Bind` and is `Decision(FeatureFrame, int[]) → int`, shared by all frames; `Evaluate` does not check that the frame has the layout the condition was bound to (documented: a frame of another layout reads other features without an error — build every frame of a strategy from the same plan).
7. ⚠ *Needs the owner's confirmation.* **The parser is a hybrid, recovery is best effort after the first problem, the stages do not mix, and at most 100 problems are listed.** *Approved (scope item 4): "all problems found are reported, not only the first".* The tokenizer and the small productions are Superpower combinators; the recursive spine is plain Superpower parser functions with precedence climbing (nine combinator layers needed more than 1 MB of stack at 64 levels). At a syntax failure the parser explains it, repairs the token list and parses again: the first problem is exact, the later ones are those of the repaired text. A text with a syntax problem is answered with its syntax problems only (the names and the lint are not run), so "all problems are reported" holds within a stage. *Limit:* every repair parses the whole text again, so a text of 4,000 characters made of nothing but faults cost up to 0.7 s and 1.5 GB (3,990 commas after `f(`); the recovery now stops after 100 problems (lexical ones counted) or 232 parses, whichever comes first, and the parser lists the first 100 in source order followed by one `strategy.syntax.too_many_problems` whose span is the rest of the text (≤ 52 ms and ≤ 27 MB for the worst texts measured). A follow-on problem is not reported after a value the recovery supplied, at a comma already reported as having no argument, at a `!` after a value (already an `unknown_character`) or at an end the recovery made itself (`close <> 5`, `rsi(,)`, `close ! 5`, `close === 5`: one problem each).
8. **Grammar details the spec left open or contradicted.** Identifiers accept upper-case letters (the spec's `[a-z_]…` contradicts `MON … SUN`; the binder refuses `RSI` as `unknown_name`, suggestion `rsi`); a subscript parses with an optional minus (`close[0]`, `close[-1]`, `close[300]` parse and the lint decides), `x[1.5]` and `x[1e3]` are `bad_subscript`, one beyond the range of an integer `number_out_of_range`; a subscript on anything but a reference is the syntax problem `subscript_on_non_reference` (criterion 1 asks for a syntax problem for a subscript on a call), so `lag_on_non_feature` remains for a parameter, a constant and `time`; only a lower-case `e` is an exponent (`1E5` is `number_followed_by_identifier`); strings have no escapes and cannot hold a quote or a line break; a bare `tf` is an ordinary name that the binder rejects, `tf("1h")` alone is `bad_timeframe_qualifier`; a look-alike character (`＞`, `&&`, `||`, `!`, `≥`, typographic quotes) is reported once, with the replacement as suggestion, and then read as the token it stands for; a parenthesised node's span includes its parentheses.
9. **Type rules the spec contradicted or left open.** *Types* said `==`/`!=` take `time` with a time string and ordering takes numbers, while the main example is `time >= "09:45"`: `time` takes all six comparisons, the text on either side. `regime()` takes `==` and `!=` only, against a name or a constant integer 1 to 9. A feature with parameters written bare (`rsi`; suggestion `rsi()`) and a function written bare (`abs`) are `bad_arguments`; a feature without parameters takes `vwap` and `vwap()`; `tf("1h").crosses_above(…)` is `unknown_name`. The type errors of `and`/`or`/`not`, of arithmetic and of the builtins name the operand that is wrong, not both operands (Amendment 18).
10. **The lag-rule boundaries.** `negative_or_zero_lag` ("not an integer in 1 … 255") overlaps `lag_too_deep` ("the history exceeds 256") in the table: built, `negative_or_zero_lag` is below 1 or not whole, `lag_too_deep` is a history of more than 256, the lags adding up (`close[256]`, `rising(close, 256)`, `rising(close[200], 100)`, `crosses_above(close[255], vwap)`). `mixed_timeframes_in_lag` applies to `crosses_*`, `rising` and `falling`; "`x[k]` of an expression" does not exist because a subscript is only read after a reference. The test plan's "DSL aliases for every context name" is only `index.trend` and `index.adx`; the others are flat.
11. **Lint added and extended.** `strategy.lint.shadowed_name` (warning) is new (the test plan asks for a warning when a parameter shadows a feature; the table had no code). `constant_condition` flags the largest data-free true/false *part* of a condition, counts parameters as constants, and flags a bare `true`/`false` only when it is the whole condition. `needs_context` and `needs_expiry_days` are reported once each, at the first feature that needs them, only when the condition has no error, and are in `CompileResult.Problems`, not in `CompiledCondition.Warnings`.
12. **Arithmetic edge cases.** Only an exact zero divisor gives NaN (not ready); a quotient that overflows is ±infinity, a number; `inf − inf` is NaN, so unknown; `min` and `max` pass a NaN on; a feature argument and a `rising/falling` count are folded at compile time with the same rules, and a NaN or infinite one is refused; a non-finite strategy parameter is a `type_mismatch` where it is used. The lagged builtins and `between` are atomic (unknown if any value is not ready). "Not ready" is NaN, relying on the `IIndicator` contract that a value is NaN exactly when not ready.
13. **`time`** is unknown while `frame.Steps == 0` (not when `LastBarTime == 0`, so a real bar at epoch 0 is a bar), is the India clock minute (the domain's `SessionClock.MinuteOfDay`, so the offset of 19,800 s is written once; `bad_time_literal` uses its `OpenMinute` and `CloseMinute` too) and wraps at midnight.
14. ⚠ *Needs the owner's confirmation.* **Test shape; the negative control of criterion 10 is not the approved one.** *Approved (criterion 10): a negative control through "a deliberately wrong frame wrapper (reads the first bar after the step; reads the forming bar of a higher timeframe)" that is reported as a violation.* The oracle (criterion 7) is model-based, so that it also covers the binder, plus a second interpreter over the bound tree; it compares after every 1-minute step on all nine timeframes. The negative controls of criterion 10 are three feeders (`NextBarFeeder`: the first bar after the step; `FormingBarFeeder`: the frame run on to the close of the slowest higher-timeframe bar; `SameDayContextFeeder`: the date lane reads the context record of the date itself), not a wrapper of the frame. On the seeds that have a context the property also cuts the context: in the truncated run the context days dated at or after the cut date are removed, in the perturbed run they are replaced by changed ones. A truncation property cannot see a read of the forming bar that uses only past minutes — the approved control, "reads the forming bar of a higher timeframe", is therefore modelled as reading the bar in its final state before it closes —; the forming bar is guarded where it is made, by the frame's own tests (ADR 0031), not by this property. Nor can the property fail for a change in the compiler (a compiled condition is a pure function of the frame as it is at the step); that guarantee is structural and is pinned by an architecture test (the library may reference only `FeatureFrame.this[]`, `At`, `Steps`, `LastBarTime`, `HandleOf`, `HistoryDepth` and `Create`, with a sentinel that proves the rule can fail) and by `CompiledTreeTests`, an audit of the expression trees (only kernel calls, the frame reached through three functions, nothing but numbers held, no lag nearer than written), both added after review.
15. **The prerequisites** (scope item 0) differ from the sketch in four details, none changing behaviour: the internal `IndicatorInfo.DateFeature` property is removed (its only user was `FeatureFrame.Create`, and the name clashes with the type); the two requirement checks in `Create` are independent `if`s; two `ArgumentOutOfRangeException` messages say "date feature"; `DateFeature.ReadsContext(kind)` remains as the internal helper that sets the flag. 281 new tests (226 pin the flags for all 56 names, 54 `LastBarTime`, one allocation test).
16. **Architecture tests:** 21 new (111 → 132). The anonymous types of LINQ query syntax are excluded from the forbidden-namespace check; the Superpower-leak rule reads public signatures; exactly three classes may be unsealed (`SyntaxNode`, `Expression`, `Argument`, the abstract bases of the closed family of sealed records).
17. **Older documents keep the old names.** [ADR 0033](../adr/0033-weekly-monthly-timeframes-calendar-features-and-the-market-context.md) and [P3-01c](P3-01c-weekly-monthly-timeframes-and-market-context.md) say `ContextFeature` / `ContextFeatureKind`; they are history, with a note that points here. The live documents ([doc 03](../design/03-target-architecture.md), [doc 11](../design/11-strategy-lab.md)) use the new names.
18. ⚠ *Needs the owner's confirmation.* **Two claims of the approved text are corrected, because the code does not make them true.** (a) *Approved (Goal): "decides in constant time".* Built: a condition takes the same time on every bar and whatever the history, except `rising`/`falling(x, n)`, which compile to a loop of n steps (n up to 255). A scratch probe on a Release build (Apple-silicon Mac, a series that rises all the way so that the run never breaks early, 2 million evaluations each) gave 14.5 ns for `rising(close, 3)`, 117 ns for `rising(close, 50)`, 452 ns for `rising(close, 255)` and 950 ns for `rising(rsi(14) + ema(20), 255)` per `Evaluate`, against 2.8 ns for `close > ema(20)`: one long run costs more than the whole ten-condition set of the 0.3 µs target, whose longest runs are `rising(close, 3)` and `falling(roc(5), 2)`; no benchmark measures a long run. (b) *Approved (Types): "Anything else is a type error naming both sides".* Built: a comparison names both sides (`close > true`: "`>` cannot compare `close` (a number) with `true` (a true/false value)"); `and`/`or`/`not`, `+ - * /`, the unary minus and the arguments of a builtin name the operand that is wrong, the type the place needs and the type it has (`close + true > 1`: "The right side of `+` needs a number, but `true` is a true/false value"), which is all a reader needs to fix it; the code, the span and the suggestion are unchanged.
19. **Lagged reads are by position, not by session; `lag_across_session` (warning) is new** (the approved text was silent). Found by the final review: `crosses_above(close, vwap)`, the headline example of the language, compares the first bar of a session with the last bar of the one before, because the history of the frame runs on across sessions (ADR 0031, decision 4) while `vwap` starts again at the open; `close > vwap and close[1] <= vwap[1]`, `rising(vwap, 1)` and `crosses_above(close, today_open)` do the same (the review's seeded random walk of 500 sessions: true on the first bar of about a quarter of the sessions, against a few percent at every other bar). Built: `x[k]` keeps its meaning, `IndicatorInfo.HasValueAtSessionOpen(spec)` is new in the catalog (true for `vwap`, `today_open/high/low`, `prev_day_*`, `gap_pct` and an opening range of one bar), and the lint warns once for each call or lone subscript, with the `time` check that clears it (see *Meaning*); pinned by a hand-calculated two-session example and by a check of the asked-for time against the real frame (28 shapes). Not marked ⚠: nothing the owner approved is changed or refused, and a warning does not stop a compile (as in Amendment 11). **The stronger rule was not built:** a lagged read of such a feature that is *unknown* across a session reset needs the frame to know the session of each history slot (a new member of `FeatureFrame`, which the architecture test of the library lists by name), changes the oracle, and needs a rule of its own for `prev_day_*`; open as ISS-13 in the roadmap issues log, the owner may ask for it.

## Follow-ups
Things the build deliberately left, each a candidate for the slice that touches the area.
- **P3-03 — the frame and the plan.** The merged plan does not add a feature on the evaluation timeframe: a plan with no feature on it (`time >= "09:45"` alone has no feature at all, and `FeatureFrame.Create` refuses an empty list) needs one added by the caller before `BarClosed(evaluationTimeframe)` can be asked. Every frame of a strategy must be created from the same plan: a `BoundCondition` is not checked against the layout of the frame it is given. The simulator must report `IgnoredBars` and `IncompleteBarsConsumed` (ADR 0031) and must pass the `TradingCalendar`, the `MarketContext` of P3-01d and the expiry dates when the plan says so.
- **P3-02b / P3-03 — the `time` check across sections.** `lag_across_session` sees a `time` check only in the same condition. The example strategy of doc 11 has `time >= "09:45"` in `setup` and `crosses_above(close, vwap)` in `trigger`: compiled as two conditions, the trigger is warned about although the setup guards it. P3-02b should compile the sections of a rule so that the check is seen (the `all:` lists of setup and trigger as one `and`, or the setup's lower bound passed to the compile); P3-03 should say what the simulator does on the first bars of a session. The stronger rule (unknown across a reset) is ISS-13.
- **P3-02b — the strategy file.** It hands conditions and the parameter map to `Compile` and may use `ExpressionPrinter` for the canonical text of a condition. The `all:` / `any:` lists of doc 11 become `and` / `or`. The limit of at most four `params` is its rule, not this library's.
- **ISS-12 — the cold start.** Measure `PublishReadyToRun` (and tiered compilation settings) for the hosts that compile conditions; the cause named in the ADR (first-use JIT of Superpower's generic tokenizer, the binder and the expression compiler) is from the stage timings, not from a profile. If it helps, add an assertion on the cold figure to the explicit benchmark; today only the warm median (≤ 3 ms) and the evaluation share (≤ 300 ns) are asserted, and not by `scripts/check.sh`.
- **Messages.** The wording is English only and may change; codes, spans and suggestions are the contract. A later UI story (the form builder, Monaco) reuses them; the wording of `unknown_character` for look-alikes and of the recovery's second and later problems can be improved there.
- **Dotted spellings for the other context names** (`index.vol_pct`, `vix.pct` …) are not defined; the flat catalog names are the spelling (`unknown_name` suggests `index_vol_pct` for `index.vol_pct`). Decide with the form builder whether the dotted forms are wanted.
- **Constant detection** sees literals and parameters only; `rsi(14) > 100` passes silently. A range-aware check would need the catalog to declare the range of each output.
- **Open question 8** (the six flagged deviations of ADR 0033) is still open and the owner's answer may change definitions in doc 11.
