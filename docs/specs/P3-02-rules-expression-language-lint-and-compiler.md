## Goal
Turn the **condition text** of a rule — `rsi(14) > 55`, `crosses_above(close, vwap)`, `tf("1h").ema(20) > tf("1h").ema(50)`, `time >= "09:45"`, `regime() == "UP_LOW_VOL"` — into something the simulator and the live engine can run over a `FeatureFrame`: parsed with precise errors, bound to the 56 catalog features, checked by a **look-ahead lint** that refuses what could read the future or mix timeframes in a way that gives a wrong answer, and compiled to a delegate (LINQ expression tree, never `eval`) that decides with **zero allocation** in time **bounded by its text** (an upper bound, not "constant time": the work of a condition never grows with the history the frame keeps or the number of bars, and `rising`/`falling(x, n)` cost n reads: Amendment 18). A test proves the whole chain cannot look ahead. Still pure library code: no database, API, YAML or screens.

## Definitions (numbers and rules the tests pin)
These are the rules **as built**; the tests pin exactly these. Where a rule differs from the text the owner approved on 2026-10-16 — or settles a contradiction inside it — it names its Amendment below. The ones that change, narrow or settle approved text (Amendments 1, 2, 3, 4, 7, 14 and 18, and 19 through ADR 0035) were **decided on research under the owner's delegation (2026-10-16/17); the owner may revert**; the approved wording, where there is one, is kept in the Amendments, which also give the status of each. The Definitions are the part a simulator or an editor author reads; the Amendments are the record of how they changed. The full language reference with examples is [doc 11 §2](../design/11-strategy-lab.md).

**Grammar** (precedence from loosest to tightest; keywords are lower-case: `and or not true false`):
```
or      := and ( "or" and )*
and     := not ( "and" not )*
not     := "not" not | compare
compare := sum ( ("<" | "<=" | ">" | ">=" | "==" | "!=") sum )?        -- not chained: a < b < c is an error
sum     := product ( ("+" | "-") product )*
product := unary ( ("*" | "/") unary )*
unary   := "-" unary | primary
primary := number | string | "true" | "false" | "(" or ")" | call
         | reference ( "[" ["-"] digits "]" )?                           -- a subscript only right after a reference; the lint decides which lags are usable (Amendments 1, 8)
reference := ident | "tf" "(" string ")" "." ident | ident "." ident    -- close, vwap, tf("1h").close, prev_day.high, today.open, index.trend
call      := ident "(" [ arg ( "," arg )* ] ")" | "tf" "(" string ")" "." ident "(" [ arg ( "," arg )* ] ")"
arg       := or | ident "=" ident                                        -- named argument: source=high
```
Numbers are decimal: digits, an optional fraction and an optional lower-case exponent (`55`, `0.5`, `1e-3`; `.5`, `1.` and `1E5` are errors, and so is a number the language cannot hold, `1e400`); strings use double quotes, with no escapes and no quote or line break inside; comments are not supported; whitespace (space, tab, CR, LF) is free; identifiers are letters, digits and underscores, not starting with a digit (upper case is read so that `MON … SUN` can be names; the binder refuses `RSI`, Amendment 8). Everything is case-sensitive. Only ASCII is part of the language outside strings: any other character is a problem that names its code point. **A text is at most 4,000 characters and nests at most 64 levels (the brackets and prefix operators open at once, and the depth of the tree, where every operator of a chain is a level, so about 60 conditions joined by `and` is the most one condition can hold: Amendment 3).**

**Names.** An identifier resolves in this order: strategy parameter → builtin, constant or `time` → catalog feature (a feature qualified with `tf("…")` or written dotted is always a catalog feature). A parameter is a *number* known at compile time; used as a catalog argument (`rsi(rsi_len)`) it becomes part of the `FeatureSpec`, and a parameter that hides a feature, builtin, constant or `time` wins with a warning (`shadowed_name`, Amendment 11). A catalog feature is called with its parameters positionally in catalog order (`bb_upper(20, 2)`), with defaults for the trailing ones the catalog declares (`rsi()` is `rsi(14)`); each argument is a number known when the condition is compiled (a literal, a parameter, `MON … SUN`, or arithmetic, unary minus, `abs`, `min`, `max` of those); source-aware indicators take `source=close|open|high|low` as a named argument. A feature with parameters written without parentheses (`rsi`) and a function written without them (`abs`) are `bad_arguments`; a feature without parameters takes both `vwap` and `vwap()` (Amendment 9). DSL spellings: `prev_day.X` → `prev_day_X` (open, high, low, close, volume), `today.X` → `today_X` (open, high, low), `index.trend` → `index_trend`, `index.adx` → `index_adx` (every other dotted pair is an error; the other context names are written flat: `vix_pct`, `index_vol_pct`, `regime_trend` …).

**Timeframes.** An unqualified feature uses the *evaluation timeframe* given to the compiler (the strategy timeframe). `tf("1h").F` uses another one of `1m 5m 10m 15m 30m 1h 1D 1W 1M` (case as written; `1d` is an error with the suggestion `1D`). The value is always that of the **last closed bar** of the timeframe (the frame's rule), with one exception: the twelve per-session names (`vwap`, `or_high`, `or_low`, `today_*`, `prev_day_*`, `gap_pct`) on 1m to 1h are not ready between the first 1-minute bar of a new India date and the timeframe's first closed bar of that date (they are *pending*: a coarser timeframe such as `tf("1h")` is unknown for up to 60 minutes of every session; [ADR 0035](../adr/0035-per-session-features-keep-the-history-of-the-session-only.md), the rule is under *Meaning* below). The catalog's refusals apply and become errors with the feature and timeframe named (`vwap` on 1D, `prev_day_*` on 1W …). The twelve calendar and context features are always read on 1m, whatever the strategy timeframe (`tf("1h").vix` is an error; `tf("1m").vix` is allowed). Only a catalog feature can be qualified: `tf("1h").crosses_above(…)` is `unknown_name`.

**Types.** `number` (double), `bool`, `time` (the keyword `time`, compared with a string literal of the form `"HH:MM"`) and `regime` (the function `regime()`, compared with one of the nine names, or with a constant integer 1..9) — the last two and a string literal exist only next to such a comparison. `and or not` take bool; arithmetic and ordering take number; `==`/`!=` take two numbers or two bools; `time` takes all six comparisons with a time string on either side; `regime()` takes `==`/`!=` only. A parameter must be a finite number. The whole condition must be bool. Anything else is a type error: a comparison names both sides, and every other operator and every builtin names the operand that is wrong, the type that place needs and the type it has; a number where a true/false value is needed (a whole condition, or an operand of `and`, `or`, `not`) also gets the advice "Compare it with something, like rsi(14) > 55." (Amendments 9, 18).

**Builtins:** `crosses_above(a, b)`, `crosses_below(a, b)`, `rising(x, n)`, `falling(x, n)`, `between(x, lo, hi)` (inclusive), `abs(x)`, `min(a, b)`, `max(a, b)`, `regime()`, and the keyword `time`. Constants: `MON … SUN` = 1 … 7 (for `day_of_week`). `n` is a whole number of at least 1 known when the condition is compiled.

**Meaning:**
- `x[k]` (k = 1 … 255, an integer literal after a reference): the feature's value **k closed bars of its own timeframe ago** (frame `At(handle, k)`). **`x[0]` is refused** (`negative_or_zero_lag`, suggestion `x`; Amendment 1). *Approved wording: "`x[0]` is `x`".* In the formulas of this section `a[k]` is notation for the expression `a` with every feature read `k` closed bars further back, not syntax: the language writes `a` for `k = 0` and allows a subscript only after one reference, with a whole number from 1 to 255 (`close[1]`).
- Lagged evaluation: `crosses_above(a, b)` is `a[0] > b[0] and a[1] <= b[1]`; `crosses_below(a, b)` is `a[0] < b[0] and a[1] >= b[1]`; `rising(x, n)` is `x[0] > x[1] > … > x[n]` (n whole steps, strict), `falling(x, n)` the mirror. `a`, `b`, `x` may be any numeric expression: the expression is evaluated *at lag k*, i.e. every feature leaf is read with `At(handle, k + its own subscript)` and constants stay constants. The lags add up (`rising(close[200], 100)` reads 300 bars back, Amendment 10).
- **Per-session features keep the history of the session only** ([ADR 0035](../adr/0035-per-session-features-keep-the-history-of-the-session-only.md); it supersedes Amendment 19, which had only warned about the crossing of two sessions). `x[k]` is still the value `k` closed bars of the feature's own timeframe ago, by position, and the history of the frame still runs on across sessions for the rolling features (`ema(20)` at 09:30 uses the previous day's bars; ADR 0031, decision 4). The twelve names that start again at each India date — `vwap`, `or_high`, `or_low`, `today_open/high/low`, `prev_day_open/high/low/close/volume`, `gap_pct` — do not. On an intraday timeframe (1m 5m 10m 15m 30m 1h) the frame forgets their history at the timeframe's first bar of a new India date and holds them *pending* (not ready at any lag, `Value` NaN) from the first 1-minute bar of the date until the timeframe closes its first bar of that date. With S the number of bars the timeframe has closed on the date, lag 0 is the value when S ≥ 1, and lag k ≥ 1 is the value k bars ago when k < S, else unknown. So `vwap[1]` and `crosses_above(close, vwap)` are unknown until the timeframe has closed a second bar of the date and `rising(vwap, 3)` until the fourth: a lag never compares two sessions, and unknown is not true (the three-valued logic below), so `not crosses_below(close, vwap)` is unknown on the first bar too. `prev_day_*` and `gap_pct` get no exemption: a lag across the open is unknown. What remains is written by hand: yesterday against the day before is `tf("1D").close[1]` or `tf("1D").gap_pct[1]`, and a gap through yesterday's level is `close > prev_day.high and close[1] <= prev_day.high` (the level read at lag 0 only; `crosses_above(close, prev_day.high)` is unknown on a gap-up first bar). On 1D nothing restarts (`gap_pct[1]` on 1D is yesterday's gap); 1W and 1M refuse these names; the rolling and the date-driven features are untouched. A `time >= "HH:MM"` check is a trading rule now, no longer a correctness device. The rule is in the data of the frame: no new `FeatureFrame` member, no change to the compiled code. A session is the India date of the start of the bar a timeframe feeds its indicators, so a morning and an evening block on one date are one session (a documented limit). *Decided on research under the owner's delegation (2026-10-16/17); the owner may revert.*
- `time` is the **India clock time at which the evaluated bar closed**: the start of the last accepted 1-minute bar plus one minute (the bar `09:44` makes `time` = `09:45`); it is read from `FeatureFrame.LastBarTime`. A comparison of `time` with `"HH:MM"` is on whole minutes. `time` is unknown before the frame has accepted a bar and is refused when the evaluation timeframe is 1D or longer.
- `regime()` is the `regime` feature (1 … 9); `regime() == "UP_LOW_VOL"` is resolved to the code at compile time (the names are case-sensitive and exact).
- **Three-valued logic** (Kleene): *unknown* is the result of a comparison, `crosses_*`, `rising/falling`, `between` or `time` when any operand is not ready; `false and unknown = false`, `true and unknown = unknown`, `true or unknown = true`, `false or unknown = unknown`, `not unknown = unknown`. The lagged builtins and `between` are atomic: unknown if any of their values is not ready, even when another would already decide. A decision (`Evaluate`) returns *true* only when the result is *true*; *unknown* is false. Arithmetic with a not-ready operand is not ready (NaN); `x / 0` (an exact zero divisor) is not ready (NaN), never an exception; a quotient that overflows is ±infinity, a number (Amendment 12).
- **When to evaluate** is the caller's business (the simulator evaluates at steps where `frame.BarClosed(evaluationTimeframe)`); the compiled condition itself is a pure function of the frame as it is *now*.
- **Problems.** A bad condition is never an exception: the result carries every problem found, each with a code, a message, a span (offsets, line, column) and a severity. If the text does not parse, the problems are the syntax ones (`strategy.syntax.*`; the first is exact, the later ones best effort); if it parses, all binder and lint problems are reported together, in source order (Amendment 7). At most 100 syntax problems are listed: the first 100 found, in source order (the lexical problems are found before the syntax ones, and an unclosed bracket found at the end of the text may not be listed); a text with more has one `strategy.syntax.too_many_problems` that covers the rest of the text (Amendment 7).

**Lint rules** (each has a stable code `strategy.lint.<name>`, a message that names the offending text, and a suggestion where one exists; all are errors unless marked warning or information):
| Code | Rule |
|------|------|
| `unknown_name` | an identifier or function is not a parameter, builtin, constant, `time` or catalog feature; a dotted pair that is not one of the spellings; a regime name that is none of the nine; a builtin or parameter written with `tf(…)` (suggestion: the names at the smallest edit distance found, if that is at most 2 — at most 1 for a text of one or two letters —, compared case-insensitively, at most five; the nearest tier only) |
| `bad_arguments` | wrong number, kind or range of arguments (the catalog's parameter names, ranges and defaults are quoted); an argument that is not known at compile time; a function or feature written without its parentheses; a bad or repeated `source=`. The span of too many arguments runs from the first surplus argument to the last |
| `unsupported_timeframe` | `tf("…")` is not one of the nine, or the catalog does not support the feature on it |
| `negative_or_zero_lag` | a subscript or `rising/falling` count that is not a whole number of at least 1 (`x[0]`, `x[-1]`, `rising(x, 1.5)`; Amendment 1). The span is the number, except for a subscript of zero (`close[0]`, `close[-0]`, `close[00]`), where it is the whole subscripted feature (`close[0]`, `tf("1h").close[0]`, not only the `[0]`), so that the suggestion `close` replaces its own span; a negative lag, or a target that could not be bound (`closee[0]`), has no suggestion |
| `lag_too_deep` | the history depth needed (the largest lag read plus 1, the lags adding up) exceeds 256 (the frame's cap) |
| `lag_on_non_feature` | a subscript applied to a strategy parameter, a constant or `time` (a subscript after a call, a group, a literal or another subscript is the syntax problem `subscript_on_non_reference`; use the lagged builtins, or write the feature twice) |
| `mixed_timeframes_in_lag` | a `crosses_*`, `rising` or `falling` whose feature leaves are not all on one timeframe: "the previous value" would mean different times; compare on one timeframe, or lag one operand explicitly. The calendar and context features are a clock of their own, the date: lagged among themselves and against numbers, never together with a bar feature, on 1m and 1D too (Amendment 4); when the date is among the clocks and there is no explicit form, the advice is "A calendar or context feature changes once a date, so compare it without a lag, or lag only the bar side by hand." |
| `time_on_daily` | `time` used when the evaluation timeframe is 1D, 1W or 1M |
| `bad_time_literal` | a time string that is not `HH:MM` within 09:15 … 15:30 |
| `type_mismatch` | see *Types* |
| `constant_condition` (warning) | a true/false part that reads no data (`1 < 2`, `crosses_above(1, 2)`, a parameter against a number); a bare `true` or `false` only when it is the whole condition; `rsi(14) > 100` for a bounded oscillator is *not* detected (Amendment 11) |
| `redundant_timeframe` (warning) | `tf("15m").ema(20)` when the evaluation timeframe is already 15m |
| `needs_context` / `needs_expiry_days` (information) | the plan reports that the frame must be created with a `MarketContext` / expiry dates; these are not lint failures, and are reported only for a condition without errors |
| `shadowed_name` (warning) | a strategy parameter has the name of a feature, builtin, constant or `time` and wins (Amendment 11; not in the approved table) |
| `lag_across_session` (warning) | a lagged read (a subscript, or the lags of `crosses_*`, `rising`, `falling`) of one of the twelve per-session features (`vwap`, `or_*`, `today_*`, `prev_day_*`, `gap_pct`) on 1m to 1h from further back than a whole session holds: `k` bars of its timeframe `T` with `k · T` at least the 375 minutes of a session (`vwap[75]` and `rising(vwap, 75)` on 5m, `rising(vwap, 7)` on 1h, `tf("5m").vwap[80]` on a 1D strategy). Every bar that far back is in an earlier session, where the feature has no value, so that part of the condition is never known (unknown is not true). Whatever the strategy's timeframe; not for the 1D lane, where nothing restarts; a `time` check does not clear it. A shorter read that reaches before the first bars of a session is unknown on those bars only and is not warned. On a 1m lane the warning always comes with `lag_too_deep` (375 is above the 256 of the frame). The message names the features, how far back and the most a session holds (ADR 0035; the warning of Amendment 19 asked for a `time` check instead) |

## Acceptance criteria
**Syntax**
1. A table of ≥ 60 valid sources parses to the expected AST (hand-written expected trees): precedence and associativity (`a or b and c`, `not a and b`, `-x * y`, `a - b - c`, `a / b * c`), every literal form, the dotted DSL spellings, `tf("1h").ema(20)`, named arguments, nested calls and subscripts. A table of ≥ 60 invalid sources yields the expected problem code and exact span (empty text, unbalanced parentheses, unknown character, chained comparison `a < b < c`, a subscript on a call, missing argument, trailing comma, unterminated string, a number followed by an identifier …); every problem has line and column. **[As built: 98 valid and 108 invalid sources; Amendments 7, 8.]**
2. The printer is canonical and round-trips: for ≥ 500 generated ASTs `Parse(Print(ast))` equals `ast`, and the printed form of two sources that differ only in whitespace is identical. **[As built: 1,000 generated trees.]**

**Binding and typing**
3. Every catalog feature (all 56) can be written in its DSL form with its default arguments and binds to the `FeatureSpec` the catalog's `DefaultSpec` gives; a table pins the spec produced for ≥ 30 forms (positional arguments, defaults, named `source=`, `tf()` qualification, dotted spellings, parameters, `regime()`); two spellings of the same feature produce *equal* specs (so the frame shares one instance).
4. Unknown names, wrong argument counts or ranges, unsupported timeframes and type errors each give the documented code, quote the catalog's parameter names/ranges, and suggest the closest names; a typo in any of the 56 names (one deleted, inserted or swapped letter) yields the right suggestion (property over all names).
5. Parameters: `rsi(rsi_len)` with `rsi_len = 21` equals `rsi(21)`; an unknown or non-number parameter is an error; the parameter map is not mutated; compiling the same text with two maps gives two independent plans.

**Lint**
6. Every row of the lint table has at least one failing example (exact code, span, message text pinned) and one near-miss that passes; the three-way set of rules around lags (`lag_on_non_feature`, `mixed_timeframes_in_lag`, `lag_too_deep`) is exercised on every timeframe pair of {1m, 5m, 15m, 1h, 1D, 1W}; all problems of a source with several faults are reported together in source order. **[As built: 161 failing and 93 near-miss examples at the build (the row `lag_across_session` was added, Amendment 19); 166 failing and 99 near-miss at the close-out (the `lag_across_session` examples were rewritten for the narrower rule of ADR 0035, the lag-0 span of Amendment 1 and the operand advice of Amendment 18 were added, and a convention test checks that replacing the span of a problem with its suggestion removes that problem).]**

**Evaluation semantics**
7. The compiled condition equals an **independent tree-walking interpreter** (plain code in the test project, written from the Definitions, sharing nothing with the compiler) on ≥ 200 seeded random expressions × random frames (random bars over several sessions and weeks, every evaluation timeframe 1m … 1W, with and without a context), comparing the full three-valued result at every closed bar of the evaluation timeframe. **[As built: 864 conditions on all nine evaluation timeframes, compared after every 1-minute step, with a second interpreter over the bound tree; Amendment 14. Since ISS-13 (ADR 0035) the interpreters read the twelve per-session features from an independent reference built from the definition of the rule (a public `TimeframeBuilder` and the catalog indicator, the session counted from bucket start dates), and 288 session-bound conditions (48 on each of the six intraday timeframes, over dense, gappy and sparse series) are compared as well; a positional reference without the rule must disagree with the compiled conditions.]**
8. ## Contract (public surface, sketch)
```csharp
public readonly record struct SourceSpan(int Start, int End, int Line, int Column);
public sealed record Problem(string Code, string Message, SourceSpan Span, string? Suggestion = null, ProblemSeverity Severity = ProblemSeverity.Error);

public sealed record CompileContext(Timeframe EvaluationTimeframe, IReadOnlyDictionary<string, double> Parameters);

public sealed class ConditionCompiler {
  public static Result<CompiledCondition, IReadOnlyList<Problem>> Compile(string source, CompileContext context);   // parse + bind + lint
}
public sealed class CompiledCondition {
  public string Source { get; }
  public IReadOnlyList<FeatureSpec> Features { get; }      // exactly what the expression reads
  public int HistoryDepth { get; }                         // 1 … 256
  public bool NeedsContext { get; }  public bool NeedsExpiryDays { get; }
  public IReadOnlyList<Problem> Warnings { get; }
  public BoundCondition Bind(FeatureFrame frame);          // resolves handles; throws only on a frame that was not created from these features
}
public sealed class BoundCondition {
  public bool Evaluate(FeatureFrame frame);                // unknown => false; zero allocation
  public Truth EvaluateTruth(FeatureFrame frame);          // True / False / Unknown
}
public enum Truth : sbyte { False = 0, True = 1, Unknown = -1 }

public static class ConditionSet { /// merges the plans of several conditions (one frame for all): union of features, max history depth
  public static CompiledPlan Merge(IReadOnlyList<CompiledCondition> conditions); }
```
(The exact `Result` shape follows the library's existing `Result` type; if it cannot carry a list of problems, a `CompileResult` record is used instead — decided in the build and recorded in the ADR.)

**As built (Amendments 5, 6):** `ConditionCompiler` is a static class and `Compile` returns `CompileResult(CompiledCondition? Condition, IReadOnlyList<Problem> Problems)` (on success `Problems` holds the warnings and the `needs_*` notes; `IsSuccess`, `Errors`); `ConditionParser.Parse(string)` returns `ParseResult(Expression? Tree, IReadOnlyList<Problem> Problems)`; `CompileContext` also has a constructor that takes only the evaluation timeframe (no strategy parameters; there is no constructor without arguments); `CompiledCondition` also has `EvaluationTimeframe`, `BoundCondition` has `Condition`; `CompiledPlan` (the result of `ConditionSet.Merge`) has `Conditions`, `Features`, `HistoryDepth`, `NeedsContext`, `NeedsExpiryDays` and `BindAll(frame)`. `Bind` throws an `ArgumentException` for a frame that lacks a feature of the condition **or keeps less history than it needs**; the delegate is built at the first `Bind`. Public types are in `XDrishti.Strategies` (`SourceSpan`, `Problem`, `ProblemSeverity`), `.Syntax` (the parser, the tree, the printer, `SyntaxCodes`), `.Lint` (`LintCodes`) and `.Compilation`; the binder, the bound tree, the linter and the expression builder are internal. **Close-out addition (Amendment 2):** `CompilerWarmup` (static, in `.Compilation`) with `public static void Run()`, which compiles fixed sources through the public pipeline and drops the results; a host starts it once per process on a background thread.

## Non-functional
- Performance: criterion 12; the evaluator is a compiled `Func<FeatureFrame, sbyte>`-style delegate over `int` handles resolved once at `Bind`, no boxing, no LINQ at run time. **As built:** `Decision(FeatureFrame, int[] handles) → int` (1 true, 0 false, −1 unknown), compiled once per condition at the first `Bind` and shared by every frame; the handles are the per-frame part (Amendment 6). The time of a condition is bounded by its text, never by the history or the number of bars; `rising`/`falling(x, n)` cost n reads (Amendment 18). A host runs the compiler warm-up once at start (Amendment 2).
- Security: no string is ever executed; the only dynamic code is an expression tree built from the validated AST; every identifier is checked against a closed vocabulary (catalog, builtins, parameters); numeric literals are bounded; recursion depth is limited (a source nested more than 64 levels or longer than 4,000 characters is refused with a problem, never a stack overflow). **As built:** the 64 levels are the brackets and prefix operators open at once and the depth of the tree, where each operator of a chain is a level (Amendment 3, kept: the depth check is what makes "a problem, never a stack overflow" true for the printer, the delegate builder and the plan, which have no stack guard of their own).
- Privacy: tests use only invented series and invented strategy text; nothing is read from `data/`.
- Observability: none (pure library).

## Open questions (1–7 answered 2026-10-16: recommendations approved; 8 still open)
1. **Split.** This slice is the *expression language* (text of one condition → checked, compiled, evaluated); the *strategy file* around it (YAML sections, `params` ≤ 4, `sell:` block, BUY → SELL mirror, JSON Schema) is **P3-02b**. **Recommendation:** split as written, so each slice stays reviewable and testable in isolation. OK?
2. **Parser technology.** Doc 03 names Superpower (a parser-combinator library, one NuGet package) with compiled expression trees. **Recommendation:** follow doc 03. The alternative is a hand-written parser with no dependency, which is also easy for a grammar this small; say so if you prefer no new dependency.
3. **Unknown is not true.** Three-valued logic: a condition whose data is not ready is *unknown*, not *false*, so `not (rsi(14) > 55)` cannot fire before RSI exists; a decision treats unknown as false. **Recommendation:** as written.
4. **`time` means the close time of the bar being evaluated** (a 15-minute bar covering 09:30–09:45 is evaluated at `time` = 09:45, so `time >= "09:45"` first holds on that bar, not on the one before it). **Recommendation:** as written; the alternative (the bar's start) would let a 09:45 rule act on a bar that closed at 09:30.
5. **Lagged evaluation needs one timeframe.** `crosses_above`, `rising`, `falling` and `x[k]` of an expression are refused when their operands sit on different timeframes (for example `crosses_above(close, tf("1D").ema(20))` on a 15m strategy): the "previous value" of the two operands would be different instants. The explicit form `close > tf("1D").ema(20) and close[1] <= tf("1D").ema(20)` is allowed and says what is meant. **Recommendation:** refuse, as written, with that suggestion in the message.
6. **Strictness.** `crosses_above(a, b)` is `a[0] > b[0] and a[1] <= b[1]` (a touch that does not pass is not a cross; equality on the previous bar counts as "not above yet"); `rising(x, n)` is strict at every step. **Recommendation:** as written.
7. **The two small frame/catalog prerequisites** (rename to `DateFeature`, flags on `IndicatorInfo`, `FeatureFrame.LastBarTime`) are done inside this slice as its first step. **Recommendation:** yes — they are the P3-01c review follow-ups and they must precede the first user of the names.
8. **Still open from P3-01c:** the six flagged build deviations of ADR 0033 (the `vix_pct` window, the `regime_vol` fallback, the cursor, the partial first week, the exact thirds, the end of the context) are waiting for your confirmation. This slice does not depend on them (it only uses the names), but if you revert one, the definitions in doc 11 change.

So a lagged call (`crosses_*`, `rising`, `falling`) may read them among themselves and against numbers (`crosses_above(vix, 20)`, `rising(vix, 2)`, `rising(vix - index_trend, 2)`; `regime() == 3` has no lag) and never together with a bar feature, on any strategy timeframe, 1m included, and for `tf("1m")` bar features too: `crosses_above(close, vix)` is refused on 1m, 15m, 1D and the rest (the message offers `close > vix and close[1] <= vix`, which lags the bar only). *History:* the first build counted them as timeframe 1m and so let `crosses_above(close, vix)` through on a 1m strategy, where `vix[1]` is yesterday's value all day and the "crossing" holds at every minute of a date (VIX 50 yesterday, 30 today, close 25 yesterday and 40 all today; the explicit form holds at the first minute only); a review found it and the rule was tightened. *No exception for 1D (close-out):* on a 1D strategy the previous date and the previous bar coincide only on complete data: a session whose closing minute (15:29) is missing closes its daily bar at the first minute of the next date, after the date features have moved on, and the pairing is lost (pinned by `DailyStrategyDateLagTests`: with Wednesday's 15:29 missing, the value one date back is no longer the value the previous daily close saw at two of the three closes after the first, and the explicit form `close > vix and close[1] <= vix` over the four daily closes changes from false-true-true-true to false-false-true-true). So the refusal is uniform: one rule for nine timeframes, no demonstrated use for a relaxation, and relaxing a refusal later is additive (it breaks no stored strategy) where tightening it later is not. *Legitimate uses:* a date-only lagged call is allowed, and it describes the date: it holds at every evaluation of that date (`crosses_below(vix, 40)` is true at every minute of the date on which the VIX fell below 40; one entry per instrument per day is the simulator's job, P3-03); the explicit form exists only when one side is a plain reference on the strategy's timeframe, so `crosses_above(adx(14), index_adx)` has none. *Message (built at the close-out):* when the date is among the clocks and there is no explicit form, the advice reads "A calendar or context feature changes once a date, so compare it without a lag, or lag only the bar side by hand."; the messages that offer the explicit form still say "Compare on one timeframe, or say what you mean: …". *Known limit (open, minor):* the date advice also replaces "Compare on one timeframe" when the call mixes two bar timeframes as well (`rising(close + tf("1h").close - vix, 2)`), so removing the date feature leaves the other fault to be found next.

7. *Decided on research under the owner's delegation (2026-10-16/17); the owner may revert. Status: kept; the note was reworded and the work bound was pinned by tests.* **The parser is a hybrid, recovery is best effort after the first problem, the stages do not mix, and at most 100 problems are listed.** *Approved (scope item 4): "all problems found are reported, not only the first".* The tokenizer and the small productions are Superpower combinators; the recursive spine is plain Superpower parser functions with precedence climbing (nine combinator layers needed more than 1 MB of stack at 64 levels). At a syntax failure the parser explains it, repairs the token list and parses again: the first problem is exact, the later ones are those of the repaired text. A text with a syntax problem is answered with its syntax problems only (the names and the lint are not run), so "all problems are reported" holds within a stage. *Limit:* every repair parses the whole text again, so a text of 4,000 characters made of nothing but faults cost up to 0.7 s and 1.5 GB (3,990 commas after `f(`); the recovery now stops after 100 problems (lexical ones counted) or 232 parses, whichever comes first, and the parser lists the first 100 found, in source order, followed by one `strategy.syntax.too_many_problems` whose span is the rest of the text (≤ 52 ms and ≤ 27 MB for the worst texts measured). A follow-on problem is not reported after a value the recovery supplied, at a comma already reported as having no argument, at a `!` after a value (already an `unknown_character`) or at an end the recovery made itself (`close <> 5`, `rsi(,)`, `close ! 5`, `close === 5`: one problem each). *Close-out:* "found" is not the order of the text: the lexical problems are found before the syntax ones and an unclosed bracket is found at the end of the text, so with enough problems an earlier one may not be listed (pinned: 150 unknown characters after an early trailing comma hide the comma; `(` followed by 150 conditions with a trailing comma hides the unclosed bracket). The recovery can also end on its bound of parses with one or two problems listed (silent repairs such as `[ ) ` repeated 1,000 times), so the note no longer says "the limit is 100": it reads "There are more problems than are listed: the first N are shown. Fix them and read the condition again to see the rest." The bound of 232 parses had no test (removing it left every syntax test green); four more worst-case shapes (`[ ) `, `[ ] `, `) [ ` and `] [ `, each repeated 1,000 times) now pin it. *The stage rule stays:* binding the repaired tree to show name problems earlier was measured in a scratch copy and rejected (it found the name typo in 93.5 % of 291 cases, but in 34.7 % of the cases it also gave an error that the typo-only text does not give); going back to the approved wording would need an uncapped recovery (0.84 s and 1.5 GB for one 4,000-character text) or a rewrite of the grammar and the recovery. *For P3-02b:* the aggregate of the problems of many conditions needs a cap of its own, and a tool that hands the list to an assistant should pass only the first few problems.
8. **Grammar details the spec left open or contradicted.** Identifiers accept upper-case letters (the spec's `[a-z_]…` contradicts `MON … SUN`; the binder refuses `RSI` as `unknown_name`, suggestion `rsi`); a subscript parses with an optional minus (`close[0]`, `close[-1]`, `close[300]` parse and the lint decides), `x[1.5]` and `x[1e3]` are `bad_subscript`, one beyond the range of an integer `number_out_of_range`; a subscript on anything but a reference is the syntax problem `subscript_on_non_reference` (criterion 1 asks for a syntax problem for a subscript on a call), so `lag_on_non_feature` remains for a parameter, a constant and `time`; only a lower-case `e` is an exponent (`1E5` is `number_followed_by_identifier`); strings have no escapes and cannot hold a quote or a line break; a bare `tf` is an ordinary name that the binder rejects, `tf("1h")` alone is `bad_timeframe_qualifier`; a look-alike character (`＞`, `&&`, `||`, `!`, `≥`, typographic quotes) is reported once, with the replacement as suggestion, and then read as the token it stands for; a parenthesised node's span includes its parentheses.
