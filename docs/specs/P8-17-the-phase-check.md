# P8-17 — The phase check

- **Status:** Draft (written 2026-10-24; decisions below were researched under the owner's delegation; the owner's Approved is still needed before an agent builds it)
- **Phase / roadmap row:** P8 — Reports & UI, slice P8-17 of [P8-00](P8-00-reports-and-ui-plan.md); the exit: "'What works, in which basket, on which TF, with which exit' answered in < 2 min"
- **Design refs:** docs/design/18-roadmap.md (P8 exit) · P8-00 acceptance criteria 1 to 10, Q10 · P7-18 and ADR 0097 (the pattern: a read-only check of stored records, MET only on real evidence) · ADR 0080 (P6 check, "supplied, never verified" inputs) · P8-06 (endpoints, `ReportsOptions`), P8-08 (the Reports screen and its 3-interaction test), P8-16 (browser evidence) · ADR 0099 (population rule, six states)
- **Needs:** P8-08 and P8-16 built; P8-01, 05, 06 built. Wall-clock for (b): the owner's stopwatch on the owner's data after the stack runs the P8 build. Reads the screens P8-09 to P8-15 only as "built" flags.
- **Size:** 2 agent-days plus the owner's wall-clock minutes
- **Safety:** no. The check is a read: it writes nothing, runs no job and changes no setting; its local script reads files under `data/p8-evidence/` and runs `npm run size` and one Vitest file, nothing that touches the stack's state. The stopwatch note is typed by the owner into a local file, never sent anywhere.

## Goal
Say, from what can be read, whether the phase exit is met: the question answered in at most four interactions and two minutes by the owner's stopwatch on the owner's data, each request of the path under one second, every report number carrying its evidence and honest state, no double counting, read-only screens, the first-load bundle within 200 KB gzip, and the responsive/accessibility pass recorded. "Nothing has enough evidence yet" is a valid answer; the check never demands a winner and never prints MET on a criterion it could not read.

## Scope
**In:**
- (a) the automated **interaction-budget test** (frontend) and its **path manifest** (shared with a backend timing test);
- (b) the **owner stopwatch procedure** and its recorder;
- (c) the read-only **server check**: pure `Domain/Reporting/ReportsPhaseCheck`, handler `EvaluateReportsPhaseCheckHandler`, `GET /api/reports/phase-check`, `xd reports phase-check`;
- (d) the **local summary**: `scripts/p8-phase-check.sh` and `frontend/scripts/p8-evidence.mjs` (bundle, browser checklist, interaction test, stopwatch);
- the ADR that closes the phase, with the owner's dated stopwatch note.
**Out:** any change to a report, screen or setting; running the P8-16 browser pass (it reads its output); asserting real-data timing in CI (reported, not asserted); judging the owner-gated slices P8-18 to P8-21 (listed as built or not, never required); a stored copy of the check (it is recomputed).

## Acceptance criteria
1. Given the seeded fixture (three baskets, three strategies, two exit labels, a known answer) and a signed-in user at Today, when the test clicks Reports, opens the Baskets control and picks a basket, then the headline card shows the known answer sentence; the test counts interactions with the counting wrapper (rule below) and **fails above 4**; with the optional fourth interaction ("open What works") the full ranked view is shown. A fixture with no qualifying cell shows "Nothing has enough evidence yet" within the same count. *`whatWorksPath.test.tsx`.*
2. Given the same run, then the requests the screen made for the answer are exactly the `answerPath` operations of `backend/contracts/what-works-path.json` (`GetReportRuns`, `GetReportWhatWorks`, matched by method and path against the OpenAPI contract), no request is repeated more than twice, and the page made at most 12 requests in all. *`whatWorksPath.test.tsx`.*
3. Given the manifest, when `ReportsPathBudgetTests` runs on the Testcontainers fixture, then each `answerPath` request has p95 under 1,000 ms over 20 calls after one warm-up (the first, cold, call is reported in ms, not asserted), and the other landing requests are timed and reported. *backend integration test.*
4. Given `GET /api/reports/phase-check`, then it returns criteria 1 to 10 of P8-00 (numbered as there) each `MET | NOT MET | NOT EVALUABLE` with a detail line, the limits always printed, and the answer the What-works view gives on the owner's default set (ranked cell with its n and lower bound, or the "nothing has enough evidence yet" sentence with the counts); it writes nothing (statement-recording test). Exit code of the verb 0 whatever the verdicts. *`ReportsPhaseCheckTests`, `ReportsPhaseCheckApiTests`.*
5. **Criterion 1 (the exit question).** MET only when all of: the server ran the answer path on the default set and each request took at most 1 s (cold and warm both shown); the interaction test passed at the commit under test; the owner's stopwatch note exists with three trials each at most 120 s and at most 4 interactions, dated, for the same commit. With any of these missing it is NOT EVALUABLE naming what is missing; a stopwatch trial above 120 s or an interaction count above 4 is NOT MET. *`ReportsPhaseCheckTests` (hand table), `p8-evidence.test.ts`.*
6. **Criterion 2 (evidence).** The check calls each built report handler in process on the default set and requires a non-empty evidence block (n, basis, range or run keys, limits). MET when every built report has it; NOT MET names the report; NOT EVALUABLE with no stored run. *`ReportsPhaseCheckTests`.*
7. **Criterion 3 (states).** Over every `MetricView` of those responses: a number exists only in state `value` or `provisional` and is finite; every other state has an empty number and a non-empty reason. MET when none breaks it (caveat in the label: "screen rendering is proved by the per-screen tests, not here"); one break is NOT MET with the path to the field. *same.*
8. **Criterion 4 (no double counting).** A pure probe builds a set with two overlapping runs of one strategy and a set with a gross and a costed run and requires `reports.run_overlap` and `reports.mixed_basis`; and the default set built from the stored runs is valid. MET when all three hold; NOT MET otherwise. *same.*
9. **Criterion 5 (read-only).** The check lists every route under `/api/reports`, `/api/learning`, `/api/cells`, `/api/plans/notices`, `/api/changelog`, `/api/lessons`, `/api/hypotheses`, `/api/experiments` and `/api/exports` from the host's endpoint table and requires GET only; a non-GET route is NOT MET unless it is on the compile-time approved list (empty in this slice; P8-18, P8-19 and P8-20 each extend it by commit with their POSTs, the owner's answer recorded). MET with the caveat "frontend folders are checked by the no-write test, not here". *`ReportsPhaseCheckApiTests`.*
10. **Criteria 6, 9 and 10 that need no records of the stack** are `NOT EVALUABLE` with the test or process that proves them: layers and contract (`Architecture.Tests`, `scripts/gen-api.sh`), determinism and security (a live probe: the same request twice gives byte-identical bodies for every built report, MET with caveat "names of fields, not content, were scanned for account, client, token and password words"), gates (`scripts/check.sh`, reviewer pass). *`ReportsPhaseCheckTests`.*
11. **Criteria 7 and 8 (bundle; responsive/accessible), by the local summary.** `scripts/p8-phase-check.sh` prints: bundle MET when `data/p8-evidence/bundle.json` (written by `npm run size` when `XD_EVIDENCE_DIR` is set, which `scripts/check.sh` does) shows guarded first load at most 200,000 bytes gzip and every lazy budget kept, recorded at the current `HEAD`; browser checklist MET when `browser-checklist.jsonl` has no `fail` for the screens built and every `na` has a reason, recorded for the current `HEAD`; evidence recorded at an earlier commit is **accepted when `git diff --quiet <recorded> HEAD -- backend frontend` shows no change**, else stale: NOT EVALUABLE ("recorded at X, HEAD is Y, code changed: run again"); an absent file is NOT EVALUABLE. *`p8-evidence.test.ts`.*
12. **Headline.** `P8 exit: MET` is printed only when criteria 1 to 5 and 7 and 8 are MET and none of 1 to 10 is NOT MET; any NOT EVALUABLE among 1 to 5, 7, 8 gives `NOT EVALUABLE (n of 8 need evidence)`; any NOT MET gives `NOT MET`. A MET resting on a convention carries its caveat in the label. Before it prints MET the code re-checks that criteria 1 to 5, 7, 8 are all present and distinct (anything else: `NOT EVALUABLE, malformed report`). *`ReportsPhaseCheckTests`.*
13. Given `Reports` has no stored run (the likely state at first), then criteria 1, 2, 3 are NOT EVALUABLE with "no stored run", criterion 4's probe and criterion 5 still run, and the text says so. *same.*

**Built P8-08 note (ADR 0103):** the Baskets multi-select menu stays open and hides the page from assistive technology, so the P8-08 test closes it with Escape: 4 interactions (click Reports, open Baskets, pick, Escape). Count the Escape step; the limit stays 4.

**Counting rule (the wrapper `countingUser`, written once in `src/test/interactions.ts`, reused from P8-08):** every call of `click`, `dblClick`, `hover` only if a menu opens on it, `selectOptions`, `type` (per field, however many characters), `upload` is 1; `keyboard('…')` is 1 per key token; `tab()` is 1 per call; opening a menu and choosing an item are 2. Navigation by the test's `initialEntries` is 0 (the cold start), a click on the sidebar entry is 1.

## The owner stopwatch procedure (written into the ADR; the owner's act)
1. **When:** after P8-16's pass, on the stack built from the commit under test (`deploy/xd-up.sh`), with the owner's real stored runs. Note the commit (`git rev-parse --short HEAD`).
2. **Before starting:** decide the basket you care about and write its name down; sign in; close other tabs; leave the **Data used** panel on its default set. Use a phone stopwatch.
3. **Trial:** open a new tab; start the stopwatch as you press Enter on `http://127.0.0.1:8080/reports` (the first trial after a hard reload, Cmd+Shift+R); choose your basket; stop when you can say the answer aloud in one of two forms, **using only what is on the screen**: "In basket B, strategy S, timeframe T, exit E: lower bound x R, n = N", or "Nothing has enough evidence yet: the largest sample is N of M needed". An answer you cannot back with the n and bound on screen does not count.
4. **Count your own interactions** (clicks, key presses, menu opens: the same rule as the test) and, if you like, note any panel that stayed on "Loading" for more than a second.
5. **Three trials**; record: `node frontend/scripts/p8-evidence.mjs stopwatch --seconds 84,97,71 --interactions 3,3,3 --basket "NAME" --answer "RANKED|NOTHING" --date YYYY-MM-DD --note "…"`. The recorder writes `data/p8-evidence/stopwatch.json` with the commit and prints it back; nothing is sent anywhere. Copy the numbers into the ADR.
6. **Reading it:** the criterion is the time to an answer, not the quality of the answer; "nothing has enough evidence" is expected on about 2.1 years of data. Do not rehearse the path first and call that cold.

No query parameters (the owner's stopwatch is never taken from a request). Problem codes: none new. `scripts/gen-api.sh` in the same change.

## Non-functional
The server check runs the answer path twice (cold, warm) plus the other report handlers once on the default set: it is an owner's read, not a polling target; it is single-flight and bounded by `ReportsOptions` (cache limit, run limit) so it cannot read more than the screens can. No secret read or logged; logs hold counts and milliseconds.

## Test plan
- **Unit (Domain):** `ReportsPhaseCheckTests` hand tables: criterion 1 across the nine combinations of {server timing ok/over/missing} x {interaction pass/fail/missing} x {stopwatch ok/over/missing} reduced to the rules above; the headline (all MET; one NOT MET; one NOT EVALUABLE; malformed); metric-invariant scan on crafted DTOs (a number on `insufficient`, a NaN, an empty reason); the overlap and mixed-basis probes.
- **Application:** handler with fakes: no runs; one run; a handler that returns a report without evidence; timings recorded with a fake `TimeProvider`; nothing written (every call a read).
- **Integration (Testcontainers):** seeded fixture, `GET /api/reports/phase-check` 200 and 401; a planted non-GET route in a test host is reported NOT MET; `ReportsPathBudgetTests`; contract snapshot.
- **Frontend:** `whatWorksPath.test.tsx` (ranked, nothing-qualifies, and a deliberately 5-interaction fake that fails the budget as a positive control); `p8-evidence.test.ts` for the recorder and `summary` (stale commit, missing file, `na` without reason).
- **Real-data check (reported, not asserted):** `scripts/p8-phase-check.sh` once on the owner's machine; the output and the stopwatch note go into the ADR whichever way they fall.

## Decisions (researched)
1. **Three witnesses, because each sees something the others cannot.** A test sees interaction counts on fixtures; a server check sees real stored data and real timings; only the owner's stopwatch measures "answer in under two minutes" as a person. The server cannot see the frontend bundle or the browser pass (the container mounts no `data/`: `deploy/compose.yaml` mounts only the CSV folder for the API), so those are read by a host script from files, not guessed. Rejected: a server endpoint that reads host files (would need a new mount, a deployment change for a read-only convenience); a combined single number.
2. **The stopwatch is supplied, never verified** (the pattern of the P6 phase check's `ReplaySeconds`, ADR 0080): printed as recorded with its commit and date; evidence for another commit is stale. It enters through a local file, not an HTTP field, so no UI or request can supply a flattering time.
3. **The budget is 4 interactions and 120 seconds; the test fails at 5.** P8-00 criterion 1 states "within 4 interactions and 2 minutes"; P8-08's own test expects 3 to the filtered answer (and fails above 4), leaving one for opening the full view. A budget of exactly the current count would make any later feature a failure; one more than needed would hide a regression. Rejected: counting only clicks (a keyboard path would look free).
4. **Timing: assert on the fixture, report on the owner's data.** CI machines differ; the owner's database size is unknown; P8-06 already reports cold and warm timing. Asserting p95 under 1 s on the seeded fixture (20 calls after warm-up) catches regressions; the real-data number is printed with its cache state.
5. **Read-only is checked on the route table, not on source text.** `EndpointDataSource` lists the real routes and their methods at runtime, so a POST added later under these prefixes is caught even if a code search would miss it; frontend writes are caught by the per-folder test (P8-00 D6).
6. **MET needs real evidence for every counted criterion.** Same posture as ADR 0097: NOT EVALUABLE is the default, MET is earned, and a MET that rests on a convention is labelled.
7. **No composite score.** The headline is the list of verdicts, not a percentage (P8-00 D10).
8. **Sources:** repo only (P7-18, ADR 0097, 0080, P8-00, P8-06, P8-08, P8-16, `deploy/compose.yaml`).

## Risks and honest limits
- The stopwatch measures one person on one machine; a faster second visit is not a cold start; the procedure says so and asks for the first trial after a hard reload.
- On about 2.1 years of data the honest answer is likely "nothing has enough evidence yet"; the check treats that as an answer. The exit therefore proves the machinery and its honesty, not that a winning cell exists.
- Fixture timings say little about the owner's database; the real run is reported, not asserted.
- Evidence files are plain files the owner or an agent could edit; they are labelled "recorded", never "verified", and tied to a commit.
- The server check cannot see that a screen renders a state correctly; it checks the data the screen is given.
- This slice needs the owner's minutes (stopwatch, the P8-16 walkthrough); until then the verdict is NOT EVALUABLE, correctly.
