## Goal
The owner's stored simulated trades become readable as reports through HTTP: the runs a report may use, KPIs, groups by any lens, a two-dimension pivot, "what works", equity and drawdown series, the R distribution, auto-insights and a paged trade list, all computed on the server by the P8-05 engine, each response carrying its evidence block and the six honest states. The browser computes no statistic.

## Scope
**In:** a 0.5-day spike (acceptance item 1); the reader port `IReportTradeSource` and its Infrastructure adapter; the run-label reader; the default run-set builder; an in-process cache of loaded trades per run; pure additions to `Domain/Reporting` (equity series, R histogram); handlers and DTOs; the endpoint module `ReportingEndpoints` (nine GETs); the ADR; contract regeneration.
**Out:** basket buy-and-hold (P8-07); the `plan-vs-actual` read (P8-04); sector/hour dimensions, MAE/MFE grid, exit-comparison list (P8-10); any screen; any write, export or job; a stored pre-aggregation (named follow-up if the p95 is missed); regime and account (typed refusals already in the engine).

## Acceptance criteria
1. **Spike first (0.5 d), before any endpoint is written.** A throwaway program under `backend/spikes/XDrishti.ReportSpike` (not shipped, same build rules, read-only SQL and port reads only, nothing written) reports three facts on the owner's real database, written into the new ADR and `data/p8-06-spike/` (git-ignored), with the decided fallback applied as below:
   - **Fact 1 — are exit and style recoverable per run?** For every stored run: (a) is it a member of a stored comparison (`research.sim_comparisons.member_run_keys` with `member_candidate_ids`)? (b) does the definition text inside `sim_runs.record_json` (`StrategyRecord.DefinitionJson`; also check `record_json` length against the header's `RecordJsonLength`, because reading it for every run must be cheap) name a `style` and exactly one exit per side without overlays? (c) which exit labels does the newest `GET /api/cells` snapshot use, and do labels derived by (a)/(b) spell the same (`FIXED_RR{rr=2}`)?
     - Outcome A (all runs resolve by comparison or definition): labels are read-only derived, `labelSource` = `comparison` | `definition`. No migration.
     - Outcome B (some runs resolve, some do not): the unresolved runs get `exit`/`style` = null, `labelSource` = `not_recorded`; a group by that dimension is `Unavailable` naming the run (engine behaviour); "what works" leaves the dimension out and says so. No migration.
     - Outcome C (the derived spelling differs from the cell snapshot's labels): the reader maps by the spelling the cells use, and the ADR records the mapping; still no migration.
     - Outcome D (no run resolves): ship with the dimension unavailable everywhere and write the follow-up "P8-06b run labels" (insert-only `research.run_labels`, written by a verb) under Findings; do not block the other endpoints.
   - **Fact 2 — are `basket_ids` filled?** `SELECT cardinality(basket_ids), count(*) FROM research.sim_trades GROUP BY 1` joined to the run's `universe_kind`. Outcome A (basket-universe runs hold their basket, list runs hold none, as `RunTrade` documents): stored where present (`basketSource` = `stored`), and for an instrument-list run the reader **reconstructs** the baskets from the basket history as of the run's creation date (`IBasketQueries.MembersAsync(basketId, cutoff, asOf)` for each non-archived manual basket; `basketSource` = `reconstructed`, printed in the limits). Outcome B (list runs hold baskets too): all stored. Outcome C (a run holds none and no basket history reaches back): `basketSource` = `none`; the basket dimension is `Unavailable` for that run. Also report how many instruments sit in two or more baskets among the runs: separate basket runs that share an instrument and a strategy trigger `reports.run_overlap` (TradeOverlap), so item 5 applies.
   - **Fact 3 — size.** Row counts and `pg_total_relation_size('research.sim_trades')`, the largest run, and the measured time to stream the largest stored run through `IReportTradeSource` (ms per 100,000 rows, process memory before and after). Outcome: total closed trades ≤ `Reports:CacheMaxTrades` (default 1,000,000): in-memory path as specified. Above it: the endpoints answer `422 reports.too_large` until the set is narrowed, and the follow-up "P8-06c stored pre-aggregation" is written under Findings; the p95 target is then restated from the measurement.
2. Given the seeded fixture (Test plan), when `GET /api/reports/runs` is called, then every run is listed with its window, costed flag, universe, labels and label source, engine-verified flag, and the response names the default run set and the runs left out of it with the reason (`older run of the same strategy/universe/style/exit`, `mixed basis`, `experiment candidate`, `overlaps run X`), and `facets.dimensions` lists every dimension with `available` and, for regime and account, the engine's reason text (so a screen prints the server's words beside a disabled filter instead of matching strings).
3. Given the default run set, when any report endpoint is called without `runs`, then the numbers equal `ReportPopulation` built by the test from the same trades (differential test), in every endpoint.
4. Given `runs=A,B` where A and B hold the same strategy, universe, overlapping window and labels, then 409 `reports.run_overlap`; where they share a signal under the same labels, 409 `reports.run_overlap`; where one is costed and one gross, 409 `reports.mixed_basis`; an unknown key, 404 `reports.not_found`. Each message names the runs.
5. Given the default run set would contain two runs that share a signal, then the builder drops the older and lists it in `leftOut` (`overlaps run X (same signals)`); the report never double counts and never fails because of a default it chose itself.
6. Given `basis=net`, then the server fills the confirmation only from the stored owner confirmation (`IChargeSheetConfirmations`); with none it answers 422 `reports.net_not_confirmed`, with no net R in the runs 422 `reports.net_unavailable`; a gross request over costed runs uses the filled-price R. The evidence prints what was confirmed as text. No request, query, command, body or DTO type carries a `ChargeSheetConfirmation` or a flag named for one (`ReportingArchitectureTests` stays green).
7. Given an unknown or malformed parameter (unknown dimension, metric or basis, `from` after `to`, more than 50 runs, a pivot of the same dimension twice, more than 2,000 pivot cells), then 422 `reports.invalid` with the field named. Regime or account as a dimension: 422 `reports.dimension_unavailable` with the engine's reason.
8. Given a group with fewer trades than the minimum (30; insights 15), then every figure of it is `insufficient` and carries no number; given a label no run recorded, `unavailable` naming the run; the response carries `minTrades` and `insightMinTrades` so a client can print "n 12 of at least 30".
9. `GET /api/reports/what-works` returns the engine's answer including `NothingQualifies` with the counts, as 200, never as an error.
10. `GET /api/reports/equity` returns, per group (at most 12, by trade count descending, the rest counted in `omittedGroups`), one point per exit date with `dayR`, `cumulativeR`, `drawdownR` in the engine's exit order; `GET /api/reports/distribution` returns 0.5 R bins from -5 R to +5 R plus a tail below and a tail at or above, counts only. Both are pure additions to `Domain/Reporting` with hand tables.
11. Given `GET /api/reports/trades`, then a page of at most 200 trades (default 50) in order exit date descending, run key, trade key, by an opaque cursor; filtering and paging read the cached trades in one pass with a bounded selection (no full sort); `total` is the filtered count.
12. Given the same stored runs and the same query, then the response bytes are identical (determinism), and the order of the `runs` parameter changes nothing.
13. Every response has an `evidence` block (item "Contract"); a test per endpoint fails if a success response lacks it.
13a. Given a stored run whose `created_by` is `experiment:<jobId>`, then it is never in the default run set, appears in `runs` with `isExperimentCandidate` true and in `leftOut` with reason `experiment candidate`, and an explicit `runs=` naming it is accepted and flagged in the evidence `filters`/limits (test in this slice; P8-18 adds its own).
14. A second request over the same runs reads no trade from the database (cache hit, log event), and a damaged stored trade (`StoreReadException`) answers 500 `reports.read_failed` without content.
15. The contract is regenerated (`scripts/gen-api.sh`), every DTO is in `ApiJsonContext`, `Architecture.Tests` are unchanged and green, `LogEventIdTests` green.

## Non-functional
- p95 under 1 s on the seeded fixture; on a synthetic 500,000-trade run the warm path (cache hit) p95 is measured and written in the ADR (target UNVERIFIED: 1 s; cold read is reported separately in ms per 100,000 rows). A miss is a recorded finding, not a silent pass.
- Memory: about 140 bytes per cached trade (estimate, measured in the spike); the cache refuses to exceed `CacheMaxTrades`.
- Security: session only; read only; no run text beyond keys and labels leaves the server; strategy names and symbols are rendered as text by clients. `[LoggerMessage]` events (next free block at build time; highest used today 4791; `LogEventIdTests`): `report.read` (kind, runs, trades, ms, cacheHit), `report.refused` (code), `report.default_set` (runs, leftOut). Never content, never a free-text parameter.

## Test plan
- **Unit (Domain):** equity series and drawdown by hand: exits R: +2, -1, -1, +2 on dates d1, d2, d2 (run keys a < b), d3 → points (d1: day +2, cum +2, dd 0), (d2: day -2, cum 0, dd -2), (d3: day +2, cum +2, dd 0). Histogram by hand: R = -1.0, -0.7, -0.2, 0.0, 0.3, 0.5, 1.9, 2.0, 6.0, -7.0 → bins [-1.0,-0.5) 2, [-0.5,0.0) 1, [0.0,0.5) 2, [0.5,1.0) 1, [1.5,2.0) 1, [2.0,2.5) 1, above 1, below 1 (total 10). Properties: counts sum to n; order of input changes nothing.
- **Unit (Application):** parser (every whitelist, every 422); default run-set builder (newest per strategy/universe/style/exit; mixed basis kept to the majority kind, ties gross; the older of two overlapping runs dropped with its reason; deterministic); label derivation per outcome A to D with fakes; basket reconstruction with a fake `IBasketQueries`.
- **Integration (Testcontainers, seeded through `IRunStore.StoreAsync`):** run A (strategy ORB, basket B1, gross, exit `FIXED_RR{rr=2}`, intraday): 40 trades, 24 at +2.0 R and 16 at -1.0 R → n 40, win rate 0.60, expectancy +0.80 R, total +32.0 R, profit factor 48/16 = 3.00. Run B (ORB, basket B2) repeating 5 of A's signals → 409 `reports.run_overlap`. Run C (VWAP, B2): 12 trades, 5 at +1.5 and 7 at -1.0 → expectancy 0.5/12 = +0.0417 R, n 12 so every figure `insufficient` while `trades` is 12. Run D: an instrument-list run over I1..I6 with baskets B1 = {I1,I2,I3}, B2 = {I3,I4}, B3 = {I5} at its creation date, one trade each → by basket n 3, 2, 1, sum 6 + 1 (I3 twice) = 7, `nonAdditive` true, `basketSource` reconstructed. Net request over gross runs → 422 `reports.net_unavailable`. 401 without a session. Cache hit logged on the second call. Contract snapshot.
- **Differential:** each endpoint's numbers equal an in-memory `ReportPopulation` on the same trades. **Determinism:** two calls, byte-equal; `runs` order changed, byte-equal.
- **Architecture:** `Domain/Reporting` stays pure; only Infrastructure implements the reader; no request type carries a charge-sheet confirmation; no order-named member.
- **Performance (explicit, `[Fact(Explicit = true)]`):** 500,000 synthetic trades cold and warm, written to the ADR.

## Decisions (researched)
1. **Where do exit and style come from?** Question: they are not trade columns (P8-00 D5). Chosen: read-only derivation in the order stored comparison membership (exact candidate id per run) > the strategy definition inside `record_json` (style; the single exit candidate when no overlay) > not recorded. Reason: the comparison header already stores `member_run_keys` with `member_candidate_ids`, and the run key hashes the definition text, so both are facts of the stored records, not guesses. Rejected: a new labels table now (a write path and a migration for something that may already be recoverable); asking the owner to label runs by hand. Source: `SimComparisonRow`, `StrategyRecord`, `CellSourceReader` (labels supplied by the verb), ADR 0045, 0064. Verified by acceptance item 1 before relying on it.
2. **Default run set.** Chosen: runs whose `created_by` starts with `experiment:` (candidate runs stored by P8-18, which differ from their baseline by one stressed knob) are excluded from the default, listed in `leftOut` as `experiment candidate` and offered in the picker labelled "experiment candidate" (`IsExperimentCandidate`, set from the prefix; an explicit `runs=` may include one and the evidence says so); otherwise a stressed run would silently become the default Reports view (requirement from P8-18 D5). Of the remaining runs: newest run per (strategy, universe, style, exit); if costed and gross runs both remain, keep the kind with more runs (ties gross); then drop the older of any pair the engine refuses for shared signals; every dropped run is listed with its reason. Reason: P8-00 D2 asks for a visible default and the engine refuses double counting; a default that fails is useless on the first screen. Rejected: failing on conflict (first screen error); silently merging (double count). Source: `ReportPopulation.Create`, P8-00 D2, Q11.
3. **Universe key for the overlap rule.** `basket:{id}` for a basket run, `list:{sha256 of the sorted member ids}` for a list run, the members read from `record_json` once per run (cached forever, runs are insert-only). Reason: `UniverseLabel` ("members as of today") is not unique. The shared-signal refusal backstops a wrong key. Source: `UniverseRecord`, `UniverseLabels`.
4. **Basket attribution of a list run** is reconstructed from the basket history at the run's creation date and said so (`basketSource`), because P8-00 Q13 wants "as of the run" and `BasketMember.WasMemberAt` can give it; "current membership" stays a later switch. Rejected: attributing by today's membership (look-ahead without saying so). Source: `IBasketQueries.MembersAsync`, doc 06 §4, ISS-22.
5. **Caching loaded trades per run key**, unbounded by time, bounded by count. Reason: ADR 0045 makes runs insert-only, so a cache entry never goes stale; it turns a second click into milliseconds. Rejected: a stored pre-aggregation now (a write path and a design change, kept as P8-06c if item 1 fact 3 demands it); querying SQL per request (500,000 wide rows each click).
6. **Filtering in memory, not SQL.** One path for every endpoint and the cache; style and exit are run labels that SQL cannot filter anyway. Rejected: SQL filters for the column dimensions (two code paths that must agree).
7. **Net basis.** The request may say `basis=net`; the confirmation comes from `IChargeSheetConfirmations`, which reads the stored sheet (`ICostSheetStore`, `CostSheet.Checked` non-null = the owner wrote what it was checked against; date from the stored row's update time, UNVERIFIED how the settings row exposes it: the first step reads it and, if absent, uses the sheet's first effective date and says so). On the owner's data today no costed run exists (ISS-25), so net answers 422. Source: ADR 0044, P8-05 assumption 6, Q19.
8. **Series and histograms are server work** (equity, drawdown, bins): the browser would otherwise compute statistics (P8-00 "The browser computes no statistic"). Points are per exit date, not per trade, so a series has at most about 520 points on 2.1 years.
9. **`what-works` is an endpoint of its own.** P8-00's endpoint list omitted it although the exit criterion is that view (finding for the index).
10. **Questions Q10, Q11, Q13, Q19** are taken as recommended (P8-00); Q12 (no composite score) is enforced by the architecture test already in place.

## Risks and honest limits
- On the owner's data most groups are `insufficient`; the endpoints say so and never fill a number.
- Labels may be missing for runs made outside a comparison; the exit lens is then unavailable for them (outcome B/D).
- Separate basket runs sharing instruments cannot all be in one default set (item 5); the right way to ask "which basket" is one run over the whole tracked list with reconstructed membership (limits line).
- Basket reconstruction depends on basket history completeness; a basket created after the run has no history before it.
- Memory and p95 figures are estimates until the spike; the 500,000-trade run is synthetic.
- All numbers are in-sample on replayed history with modelled fills, gross unless the sheet is confirmed (the engine's limits text, unchanged).
