## Goal
A finished `SimulationRun` can be turned, by pure code, into the bytes of `trades.csv`, `open_at_end.csv`, `run.json` and `README.txt`, with a `manifest.json` that lets a reader check them, and a host class can put them into `data/exports/sim/<run-id>/` atomically, with owner-only permissions, a path guard and a safe overwrite policy. `run.json`, `README.txt` and the console banner (b2) carry the labels that say what a P3 number means; no file prints a performance statistic. The same record gives identical bytes. Nothing here reads a database or runs a verb: that is b2.

**E1 — Where the code lives, and why.**
| Piece | Project | Rule |
|-------|---------|------|
| `ExportSpellings`, `TradesCsv`, `SimExportJson`, `ExportManifest`, `ExportKey`, `RunId`, `RunBanner`, `RunReadme` | new `XDrishti.SimExport` (Domain only; namespaces `Csv`, `Json`, `Manifest`, `Text`) | pure: bytes to an `IBufferWriter<byte>` or a string out; no `System.IO`, `Console`, `Environment`, network, clock, `Random`, `Guid.NewGuid`; sealed; one public type per file; referenced by `XDrishti.Api` and the tests only |
| `RunLabels`, `RunLabelSet`, `TickUnitCheck`, `TickProbe` | `XDrishti.Domain.Research` | plain values and pure functions; the exact-list test of the public types gains them |
| `ExportFolderWriter`, `HashingFileSink` | `XDrishti.Api/Simulate` (internal) | the file system for the export; no decisions beyond the overwrite policy of E7 |
A library that takes an `IBufferWriter<byte>` (from `System.Buffers`, not `System.IO`) lets the host stream to a file and hash as it writes, so memory stays flat for files of tens of megabytes (E4); a library that returned `byte[]` or `string` would hold a copy of up to 140 MB. The writer is in the host and not in a handler because ADR 0039 forbids Application from referencing `XDrishti.SimExport`; this is recorded in ADR 0040 (b2) as a deliberate exception on the `OwnerBootstrap` precedent, with its consequence: the Lab of P5 will call the same library and re-order the pipeline itself. A new `src` project needs a `COPY` line in the `Dockerfile` and an entry in `XDrishti.slnx` (`backend/CLAUDE.md`). `LayerDependencyTests` has no rule that rejects a new Domain-only project, so AC 13 adds one for `XDrishti.SimExport` and one that only `XDrishti.Api` references it. The alternative of `internal` renderers in `XDrishti.Api` is rejected: presentation code in a host the rules call thin, and its unit tests inside the Testcontainers project.

**E2 — One spelling table, and the number format.**
- `ExportSpellings` holds exhaustive switches (an unknown member throws `ArgumentOutOfRangeException`, never a default string) for `Side` (`BUY`/`SELL`), `ExitReason` (`stop|target|square_off|end_of_data`), `FillBasis` (`modelled|no_slippage`, the export's spelling of `Modelled|Exact`), `CostBasis` (`none`), `EntryFill` (`at_open|at_limit`), `Timeframe` (its code), `SkipReason` (`SkipReasons.ToCode`), and snake_case for the other enums of the record. **Both the CSV and the JSON writers use it.** A reflection test enumerates every member of these enums with `Enum.GetValues` and every enum reachable from the types of the record (found by reflection over the `SimulationRun` type graph: among them `CorporateActionKind` in `Domain.Market.Actions`, `NoTradeReason`, `UniverseKind`, `SessionExclusion`), and fails on a member with no spelling or two members with one spelling, so that a member added by P3-03c or P3-03d (`ExitReason.MaxHold`, a cost basis) fails a test instead of being written as a default.
- **Numbers.** `SimTrade` holds `double`s: every double is written with `CanonicalText.Number` (round-trip form, invariant culture, `-0` as `0`), in the CSV and, through a converter that writes the same text with `Utf8JsonWriter.WriteRawValue`, in the JSON; **decimals** (`TickSize`, an adjustment's factor) with `CanonicalText.Number(decimal)` (fewest digits: `0.05`, never `0.0500`). **A NaN or infinity throws `ArgumentException`** in both writers (`CanonicalText.Number` would write `NaN`). Whole numbers are plain integers; booleans `true`/`false`; dates `yyyy-MM-dd`; `*_ist` is `yyyy-MM-dd HH:mm` India time derived from the epoch, never from the machine's zone. No file depends on the culture or the time zone of the machine.

**E3 — `trades.csv` and `open_at_end.csv`.** `TradesCsv.Write(IBufferWriter<byte> sink, IReadOnlyList<RunTrade> trades)`: the same columns in both files; `trades.csv` is `run.Trades`, `open_at_end.csv` is `run.OpenAtEnd` (apart on purpose, as in the record, so a sum over a file cannot count a position the data cut short); both are always written (a header and no rows when empty). One row per `RunTrade` in the record's order (entry instant, place in the universe, Buy before Sell).
- **Columns** (`snake_case`, in this order): `run_key` (the full 64 hex, which the P3-09 check log needs), `schema_version`, `strategy_id`, `instrument_id`, `symbol`, `side`, `trade_date`, `decision_epoch`, `decision_ist`, `trigger_timeframe`, `trigger_bar_epoch`, `trigger_bar_open`, `trigger_bar_high`, `trigger_bar_low`, `trigger_bar_close`, `trigger_bar_volume`, `trigger_bar_minutes`, `trigger_bar_complete`, `entry_epoch`, `entry_ist`, `entry_price`, `stop_price`, `target_price` (empty when null), `exit_epoch`, `exit_ist`, `exit_price`, `exit_reason`, `r_exact`, `mae_r`, `mfe_r`, `fills`, `costs`, `r_filled`, `slippage_r`, `entry_filled_price`, `exit_filled_price`, `entry_fill`, `tick_fallback`, `basket_ids` (GUIDs joined by `;`), `key` (`SimTrade.Key`). `EntrySnapshotJson` is not a column (reserved, always null); a reflection test requires every other positional property of `SimTrade` to be a column, so the schema 3 and 4 that P3-03d and P3-03c are expected to bring fail it until the CSV is revised on purpose (the exporter format is then raised). The `run_key` is the one the writer is given.
- **Format.** UTF-8 without a byte order mark, `\n`, a final newline, RFC 4180 quoting (a cell with a comma, a quote, CR or LF is quoted, quotes doubled).
- **Text cells** (`symbol`, `strategy_id`, `basket_ids`, `key`, any future text column) are handled in this order: strip every character of Unicode category **Control** (a NUL, tab, CR or LF inside a cell is dropped) or **Format** (U+202E and the other bidi controls, zero-width characters); then, **if the first character of the original text or of the stripped text is `=`, `+`, `-`, `@`, TAB, CR or LF, the cell gains a leading `'`**. The two tests together close the bypasses that a single test leaves (a zero-width character or a NUL or a line feed in front of `=1+1`). **Numeric cells are not text cells:** they are written by the number formatter of E2, never as free text, so a negative R such as `-1.5` is not prefixed.

**E4 — `run.json`.**
- **Envelope:** `{ "export": { "format": <string given by the caller>, "schema": 1 }, "labels": <RunLabelSet, E5>, "run": <SimulationRun> }`. `SimExportJson.Write(IBufferWriter<byte> sink, SimulationRun run, RunLabelSet labels, string format)`. `run` is the full record (schema 2): run key, engine version, the strategy record (parameters, `definition_json` as the hashed string, its SHA-256, timeframe, sides), window, options, acknowledgement, the fills text, the universe and its members, the calendar exceptions, **every `InstrumentRun`** (skip reason and detail, data facts, bars read, fed, excluded and outside, the bar-stream SHA-256, the tick and its fallback flag, the adjustments, session counts, notes, discontinuities, scan counters per side with the per-condition counts, walk counters, fates, candidates and trades in the window), `trades`, `open_at_end` and `totals`.
- **Serialiser:** `System.Text.Json` source generation (`SimExportJson` holds a `JsonSerializerContext`; not an engine namespace, so the engine rule against `System.Text.Json` does not apply), through a `Utf8JsonWriter` over the sink. `snake_case` names, declaration order, **compact** (no indentation: a tool such as `jq` reads it; the file is for machines and the cards and the CSV are for eyes), `\n` nowhere inside. Spellings from `ExportSpellings`; `DateOnly` as `yyyy-MM-dd`; GUIDs in `D` form; **dictionaries** (`StrategyRecord.Parameters`) written with ordinal sorted keys through a converter (a reflection test fails on any other dictionary-typed property of the record, so a new one cannot be serialised unsorted). The file holds no clock time, no machine path and no culture-dependent text.
- **Size (an estimate, UNVERIFIED).** ADR 0037 Amendment 3 counted 11,749 trades for 20 invented instruments, which scales to about 126,000 for 214; an upper bound is one trade per instrument, side and session, about 214 × 507 × 2 = 217,000. One trade is about 650 bytes of compact JSON and about 400 bytes of CSV: `run.json` about 80 to 140 MB and `trades.csv` about 50 to 90 MB at the bound, far less for a selective rule (a real ORB count is UNVERIFIED). Hence the streaming sink (E1), the compact JSON, and these consequences: writing and re-hashing a full export takes seconds (the `unchanged` check hashes every file, E7), `--force` keeps one previous copy (E7), and the explicit benchmark `Export_phases_for_seeded_universe` (the 20 invented instruments of P3-04a's benchmark) prints the bytes of every file and the peak memory so the estimate is replaced by a figure.
- **Labels in the file:** `labels` is `{ "lines": [<string>…], "not_modelled": [ { "code": …, "text": … }… ], "engine_verified": false }`; its text is pinned by a golden test.

**E5 — The labels, the banner and the readme (what a P3 number means).**
- `RunLabels.Of(SimulationRun run, FillRules rules)` returns a **`RunLabelSet(IReadOnlyList<string> Lines, IReadOnlyList<FillLimit> NotModelled)`** (Domain; it throws unless `rules.ToCanonicalJson() == run.Fills`, so a label cannot say a thing the run did not do). `Lines`, in this order: **(1)** `exploration: signal-level mechanics on past data, not evidence of an edge`; **(2) to (6)** the five labels of `SimulationHeader`: `fills: modelled` or, when the slippage is `None`, `fills: modelled, no slippage, no tick rounding of fills` (`FillBasis.Exact` is documented as no slippage **and** no tick rounding of a fill, so the label says both; the engine's own header keeps `fills: exact` and its tests are untouched), `entry limit: +0.1 %`, `costs: none`, `portfolio limits: not simulated`, `sample: in-sample` (the fixed three move from `SimulationHeader.FixedLabels` to `RunLabels`; the header delegates, so `SimulatorRunTests` and `FillLimitsAndLabelsTests`, which pin the labels, stay unchanged and green); **(7)** `universe: members as of today` or `universe: instruments as listed`, each followed by `; survivorship is bounded and disclosed, not avoided (ISS-22)`; **(8)** the data line from the instruments that ran: `data: <n> instruments; first bars <min first> to <max first>, last bars <min last> to <max last>; length from about <shortest> to about <longest> years (days / 365.25, one decimal); no hold-out (ISS-19)`, or `data: none` when nothing ran (the owner's files start between 2024-04-01 and 2024-12-18, so one range would overstate the shortest; per-instrument ranges are in `run.json`); **(9)** `engine: not yet verified (P3-08)` (the constant `RunLabels.EngineVerification`; P3-08 changes it with its ADR); **(10)** `tick: today's master tick; rounding to the grid is approximate`; **(11)** `opening bar: the stored 09:15 bar can be widened by the CSV importer and the first 1-minute open is not the auction open (ISS-21, ISS-18)`. `NotModelled` is `FillLimits.NotModelled` as it is. `costs: none` is constant while `CostBasis` has one member; P3-03c's draft makes it `CostDescription.Label(run.Costs)` and adds the sizing label and `CostLimits`, which changes this function and its golden.
- **`RunBanner`** gives the text in the two parts a renderer needs: `RunBanner.Visible(labels)` (the `Lines`, one per line) and `RunBanner.Limits(labels)` (`not modelled: <code>: <text>`, one per line), and `RunBanner.Text(labels)` (both, for the console and the readme). P3-04c wraps `Visible` in always-shown HTML and `Limits` in a `<details>`; nothing in it is HTML.
- **`RunReadme.Text(labels, runId)`** is `README.txt`: the banner, then a paragraph saying what the folder is (the output of the `simulate` verb; `trades.csv` and `open_at_end.csv` hold the trades, `run.json` the full record, `manifest.json` the hashes; nothing in it is evidence of an edge) and that the CSV must not be passed on without this notice. A CSV is what gets opened in a spreadsheet and sent on, and carries no label itself, so the sidecar sits in the same folder and is hashed in the manifest. No time, no path.
- **One text edit in the Domain:** the text of `touch_is_fill` in `FillLimits` quotes "about 0.1 R off every winner", a figure nothing in the repo measured. It is reworded without a number and without the word *winner*; a test requires that no limit text contains a digit followed by ` R` or a word of the forbidden list of AC 6 below (whole-word, case-insensitive: the only hit today, checked in the repo, is `winner` in this text).

**E6 — The manifest, the export key, the run id: extension points for P3-04c.**
- **Entries.** A *file entry* is `ManifestEntry(string Name, long Bytes, string Sha256)`. A name is relative with at most one `/` (segments from `[A-Za-z0-9._&-]`, not `..`), which allows `cards/0001-….html` later. The library does not know which files exist: it works over a list of entries plus a list of *extra lines* (ordered strings), so P3-04c adds entries (`index.html`, the cards) and extra lines (`cards.cap=200`, `cards.selected=<trade key>|<stratum>`) **without modifying** any type here.
- `ExportKey.Of(string format, string runKey, Guid? basketId, IReadOnlyList<ManifestEntry> entries, IReadOnlyList<string> extraLines)` is the lower-case hex SHA-256 of the UTF-8 lines `format=<format>`, `run_key=<key>`, `basket=<guid D or ->`, then `file=<name>|<sha256>` for each entry in ordinal name order, then `extra=<line>` for each extra line in the given order, each ending in `\n`. The key covers the basket id because **`RunAssembler.KeyText` does not** (it has the universe label and the instrument ids only, checked in the repo): two baskets with the same members and label have one run key and one folder name.
- `ExportManifest.Build(format, runKey, basketId, entries, extraLines)` returns the bytes of `manifest.json`: `{ "format", "run_key", "basket_id" (or null), "export_key", "files": [ { "name", "bytes", "sha256" }… ], "extra": [ "<line>"… ] }`, files in ordinal name order, compact, no time. **A manifest lists the other files, not itself:** in this slice it lists four, `README.txt`, `open_at_end.csv`, `run.json` and `trades.csv`. `ExportManifest.Parse(ReadOnlySpan<byte>)` returns a `Result` of the parsed manifest (format, run key, basket id, export key, entries, extra lines) or a code (`manifest.malformed`, `manifest.names_invalid`); the `unchanged` check of E7 needs it. The `format` is a **string given by the caller** (`xd-sim-export-1` here; P3-04c passes `-2`): no assembly version is ever written, so a golden does not break on every build.
- `RunId.Of(string strategyId, DateOnly from, DateOnly to, string runKey)` is `<strategy id lower-case with each '_' written '-'>-<from yyyyMMdd>-<to yyyyMMdd>-<first 12 hex of the run key>` (for example `vwap-pullback-20240401-20260430-3fa91c2d07be`; ids such as `VWAP_PULLBACK` and `BASE_BREAKOUT` contain `_`); a character outside `[A-Za-z0-9_]` in the id throws, and the result is at most 80 characters over `[a-z0-9-]`.

**E7 — The folder writer.** `ExportFolderWriter.WriteAsync(root, runId, files, buildManifest, force, ct)` with `files` a list of `(Name, Action<IBufferWriter<byte>> Render)`, `buildManifest` a function from the entries it produced to `(manifest bytes, export key)`, and a result of `Written`, `Unchanged`, `ReplacedPrevious` or a refusal.
- **Layout:** `<root>/sim/<run-id>/` holding `manifest.json` and the files given. Each file is rendered by the library into a `HashingFileSink` (an `IBufferWriter<byte>` over a `FileStream` that updates an `IncrementalHash` SHA-256 and counts bytes as it flushes), so the entry's hash is known without reading the file back.
- **Atomic writes.** Everything is written into a staging folder `<root>/sim/.staging-<run-id>-<random>`, `manifest.json` last, flushed to disk, then the folder is renamed to `<run-id>` in one `Directory.Move` (same file system). An error or a cancelled run before the rename removes the staging folder it made (the one folder the writer ever deletes, with its own files). A killed process leaves its `.staging-*` folder; the writer counts the leftovers and returns the count and names for a notice and **never removes them** (the owner does).
- **Overwrite policy.** If `<run-id>` does not exist, rename the staging folder into place. If it exists: *unchanged* means that its `manifest.json` parses, its export key equals the new one, the directory holds **exactly** `manifest.json` and the listed files (no extra, no missing), and every listed file hashes to its recorded value (the writer hashes the files on disk); then the staging folder is removed and the result is `Unchanged` (with or without `force`: nothing is renamed). Anything else (another basket, another fills mode, a hand-edited or extra or missing file, an unreadable manifest) is a refusal without `force`. With `force` and a valid manifest in the existing folder: the existing folder is renamed to `<run-id>.previous`, then the staging folder to `<run-id>`; if `<run-id>.previous` already exists the result is a refusal telling the owner to remove it by hand (**one previous copy per run id**, so the retention is bounded at one extra copy of up to a few hundred megabytes and nothing is deleted on the owner's behalf). If the second rename fails, `<run-id>.previous` is renamed back to `<run-id>` and the failure is raised; if that also fails, the exception names both folders. The two renames are not atomic together; a crash between them leaves no `<run-id>` and a complete `.previous` (acceptable). A folder with no valid manifest is never replaced, even with `force`. The writer deletes nothing but its own staging folder.
- **Path guard.** `root` must be absolute and its parent must exist; the writer creates `<root>` (if missing), `<root>/sim` and the run folders, never a deeper unknown path. Every path is built from fixed names plus the sanitised run id and entry names, resolved with `Path.GetFullPath`, and must start with `<root>/sim/` (ordinal); a name cannot contain `..`, a backslash, `:` or a control or Format character; `sim`, the run folder and the staging folder must not be symbolic links (`FileSystemInfo.LinkTarget` null). Files are opened with `FileMode.CreateNew`.
- **Permissions at creation, with no umask window:** directories the writer creates with `Directory.CreateDirectory(path, UnixFileMode.UserRead | UserWrite | UserExecute)` (0700), files with `FileStreamOptions { Mode = CreateNew, Access = Write, UnixCreateMode = UserRead | UserWrite }` (0600); an existing directory is not changed.
- `data/` is git-ignored (`data/**` except the README and `inbox/`); `data/exports/` is created by the writer. Nothing in the system reads an export back.

**E8 — `TickUnitCheck` (Domain, pure).** `TickProbe(Guid Id, string Symbol, InstrumentType Type, decimal? StoredTick)` and `TickUnitCheck.Suspect(IEnumerable<TickProbe>)` list the **`Share` and `Etf`** instruments whose converted tick (`TickSpec.FromMasterPaise`) is positive and **below 0.01 rupee**. The finest tick of an NSE equity is one paisa; a table holding rupees (`0.05`) converts to `0.0005`, which passes `TickSpec`'s own range (0, 1] and would be a silent factor of 100 on every limit and slipped fill. A null tick (the flagged fallback) and a tick above one rupee (skipped later as `tick_size_invalid`) are not suspects. `Index`, `Future` and any other type are never suspects (the committed fixture `backend/tests/XDrishti.Application.Tests/Fixtures/dhan-master-sample.csv` has INDEX rows at `0.0500` and FUTCUR/OPTCUR rows at `0.2500`, which convert to 0.0005 and 0.0025 rupee and are legitimate). **The threshold 0.01 is a decision with a reason:** the smallest tick the NSE has for a share; it is a net for the unit mistake, not the guard (the guard is the one-time read of b2). The mapping of the strings of `InstrumentSummary.Type` and `InstrumentDetail.Type` to `InstrumentType` is b2's (`InstrumentTypeCodes.TryParse`; an unknown code is not gated and is noted).

**E9 — The golden-file helper is parameterised.** `XDrishti.Simulation.Tests/Support/GoldenFile.cs` hard-codes `SimulationEngine.Version` (so it needs `XDrishti.Simulation`) and finds its folder by walking up to `XDrishti.Simulation.Tests.csproj`; `backend/tests/Shared` is linked into projects that do not reference the engine. ## Acceptance criteria
Numbered, each testable. Fixture series are invented (P3-03's F-days; fabricated records for the pure tests); nothing is read from `data/`. Tests: `XDrishti.SimExport.Tests` (new, pure), `XDrishti.Domain.Tests`, `XDrishti.Architecture.Tests`, and `XDrishti.Api.IntegrationTests` for the writer (plain temp-directory tests outside the Testcontainers collection; the project has `InternalsVisibleTo` for the Api).
1. **Spellings.** A reflection test finds every enum reachable from the `SimulationRun` type graph, includes `CorporateActionKind`, `Side`, `ExitReason`, `FillBasis`, `CostBasis`, `EntryFill`, `Timeframe`, `SkipReason`, `NoTradeReason`, `UniverseKind`, `SessionExclusion`, and for each member requires one spelling, unique within its enum, used by both the CSV and the JSON writers; a hand-made enum value with no spelling throws `ArgumentOutOfRangeException` from both writers; `FillBasis` is written `modelled` or `no_slippage`.
2. **`trades.csv` format.** Given three golden trades (a BUY at the target, a SELL at the stop with slippage, an `EndOfData` trade that goes to the other file) then the header is the column list of E3 in order, the rows equal a golden file byte for byte (UTF-8, no byte order mark, `\n`, final newline), every number is the round-trip form and parses back to the same double, `run_key` is 64 hex, the times are India time under a non-India zone and under `de-DE`/`tr-TR`, a null target is an empty cell, the two files hold exactly `run.Trades` and `run.OpenAtEnd` (header only when empty), a reflection test shows every positional property of `SimTrade` except `EntrySnapshotJson` is a column, `-0` is written `0`, and a trade with a NaN or infinite price makes the writer throw `ArgumentException`.
3. **CSV safety.** Given text cells `=1+1`, `+SUM(A1)`, `-2+3`, `@cmd`, `\tx`, `\rx`, `\n=1`, `a,b`, `say "hi"`, a line break inside, an empty string, a non-ASCII symbol, and the four bypass inputs U+200B + `=1+1`, NUL + `@x`, LF + `=1`, U+202E + `@cmd` then each cell whose original or stripped first character is `= + - @ TAB CR LF` gains a leading `'` (the four bypasses give `'=1+1`, `'@x`, `'=1`, `'@cmd`), Control and Format characters are absent from the output (the cell with U+202E equals the same text without it), the others that need it are quoted as RFC 4180 says, a numeric cell `-1.5` and `-0.05` is **not** prefixed, and a small independent RFC 4180 reader written in the test project parses the file back to the expected cells (no new package).
4. **`run.json`.** Given the record of the F1/F2 run with a skipped instrument, a flagged day, an adjustment, session notes and both sides' counters then the text equals a golden file (compact; `export`, `labels`, `run` in that order); it parses back with `System.Text.Json` and the run key, every trade, every `InstrumentRun` and the totals equal the record's; `StrategyRecord.Parameters` is written with ordinal sorted keys and a reflection test fails on any other dictionary-typed property; decimals are written in the fewest digits; a NaN or infinite double throws; the file holds no clock time, no machine path and no culture-dependent text (identical under two cultures and two zones); the `labels` object has the shape of E4 and equals a golden.
5. **Labels, banner, readme.** Given `RunLabels.Of(run, rules)` for the default fills, for `no-slippage`, a basket run, a list run, a run in which nothing ran, and a run whose instruments start on 2024-04-01 and 2024-12-18 and end 2026-04-30 then `Lines` are produced in the order of E5 and equal a golden text; the data line shows the earliest and latest first bars and the shortest and longest length (`about 1.4 to about 2.1 years` for the last case) and `data: none` when nothing ran; `Lines[1..5]` equal `SimulationHeader.LabelsOf(rules)` except that, for `no-slippage`, the first reads `fills: modelled, no slippage, no tick rounding of fills` where the header says `fills: exact`; `NotModelled` is `FillLimits.NotModelled`; passing rules that do not match `run.Fills` throws; `RunBanner.Visible` and `RunBanner.Limits` concatenate to `RunBanner.Text`, contain no HTML character other than those of the texts, and `README.txt` equals a golden.
6. **The limit text.** No text of `FillLimits.NotModelled` is empty, contains a digit followed by ` R`, or contains a word of this list (whole-word, case-insensitive): `win`, `wins`, `winner`, `winners`, `winning`, `loss`, `losses`, `loser`, `losers`, `losing`, `hit`, `hits`, `expectancy`, `profit`, `profits`, `profitable`, `drawdown`, `average`, `mean`, `sum`, `total`, `percent`, `percentage`, `rate`, `ratio`. The same scan, over the banner text of every case of AC 5, finds nothing. `SimulatorRunTests` and `FillLimitsAndLabelsTests` stay green unchanged (they pin the header labels and the limit codes).
7. **The tick check.** Given probes of a share and an ETF with stored ticks 1, 5 and 10 (0.01, 0.05 and 0.10 rupee), a share stored as `0.05` (0.0005 rupee), an index at `0.05`, a future at `0.25`, a null tick, and a share at 150 (1.5 rupees) then only the share stored as `0.05` is suspect and every other probe is not; a share or an ETF stored as `0.5` (0.005 rupee) is suspect too; the result names the stored and converted values.
8. **Manifest and key.** Given entries and extra lines then `ExportManifest.Build` equals a golden, `Parse` of it gives the same format, run key, basket id, export key, entries and extra lines, a malformed text, a name with `..`, a backslash or a second `/`, a duplicate name and a missing member give the codes of E6; `ExportKey.Of` equals the SHA-256 of the lines of E6 (a known answer computed with an independent tool), changes when any one of the format, the run key, the basket id, one file hash, one extra line or the order of the extra lines changes, and does **not** change when the entries are given in another order; **adding a hand-made entry `cards/0001-x.html` and two extra lines needs no change to any type here** (the extension test P3-04c relies on); `RunId.Of` gives the examples of E6 (including `_` written `-`), throws for a character outside the set, and is at most 80 characters.
9. **The folder.** Given fabricated files (the four of this slice) when the writer runs into an empty root then `<root>/sim/<run-id>/` holds exactly `manifest.json` and those four; `<root>`, `sim` and the staging folder (when created by the writer) are `0700` and the files `0600` **at creation** (the creation calls carry the mode; the test also checks the mode of what exists); the manifest lists the four with byte counts and SHA-256 that match the files (hashed independently), the export key equals `ExportKey.Of`; no staging folder is left; the files of two runs into two roots are identical byte for byte.
10. **Overwrite.** Given an existing export then (a) the same input again is `Unchanged` after hashing every file on disk, nothing renamed, with and without `force`; (b) another fills mode, another basket id with the same run key, a hand-edited file, a missing file, an extra file in the folder and an unreadable manifest are each a refusal without `force` (never `Unchanged`); (c) with `force` and a valid manifest the old folder becomes `<run-id>.previous` and the new one is complete; a second `force` while `<run-id>.previous` exists is a refusal that names the folder, and nothing is deleted; (d) when the second rename is made to fail (a hook), `<run-id>.previous` is renamed back and the failure is raised, and when the rename back also fails the exception names both folders; (e) a folder with no valid manifest is not replaced even with `force`; (f) a failure while rendering a file and a token cancelled between two files leave no `<run-id>` folder and remove only the staging folder the writer made; a pre-existing `.staging-*` folder is reported and not removed.
11. **The path guard.** Given a relative root, a root whose parent does not exist, a root whose `sim` folder is a symbolic link, a run folder that is a symbolic link, entry names with `..`, `/`, `\`, `:`, NUL, control and Format characters, very long names and a Windows device name (`CON`), and an existing file where a file is to be created then every one is refused (the first two as a configuration error, the others as a refusal), every built path starts with `<root>/sim/` after `GetFullPath`, a table of at least 15 cases gives the exact built name, and nothing is created outside the root (the test lists the whole temp tree before and after).
12. **Streaming and memory.** The `HashingFileSink` produces the same SHA-256 and byte count as hashing the finished file; rendering a synthetic 200,000-trade record to the sink allocates a bounded amount (well under the size of the output; the figure is printed by the explicit benchmark `Export_phases_for_seeded_universe` together with the bytes of every file), and no `byte[]` or `string` of the whole file is built by the library (the architecture scan finds no `MemoryStream` and no `ToArray` of the output; the writer holds a bounded buffer).
13. **Architecture.** (a) `XDrishti.SimExport` references `XDrishti.Domain` only (project file and compiled references) and uses no `System.IO`, `System.Console`, `System.Environment`, `System.Net`, `System.Diagnostics.Process`, clock, `Random` or `Guid.NewGuid` (an IL scan with a sentinel type that does each); (b) a new rule: nothing in `src/` but `XDrishti.Api` references it, and `XDrishti.Simulation` is still referenced by Infrastructure only; (c) the `Dockerfile` copies the project file of `XDrishti.SimExport` and the solution lists it and its test project; (d) the existing tests that must be edited on purpose are edited and named in the change: `DomainResearchSurfaceTests` (the exact list of public types of `Domain.Research` gains `RunLabels`, `RunLabelSet`, `TickUnitCheck`, `TickProbe`); `SimulationArchitectureTests` (it lists the types of `XDrishti.Simulation.Replay`, lines 165 and 168 of today's file) is edited in **b2** when the registry adds `BuiltInEntry`; `FillLimitsAndLabelsTests` and `SimulatorRunTests` are not edited (AC 6); (e) the rest (`LayerDependencyTests`, `ResearchLayeringArchitectureTests`, the compiler warm-up rule) stay green; each new rule has a sentinel that proves it can fail.
14. **The golden helper.** The shared parameterised `GoldenFile` exists once in `backend/tests/Shared`; `XDrishti.Simulation.Tests` uses a thin wrapper and its five golden files are byte-identical to before; a failing comparison names the header and the update switch.

## Non-functional
- **Performance:** no budget is asserted; the benchmark of E4 prints times and bytes. **Memory:** flat in the size of the files (E1, AC 12); the record itself (up to ~217,000 trades) is in memory as it is after the run.
- **Security and privacy:** files `0600` in `0700` folders under a git-ignored root; nothing leaves the machine; paths built from sanitised parts and guarded (AC 11); CSV hardened against formula and bidi injection (AC 3); no secret enters any file (b2 AC scans them).
- **Determinism and fail closed (NFR-3, NFR-4, NFR-7):** no clock, `Random` or machine fact in a file; the export key covers the basket id and the hashes of the files and the extra lines; a refused overwrite or a failure leaves no partial export.

## Risks
- **The size estimate of the files is a guess** (E4): 126,000 to 217,000 trades is an extrapolation from invented data; the benchmark prints the real bytes; the design (streaming, compact JSON, one `.previous`) holds either way.
- **Merge conflicts with P3-03d and P3-03c** in `FillLimits`, `SimTrade` (the CSV reflection test goes red on purpose), the labels (costs) and the ADR number: see *Merge order*.
- **A label drifts from the truth.** Mitigation: `RunLabels.Of` checks the rules against `run.Fills`; the labels are golden-pinned; the engine-verified flag is one constant.
- **The CSV travels without its notice.** Mitigation: the `README.txt` sidecar in the same folder; a CSV cannot carry a label without breaking its columns.
- **Hashing and re-hashing hundreds of megabytes** on every run and every `unchanged` check: seconds on an SSD; measured by the benchmark.
