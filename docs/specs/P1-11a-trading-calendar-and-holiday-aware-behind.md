# P1-11a — Trading calendar and holiday-aware "behind" detection

- **Status:** Approved (owner, 2026-10-12, quote in [ADR 0017](../adr/0017-trading-calendar-eod-schedule-quality-adjustments-and-csv-undo.md)) · **Phase:** P1 — the calendar part of **P1-11** (the daily context data series — index, VIX, breadth — moved to **P3-01d**, [ADR 0033](../adr/0033-weekly-monthly-timeframes-calendar-features-and-the-market-context.md)) · depends on P1-17a
## Goal
The system knows which dates had a session; "behind", gaps, the schedule and quality all use it.
## Backend
1. Migration: `market.trading_days (date PK, kind holiday|special, session_from, session_to, source manual|observed|nse, status confirmed|proposed, note, updated_at)`; seed nothing. Domain `TradingCalendar` (pure): `IsTradingDay(date)`, `SessionOf(date)` (09:15–15:30 IST, special window when listed), `LastClosedSession(nowIst)`, `TradingDaysBetween(a, b)`, `ExpectedMinutes(date)`.
2. Sources: manual add/remove/confirm (`POST/DELETE /api/data/calendar`, `PUT /api/data/calendar/{date}/confirm`); **observed** proposals computed after every data job (rule in ADR 0017 §1; never auto-confirmed); **NSE** best-effort fetch of the public trading-holiday list (tolerant of failure, warnings only, one attempt per day and on request `POST /api/data/calendar/refresh`; the endpoint must be added to the master-data endpoint allow-list of ADR 0010, tested). Specials observed in the 214 CSV files (2024-11-01 Muhurat; a Saturday session) must appear as proposed `special` days after the first aggregate run.
3. `GET /api/data/calendar?from&to` (days, proposals, next holiday) and use the calendar in: `DataFreshness` / overview `expectedSession`, `daysBehind` (trading days), `status current|behind|empty`, instrument rows, and `ExpectedMinutes` for later slices. Replace the weekday approximation of P1-17a; keep the overview JSON shape (add `nextHoliday`, `calendarProposals` count).
4. Tests: calendar rules (holiday, special, weekend, after close, 15:29 vs 15:30, Muhurat), observed proposals over fixtures, confirm/remove, NSE parse + failure tolerance + allow-list, behind/current across a long weekend, contract regenerated, docs 05 (§4 special sessions) + 04.
## Frontend (Data screen)
A compact **Trading calendar** card or drawer on the Data page: upcoming holidays, **proposed** holidays/special sessions with Confirm / Dismiss, manual "Add holiday / special session" (date, kind, session window, note), "Refresh from NSE"; the freshness strip and coverage statuses read the new fields ("Behind by 2 trading days · expected the 12 Oct session"; a proposal badge when something awaits confirmation). Tests, a11y, ≤ 200 KB initial bundle.
## Decisions taken in the backend build
Details the ADR and this spec leave open; object to any.
- **Status `dismissed`** (third value next to `confirmed|proposed`): `DELETE /api/data/calendar/{date}` is also "Dismiss". The owner's own (manual) entry is deleted; a proposal from the bars or a day from NSE's list is kept as `dismissed` so the next job does not propose it again and NSE's list does not bring it back; deleting a dismissed day removes the row (the undo of a dismissal). Dismissed days are not listed and do not count.
- **Reference for the 5 % rule:** the instruments that have a bar *before and after* the date (their own first and last day around it), not only the neighbouring days — equivalent for isolated holidays and robust for two holidays in a row. No minimum number of instruments: with one instrument a gap is a proposal too (it is only a proposal).
- **Specials:** a weekend date with bars from at least 5 % of the instruments (at least one), or a weekday whose bars lie in the evening window (≥ 17:30), with the window most instruments share (first bar → minute after the last bar). One window per date. Window minutes are read from the 1-minute bars only for the few candidate dates (weekends, weekdays with fewer than 375 bars in the median), newest 200 first.
- **When it runs:** after every data job (any steps), but only when no instrument has changes that are not aggregated yet (the daily rows would be out of date); so after the first aggregate run. Stale observed proposals are withdrawn; `confirmed` and `dismissed` rows are never touched.
- **NSE:** weekday holidays of the `CM` segment are stored **confirmed** (`nse`), because the list is official; a session seen on a listed holiday is proposed *next to* the confirmed holiday, which keeps deciding until the owner confirms the proposal (review fix, 2026-10-12), and the list never overrides the owner's rows or dismissals. One automatic attempt per India date after a data job (in-memory per process, so a restart may try once more that day) and `POST /api/data/calendar/refresh` any time; the request is one plain GET with a browser-like `User-Agent`, no cookies, and a refusal answers 200 `succeeded:false` (a warning on the job).
- **Audit:** `CalendarDayAdded`, `CalendarDayConfirmed`, `CalendarDayRemoved`, `CalendarRefreshedFromNse` in `accounts.account_events` (date, kind, window, source — never the note).
- Application port for later slices: `ITradingCalendar.GetAsync()` → the pure `TradingCalendar`, scoped (one read per request or job), `Invalidate()` after a change.
