# P12-07 — Account execution modes: the ladder, the evidence gates, automatic demotion and the assisted order sheet

- **Status:** Draft (written 2026-10-24; decisions below were researched under the owner's delegation; the owner's Approved is still needed before an agent builds it)
- **Phase / roadmap row:** P12 — Execution service, slice P12-07 of [P12-00](P12-00-execution-service-plan.md) (written in parallel by another agent; referred to by id only)
- **Design refs:** docs/design/20-extended-modules.md §A (modes) · 04-accounts-access-and-operations.md §1 (account modes), §4.1 ("enabling execution" is "Only you") · 16-configuration.md (`autonomy.always_ask`, `execution`, `step_up_for: execution`) · 19-risks-and-compliance.md §4 (automation over-reach), §5 · 09-learning-engine.md §13 · ADR 0091 (an option behind an owner setting, database-checked), 0083, 0095
- **Needs (build order of the group: P12-07, P12-11, P12-08, P12-09, P12-10, P12-12):** P11-04A (`PoolMode`, the live allocation check with `risk_scale` and `ramp_event_id`), P11-01 (journals `manual_live` fills), P12-03 (the `advisory` run kind), P12-01 (the `execution` schema, `settings`, `IModeSource` which this slice implements as `ModeTrailSource`, `ExecSettingRegistry` which must move to `XDrishti.Domain` so `xd-api` can validate keys, the intent state machine that asks `ModeRouting`), P12-02 (sandbox suite result), P12-05 (kill-switch drill record), P12-06 (reconciliation records), P11-06 and P10-06 (phase-check verdicts), P7-12 (the setting rule). The gates read P12-11's records (`day_states`, attestation) and show them `unavailable` until P12-11 is built, so a gate stays closed. Feeds P12-11, P12-08, P12-09, P12-10, P12-12.
- **Size:** 3.5 agent-days (estimate; the allocation relaxation adds half a day). If it runs over, the assisted sheet (criteria 14 to 17) splits off as P12-07b.
- **Safety:** yes. It writes the setting that decides whether the system may ever send an order for an account. Default for every account: `paper` or `manual_live` as today; the global switch `execution_enabled` defaults OFF; the spec being Draft is what holds the build; the owner's Approved is the owner's act.

## Assumptions (taken as researched; the owner's answers, where he has already given them, are binding)
1. **No order is placed by this slice.** It stores which mode an account is in and decides what the next slices may do; the only thing it produces for the broker is text (the assisted sheet) that the owner types into Dhan by hand. Names avoid the words of the no-order tripwire (`NoOrderPlacementArchitectureTests`: place, submit, modify, cancel, send, create + order, `NewOrder`, `OrderRequest`; route segments `orders`, `execute`, `square-off`, `send-to-broker`); how the tripwire treats the new execution assembly is decided in P12-01, this spec follows it (UNVERIFIED until read).
2. **Mode names.** `TradingMode` (Domain/Accounts, verified: `Paper`, `ManualLive`, stored by name, "never rename a value") gains `Assisted`, `SemiAuto`, `AutoLive`. API names (`AccountCodes.Name`): `paper`, `manual_live`, `assisted`, `semi_auto`, `auto_live` (doc 20 A). Column `accounts.trading_settings.mode` is `varchar(16)`: longest stored name is `ManualLive` (10).
3. **The setting rule (CLAUDE.md, 2026-10-23).** Each manual step below has an automatic form behind a setting that defaults OFF, is turned on only by the owner with a password, is recorded as automatic with the setting snapshot, and `unavailable` inputs never count as a pass. Here: the promotion confirm is manual by design and is on the always-ask list (`enable_execution`), so it has **no** automatic form (stated in Decisions D1); the automatic forms live in P12-08 (the tap) and P12-09 (`auto_live`).
4. **P11 interplay.** P11-01 journals only `manual_live` fills (the owner typed them); fills of `assisted`, `semi_auto` and `auto_live` accounts are journaled through the path P12-06 now defines (its fills from the trade book), not by P11-01. A promotion out of `manual_live` deletes no P11 record, and the ramp scale of P11-04 keeps sizing the allocations of every live mode.

## Goal
Every Trading account has an effective execution mode that moves up only one step at a time, only on stored evidence, only by the owner (password, a two-step act with a cooling-off), and moves down by itself the moment the evidence says the machinery cannot be trusted; and in `assisted` the system gives the owner the exact order to type, then checks what was really entered.

## Scope
**In:** the extension of P11-04A's `ck_plan_item_allocations_shape` (which `AddRampAndHalts` already changes to allow `manual_live` with `risk_scale` and `ramp_event_id` required; P11-01 relies on it) to the remaining live modes `assisted`, `semi_auto` and `auto_live`: the live branch keeps its `risk_scale` and `ramp_event_id` requirements unchanged (the P11 ramp scale still sizes every live allocation); `PerAccountAllocator`'s `PoolMode` and the checklist account gate (`account_not_live`, ADR 0095) accept a live-mode account only when its effective mode from the trail (or the configured `manual_live`) is that mode and the connection is `connected`; a mode name on an allocation is the mode at allocation time and decides nothing later (the effective mode is read at send time); until the spec is Approved the check stays as P11-04A left it; pure `TriggerWatcher` (`TriggerCrossed`, reused by P12-08's intent creator); Domain `Execution` (ladder helpers over `TradingMode`, ranks, `ModeGate` rules and `ModeGateFacts`, `DemotionPolicy`, `ModeRouting`, `PromotionRequest`, `ExecutionSettings` and the key catalogue with risk direction, `AssistedSheet`, `SheetMatch`); Application handlers (get modes, request, confirm, demote, build a sheet, match sheets), ports (`IModeTrailStore`, `IUpstreamVerdicts`, `IReconciliationFacts`, `IObservedOrders`, `IExecutionSettingsStore`); Infrastructure stores and migration `AddExecutionModes`; endpoints; the generic `PUT /api/accounts/{id}/trading` refuses the three automated modes; contract; ADR.
**Out:** the intent state machine and its submit path (P12-01), the tap (P12-08), the caps and `auto_live` behaviour (P12-09), every screen (P12-10), the daily login (P12-11), the exit measurement (P12-12). Paper to `manual_live` stays the existing step-up setting change (D2).

## Acceptance criteria
1. Given an account, when its mode is read, then effective mode = the newest `execution.mode_trail` row with `effective_from <= now()`, else the account's configured `paper`/`manual_live`; an unknown stored name reads as `paper` and is logged (fail to the safer side). *`ExecutionModeTests`.*
2. Given `manual_live`, when a promotion request names `semi_auto` (skipping `assisted`), then 409 `execution.mode_not_adjacent`; promotion is one step only; demotion may skip steps. *`ModeGateTests`.*
3. Given each gate of the table in Contract, when its facts are all pass, then `eligible`; when any fact is `fail` or `unavailable` (an upstream verdict missing, a record not readable), then `not_eligible` listing **every** reason with its n and the number needed; `unavailable` never passes; the gate reads only stored records. *`ModeGateTests` (hand table, boundary of every number).*
4. Given an eligible gate and a password, when the owner requests, then a row in `execution.promotion_requests` stores the evidence snapshot and its hash, `eligible_from` = the close of the second trading session after the request, `expires_at` = the close of the fifth; a newer request for the account supersedes the older; the request grants nothing. *`PromotionHandlersTests`, `ExecutionModesDatabaseTests`.*
5. Given a request, when the owner confirms before `eligible_from`, then 409 `execution.cooling_off` with `eligibleFrom`; after `expires_at`, 409 `execution.request_expired`; in the window, the gate is **re-evaluated** and must still be eligible with the same hash-able evidence kinds (else 409 `execution.mode_gate_failed` with the reasons), and the password is checked again (fresh, `Elevate: false`, as the autonomy PUT). *`PromotionHandlersTests`.*
6. Given a confirm that passes, then one `mode_trail` row is inserted (kind `promotion`, actor `owner:<email>` from the session, the gate snapshot, the request id) with `effective_from` = 09:00 IST of the next trading day; the configured `trading_settings.mode` is updated in the same transaction only for `manual_live` (the automated modes live in the trail alone). *`ExecutionModesDatabaseTests`.*
7. The database refuses: a promotion row without a request that is inside its window and names the same `to_mode`; a promotion by an actor not `owner:%`; a promotion whose `from_mode` is not the account's effective mode; a non-adjacent promotion; `to_mode` above `assisted` while `execution.settings.execution_enabled` is OFF in the newest settings row; an UPDATE or DELETE on the trail (grants: SELECT and INSERT only). *`ExecutionModesDatabaseTests`, `ExecutionGrantsTests`.*
8. Given a system actor (`system:mode-guard`), then the database accepts only a row whose `to_mode` ranks below `from_mode` and whose `effective_from` = `changed_at`; given an owner demotion (kind `owner_demotion`, session + CSRF, no password because it lowers risk), the same. *`ExecutionModesDatabaseTests`.*
9. Demotion triggers (table in Contract), each by a hand table with the facts that fire it and the facts that do not; a trigger that cannot be evaluated (`unavailable` reconciliation facts for a session that had orders) **fires** (fail to the lower mode). *`DemotionPolicyTests`.*
10. After a demotion, re-promotion to the same mode needs the full gate again plus `min_sessions_since_demotion` (10 trading sessions in the lower mode); the facts count only sessions after the demotion row. *`ModeGateTests`.*
11. `PUT /api/accounts/{id}/trading` with `mode` `assisted`, `semi_auto` or `auto_live` answers 400 `accounts.invalid` for field `mode` ("Automated modes are changed on the Execution screen"); `paper` and `manual_live` work as before; an account whose Trading role is switched off, that is archived or whose client id is changed is demoted to `paper` by `system:mode-guard` in the same change. *`TradingSettingsTests`, `AccountsEndpointsTests`.*
12. `ModeRouting.Route(mode, actionClass)` is total and pinned by a table over the eight `ActionClass` members (`Entry`, `StopTighten`, `StopLoosen`, `ExitReduce`, `CancelPending`, `AddToPosition`, `ReEntry`, `OutsidePlan`; this slice introduces the enum, P12-08 explains each): `paper`, `manual_live` → `None`; `assisted` → `PrepareSheet` for `Entry` and `None` for the rest (the owner does those by hand); `semi_auto` → `AwaitConfirm` for `Entry`, `Automatic` for `StopTighten`, `ExitReduce`, `CancelPending`; `auto_live` → `Automatic` for `Entry` (inside limits, P12-09) and the three reducing classes; `StopLoosen`, `AddToPosition`, `ReEntry` → `Refused` in every mode until P12-13 specifies them (P12-00); `OutsidePlan` → `Refused` in every mode; an unknown mode → `None`. Entries are BUY only until P12-13. *`ModeRoutingTests`.*
13. `ExecutionSettings` keys carry a risk direction; a change that raises risk is stored with `effective_from` after the same cooling-off, a change that lowers it is immediate; every change is an insert-only snapshot row with actor, reason, database time and hash; the password is required for every change that raises risk and is **not** required to lower. *`ExecutionSettingsTests`, `ExecutionSettingsDatabaseTests`.*
14. Assisted sheet. Given an Armed plan item of an `assisted` account whose trigger level was crossed (`TriggerWatcher`; no intent is created for an `assisted` account, P12-01's gate stays closed) and whose P12-03 **`advisory` run** (same checks, skips `gate_open`, never authorises a send; keyed by account and plan item) is `cleared`, then one sheet is stored with its own `sheet_ref` (no `intentId` is needed): canonical parameters, the text rendered from them, `text_hash`, `valid_until` = the ticket's validity end, and the advisory run id; a plan item whose advisory run is rejected gets no sheet and a listed reason; the text and the parameters are in bijection (a property test: every parameter is in the text, nothing else is). *`AssistedSheetTests`.*
15. Hand example: BUY 120 TATAPOWER, limit 412.35, stop 405.10, target 425.80, intraday → text contains "BUY 120 TATAPOWER", "LIMIT 412.35", "stop-loss 405.10", "target 425.80", "worst case at the stop Rs 870.00" (120 x 7.25) and "notional Rs 49,482.00" (120 x 412.35). The sheet reference is `XA` + yyMMdd + 6 base36 digits of the sheet's sequence number (14 characters of `[A-Z0-9]`, e.g. `XA2610240000A1`); it is shown on the sheet for the owner's notes, is not a client order id, and its prefix differs from P12-01's `XD` so reconciliation never mistakes an owner-typed order for ours (Dhan's web form cannot set `correlationId` anyway). *`AssistedSheetTests`.*
16. Match. Given the broker's order for that account, then `SheetMatch` returns `exact` (side, quantity, product, type, price on the tick grid, legs equal), `differs` with the list of fields and both values (price, quantity, product, missing stop or target), `ambiguous` (two candidate orders), or `unmatched` once the sheet expired; an order never entered is recorded as `unmatched`, never as an error. The match is stored insert-only. *`SheetMatchTests`.*
17. In `assisted` the system holds no order-capable call: a test lists the ports used by the sheet handlers and fails on any port that can write to a broker. *`AssistedSheetArchitectureTests`.*
18. Endpoints answer as in Contract; GET needs a session; POSTs need CSRF; `ExecutionModesView` never carries a token, secret, client id or balance. `scripts/gen-api.sh` run; `scripts/check.sh` green.

## Contract
- **API (all under `/api/execution`, no route segment named `orders`):**
  `GET /modes` → `ExecutionModesView { executionEnabled, gatePolicyVersion, accounts: [ { accountId, name, configuredMode, effectiveMode, effectiveFrom, pending?: { toMode, effectiveFrom }, request?: { id, toMode, eligibleFrom, expiresAt, evidenceHash }, ladder: [ { from, to, verdict: eligible|not_eligible, checks: [ { code, outcome: pass|fail|unavailable, text, n?, needed? } ] } ], trail: [ latest 20 ] } ] }`.
  `POST /modes/{accountId}/promotion-requests` body `{ toMode, reason, password }` → `PromotionRequestView`; 401 `auth.invalid_credentials`, 423 `auth.locked`, 403 `execution.owner_only`, 409 `execution.mode_not_adjacent | execution.mode_gate_failed | execution.disabled`, 400 `execution.values_invalid`.
  `POST /modes/{accountId}/promotion-requests/{id}/confirm` body `{ password }` → `ExecutionModesView`; 409 `execution.cooling_off | execution.request_expired | execution.mode_gate_failed | execution.stale`.
  `POST /modes/{accountId}/demotions` body `{ toMode, reason }` → view.
  `GET /sheets?date=&accountId=` → `[ AssistedSheetView { id, planItemId, accountId, text, textHash, params, clientOrderId, preparedAt, validUntil, match?: { outcome, differences, matchedAt } } ]`.
  `GET /settings` and `PUT /settings` body `{ values: {key: value}, reason, password? }` (keys from the catalogue; unknown key 400).
- **Data (schema `execution` is created by P12-01's `AddExecutionRecord`, which also creates `settings` in the shape below, role `xd_exec` and `intents` with `mode_trail_id`; this slice does not recreate them):** migration `AddExecutionModes` adds `mode_trail`, `promotion_requests`, `prepared_sheets`, `sheet_matches`, the FK `intents.mode_trail_id -> mode_trail.id` that P12-01 left open, and the triggers on `settings`.
  `execution.mode_trail` (insert-only): `id bigserial pk`, `account_id uuid fk accounts.broker_accounts`, `from_mode varchar(16)`, `to_mode varchar(16)`, `kind varchar(14) check in ('promotion','demotion','owner_demotion')`, `actor text check (kind = 'promotion' and actor like 'owner:%' or kind = 'owner_demotion' and actor like 'owner:%' or kind = 'demotion' and actor like 'system:%')`, `reason text`, `request_id uuid null`, `gate_snapshot jsonb`, `gate_hash char(64)`, `effective_from timestamptz`, `changed_at timestamptz` (stamped by trigger from the database clock). Trigger `execution.check_mode_trail` enforces criteria 7 and 8 after taking an advisory lock per account (id order = commit order, the pattern of `autonomy_settings`).
  `execution.promotion_requests` (insert-only): `id uuid pk`, `account_id`, `from_mode`, `to_mode`, `requested_by`, `requested_at timestamptz` (stamped), `eligible_from`, `expires_at`, `evidence jsonb`, `evidence_hash char(64)`, `policy_version int`.
  `execution.settings` (created by P12-01; this slice adds the trigger that stamps `changed_at` and `snapshot_hash`, and the risk-direction and cooling-off check; insert-only complete snapshots, as `workflow.autonomy_settings`): `id bigserial`, `execution_enabled bool not null default false`, `auto_live_enabled bool not null default false`, `values jsonb not null default '{}'`, `actor` (`owner:%`), `reason`, `changed_at`, `effective_from`, `snapshot_hash char(64)` (SHA-256 of the canonical text, stamped by trigger).
  `execution.prepared_sheets` (insert-only): `id uuid`, `sheet_seq bigint identity`, `sheet_ref varchar(16)` (derived from `sheet_seq`), `account_id`, `plan_item_id bigint` (identity, as `trading.plan_items`), `session_date date`, `advisory_run_id bigint` (P12-03), `params jsonb`, `text text`, `text_hash char(64)`, `super_order bool`, `prepared_at`, `valid_until`; unique `(account_id, plan_item_id, session_date)`.
  `execution.sheet_matches` (insert-only): `id bigserial`, `sheet_id uuid fk`, `outcome varchar(12) check in ('exact','differs','ambiguous','unmatched')`, `observed_order_id text null`, `differences jsonb`, `matched_at`.
  **Grants (this relaxes P12-01 criterion 10 on purpose, Decision D10):** `xd_app` (the only process that verifies the owner's password and session) INSERT on `settings`, `promotion_requests` and on `mode_trail` (promotion and owner demotion rows only, enforced by the trigger); `xd_exec` INSERT on `mode_trail` (system demotions), `prepared_sheets`, `sheet_matches`; both SELECT; nobody UPDATE, DELETE or TRUNCATE. `ExecGrantsTests` of P12-01 is edited in this slice to list these exceptions and still fail on any other write.
- **Gate table (policy version 1; the numbers are constants in Domain, not settings: loosening a gate is a code change with an ADR, never a setting):**
  | From → to | Facts (all must pass; each prints n and needed) |
  |---|---|
  | `manual_live` → `assisted` | `execution_enabled` ON; account Trading role on and a Dhan connection `connected`; P11-06 verdict `MET`; sandbox suite of P12-02 passed (stored record, at most 30 days old); static-IP attestation of P12-11 present and at most 30 days old |
  | `assisted` → `semi_auto` | at least 10 trading sessions in `assisted` since the last mode row, each with at least one sheet matched `exact` or `differs` (reachable because a sheet needs only the advisory run, not an intent); in those sessions the P12-06 reconciliation ran for the account (it must run `continuous`, `eod` and `final` for accounts from `assisted` up, foreign activity only: alignment point for P12-06, UNVERIFIED) and reported 0 breaks (`unavailable` fails); P12-02 sandbox record including broker-side stop placement (P12-04) at most 30 days old; a P12-05 kill-switch drill at most 30 days old; readiness `ready` at 09:10 on at least 8 of the last 10 sessions (P12-11) |
  | `semi_auto` → `auto_live` | P12-12 verdict `MET` for this account (30 counted sessions, 0 breaks); `auto_live_enabled` ON in settings; the limits sheet of P12-09 complete (every cap set, allow-list non-empty); a kill-switch drill at most 30 days old; no demotion row in the window |
  `paper` → `manual_live` is not gated (D2); its evidence (P10-06 verdict) is shown beside the control, not enforced.
- **Demotion triggers** (policy version 1, evaluated by `system:mode-guard` after each reconciliation run and on each execution event):
  | Fact | From | To |
  |---|---|---|
  | any reconciliation break recorded for the account's session (P12-06), or reconciliation `unavailable` for a session that had orders or carried a position | `semi_auto`, `auto_live` | `assisted` |
  | a filled entry without a confirmed broker-side stop at the deadline (P12-04 reports it) | `semi_auto`, `auto_live` | `assisted` (the kill switch is P12-05's) |
  | a cap observed exceeded (orders or notional above the day ledger's cap snapshot) | `semi_auto`, `auto_live` | `assisted` |
  | an order at the broker, not ours, on an instrument we manage (`foreign_conflict`, P12-06) | `semi_auto`, `auto_live` | `assisted` |
  | 3 day-halts for the loss cap within 10 sessions | `auto_live` | `semi_auto` |
  | Trading role off, account archived, client id changed (a different broker account; the always-ask item `account_changes`) | any above `paper` | `paper` |
- **Setting keys.** All keys use P12-01's `exec.` prefix and registry (default, range, compiled ceiling) and gain a `RiskDirection` (`HigherIsRiskier`, `LowerIsRiskier`, `OnIsRiskier`, `OffIsRiskier`, `Neutral`) in the shared catalogue `XDrishti.Domain/Execution/ExecutionSettingCatalogue` (P12-01's `ExecSettingRegistry` reads it). Keys added by P12-08 to P12-11 are listed in their specs. P12-04 asks this catalogue for the per-account protection structure: key `exec.structure` (`super` default, `plain_stop`) with a per-account override key `exec.structure@<accountId>` (a catalogue pattern key; risk direction `Neutral`, but a change takes effect from the next session open and is audited like any snapshot).
- **UI:** none here (P12-10 draws the mode panel from `GET /modes`).
- **Events/jobs:** `system:mode-guard` runs in `xd-exec` (P12-01 registers the loop) and after each reconciliation; idempotent: a second run on the same facts inserts nothing (the target is already the effective mode). The sheet builder runs on the `TriggerWatcher` event of an `assisted` account's Armed plan item and its advisory run (no intent exists).

## Non-functional
`GET /modes` reads at most 5 small tables per account (budget: p95 under 80 ms for 3 accounts); the demotion check is O(sessions in window). Logs (ids 6700 to 6709) carry account ids as short hashes, modes, counts and codes, never an actor, e-mail, reason text, password or token. Time through `TimeProvider`; the database clock decides `effective_from`, the cooling-off and the settings in force. The password is verified server-side through `StepUpCommand` with `Elevate: false` (the autonomy PUT pattern, verified in `AutonomyEndpoints`), under the sign-in rate limit.

## Test plan
Unit: gate and demotion hand tables with every boundary (9 sessions vs 10; a verdict 29 days vs 31 days old; `unavailable` for each fact); `ModeRouting` totality (every enum value x every action class); sheet text bijection property over 2,000 generated parameter sets; match table (exact, price off by one tick, quantity 100 vs 120, product CNC vs MIS, missing stop, two candidates, expired). Integration (Testcontainers): every database refusal in criteria 7 and 8, advisory-lock order under two concurrent promotions (one wins), grants as `xd_app`. API: anonymous 401, missing CSRF 403, wrong password counts toward lockout, request/confirm/demote round trip, the generic trading PUT refusal. Architecture: unchanged; the sheet handlers' port list; log ids unique.

## Decisions (researched)
- **D1. Promotion is a two-step owner act with a cooling-off and has no automatic form.** Question: should enabling execution be one password-confirmed click? Answer: no; request (password) then confirm (password) at least two closed sessions later and inside five, effective at the next open. Reason: doc 04 §4.1 and doc 19 §4 name enabling execution on the always-ask list; the setting rule asks for an auto form only for approvals that can be automated safely, and raising the system's own authority cannot. Rejected: a single click (a good week would escalate on impulse); an automatic promotion on evidence (the evidence is the reason to ask the owner, not to skip him). Source: docs 04 §4.1, 19 §4, 16 `always_ask`; ADR 0091.
- **D2. `paper` to `manual_live` stays ungated.** It gives the system no order power (the owner types every order in Dhan), it exists today behind step-up, and gating it would duplicate P10/P11's phase checks; the P10-06 verdict is shown next to the control. Rejected: gating it here. Source: `TradingMode`, `UpdateTrading` (verified), roadmap P10/P11 rows.
- **D3. Gates are code constants with a policy version, evidence is stored records only.** Reason: the same pattern as ADR 0080/0097 (a phase check reads stored records, never prints MET on thin data); a gate the owner can edit in the app is a gate that gets edited after a bad day. Rejected: editable thresholds (risk increase by setting). The numbers (10 assisted sessions, 8 of 10 ready days, 30 days of drill age) are judgement, chosen so each gate costs about two weeks of real operation, and are a printed limit.
- **D4. Demotion is fail-to-lower and system-written.** Any unprovable state demotes; the database lets a system actor write only downward rows, so a bug in the guard cannot promote. Target `assisted`, not `paper`: the account keeps its live connection and the owner keeps the sheet. Source: doc 20 A ("mismatch ⇒ freeze"), doc 19 §4 (runaway orders).
- **D5. The effective mode is a trail, not a mutable column.** The database can check "the owner promoted this account, on this evidence, after this wait", as ADR 0091 does for auto approvals; a column cannot. `trading_settings.mode` keeps only `paper`/`manual_live`. Rejected: extending the column and trusting the endpoint.
- **D6. Settings keys carry a risk direction.** The catalogue decides cooling-off generically (higher cap = more risk, window wider = more risk, a requirement switched OFF = more risk), so P12-08/09/11 add keys without new rules. Rejected: a column per key (a migration per slice and a hash that changes).
- **D7. Assisted sheet instead of "just show the ticket".** The sheet is the exact text the system would send, so assisted sessions test the text, the stop math and the ids on real days at no order risk, and the `differs` list measures how far hand entry drifts from the plan. Dhan order fields used: `correlationId` at most 30 characters of letters, digits, spaces, `_` and `-`; Super Order legs (entry, target, stop loss, `trailingJump`). Source: <https://dhanhq.co/docs/v2/orders/> and <https://dhanhq.co/docs/v2/super-order/>, read 2026-10-24. Dhan's web order form cannot set `correlationId`, so matching is by account, instrument, side, quantity and time, not by id (stated limit).
- **D8. Live modes need a live account.** `assisted` and above are refused for an account without a `connected` Dhan connection; a paper account has no broker to place with.
- **D10. Who writes what.** Question: P12-01 lets `xd_app` insert only into `commands`; where do the owner's acts land? Answer: in the owner-act tables named above, written by `xd_app` after the session, CSRF and password checks, because only `xd-api` has them; `xd-exec` never trusts a payload that says "the owner verified" (it acts only on rows that `xd_app` wrote under the triggers; the same pattern holds for `halt_releases` and `break_resolutions`, which P12-05 and P12-06 make owner-act `xd_app` tables with an actor trigger). The database triggers check order, window and shape, not identity. Rejected: routing every owner act through `execution.commands` (the service would have to trust the claim, a mode change would wait for the service and could not be lowered while it is down). Source: P12-01 D3/D4 and criterion 10 (read 2026-10-24); the limit that a compromised API process could forge an owner row is the same as it could forge a command, and is stated below.
- **D11. Where the pure code lives.** The ladder, gates, routing, demotion policy, text and match functions are pure and are needed by `xd-api` (endpoints) and `xd-exec` (sheets, mode guard); `xd-api` cannot reference `XDrishti.Execution` (P12-01 boundary test c), so they live in `XDrishti.Domain/Execution`, which `XDrishti.Execution` references. The ladder type is `TradingMode` itself; P12-01's `ExecMode` is mapped 1:1 by `ModeTrailSource`.
- **D9. Log ids.** 6700 to 6799 are reserved for P12-07 to P12-12 (6700 to 6709 here); P12-00 to P12-06 keep 6600 to 6699 (P12-01 uses 6600 to 6614, P12-02 6615 to 6634, P12-03 6635 to 6644: consistent, checked 2026-10-24).

## Risks and honest limits
- The gates measure the machinery and the owner's process, not an edge; a clean ladder says "the plumbing held", never "the strategy works". Every verdict line says so.
- Rows are strings and numbers: code holding `xd_app` could write an `owner:` actor. The control is that only the endpoint writes them (session, CSRF, fresh password) and the review rules; the database checks shape and order, not identity (same limit as ADR 0091).
- Reconciliation facts come from P12-06 (`recon_runs`, `recon_breaks`; a clean session is its criterion 10); if its break definition is loose, the demotion is late. Verified against P12-06 (2026-10-24): foreign orders are explained and listed, a foreign working order or position in a managed instrument is the break `foreign_conflict`, which this spec's demotion table treats like any other break.
- A mode change takes effect at the next open; a demotion at once. An order already sent before a demotion is not recalled (the kill switch is P12-05).
- The match in `assisted` can pair the wrong order when the owner trades the same instrument by hand twice (`ambiguous` is reported, never guessed).
- Gate numbers are provisional (D3); the first real ladder run may justify a new policy version, with an ADR.
