## Goal
Create, in one place, everything that later makes an order possible, and prove that nothing else can: the project `XDrishti.Execution` with a pure Domain core (intent aggregate, a 14-state machine with 23 legal moves, leg status rules, the idempotent client order id, the account gate, the settings registry), an insert-only event log with a rebuildable projection, the command plane, the container `xd-exec` with its database role, and the architecture test that relaxes the no-order rule in exactly one place.

2. The new `ExecutionBoundaryArchitectureTests.cs` is the only place the exemption is written:
   a. It reads the old test's text and fails if it contains `XDrishti.Execution`.
   b. The state machine, checks and everything else show none.
   c. No `Shipped` assembly references `XDrishti.Execution`. The only `.csproj` files with a `ProjectReference` to it are `tests/XDrishti.Execution.Tests` and `tests/XDrishti.Architecture.Tests` (the second only so that test (b) can load the assembly; it is not a `Shipped` assembly and ships nothing). `XDrishti.Execution` is itself the host (Worker SDK); no other host references it. `xd-api` reaches it only through `execution.commands`.
   d. The order-write literals `/v2/orders`, `/v2/super/orders`, `/v2/killswitch`, `/v2/pnlExit` appear in source only in `XDrishti.Execution/Dhan/ExecutionEndpoints.cs` (P12-02). ## Acceptance criteria
1. **Machine table.** The 14 states are planned, armed, checking, rejected, submitting, open, filled, protected, managing, closing, closed, reconciled, cancelled, failed. Of the 196 ordered pairs exactly 23 are legal: planned>armed, planned>cancelled, armed>checking, armed>cancelled, checking>rejected, checking>submitting, checking>cancelled, submitting>open, submitting>failed, open>filled, open>cancelled, open>failed, filled>protected, filled>closing, filled>closed, protected>managing, protected>closing, protected>closed, managing>closing, managing>closed, closing>closed, closing>protected, closed>reconciled. Any other pair is refused naming the legal moves; rejected, cancelled, failed, reconciled are final. *`ExecLifecycleTests`.*
2. **Property: no illegal path.** Over 5,000 seeds of 1 to 40 attempted moves, the state is always reachable by legal moves, a refused move changes nothing, accepted moves replay to the same state. *`ExecIntentPropertyTests`.*
3. **Cancel only before a fill.** `open>cancelled` is refused when `filled_qty > 0` (cancelling the rest of a part-filled entry is `open>filled`). *`ExecIntentTests`.*
4. **Leg status rank.** Broker statuses applied out of order never move a leg back (new < sent < transit < pending < part_traded < traded; cancelled, rejected, expired and CLOSED (a super order whose entry and one exit leg both completed) final), `filled_qty` never decreases or exceeds `qty`, a late lower status is ignored and counted (`stale_updates`). *`LegStatusTests`, 5,000 seeds.*
5. **Client order id.** `ClientOrderId.Build(sessionDate, intentId, kind, attempt)` = `XD` + yyMMdd + 6 base36 digits + kind letter (E entry, S stop, T target, X exit, F flatten) + attempt 1 to 9: 16 characters of `[A-Z0-9]`, unique per tuple below 36^6 intents, `TryParse(Build(x)) == x`, deterministic. Hand case: session 2026-10-24, intent 361, entry, attempt 1 gives `XD2610240000A1E1`. An entry's attempt is always 1. *`ClientOrderIdTests` incl. property.*
6. **Gate.** `AccountGate.MayAct(modeAnswer, processEnvironment)` where `modeAnswer` = `IModeSource` result `{effectiveMode, executionEnabled}` is true only when `executionEnabled` is true (the global switch `execution_enabled` of P12-07, default OFF), the effective mode is `semi_auto` or `auto_live`, and the environment is `sandbox` or `live`; `paper`, `manual_live`, `assisted` (it only prepares text, P12-07), `executionEnabled` false, no answer, `none` all refuse with a reason code. The default source answers nothing, so every gate is closed. P12-03's `gate_open` reads the same answer. *`AccountGateTests` table.*
7. **Event log.** A transition inserts one `events` row (kind `state`) and updates `intent_state` in one transaction; the chain (`prev_event_id`) must continue from the previous state event; the database check lists the same 23 pairs as the Domain table (a test compares all 196); an illegal pair, a second start or a fork fails. *`ExecEventStoreTests` (Testcontainers).*
8. **Projection is a fold.** For 200 random intents, dropping and rebuilding `intent_state`, `legs`, `positions` from `events` and `fills` gives the live projection. *`ProjectionReplayTests`.*
9. **Position book.** Fold of fills per account, symbol, product: buy 10 @100, sell 4 @102 gives net 6, average 100, realised 8.00; selling beyond the net gives a negative net and `oversold` (never clamped). Entries are BUY-only in P12 (P12-03 `product_segment`), so any negative net, i.e. any short, is a fault to alarm, not a state to manage. *`PositionBookTests`.*
10. **Grants.** As `xd_exec`: INSERT on `events`, `intents`, `fills`, `command_results`, `broker_calls`, `check_runs`, `check_results`, `alarms`, `alarm_clears`, `halts`, `halt_auto_clears`, `day_marks`, `drills`, `recon_runs`, `recon_breaks`; INSERT and UPDATE on `legs`, `intent_state`, `positions`; SELECT on `commands`, `settings` and every `xd_app`-written table below; no DELETE or TRUNCATE anywhere; no write outside `execution` except `platform.service_heartbeats`. As `xd_exec` SELECT on the outside tables it reads (exact names verified at build): `trading.plans`, `plan_items`, `plan_item_allocations`, `plan_events`, `workflow.approvals`, `accounts.broker_accounts`, `accounts.broker_connections`, `accounts.broker_secrets` (the vault rows), `auth.sessions` is **not** granted (an owner act is proved by the `xd_app`-written rows below, never by reading a session), `market.live_quotes`, `market.instruments`, `market.instrument_broker_ids`, the calendar, `portfolio` holdings. As `xd_app`: SELECT on every `execution` table; INSERT on `commands`; INSERT (owner acts, each with an actor-kind trigger like `mode_trail`, `xd_exec` has no INSERT on them) on `settings`, `mode_trail`, `promotion_requests`, `limits`, `ip_attestations`, `compliance_rechecks`, `day_unlocks`, `halt_releases`, `break_resolutions` and the confirmed/skipped rows of `ticket_outcomes` (the owning slice creates each; this test lists them all and fails on a table that is missing from the list or granted wider); nothing else (no UPDATE, DELETE, TRUNCATE, no INSERT on `events`, `intents`, `legs`, `fills`). A later migration that re-grants a schema (default privileges give `xd_app` DML on new tables) must repeat the revokes; the test fails otherwise. *`ExecGrantsTests` (dedicated server), one row per table and role.*
11. **Settings reader.** `IExecSettingsReader` returns, per registry key, the newest snapshot's value merged over the default; an unknown key is ignored; a value outside the registry range or above its compiled ceiling is replaced by the default and logged; no snapshot means all defaults. *`ExecSettingsReaderTests`.*
12. **Status.** `GET /api/execution/status` returns `{service:{state: recovering|ready|halted|down, lastBeatAt}, environment, accounts:[{accountId, mode, gate:{open, reason}}], halts:[], openIntents, settingsHash}`; `down` when the heartbeat is older than 30 s; an empty database answers environment `none` and closed gates. *integration.*
13. **Commands.** A row in `execution.commands` (id uuid, kind, account id or null, payload up to 2 KB, actor, at) is picked up within 1 s and answered by one `command_results` row (`done|refused|error`, code); an unknown kind is `refused` `execution.command_unknown`; one id is never applied twice. *`CommandPollerTests`.*
14. **Boot.** With environment `none` the host heartbeats, reads settings and commands, enters `recovering`, and builds no broker client (a test asserts no `HttpClient` for the broker is created). *`ExecHostTests`.*
15. **Architecture.** The boundary tests (a) to (h) pass; the old tripwire file is unchanged; the three pins are updated. *`ExecutionBoundaryArchitectureTests`.*
16. **Deploy.** `xd-up.sh` without `--exec` does not start `xd-exec`; with it the container runs non-root, read-only, `cap_drop ALL`, 256 MB, no published port, health green; `xd-db` reachable on `exec`. *compose check + manual.*
17. **Refused actions.** `ExecAction` includes `StopLoosen`, `AddToPosition` and `ReEntry`; `ActionPolicy.Check(action, mode)` answers `Refused` for each of them in every mode (until a later slice, P12-13, decides otherwise): a stop only tightens (P12-04 I3), a position is never added to, a ticket is never re-entered (`unique(account_id, plan_item_id)`). *`ActionPolicyTests`, every mode x action.*
18. **Halt source closed default.** The default `IHaltSource` answers `Unreadable`, and `Unreadable` means halted: no entry can leave while the halt store cannot be read. *`HaltSourceDefaultTests`.*
19. `scripts/gen-api.sh` run; `scripts/check.sh` green.

## Contract
- **Types.** `ExecIntent` (id, publicId, accountId, planItemId, side, symbol, securityId, qty, entry, stop, target, product `INTRADAY`, structure `super|plain_stop`, state, seq) with `Apply(ExecEvent) -> Result<ExecIntent>`; `ExecEvent` kinds `state|leg_sent|leg_acked|leg_update|fill|modify_sent|cancel_sent|check_run|halt_seen|alarm`, source `engine|broker_update|broker_poll|owner|recovery`, payload at most 4 KB, no secrets. `ExecMode` = paper, manual_live, assisted, semi_auto, auto_live (doc 20 spellings, stored by name; `TradingMode` gains the three in P12-07).
- **Data (`execution`).** `intents(id bigint identity, public_id uuid unique, account_id uuid fk, plan_id bigint, plan_item_id bigint, session_date date, symbol, security_id, side, quantity int check > 0, entry_price/stop_price/target_price numeric(18,4), product, structure, environment, mode_trail_id bigint (FK added by P12-07), approval_id bigint, created_by, created_at, unique(account_id, plan_item_id))` insert-only; other specs refer to an intent by `public_id`. `events(id bigint identity, intent_id fk, seq int, kind, from_state null, to_state null, prev_event_id null, source, actor, broker_ref null, payload jsonb, at timestamptz default now(), unique(intent_id, seq))` insert-only, chain keys and the legal-pairs check as in ADR 0083, trigger `execution.check_event`. `legs(id bigint identity, intent_id, kind char(1), leg_no smallint null (1 entry, 2 stop, 3 target as the broker numbers them), parent_leg_id null fk, client_order_id text null unique where not null, broker_order_id text null, algo_id null, status, qty, filled_qty, avg_price, price, trigger_price, send_started_at, acked_at, last_update_at, stale_updates)`. (unique on `(parent_leg_id, leg_no, broker_order_id)` where `parent_leg_id` is not null: the stop and target legs of a super order are created by the broker and are keyed by parent, leg number and the broker's order id, not by a client order id of ours; a leg found at the broker that matches this key is ours.) `fills(id, leg_id, intent_id, exchange_trade_id text unique, qty, price numeric(18,4), at, source)` insert-only. `intent_state(intent_id pk, state, seq, updated_at)`. `positions(account_id, symbol, product, net_qty, avg_price, oversold, updated_at; pk of the three)`. `settings` as in P12-07. `commands`, `command_results`. Column names of tables outside `execution` (`broker_accounts`, `plan_items`, `approvals`) are verified against the migrations at build time (UNVERIFIED here).
- **Settings registry (key, default, range, compiled ceiling).** `exec.max_orders_per_second` 2 (1..5), `exec.max_orders_per_minute` 30 (1..120), `exec.max_orders_per_day` 200 (10..1000), `exec.max_order_value_inr` 100000 (1000..1000000), `exec.max_order_qty` 2000 (1..10000), `exec.price_band_pct` 2.0 (0.1..5), `exec.feed_max_age_s` 5 (1..30), `exec.protect_deadline_s` 10 (3..60), `exec.flatten_on_unprotected` true, `exec.entry_window_start` 09:20, `exec.entry_window_end` 15:00, `exec.square_off_time` 15:15 (15:00..15:20), `exec.token_min_remaining_min` 20 (5..120), `exec.max_modifications_per_intent` 20 (0..24; the broker caps 25), `exec.canary_pending` true (a flag, default ON: while ON, P12-03 caps every entry at 1 share; only the owner turns it OFF, with a password, after recording canary C1 and C2 in P12-00; P12-08/09 reference it). Later slices add keys; a ceiling changes only by code. The endpoints to change them are P12-07's.
- **Problem codes:** `execution.command_unknown`, `execution.gate_closed`, `execution.illegal_move`, `execution.event_conflict`.
- **Migration:** `AddExecutionRecord` with `Down`; creates role `xd_exec` NOLOGIN when missing; `xd-migrate` sets its password when the secret file `Database__ExecPassword` is present (mechanism UNVERIFIED: read `DatabaseMigrator`); explicit revokes for `xd_app` after the default privileges.
- **Log ids** 6600 to 6614, ids/counts/codes only, never a token, client id or order detail.

## Non-functional
Idle container under 40 MB RSS and 1% CPU; command latency under 1 s; a transition under 10 ms p95; migration under 5 s. No secret in logs, events or payloads (a scan of payload keys). Every instruction to the service is a row in `commands`/`command_results`.

## Decisions (researched)
1. **One project, `XDrishti.Execution`, with Domain, Application, Persistence, Dhan inside.** One place to exempt, one assembly to audit; docs 20 and 03 name one project and one container. Rejected: an `Order` aggregate in `XDrishti.Domain` (would turn the tripwire off for the whole Domain) and a separate broker project (two exempt places). Source: docs 20, 03 §4; `NoOrderPlacementArchitectureTests` (opened 2026-10-24).
2. **Tables in schema `execution`, mapped in `XDrishtiDbContext`, used by the host under role `xd_exec`; row classes named `Exec...Row`.** `backend/CLAUDE.md` wants one context and `xd-migrate` migrations; `xd-api` reads the same rows; no order verb in any Infrastructure name. Rejected: a second DbContext in Execution (`xd-migrate` would have to reference it, breaking rule c). The schema name follows P12-07.
3. **A new role `xd_exec`; `xd_app` cannot write the order record.** `deploy/db/init/10-roles.sh` gives `xd_app` DML on all new tables by default, so a compromised API could forge events; per-table revokes leave it only `commands`. Source: `10-roles.sh`, `MigrationBuilderExtensions.cs`, ADR 0083 §6a.
4. **`xd-api` instructs `xd-exec` only by rows.** Doc 04 §3 (UI records desired state, services execute); no inbound port on `exec`; the log is the audit. Rejected: an HTTP endpoint on `xd-exec` (a second route surface needing its own exemption).
5. **Two states beyond doc 20's diagram: `submitting`, `closing`.** Crash safety needs a write-ahead state before the call; our own exit in flight is not "protected". Rejected: the diagram as drawn (no place to say "we may have sent it").
6. **One attempt per ticket and account.** A failed entry is never retried by the system; runaway risk (doc 19 §4).
7. **A 16-character alphanumeric client order id.** Dhan's `correlationId` is at most 30 characters and its character class is unclear (https://dhanhq.co/docs/v2/orders/, read 2026-10-24). Whether Dhan rejects a repeated correlation id is UNVERIFIED, so no design depends on it (P12-02 looks up before any resend).
8. **The environment is a process setting, not data.** `Execution:Environment` = `none` (default) | `sandbox` | `live`; it cannot be flipped from the browser.
9. **The mode comes through a port with a closed default.** `TradingMode` has only `Paper` and `ManualLive` today (opened 2026-10-24); the ladder, its evidence gates and the audited trail are P12-07. Until then nothing can open a gate.

## Risks and honest limits
- The tripwire is by name; reflection or strings are not caught. The barriers are the others listed.
- Dhan has one access token per client, not scoped to orders (P12-02): every container that can decrypt the vault holds an order-capable credential. Isolation is by code, role and network.
- The exempt list is two names; a future agent could widen it by editing one list: the review reads that list.
- Grants tests need a dedicated server; a developer database with another role set-up will not show a grant problem.
