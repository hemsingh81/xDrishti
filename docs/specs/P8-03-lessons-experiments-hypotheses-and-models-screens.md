## Goal
The owner reads every learning record the system stored: what a monitor found wrong (lessons), what was tried and what the stored judgement was (experiments and the hypotheses behind them), which models exist and whether they beat the baselines (models), and the weekly digest, with "no measurable change", "inconclusive" and "no model stored" shown as ordinary results, never as failures or blanks.

## Scope
**In:** four tabs added through the tab registry of P8-02b: `lessons`, `experiments` (with a Hypotheses section), `models`, `digest`; deep links; detail drawers; fixtures; tests.
**Out:** starting an experiment, applying anything, moving a lesson/hypothesis/model/cell, designating a champion (P8-18/P8-19); loss-tag charts and smart-rule evidence (P8-13); the frozen-model counterfactual (P8-12); calibration reliability diagrams (P8-10 pointer); a structured per-fold table (see Decisions 4); any server change.

## Acceptance criteria
1. Given the registry of P8-02b, then four tabs are added by four files and four registry lines; no other built Learning file changes (the `?cell=` link of the built page keeps opening Setups); the feature's `readOnly.test.ts` (a glob over the feature's own sources, so new files are covered automatically) still passes.
2. **Lessons.** Given `GET /api/lessons` (newest 50, state filter `all|open|linked|closed|dismissed` in `?state=`), then each card shows: the problem text, the monitor kind chip (growing_tag, rolling_band, cusum, calibration; words), the subject (a cell key links to Setups `?tab=setups&cell=`), the state chip, "Fix": the linked hypothesis (`#id`, link to Experiments `?hypothesis=`) or "No fix tried yet" (`empty`), "Result": `improved` / `no measurable change` once closed, else "Not closed"; created and updated times (India time). The server's `note` ("Linking or closing it changes nothing…") is printed under the list.
3. Given a lesson card is opened (`?lesson=<id>`), then the drawer loads `GET /api/lessons/{id}` and, when `experimentId` is set, `GET /api/experiments/{experimentId}` for the evidence: before and after pooled mean R with the experiment's baseline and candidate trade counts as n, before and after total R, the experiment outcome word, the fold count; the history of steps (state, actor, reason, time). Numbers appear only here and only with their n; a closed lesson with `no_measurable_change` is a normal card (neutral chip, no warning icon, never a failure colour); a lesson with `result` null shows no before/after block.
4. **Experiments.** Given `GET /api/experiments` (newest 50), then the table has: knob (name, kind), baseline to candidate value, outcome word (Better, Not better, Inconclusive, Cheaper assumption, each with an icon and a one-line meaning), folds better of folds used and the folds needed, required improvement after the trials ("+0.03 R after 4 trials in 30 days"), pooled mean R of baseline and candidate with trade counts, total R of both after the expected live gap, the hold-out ("no hold-out kept" when `holdOutStart` is null), the measured comparison time ("comparison read in 1.2 s; the replay is not timed"), created by and time. Pooled mean R null is `unavailable`. **No row is styled as success except that "Better" uses the word and the neutral-positive icon, never a green fill**; "Cheaper assumption" says "not a gain: a cheaper cost assumption cannot win".
5. Given an experiment with fewer used folds than needed, or no hold-out, then its `reasons` (server text, verbatim) are listed under it, including the cap sentence the server stores ("only 3 used folds, 6 needed to call it better"; "no hold-out was kept…, no change can be called better"); the screen never rephrases a reason or adds a number the server did not send.
6. Given an experiment is opened (`?experiment=<id>`), then the drawer loads `GET /api/experiments/{id}` and prints `reportText` (preformatted, scrollable, labelled) and `parameters`, with the honest limits it contains.
7. **Hypotheses** (a section of the Experiments tab, `GET /api/hypotheses`, state filter): each row shows state, source (owner or grid), cell (link), knob and baseline to candidate, rationale, the experiment that judged it (link) and the states it "may move to" as text; the drawer (`?hypothesis=<id>`) adds the history. The server note "Accepting it changes nothing: applying a change is the owner's own act" is printed.
8. **Models.** Given `GET /api/models` (newest 50, role filter), then each row shows id, role chip (challenger, champion, retired), trainer, feature version, created time, training rows and date range, hold-out ("no hold-out kept" or the first day), verdict word (Eligible, Cannot beat baselines, Inconclusive), folds used, folds beating both baselines and folds needed, pooled calibration error (percentage points), log loss, Brier, "may be champion" yes/no with the server's reasons; with no model the tab shows `empty` "No model stored yet; run `xd learn model`" and the expected-first-view line "On about 2.1 years of history most checks will be NOT EVALUABLE".
9. Given a model is opened (`?model=<id>`), then the drawer loads `GET /api/models/{id}` and shows the validation report text (`reportText`, which holds the fold table, preformatted), the parameters, the calibration mapping as a table (raw score to probability; labelled "the map from score to probability, not a reliability diagram"), the feature importance (path-based contributions, labelled "not exact, not SHAP", top 15), every designation (role, reason, who, when) and the server's `limits`. Model bytes are never shown.
10. **Digest.** Given `GET /api/learning/digests` (limit 12) and `GET /api/learning/digest?week=`, then a week list (ISO week, dates, built by, stored time) selects one digest (`?week=2026-W43`); the digest shows its sections (title and lines) as text, the section "plan outcomes" labelled "simulated on plan prices", and the footer "Every section says nothing was applied"; 404 `learning.digest_not_found` shows "No digest stored for this week"; an empty list shows `empty` with "the weekly service builds one each week once it is switched on (Services)".
11. Given every record list, then an empty list is `empty` (icon + words + the verb: `xd learn lesson`, `xd learn experiment`, `xd learn hypothesis`, `xd learn model`), a failure is `ErrorState` for that tab only, and a record with a null optional figure shows `unavailable` with a reason, never "0" or "-".
12. Given server text (problem, rationale, reasons, notes, report text, parameters, actors, digest lines), then it is rendered as text (the preformatted blocks as text nodes); a markup test covers each field.
13. Layout: cards stack on a phone; tables scroll inside labelled regions; drawers are full width below 600 px; 44 px targets; no horizontal page scroll (P8-16 checklist).
14. Bundle: all four tabs are lazy chunks; first-load JavaScript is untouched; chunk sizes are printed and recorded. Dates are tested with `pinClock`.

## Decisions (researched)
1. **No before/after number without its n,** and numbers only in the drawer. The `LessonView` carries means and totals but no counts; the counts live in the linked experiment, so the drawer fetches it. Rejected: showing the list-level numbers (n missing, D1).
2. **"No measurable change" is neutral.** Doc 09 §10 and ADR 0078 call it a legitimate result; a red or warning style would teach the owner to hunt for changes. Same for "Inconclusive" (neutral) and "Not better" (neutral, with the reasons).
3. **Hypotheses inside the Experiments tab.** A hypothesis is an experiment that has not run or whose judgement is pending (`experimentId` links them); two tabs would split one story. Rejected: a fifth tab.
4. **The fold table is the stored report text.** `ModelDetailView` and `ExperimentView` hold the per-fold results inside `reportText`; there is no structured fold list. Chosen: show the text preformatted, unparsed. Rejected: parsing it (fragile) or adding an endpoint (a design change for a display); a structured fold read model is listed under Findings for the index if the owner wants charts of folds.
5. **The calibration mapping is a table with a plain label,** because `CalibrationPoint(score, probability)` is the isotonic/PAV map, not predicted-versus-actual; a chart of it would be read as a reliability diagram (R12 needs a champion and outcomes, a P8-10 pointer).
6. **Digest tab here.** P8-00 lists a Digest tab but no slice owns it; P8-03 holds the other learning records and the digest is their weekly roll-up (ADR 0094). The `/plans` page keeps its own digest list (P7-17) untouched.
7. **"May move to" as text.** The server returns `nextStates`; showing them informs without a control (D6). The line says where the move is made today (the `xd learn` verbs) and that the screen cannot make it.
8. **Outcome words are the server's enum names mapped once in `outcomeText.ts`,** with a test that fails if the API gains an outcome the map lacks (the UI shows the raw name and an "unknown outcome" note rather than hiding it).
9. **Q8, Q12, Q14, Q19** (P8-00) as recommended: read only, no composite, learning screens in parallel with the report engine, gross unless confirmed (the experiment figures are R per trade on the stored runs).

## Risks and honest limits
- On the owner's data no model, experiment, hypothesis or lesson was stored as last read (ADR 0080, 2026-10-23); every tab opens `empty` until the verbs or the weekly service run.
- Experiment judgements rest on replayed history with modelled fills and no hold-out (ISS-19), so "Better" cannot occur until a hold-out is kept; fewer than 6 folds caps the outcome at Inconclusive. The screen prints the server's reasons instead of softening them.
- A lesson's "improved" is a before/after on the same replayed history, not a live result.
- Model verdicts are out of sample for the model but the data have been seen; a model is advisory and changes no plan (ADR 0070).
- Large report texts are shown whole; very long text may need the scroll region.
