# P11-01 — Manual-live fill capture: the owner's trades and orders read from Dhan, matched to approved tickets, one outcome per ticket

- **Status:** Built 2026-10-28 on the owner's instruction (ADR 0149; see "Amendments at build"). Draft decisions below were researched under the owner's delegation. Not committed or deployed by the builder; services and the order book stay OFF.
- **Phase / roadmap row:** P11 — Small live capital, slice P11-01 of [P11-00](P11-00-small-live-plan.md)
- **Design refs:** docs/design/05-data-and-brokers.md §8, §8.3 · 09-learning-engine.md §3 (step 2), §9 · 12-portfolio-monitoring.md (auto-journal, discretionary tag) · 19-risks-and-compliance.md §4 · ADR 0025 (trade history sync; amendment c skips intraday), 0083 (no order by name), 0090, 0093 (journal), 0097 (allow-list pin and refused probes)
- **Needs:** P11-04A (live allocations exist), P7-13, P7-14, P2-13/P2-16. **Size:** 3.5 agent-days (the largest P11 slice; if it overruns, split the order-book half off as P11-01b). **Safety:** **yes** — two new broker reads (the day's trade book and order book: GET, no body, read only) and a change of the pinned allow-list; the system still places, modifies and cancels nothing. The Approved status on this spec is the owner's consent to the pin change.

## Goal
For a `manual_live` account, everything the owner did at Dhan that day (every fill of every product, every order and its fate) is captured read only and matched to the approved tickets, so that by the evening each approved ticket has exactly one stated outcome (filled, partial, rejected, missed and why), each fill is an entry, an exit or a discretionary trade, and nothing is guessed.

## Scope
**In:**
- Infrastructure: `DhanTradeBookClient` and `DhanOrderBookClient` (GET `https://api.dhan.co/v2/trades` and `.../v2/orders`, no query, header `access-token`, the existing HTTPS / no redirect / 30 s / 5 MB / `DhanHistoryThrottle` rules), `DhanTradeBookMapper` (all NSE_EQ products kept, symbol through `BrokerTradeSecurities`) and `DhanOrderBookMapper`; two rules in `BrokerEndpoints.Rules` (exact path, no query); `IsAllowed`/`Describe` updated; **`PlanPhaseCheck` pin updated and the probe `GET /v2/orders` removed from `RefusedProbes` in the same commit** (the POST / PUT / DELETE order probes, positions and funds stay refused; a new probe set `GET /v2/orders/1`, `GET /v2/orders?x=1` and `POST /v2/trades` is added and must be refused).
- Application: ports `IBrokerTradeBook`, `IBrokerOrderBook` (names pass the no-order tripwire: "OrderBook" is not an order verb), `ILiveCaptureStore`, `IHaltSource` (returns "none known" until P11-04B); handlers `CaptureLiveSessionHandler` (poll), `SettleLiveSessionHandler` (history read for charges, grade, journal, outcomes), `GetLiveCaptureHandler`, `ListLiveOutcomesHandler`; services `live-capture` (Window 09:10-15:40, trading days, poll `Live:Capture:PollSeconds` = 120) and `live-settle` (After `portfolio-broker-history`); both registered **paused**.
- Domain `Domain/LiveTrading`: `LiveFill`, `LiveOrder`, `LiveFillMatcher` (wraps the unchanged `JournalMatcher`, adds the flags), `TicketOutcomeClassifier`, `ProtectionCheck`, `OutcomeCodes`, `CaptureHealth`.
- Data: migration `AddLiveCapture`: `trading.live_capture_runs`, `live_fills`, `live_fill_charges`, `live_orders`, `live_ticket_outcomes`; `journal_fills` made to point at either source. API, CLI, `/live` Capture tab, tests, ADR.
**Out:** any order action; super / forever / GTT order reads (swing stop protection is `unavailable`); positions and funds endpoints; slippage and capacity (P11-02); halts (P11-04B); the report (P11-03); editing a captured row (rows are final).

## Acceptance criteria
1. Given a recorded real answer of Dhan's trade book and order book (scrubbed, the first task of the slice), when mapped then every kept row has side, product, quantity, price, order id and an India time, rows of other segments are skipped per reason, and an unreadable row is dropped and counted by reason (the `BrokerDropReasons` set), never stored half-read.
2. Given an MIS (intraday) fill, when captured then it is stored in `live_fills` and **not** in `portfolio.transactions`; given a CNC fill that the history sync also stores, then both exist, and the settle step reports whether the two agree (`portfolio.transactions` identity `t:yyyyMMdd:<exchangeTradeId>` versus `live_fills.broker_trade_id`).
3. Given the same trade seen by ten polls, then one row exists (`uq_live_fills_account_trade`); given an order whose status moves from PENDING to PART_TRADED to TRADED, then three revisions exist and the newest is the one read; running capture twice writes nothing new.
4. Given the fixture day below, when settled then T1 is `filled` with the VWAP and 40 shares, T2 `rejected` with its text, T3 `missed_no_order` with `missed_r` equal to its plan-grade R, T4 `not_triggered` with no `missed_r`, the SBIN fill `discretionary`, the sale an `exit` of T1.
5. Given a fill that fits two approved tickets (same account, symbol, side, day), then it stays unmatched with the P7-14 reason and no outcome counts it.
6. Given entry quantity above the allocation then flag `over_allocation`; below 90 % of it with no order evidence then flag `size_below_allocation`; an entry beyond 0.25 R worse than the plan entry then flag `chased_entry` (or beyond 1.0 % when the plan has no stop); flags never change which ticket a fill belongs to.
7. Given the entry's last fill at t, when an opposite-side order with a trigger price, quantity >= the position and status transit / pending / traded exists created at or before t + 300 s, then `protected`; otherwise flag `unprotected` for intraday products; for CNC with no such order `protection_unknown` (forever orders are not read).
8. Given no order evidence for the session (setting off, call failed, token expired), then every order-dependent field is `unavailable` and a ticket with no fill whose replay graded is `missed_unknown`, never `missed_no_order`.
9. Given a ticket whose plan grade is still pending (not stored), then no outcome is written and the next settle run retries; after 5 sessions it is written as `unknown`.
10. Given no successful poll for more than 30 minutes of the session or a failed settle, then `CaptureHealth` is `gap` for that day and the API says so; a day with no run at all is `not_run`.
11. `xd_app` can insert and select the five new tables, not update, delete or truncate (grants test); the database refuses a second outcome for one ticket and account, a fill without a side, a status outside the seven values, and a `journal_fills` row that names both or neither source.
12. The allow-list equals its pin, the refused probes include every order write, the positions and funds endpoints and the new probe set; no order-named type or route exists (tripwire green).
13. No poll runs outside the window or on a non-trading day; a 429 / DH-904 is a quiet retry and a 401 / DH-901 marks `token_expired` (the existing self-healing messages), never an empty day.

## Contract
- **API (GET only):** `GET /api/live-trading/accounts/{accountId}/capture?date=YYYY-MM-DD` → `LiveCaptureView { date, health, runs[{kind,startedAt,outcome,fillsNew,ordersNew}], tickets[{itemId,symbol,side,allocatedQty,orderedQty,filledQty,avgEntry,outcome,flags[],missedR,orderEvidence}], unmatched[{symbol,side,qty,price,time,reason}], discretionary[…], evidence }`; `GET /api/live-trading/outcomes?accountId=&from=&to=&page=&size=` (size <= 200, range <= 92 days). Errors: 404 `live.not_found` (no such live account), 422 `live.invalid` (date in the future, bad range). Routes contain no `orders` segment.
- **CLI:** `xd live capture [--account ID] [--date D]` (one poll + settle, read only), `xd live outcomes --date D`; exit codes as `xd plan journal`.
- **Data (schema `trading`, all insert-only for `xd_app`, `MakeAppendOnlyForAppRole`):** `live_capture_runs(id bigint identity, account_id uuid, kind varchar(8) poll|settle, for_date date, started_at, finished_at timestamptz, outcome varchar(16) ok|partial|token_expired|rate_limited|unavailable|rejected, fills_seen int, fills_new int, orders_seen int, orders_new int)`; Migration `AddLiveCapture` with `Down`, `GrantTableToAppRole`/append-only per table; `JournalFill` and `JournalFillRecord` gain `LiveFillId` (nullable `Guid`) beside the nullable `TransactionId`; the existing foreign key `fk_journal_fills_transactions_transaction_id` stays on `transaction_id` only, so a live fill id is never stored in it.
- **Reads of the journal:** `GetPlanJournalHandler` resolves each fill from whichever source its row names (UNVERIFIED how it joins today; the builder opens it first). ## Non-functional
Poll: two GETs, one page each; own work p95 < 1 s for 500 rows (not counting Dhan). Settle: a session of up to 200 fills and 400 order revisions in < 5 s. Endpoint p95 < 300 ms for one day. Security: the token is read through the existing secret path and goes only in the header; no log or exception carries a token, URL, row, price, quantity, symbol or order id (counts, run id, ms); `reject_text` and any broker text are length-capped, stored as data and rendered as text (a markup test). Observability: log events per run (kind, outcome, counts).

## Decisions (researched)
1. **Q: Where do intraday fills live?** A: `live_fills`, never `portfolio.transactions`. Why: ADR 0025 c skips MIS so lots and XIRR stay clean; mixing them would change returns. Rejected: lifting the skip (changes P2 behaviour and every lot rebuild). Source: ADR 0025, `DhanTradeMapper`.
2. **Q: Trade book or history for today?** A: Trade book for polling, history at settle for charges and agreement. Why: Dhan documents `GET /trades` as the day's executed trades (https://dhanhq.co/docs/v2/orders/, read 2026-10-24); whether the history endpoint returns today's trades is undocumented (UNVERIFIED). Rejected: history only (a day late; no intraday halt).
3. **Q: Is the order book needed?** A: Yes, behind its own switch. Why: rejections, partial fills, unfilled limits and the order time exist nowhere else; fields `orderStatus` (TRANSIT, PENDING, REJECTED, CANCELLED, PART_TRADED, TRADED, EXPIRED), `filledQty`, `averageTradedPrice`, `createTime`, `exchangeTime`, `omsErrorDescription`, `algoId` (same page). Rejected: omitting it (capacity and missed-trigger classes become guesses).
4. **Q: Day key or a time window for matching?** A: The P7-14 day key. Why: a ticket is valid for its planned session only (`ExpireTicketsHandler`), so the day is exact; swing exits are matched later by the existing 30-day rule. Rejected: a sliding window (ambiguity between consecutive tickets of the same name).
5. **Q: Tolerances: do they reject a match?** A: No, they flag (D4). Why: a rejected match turns a real chased entry into a "discretionary" trade and hides the cost; flags keep the cost visible. 0.25 R is a quarter of the planned risk; 90 % allows rounding to lots. Rejected: hard price bands (hide the worst executions).
6. **Q: Protection window?** A: 300 s, configurable. Why: a person can place a stop within minutes; five minutes is a stated, adjustable bar, not a finding. Rejected: none required (a position without a broker-side stop is the main live risk until P12).
7. **Q: Poll interval?** A: 120 s. Why: Dhan non-trading APIs allow 20 per second (https://dhanhq.co/docs/v2/, read 2026-10-24); halts need minutes, not seconds. Rejected: 10 s polling (no gain, more token noise).
8. **Q: Outcome rows written once?** A: Yes, final, after the grade exists. Why: insert-only discipline of P7-13/14; a late fill is a stated limit, as in ADR 0093. Rejected: updating rows.

## Risks and honest limits
Dhan's real answers are unseen (fixture first). The current-day behaviour of the history endpoint is unknown. Forever / super orders are not read, so swing stops read `protection_unknown` and the `unprotected` flag covers intraday only. `algoId` is stored as evidence that the order was not the system's; its content for manual orders is unknown. An order cancelled and replaced by the owner appears as two order ids; the ticket's `orderedQty` is the largest single entry order, stated. A fill at an instant the owner placed no ticket for is discretionary by definition, including a correction of an earlier mistake. A shared Dhan account used by someone else cannot be told from the owner.

## Amendments at build (2026-10-28, ADR 0149)
1. **`journal_fills` unchanged; live fills are not journaled here.** The `live_fill_id` change (and acceptance criterion 11's journal clause, the double-journal guard and the grader read of live fills) moves to **P11-01b**. The matching and the outcomes do not depend on it; no fill is journaled twice because `JournalPlansHandler` is untouched.
2. **Charges** come from the existing history mapper (delivery trades only); intraday fills have no charges row (`unavailable`). The history agreement is reported in the settle summary and log, not stored. A mapper entry that keeps intraday is deferred to P11-02.
3. **No `IHaltSource`** (P11-04b adds it with the halts). The settle does not call grading for today (the use case refuses it); it grades a finished session and reads stored grades.
4. **Columns added** to `live_ticket_outcomes`: `protection` and `reject_text`. Poll run words: `ok` = both books read, `partial` = trade book only; order evidence = at least one `ok` poll that day.
5. **Outcome rules fixed:** `partial` = below the allocation with an entry order that never filled in full; `size_below_allocation` only when no order explains it; `rejected` = every entry order rejected; `missed_unfilled` = an entry order exists and never filled; plan entry and stop = the ticket's levels, else the stored grade's; after five trading sessions a ticket with no stored grade is `unknown`; a ticket with no fill whose grade cannot be computed is `unknown`.
6. **Services:** `live-capture` is an Interval service (every `PollSeconds` rounded up to whole minutes, 09:10 to 15:40), `live-settle` follows `portfolio-broker-history` and looks at the last seven days; both start paused (`Live:Capture:Enabled` seeds them). A manual poll (`xd live capture`) may run outside the window; the scheduled one never does.
7. **API:** query parameters of `/outcomes` default to the last 30 days; `GET /capture` defaults to today. The CLI is `xd live capture` / `xd live outcomes`.
8. **Samples:** the mappers are tested against made-up samples shaped like Dhan's documentation. The owner's real, scrubbed answer is still an open act; it replaces them.
9. **Allow-list:** the pin gains `GET api.dhan.co/v2/trades` and `GET api.dhan.co/v2/orders`; the probes change as in ADR 0149 (`GET /v2/orders` leaves; `GET /v2/orders/1`, `GET /v2/orders?x=1`, `POST /v2/trades` join).
