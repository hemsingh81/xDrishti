# P12-02 — Dhan order adapter, the send protocol, the fake broker and the sandbox

- **Status:** Draft (written 2026-10-24; decisions below were researched under the owner's delegation; the owner's Approved is still needed before an agent builds it)
- **Phase / roadmap row:** P12 — Execution service, slice P12-02 of [P12-00](P12-00-execution-service-plan.md) ("Dhan sandbox first")
- **Design refs:** docs/design/20-extended-modules.md §A (idempotent client order ids, ≤ 2 orders/s, static IP, sandbox first) · 05-data-and-brokers.md §7 (`IOrderExecutor`), §8.1 · 17-deployment-and-operations.md §3 (egress allow-list table) · 19 §4, §5 · ADR 0008, 0009, 0097 (data allow-list pinned). **Design change:** doc 05 §7 (the port is `IBrokerOrders`, inside `XDrishti.Execution`, not in Application), doc 17 §3 (a second allow-list table for `xd-exec`). ADR: next free ADR number at build time.
- **Needs:** P12-01. Does not need P12-03..06.
- **Size:** 3 agent-days
- **Safety:** yes. It is the first code that can send a request which places, changes or cancels an order. Reachable only when the process environment is `sandbox` or `live`, the account gate is open (P12-01) and the container is started with `xd-up.sh --exec`; default none of these. The sandbox part needs credentials that only the owner can create.

## Goal
One audited, rate-limited, guarded path from our state machine to Dhan's order, super-order, trade-book, position, funds, profile, static-IP and kill-switch endpoints, with an exactly-once discipline for sends (write-ahead, three-way outcome, lookup before any resend), and a stateful `FakeBroker` that encodes Dhan's documented behaviour so that CI can run every later slice, plus an opt-in sandbox contract smoke.

## Scope
**In:**
- `XDrishti.Execution/Application/Ports/IBrokerOrders.cs` (the only interface with order verbs) and `BrokerOutcome`/instruction types (named `BrokerInstruction`, `BrokerLegView`, no order verb in any other name).
- `XDrishti.Execution/Dhan/`: `ExecutionEndpoints` (the single guard table and the only file with the paths), `DhanOrderClient`, `DhanJson` (tolerant parsing), `DhanErrorMap`, `ExecRateLimiter`, `ExecTokenSource`.
- `Application/LegSender` (the send protocol) and `Application/LegLookup`.
- Table `execution.broker_calls` (insert-only audit), migration `AddExecutionBrokerLog`.
- `tests/XDrishti.Execution.Tests/Fake/FakeBroker` (stateful, deterministic, scriptable) and `BrokerContractTests` run against it and, explicitly, against the sandbox.
- Settings: `exec.exit_collar_pct` 1.0 (0.2..3), `exec.send_timeout_s` 10 (3..30), `exec.order_valid_for_s` 5 (1..30).
**Out:** deciding what to send and when (P12-03/04/08/09), the order-update WebSocket (P12-06), daily login and token renewal (P12-11), setting or changing the static IP (the owner does it in Dhan's web app; P12-11 explains), order slicing, market orders, after-market orders, bracket and cover products, MTF, forever orders.

## Acceptance criteria
1. **One guard.** Given the table in `ExecutionEndpoints`, then exactly these requests pass (HTTPS, exact host, default port, no user info, no redirect, only the named query): `POST /v2/orders`, `PUT /v2/orders/{id}`, `DELETE /v2/orders/{id}`, `GET /v2/orders`, `GET /v2/orders/{id}`, `GET /v2/orders/external/{cid}`, `GET /v2/trades`, `GET /v2/trades/{id}`, `POST /v2/super/orders`, `PUT /v2/super/orders/{id}`, `DELETE /v2/super/orders/{id}/{leg}`, `GET /v2/super/orders`, `GET /v2/positions`, `GET /v2/fundlimit`, `POST /v2/margincalculator`, `GET /v2/profile`, `GET /v2/ip/getIP`, `GET /v2/killswitch`, `POST /v2/killswitch?killSwitchStatus=ACTIVATE|DEACTIVATE`, `GET|POST|DELETE /v2/pnlExit`; and the socket `wss://api-order-update.dhan.co` (used by P12-06). Refused with a test each: `POST /v2/orders/slicing`, `PUT /v2/ip/setIP`, `PUT /v2/ip/modifyIP`, `/v2/RenewToken` (P12-11 adds it by its own decision), `/v2/positions/convert`, forever-order paths, any other path, any other host, `http`, a redirect, a query on a path that takes none. *`ExecutionEndpointsTests`.*
2. **Host by environment.** In a `sandbox` process only the sandbox host passes for order paths; in a `live` process only `api.dhan.co`; `none` allows nothing. The data-side `BrokerEndpoints` (Infrastructure) is untouched and `BrokerAllowListTests` stays green. *same.*
3. **Wire mapping, hand-checked.** A BUY of 10 shares of security `1594`, entry limit 1500.00, stop 1485.00, target 1530.00, no trail, structure `super`, intent 361, session 2026-10-26 produces `POST /v2/super/orders` with JSON `{dhanClientId, correlationId:"XD261026" + "0000A1E1", transactionType:"BUY", exchangeSegment:"NSE_EQ", productType:"INTRADAY", orderType:"LIMIT", securityId:"1594", quantity:10, price:1500.00, targetPrice:1530.00, stopLossPrice:1485.00, trailingJump:0}`; a plain entry produces `POST /v2/orders` with `validity:"DAY"`, `price`, no `triggerPrice`; a protective stop produces `orderType:"STOP_LOSS"` (stop-loss limit) with `triggerPrice` and `price` = trigger less (sell) or plus (buy) `exec.stop_limit_buffer_pct` (P12-04), a reduce-only exit `orderType:"LIMIT"` at the marketable price. A price off the instrument's tick, a non-positive quantity, a stop on the wrong side or `MARKET` as order type is refused before any request (`execution.instruction_invalid`). *`DhanWireMappingTests`.*
4. **Never.** `orderType` `MARKET`, `afterMarketOrder`, `disclosedQuantity`, product `CO|BO|MTF|CNC` and slicing cannot be expressed by `BrokerInstruction` (the type has no such member); a test enumerates its members. *`BrokerInstructionShapeTests`.*
5. **Three-way outcome.** Every send returns `Acked(orderId, status)`, `NotSent(reason)` or `Unknown`. `Acked`: 2xx with a non-empty `orderId` and status `TRANSIT|PENDING`. A 2xx whose status is `REJECTED` is `BrokerRejected(code, omsErrorDescription)` (definitive). `NotSent` only for (a) a failure before the request body was written (DNS, connect refused, TLS) and (b) a 4xx with a parseable Dhan error body (`errorType`, `errorCode`, `errorMessage`). Everything else (timeout after sending, 5xx, 429 with no body, unreadable body, missing `orderId`) is `Unknown`. *`DhanErrorMapTests` table incl. DH-901 (token), DH-904 (rate), DH-905 (input; an invalid-IP message is `IpNotAllowed`), DH-906 (order error), DH-908/909/910.*
6. **Write-ahead.** Given a send, when `LegSender` runs, then the order of effects is: gate and halt check, local rate check, insert `legs` row with the client order id and `send_started_at` plus event `leg_sent` (committed), a second halt-gate check (P12-05: an entry is dropped, never sent, if a halt appeared meanwhile) which then stamps `send_started_at` (an entry dropped here ends `submitting>failed` with reason `halted_before_send`, never `checking>rejected`: the write-ahead already moved the intent to `submitting`), the HTTP call, then the outcome event; a fault injected after any of these four points never yields two broker orders for one id and never leaves a leg without a recorded fact. *`LegSenderFaultTests` (all four points, FakeBroker).*
7. **Lookup before resend.** Given a leg in `Unknown`, when resolved, then `GET /v2/orders/external/{cid}` is called: found means adopt the broker's status and quantities; absent in two lookups 2 s apart means the leg is `failed(not_sent)`; a lookup that itself fails keeps the leg `Unknown` and raises alarm `send_unknown` after 30 s (P12-04 alarms table). Only a protective stop, an exit or a flatten leg may then be resent, with attempt + 1 (new client order id), at most 3; an **entry is never resent**: the intent goes `failed` and the owner decides. *`LegLookupTests`.*
8. **Rate and age.** The limiter admits at most `exec.max_orders_per_second` sends per second, `..._per_minute`, `..._per_day` across all accounts (counted from the `broker_calls` rows of **writes only**, POST, PUT and DELETE, never GETs, so a restart keeps the day count and reads cannot exhaust the budget); a refused send writes no leg and returns `execution.rate_limited`; a send older than `exec.order_valid_for_s` seconds when its turn comes is dropped as `failed(stale)` and never sent late. Reads (GET) have their own limit of 5 per second and are never starved by sends. *`ExecRateLimiterTests` with a fake clock.*
9. **Audit.** Every request, sent or not, writes one `execution.broker_calls` row: time, account, method, path template (never the id values or query values), HTTP status, Dhan code, latency, the offset between the response's `Date` header and our clock (`skew_ms`, null when absent; P12-05 halts above 2 s), client order id, outcome. No body, header, token or client id is stored or logged. *`BrokerCallAuditTests` incl. a scan.*
10. **Token.** The token comes from `IBrokerSecretVault` per account, cached in memory at most 60 s, never logged; a call is refused locally with `execution.token_unavailable` or `execution.token_expired` when the connection's `expiresAt` has passed (no broker call). *`ExecTokenSourceTests`.*
11. **Reads.** `GetOrderBook`, `GetOrderByCorrelation`, `GetTradeBook`, `GetPositions`, `GetFunds`, `GetMargin`, `GetProfile` (token validity, data plan), `GetStaticIp` and `GetKillSwitch` return typed views; unknown fields are ignored; a quirk of the docs is handled by name: `availabelBalance`, `totalQuatity`, duplicated keys of different case, a missing value after a colon. The legs of a super order in `GET /v2/super/orders` (`legDetails`) are returned keyed by (parent order id, `legName`, leg order id), which is the key of `legs` (P12-01), so a stop or target leg the broker created is recognised as ours and never as an unknown order. A view that cannot be built is `Unreadable`, never a guess. *`DhanJsonTests` with the documented samples.*
12. **Fake broker.** `FakeBroker` implements `IBrokerOrders` with: the status set TRANSIT, PENDING, PART_TRADED, TRADED, CANCELLED, REJECTED, EXPIRED, CLOSED; super orders with entry, target and stop legs; modification cap of 25 per order; limit-order matching against a scripted price path; partial fills; a virtual clock; a static-IP rule (DH-905), expired token (DH-901), rate limit (DH-904 above 10 per second), kill switch only when flat and no pending orders; fault injection: drop the response after accepting, delay the ack, answer 5xx, duplicate or reorder updates, reject with a code, silently delete a stop leg, end-of-day square-off. Seeded and replayable (`seed` prints on failure). *`FakeBrokerSelfTests`.*
13. **Contract tests.** The same `BrokerContractTests` (place, get by correlation id, modify, cancel, trade book, positions, funds, profile, static IP, super order if the environment supports it) run against `FakeBroker` in CI and, when marked explicit and credentials exist, against the sandbox; a sandbox run prints a table of expected versus observed and never fails on a documented gap. *`BrokerContractTests`.*
14. **Environment wiring.** `Execution:Environment` selects base URL and credentials: `sandbox` reads the secret files `Execution__Sandbox__ClientId` and `Execution__Sandbox__Token` (owner-created, Keychain `xdrishti/dhan-sandbox/client-id` and `.../token`); `live` reads the account's vault token and client id. Missing sandbox files: the host starts, the sandbox adapter reports `unavailable`, tests skip. *`ExecHostTests`.*
15. `scripts/check.sh` green; boundary tests of P12-01 green (the paths exist only in `ExecutionEndpoints.cs`).

## Contract
- **Port `IBrokerOrders`** (methods, all `CancellationToken`, all returning `BrokerResult<T>` with kinds `Ok|Rejected|NotSent|Unknown|Unreadable|Throttled|Unauthorized|IpNotAllowed`): `PlaceAsync(BrokerInstruction)`, `PlaceSuperAsync`, `ModifyAsync`, `CancelAsync`, `GetOrderBookAsync`, `GetByCorrelationAsync`, `GetTradeBookAsync`, `GetPositionsAsync`, `GetFundsAsync`, `GetMarginAsync`, `GetProfileAsync`, `GetStaticIpAsync`, `GetKillSwitchAsync`, `SetKillSwitchAsync` and `ConfigurePnlExitAsync` (callable only from P12-05 code; an architecture test lists the callers).
- **Data:** `execution.broker_calls(id bigint identity, at timestamptz, account_id uuid null, method text, path text, http_status int null, dhan_code text null, latency_ms int, skew_ms int null, client_order_id text null, outcome text, environment text)` insert-only for both roles' purposes (xd_exec INSERT, xd_app SELECT); index on `(at)` and `(client_order_id)`. Migration `AddExecutionBrokerLog` with `Down`.
- **Network:** `xd-exec` joins `egress`; the HTTP client name `dhan-exec` is separate from the data clients; timeouts: connect 5 s, total `exec.send_timeout_s` (10) for writes, 10 s for reads; **no automatic retry of POST, PUT or DELETE**; GET retried once after 250 ms.
- **Log ids** 6615 to 6634. **Problem codes** (internal, shown by P12-10): `execution.instruction_invalid`, `execution.rate_limited`, `execution.token_unavailable`, `execution.token_expired`, `execution.ip_not_allowed`, `execution.broker_rejected`, `execution.send_unknown`.

## Non-functional
Local overhead of a send (gate, write-ahead, audit) under 15 ms p95 excluding the network; the 2 per second cap holds under a burst of 50 instructions (test); memory under 80 MB. Security: the token is read only inside `ExecTokenSource` and is passed as the `access-token` header; the audit has no body; the guard is the only code that builds URLs; no secret in exception messages (a test throws inside the client and scans the message).

## Test plan
Unit: guard table (every allowed row, 40 refused shapes), mapping, error map, JSON samples from the Dhan pages, limiter, token source. Fault tests: the four points of the protocol times {drop, 5xx, timeout, duplicate ack}. Integration (Testcontainers + FakeBroker): the write-ahead rows, the audit, the day count surviving a restart. Properties (2,000 seeds): over random scripted broker behaviour no client order id is ever accepted twice by the FakeBroker, and every `Unknown` ends in `Acked`, `failed(not_sent)` or an alarm. Negative control: a doctored sender that sends before the write-ahead must be caught on at least 10 seeds. Explicit sandbox smoke (not in `check.sh`): `dotnet test --project tests/XDrishti.Execution.Tests -- --explicit only --filter-class "*SandboxSmoke*"`.

## Decisions (researched)
1. **Super order is supported as an instruction shape; the choice of structure is P12-04's.** Dhan documents `POST /v2/super/orders` with entry, target and stop-loss legs and an optional trailing jump (`trailingJump`, required in the table, `0` or omission cancels), products CNC, INTRADAY, MARGIN, MTF, order types LIMIT or MARKET, validity DAY. Source: https://dhanhq.co/docs/v2/super-order/ (read 2026-10-24).
2. **No MARKET orders, ever.** Reason: other Indian brokers report that under the 2026 framework market and SL-M orders need market-price protection (Kite forum, https://www.kite.trade/forum/discussion/comment/52157, read 2026-10-24; FYERS says market orders are converted to MPP, https://fyers.in/notice-board/new-sebi-framework-for-retail-algo-trading-from-april-01-2026, read 2026-10-24). Dhan's field for it is not in its order page (UNVERIFIED), so the system uses LIMIT only and a marketable limit (last price plus or minus `exec.exit_collar_pct`) when it must exit at once. Rejected: SL-M stops (gap risk and an unknown protection field).
3. **Our cap is 2 orders per second; the broker's is 10, SEBI's threshold 10.** Dhan's page lists order APIs at 10 per second, 250 per minute, 1,000 per hour, 7,000 per day and "25 modifications per order" (https://dhanhq.co/docs/v2/, read 2026-10-24). Doc 20 and doc 16 say 2; our minute and day caps (30, 200) are far below the broker's. Staying under 10 per second keeps the account below the exchange registration threshold (secondary sources, section Risks).
4. **JSON bodies.** The Dhan intro says POST and PUT parameters are form-encoded but every example is JSON and the repo's `DhanQuoteClient` already posts JSON. Decision: JSON; the sandbox smoke is the check (UNVERIFIED until run).
5. **No retry of writes; lookup instead.** Dhan's page does not say it rejects a repeated `correlationId` (UNVERIFIED), so a retried POST could place a second order. `GET /v2/orders/external/{correlation-id}` exists (https://dhanhq.co/docs/v2/orders/, read 2026-10-24); two empty lookups 2 s apart are the proof of absence. Rejected: blind retry; relying on broker de-duplication.
6. **Entries are never resent.** A lost entry costs a missed trade; a duplicated one costs a double position. Protective legs may be resent because their absence is the larger risk (P12-04).
7. **FakeBroker is the CI tool; the sandbox is a smoke only.** Third-party descriptions say the sandbox fills every order at 100, has no quotes or WebSocket, needs no static IP and resets capital daily (https://www.marketcalls.in/algo-trading/dhan-sandbox-kickstart-your-algo-trading-journey-with-risk-free-testing.html, article dated 2025-05-19, read 2026-10-24); Dhan's own FAQ says it tests integration and order workflows, is not paper trading and has no virtual-fund simulation (https://dhan.co/support/platforms/dhanhq-api/what-can-i-test-using-the-dhanhq-sandbox/, read 2026-10-24). The base URL `https://sandbox.dhan.co/v2` is from the same blog (UNVERIFIED by Dhan). So the sandbox cannot test fills, partial fills, stops or updates; only the wire contract.
8. **`DH-905` with an unregistered IP.** Dhan says orders are rejected as DH-905 when the request IP is not the whitelisted one and that a token generated before adding the IP must be regenerated (https://dhan.co/support/platforms/dhanhq-api/i-have-added-my-static-ip-s-on-dhan-web-but-my-orders-are-getting-rejected-stating-dh-905-invalid-ip-while-placing-them-through-the-api-what-should-i-do/, read 2026-10-24). `IpNotAllowed` is therefore its own outcome and a halt trigger (P12-05).
9. **Audit of every call in the database, not only in logs.** Reason: SEBI's framework expects audit trails at the broker and the owner's own record of what was sent is the evidence for a reconciliation break; bodies are left out so no secret or price detail is stored twice.
10. **`algoId` is recorded when the order book returns it** (Dhan's order object has `algoId`, exchange algo id for Dhan). It is stored on the leg row for the audit; nothing is sent.

## Risks and honest limits
- Dhan's pages contain typos and inconsistencies (`totalQuatity`, `availabelBalance`, duplicate keys, kill-switch "header" versus query). The parser is tolerant, but the first live day still decides: the **canary protocol** (P12-00) is one share with the owner watching.
- Whether a super order's stop leg is stop-loss market or limit, how it handles a part-filled entry and whether Dhan squares off INTRADAY super orders by itself are UNVERIFIED (P12-04 decides the structure with that in mind).
- The sandbox is not a fidelity source for fills. The FakeBroker encodes our reading of the documents; it can be wrong in the same way as the code.
- The token is not scoped to orders (Dhan has one access token per client); the guard, the role and the gate are the barriers, not the credential.
- A trade through the adapter uses the Mac's public IP. Containers share it; the whitelisted address must be the ISP's fixed one (P11-05, P12-11).
