## Goal
Show, by a second implementation that did not see the first, that the walker and the position gate do what the written rule tables say on thousands of adversarial series, with every disagreement triaged in writing. Passing says the engine agrees with the rule tables as a second author reads them; it does not say the tables are right (the external-chart comparison of P3-09 does that) and it does not say any strategy has an edge.

## Definitions (numbers the tests pin)
Roles: **O** is the agent that writes the oracle and its hand data; **E** is the agent that owns the engine, the adapter and the comparison; **T** is a third reader (the `reviewer` agent) that audits and triages and never edits. O and E are different sessions.

### D1 — What independence means, and what O may read
The oracle is independent when O wrote it from the written rules only. **O may read:** `docs/adr/0036` to `0044`; the *Definitions* and hand-calculated tables of the specs P3-03, P3-03b, P3-03d, P3-03e (and P3-03c for Annex C); `docs/design/07`, `08`, `16`. **O may not read** anything else in the repository: `backend/src` (all of it, Domain included: the vocabulary O needs is in the ADRs and in the field table of P3-03; Domain doc comments and the XML documentation files under `bin/` and `obj/` describe the rules in the engine's words), `backend/tests` (hand rows as code, goldens, generators, `tests/Shared/TestCostSheet.cs` with its worked expected values), `docs/site`, `docs/prototype`, git history and other refs. **O references nothing:** its records are its own (`OracleBar`, `OracleTrade`, `OracleCandidate`, `OracleRules`, `OracleCalendar`, `OracleCounters`; own enums spelled as the ADRs spell them), so no Domain type, comment or helper is shared; the mapping to `Bar`, `SimTrade` and `WalkCounters` is the adapter's (D3), written by E.

### D2 — How independence is organised, and what it can and cannot prove
(a) **A clean-room workspace, not a worktree.** A git worktree shares the object store (`git show main:path`, `git log -p`, `git cat-file` and `git sparse-checkout disable` all reach the engine), and a sparse pattern cannot drop `CostModel` or `TradeCostApplier` from Domain without breaking the project that holds the allowed types. So O works in a throwaway directory **outside the repository** (the session scratchpad) that E prepares with: a copy of the allowed documents of D1; an empty class library and an xunit test project that reference nothing of xDrishti; a one-page note of the record names O must use (D4). No `.git`. E copies the finished library into `tests/XDrishti.SimOracle` and the hand data into `tests/XDrishti.SimOracle.Tests`'s embedded data (or the oracle's own data folder). (b) **A hard instruction in O's brief:** read only inside the workspace; never run git against any repository; never open a path under the repository root other than those listed; report every tool call that opened a file outside the workspace. (c) **What this can prove and what it cannot.** It cannot prevent a read by absolute path, and O's list of files read is a self-report. T therefore audits **O's tool calls** (the transcript of the O session, if the harness lets T read it: UNVERIFIED; if it does not, the audit rests on the self-report alone and the ADR says so), and reads the oracle source once before the first comparison for engine identifiers, shared helpers and lines that look copied from a rule table without derivation. The claim the label (Annex C) makes is bounded accordingly: *"written by a second agent from the rule tables, by a process that is checked and not enforced"*. (d) **Architecture test** (new, in `XDrishti.Architecture.Tests`): `XDrishti.SimOracle` has no project reference and no package reference (read from the project file, as `ResearchLayeringArchitectureTests` does); no `src/` project references it; the only references to it are `XDrishti.Simulation.Tests` (the comparison) and `XDrishti.Architecture.Tests` itself (which must load the assembly to inspect it: an exception to "only Simulation.Tests", stated here and asserted); its assembly references no `XDrishti.*` assembly (assembly-reference scan; NetArchTest checks type dependencies, so this is the check that holds); `OracleFaults` is not passed non-empty by a production comparison (IL scan of the comparison types with `AssemblyScan.MembersUsedBy`, already used by `CostArchitectureTests` and `ResearchLayeringArchitectureTests`: verified present in `ArchitectureScan.cs:71`); sentinels reject a case that does reference an engine type. (e) **Wiring (priced in *Size*):** the project is added to `backend/*.slnx` next to `XDrishti.Simulation.Tests`; it is a plain library under `tests/` that imports no `Tests.props` (it has no test of its own except through its test project, which imports `Tests.props`); `scripts/check.sh` builds it with the solution, and it counts as test code for coverage (excluded from the coverage gate of `src/`); `Directory.Packages.props` needs no new package. Whether `scripts/check.sh` and the coverage settings treat a non-test project under `tests/` as intended is UNVERIFIED and is read at build time.

### D3 — Inputs, generators and the adapter
The oracle takes `OracleBar[]` (epoch seconds, open, high, low, close as `double`, volume as `long`), an `OracleCandidate` (decision index and instant, side, the trigger close and trigger bar fields, the stop level), `OracleRules` (reward-to-risk, square-off minute, the limit percent and the four slippage numbers, the tick as a decimal, an optional hold: the maximum sessions and an `OracleCalendar` of sessions with open and close minutes and holiday dates) and returns an `OracleResult` (its own trade or the no-trade reason, its own counters, the set of rule-row ids it applied). **The doubles are converted by the oracle**, by the rule written in ADR 0038 item 7 and ADR 0042 D3 (`Math.Round((decimal)x, 8)`, the default midpoint rule of that function, which the ADRs do not name: a gap listed in D10). **Two generator families** are compared: (1) the engine's (`SeededDays`, `SeededDaily`, `SwingSeries`, `SeededReplaySeries`), through the adapter E writes; (2) **`OracleSeries`, written by O** in the oracle library (SplitMix64, the published constants, seeded by an integer) from the category list of D7, never from the engine's generators, so that a blind spot of one is not the blind spot of both. The adapter is the one place E's reading of the engine can hollow a comparison; it is therefore tested on its own (round trip: engine case → oracle case → the engine's fields rebuilt equal the originals, over every generator family, field by field).

### D5 — Tolerance rules
Where both sides compute in `decimal` and convert to `double` once, **exact equality** (bit equality for doubles, `==` for decimals, ordinal for text) for epochs, enums, integers, counters and every price. For the ratio fields `RExact`, `RFilled`, `SlippageR`, `MaeR`, `MfeR` — whose formulas the ADRs give but whose order of operations after the first is not always stated (the gap on `SlippageR` in D4; ADR 0038 item 13 normalises `-0`) — **exact equality is tried first**; if it fails only in the last digits the tolerance is `|a − b| ≤ 1e-12`, written in the test with the measured maximum and the reason, and the **measurement and the decision go into ADR 0047** (not only into the test). A tolerance never applies to a price, an epoch or a counter. A decimal zero is `+0.0` on both sides.

### D6 — The hand rows are O's own data (who holds the expected values)
The reviewer's finding stands: if E's adapter built the hand cases from the engine's test code, dropped or normalised data would make the agreement hollow. So **O encodes every hand-calculated row of the specs itself, as data**: the minutes (time, O/H/L/C, volume), the candidate (decision instant, trigger close, stop level), the rules (reward-to-risk, square-off, limit percent, slippage, tick, hold and calendar), and the **expected values as numbers copied from the spec table** (entry, exit, reason, R, MAE, MFE, fill kind, counters). These are in O's test data and **O's test holds the expectations**: the oracle must equal them. Then E's adapter maps O's data to the engine's types and the engine must equal **the same O-held numbers**. The engine's own hand rows (`HandCases` and the rest) are not used here and keep their own tests; the engine-side adapter of D3 is used only for the seeded generators. The rows are those of the P3-03, P3-03b, P3-03d and P3-03e specs (F, W, H, M, K, G, J, Q, O, DF families); the table of ids is part of O's data, and a spec row not encoded is named with a reason. The three-way agreement (spec numbers, oracle, engine) on every row is the first gate; the seeded comparison does not start before it holds. A row whose spec text is too ambiguous to encode as numbers is a D9 class A entry on day one.

### D7 — Edge categories and non-vacuity
The oracle returns the set of rule-row ids it applied (`E0` to `E9`, `X1` to `X9`, `S1` to `S5`, the gate rows). **Coverage is measured from the oracle's own trace**, not from the engine's counters. Categories, each with **at least 500 series in the combined run and at least 500 from `OracleSeries` alone** (the oracle's generator must carry the floor by itself, so the engine generators cannot hide a gap in it): (1) a gap above the limit (E5); (2) a gap through the stop at entry (E6); (3) a stop gap exit; (4) a target gap exit; (5) a minute that reaches stop and target with the open between them; (6) the same with the open beyond the target; (7) holes before the fill minute; (8) holes inside the position; (9) a hole at the due minute or at the square-off minute (a missing 15:29); (10) ties: a price equal to the limit, to the stop, to the target; a price on and off the grid; (11) zero-volume minutes; (12) a special (short) session with a calendar, and a holiday between two sessions; (13) the end of the data inside a position (`EndOfData`) and with an order pending; (14) overnight orders: Friday to Monday, over a holiday, the 09:20 and 09:21 fills, the 09:15 minute with a widened range; (15) `MaxHold` at the close of session N, with the due minute present and absent; (16) the gate: a candidate at 15:30 on the day a position leaves at the close, a position ended by the data. Each category is asserted per sub-case where it has them (the floors apply to each listed item separately, so (5) and (6) are two floors, not one). Costing sub-cases are in Annex C. A category below its floor fails the suite.

### D8 — The faults check (walker, at least 14 here)
The oracle accepts an `OracleFaults` flag set (test use; empty by default). Each fault is a one-line deviation from a rule; switched on one at a time, **O's hand data (D6)** run through the faulted oracle must fail on at least one row. The walker faults here: a fill on the signal minute; the stop checked after the target; a gap filled at the stop price instead of the open; an off-by-one minute; a target filled at the open when the open is beyond it for a buy only; the limit rounded to the nearest tick instead of down; slippage applied to a target exit; the extra stop ticks on a `MaxHold` exit; the entry slipped past the limit; MAE counted from the filled entry; the high of an `AtLimit` fill minute counted into MFE; a zero-volume minute treated as a trade; `MaxHold` counted from the decision date instead of the fill session; the weekend not skipped in E9; 09:21 allowed; a pending order read as `NoFillBar`. The rows that catch the last four are rows of the P3-03e tables (O1, O5b, O6, O7, O8: **confirmed present in the spec**, no new hand row is needed for them); any other fault that no row catches names a missing hand row, which is added to the spec's table and priced, or the fault is declared equivalent with a reason. The cost faults are in Annex C; the roadmap's 20 is the total of the two parts.

### D9 — Triage, the log and who decides
A disagreement is any difference in D4 beyond D5. It goes into a **log created by the build** at `docs/research/p3-08-disagreements.md` (the folder `docs/research/` does not exist today; the build creates it) as a table with fixed columns the suite parses: `id | generator | seed | category | field | oracle | engine | rule row | minimal series | class | verdict (ADR sentence) | fix | regression row`. **Classes:** (A) rule-table ambiguity; (B) engine bug; (C) oracle bug; (D) generator or adapter fault. **Who decides:** T reads the ADR sentence and both traces and proposes a class; T never edits. **Class A is the owner's** (a rule is the owner's: asked in chat, ADR 0047 amended, a hand row added, both sides conform). **Class B is the owner's decision before any fix**, because a fix that changes any output moves the golden files and the engine version (`sim-6`, with the golden diff read as in P3-03e); the owner is told, in chat, the case, the rule sentence and the consequence. Class C is fixed by O or a fresh O session, never by E; class D by E. The oracle is never edited to match the engine, and the engine is never changed to match the oracle, without an entry citing the ADR sentence. Every B or C entry becomes a permanent hand row. The suite fails on an entry without a class, a verdict or (for B and C) a regression row; an unresolved entry blocks P3-09.

### D10 — The gaps of the dry read, closed before the oracle is written
Before O starts, E drafts the text of **ADR 0047** that closes the gaps of D4 so that O reads a rule and not a guess: `SlippageR` as the decimal difference converted once (or as the difference of doubles: the owner's call if it changes any golden, otherwise the reading that matches the code is recorded and the other is rejected with a reason); the midpoint rule of the 8-place conversion; the intraday sentence of `EntriesAfterMissingMinutes`; the hold end as the start of the exit minute; the rounding of the target level; and the corners marked in D4. Writing the ADR text is a read of the engine by E and is allowed; O never sees it before it is committed as text. A gap whose resolution would change engine output is a class A entry and waits for the owner. The dry read is repeated at the end of the build by the reflection test of D4.

## Acceptance criteria
1. **Clean room.** The architecture test of D2 (d) passes with its sentinels: the oracle has no project or package reference and its assembly references no `XDrishti.*` assembly; only `XDrishti.Simulation.Tests` and `XDrishti.Architecture.Tests` reference it; no production comparison passes non-empty faults (IL scan); the solution file lists the project. T's audit of O's tool calls and of the oracle source is recorded in the log, with the statement of D2 (c) on what it can and cannot show.
2. **Dry read.** Every property of `SimTrade` and `WalkCounters` has a row in the table of D4 (reflection test) and no row has the status "no sentence"; the gaps of D10 are closed in ADR 0047 text before O's start (commit order shown in the log).
3. **Hand rows.** Given O's data for the rows of D6, then the oracle equals the O-held numbers on every row, and the engine, through the adapter from O's data, equals the same numbers, in both fill modes (`SlippageConfig.None` gives `EntryFilledPrice = EntryPrice`); every spec row id is encoded or named with a reason.
4. **Adapter.** The round-trip test of D3 holds on every generator family; a deliberately dropped field makes it fail (sentinel).
5. **Walker comparison.** Over `OracleSeries` and the four engine generator families, in total at least 2,000 series (intraday, swing, daily), the oracle and `TradeWalker` agree on every field of D4 under D5; every disagreement is in the log; the largest ratio difference seen is printed and, if a tolerance was needed, recorded in ADR 0047 (not only in a test).
6. **Gate comparison.** Over at least 500 multi-candidate swing series, the blocked set and each hold end equal those of `PositionGate`, including the candidate decided at 15:30 on the day a position leaves at the close and a position ended by the data.
7. **Replay level.** Over 100 seeded replay series, the oracle's trade list for a window (decision date in the window, the cut of ADR 0043 D6, the gate, `OpenAtEnd` and `OrderPendingAtEnd`) equals the replayer's trade for trade and fate for fate.
8. **Coverage.** Each category and sub-case of D7 reaches its floor in the combined run and from `OracleSeries` alone, measured from the oracle's trace; the test prints the counts; a shortfall fails.
9. **Faults.** Each fault of D8 makes at least one of O's hand rows fail; the fault-to-rows list is written in the test output; none is caught only by the seeded comparison.
10. **Log.** The log exists with the columns of D9; every entry has a class and a verdict; B and C entries have regression rows; there is no open entry; the log lists the number of series compared per generator.
11. **Triage rehearsal.** Before the first real run one walker fault is left on; the run reports disagreements; T classes each as C. This shows the loop of D9 works.
12. **Runtime and reproducibility.** The same seeds give byte-identical summaries on two runs; this part adds at most 20 seconds to `scripts/check.sh` on the developer machine (measured and written in ADR 0047; the budget is UNVERIFIED until measured); counts of 5,000 per category are explicit tests and stay out of `check.sh`.
13. **Documents.** ADR 0047 (the clean-room process and its limits, the comparison set and the dry-read table, the tolerance and its measurement, the triage rule, the closed gaps); ADR 0037 Amendment 10 only if the run-record text changes (it does not in this part); the roadmap row and ISS-18 are the coordinator's; `scripts/build-docs.sh`.

## Non-functional

## Risks
- **A shared misreading.** O is of the same model family reading the same ADR text. Mitigations: O's hand data copies the spec's by-hand numbers, the faults check, T's audit, the external-chart comparison of P3-09 (at least 5 of the 20).
- **Independence is a process.** A read by absolute path is not prevented; the self-report proves only what O says; the transcript audit is UNVERIFIED as available.
- **The comparison proves less than it looks.** The scanner, frame and compiler have no second implementation; a wrong stop level from the scanner passes this suite.
- **The dry read finds gaps.** Several are already listed (D4); each class A entry waits for the owner, which the roadmap does not count in agent-days.
- **Generators tuned by their authors**; the floor is a floor.
- **A tolerance hiding a bug**: exact first, measurement recorded.
- **Runtime** unmeasured.

## Annex C — proposed P3-08c: the cost oracle, the cost chain and the label (about 1.3 agent-days)

## Annex B — proposed P3-08b: the added leak and invariance properties (about 0.85 agent-day)
**Scope.** Properties through `Simulator.Run` and `InstrumentReplayer`, each with a negative control that must fail on at least 10 seeds while the honest run reports none. Only what is *not* already in the repository (see *What exists*): (a) **scale invariance** (prices and tick × 2 and × 4; ratios and charges-in-R unchanged; the rupee-threshold exclusion list asserted empty for ORB v1, UNVERIFIED that it is); control: a fill rounded to a fixed 0.05 grid; (b) **date-shift invariance through the loop** (the same series moved by 1, 5 and 52 whole weeks, calendar of exceptions moved with it; `SwingShiftInvarianceTests` inserts a night and does not do this); control: a calendar anchored to a fixed date; (c) **instrument-order independence** (6 to 12 instruments in the given order, reversed and three seeded permutations; per-instrument results byte-identical; no result depends on which other instruments are present); control: a universe-dependent fill using a shared last price; (d) **no state leaks between instruments** through the scanner and the replayer (**re-scoped after review**: the engine creates a new frame per scanner and never calls `Reset`, so "fresh frame versus `Reset`" tests something the loop does not do; the `Reset` equivalence is covered by `XDrishti.Indicators.Tests` and the inventory says so): one `PreparedStrategy` replayed over sequences A, B, A of 100 seeded series, results of the second A equal the first; the architecture tests already forbid mutable statics in `XDrishti.Simulation`, so this is the dynamic check of caches in the compiled sides; control: a scanner that caches the previous instrument's last value; (e) **daily truncation through `Simulator.Run`** over 500 `SeededDaily` series (the overnight walk and gate are covered at their level by `OvernightEntryTests`; the loop is not); the existing controls are kept; (f) an **inventory test**: a table property → the test that proves it → its control, failing by reflection if a named test disappears, stating which exist (look-ahead, truncation and perturbation, determinism, slippage, tick grid, the night insertion, `RNet` chain) and which are added here; Larger counts are explicit tests.
