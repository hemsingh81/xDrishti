## Assumptions (the safest answer that still serves the goal)
1. **Nothing about the app is cached.** The service worker stores exactly: `/offline.html`, `/manifest.webmanifest`, the icons. Not `index.html`, not the hashed JS/CSS, not any `/api`, `/hubs`, `/health`, `/prototype` or `/docs` response. Offline, a page load shows a static page saying so. So "cannot show data while offline" holds by construction (P8-00 D9), and the usual PWA bug of an old shell with new chunks cannot occur.
2. **The access path is decided here and recorded in an ADR**, as P8-00 Q5 requires before the slice (decision D1): a **private tailnet in front of a loopback-only proxy**. No port is ever bound to the LAN.
3. **The owner's acts** (installing Tailscale, signing in, enabling HTTPS, running `tailscale serve`) are not done by an agent and not by a script of this repo; the repo supplies the loopback port, a runbook and a fail-closed check.
4. **An update prompt, not auto-update.** A running phone app is told a newer build exists and reloads only when the owner taps; no automatic reload (it would drop a half-typed password form or reason).
5. **Sign-out, expiry and lock leave nothing behind.** There is no separate lock screen in the app: "lock" is the idle or absolute session end (`AuthSession`), which already runs through `endSession(queryClient, reason)` in the frontend; that is the one hook.

## Goal
The owner can reach the app from her own phone over an encrypted private network, install it to the home screen, review a plan before the cutoff, and see an honest offline page when there is no connection, while the Mac still listens only on loopback, the phone holds no trading data, and the whole thing is OFF until she switches it on.

## Scope
**In:** `manifest.webmanifest`, icons, `offline.html`, `sw.js` (hand-written, ~50 lines), the lazy `pwa` module (register, kill switch, version check, update snackbar), cache clearing in `endSession`, `Clear-Site-Data` on logout over HTTPS, `Cache-Control: no-store` on `/api/*` at the proxy, the second Caddy site `:8081`, `deploy/compose.phone.yaml` and `xd-up.sh --phone`, `scripts/phone-check.sh`, the runbook in doc 17, the doc 13/19/04 wording, the ADR, tests.
**Out:** Web Push or any notification outside the app (Q6), offline data of any kind, background sync, a share target, shortcuts, an app-store wrapper, a public tunnel, a LAN bind, installing or configuring Tailscale from the repo, a lock screen, biometric unlock.

## Acceptance criteria
1. **Manifest.** `GET /manifest.webmanifest` returns `Content-Type: application/manifest+json` and `Cache-Control: no-cache`; it has `id "/"`, `name "xDrishti"`, `short_name "xDrishti"`, `start_url "/"`, `scope "/"`, `display "standalone"`, `theme_color "#4338ca"` (the `index.html` value), `background_color`, `icons` of 192 and 512 PNG plus a 512 `maskable`, `prefer_related_applications false`, and **no** `shortcuts`, `share_target`, `protocol_handlers` or `related_applications`. Every icon file exists with the declared size. `index.html` links the manifest and an `apple-touch-icon` (180). *Build-output test.*
2. **Service worker file.** `/sw.js` is served from the root (scope `/`) with `Cache-Control: no-cache`; the CSP is unchanged (`script-src 'self'` covers it). *Proxy test + build test.*
3. **The worker never intercepts data.** Given requests for `/api/*`, `/hubs/*`, `/health/*`, `/prototype/*`, `/docs/*`, any non-GET method, any cross-origin URL, any `Range` request and any `/assets/*`, when the `fetch` event fires, then `respondWith` is not called (the network handles it, no cache is read or written). Only a same-origin `navigate` request outside those prefixes is answered, by `fetch(request)` with a fallback to the cached `/offline.html` when the fetch rejects. *Unit test running `sw.js` source in a Node `vm` with fake `self`, `caches`, `fetch`.*
4. **Cache contents are an allow-list.** At install the worker puts exactly `/offline.html`, `/manifest.webmanifest` and the icon paths into the cache `xd-offline-1`; the source contains no other `cache.put`/`cache.add` call (a text guard) and the test records every call; at activate it deletes every cache whose name starts `xd-` except the current one. A `message` of `{type:"clear"}` deletes all `xd-` caches. *Unit.*
5. **Offline.** Given the network is down, when a page is navigated to, then `offline.html` is shown: the sentence "You are offline. xDrishti shows no data without a connection and keeps none on this device." with a retry link, no script, no external resource, readable at 360 px and in dark mode (`prefers-color-scheme`). *Unit for the fallback + a real-browser check recorded in the PR.*
6. **Default OFF and kill switch.** Given the capability `pwa` is OFF or unknown, when the app loads, then no worker is registered; if one is registered from an earlier ON, it is unregistered and every `xd-` cache is deleted. Given ON and a signed-in session, then the worker is registered after load (`requestIdleCallback`), never before sign-in. *Vitest with a fake `navigator.serviceWorker`.*
7. **Sign-out, expiry and 401-expired leave nothing.** Given a registered worker and a filled cache, when `endSession` runs for `signed_out`, `expired` or an idle timeout, then all `xd-` caches are deleted and the registration is unregistered; the `POST /api/auth/logout` response carries `Clear-Site-Data: "cache", "storage"` when the request was HTTPS (as seen through the trusted proxy) and does not otherwise. *Vitest + API test.*
8. **Update prompt.** Given the page was loaded with entry script `/assets/index-AAA.js`, when the app becomes visible (and at most every 30 minutes while visible) and a fresh `fetch('/', {cache:'no-store'})` names `/assets/index-BBB.js`, then a snackbar "A new version is ready" with a Reload button appears; tapping it reloads; ignoring it changes nothing; equal names show nothing; a failed fetch shows nothing. No `skipWaiting` message, no automatic reload. *Vitest with fake timers and a pinned clock.*
9. **No exposure by default.** `podman compose config` of the default stack publishes only `127.0.0.1:8080` for the proxy (and the existing ones for seq/db in their profiles); with `compose.phone.yaml` it additionally publishes **`127.0.0.1:8081`** and nothing else; no entry binds `0.0.0.0` or a LAN address. *A script test over the rendered config, in `scripts/check.sh`.*
10. **Second site equals the first.** `:8081` imports the same routes, headers, CSP, the guarded `/prototype` and `/docs`, the hub block and the SPA fallback as `:8080` (one shared snippet, so they cannot drift); the differences are only: `X-Forwarded-Proto https` to `xd-api`, `Strict-Transport-Security: max-age=31536000` (no `includeSubDomains`, no `preload`), and `Cache-Control: no-store` for `/api/*` on both sites. `CaddyfileTests` pin both sites; `scripts/check-proxy.sh` validates the file with the proxy image.
11. **Cookie and hub over the private entry.** Given a request with `Host: xd-mac.example.ts.net`, `Origin: https://xd-mac.example.ts.net`, `X-Forwarded-Proto: https` coming from the trusted proxy, then the session cookie is `Secure`, the hub handshake is accepted, and an `Origin` for another host is still 403 `hub.origin_forbidden`; CSRF is unchanged. *Integration with the existing hub harness (`HubSocket`, `LiveHubAccessTests`).*
12. **`scripts/phone-check.sh` fails closed.** It exits non-zero when `8080` or `8081` is published on anything but `127.0.0.1`, when `tailscale funnel status` shows anything on, when `tailscale serve status` maps anything but `127.0.0.1:8081`, and when any of these outputs cannot be parsed (the raw lines are printed). With no `tailscale` binary it prints "phone access is not set up (a valid state)" and exits 0. *Shell test with stubbed `podman`/`tailscale`.*
13. **Bundle and dependencies.** Eager (entry chunk) growth ≤ 0.5 KB gzip (the lazy import plus the 40-byte cache clearing in `endSession`); `npm run size` passes and prints the lazy `pwa` chunk; no new package. `scripts/check.sh` green.
14. **Docs.** Doc 17 §2 row and a new "Phone access" section, doc 19 §4 two rows, doc 13 §4 and doc 04 §4.2 wording updated; ADR written; roadmap row; `scripts/build-docs.sh`.

## Contract
- **API:** no new endpoint. `POST /api/auth/logout` gains the `Clear-Site-Data` header on HTTPS. `GET /api/capabilities` (P8-18) gains the meaning of `pwa`.
- **Data:** none; the capability `pwa` row in P8-18's table. No browser storage other than the one cache `xd-offline-1`.
- **UI:** `frontend/public/{manifest.webmanifest, offline.html, sw.js, icons/}`; `frontend/src/pwa/` (`register.ts`, `useVersionCheck.ts`, `UpdateSnackbar.tsx`, lazy-imported once from the shell after the session is known); `endSession` calls `clearOfflineCaches()` (a 6-line function in `shared/lib`, no import of `pwa/`). `sw.js` is plain JavaScript in `public/` (copied unhashed by Vite, `/sw.js` must be at the root and must not be hashed). Icons are generated once from `favicon.svg` with a tool on the Mac (e.g. `rsvg-convert` or headless Chrome: UNVERIFIED which is installed) and committed as files; no build-time image dependency.
- **Proxy/compose:** `deploy/caddy/Caddyfile` restructured to a snippet `(xd_site)` imported by `:8080` and `:8081`; `deploy/compose.phone.yaml` adds `127.0.0.1:${XD_PHONE_PORT:-8081}:8081` to `xd-proxy`; `deploy/xd-up.sh --phone` adds `-f compose.phone.yaml`; the container's healthcheck is unchanged. Nothing is added to the `back` network.
- **Scripts:** `scripts/phone-check.sh` (read-only, no secret).
- **Events/jobs:** none.

## Non-functional
Security: nothing sensitive is cached; the worker's scope is `/` but its code path touches only navigations and four static paths; `no-store` on `/api/*`; HSTS on the private entry only; cookie flags unchanged (HttpOnly, SameSite=Lax, Secure over HTTPS); the lockout and idle timeout apply on the phone as on the Mac. Performance: first-load JavaScript budget as P8-00 D7; the worker adds one small request at install. Observability: a client log line is not added (no telemetry leaves the app); the proxy's access log is the record.

## Decisions (researched)
- **D1 Access path: Tailscale `serve` to a loopback-only port.** Chosen: the Mac keeps listening only on loopback (`127.0.0.1:8081`, published only with `--phone`); the owner runs `tailscale serve` on the Mac to publish it **inside her tailnet only** over HTTPS with the certificate Tailscale provisions for `<machine>.<tailnet>.ts.net`. The phone joins the same tailnet. Why: (a) no LAN bind, so the standing rule "every published port binds 127.0.0.1" and doc 19's "local only" hold; (b) a publicly trusted certificate, so a phone installs the PWA with no root-certificate profile; (c) works away from home (the use case is reviewing a plan on the way to work before the 09:05 cutoff), which the home LAN does not; (d) device-level WireGuard authentication before the login page is even reachable. `tailscale serve` is limited to the tailnet (Funnel is the public one) and HTTPS needs MagicDNS and the HTTPS Certificates setting enabled in the admin console, which publishes machine names in the public Certificate Transparency log (the runbook: rename the Mac to a neutral name first, keep Funnel off, device sharing off, key expiry on). Sources: https://tailscale.com/kb/1242/tailscale-serve and https://tailscale.com/kb/1153/enabling-https (read 2026-10-24). **Rejected:** (1) **Caddy `tls internal` on the LAN**: Caddy's local CA signs certificates only for names/addresses it serves locally and the root must be installed in each client's trust store by hand (https://caddyserver.com/docs/automatic-https#local-https, read 2026-10-24); it needs the Mac to listen on the LAN, a root certificate trusted on the phone for every site (a larger blast radius than one app), and gives no access away from home. (2) **A public tunnel or reverse proxy** (any service that terminates TLS at a third party and exposes a public name): data and login page reachable by the internet; UNVERIFIED in detail, rejected by principle (doc 19 "local only", doc 02). (3) **No phone access:** a valid state; this slice still ships the installable shell for the Mac and `localhost`, and the plan-review mitigation of doc 19 stays "unreviewed tickets lapse".
- **D2 Cost and trust of D1, said plainly.** Tailscale is a third-party coordination service and an account; the payload is end-to-end encrypted between the owner's devices, the service sees metadata (devices, times). Pricing and plan terms were not checked (UNVERIFIED). This is the owner's decision to accept: the slice does not depend on it and nothing in the repo calls Tailscale.
- **D3 Hand-written worker, not Workbox.** The worker needs one precache of four static files, one navigation fallback and a cache sweep. Workbox is a good library (workbox-build 7.4.1 is the current release per the npm registry, read 2026-10-24) but brings a build plugin and a dependency tree, a precache manifest and runtime-routing machinery that this design deliberately does not use. Fewer lines, fewer ways to cache the wrong thing, no new package (pins nothing). Rejected: `vite-plugin-pwa` / `workbox-build`.
- **D4 No shell caching.** A cached `index.html` plus hashed chunks is what makes PWAs show an old version for days; the worker lifecycle keeps an old worker serving until every client closes unless `skipWaiting` mixes versions on one page (web.dev, https://web.dev/articles/service-worker-lifecycle, read 2026-10-24). The assets are already `Cache-Control: public, max-age=31536000, immutable` at Caddy, so the worker would add no speed. Offline the app could not show data anyway. Rejected: precaching the entry chunks.
- **D5 `skipWaiting` and `clients.claim` are safe here** because this worker serves only `offline.html`; so the worker updates itself silently; the **update prompt is about the app build**, found by comparing the entry script name in a fresh `/` with the one loaded. Rejected: a waiting-worker prompt (it would tell the owner about a change that has no visible effect).
- **D6 Manifest and install.** Chromium requires `name` or `short_name`, 192 and 512 icons, `start_url`, `display` and no `prefer_related_applications`, served over HTTPS (localhost counts); a worker is not an install requirement. iOS 16.4+ installs from the Share menu in Safari and other browsers and has no `beforeinstallprompt`, so the app shows no custom install button, only a sentence in the owner's runbook. Source: https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Making_PWAs_installable (read 2026-10-24). iOS may drop a home-screen app's storage after weeks of non-use (secondary sources: firt.dev/notes/pwa-ios, WebKit bug 232302; not verified against Apple): harmless here, because there is nothing to lose.
- **D7 Clearing.** The page clears the cache and unregisters in `endSession` (works wherever JavaScript runs). `Clear-Site-Data: "cache", "storage"` on logout is a second line over HTTPS: "storage" unregisters worker registrations and clears DOM storage; MDN does not say whether it covers the Cache Storage API, and Safari support was not confirmed, so it is never the only mechanism (https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Clear-Site-Data, read 2026-10-24). Rejected: attaching it to every 401 (it would wipe storage on every anonymous request).
- **D8 One Caddy snippet, a second site.** The private entry must apply the same CSP, hub block and guarded docs; a copy would drift. `X-Forwarded-Proto https` is set by Caddy itself on `:8081` so the API's `Secure` cookie and the hub's same-origin check (scheme, host, port must match the `Origin`) do not depend on what `tailscale serve` adds (the official page documents identity headers, not forwarded headers: UNVERIFIED). Rejected: relying on Tailscale's headers.
- **D9 Capability, not only a build flag.** `pwa` OFF means no registration and a kill switch for any earlier one; the static manifest link stays in `index.html` (inert metadata; without a worker the browser can only offer a shortcut to the same page).

## Risks and honest limits
- Whether `tailscale serve` passes WebSockets and the original `Host` unchanged was not verified here; the owner's check is the live indicator on the phone. If the hub fails behind it, the app still works by polling where screens have it, and the origin rule is not relaxed.
- A phone is a more exposed device than the Mac: a lost unlocked phone with an open session shows plans. Mitigations that exist: idle timeout, lockout, sign-out clearing, no data cached; the owner's own phone lock is the real control.
- The login page and the static bundle are reachable by anything in the tailnet; keep the tailnet to the owner's devices.
- Certificate names appear in a public ledger; the runbook says to use a neutral machine name.
- `Clear-Site-Data` support differs by browser; the JavaScript path is primary.
- The hand-written worker is small but is security-relevant code: the allow-list tests are the guard, and the reviewer is told to read `sw.js` line by line.
