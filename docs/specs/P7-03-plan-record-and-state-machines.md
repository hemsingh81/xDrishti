## Assumptions (taken as recommended)
1. **Safe by construction.** No order is placed, modified or cancelled by any type; no credential is read; no approval can be made by anything but the owner. The `approvals.kind` column accepts only `owner` (a check); the `ApprovalKind` enum has one member. There is no `system`, `rule` or `auto` kind. Raising that is the owner's decision (P7-00 Q3, Q4) and a new migration.
2. **The state is the newest row.** No state column exists. `trading.plan_events` holds every state change of a plan (`item_id` null) or a ticket; the first state (plan `draft`, ticket `proposed`) has no row; `published` is written in the same transaction as the plan. A move takes a transaction advisory lock per plan or item, re-reads the newest state, and writes only if it is still the one the caller saw (else `stale`): of two concurrent moves one wins.
3. **Tickets** (10 states, doc 04 §4.2): Proposed, Modified, Approved, Rejected, Lapsed, Armed, Invalidated, Expired, Triggered, Closed. Thirteen moves: the diagram plus Modified to Rejected, Modified to Lapsed (an edited ticket can still be turned down or left unreviewed) and Approved to Expired (the window ended before arming). Approved, Modified and Rejected are the owner's moves only; every other move is a service's. A reserve ticket reaches Armed only through Approved (no promotion). The group (primary, reserve, rejected) is fixed at publish time; a **rejected candidate is not a ticket**, has no state rows and no moves (the store and the table refuse it).
4. **Plans** (8 states): Draft, Published, InReview, Approved, Rejected, Lapsed, Armed, Expired; eleven moves. A plan is Approved only when no ticket is open and at least one is approved; Rejected or Lapsed only when none is open and none approved; Armed only with an armed ticket; InReview only after a decision. The plan can never say more than its tickets.
5. **The default at the review cutoff is lapse.** `ReviewCutoff.Decide` (pure) lapses every Proposed or Modified ticket (reserve included) and sets the plan to Approved only if the owner approved a ticket, else Rejected (all rejected, none lapsed) or Lapsed. `ApplyReviewCutoffHandler` is refused before the cutoff time, for an owner actor, and for a plan that is not Published or InReview. There is no `arm_top_n`, no promotion from reserve, no option that approves.
6. **Allocations are paper-only for now**: `plan_item_allocations.mode` has a check `= 'paper'` (P7-00 Q2: paper first; a manual-live account gets nothing until the owner decides, by a later migration).
7. **Plans are immutable.** A plan is stored once by `plan_key` (idempotent, concurrent publishes store one); a different input is a new `version` of the date, never an edit. Notice ("no order is placed by this system; armed means watched") and honest-limits sentences are stored on every plan as data (`PlanWording`, pinned by a test); each item carries its evidence block (cell, trades, data range, P(win) basis, conservative expectancy, unavailable inputs, advisory note) as columns.
8. **No pipeline, no write endpoint, no screen.** Tests build plans from fixtures through the store. The write use cases (`MoveTicketHandler`, `MovePlanHandler`, `ApplyReviewCutoffHandler`) exist for P7-10/P7-11 and are not exposed over HTTP. The API is read only.
9. **`plan_runs`** records one row per pipeline attempt (outcome `published` with its plan, `failed_closed` with the failing gate, or `dry_run`; a `manual` flag for the phase check). Written by the P7-08 pipeline; here only the table and the port method.
10. **Naming.** Schemas `trading` and `workflow` are new (the existing accounts live in `accounts`; doc 03's `trading.accounts` is not moved). Log ids 4650 to 4653. ADR 0083. Migration `AddPlanRecord`.
11. **The architecture rule** `NoOrderPlacementArchitectureTests` is a tripwire, not a guarantee. It scans every type and member name (any casing, underscores ignored) of the shipped assemblies for `placeorder`, `submitorder`, `modifyorder`, `cancelorder` and for the verbs create/send/post/execute/route/transmit/buy/sell with order(s) or (execute/buy/sell/send/post) with trade (the owner's trade journal names such as `CreateTradeBatch` are not matched); scans the route templates of `XDrishti.Api/Endpoints` for order routes (`orders`, `place-order`, `send-to-broker`, `execute`, `square-off`); and checks that no shipped assembly references a broker or order-routing library. It is proved by a planted member and a planted type in the test assembly itself. (The spec of P7-00 said Application, Domain, Infrastructure; the rule also covers Hosting, Api, Worker and Feed.)

12. **Owner-only is enforced by the database, not only by the handler (safety review).** An item event into approved, modified or rejected must name an approval row and no other event may (check `ck_plan_events_approval`); the approval is `owner` by its kind check and its actor must start with `owner:` (check); composite foreign keys tie an event and an approval to an item of the same plan and an event to an approval of the same item and plan. The store throws if the move is an owner decision without an approval, or the other way round, or if the approval's decision is not the state moved to. Only `owner:` actors count as the owner (the learning verb's `cli:xd` does not). The first write endpoint must set the actor from the authenticated identity, never from a request body.
13. **Continuity.** A state is left at most once (partial unique indexes on `(item_id, from_state)` and, for plans, `(plan_id, from_state)`), so a trail is one chain even if a lock were skipped.
14. **The plan is consistent with its tickets at the moment it moves.** Ticket moves take the plan lock and then the item lock; a plan move recomputes the ticket facts in SQL under the plan lock from the newest event of each ticket, so a plan is never approved or armed without a live approved or armed ticket (a race test). An owner decision is accepted only while the plan is Published or InReview.
15. **The cutoff is the plan's, not the caller's.** `trading.plans.review_cutoff` is set when the plan is published (derived by the pipeline from the session calendar, P7-08). An owner approval or modification at or after it is refused by the store (`AfterCutoff`) and by a check on `workflow.approvals` (`decision = 'reject' OR decided_at < cutoff`); a rejection after the cutoff is allowed. The cutoff handler reads the plan's cutoff and takes no cutoff argument.
16. **A plan Approved is a consequence of owner approvals.** The plan move to Approved needs at least one ticket whose newest state is Approved, and a ticket is Approved only through an event that names an owner approval row (assumption 12); so the cutoff handler's plan move is a service move that can only follow an existing owner approval.
17. **Later migrations must not re-grant the schemas.** A migration that calls `GrantSchemaUsageToAppRole` for `trading` or `workflow` would give UPDATE and DELETE back; an architecture test fails on it, and `PlanGrantsTests` checks the privileges.
18. **The database holds the rules on a direct insert too (second safety review).** (a) An approval names the state it backs (generated column `state`: approve to approved, modify to modified, reject to rejected) and an event's `to_state` must equal it (composite foreign key), so a reject approval cannot back an approved event. (b) Every event has a `prev_event_id`; exactly the first event of an item starts at `proposed` and of a plan at `draft` with no previous event, and every later one continues from the previous event's `to_state` (composite foreign key on `(prev_event_id, plan_id, lane, from_state)`; lane 0 is the plan). (c) A `BEFORE INSERT` trigger on `plan_events` (`trading.check_plan_event`, owned by the migration role, dropped in `Down`) applies the plan rules from the newest event of each ticket: approved needs an approved ticket and none open; rejected and lapsed need none open and none approved; armed needs an armed ticket; in review needs a decision; and an event on a rejected-group item is refused. (d) An approval's `(plan_id, cutoff)` is a foreign key to `(id, review_cutoff)` of its plan, so the cutoff is the plan's; `decided_at` is stamped by the database clock by a `BEFORE INSERT` trigger on `workflow.approvals` (whatever the insert says, so a direct insert cannot back-date an approval before the cutoff; the check that follows refuses an approve or modify at or after it), the store reports that refusal as `AfterCutoff`, and the store reads the application time after taking the locks. (e) `review_cutoff` must fall on `for_date` in India.
19. **Known decay.** A plan that is Approved or Armed is not taken back if its last approved ticket is later invalidated or expires: the rule holds at the moment of the plan move, not afterwards (the plan state is a record of what was true then; the tickets carry the live state). The trigger reads committed rows, so a direct writer that bypasses the store lock can still race it; the store takes the plan lock first.

## Goal
The plan, its tickets and every decision about them are permanent, insert-only records with exhaustive, tested state tables whose default at the cutoff is to lapse, readable over the API, with a build rule that no code can place, modify or cancel an order.

**In:** Domain `Planning` (`TicketState`, `TicketGroup`, `TicketLifecycle`, `PlanState`, `PlanLifecycle`, `PlanFacts`, `ReviewCutoff`, `MoveReplay`, `ApprovalKind`, `PlanWording`); Application port `IPlanStore` and records, handlers (list, get, move ticket, move plan, apply cutoff); Infrastructure `PlanStore`, six record types and configurations; migration `AddPlanRecord` (`trading.plans`, `plan_items`, `plan_item_allocations`, `plan_events`, `plan_runs`, `workflow.approvals`, all insert-only for `xd_app`, with `Down`); `GET /api/plans`, `GET /api/plans/{id}`; the architecture rule; ADR 0083; docs; contract regenerated.

## Acceptance criteria
1. The ticket table has exactly the 13 moves; for every one of the 100 pairs a move outside the table is refused naming the legal moves (or "final"); final states have no moves. *`TicketLifecycleTests`.*
2. (Also enforced by the database, see assumption 12.) Approving, modifying and rejecting are refused to a service; every other move is refused to the owner as a hand move; no state can be approved by a service; a reserve ticket cannot reach Armed except through Approved; a rejected candidate has no moves. *`TicketLifecycleTests`, `PlanHandlersTests`.*
3. The plan table has exactly the 11 moves with the fact rules of assumption 4. *`PlanLifecycleTests`.*
4. The cutoff default is lapse and never approval for every ticket state; a plan is Approved at the cutoff only with an owner-approved ticket; refused a second before the cutoff and for an owner actor. *`PlanLifecycleTests`, `PlanHandlersTests`, `PlanRecordApiTests`.*
5. A plan is stored once per key under concurrency; its items, allocations and Published row are one transaction. *`PlanRecordApiTests`.*
6. Concurrent decisions on one ticket: one wins, the others are stale or refused; an owner decision writes exactly one `owner` approval row that the trail points at; a service attempt writes nothing. *`PlanRecordApiTests`.*
7. The database agrees with both tables on every pair (events check), refuses an approval kind other than `owner`, a modify without modifications, a manual-live allocation, a published run without a plan, a failed-closed run without a gate, a reserve item without reasons. *`PlanRecordApiTests`.*
8. `xd_app` can SELECT and INSERT but not UPDATE, DELETE or TRUNCATE on every table of `trading` and `workflow`, and cannot create or alter objects there. *`PlanGrantsTests`.*
9. `GET /api/plans` (date, account, limit 1 to 200; 422 `plans.invalid`) and `/{id}` (404 `plans.not_found`) show state, next states, tickets with evidence, size per account, notice and the trail. *`PlanRecordApiTests`.*
10. The build fails on any type or member named for placing, modifying or cancelling an order, on an order route and on a broker library reference; the rule is shown to fail on a planted example. *`NoOrderPlacementArchitectureTests`.*
10c. A reject approval cannot back an approved event; a first event cannot skip proposed; a later event must continue from the previous one; a plan move the tickets do not support, an event on a rejected candidate, an approval with a cutoff the plan does not have or after its cutoff, and a cutoff on another day are all refused by the database on a direct insert. *`PlanRecordApiTests`.*
10b. The database refuses an owner-decision event with no approval, an approval for another item or plan, a non-owner actor, and an approval at or after the cutoff; an owner approval after the plan's cutoff is refused; a plan cannot be approved after its last approved ticket was invalidated, also under a race. *`PlanRecordApiTests`.*
11. Handlers are internal sealed and registered; log ids 4650 to 4653 are unique; `scripts/gen-api.sh` run; `scripts/check.sh` green.

## Contract
- **API:** `GET /api/plans?date=&account=&limit=` -> `PlanView[]` (items and history empty in a list); `GET /api/plans/{id}` -> `PlanView`. Errors: 422 `plans.invalid`, 404 `plans.not_found`. Internal (no HTTP): `plans.item_not_found`, `plans.move_refused`, `plans.stale`.
- **Data:** the six tables above; keys and foreign keys (items to plans, allocations to items and `accounts.broker_accounts`, events to plans/items/approvals, approvals to plans/items, runs to plans); unique `plan_key`, `(for_date, version)`, `(plan_id, item_rank)`, `(item_id, account_id)`; checks as in the tests. Migration `AddPlanRecord` with `Down`.
- **UI:** none (P7-17).
- **Events/jobs:** none.

## Non-functional
Plan read: one query per plan plus items and trail (a few dozen rows). Logs carry ids, state codes and error codes only (4650 to 4653), never a reason, a modification or an account. Time through `TimeProvider`. No broker, credential or network code is reachable from this slice.

## Test plan
Unit (exhaustive tables, cutoff, replay, wording), Application with a fake store (refusals before any write, owner-only decisions, cutoff), integration on a real database (publish idempotency, concurrency, approval rows, cutoff, events check against both tables, constraint refusals, runs, endpoints), grants as `xd_app` on a dedicated server, architecture (no-order rule with planted violation, Domain namespace list, log ids).

## Honest limits
Records and tables only: nothing proposes a plan yet and no screen shows one. The concurrency guarantee is per ticket or plan (two different tickets move independently). The no-order rule is by name: it stops the obvious, not a determined bypass; the real barrier is that no broker write endpoint is on the allow-list and no order-capable credential is held.

Also: **"owner" in the database is the actor prefix plus the kind** (`owner:...`, `kind = 'owner'`): any code holding `xd_app` can write it. The control is that no path or endpoint does, the architecture tests and the GET-only endpoints; the first write endpoint must take the actor from authentication. The database does not require a published plan before item events, and does not bound `review_cutoff` to the calendar session beyond the date (P7-08 derives it from the session calendar).
