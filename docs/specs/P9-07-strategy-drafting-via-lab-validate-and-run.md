# P9-07 — Strategy drafting: English idea to validated YAML, owner confirm, then a Lab quick test

- **Status:** Draft (written 2026-10-24; decisions below were researched under the owner's delegation; the owner's Approved is still needed before an agent builds it)
- **Phase / roadmap row:** P9 — AI assistant and Hermes PoC ("strategy drafting"); slice of [P9-00](P9-00-ai-assistant-plan.md) (written in parallel; UNVERIFIED text).
- **Design refs:** docs/design/14-ai-assistant.md §1 (row "Draft strategy rules"), §3 (guardrails: "no write tools except `lab_run`"), §4 feature 3, §5 (10 ideas) · docs/design/11-strategy-lab.md §1 (channels, "Plain English"), §2 (language as built) · ADR 0057 (Lab API), 0058 (Lab runs), 0034/0036/0055 (language, model, file) · P5-01, P5-02 · ADR 0005.
- **Needs:** P9-01 (`IChatClient`), P9-02 (xd-mcp `lab_validate`), P9-03 (schema `ai`, settings endpoint, the chat turn loop where the local tool is registered, tokenizer), P9-06 (`TextGuard`), P5-01/P5-02 (built). Used by: P9-09 (eval set C), P9-10 (Hermes may call `lab_validate` only; it cannot create drafts).
- **Size:** 3.5 agent-days (checks and `SubmitDraft` core 1.0, draft job + prompt sheet 0.8, chat tool + auto option + settings column 0.6, store + migration + endpoints + confirm 0.7, panel + tests 0.4). Cut order: auto option, then chat tool (the dedicated job stays); a split into 07a (core, job, confirm) and 07b (chat tool, auto option) is natural if day one runs long.
- **Safety:** **yes.** The owner's confirm stores a strategy version and starts a Lab job from the UI, and a draft starts a model job. The model itself gets no write path. Default OFF: `Assistant:Drafts:Enabled` is false (and it also needs `ai.settings.enabled`), Confirm needs the capability `ai.settings.allow_draft_confirm` (false) and the fresh password per action; the build stops for the owner's Approved on this spec.

## Goal
The owner types a trading idea in plain English and gets back either a candidate strategy text that already passes `validate` (with a plain list of what the model understood and which values it chose on its own), or an honest "this idea cannot be written in the language today, because ...". Nothing is stored and nothing is run until the owner reads the text, edits it if wanted and presses Confirm; Confirm stores it as a normal library version and starts a quick test, whose deterministic summary is shown beside the draft.

## Scope
**In:**
- Domain `XDrishti.Domain.Assistant.Drafting` (pure): `DraftSubmission` (yaml, understood, assumptions, not_expressed, requested_test, idea), `DraftChecks` (C1 to C6 below), `DraftIdea` (extract numbers/times from the idea), `AutoDraftRule`, `DraftWording`.
- Application `XDrishti.Application.Assistant.Drafting`: ports `IStrategyDrafter` (adapter over `IChatClient`), `IDraftStore`; **`SubmitDraftHandler`** (the one core: validate with `ValidateStrategyQuery`, run C1 to C6, store the draft, no model involved), `DraftStrategyHandler` (the dedicated job: model call, repair loop, then `SubmitDraft`), `ConfirmDraftHandler`, `DiscardDraftHandler`, `GetDraftHandler`, `ListDraftsHandler`, `AutoDraftHandler`; `DraftSheet` (the prompt sheet); and **`lab_propose_run`** (arguments: the YAML and the explanation fields only; **no idea argument**: the server stores the conversation's latest user message verbatim as the draft's idea), a *local* function registered in the P9-03 turn loop inside `xd-api` (not in `xd-mcp`, whose host has no write code, P9-02/P9-00 D1) that calls `SubmitDraftHandler` and returns `{draftId, status, problems[], findings[]}` to the chat model so it can repair within its call budget. This is P9-00 D9's "proposal" tool: it stores a draft and executes nothing.
- Infrastructure: `ai.strategy_drafts`, `ai.strategy_draft_decisions`, migration `AddStrategyDrafts` (the two draft tables only), and migration **`AddAiWriteSwitches`** (the `ai` schema): adds to `ai.settings` the booleans `allow_draft_confirm`, `auto_lab_quick_test`, `allow_proposal_accept` and `auto_accept_hypothesis` (all `not null default false`; the last two are used by P9-08) and **replaces the `snapshot_hash` trigger function** so the canonical text of the row includes all four new values (P9-02 criterion 4 hashes the row values; without the replacement a flipped switch would not change the hash). Test: flipping each of the four columns in an otherwise equal row changes `snapshot_hash`, and a row that changes none keeps it; the old rows still verify.
- Api: `POST /api/assistant/strategy-drafts`, `GET /api/assistant/strategy-drafts[/{id}]`, `POST .../{id}/confirm`, `POST .../{id}/discard`; verb `xd assistant draft "<idea>" [--show]` (draft only; confirm is not a verb).
- Frontend: `DraftPanel` (idea box, result, editor reuse of the Lab editor if cheap, Confirm/Discard, run summary), lazy.
**Out:** the model starting a run or storing a strategy by its own act (never; only the owner's Confirm, or the owner's auto setting, D9); full test, walk-forward, robustness (the owner starts those in the Lab as today); promotion; C# plugins; editing an existing strategy (the model drafts new families only; a clone-and-change is the owner's); model-written run summaries (follow-up; the summary here is deterministic); image or file input; a form builder.

## Acceptance criteria
1. Given the idea "Intraday: after 9:45 buy when a 15-min candle closes above VWAP with RSI(14) above 55 and 1-hour EMA20 above EMA50. Stop below last swing low. Target 1:2. Exit by 15:15. Mirror for shorts." and a scripted model answer, when drafted then the stored draft has `status = valid`, the YAML passes `ValidateStrategyQuery` (`Valid = true`, a `Hash`), SELL has an explicit `sell:` block (the automatic mirror is P3-02e and not built; the sheet says so), and `numbers_dropped` is empty because 9:45, 15, 14, 55, 20, 50, 1:2 and 15:15 appear in the YAML or in `not_expressed`.
2. Given an answer whose YAML has an error then the loop makes at most **2 repair turns**, each carrying only the located problems (`path`, `code`, `message` from `StrategyValidation.Problems`) and the failing YAML; a draft still invalid after that is stored `status = invalid` with the last problems, shown to the owner as "not valid, not confirmable" (Confirm is refused 422 `assistant.draft_invalid`; the owner may edit the text and Validate in the panel, and Confirm then re-validates the edited text).
3. **C3 (assumptions are true).** Each `assumptions[].field` (a YAML path such as `exits[0].rr`) must exist in the parsed YAML with the stated value; a mismatch is finding `assumption_not_in_yaml` and counts as a repair reason. **C5 (numbers).** Every number in `understood[]` and `assumptions[].why` must occur in the idea text or the YAML (the shared `TextGuard` with facts = those two); else `explanation_number_not_in_source`. **C6 (nothing dropped silently).** Every number or clock time in the idea must appear in the YAML (as a literal, a param value, or inside a condition) or be listed in `not_expressed[]` with a reason; else `idea_number_dropped`.
4. **C4 (the draft is only a draft).** The YAML must not contain `version` (the server assigns it), the id must match `StrategyIdFormat` and not exist (an existing id or a built-in id is `assistant.draft_id_taken` 409 at Confirm, the owner renames), at most 4 params, and the answer JSON has no field outside the schema (llama.cpp `json_schema` constrained output, then re-validated on our side).
5. **Decline path.** Given "buy when the quarterly result beats estimates and the news is positive" then the answer has `decline = true`, `unsupported[]` naming what the language lacks (events and news data are P15, `sector_rs` is not built, tick/depth is P13, options P14, fundamentals P15), no YAML, status `declined`; Confirm is not offered. A model answer with `decline = true` that also carries YAML is a repair reason `decline_with_yaml`. Declining an idea the language can express is not penalised here but is counted in the eval (P9-09 set C).
6. **The model has no write path (N1 to N8, tests).** `SubmitDraftHandler` and the job reference only the validator and the draft store; the chat model's drafting tools are exactly `lab_validate` (MCP) and `lab_propose_run` (local, draft rows only); `ConfirmDraftHandler` and `AutoDraftHandler` are the only types in `Assistant.Drafting` that reference `CreateStrategyCommand` and `StartLabRunCommand`; Confirm refuses (403 `assistant.owner_only`) any actor not beginning `owner:`, the auto handler runs only as `system:auto-draft` under criterion 13; a reflection/architecture test fails if another type references them. No code path stores, runs, clones, edits, activates or promotes without Confirm or the owner's auto setting.
7. **Confirm.** Given a `valid` draft (or an owner-edited text that validates) when `POST .../confirm` with `{ text?, universe: { basketId | symbols }, run: true, password }` then the handler re-validates the text actually sent (never the stored draft text), stores it with `CreateStrategyCommand(text, note, parentHash: null)` where `note = "Assistant draft <id>; confirmed by owner"`, starts `StartLabRunCommand(method: "quick", window: default)` when `run` is true, writes the decision row (`confirmed`, stored strategy id and version, lab run id, whether the text was edited) and returns both ids. `POST .../confirm` also carries `password` in the body: it needs the session, the CSRF token, **the fresh password on every call** (`StepUpCommand` with `Elevate:false`, the pattern of `AutonomyEndpoints`; a wrong password counts toward the lockout; the 5-minute step-up window is not used) **and** the capability `ai.settings.allow_draft_confirm` (false by default; else `409 assistant.capability_off`). Both are the owner's, set through `PUT /api/assistant/settings` (new optional body fields `allowDraftConfirm`, `autoLabQuickTest`, `allowProposalAccept`, `autoAcceptHypothesis`; absent means unchanged). A second Confirm of the same draft returns the first result and starts nothing.
8. **Window and universe are the owner's.** The idea's requested test ("2022 to today on MyChoice and Best stocks") is shown as `requestedTest` text only; the Confirm form defaults to the quick-test window of P5-02 and requires the owner to pick a basket (or symbols); baskets whose names the idea mentions are pre-selected only when the name matches exactly one basket of the owner's. A quick test is labelled exploration, not a verdict (P5-02 D6).
9. **Run summary (deterministic).** `GET .../{id}` returns, once the linked Lab run is `succeeded`, a `runSummary` built from `LabRunView`: state, instruments run and skipped, trades, open at end, the labels of the run verbatim (cost basis, sample, exploration), no win rate, expectancy or verdict (a quick test is not a verdict); for `failed`/`cancelled`/`interrupted` it says so with the run's located problems. No model text is involved.
10. **Limits.** One draft job at a time (the model is single-slot, ADR 0005); `Assistant:Drafts:MaxPerDay` (20) per India date: `429`-like `assistant.limit` 409; the idea is 10 to 2000 characters, plain text, no control characters (`assistant.invalid` 422); a draft job times out after 6 minutes (`status = failed`, reason `timeout`, nothing else changes). `Enabled = false` answers 409 `assistant.disabled`.
11. **Audit and storage.** `ai.strategy_drafts` stores the idea, every attempt (model JSON, YAML, problems, findings), model id and sha, prompt version and sheet hash, params, and is insert-only; `xd_app` has insert and select only on both tables (grants test). The log never contains the idea or YAML (ids, counts, codes, ms; 6170 to 6179). Provenance appears on the stored strategy only as the note.
12. Determinism: with a scripted drafter the same idea gives the same stored attempts; the sheet is byte-identical across runs and its hash is stored; the sheet contains every feature name of `IndicatorCatalog` (a test fails when a catalog name is missing, so a new indicator forces a sheet review) and both examples validate.
13. **Auto option (P9-00 D9; the owner's standing rule that anything needing approval can also run automatically, default OFF).** The setting `ai.settings.auto_lab_quick_test` is false by default, changed only through `PUT /api/assistant/settings` of P9-03 by the owner with the password in the body (optional body field `autoLabQuickTest`; absent means unchanged; a new insert-only `ai.settings` row; `snapshot_hash` by the trigger replaced in `AddAiWriteSwitches`). **Auto runs only for the dedicated drafting job on the owner's own typed idea:** the stored `idea` of such a draft is the text the owner posted to `POST /api/assistant/strategy-drafts`, copied verbatim by the server, and is never a model argument or output; drafts made through the chat tool `lab_propose_run` (`via = 'chat_tool'`) are **never** auto-confirmed, because stored text (basket names, lessons, instrument names, notes) can steer what a chat model submits. Also required: `Enabled` and `ai.settings.enabled`. When true, a draft that is `valid`, has no finding, whose idea names exactly one existing basket by exact name, and whose id is free, is stored and queued for a **quick** test as actor `system:auto-draft`; the decision row is `confirmed`, `auto = true`, with the `ai.settings.id` and `snapshot_hash`. At most 1 auto run per hour and 3 per India date (counted from decision rows); a draft that fails any condition, or whose basket cannot be resolved (`unavailable`), stays `valid` and waits for the owner: an unavailable input never counts as a pass. Auto never runs a full test, never edits a strategy and never touches an order path (none exists).

## Contract
- **API:** `POST /api/assistant/strategy-drafts` body `{ idea: string, basketId?: guid }` -> `202 DraftView` (the job runs in `xd-api`; poll `GET`, or the hub event `assistantDraftFinished {id, status}` UNVERIFIED if P9-03 offers a hub path; polling is the contract). `GET /api/assistant/strategy-drafts?limit=` (1 to 50), `GET .../{id}`. `POST .../{id}/confirm`, `POST .../{id}/discard`. Codes: `assistant.invalid` 422, `assistant.disabled` 409, `assistant.limit` 409, `assistant.busy` 409, `assistant.draft_not_found` 404, `assistant.draft_invalid` 422, `assistant.draft_id_taken` 409, `assistant.owner_only` 403, plus the Lab codes (`lab.invalid_strategy` with problems, `lab.not_found`, `lab.no_data`).
- **`DraftView`:** `id, status (drafting|valid|invalid|declined|failed|confirmed|discarded), idea, understood[], assumptions[{field,value,why}], notExpressed[{what,why}], unsupported[], requestedTest, yaml, problems[{path,span,code,message,severity}], findings[{code,detail}], attempts, modelId, promptVersion, confirmed?{strategyId,version,labRunId,edited}, runSummary?, createdAt`.
- **Model answer schema (grammar-constrained):** `{ decline: bool, unsupported: string[], understood: string[<=8], assumptions: [{field, value, why}] <=12, not_expressed: [{what, why}], requested_test: {from?, to?, baskets: string[]}, yaml: string|null }`.
- **Data:** `ai.strategy_drafts(id bigserial pk, idea text, status varchar(12), yaml text null, answer_json jsonb, attempts_json jsonb, problems_json jsonb, findings_json jsonb, model_id, model_sha256, prompt_version, sheet_hash char(64), params_json jsonb, requested_by varchar(64), created_at timestamptz)` (the row is written once, when the job ends; a job in progress is held in memory and in `ops` service state, UNVERIFIED; a crash loses it, which is stated); `ai.strategy_draft_decisions(id, draft_id fk restrict unique, decision varchar(10) check in ('confirmed','discarded'), strategy_id varchar(64) null, strategy_version int null, lab_run_id uuid null, edited bool, actor varchar(64), decided_at)`. Migration `AddStrategyDrafts` with `Down`.
- **Settings (config only):** `Assistant:Drafts:Enabled` false (also needs `ai.settings.enabled`); `MaxPerDay` 20; `MaxRepairs` 2 (0 to 3); `JobTimeoutSeconds` 360; `Seed` 1337.
- **Model request (dedicated job):** `ChatOptions` temperature 0, seed, `ResponseFormat` JSON with the schema above (llama.cpp `json_schema`/`response_format`, README 2026-10-24; M.E.AI mapping UNVERIFIED), max output 1800; thinking is the server's setting (P9-01); prompt at most 6000 tokens (sheet about 3000). Chat path: the same checks, the model's own tool call.
- **Registered prompt:** the draft system prompt and the sheet hash are registered in P9-03's `PromptRegistry` (which P9-09 reads) so a change makes the eval stale. Every model call of the dedicated job is recorded in `ai.model_calls` with purpose `draft`.

## Non-functional
The loop is at most 3 model calls (about 60 s each worst case at the benchmark's 41 tok/s for 1800 tokens plus reading 4K prompt tokens, so under 4 minutes; UNVERIFIED on the owner's machine). `validate` is 50 ms (P5-01 budget). The idea is user text and is put in the prompt inside a fenced block labelled data; it is never concatenated into the system prompt. Provider secrets: none involved. Everything the model returns is parsed as data; the YAML goes through the existing parser limits (64 KB, alias and anchor limits, P3-02c) before anything else.

## Decisions (researched)
**D1. Where the model's job ends.** *Answer:* it produces a text and a plain explanation; `validate` and the checks decide whether the text is offered; only the owner's Confirm stores or runs. *Reason:* doc 14 §1 "you confirm; tests decide", doc 11 §1 "you confirm", the library is immutable (ADR 0057), every stored version enters the Lab's trial ledger (multiple-testing tightening, ADR 0059), so a flood of stored guesses would harm the gates. *Rejected:* doc 14 §3's `lab_run(yaml)` tool for the model. **Design change: doc 14 §3 and §4**, already decided in P9-00 D9 (`lab_run` becomes the proposal tool `lab_propose_run`; "no write tools except `lab_run`" becomes "no write tools"); the ADR is written at build time (next free ADR number at build time).
**D2. Two entrances, one core.** *Answer:* the dedicated job calls validate itself and offers the model no tools, so the contract is "JSON in, JSON out" (this is what the eval measures); the chat path gives the model `lab_validate` and `lab_propose_run`, and both end in `SubmitDraftHandler`, so the checks are identical. *Reason:* removes tool-call parsing failures from the metric; the benchmark showed tool-call validity 10/10 but the draft is a single structured answer. *Rejected:* only the chat path (not reproducible for the eval). Hermes can call `lab_validate` but has no `lab_propose_run`, so it cannot create a draft.
**D3. Prompt sheet from code, not prose.** *Answer:* the grammar sheet is generated from `IndicatorCatalog` and constants (features with argument forms and defaults, the three-valued rule, the lag rule, stop kinds, exit policies the simulator runs, `time_rules` keys), plus two examples copied from `Seed/Strategies` (`VWAP_PULLBACK`, `BASE_BREAKOUT`), and lists the known gaps: BUY-to-SELL mirror not built (write `sell:`), one exit candidate only, `buffer_atr` not on swing stops, no `sector_rs`, no filters with data not stored. *Reason:* the doc 11 §2 example does not validate today (ADR 0057 honest limits); a hand-written sheet rots. *Rejected:* giving the whole JSON Schema (about 5K tokens, no examples).
**D4. Repair budget 2.** *Answer:* two repair turns with located problems only. *Reason:* each turn is about a minute; a third rarely fixes what two did not; the eval measures first-shot and repaired validity separately (P9-09). *Source:* P0-15 timings; Hermes PoC counts "8/10 valid" (doc 14 §6).
**D5. What "matches intent" means in code.** *Answer:* machine checks C3, C5, C6 plus the owner's reading of `understood[]` and `assumptions[]`; the owner's review is part of Confirm, not of the build. *Reason:* a human review of every draft cannot be a test; dropped numbers and false explanations are the failures that can be found by machine. *Rejected:* a second model grading the first (non-deterministic, circular).
**D6. Fresh password per Confirm plus a capability.** *Answer:* the password in the body on every call (`Elevate:false`, as the autonomy endpoint and P8-18/P8-19) and `allow_draft_confirm` (default false), one rule for every UI write that starts a job or changes research state. *Reason:* the safest option that still serves the goal; a click can store a strategy and start a CPU job; the Lab's trial ledger makes each stored variant cost future gate strictness. *Rejected:* the 5-minute step-up window (one elevation would cover many writes). *Source:* ADR 0091, brief rule for SAFETY items.
**D7. Provenance.** *Answer:* a note on the version, a link in `ai.strategy_draft_decisions`; the YAML carries nothing about the model. *Reason:* the file hash must depend on the strategy only (ADR 0055).
**D8. One variable and the hypothesis rule are not applied to drafts.** A draft is a new family, not a change to a tested one; one-variable discipline starts when the strategy exists (P9-08, P6-10).
**D9. Auto option.** *Answer:* one setting, `auto_lab_quick_test`, as P9-00 D9 names it, with the limits of criterion 13. *Reason:* the standing rule requires an auto path for anything with a manual approval, default OFF, owner-set, recorded as auto with the setting snapshot, `unavailable` never a pass; quick-only and 3 per day bound the cost to the Lab's ledger. *Rejected:* auto for full tests or edits of existing strategies (out of scope and far costlier).

## Risks and honest limits
- A valid text is not a good strategy: validation proves the language accepts it. The quick test is exploration on about a year and at most 30 symbols; the Lab's gates, walk-forward and robustness (P5-03 to P5-06) are what judge a strategy, and the screen says so beside the summary.
- Trying many drafts is a search; every confirmed version counts in the Lab ledger and tightens the gates, which is the intended brake. Discarded drafts are stored but not counted as variants (they were never run).
- Intent checks catch dropped numbers and false explanations, not a wrongly understood idea ("above VWAP" read as "below"). The `understood[]` list exists so the owner can see that.
- A model that declines too often or writes invalid text more than twice in ten is a model problem found by P9-09, not hidden here.
- Idea text is the owner's own; if pasted from the web it could carry hostile instructions. The model has no tools in this call, so the worst result is a bad draft the owner reads before Confirm.
