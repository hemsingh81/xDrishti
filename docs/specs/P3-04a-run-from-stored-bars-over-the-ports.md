# P3-04a — Run from stored bars over the ports: the use case, the engine port and the skip list

- **Status:** Approved (owner, 2026-10-18: "approve P3-03a and P3-04a"; the six decisions under *Open questions*, the size of 2.5 agent-days and *Changes to P3-04* stand as drafted). This is the second half of the first draft of P3-04, split on review on 2026-10-18: [P3-04](P3-04-run-from-stored-bars-window-independent-replay.md) (Approved) is the pure replay and the run record; this slice reads the bars, chooses the universe, decides the skips that need I/O and builds the record with that slice's functions. It is written from the section *Hand-over to P3-04a* of P3-04 (whose design was settled in its review) and from the list *Handed to P3-04 and P3-04a* of [P3-03b](P3-03b-fill-realism-gaps-slippage-ticks-and-minute-order.md); the names of the ports and records in this spec were read from the code on 2026-10-18, and the draft was changed after an independent review the same day (17 findings; see *Changes to P3-04*). Depends on P3-04 (and through it on [P3-03a](P3-03a-entry-scanner-simulator-and-orb-v1.md), P3-03 and P3-02b); P3-04b then depends on this slice and on P3-03b. Plan questions Q1 and Q2 reach this slice through P3-03; this slice has no question of its own that needs the owner (see *Open questions*).
- **Phase / roadmap row:** P3 — the event-driven simulator reads the stored bars. Build order: P3-03 → P3-03a → P3-04 → **P3-04a** → P3-04b (which also needs P3-03b). The exit check of the database half of the plan is this slice's.
- **Design refs:** docs/design/03-target-architecture.md §3–4 (layers; engine modules have no I/O), 05-data-and-brokers.md §3 (CSV import), §4.1 (the trading calendar), §4.2 (corporate actions; the owner's CSVs are adjusted at the source), §9 (storage), 06-instruments-and-baskets.md §3.3 (baskets as universes), §3.4 (dated membership), 10-trade-selection.md §1 (every candidate carries its basket), 11-strategy-lab.md §6 (reproducibility), 02-requirements.md NFR-3, NFR-4, NFR-7, the roadmap issues ISS-19 to ISS-22 · [ADR 0016](../adr/0016-market-bars-csv-load-dhan-fetch-and-app-managed-aggregates.md), [ADR 0017](../adr/0017-trading-calendar-eod-schedule-quality-adjustments-and-csv-undo.md) (§1 calendar, §5 adjustments), [ADR 0002](../adr/0002-config-and-strategies-in-app.md), the simulation ADR of P3-03 (expected 0037, with P3-04's amendment); `backend/CLAUDE.md` (one use case, one handler; every I/O behind a port)

## Goal
A strategy can be run, by one request, over the stored 1-minute bars of a set of instruments (an explicit list or a basket), and the answer is the complete run record of P3-04: what ran, what was skipped and why, every trade and every counter, and the key that identifies the run. The use case reads, in order and one instrument at a time, only through ports; applies the guard against adjusting a CSV-adjusted series twice; and never names a type of the engine. Nothing is written to any table. A run in which every instrument is skipped succeeds and says so.

## Scope
**In:**
1. **The use case** `RunSimulationHandler : IQueryHandler<RunSimulationQuery, Result<SimulationRun>>` (`internal sealed`, `XDrishti.Application/Research`, registered explicitly in `DependencyInjection.cs` in a new `AddResearch`), as `GetInstrumentBarsHandler(IBarQueries, IAdjustmentFactors)` is: one use case is one handler and every I/O is behind a port in `Abstractions/` (`backend/CLAUDE.md`). It validates the request, prepares the strategy, resolves the universe, and per instrument in order reads the bars, the adjustment factors and the corporate actions, applies the double-adjustment guard with `CsvAdjustment.AdjustsTwice` (internal to Application: the predicate of ADR 0017 §5), calls the engine port and assembles the record with `RunAssembler` (P3-04). It takes a `TimeProvider` only to time the phases for the log (D5); no time enters the record.
2. **The request** `SimulationRequest` (D1, its own file) and the query that wraps it; **the validation**, the refusals before any read, and the errors `simulation.invalid`, `simulation.strategy_invalid` and `simulation.basket_not_found`, added to `SimulationErrors` in `XDrishti.Domain.Research`, the one Domain class that also holds the `simulation.*` codes of P3-03, P3-03a and P3-03b (`slippage_invalid`, `fill_rules_invalid`, `tick_size_invalid`, `bars_not_ascending`, …): this slice declares only its own three and does not redeclare the others.
3. **The engine port** `ISimulationEngine` in `XDrishti.Application/Abstractions/Research` and its opaque handle `IPreparedStrategy` (an Application interface that exposes only `StrategyRecord` and the compile warnings): `EngineVersion`, `Prepare(strategyId, parameters, evaluationTimeframe, fills)` giving `Result<IPreparedStrategy>` with field errors that carry paths and codes, and `Replay(strategy, input)` giving P3-04's `InstrumentReplay`: pure, synchronous, over Domain values. Application cannot name `Simulator`, `PreparedStrategy` or any Simulation type, so everything the port's signatures use lives in `XDrishti.Domain` (`InstrumentReplayInput` moves there: see *Changes to P3-04*).
4. **Its adapter** `SimulationEngineAdapter` in `XDrishti.Infrastructure/Research` (`internal sealed`, no I/O, thin) over P3-04's `StrategyPreparation` and `InstrumentReplayer`. The **built-in strategy factory** (strategy id and parameters to `OrbV1`: `or_min`, `rr`; the registry of P3-04b reuses it) is `BuiltInStrategies` in `XDrishti.Simulation.Replay` (a documented namespace of P3-04), so the adapter names no type of `XDrishti.Strategies` except the problem record it maps to field errors. Infrastructure gets the one project reference to `XDrishti.Simulation`; Application and Domain get none. The adapter wraps the prepared strategy in a private `PreparedHandle : IPreparedStrategy`.
5. **The tick** (the request-side obligation of P3-03b): `BarsInstrument` (Application, `IBarQueries.cs`) gains `decimal? TickSize`, one more column of the row `FindInstrumentAsync` already reads (`id, canonical_symbol, name` of `market.instruments` today; the tick column is mapped by `InstrumentConfiguration`), added as a last parameter with the default `null` so that the callers and tests that build the record keep compiling; a basket member's `InstrumentSummary.TickSize` is used as it is, so there is no `IInstrumentQueries.GetAsync` per instrument. `TickSpec.FromMasterPaise` turns it into rupees; an instrument whose tick is invalid is skipped with `tick_size_invalid` and a note, and the run goes on (P3-03b types; see *Order with P3-03b*).
6. **The layering rule** "an engine module is reached from an adapter in Infrastructure, never from Application" as its own ADR (the next free number, expected 0039 after P3-03b's 0038; linked from `docs/adr/README.md`) and in doc 03 §4, which today draws the engine modules beside Infrastructure; an architecture test enforces it (AC12). It is not an amendment of the simulation ADR.
7. **Three log lines** (D5), tests at three levels (the handler with a fake engine; the adapter; the database half with Testcontainers), the **shared F-day builder** (a source file under `backend/tests/Shared/` that builds P3-03's invented days; `XDrishti.Simulation.Tests` creates it for P3-03 and the test projects of this slice link it with `<Compile Include=… Link=…>`; `XDrishti.Architecture.Tests` gains a project reference to `XDrishti.Simulation`) and the amendment of the simulation ADR for the decisions of D2 to D4.

**Out (not in this slice):**
- The `simulate` verb, `scripts/simulate.sh`, the built-in registry command line, the export (`trades.csv`, `run.json`), the trade cards and the banner (P3-04b). An HTTP endpoint, a job, a screen: the Lab (P5) and the scanner (P7) reuse the handler; none is built here, so there is no API change and no `scripts/gen-api.sh`.
- Any table or migration; the result store (`research.sim_runs`, `research.sim_trades`: P3-10). The run record is a value returned to the caller.

## Definitions (decisions the tests pin)
All dates are India dates. Names of the P3-04 values (`SimulationRun`, `InstrumentReplay`, `InstrumentReplayInput`, `ReplayOptions`, `RunHeader`, `RunAssembler`, `BarStreamHash`, `UniverseRecord`, `SkipReason`) are P3-04's; of the engine, P3-03a's and P3-03b's.

**D1 — The request.**
```csharp
// XDrishti.Application/Research  (the file holds the query record and the handler, as the feature folders do)
public sealed record SimulationRequest(
    string StrategyId,                                  // a built-in id ("ORB"); the built-in factory knows it
    IReadOnlyDictionary<string, double>? Parameters,    // null or empty: the strategy's defaults; names known to the factory
    string EvaluationTimeframe,                         // "5m" or "15m" for ORB (the code of Timeframe)
    DateOnly From, DateOnly To,                         // India dates, inclusive
    IReadOnlyList<Guid>? InstrumentIds,                 // exactly one of the two universes
    Guid? BasketId,
    bool AcknowledgeCsvAdjusted = false,
    ReplayOptions? Options = null,                      // null: ReplayOptions defaults (0.90 and 0.20)
    FillRulesInput? Fills = null);                      // P3-03b only; null: FillRules.Default
public sealed record FillRulesInput(double EntryLimitPercent, double Ticks, double BarRangeFrac, double StopExitExtraTicks);   // raw numbers: FillRules and SlippageConfig are valid by construction, so the handler builds them with Create and the invalid case can exist
public sealed record RunSimulationQuery(SimulationRequest Request) : IQuery<Result<SimulationRun>>;   // each public type in its own file
```
**Order of operations:** (1) validate the request, (2) build `FillRules` from `Fills` (P3-03b), (3) `engine.Prepare`, (4) only then read any port (the basket, the calendar, the bars). Validation (failures are `simulation.invalid` with a `FieldErrors` entry per field): `StrategyId` not empty; `EvaluationTimeframe` parses; `From ≤ To`, both in the years 2000 to 2099 (the importer's range: from 2000-01-01 up to but not including 2100-01-01, `CsvBarReader`); exactly one of `InstrumentIds` and `BasketId`; `InstrumentIds` has 1 to 2,000 ids, no repeats; every number in `Parameters`, `Options` and `Fills` is **finite** (NaN and ±Infinity are refused; a range test written with `<` or `>` lets NaN through, so finiteness is tested first); `Options` within P3-04's limits (completeness in (0, 1], threshold above 0). A `Fills` that `SlippageConfig.Create` or `FillRules.Create` refuses gives `simulation.slippage_invalid` or `simulation.fill_rules_invalid` (the codes of P3-03b, passed through) before any bar is read.

**D2 — The universe** (exactly one; the label is written in the record, P3-04's `UniverseRecord`).
- `InstrumentIds`: run **in the order given**, label `instruments as listed`. An id with no row is not a failure of the request: that instrument is skipped as `instrument_not_found`. An explicit list costs one `FindInstrumentAsync` and one factors query per id, accepted for at most 2,000 ids (the bar read dominates); revisited if the benchmark shows otherwise. The tick comes from the row `FindInstrumentAsync` returns (Scope 5).
- `BasketId`: a **manual**, **not archived** basket; its members **now**, `IBasketQueries.MembersAsync(basketId, null, null, ct)`, in the basket's order (`Position`), retired members and members without bars included; label `members as of today`: a basket is dated only from the day the owner built it (doc 06 §3.4) and the system has no historical index membership (ISS-22). A portfolio basket (not in `market.baskets`: `MembersAsync` returns null for it), an archived basket (`MembersAsync` returns its members, so the handler checks `ArchivedAt`) and an unknown id give `simulation.basket_not_found`. The tick is the member's `InstrumentSummary.TickSize`; the id of the basket goes into `RunTrade.BasketIds` of every trade (none for a list).
- A retired instrument that has stored bars is replayed: leaving it out would add survivorship bias.

**D3 — Reading one instrument** (one at a time, in universe order; a read never starts before the previous replay has finished). In this order:
1. `BarsInstrument` or the basket member gives the symbol and the tick. **No row** → the handler builds the instrument's record itself with a Domain factory `InstrumentRun.NotFound(id)` (skip `instrument_not_found`, symbol `?`, no data facts) and reads nothing for it.
2. `IBarStore.ReadAsync(id, from, to, ct)` with `from` = 2000-01-01 00:00 India time and `to` = 23:59 India time on `To`, **both converted with `ToUniversalTime()`** (Npgsql writes a `DateTimeOffset` to `timestamptz` only with offset 0 and throws for +05:30; `BarFixtures.Epoch` builds offset-330 values, which would fail here). Both bounds are inclusive in the store (`ts >= from AND ts <= to`, oldest first) and bars start on whole minutes, so 23:59 is the last minute of the day. The replay therefore starts at the instrument's **first stored session**, whatever `From` is (P3-04 Scope 3). An empty list is passed to the engine as it is: the replay decides `no_bars` (P3-04 Scope 8), the handler does not.
3. `IAdjustmentFactors.GetAsync(id)` gives the applied actions (the factors the replay applies to a copy). **The guard against adjusting twice**: `ICorporateActionQueries.ListCsvAdjustedThroughAsync` is asked **once for all ids of the run**; if any applied action that changes the bars read (`ActionsAfter(date of the first bar)`) has `CsvAdjustment.AdjustsTwice(exDate, through, id)` and `AcknowledgeCsvAdjusted` is false, the handler passes the instrument to the engine with `PresetSkip = csv_adjusted_twice`. The rule is the screens' own, conservative one (ADR 0017 §5): `exDate <= the date the loaded files reach`. Its known edges, written so that nobody is surprised: it also flags an action dated before the CSV start (harmless for the CSV bars, and right for any earlier Dhan bars); it flags a CSV range that Dhan bars have since overwritten (those bars are raw); and an instrument whose files predate the recorded range, or that has no loaded CSV, is **absent from the answer**, so the guard is silent for it. With the acknowledgement the run goes on and the record marks each such adjustment `OnCsvBars` (P3-04 Scope 5); the acknowledgement is part of the run key. A mixed-source instrument (Dhan bars and a CSV span) is covered by the same predicate because `ReadAsync` returns the merged series with no source per bar; a precise rule needs a CSV first-bar date from the port (`CsvFileMark.FirstBar` exists) and is not built here.
4. `ITradingCalendar.GetAsync` once per run, before the first instrument (the exceptions of the calendar are in the record).
5. `TickSpec.FromMasterPaise(tick)` (P3-03b): invalid → `PresetSkip = tick_size_invalid` with a note.
6. `engine.Replay(strategy, input)` (P3-04's `InstrumentReplayInput`, which this slice moves to Domain and gives two members, `PresetSkip` and `SkipDetail`; `Tick` is then absent when `PresetSkip` is `tick_size_invalid`). With a preset skip the replayer still classifies the sessions, hashes the bars and returns the record **without scanning**, so a skipped instrument that was read keeps its bars hash, session counts and notes. The result is an `InstrumentReplay` whose `Record` carries the skip.

**Skip precedence** (the first that applies; the same list as P3-04): `instrument_not_found` (handler), `no_bars` (replay: an empty list), `csv_adjusted_twice`, `tick_size_invalid` (preset by the handler, recorded by the replay after `no_bars`), then `no_runnable_sessions`, `no_sessions_in_window`, `features_not_ready` (replay). A run in which every instrument is skipped succeeds. The record is assembled with `RunAssembler.Assemble(header, replays)` in universe order; the run key is P3-04's. No time or random source enters the record: when and how long are logged (D5).

**D4 — Refusals before any read.** `engine.Prepare` runs once, after the validation and before any port is read (the basket, the calendar and the bars included): an unknown strategy id or an unknown parameter (the factory's closed list), a definition the compiler refuses, a plan that needs a market context or the expiry days, and everything `Simulator.Create` refuses by name (P3-03a AC11) give `simulation.strategy_invalid`, whose `FieldErrors` carry the path and the code of each problem, at most 20 (the rest counted in the message). Nothing is read from any port by a request that fails here or in D1. The compile warnings of a prepared strategy are exposed on `IPreparedStrategy.Warnings`, counted in the start log line and not stored in the record (the record of P3-04 has no field for them).

**D5 — Logging and failure.** Three `[LoggerMessage]` lines, in `Research/SimulationLog.cs`, event ids 4402 to 4404 (4401 is P3-03a's warm-up line; the highest id in `src` was 4324 when checked; `LogEventIdTests` keeps them unique): run started (strategy id, universe label and size, from, to), instrument skipped (symbol, reason), run finished (instruments run and skipped, trades, the times of the phases read, replay, assembly, measured with `TimeProvider.GetTimestamp()` and never stored in the record). Never prices, bars or strategy text. A run is not resumable: any unexpected exception ends it with no partial record; `OperationCanceledException` is not swallowed.

**D6 — The engine port and the adapter.**
```csharp
// XDrishti.Application/Abstractions/Research
public interface IPreparedStrategy { StrategyRecord Record { get; } IReadOnlyList<FieldError> Warnings { get; } }   // opaque; the adapter holds the prepared strategy behind it in a private wrapper
public interface ISimulationEngine
{
    string EngineVersion { get; }                                              // SimulationEngine.Version (P3-03)
    Result<IPreparedStrategy> Prepare(string strategyId, IReadOnlyDictionary<string, double> parameters, Timeframe evaluationTimeframe, FillRules? fills);   // field errors with paths and codes
    InstrumentReplay Replay(IPreparedStrategy strategy, InstrumentReplayInput input);   // pure, synchronous; caller errors throw (ArgumentException / InvalidOperationException, P3-04); a handle the adapter did not make throws ArgumentException
    // Prepare(string strategyId, …) takes a built-in id: until stored strategies exist (P3-02c, P3-02d) there is no text to give; the port changes then (StrategySpec with id, text and parameters), recorded in the simulation ADR
}
```
`SimulationEngineAdapter` maps `Prepare` to `BuiltInStrategies` and `StrategyPreparation.Prepare` (a located problem becomes a `FieldError` whose `Field` is the path and `Code` the code) and `Replay` to `InstrumentReplayer.Replay`; it holds no state and is registered as a singleton (stateless; the prepared strategy is per run, and no scoped service is injected into it). Infrastructure's `DependencyInjection.cs` registers it; the project file of Infrastructure gains `ProjectReference` to `XDrishti.Simulation`.

## Changes to P3-04
The review of this spec found that three points of the Approved P3-04 cannot be built together with this slice. They are proposed here and applied to the P3-04 spec (and its snapshot criteria 12 and 13) when this spec is Approved; they change no behaviour that P3-04 pins.
1. **`InstrumentReplayInput` moves to `XDrishti.Domain.Research`** (P3-04 puts it in `XDrishti.Simulation.Replay`). All its fields are Domain types (`Guid`, `string`, `IReadOnlyList<Bar>`, `AdjustmentFactors`, `DateOnly?`, `TradingCalendar`, `ReplayOptions`, `DateOnly`, and `TickSpec` from P3-03b), and the Application port must name it.
2. **A preset skip**: `InstrumentReplayInput` gains `SkipReason? PresetSkip` and `string? SkipDetail`. A non-empty list with a preset gives the record with sessions classified and the bars hashed and no scan; an empty list gives `no_bars` whatever the preset says. `Tick` is `TickSpec?`, absent only when `PresetSkip` is `tick_size_invalid`. The Domain gets the factory `InstrumentRun.NotFound(id)` for an id with no row.
3. **Years 2000 to 2099**, not 2000 to 2100 (the importer's range excludes 2100-01-01).

## Acceptance criteria
Numbered, each testable. The handler is tested in `XDrishti.Application.Tests` with a **fake** `ISimulationEngine` and fake ports (the existing `FakeBarStore` extended with a call log and a read that really awaits, so that overlap can be observed; `NSubstitute` for the queries); the adapter in `XDrishti.Infrastructure.Tests`; the database half in `XDrishti.Api.IntegrationTests` (the Testcontainers suite: `ApiFactory`, `DataTestBase`, `BarFixtures`; the handler is `internal`, reached through the container with `InternalsVisibleTo`, which that project already has).

**The request and the refusals**
1. **Validation.** Given each invalid request of D1 (empty strategy id, unparsable timeframe, `From` after `To`, a year outside 2000 to 2100, both universes, neither, 0 or 2,001 ids, a repeated id, options out of range, a NaN or infinite parameter, option or fill number, year 2100) when the handler runs then it returns `simulation.invalid` naming the field, and the fake store, the queries and the engine were not called.
2. **Refusals come before any read.** Given an unknown strategy id, an unknown parameter name, a strategy the compiler refuses, a plan that reads a context name, and an invalid `FillRulesInput` (P3-03b) when the handler runs then it returns `simulation.strategy_invalid` (with the path and code of each problem, at most 20), `simulation.slippage_invalid` or `simulation.fill_rules_invalid`, and no port was read (call counts 0, the basket, the calendar and the bars included: `Prepare` runs before the basket is resolved).

**The universe**
3. **Instruments as listed.** Given a list of three ids (one without a row) when the run is made then the instruments are replayed in the order given, the missing one is skipped as `instrument_not_found`, the label is `instruments as listed` and trades carry no basket id. **Baskets.** Given a manual basket of three members (one retired with bars, one without bars) then all three are in the run in the basket's order, the label is `members as of today`, `MembersAsync` was called with no cutoff and no date, and every trade carries the basket id; a portfolio basket, an archived basket and an unknown id give `simulation.basket_not_found`.
4. **The skip list.** Given instruments that exercise each reason (no row, an empty read, a double-adjustment, an invalid tick, and the three the replay decides, returned by the fake engine) when the run is made then each skip carries exactly its reason in the precedence of D3, the handler passes `PresetSkip` for the double-adjustment and the tick and an empty list for `no_bars`, a skipped instrument that was read keeps its bars hash and session counts (tested with the real replayer in AC13), the run succeeds, and a run in which every instrument is skipped succeeds with no trades.

**Reading and adjusting**
5. **The window of the read.** Given `From` 2026-03-03 and `To` 2026-03-05 when an instrument is read then `ReadAsync` was called with `from` = 2000-01-01 00:00 India time and `to` = 2026-03-05 23:59 India time, **both with offset 0** (asserted on the offset, not on equality of instants, which a fake would ignore), and the engine received all bars read. The same call against the Testcontainers database succeeds (AC13). A bar after `To` is the replayer's caller error (P3-04 Scope 3); the handler adds no check of its own.
6. **Adjusted once, in the database.** Given P3-04's criterion 8 scenario seeded in the Testcontainers database through the real ports (the F1 day on three days and an applied 1:2 split with ex-date after the last day) when the run is made then the trade has every price halved exactly once (entry 50.25, stop 49.00, exit 52.75, R +2.0), equal to a direct `Simulator.Run` on the halved bars; and given P3-04's criterion 7 scenario (a raw close of 100.00 on d1, a raw open of 50.05 on d2, an applied 1:2 split with ex-date d2) d2 is not flagged, while without the action it is. **Double adjustment.** Given a CSV-loaded series (`ListCsvAdjustedThroughAsync` reaching d3) and an applied action with ex-date d2 then the instrument is skipped as `csv_adjusted_twice` and keeps its session counts; with `AcknowledgeCsvAdjusted` it runs and the adjustment is marked `OnCsvBars`, and the run key differs between the two requests. A mixed-source instrument (Dhan bars up to d1, CSV from d2, an action with ex-date inside the CSV span) is skipped the same way; an instrument absent from the CSV answer is not skipped (the known edge of D3, pinned by a test so that a change of the rule is deliberate).
7. **The tick** (P3-03b types; waits for P3-03b). Given an instrument whose master tick is 5 paise, a missing tick (the fallback 0.05, flagged) and an invalid one (negative or above one rupee) when the run is made then the first two reach the engine as the `TickSpec` of P3-03b, the third is skipped as `tick_size_invalid` with a note and the next instrument runs; `FindInstrumentAsync` returns the tick in the same row (integration test), and a basket member's `InstrumentSummary.TickSize` is used as it is: an NSubstitute test asserts that `IInstrumentQueries.GetAsync` is never called.
8. **The record is the replay's.** Given two instruments (seeded F1 and F2 days in the database) when the run is made then `SimulationRun` equals what `RunAssembler.Assemble` gives for replays made by direct, independent calls of `InstrumentReplayer.Replay` over the bars the test reads from the database itself (compared by P3-04's canonical text), the bars hash of each instrument equals `BarStreamHash.Compute` of the stored list read twice, and after a merge that changes one close by one tick the hash and the run key change.

**Discipline**
9. **I/O discipline and cancellation.** Reads happen in universe order and never two at a time (the extended fake store records overlap, awaits inside `ReadAsync`, and the test fails if two reads are in flight); `IBarStore.BeginMergeAsync` is never called (the fake throws if it is); the calendar is read once per run; `ListCsvAdjustedThroughAsync` is called once for all ids; a token cancelled between two instruments ends the run with `OperationCanceledException` and no partial record; an exception thrown by the fake engine for one instrument ends the run (it is not turned into a skip). Memory is not asserted here: the replay's own bound is P3-04 criterion 16, and the handler holds one instrument's list at a time by construction (reviewed, not tested through the garbage collector).
10. **Logging.** A run writes exactly the three kinds of lines of D5 (one start, one per skip, one finish), none contains a price, a bar or a strategy text: the test asserts that the message templates and their arguments hold only ids, symbols, counts, reasons and milliseconds (argument types are checked, not only the rendered text); the phase times come from a `FakeTimeProvider`; and the event ids are unique (`LogEventIdTests`).

**Structure**

## Non-functional
- **Performance:** no budget is asserted. The bar read dominates: the owner's 214 files hold about 190,000 minutes each (40.9 million rows in all); reads are one instrument at a time and sequential on purpose (flat memory, a plain order). The explicit benchmark `Run_phases_for_seeded_universe` (a Testcontainers database with 20 seeded instruments of 2 years, not in `scripts/check.sh`) prints the time of the read, the replay and the assembly per instrument; the end-to-end figure on the owner's data is first measured by P3-04b and is UNVERIFIED until then.
- **Security and privacy:** the handler is internal, takes the owner's own instruments and baskets, reads, never writes; no secrets; logs carry counts, ids and times only; nothing is read from `data/` by the tests (invented series).
- **Determinism and fail closed:** the handler reads a clock only through `TimeProvider`, for the log; equal requests on equal stored data give equal records and the same run key; a failure ends the run, never a partial record (NFR-4, NFR-7); every expected condition is a skip with a reason.
- **Observability:** the skip reasons and the record are the user-facing explanation; the three log lines are the operational one.

## Open questions
None needs the owner: the design was settled in the review of P3-04 and the choices below are decisions of this draft, taken on research (the code read on 2026-10-18) and cheap to change before the build; the owner may revert any of them.
1. **The handler is in Application and the engine is behind a port** (D6), not the first draft's Infrastructure adapter named after the use case: it keeps the orchestration of every later consumer (P4 walk-forward, P5 Lab, P7 scanner) in Application and leaves the strategy factory with the adapter.
2. **A portfolio basket is not a universe in P3** (`simulation.basket_not_found`): its members are the owner's holdings now, not a research universe, and it has no dated membership. The alternative (accept it as "members as of today") is one more branch (`IPortfolioBasketSource`) and can be added when the Lab asks.
3. **An id with no row is a skip, not a request error** (`instrument_not_found`): a long list should not fail whole because of one stale id, and the skip is in the record.
4. **`csv_adjusted_twice` skips the instrument** unless the request carries the acknowledgement, the same consent as the corporate-action screens (`acknowledgeCsvAdjusted`, ADR 0017 §5), instead of failing the run or silently adjusting. The owner already acknowledged when applying such an action, and the run asks again: that is deliberate (a result computed on twice-adjusted prices must be a conscious choice), and a stored acknowledgement per action would be a change to the corporate-action screens.
5. **The port takes a built-in strategy id** (D6): stored strategies arrive with P3-02c and P3-02d, and the port then takes a spec with the text; recorded in the simulation ADR so nobody mistakes the id for the final shape.
6. **The size is 2.5 agent-days, not 1.5** (Size): the roadmap total of the exit path rises by one day.
