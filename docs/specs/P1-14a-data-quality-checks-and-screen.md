# P1-14a — Data quality checks and the Data quality screen

- **Status:** Approved (owner, 2026-10-12) · decision [ADR 0017](../adr/0017-trading-calendar-eod-schedule-quality-adjustments-and-csv-undo.md) §4 · design doc 05 §10, §10b · **Phase:** P1 — **P1-14** (official-daily comparison deferred) · depends on P1-11a, P1-12a
## Backend
1. Tables `market.quality_runs (id, trigger manual|daily|after_job, status, started/finished, sessions, instruments, passed/warned/failed, error)` and `market.quality_results (run_id, instrument_id, status pass|warning|fail, score 0–100, bars_checked, missing_minutes, checks jsonb)` + grants.
2. Checks (pure, unit-tested) over the last `Data:Quality:Sessions` (default 5) trading sessions of every tracked instrument with bars: **completeness** (expected minutes from the calendar; missing minutes listed; days marked `unfillable` in `bar_gaps` are warnings, not failures), **bar sanity** (low ≤ open/close ≤ high, positive prices, volume ≥ 0), **spikes** (move > k × median 1-minute move and > 1 %, k default 20, reversal rule), **aggregates vs 1-minute** (every stored 5m/10m/15m/30m/1h/1D/1W/1M bucket in the window recomputed with an independent implementation and compared exactly OHLC + volume + bar count; differences listed), **freshness** (calendar-aware), **official daily**: reported `notAvailable`. Status rules: any sanity/aggregate mismatch or freshness failure = fail; missing minutes above 1 % of expected or spikes = warning (thresholds in options). Score = weighted.
3. Runner: job-like background run (one at a time), `POST /api/data/quality/run {instrumentId?}` → 202; runs automatically after the scheduled EOD data job (wire the P1-12a hook) and after manual data jobs when requested; fix actions: `POST /api/data/quality/instruments/{id}/refetch` (starts a Dhan fetch of the instrument's gap days, then rebuilds its aggregates, then re-validates it) and `.../refresh-aggregates` (rebuild its window, re-validate).
4. Read API: `GET /api/data/quality/overview` (last run, counts, score, gate), `GET /api/data/quality/instruments?status&q&sort&page`, `GET /api/data/quality/instruments/{id}` (all checks, missing-minute list capped, stored-vs-recomputed rows with `differencesOnly`), `GET /api/data/quality/runs`, `GET /api/data/quality/gate` → `{ok, blocked, reasons[]}` (fail-closed: blocked when index data is missing is out of scope; blocked when > `Data:Quality:MaxFailedPercent` (default 5 %) of tracked instruments fail or the last run failed).
5. Tests: each check with fixtures (gap, bad bar, spike with and without reversal, a tampered aggregate, stale instrument, unfillable day), score/status rules, runner exclusivity, fix actions end-to-end, gate; integration; contract; docs 05 §10b; plan-data-1.js.
## Frontend (screen `/quality`, nav "Data quality")
Match the prototype's Data quality page in style, simple: header with **Run checks** (+ last run time/trigger), summary tiles (passed / warnings / failed, score, gate state), table of instruments (status chip with icon + text, score, coverage, bars checked, missing minutes, per-timeframe aggregate status, source) with search/status filter/sort/paging, **Inspect** drawer (each check with its result, missing minutes, stored-vs-recomputed table with a "differences only" toggle, small 1-minute sparkline only if cheap else skip) with **Re-fetch** and **Refresh aggregates** buttons that run and re-validate, run history list. Pending suggested corporate actions (P1-10a) show an alert row when that exists (leave the slot). Tests (stateful fake), a11y, responsive, lazy chunk.
