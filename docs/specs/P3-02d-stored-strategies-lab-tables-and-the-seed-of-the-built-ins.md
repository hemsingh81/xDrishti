## Goal
Strategies live in the database, as the owner's design says: each version is stored once, whole and unchangeable, with its text and content hash; the three built-ins (`ORB`, `VWAP_PULLBACK`, `BASE_BREAKOUT`) are written there on first start from embedded text; and the simulator and the verbs can run a stored strategy by id and version (or hash) exactly as they run a built-in today. Nothing about a simulation rule changes.

## What the code does today (read 2026-10-22)
- **No `lab` tables.** The `lab` schema is named in doc 03 §6 and doc 11 §6 and has no migration (UNVERIFIED by a search of `XDrishti.Infrastructure/Persistence/Migrations`; the latest migration there is `AddSimComparisons`, `20261022055710`). The nearest model is `research.sim_runs` / `sim_trades` (`AddResearchResultStore`, 2026-10-19): `GrantSchemaUsageToAppRole("research")` then `MakeAppendOnlyForAppRole(schema, table)` (`MigrationBuilderExtensions`: grants all DML on the schema's tables, then revokes UPDATE/DELETE), with a grants test as `xd_app`.
- **The built-ins are C# builders** reached by id: `BuiltInStrategies.Build(id, parameters)` looks the id up in a private table, checks parameter names and ranges (`simulation.unknown_strategy`, `unknown_parameter`, `parameter_out_of_range`), fills defaults and calls `OrbV1.Create`, `VwapPullback.Create`, `BaseBreakoutV1.Create`; `BuiltInStrategies.Prepare(id, parameters, timeframe, fills, exits)` then calls `StrategyPreparation.Prepare` (one strategy or, with two exit candidates, `PrepareComparison`) and builds the `StrategyRecord` (id, effective parameters sorted by name, canonical JSON, SHA-256, timeframe, sides). The verb parameter `rr` is **not** a parameter of the model: each builder writes `rr` as a literal in its `FIXED_RR` exit; only the factory knows it.
- **The port:** `ISimulationEngine` (Application) has `BuiltIns` (a list of `BuiltInStrategyInfo`) and `Prepare(string strategyId, IReadOnlyDictionary<string,double> parameters, Timeframe evaluationTimeframe, FillRules? fills, ExitChoice? exits = null) → Result<IPreparedStrategy>`; `SimulationEngineAdapter` (Infrastructure/Research) implements it over `BuiltInStrategies`. Its own comment says the `BuiltIns` list "becomes" the stored strategies when they exist. The architecture rule (ADR 0039) is that Application never names an engine type.
- **The run record** (`StrategyRecord`) already carries the strategy id, the effective parameters, the canonical JSON and its SHA-256; the hash is part of the run key. It carries no "version" number.
- `Simulator.Create(definition, timeframe, fills)` takes any `StrategyDefinition`; it does not know where the definition came from.

## Definitions

**D1. `lab.strategies`** (one row per family; written once). `id text PRIMARY KEY` (check `~ '^[A-Za-z][A-Za-z0-9_]{0,63}$'`, the model's rule), `style text NOT NULL` (`intraday`/`swing`, copied from the first version for listing), `built_in boolean NOT NULL`, `created_at timestamptz NOT NULL`. No `latest_version` column: it would have to be updated; the latest is `max(version)`.

**D2. `lab.strategy_versions`** (one row per version; written once). `strategy_id text NOT NULL REFERENCES lab.strategies(id)`, `version integer NOT NULL CHECK (version >= 1)`, `schema_version smallint NOT NULL` (the model's schema, 1), `hash char(64) NOT NULL UNIQUE CHECK (hash ~ '^[0-9a-f]{64}$')`, `source_text text NOT NULL CHECK (octet_length(source_text) <= 262144)` (what the owner posted or the seed resource, byte for byte, comments included), `canonical_json text NOT NULL` (P3-02c D8; **`text`, not `jsonb`**, so the bytes that were hashed are the bytes kept, ADR 0045 D1), `parent_hash char(64) NULL REFERENCES lab.strategy_versions(hash)`, `note text NULL` (≤ 500), `created_at timestamptz NOT NULL`; `PRIMARY KEY (strategy_id, version)`. The unique hash gives "the same content is one row": P5-01 criterion 3's idempotence is a lookup by hash. The id is inside the hash, so a hash belongs to one family. Index: the unique hash, and the primary key (list a family's versions in order).

**D3. The migration** `AddLabStrategies`: creates schema `lab` if absent, the two tables with `Down` (drops the tables and, only if empty, the schema, without CASCADE: a later table in `lab` makes it fail and remove nothing, as `AddResearchResultStore` does), `GrantSchemaUsageToAppRole("lab")` then `MakeAppendOnlyForAppRole("lab", "strategies")` and `("lab", "strategy_versions")`; a later migration that adds `lab.*` tables must re-apply the append-only call to these two (as `MigrationBuilderExtensions` already warns). `xd_app` can SELECT and INSERT, nothing else. No trigger is needed; the grants are the guard (a superuser/owner role used by the migrator can still change rows and that is not a runtime path).

**D4. The store port.** `IStrategyStore` in `XDrishti.Application/Abstractions` (UNVERIFIED namespace), over plain records that name no engine type: `StoredStrategy(Id, Style, BuiltIn, CreatedAt, LatestVersion, VersionCount)`, `StoredVersion(StrategyId, Version, SchemaVersion, Hash, SourceText, CanonicalJson, ParentHash, Note, CreatedAt)`.
- `ListAsync(ct)`; `GetAsync(id)`; `GetVersionAsync(id, version | latest)`; `GetByHashAsync(hash)`.
- `AppendAsync(NewVersion, ct) → AppendResult(Version, Created: bool)` where `NewVersion(StrategyId, Style, SourceText, CanonicalJson, Hash, ParentHash?, Note?, ExpectedVersion?, BuiltIn)`. Semantics, one transaction: if a row with this hash exists, return it (`Created = false`, nothing written, including when `ExpectedVersion` differs: the content already has its number); otherwise create the family if the id is new (`BuiltIn` is taken **only** at family creation), compute `next = max(version) + 1` (1 for a new family), if `ExpectedVersion` is set and ≠ `next` return the conflict `VersionExists`/`VersionGap` (P5-01 maps it to `409 lab.version_exists`), insert. A concurrent insert of the same `(id, next)` or the same hash is a unique violation, which the store catches and turns into a re-read (same hash) or a retry once (same version): no lock, no advisory lock, no serialisable isolation needed for a single owner (UNVERIFIED against the project's DbContext conventions).
- `AppendAsync` **does not validate**: the caller hands over text, canonical text and hash it obtained from the file package. The store recomputes nothing and trusts nothing it cannot cheaply check: it checks `hash = SHA-256(canonical_json)` (a one-line integrity check that needs no engine) and the sizes, and refuses a mismatch with `StoreError.IntegrityFailure`. A user append to a family with `built_in = true` is refused here as `BuiltInReadOnly` (the rule lives in the store so no endpoint can forget it); the seeder appends with an `AllowBuiltIn` flag.
- Reads are `AsNoTracking`, ordered, paged (the library is small: tens of rows; no paging until needed, UNVERIFIED).

**D5. The seed.** Three embedded resources in `XDrishti.Infrastructure` (`Seed/Strategies/ORB.yaml`, `VWAP_PULLBACK.yaml`, `BASE_BREAKOUT.yaml`; the layout of ADR 0002's "embedded seed resources"), each a strategy file of P3-02c with `id`, the same sections as the builder and **the builder's default parameters**. A `StrategySeeder` runs at start, after the migrations, in the same place the other first-start seeds run (UNVERIFIED which host applies migrations; one place, not both host and worker): for each resource it reads the text with the file package, compiles every declared side on every declared timeframe with `StrategyCompiler` (any error or `exit_not_evaluated` warning for a policy that is not run is logged and **that resource is not stored**: a bad seed must be loud, not silent), and calls `AppendAsync(builtIn: true)`. Idempotent by hash: a restart changes nothing. If a later release ships a different text for the same id, the new text becomes version `n+1` with `parent_hash` the previous latest (the old version stays, because runs point at it); a user cannot create a family named like a built-in (the id exists). The seeder logs `lab.seed.strategy` with id, version, hash, created yes/no, never the text.

**D6. Seed equals builder.** For each built-in, `Read(seedText).Definition` **equals** (record value equality) the builder's `Create(defaults)`, and `StrategyHash` equals the hash `StrategyPreparation` writes today. This makes the seed provably the same strategy as the one every stored run already names. Two consequences:
- The builders stay in the code **as the test oracle** and for the equality test; they stop being the runtime source (D7).
- `rr` is a verb parameter of the factory, not a model parameter. A stored strategy takes overrides only for its **declared** params. So a stored `ORB` cannot be run with `--param rr=3` unless `rr` is declared. Two ways (question 1): **(A, recommended)** declare `rr` in the three seeds and change the three builders to declare it too and write `rr: [rr]` in the exit (`Quantity.Named("rr")`); this keeps D6 true, makes the effective parameters (which already contain `rr`, because the factory returns them) a model fact, and changes the canonical text and hash of each built-in **once**, recorded in the ADR (old stored runs keep their keys; runs after the change get new keys; the run record's `schema` is untouched). It needs `ORB` 2, `VWAP_PULLBACK` 2 and `BASE_BREAKOUT` 4 params (≤ 4, the model's limit; `BASE_BREAKOUT` is at the limit) and UNVERIFIED that the compile resolves a named `Quantity` inside an exit list (the model says any number field may). **(B)** keep `rr` literal in the seed, and make `--param rr=…` a refusal for a stored strategy and the way to change the target the `--exit FIXED_RR:rr=…` flag of P4-05, which already replaces the exit of a built-in; nothing changes in the hashes, and a verb that used `--param rr` must be changed.

**D7. Loading a stored strategy for a run.** In Application, a handler that runs a simulation resolves a **strategy reference** before it calls the engine: `StrategyRef = BuiltInId(string)` (today's) `| Stored(id, version?)` `| StoredHash(hash)`; a bare id on a verb is resolved **in the store first** (the latest version of that id), so `--strategy ORB` keeps working and now means "the stored `ORB`, latest". The handler gets a `StoredVersion` from `IStrategyStore` and calls a new method of the port:

`Result<IPreparedStrategy> PrepareStored(string sourceText, string expectedHash, IReadOnlyDictionary<string,double> parameters, Timeframe evaluationTimeframe, FillRules? fills, ExitChoice? exits = null)`

implemented in `SimulationEngineAdapter`: read the text with the file package (cached in memory **by hash**, which is safe because a version is immutable), check `hash(canonical(definition)) == expectedHash` (a mismatch is `strategy_store.hash_mismatch`, the store row or the reader is wrong, never run), substitute the given parameter values for the declared ones (names not declared are `simulation.unknown_parameter`, values judged by the compile as for any strategy; the located problem paths of the compile pass through unchanged), apply `ExitChoices.With` when `exits` is given, and call `StrategyPreparation.Prepare` / `PrepareComparison`, so the run record is **built exactly as for a built-in** and carries the same fields. The old `Prepare(string strategyId, …)` stays for the built-in path used by tests and the oracle (not removed in this slice; question 2). The adapter reads the text and reaches the engine; Application sees only strings and numbers (ADR 0039).

**D8. The catalogue and the verbs.** `ISimulationEngine.BuiltIns` stays for the C# table; a new read, `IStrategyStore.ListAsync` joined with a new engine call `Describe(sourceText)` (`id, style, timeframes, params with defaults, sides`) gives what `simulate --list` and `verify-pack` print for built-ins today (ranges are no longer printed for stored strategies: they live in the compile; the factory's `Min`/`Max` for a built-in stay in the C# table for the old path, UNVERIFIED which verbs print them). Verb flags (UNVERIFIED against `Program`/`SimulateVerb`; names for the owner): `--strategy <id>` (stored, latest), `--strategy-version <n>` with it, `--strategy-hash <64 hex>` instead of `--strategy` (a version by content), `--param name=value` as today. The run is stored and exported with the strategy hash in its record and in its run id, as now; the version number is **not** put in the run record or the key (no schema bump of the record, the key or the export format): a run names its version by its hash, and `lab.strategy_versions.hash` is unique, so `GetByHashAsync` finds the version number later. P5-02's run key uses the hash for the same reason.

## Acceptance criteria
1. Given a clean database, when the migrations run, then `lab.strategies` and `lab.strategy_versions` exist with the constraints of D1/D2; `Down` removes both; a second migration in `lab` (a test table) makes the schema drop fail without removing anything.
2. Given a connection as `xd_app`, then SELECT and INSERT on both tables succeed and UPDATE and DELETE are refused with SQLSTATE `42501` (a grants test in the integration project, as for `research`); an insert with a malformed hash, a version 0, an id with a space, or a `parent_hash` that exists nowhere is refused by a constraint.
3. Given a clean database, when the seeder runs, then three families exist (`built_in = true`), each with version 1, `parent_hash` null, a text that reads and compiles with no error on every declared side and timeframe; when it runs again, then no row is written (the counts and the `created_at` values are unchanged).
4. Given each seeded text, then the definition it reads equals the builder's `Create(defaults)` and its hash equals the hash of the run record that `BuiltInStrategies.Prepare` produces for the same defaults (D6); under option A the three hashes are the new pinned ones and the old ones are listed in the ADR.
5. Given a changed built-in text (a test seed) for an existing id, when the seeder runs, then version 2 is stored with `parent_hash` of version 1, and version 1 is unchanged.
6. Given `AppendAsync` of a new family, then version 1; of a changed text for it, then version 2 with the previous hash as parent; of the same hash again, then the same row and `Created = false`; with `ExpectedVersion` ≠ next, then a conflict and no row; for a `built_in` family without `AllowBuiltIn`, then `BuiltInReadOnly`; with `hash ≠ SHA-256(canonical_json)`, then `IntegrityFailure`.
7. Given 8 concurrent appends of the same new text, then one row exists and all 8 return the same version; given 8 concurrent appends of 8 different texts to one family, then versions 1 to 8 exist once each, with no gap.
8. Given `simulate` on a small fixture window with `--strategy ORB` (stored, latest), then its trades, run record and run key are **identical** to a run through the old built-in path (option A: compared after the same hash change on both paths; option B: byte-identical to the run before this slice); the same for `VWAP_PULLBACK` and `BASE_BREAKOUT`.
9. Given `--strategy-hash` of a stored version, `--strategy ORB --strategy-version 1`, and an unknown id/version/hash, then the first two run the same strategy and the third is a located refusal naming what exists (`simulation.unknown_strategy` with the stored ids, or the new code for a version/hash; UNVERIFIED code names).
10. Given a stored version whose `source_text` is tampered with in a test database by the owner role, when loaded, then the run is refused with `strategy_store.hash_mismatch` and nothing runs; given a reader that changes how an old text reads (simulated), the same.
11. Given a stored custom strategy (a test text with a `swing_lookback` param), when run with `--param swing_lookback=7`, then the value is substituted, the effective parameters are in the record, and the run key changes with it; `--param nonexistent=1` is `simulation.unknown_parameter`.
12. Given the architecture tests, then Application references no engine or file-package type, only `IStrategyStore`, its records and the `PrepareStored` signature of plain types; the seeder and the adapter are in Infrastructure.

## Contract
- **API:** none. P5-01 adds the endpoints over `IStrategyStore` (the codes `lab.not_found`, `lab.version_exists`, `lab.builtin_readonly` map from D4's results).
- **Data:** schema `lab`; `lab.strategies`, `lab.strategy_versions` as D1 to D3; migration `AddLabStrategies` with `Down`; insert-only for `xd_app`. Row size: a source text ≤ 256 KiB; the 3 seeds and a library of hundreds of versions are small (UNVERIFIED, tens of KiB each at most).
- **Library:** `IStrategyStore` (Application), `StrategyStore` and `StrategySeeder` (Infrastructure), `ISimulationEngine.PrepareStored` and `Describe`, the embedded resources.
- **Jobs:** the seeder at start only; failure to seed one strategy is logged at error level and surfaced by the existing health check if one exists (UNVERIFIED), and does not stop the host.

## Non-functional
Security: the store takes text from callers that have already been through the limits of P3-02c; it keeps a size check of its own; no text in logs, only id, version and hash. Performance: a version read by id is one primary-key lookup; the parsed definition is cached by hash (an immutable key), so a Lab run or a verb pays the parse once per process; the cache is bounded (e.g. 256 entries, UNVERIFIED). Determinism: a stored strategy gives the same run record as the same text read again. Observability: `lab.seed.strategy`, `lab.store.appended` (id, version, hash, created), `lab.store.hash_mismatch`.

## Test plan
Unit: the append rules of D4 over an in-memory fake; the seeder with a fake store (idempotent, bad seed not stored, new text becomes the next version); the adapter's `PrepareStored` (parameter substitution, unknown parameter, hash mismatch, cache by hash); the equality test of D6 for the three. Integration (Testcontainers, Postgres): migration up/down, the constraint cases, the grants test as `xd_app`, the concurrency cases of 7, the seed on a clean database and twice, `simulate` through the verb host on the fixture bars for all three built-ins (criterion 8, comparing the record and the key with the old path), a tampered row (criterion 10). Architecture: criterion 12. Edge cases: an id differing only in case from a built-in (`orb`: the check is case-sensitive but the store refuses a case-insensitive clash, UNVERIFIED if the owner wants that), a very long note, a unicode id (refused by the pattern), a parent hash from another family (allowed: a clone across families is a lineage, P5-01 "clone with a parent").

## Open questions (for the owner; each with a recommendation)
1. **`rr` in the model (D6).** (A) declare `rr` as a param in the three seeds and builders, which changes each built-in's hash once; or (B) keep `rr` literal and use `--exit FIXED_RR:rr=…` for the target? Recommended: A. It makes the parameters a stored strategy takes the same as the parameters of its run record, and the one-time re-key costs nothing (old runs are insert-only and keep their keys); B leaves a hidden verb-only parameter that no stored text can show.
2. **Remove the C# builders from the runtime path now?** Recommended: not in this slice. Keep `BuiltInStrategies.Prepare` for tests and the oracle, route verbs through the store, and delete the factory's runtime role in a follow-up once P5-02 has run on stored strategies. The risk of removing it at once is a wide change to P3/P4 tests for no new capability.
3. **A bad seed.** Log and skip that strategy (recommended), or fail the start? Recommended: log at error, skip, and let the run of that id fail with "unknown strategy"; a bad embedded text is a build error that the equality test (criterion 4) already catches before release.
4. **Built-in text changes in a release.** New text becomes the next version, the old one stays (recommended), or the built-ins are frozen at version 1 until the owner says? Recommended: next version; the run keys of old runs point at old hashes and stay valid.
5. **What a bare `--strategy ORB` means.** The latest stored version (recommended; the same as today for a built-in) or the explicit version required? Recommended: latest, and print the version and hash on the console first line so the run is never ambiguous.
6. **Case-insensitive id clash** (`orb` next to `ORB`)? Recommended: refuse in the store (a unique index on `lower(id)`), so the library has no two names that look the same.
7. **Version in the run record.** Leave it out (recommended; the hash names the version and finds it) or add `strategy_version` to the record (a record-schema bump and a new export format)? Recommended: leave out for now; add with the Lab run record of P5-02 if that page needs it, and then once.
8. **Order.** P3-02c first, then this slice, then P5-01 and P5-02 (P5-00 question 1). Recommended: yes.
