# P9-08 — Hypothesis and suggestion proposals (the model proposes, the engine checks, the owner decides)

- **Status:** Draft (written 2026-10-24; decisions below were researched under the owner's delegation; the owner's Approved is still needed before an agent builds it)
- **Phase / roadmap row:** P9 — AI assistant and Hermes PoC ("hypothesis proposals", doc 14 §4 feature 4 and the suggestions row of §1); slice of [P9-00](P9-00-ai-assistant-plan.md) (written in parallel; UNVERIFIED text).
- **Design refs:** docs/design/14-ai-assistant.md §1 (rows "Propose hypotheses", "Suggest instruments / basket changes / next-day focus"), §3 · docs/design/09-learning-engine.md §5 (hypothesis loop), §6 (guards) · docs/design/04-accounts-access-and-operations.md §4.1, §4.3 (suggestions inbox) · P6-10 / ADR 0076 (hypotheses) · P7-09 / ADR 0092 (plan suggestions) · ADR 0072 (trials) · P8-00 D1, D3.
- **Needs:** P9-07 (its migration `AddAiWriteSwitches` adds the `ai.settings` columns used here), P9-01 (`IChatClient`), P9-03 (schema `ai`, settings endpoint, call audit), P9-06 (`TextGuard`), P6-10 (built), P8-06 (reports reads; optional, kinds that need it say `unavailable`). Used by: P9-09 (the proposal checks are part of set B's harness tests).
- **Size:** 3.5 agent-days (pure checks and bounds 0.8, pack builder + job 0.8, inbox store + migrations + accept handlers 0.8, auto option 0.4, endpoints + panel + tests 0.7). Cut order if over: auto option for the basket kinds, `basket_remove`, then `next_day_focus`.
- **Safety:** **yes.** Accept/Reject are owner writes from the UI; accepting changes a basket or writes a hypothesis (it never tracks an instrument or starts a backfill, AC 5). The model writes only inbox rows. Default OFF: `Assistant:Proposals:Enabled` false, and Accept needs the capability `ai.settings.allow_proposal_accept` (false).

## Goal
Once a week (or on the owner's command) the local model reads an evidence pack that the engine selected, and may propose up to three things: a one-knob hypothesis for a cell, a basket change, or a next-day focus. The engine re-derives every piece of evidence itself and runs every rule check; only proposals that pass land in a suggestions inbox with a reason, evidence and an expiry. Nothing happens until the owner presses Accept, and Accept does what the owner could already do by hand, and for a hypothesis passes the same checks as the verb `xd learn hypothesis propose` (P8-19 keeps proposing a hypothesis verb-only; Accept is the UI path).

## Acceptance criteria
1. **Pack.** Given stored runs and cells, when the pack is built then it holds (a) the triggers of `EvaluateHypothesisTriggersHandler` (cells with at least `min_new_trades_per_cell` new trades; drift pause proposals) since the last proposal run, capped at 5 cells, ordered by new-trade count then cell key; (b) for each cell the cell statistics (n, expectancy, credible lower bound, state) read from the stored snapshot, the newest stored baseline run key for the cell's strategy and universe, its stored parameter names and values, and the grid values per parameter (`GridHypothesesHandler`); (c) the open hypothesis count and the cells already open; (d) the report insights (P8-06) with their `n`, or `unavailable`. (e) **basket candidates**: for each of the owner's manual baskets (at most 5) its members with stored-run `n` and credible lower bound by instrument (the 10 weakest with `n >= 15`, for `basket_remove`) and tracked instruments that are in no manual basket with `n >= 15` (the 10 strongest by lower bound, for `basket_add`), each from the report engine, or `unavailable` when P8-06 is not built. The pack is data: no owner-typed text. Same inputs give the same pack bytes and `pack_hash`.
2. **Model output** is grammar-constrained JSON: at most 3 items, each `{kind, subject, payload, reason (<= 400 chars), evidenceRefs[]}`, where `evidenceRefs` are references into the pack (`cell:<key>`, `run:<key>`, `insight:<id>`, `instrument:<symbol>`); the model supplies no evidence figures.
3. **Evidence is the engine's.** For every item the engine re-reads each reference through the same read handlers (not from the pack text) and builds `ProposalEvidence` (basis, population run keys, date range, n, figures with states, limits strings per P8-00 D1); a reference that does not resolve rejects the item (`evidence_unresolved`). The `reason` must pass `TextGuard` with facts = the evidence figures (numbers, symbols), else `reason_number_not_in_evidence`.
4. **Hypothesis checks.** payload `{baselineRunKey, cellKey?, knob: {name, kind: Parameter, baselineValue, candidateValue}}`. Accepted only if: the baseline run exists and `OneVariableRule.BaselineProblems` is empty (the knob names a parameter of that run at its stored value); the candidate has the same sign, differs, is within +/- 50 % of the baseline (`KnobBounds`), and has at most 6 significant digits; the cited cell has `n >= min_trades` (30) from the stored snapshot else `evidence_insufficient`; fewer than 3 hypotheses are open and fewer than 3 hypothesis proposals are pending; no other pending or open item has the same cell and knob. `kind` Exit or Slippage is refused with `knob_kind_not_supported`.
5. **Basket checks (no instrument-tracking kind).** `basket_add {basketId, symbol}`: the basket is the owner's manual basket and not archived, the instrument is already tracked (so no backfill can follow), is not a member, and has `n >= 15` trades in stored runs (evidence: n and credible lower bound by instrument from the report engine, else `unavailable` and refused). `basket_remove {basketId, symbol}`: a member, and the evidence holds the instrument's trades from stored runs with `n >= 15` (the insight minimum) else `evidence_insufficient`. A system (portfolio) basket is `basket_system` refused. `track_instrument` is **not a kind in this slice**: the pack has no source of untracked candidates (the master list is not scored), so there would be no engine evidence, and tracking starts a Dhan history backfill, which this slice never does; the owner tracks by hand in Instruments (design gap noted for the index). Every figure the reason uses must come from engine evidence; a reason such as "strong RS" with no figure is allowed only as plain words that contain no number and no claim word from `ProposalWording.ClaimWords` (`strong`, `best`, `outperform`, `momentum`, `breakout`) unless an evidence figure of that kind is present.
6. **Next-day focus.** payload `{planDate, prefer: swing|intraday}` is accepted only if the report insight on style (P8-05 "best exit and style") exists with both groups at `n >= 15`, favours that style, and the plan date is the next session; else `focus_not_supported`. It has no effect on any plan; the plan review shows it as text.
7. **Dedupe and the repeat block.** The key is SHA-256 over kind, subject and the payload's identity fields (cell + knob name + candidate value; symbol + basket). A key rejected by the owner within `RepeatBlockDays` (30) is not proposed again (`repeat_blocked`); an expired one may be; an identical pending one is not duplicated; one row per (key, India date) by unique index.
8. **Limits.** At most 3 items accepted per run, at most 10 pending in total, at most 3 pending hypotheses; expiry: hypothesis 7 days, basket 3 days, focus the end of the plan date (India time). Expiry is computed on read (`pending` with `expires_at <= now` is `expired`), nothing is updated.
9. **Accept (owner only).** `POST .../{id}/accept {password}` needs the session, the CSRF token, the **fresh password in the body on every call** (verified through `StepUpCommand` with `Elevate:false`, as `AutonomyEndpoints`; a wrong password counts toward the lockout; the 5-minute step-up window is not used) **and** the capability `ai.settings.allow_proposal_accept` (false by default; else `409 assistant.capability_off`); the actor is `owner:<email>`; a non-pending proposal is `409 assistant.proposal_closed`. Hypothesis: re-runs the engine checks against today's data (the world may have changed: `assistant.proposal_stale` 409 with the failing code), then calls `ProposeHypothesisHandler` with `HypothesisSource.Assistant`, the baseline run key, the knob and `Rationale = "Assistant proposal #<id>: " + reason` (clipped to 500); the new hypothesis is `proposed` and still needs the owner's approve, start and judge (P6-10) - accepting does not approve, start or apply anything. Basket: `AddBasketMembersCommand` or `RemoveBasketMembersCommand` (no tracking, no backfill, no broker call). Focus: records the decision only. The decision row stores the result reference (hypothesis id, none for the others).
10. **Reject** (reason optional, 300 chars) records the decision and starts the repeat block. Neither accept nor reject can be repeated; a double click returns the first result.
10a. **Auto option (owner's standing rule; default OFF).** `ai.settings.auto_accept_hypothesis` (bool, default false; added by P9-07's `AddAiWriteSwitches`; changed only through `PUT /api/assistant/settings` of P9-03 by the owner with the password in the body; the optional body fields `autoAcceptHypothesis` and `allowProposalAccept` are added here, absent means unchanged; a new insert-only row with `snapshot_hash`). **Only hypotheses can be auto-accepted.** Basket changes and anything else have no auto option (D8). Right after generation, for each stored hypothesis proposal when the switch is on, `AutoAcceptProposalsHandler` re-runs every engine check against today's data and accepts only if all are `ok` (a check that is `unavailable` or stale leaves it pending: unavailable never counts as a pass), at most 3 auto-accepts per India date, as actor `system:auto-accept`; the decision row has `auto = true`, the `ai.settings.id` and `snapshot_hash`, and is never shown as an owner approval. Auto-accepting a hypothesis writes it `proposed` only (the approve step keeps P6-10's autonomy rule: nothing approves automatically below the `autonomous` level, which nothing reaches). `next_day_focus` needs no switch (accepting has no effect). No setting reaches an order or a broker. Auto requires `ai.settings.enabled` and `Enabled` like generation does.
11. **Insert-only.** `xd_app` has insert and select on both tables, no update, delete or truncate; one decision per proposal (unique index); the shape checks hold (kind list, key length, reason not blank, payload is an object).
12. **The model has no other write.** The proposal service references `IProposalInbox.Insert` and read ports only; accept/reject handlers are the only types that reference the hypothesis and basket commands (no tracking command is referenced), each refuses an actor not beginning `owner:` (403 `assistant.owner_only`); the architecture test enforces both; the no-order rule stays green. With `Enabled = false` the service does nothing and `GET` still lists stored proposals.
13. **Failure is quiet.** Model not ready, invalid JSON after one retry, or every item rejected: the run stores nothing, the service run reports counts and finding codes, the inbox is unchanged, nothing else is affected.
14. **UI.** `/suggestions` lists pending first, then recent decided and expired (30 days). Each card: kind, subject, reason, the Evidence block (basis, population, range, n, limits), the engine checks as a list with a word and icon each (not colour alone), the expiry, Accept and Reject. Accept opens a confirm dialog with a password field that states exactly what will happen ("Adds EVB to basket EvalAlpha", "Writes hypothesis ORB 15m BUY: rr 2 to 2.5 as proposed; it will not run or change anything until you approve it"). States: loading, empty ("No suggestions"), error; stale and closed proposals show their reason. Text is rendered as text.
15. Logs carry ids, kinds, counts and finding codes (6180 to 6189, the E2 block of P9-00), never reason text or payload values; `scripts/gen-api.sh` run.

## Non-functional
Pack: one cell-snapshot read, one trigger evaluation on replayed data (as the `xd learn hypothesis triggers` verb, seconds), at most 5 cells x (run header + parameters + grid). Engine re-derivation reads only. One model call per run (about 20 to 60 s). Accept: a few reads and one write. No secret, no broker call, no backfill from this slice.

## Test plan
- **Unit:** `KnobBounds` table (baseline 2.0: 2.5 ok, 3.1 refused at +55 %, -0.5 refused sign, 2.0 refused equal, 1.0 ok at -50 %, 0.99 refused, a six-digit rule); `ProposalChecks` per kind (each code once as a failing row); dedupe key stability (field order, case, trailing zero `2.50` vs `2.5`); lifecycle and expiry on read; claim-word rule; `TextGuard` use on reasons with the worked case: evidence n 120 and expectancy 0.21, reason "n=120" ok, "n=121" refused.
- **Handlers over fakes:** generation happy path (3 items), one item refused by each rule, model error, invalid JSON then retry, `Enabled` false, repeat block (reject, rerun, nothing new; after 31 days new), pending limits; accept for each kind (hypothesis through a fake `ProposeHypothesisHandler`), stale accept, closed accept, non-owner, double accept; reject.
- **Integration (Testcontainers):** both migrations, the check text of `ck_hypotheses_shape` now accepting `assistant` and still refusing `foo`, grants, unique indexes, endpoints; an end-to-end on a fixture with a real baseline run: scripted model proposes `rr 2.0 -> 2.5`, accepted, `research.hypotheses` gains one `proposed` row with source `assistant` whose stored knob equals the proposal, and the open count is 1.
- **Frontend (MSW):** each card state, dialog wording per kind, step-up path, stale/closed messages, markup inert, no digit for an evidence figure in state `insufficient`.
- **Architecture:** criterion 12.

## Decisions (researched)
**D1. Pack-in, JSON-out, no tools.** *Answer:* the model sees an engine-selected pack and answers in constrained JSON; it never queries freely for this job. *Reason:* the owner's rule "numbers only from tools" and "engine validates" are easiest to prove when the input set is fixed and hashed; free tool use makes the evidence set unbounded and the run irreproducible. Doc 09 §5's "reflect via read-only tools" is satisfied by the pack being built from the same read handlers; the free-exploration variant stays in chat (the owner can ask, then enter a hypothesis by hand). *Rejected:* a tool-calling agent that writes to the inbox. *Source:* docs/design/09 §5, 14 §1, §3.
**D2. Engine evidence, model reason.** *Answer:* evidence blocks are built by the engine from references; the model's text is only the reason, checked by `TextGuard`. *Reason:* a model-supplied figure is the failure mode of doc 14 §5; P8-00 D1 requires an Evidence block on every number. *Rejected:* trusting figures in the model's JSON and checking them afterwards.
**D3. Parameter knobs only, bounded +/- 50 %.** *Answer:* exit and slippage knobs are refused; a parameter move is at most half the baseline and cannot change sign. *Reason:* P6-10 compares exit text and slippage labels as stored text (honest limit), so a model-typed value there cannot be checked; the grid of P6-10 itself stops at `steps x step_pct < 100` so values never change sign; 50 % is the largest single step P6-10 allows (`step_pct` up to 50); the doc 09 example (2.0 to 2.5, +25 %) fits. *Rejected:* unbounded values (an LLM can propose absurd ones); the fixed grid only (the doc's own example 2.5 is not on the default grid). *Source:* P6-10 assumptions 2, 7; ADR 0076.
**D4. Evidence minimums.** *Answer:* hypothesis needs the cell at `n >= 30` (`min_trades`, doc 09 §6.2), basket removal and focus need `n >= 15` (doc 15 §6). *Reason:* every judged hypothesis is a trial that raises the bar for the next (P6-11/ADR 0072) and the open limit is 3, so the inbox must not spend them on thin cells. *Rejected:* letting thin evidence through flagged `insufficient` (attention is the scarce resource).
**D5. A new table, not `workflow.suggestions`.** *Answer:* `workflow.assistant_proposals` with a payload. *Reason:* the P7-09 table requires a plan id, has only kind/subject/text, and its unique index is per plan; changing an applied table breaks the "never edit an applied migration" rule. *Rejected:* making `plan_id` nullable. Doc 04 §4.3's single-table sketch (`workflow.suggestions` with source, type, payload, reason, expiry, status) is met by the pair of tables here; **design change: doc 04 §5 table list** gains the two tables (ADR at build time, next free ADR number at build time).
**D6. Accepting a hypothesis proposes it, nothing more.** *Answer:* accept writes a `proposed` hypothesis; approve, start and judge stay the owner's separate acts (P6-10). *Reason:* two owner acts for a research change is the intended friction; autonomy cannot approve (P6-10, P7-12). *Rejected:* accept = approve.
**D7. Source `assistant` in the hypothesis record.** *Answer:* new enum member and check change. *Reason:* provenance must be visible in the Learning screen (a hypothesis by the model is read with the knowledge that models mimic what they were shown). *Rejected:* source `owner` (hides origin).
**D8. Auto option for hypotheses only, default OFF.** *Answer:* one switch `auto_accept_hypothesis` in `ai.settings` (owner password), checks re-run at auto time, cap 3 per day, recorded as auto with the snapshot. *Reason:* the owner's standing instruction that anything needing manual approval can also run automatically through a setting that defaults OFF; accepting a proposal is such an approval. Only the least risky kind qualifies: a hypothesis writes a `proposed` row and nothing else. *Rejected:* auto for basket kinds (changes the book of research populations on a model's say with thin candidate evidence; to be reconsidered only after real-data use, see Open questions); one global switch.
**D9. Where it runs.** *Answer:* weekly after the digest, plus the verb. *Reason:* doc 09 §5 trigger "weekly"; `min_new_trades_per_cell` is a weekly-scale event; keeps model use off the nightly path (ADR 0005). *Rejected:* nightly.

## Risks and honest limits
- On today's data (about 3 usable folds) every experiment is at best Inconclusive (P6-10 honest limits), so an accepted hypothesis cannot yet be accepted as a finding; the inbox will be mostly empty or full of cells that cannot be confirmed. This slice builds the path; it does not create evidence.
- A language model's proposals mimic common trading folklore; the checks bound what it can ask for, not whether the idea is good. The reason text is a story about numbers the engine produced; the story can still be a poor one.
- Trial count: each accepted-then-judged hypothesis raises the multiple-testing bar; the panel states "each judged hypothesis counts as a trial".
- Baskets: membership changes alter future reports' populations (members as of the run are stored with trades, so old reports do not change).
- Rejected proposals are blocked for 30 days by key; a rephrased knob (same idea, other value) is a different key (honest limit).
- Hermes and chat have no write path to the inbox by design (P9-10 checks this: xd-mcp has no write code, P9-02).
- The auto switches let a model's ranked idea reach the book of work without a human read; the caps and re-run checks bound it, the hypothesis still needs approve, start and judge.
