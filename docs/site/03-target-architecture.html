03 — Target Architecture

1. Architecture at a glance#

Style: a .NET modular monolith (one codebase, clear module boundaries) deployed as a few containers, with a React single-page app, PostgreSQL + TimescaleDB as the only database, ML.NET for machine learning (no Python), and a local LLM — all on Podman Desktop.

Why a modular monolith (not microservices): one developer, one machine, shared engine code across backtest / Strategy Lab / nightly scan / grading. Modules can be split into services later if ever needed.

2.4 ML — ML.NET only (no Python)#

Our ML need is modest and well-defined: a binary classifier on tabular features (~10⁵–10⁶ rows, ~50–150 features) answering "does this candidate hit target before stop?", plus calibration and explanations. ML.NET covers all of it:

Need ML.NET capability
Gradient-boosted trees LightGbm trainer (Microsoft.ML.LightGbm); FastTree (ML.NET's own GBDT) as fallback
Baselines LbfgsLogisticRegression, SdcaLogisticRegression
Probability calibration Calibrators incl. PAV (isotonic) and Platt; plus own reliability-curve check
Per-prediction explanation CalculateFeatureContribution (supported for LightGBM/FastTree/linear models)
Global importance Permutation Feature Importance (PFI)
Metrics AUC, log-loss, Brier score via evaluation APIs + own walk-forward metrics
Persistence Model .zip in the models volume + research.model_versions row; champion/challenger = DB pointer

Flow: features and triple-barrier labels are computed by the same .NET code used for scanning → a weekly Hangfire job trains, calibrates and validates per walk-forward fold → the model is saved and registered → PredictionEngine/batch transform scores candidates in-process during the nightly run.

Why not Python: no second language/runtime, no extra container, no model-export hop, identical feature code for training and scoring. What we give up — exact SHAP values, Optuna-style tuning, notebook ecosystem — is not needed: feature contributions + PFI explain decisions, and the design deliberately avoids heavy tuning (few parameters, plateaus).

Platform check (Phase 0 spike): containers on Apple Silicon are linux/arm64. Verify the LightGBM native library loads there (if not, build lib_lightgbm.so from source in the worker image); fall back to the managed FastTree trainer otherwise. The model sits behind an IProbabilityModel interface, so the trainer can change without touching Planning or Learning.

Trading configuration and strategies are not repository folders: they live in the database (versioned, validated, audited) and are managed in the app; built-in defaults ship inside the backend and are seeded on first start (ADR 0002).

Dependency rule: Domain ← Application ← (Infrastructure, Brokers.*) ← hosts, and the engine modules sit beside Infrastructure and are reached only from an adapter in it. Engine modules (Indicators, Strategies, Simulation, Learning, Planning) have no I/O dependencies — they're pure and fully unit-testable. XDrishti.SimExport is pure in the same way but is not an engine: it renders a finished run and is referenced by a host (XDrishti.Api, whose folder writer is the one place that touches the file system for the export), never by Application or Infrastructure (§4.4). Application references Domain only and never an engine module (ADR 0039): a use case that needs an engine declares a port in Application/Abstractions/<module> whose signatures use Domain values only, and an adapter in Infrastructure/<module> implements it over the engine. The sequence is handler → port → adapter → engine: the handler reads through its own ports (bars, instruments, baskets, actions, calendar) and hands plain values to the engine port; the engine stays pure. Infrastructure is the only project that references an engine module; an architecture test enforces it (ResearchLayeringArchitectureTests). The first use is the simulation run of P3-04a (RunSimulationHandler → ISimulationEngine → SimulationEngineAdapter → XDrishti.Simulation.Replay, §4.3).

4.1 XDrishti.Indicators as built (P3-01, P3-01b and P3-01c, ADR 0031, ADR 0032, ADR 0033)#

The first engine module. A pure library that turns a stream of closed 1-minute bars into indicator values, closed higher-timeframe bars (up to weekly and monthly), session context, the calendar and a daily market context; back-tests and live trading use the same code.

Part What it is
IIndicator Update(in Bar), Value, IsReady, WarmUp, Reset(); constant (or amortised constant) work per bar, 0 bytes allocated in steady state. A value that is not ready is NaN with IsReady = false (the two always agree). The value after bar k is a function of the bars 1..k; the date-driven features are a function of the India dates of those bars and of the context days strictly before each date, their WarmUp is counted in days of the context (not bars), and their IsReady can fall back to false (a day without a VIX)
IndicatorCatalog The 56 features (19 of P3-01, 25 of P3-01b: ADX/DMI, MACD, Bollinger, Supertrend, ROC, the candle patterns, pivots and the raw bar features, and 12 date-driven ones of P3-01c: day_of_week, is_expiry_day and the ten market-context names) with parameters (name, kind, min, max, default; at most 4), warm-up as a function of the spec (counted in bars of the spec's own timeframe; in days of the context for the date-driven names), session behaviour (Continuous / PerSession) and whether the feature restarts each session in the frame (RestartsEachSession(spec): the twelve PerSession names on 1m to 1h, not on 1D; ADR 0035), whether the source price is read, whether it is intraday-only, which timeframes it supports (Supports(tf): the nine of SupportedTimeframes for the continuous ones, fewer for the session-bound ones, 1m only for the date-driven ones), whether a frame that computes it needs a market context or the expiry dates (RequiresContext: true for exactly the ten names index_trend index_adx index_vol_pct vix vix_pct vix_chg breadth regime_trend regime_vol regime; RequiresExpiryDays: is_expiry_day only; P3-02, so the rules language asks the catalog instead of knowing the names) and a factory. The validator and lint of the rules language read it
TimeframeBuilder Builds closed 5m, 10m, 15m, 30m, 1h, 1D, 1W and 1M bars with the rules of the stored aggregates (doc 05 §4); Push returns 0, 1 or 2 closed bars per minute; optional TradingCalendar; late bars are ignored and counted (Ignored). A week or month is built from the 1D bars and is emitted at the close of the period's last session when a calendar is given, at the first bar of the next period when not (later, never earlier)
FeatureFrame Created once from a list of FeatureSpec (name, timeframe, price source, up to four parameters); validates them before any bar is fed, shares one instance between equal specs, builds only the needed builders, and exposes the value as of the last closed bar of each timeframe by a numeric handle. Counts the incomplete higher-timeframe bars it consumed (IncompleteBarsConsumed)
Frame API for the DSL (P3-01b) Create(specs, FrameOptions?) with FrameOptions(Calendar, HistoryDepth = 8, 1..256, Context, ExpiryDays); BarClosed(tf), ClosedBarsAt(tf), TryLastClosed(tf, out ClosedBar) and HasTimeframe(tf) (what the last step closed; a timeframe not asked for throws); At(handle, lag) and IsReadyAt(handle, lag) read the value a feature had lag closed bars of its own timeframe ago (a lag outside 0..HistoryDepth−1 throws; the history is written only when that timeframe closes a bar, twice when one minute closes two; for the twelve per-session names on an intraday timeframe only the current session counts, next row); the raw bar features open high low close volume; an ordering guard (a 1-minute bar at or before the previous one is skipped by every lane and counted in IgnoredBars; Steps counts accepted bars); PriceSource.Default resolves to the catalog default (High for highest, Low for lowest); the catalog collections are read-only; LastBarTime (P3-02): the epoch-second start of the last accepted 1-minute bar, 0 before the first step, unchanged by a skipped bar, cleared by Reset, read without allocation (the compiled time is its minute plus one, in India time)
FeatureFrame: per-session features (ADR 0035) The twelve names that start again on every India date (vwap, or_high, or_low, today_open/high/low, prev_day_open/high/low/close/volume, gap_pct) keep, on an intraday timeframe (1m to 1h), the value history of the current session only, and this is a rule of the frame, so every reader sees it. With S the bars the feature's timeframe has closed on the India date of the last accepted 1-minute bar: S = 0 (the frame has moved to the date and a coarser timeframe has not yet closed its first bar of it) is pending, not ready at any lag, Value is NaN; with S ≥ 1 lag 0 is the value and lag k ≥ 1 is the value k bars ago when k < S, else NaN. It reads as if the frame had been created at the first accepted bar of the date (for prev_day_* and gap_pct: of the previous date that had bars). On 1D nothing restarts (a lag is by position); 1W and 1M refuse the names; rolling and date-driven features are untouched. A session is the India date of the start of the bar a timeframe feeds its indicators (IndiaDays.DayOf, the call the indicators restart on); a bucket that closes late is consumed with its own date, so it does not un-pend the new one; a frame must be fed whole sessions (started mid-day it takes that bar's date as its session, so a live restart replays the current session from its first bar). Built without a new member of FeatureFrame, so the seven members the compiled library may reference are unchanged: an internal IRestartingIndicator.MarkPending() on Vwap, OrHigh, OrLow and SessionContext, restart slots in the Lane, StartSession after the lanes have consumed the minute, and the first Consume of a date clears the ring slots of the restarting features. IndicatorInfo.RestartsEachSession(spec) is the one place that says which features restart (the frame, the lint of the rules language and the tests ask there). The readiness of those four indicators depends on a flag that the frame sets and the next Update or Reset clears (covered by the determinism and reset tests and by the mutation runs). Known limits (doc 11 §2, Limits of the rule): a coarser timeframe is pending conservatively (tf("1h").prev_day_close is unknown for up to 60 minutes although the value is known), and a session is a date, so a morning and an evening block of one date are one session
Calendar and market context (P3-01c) MarketContext.Create(IEnumerable<ContextDay>, ContextOptions?) / Append / TryAsOf(date, out ContextValues): a pure object built from daily records (index high / low / close, VIX close and breadth if known), each day's values computed from that day and earlier days only (streaming Sma, Atr, Adx and a percentile window), shared by any number of frames (Append is single-writer; readers may run meanwhile and see a day only once it is complete); a context that nobody extends keeps its last day's values for ever, so the caller extends it and checks its age (ADR 0033, known risk); invalid input returns a validation error with a code (indicators.context_*), never an exception. TryAsOf(D) returns the latest day strictly before D. ContextOptions (50-day average, 5-day slope, ADX(14) ≥ 20, ATR(14), 252-day percentile window, terciles 100/3 and 200/3), ContextValues, Regime.Name / Regime.Code (UP_LOW_VOL 1 … DOWN_HIGH_VOL 9). FeatureFrame keeps the 12 date-driven features (DateFeature, kinds DateFeatureKind; named ContextFeature before P3-02, since two of them read no context) in a date lane refreshed at the first accepted step of each India date (history one entry per date); the library never reads a database, and the expiry dates are passed in by the caller

References and rules. The project references XDrishti.Domain only (for Bar, Timeframe, SessionClock, TradingCalendar). Architecture tests keep it that way: no Application, Infrastructure, Hosting, EF Core, ASP.NET Core, Npgsql, Serilog, System.IO, System.Net, System.Data, System.Diagnostics, Environment, Random or TimeProvider; no DateTime.Now/UtcNow/Today (scanned in the compiled code); no mutable static field; every public class sealed or static. The tests also read the project file: only the ProjectReference to XDrishti.Domain and no PackageReference. The only package outside the base class library that is involved is Skender.Stock.Indicators, and only in XDrishti.Indicators.Tests.

Guarantees pinned by tests. Each indicator equals an independent batch reference over seeded random series; sma, ema, rsi, atr, adx/plus_di/minus_di, macd_*, bb_* (population σ) and roc also agree with Skender (differences: the ATR seed, an RSI over a series that never moves is 50 here and 100 in Skender, and supertrend, which starts a bar earlier here and always starts up); the history At(handle, lag) equals a record kept independently by the test, for depths 1, 2, 8 and 256; the prefix property (the output for the first k bars is the same when more bars are fed) over 220 seeds, also for the weekly and monthly lanes and for the market context (the values of the first k days do not change when the series is cut or continues differently, and a frame never reads a context day dated on or after the date of its step); every MarketContext value, and every weekly and monthly bar, equals an independent batch reference; the frame never shows the forming bar; two runs are bit-identical; Reset() returns every indicator to its first state. The per-session rule (ADR 0035) is pinned by hand-calculated two-session examples, by comparison with an independent reference of the rule (built from the definition, with S counted from the start dates of the buckets) on dense, gappy, sparse and late-closing series, by a positional negative control that fails when the rule is removed, and by 28 of 30 mutations of the implementation being caught by the tests of the rule (the two survivors are provably equivalent); 480 adversarial tests written from the design by a second agent found no failing case. Entry: a limit order placed at the decision instant at the trigger close +0.1 % rounded down to the tick (a sell: −0.1 %, up), which lives for the first minute that holds a trade at or after the decision instant, at most five minutes after it, before the square-off, on the same India date; it fills at that minute's open when the open is within the limit (AtOpen), at the limit when the minute trades back to it (AtLimit), and is otherwise a counted miss, LimitNotReached, never filled later; a fill at or through the stop is no trade; a minute with volume 0 holds no trade. Simulator.Create runs the swing style on 30m and 1h (BUY only) and Simulator.HoldsOvernight says so; the internal PositionGate between the scanner and the walks keeps one open position per instrument and side (NoTradeReason.PositionOpen). In the replay a swing position open at the end of a segment that a flagged day follows is excluded and counted (ExcludedAcrossDiscontinuity); the run record is schema 3 and the run key starts xd-run 3. Intraday trades are byte-identical in the schema-2 view (three frozen files made before the change).

The replay and the run record (P3-04, ADR 0037 Amendment 2). InstrumentReplayer.Replay runs a prepared strategy over the raw 1-minute bars of one instrument, from its first stored bar to the end of To, and returns an InstrumentReplay (a record, the trades in the window, the EndOfData trades apart). It is pure: values in, values out, no clock, no random source, no I/O; reading the bars, choosing the universe and the skips that need I/O are the use case of P3-04a (below), an Application handler that reaches this engine through a port implemented in Infrastructure (ADR 0039). Rules: (1) the replay starts at the first stored session whatever From is and only the trades are cut to [From, To], so a trade does not depend on the window (an ema(10) is seeded by the first stored bar); (2) each date is classified with the trading calendar into a session that runs, closed_day, special_session, short_session (fewer than 90 % of 375 minutes) or missing_session, the excluded ones feed nothing, are counted and noted, and read as a closed market; (3) prices are adjusted for the applied actions on a copy (the raw list and its SHA-256 are never touched); (4) a day whose first open is more than 20 % from the previous close (in decimal, exactly 20 % is not flagged) is flagged, gets no entry and restarts the indicators (a new Simulator.Run over a window of the one list of fed bars, so a candidate's decision index is its index in the list the walker reads); (5) every candidate outcome has exactly one fate (suppressed, before the window, open at the end, a trade, or a no-trade by reason) and their sum equals the scanner's candidates; (6) an instrument with no trades says why (no_bars, no_runnable_sessions, no_sessions_in_window, features_not_ready, and the preset csv_adjusted_twice and tick_size_invalid that the runner decides). RunAssembler.Assemble builds the SimulationRun: totals, trades and open-at-end trades in one order with the basket ids of the universe, the exceptions of the calendar in the range of the data, and the run key, the SHA-256 of a fixed text (engine, strategy hash, effective parameters, timeframe, window, options, acknowledgement, fill rules, universe label, per instrument the hash of its bars, skip, applied actions and tick, and the calendar exceptions) that changes whenever anything that can change a trade changes. The record is the reproducibility record of doc 11 §6. Pinned by tests: the session and discontinuity tables, window independence with a control, the hash and the key with known answers computed with Python 3, a golden record with a table of versions, the names of the record's properties, 100 seeded series for the look-ahead property of the replay's own filtering (457 trades, 72 flagged days and 66 excluded sessions compared; the control differs in 100 of 100), and memory: one replay of 190,125 bars allocates 1.1 MB (0.12 times the raw list), or 10.1 MB (1.11 times) when it adjusts a copy.

The run over the ports (P3-04a, ADR 0039, ADR 0037 Amendment 3). RunSimulationHandler (XDrishti.Application/Research, internal, sealed, registered in AddResearch) is the use case: RunSimulationQuery(SimulationRequest) gives Result<SimulationRun>. Order: validate the request (simulation.invalid, a field error each; the year 2000 to 2099; one of a list of 1 to 2,000 ids or a basket; every number finite), build the fill rules (simulation.slippage_invalid, simulation.fill_rules_invalid), prepare the strategy through the engine port (simulation.strategy_invalid, the path and code of each problem, at most 20), and only then read a port. The universe is the list in the order given (an id with no row is the skip instrument_not_found) or a manual, not archived basket's members now (MembersAsync(basketId, null, null), in the basket's order, retired members and members without bars included; label members as of today; a portfolio basket, an archived one and an unknown id are simulation.basket_not_found). Per instrument, one at a time and in order: the row (symbol and tick), IBarStore.ReadAsync from 2000-01-01 to 23:59 India time of To (both bounds with offset 0), the adjustment factors and, for the whole run, the trading calendar and ListCsvAdjustedThroughAsync once; the guard of doc 05 §4.2 and the tick give a preset skip; the engine replays and the record is assembled with RunAssembler. Nothing is written; time is read only to time the phases for three log lines (event ids 4402 to 4404). Port and adapter: ISimulationEngine and IPreparedStrategy in Application/Abstractions/Research, SimulationEngineAdapter (internal, stateless, a singleton) in Infrastructure/Research over BuiltInStrategies.Prepare and InstrumentReplayer.Replay. Infrastructure gained the one project reference to XDrishti.Simulation.

The independent oracle (P3-08, ADR 0047). tests/XDrishti.SimOracle is a second implementation of the walk and the position gate, in decimal, written from the rule tables alone by a second agent (per its own report that it never saw the engine; the transcript audit was not made), in a library that references nothing (no project, no package, no XDrishti.* assembly; OracleArchitectureTests read the project file and the compiled references, with a sentinel for each rule, and an IL scan keeps OracleFaults out of every production comparison). XDrishti.Simulation.Tests/Oracle holds the engine side: an adapter that maps the oracle's records to the engine's types and back (round-tripped on every generator family, with sentinels), the author's 100 hand rows as data with the numbers copied from the specs (spec, oracle and engine agree on all of them in both fill modes), a comparator over every SimTrade field and every counter (exact, with a 1e-12 tolerance for the five ratio fields that was measured and never needed), the gate rows, 16,700 series of the author's generator and the engine's 500 + 500 + 500 seeded days, daily and swing series and 100 replay series for three strategies, coverage floors of 500 per category and sub-case from the oracle's own trace, the sixteen planted faults, a reflection check that every field of SimTrade and WalkCounters has a row of the dry-read table, and the written disagreement log (docs/research/p3-08-disagreements.md): no disagreement of any class at this run. What this shows is that the engine agrees with the rule tables as a second author reads them (and ADR 0047 states the readings that close the gaps of the tables); it does not show that the tables are right, and it says nothing about the scanner, the frame or the compiler, which have no second implementation. The cost oracle (P3-08c) is the same author's reference costing in the same library (the quantity, the two turnovers, the sixteen charge lines, CostR, RNet, the two skips, the schedule of each leg's date; fifteen planted faults): CostAdapter, CostComparer and CostCorpus compare it with TradeCostApplier on 14,400 generated trades and on 53,598 costings of the walked trades of the seeded series (the TEST sheet in each rounding mode and both schedules, the fixture sheet, capitals from 10,000 to 1,00,00,000, both sizing profiles), every field exact (CostR and RNet exact first with a tolerance fallback, measured maximum difference 0 (NotExact is asserted 0)), no disagreement of class A, B or C. The engine line of every export now reads engine: agrees with a separately written reference implementation of the rule tables (P3-08, sim-6); not checked against charts or the owner's charge sheet and engine_verified is true in run.json; the flag is bound to the engine version by a committed constant (OracleVerifiedFor) and a test, so a new engine version cannot ship it until the comparison is rerun, and the run key does not change (the labels are not part of it).

4.4 XDrishti.SimExport as built: the export library and the folder writer (P3-04b1)#

A finished SimulationRun is turned, by pure code, into the bytes of the files of data/exports/sim/<run-id>/. The simulate verb (P3-04b2, ADR 0041). The trade cards (P3-04c, ADR 0041 Amendment 1). With --cards <0..500> (default 200) the verb chooses trades with CardSelection, asks BuildTradeCardsQuery(Run, TradeKeys) (BuildTradeCardsHandler in XDrishti.Application/Research, internal, ports only: it reads again the stored bars of the instruments that have a chosen trade, one at a time, adjusts the trade day by the replay's rule, and refuses with simulation.cards_stale when the bars, the applied actions or the tick are no longer what the run read) and passes index.html and cards/… to the same folder writer, with the extra manifest lines and the format string xd-sim-export-2. CSV import#

Live active set#

Planning (armed tickets) + Portfolio (open positions, holdings) + context indices + pins → xd-feed diffs the set and (un)subscribes on the Dhan WebSocket → ticks → live 1-minute bars + LTP → Portfolio/alerts → SignalR to React.

Built in P2-10 (ADR 0024): xd-feed → ticks → last price per instrument (every 2 s) into the holdings, market.live_quotes and the price alerts → NOTIFY live_prices → (P2-10a) xd-api reads what changed and pushes it over SignalR. The feed and the API never call each other; the database is the only meeting point. Live 1-minute bars are not built yet.

Built in P2-10a - the hub /hubs/events in xd-api. Owner session cookie only (the same session middleware as the REST API, including the 30-minute idle timeout; a connection without one is refused with 401, and a connection is closed within 30 seconds after its session ends by logout, idle timeout or the 12-hour limit; an open connection does not keep a session alive, the screen's own requests do), same origin only (a request with another Origin is refused with 403; no CORS, no wildcard), WebSockets only, no anonymous method. A browser connects with skipNegotiation and the WebSockets transport (otherwise the negotiate POST needs the X-CSRF-Token header like every POST). Server methods: Subscribe(scope) where scope = {accountId?, bucketId?, holdingIds?} (the screen's scope with the meaning it has for GET /api/holdings/summary, plus the holdings shown; the server turns them into instruments, at most 1,000 instruments and 1,000 holding ids per connection) answers {subscribed, truncated, failed}; Unsubscribe(). A second Subscribe replaces the first. Client events: pricesChanged {asOf, instruments:[{instrumentId, lastPrice, priceAt, source}]} - first the current price of every followed instrument, then only changes; at most one burst a second per connection, at most 500 instruments and 32 KB per message (larger changes come as several messages); source is live, quote or sync. feedStatus {state, subscribed, lastTickAt} - on connect, on a change of state or subscribed (looked at every 5 seconds) and at least every 15 seconds, from the xd-feed heartbeat; state is the feed's own word or not_running. GET /api/live/status returns the same object. How it works: a hosted service in xd-api listens on NOTIFY live_prices (its own database connection, reopened by itself with a growing wait of 1 to 30 seconds after a database restart; a notification lost meanwhile is made up by one read when listening resumes), reads the current price of the instruments that connections follow (the holdings' price columns and market.live_quotes) and sends each connection what differs from what it was last sent; a read also happens every 30 seconds without a notification, because quote and sync prices are written without one. xd-api runs and stays healthy without the feed (the status then says not_running). The types of the hub are generated from the C# contract (XDrishti.Application/Live/Push) by scripts/gen-api.sh into frontend/src/shared/realtime/hubContract.generated.ts. Caddy proxies /hubs/* to xd-api (WebSocket upgrade is automatic in reverse_proxy).

8. Security#

  • Login required everywhere: single owner, ASP.NET Core Identity (password), idle timeout, lockout, password re-entry for sensitive actions for sensitive actions; HTTPS via Caddy on LAN; optional WireGuard for remote access (doc 04 §2).
  • Service identity: background services act on persisted desired state, not on user sessions; every action records the configuring actor for audit.
  • Secrets per container via Podman secrets; only xd-worker/xd-feed (data/account tokens) and later xd-exec (order tokens) receive broker secrets.
  • xd-mcp and the LLM use a read-only database role; no tool can change config, plans or orders.
  • xd-sandbox has no network and a read-only data mount.
  • Audit log for config activations, promotions, approvals and (later) orders.
