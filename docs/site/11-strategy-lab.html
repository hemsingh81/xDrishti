11 — Strategy Lab

Submit your own strategy rules at any time; the system validates, tests and reports a verdict — no code changes, no restart.

2. Rules language (DSL)#

Declarative, safe (parsed and compiled to expression trees, never eval), look-ahead-proof (only closed bars; higher timeframes = last closed bar). The language of one condition is built (P3-02, ADR 0034: see The rules language as built below); the typed strategy model around it and the compile of its sections are built too (P3-02b, ADR 0036: see The strategy model as built below); the YAML file, its JSON Schema and the hash are built too (P3-02c, ADR 0055: see The strategy file as built below).

"Intraday: after 9:45 buy when a 15-min candle closes above VWAP with RSI(14) above 55 and 1-hour EMA20 above EMA50. Stop below last swing low. Target 1:2, or trail after 1R. Exit by 15:15. Mirror for shorts. Test 2022 to today on my MyChoice and Best stocks baskets."

strategy:
  id: VWAP_RSI_TREND
  version: 1
  style: intraday
  timeframes: [15m]
  sides: [BUY, SELL]              # SELL auto-mirrored unless a `sell:` block is given
  universe: { baskets: [MyChoice, "Best stocks"] }   # or instruments: [...] or a rule-based basket
  params: { rsi_len: 14, rsi_min: 55, swing_lookback: 5 }
  setup:
    all:
      - time >= "09:45"
      - tf("1h").ema(20) > tf("1h").ema(50)
      - rsi(rsi_len) > rsi_min
  trigger:
    all:
      - crosses_above(close, vwap)
  entry: { type: at_close }       # at_close | stop_above_high | limit_pullback
  stop:  { type: swing_low, lookback: swing_lookback, buffer_atr: 0.1 }
  exits:
    - { policy: FIXED_RR, rr: [2.0] }
    - { policy: PARTIAL_TRAIL, book_pct: 50, t1_rr: 1.0, trail_atr_mult: 2.0 }
  time_rules: { last_entry: "14:30", square_off: "15:15" }
  filters: [not_event_day, min_turnover]

test:
  period: { from: 2022-01-01, to: today }
  method: walk_forward            # walk_forward | simple_split | full_period (exploration only)
  compare_with: [baseline_random, ORB]
  robustness: { param_sensitivity: true, monte_carlo: 1000, by_year: true, by_regime: true }

Illustrative, not valid today. This example does not pass POST /api/lab/validate (ADR 0057): it lists SELL without a sell: block (the automatic mirror is P3-02e), declares two exit candidates (the simulator runs one), puts buffer_atr on a swing-low stop and names two filters that have no data. Validate reports each with its location; the built-in texts in Seed/Strategies are valid examples.

How the sections combine. setup, trigger and the optional invalidate list (the invalidation row of doc 07 §1, "cancel if…") are evaluated together at every closed bar of the evaluation timeframe: an entry is possible when setup is true, trigger is true and invalidate is not true. That is why the example may put time and rsi(…) in setup; which parts of a setup are knowable at the previous close, for the nightly shortlist, is the business of the planner (P7), not of the model. An all: list is the Kleene AND of its conditions and an any: list the Kleene OR; the conditions are compiled and evaluated one by one and never joined into one text. time_rules is the one place for windows (first_entry and last_entry inclusive, square_off for intraday, max_hold_sessions for swing); nothing is read from the configuration, so a stored strategy is self-contained. In the stored form of P3-02b the nested trail: { type: ATR, mult: 2.0 } of PARTIAL_TRAIL is the field trail_atr_mult (the trail is the ATR in schema 1; the file of P3-02c has no nested trail: it is written trail_atr_mult, and the nested form is file.unknown_field).

In this example time >= "09:45" is the trading rule of the sentence above (no entry before 09:45), not something the language needs in order to be correct: crosses_above(close, vwap) is unknown at the first evaluation of every session (09:30 on 15m) and can first be true at the second (09:45), see Lags below.

What the frame gives the DSL. For every feature the value as of the last closed bar of its timeframe, plus BarClosed(tf) (did a bar of that timeframe close at this step? the moment to evaluate a condition), At(handle, lag) (the value lag closed bars of the feature's own timeframe ago: close[1], the previous value for crosses_above and rising(x, n); for the twelve per-session names on an intraday timeframe only the bars of the current session count; the history depth is 1 to 256, default 8; the compiler works out the depth a condition needs, CompiledCondition.HistoryDepth and CompiledPlan.HistoryDepth, and the caller must pass it in FrameOptions.HistoryDepth — a frame with the default depth refuses to Bind a condition that reads further back, close[10] for example) and the last closed bar of each timeframe. A repeated or out-of-order 1-minute bar is skipped by every timeframe and counted.

Weekly and monthly timeframes (P3-01c). A feature reads 1m, 5m, 10m, 15m, 30m, 1h, 1D, 1W or 1M; the continuous indicators (rolling, trend, momentum, volatility, patterns, raw bars) run on all nine, the warm-up is counted in weekly or monthly bars (ema(10) on 1W needs ten weeks), and the closed flags, the history and the raw bar features work as on any timeframe (tf("1W").close is the close of the last week that has closed, at every minute of the week in progress before its closing step). A week starts at India midnight of its Monday (a Saturday session belongs to the Monday-to-Sunday week it falls in), a month on the 1st, and both are built from the 1D bars of the same rules. When a week or month counts as closed: with a TradingCalendar in FrameOptions, at the step that closes the last session of the period (the Thursday when Friday is a holiday, the last weekday of a month that ends on a weekend, a known Saturday session) — the same minute at which the 1D lane closes that date; without a calendar the builder cannot know the last session, so it emits the bar at the first bar of the next period: later, never earlier. A bar of a period that has already been emitted is ignored and counted. Where this differs from the stored 1W / 1M: doc 05 §4.

The market context (P3-01c). The context is daily and read as of the previous session: at the first step of an India date D the frame takes the values of the latest context day strictly before D and keeps them for the whole date (09:15 and 15:29 read the same number), so a strategy at 10:30 on a Tuesday sees Monday's close and never Tuesday's, even when Tuesday's record is already loaded; a weekend or holiday reads the last day before it. The caller builds the MarketContext once from daily records (ContextDay: date, high / low / close of the regime index — Nifty 50 by default —, the VIX close if known, the breadth if known) and shares it between frames; every day's values are computed from that day and earlier days only. Past the last day of the context a frame keeps that day's values and stays ready (it does not say how old they are; pending owner confirmation, ADR 0033 Amendment 14): the caller extends the context as the days pass and checks its age — the data job (P3-01d) and the market gate (P7) must make a stale context visible (ADR 0033, known risk). The strategy around the language is split: the typed strategy model and the compile of its sections are built (P3-02b, The strategy model as built); the YAML sections, the JSON Schema and the hash are P3-02c, storage in lab.strategies is P3-02d and the BUY → SELL mirror is P3-02e. Reading the context from the database is part of P3-01d (it owns the table and the reader that builds the MarketContext; the simulator only uses it), and reading bars from the database is P3-04 (P3-03 runs on the bars it is given).

How the closed-bar rule is kept. A feature on a higher timeframe (tf("1h").ema(50)) is computed over bars that a TimeframeBuilder emits only once their last minute has arrived, so at 10:30 it reflects the 09:15 hour (closed at 10:14) and never the 10:15 hour that is still forming. A bar with a missing minute is emitted late and flagged incomplete, and still used; the frame counts those so the simulator can report them. An indicator that is not ready is NaN, and a condition on it is unknown (a decision treats unknown as false, but not of it stays unknown: The rules language as built). The warm-up is counted in bars of the feature's own timeframe (ema(20) on 15m needs 20 fifteen-minute bars, ema(10) on 1W ten weekly bars; prev_day.* and gap_pct need 376 one-minute bars, 26 fifteen-minute bars or 2 daily bars). A per-session feature is also not ready, at every lag, from the first 1-minute bar of a new date until its timeframe has closed its first bar of that date (up to 60 minutes for tf("1h")): it never shows the day before.

The rules language as built (P3-02, ADR 0034)#

A condition is one true/false expression: rsi(14) > 55 and close > ema(20). The library XDrishti.Strategies (doc 03 §4.2) reads its text, binds every name to the 56 catalog features above, applies the look-ahead lint and compiles it to a delegate that decides over a FeatureFrame with zero allocation, in a time bounded by the text of the condition: it never grows with the history the frame keeps or the number of bars, but it is an upper bound and not the same for every condition (rising/falling(x, n) are a loop of n reads, n up to 255; see Speed). It takes the text, the strategy's evaluation timeframe and a {name → number} map of strategy parameters, and nothing else: what surrounds it is split: the typed strategy model (setup/trigger/invalidate lists, params of at most four, the sell: block) and the compile of its sections are built (P3-02b, The strategy model as built below), the YAML file and the schema are P3-02c, storage P3-02d, and the BUY → SELL mirror P3-02e. The all: / any: lists of the example in §2 are lists of conditions, each compiled and evaluated on its own; inside one condition the operators are and, or, not. Nothing is ever executed as text: the vocabulary is closed (catalog, nine builtins, seven constants, time, the parameters) and the only dynamic code is an expression tree built from the checked tree.

Grammar (loosest to tightest):

or        := and ( "or" and )*
and       := not ( "and" not )*
not       := "not" not | compare
compare   := sum ( ("<" | "<=" | ">" | ">=" | "==" | "!=") sum )?      -- not chained: a < b < c is an error
sum       := product ( ("+" | "-") product )*
product   := unary ( ("*" | "/") unary )*
unary     := "-" unary | primary
primary   := number | string | "true" | "false" | "(" or ")" | call
           | reference ( "[" ["-"] digits "]" )?                         -- a subscript only right after a reference
reference := ident | ident "." ident | "tf" "(" string ")" "." ident     -- close, prev_day.high, tf("1h").close
call      := ident "(" [ arg ( "," arg )* ] ")" | "tf" "(" string ")" "." ident "(" [ arg ( "," arg )* ] ")"
arg       := or | ident "=" ident                                        -- named argument: source=high

Numbers are decimal with an optional lower-case exponent (55, 0.5, 1e-3; not .5, 1. or 1E5); strings use double quotes with no escapes; whitespace is free; there are no comments; keywords are lower-case; everything is case-sensitive (RSI is unknown_name with the suggestion rsi). Only ASCII is part of the language outside strings: a full-width ＞, a no-break space or an accented letter is an unknown_character problem that names the code point (a look-alike with a clear meaning is reported once and then read as the token it stands for). A text is at most 4,000 characters and nests at most 64 levels (brackets and prefix operators open at once, and the depth of the tree, where every call, not, minus sign and subscript, and every operator of a chain, is a level and parentheses are none). A chain is as deep as it is long, so about 60 conditions joined by and is the most one condition can hold (the exact number depends on the shape of each: 63 conditions of the form rsi(14) > 55 pass, 64 do not); the limit protects everything that walks the tree, and the message of the second check says so. The spec of P3-02b (Draft, awaiting the owner's approval) evaluates the entries of an all: / any: list one by one at list level (the Kleene AND / OR of the item truths) and never joins them into one text, so this limit does not apply to a list. ExpressionPrinter writes the canonical text of a tree (one space around infix operators, the fewest brackets, shortest numbers); two sources that differ only in white space or redundant brackets print the same.

Names. An identifier means, in this order, a strategy parameter (a number known at compile time; one that has the name of a feature, builtin, constant or time wins and shadowed_name warns), then a builtin, constant or time, then a catalog feature. A feature is written name(args); the arguments are positional in the catalog's order with the catalog's defaults for the trailing ones (rsi() is rsi(14), bb_upper(20) is bb_upper(20, 2)), each a number known when the condition is compiled (a literal, a parameter, MON … SUN, or arithmetic, abs, min, max of those: rsi(rsi_len * 2)), plus the one named argument source=close|open|high|low for the features that read a price. A feature without parameters is written vwap or vwap(); one with parameters needs its parentheses (rsi is an error that suggests rsi()), and so does every function.

Types. A finished condition is bool. and or not take bool; + - * / and the unary minus take numbers; < <= > >= take two numbers; == != take two numbers or two bools. time is compared with a text "HH:MM" (any of the six comparisons, the text on either side); regime() with == or != against one of the nine names or a constant integer 1 to 9. A text, time or regime() anywhere else is a type error. A comparison names both sides (close > true: "> cannot compare close (a number) with true (a true/false value)"); the other operators and the builtins name the operand that is wrong, what the place needs and what it is (close + true > 1: "The right side of + needs a number, but true is a true/false value"); a number where a true/false value is needed (rsi(14) and close > 1) also says what to do: "Compare it with something, like rsi(14) > 55".

Three-valued logic. A comparison, crosses_*, rising, falling, between or time whose data is not ready — a feature in its warm-up, a history too short for the lag, no context for the date, a day without a VIX, a division by zero — is unknown, not false. and, or, not follow Kleene's tables:

a and b b true b false b unknown
a true true false unknown
a false false false false
a unknown unknown false unknown
a or b b true b false b unknown
a true true true true
a false true false unknown
a unknown true unknown unknown

not swaps true and false and leaves unknown unknown.

A decision (Evaluate) is true only when the result is true, so unknown acts as false — but not does not turn it into true: not (rsi(14) > 55) cannot fire before RSI exists, while rsi(14) < 45 or close > 0 is true as soon as close > 0. EvaluateTruth returns the three values. The lagged builtins and between are atomic: unknown if any of their values is not ready. Arithmetic on a not-ready value is not ready (NaN); x / 0 is NaN, never an exception; a quotient that overflows is ±infinity, a number.

Lags. x[k] (a reference followed by [k], k = 1 … 255) is the feature's value k closed bars of its own timeframe ago; close[1] on a 15m strategy is the previous 15-minute close, tf("1D").close[1] the close before the last closed day. x[0] and x[-1] are refused (negative_or_zero_lag; for x[0] the suggestion is x and replaces the whole subscripted feature): a subscript always asks for the past, and x already is the value as of the last closed bar. Crossings and runs use the previous value of each operand, which may be any numeric expression (every feature in it is read one bar further back; constants stay constants):

Builtin Means
crosses_above(a, b) a[0] > b[0] and a[1] <= b[1] — a touch that does not pass is not a cross; equal at the previous bar counts as "not above yet"
crosses_below(a, b) a[0] < b[0] and a[1] >= b[1]
rising(x, n) x[0] > x[1] > … > x[n]: n whole steps back, strict at each (n ≥ 1, known at compile time); falling is the mirror
between(x, lo, hi) lo <= x <= hi, both ends included

The lags add up: rising(close[200], 100) reads 300 bars back. The history needed is the largest lag plus 1 and may not exceed 256 (the frame's cap). The operands of crosses_*, rising and falling must all be on one timeframe, or "the previous value" of the two would be different moments: crosses_above(close, tf("1D").ema(20)) on a 15m strategy is an error, and says to write close > tf("1D").ema(20) and close[1] <= tf("1D").ema(20). The calendar and context features are read on 1m but change once a date, so their previous value is the previous date, never the previous minute: they are a clock of their own and may be lagged among themselves and against numbers (rising(vix, 2), crosses_above(vix, 20), rising(vix - index_trend, 2)), never together with a bar feature, on any strategy timeframe, 1m included. crosses_above(close, vix) is an error that says to write close > vix and close[1] <= vix (the bar is lagged, the date's value is read as it is now); where no explicit form can be offered (rising and falling, or a crossing whose bar operand is not a plain reference of the strategy's timeframe) the message says that a calendar or context feature changes once a date, so it is compared without a lag, or only the bar side is lagged by hand.

A lag counts bars, and a per-session feature keeps the bars of its session only. For a rolling feature the history runs on across sessions (ADR 0031, decision 4), so close[1] at 09:30 is the previous day's last close and ema(20) at 09:30 still uses the previous day's bars, which is what a rolling average is for. Twelve names start again on every India date: vwap, or_high(m), or_low(m), today.open|high|low, prev_day.open|high|low|close|volume and gap_pct. On an intraday timeframe (1m, 5m, 10m, 15m, 30m, 1h) the frame forgets their history at the timeframe's first bar of a new date and holds them pending (not ready at any lag, NaN) from the first 1-minute bar of the date until the timeframe has closed its first bar of it, so a lag never compares two sessions (ADR 0035). With S the number of bars the feature's timeframe has closed on the date: lag 0 is the value when S ≥ 1; lag k ≥ 1 is the value k bars ago when k < S and is unknown otherwise. It reads as if the frame had been created at the first bar of the date (for prev_day.* and gap_pct, with the values of the previous session that had bars known). The session is the India date of the start of the bar the timeframe feeds its indicators, the same date the indicators restart on. Nothing else changes: rolling and date-driven features run as before; on a 1D strategy nothing restarts (a daily bar is a whole session, gap_pct[1] is yesterday's gap and crosses_above(close, prev_day.high) reads by position); 1W and 1M refuse these names.

The first evaluations of a session. For these features every lag is unknown at the start of a session, and unknown is not true (ADR 0034, decision 3). crosses_above(close, vwap) is unknown at the first evaluation of a session (09:30 on 15m) and can be true from the second bar of the feature's timeframe; rising(vwap, 3) from the fourth; vwap[1] on the first bar is unknown, not yesterday's last vwap; not crosses_below(close, vwap) is unknown on the first bar and so does not fire either. A decision treats unknown as false, so nothing fires on it, and nothing needs a guard to stay correct: a time >= "HH:MM" check is a trading rule (when the strategy may act), not a device that makes a lag safe. A coarser timeframe is pending for longer: tf("1h").vwap is unknown until the first hourly bar closes at 10:15. The simulator (P3-03) and the live engine get this from the frame and need no code of their own; before it, crosses_above(close, vwap) compared the last bar of one session with the first of the next and was true on the first bar of about a quarter of the sessions of a seeded random walk.

Spellings. Yesterday against the day before is read on the daily timeframe: tf("1D").close > tf("1D").close[1], and likewise for the other daily values (tf("1D").gap_pct[1]). A dotted spelling cannot carry tf(…), so a per-session name on another timeframe is written flat: tf("1h").prev_day_close (tf("1h").prev_day.close is refused by the parser). A gap through yesterday's level is written in the level form, which reads the level at lag 0 only and lags the close, whose history is continuous: close > prev_day.high and close[1] <= prev_day.high is known on the first bar of a session and true on a gap up through the level, where crosses_above(close, prev_day.high) is unknown on that bar (it needs the level one bar back). The level form is the spelling for the levels of the previous day. A level that is constant within a session (today.open, prev_day.*, gap_pct, a closed or_high / or_low) is the other operand of a comparison, not the subject of a run: rising(today.open, 1) is never true intraday, while rising(today.high, 1) means "the high of the day was raised on this bar" and needs the second bar. The lint (lag_across_session) asks for no guard; it warns only about a read that no session can hold (table below).

Limits of the rule. (a) A timeframe that has not closed its first bar of the date shows nothing, even a value that is known: tf("1h").prev_day_close is unknown for up to 60 minutes. (b) A lag that fits in a session but is large (rising(vwap, 60) on 1m) is unknown for the first 60 minutes and is not warned. (c) A session is an India date: a morning and an evening block of one date are one session, and a bucket that closes late (the 15:29 minute is missing) is consumed with its own date, so it is evaluated with these features unknown and the new date stays pending. (d) or_high(m) and or_low(m) of several bars are not ready until the range has closed, which lag_across_session does not count, so it can under-warn; a value is never wrong.

time is the India clock time at which the evaluated bar closed: the start of the last accepted 1-minute bar plus one minute (the bar 09:44 makes time = 09:45; FeatureFrame.LastBarTime is its source). A 15-minute bar covering 09:30–09:45 is evaluated at time = 09:45, so time >= "09:45" first holds on that bar, not on the one before it. A time comparison is a trading window; it is not what keeps a lag of a per-session feature honest, the frame does that (Lags). The literal is "HH:MM" within 09:15 … 15:30; time is refused on a 1D, 1W or 1M strategy and is unknown before the first bar. regime() is the regime feature compared with its name or code: regime() == "UP_LOW_VOL" (names UP_LOW_VOL 1 … DOWN_HIGH_VOL 9, case-sensitive; "up_low_vol" suggests "UP_LOW_VOL"). When to evaluate is the caller's business: the simulator evaluates at the steps where frame.BarClosed(evaluationTimeframe).

Problems are data. A compile returns every problem it found, in source order: a stable code, a message that names the offending text between backticks, a span (UTF-16 offsets, 1-based line and column), a suggestion where one exists (the names at the smallest edit distance found when that is at most 2 — at most 1 for a text of one or two letters, case ignored, the nearest tier only, at most five —, the corrected literal, the explicit form) and a severity. Nothing is thrown for a bad condition. If the text does not parse the problems are the syntax ones (the first is exact, the later ones best effort, at most 100 of them: a text with more has the first 100 found listed, in source order, and one too_many_problems for the rest; lexical problems are found before syntax ones and an unclosed bracket found at the end of the text may not be listed; the recovery also stops after 232 parses of the text); if it parses, all name and lint problems are reported together, also those that sit in the same call as another fault (a rising(close + tf("1h").close, 0.5) reports the bad count and the mixed timeframes at once). Using it. ConditionCompiler.Compile(text, new CompileContext(timeframe, parameters)) returns a CompileResult: the CompiledCondition (exactly the features the text reads, in canonical form and in order of appearance; the history depth, 1 … 256; whether the frame needs a market context or expiry dates; the warnings) or the problems. ConditionSet.Merge(conditions) unites the plans of several conditions. The caller creates one frame from plan.Features with FrameOptions { HistoryDepth = plan.HistoryDepth, Calendar, Context, ExpiryDays } (the last two when the plan says so), then plan.BindAll(frame) gives a BoundCondition per condition; at each closed bar Evaluate(frame) returns the decision and EvaluateTruth(frame) the three values. A condition that reads no feature of the evaluation timeframe (time >= "09:45" reads none at all) needs one added to the frame by the caller before it can ask BarClosed. All conditions of a strategy must be bound to frames made from the same plan. Checking a condition (what an editor does) does not build the delegate; it is built at the first Bind and shared by every frame. A host that compiles on request calls CompilerWarmup.Run() once, on a thread-pool thread right after it starts and without waiting for it (the compiler warm-up: it compiles a fixed set of sources so that the JIT has compiled the compiler before the first real request; see Speed).

Why a condition cannot look ahead. The language has no word for the future: a compiled condition reads the frame through frame[handle] (the value as of the last closed bar of its timeframe), At(handle, lag) with a lag of 0 or more, and Steps and LastBarTime for time; a lag below 1 in a subscript is refused when the text is read; a lag the frame does not keep, a "previous value" across timeframes (or across a bar and a date) and a time on a bar that has no time of day are lint errors. The guarantee rests on three kinds of test, and each guards a different thing. The library is kept to those doors: an architecture test allows it to reference only seven members of the frame (four to read, three to bind), and an audit of the expression trees of about 2,700 generated conditions shows that a tree can call only the kernel, hold nothing but numbers and have no negative lag (the exact lag is held by the oracle and the hand examples). The compiler's meaning is guarded by an independent tree-walking interpreter written from these definitions, which agrees with the compiled conditions on 864 random conditions at every step, on 288 more over the twelve per-session names (read through an independent reference of the session rule, built from the definition and the catalog indicators) and on hand-calculated examples; a compiler-mutant control (a lag one bar nearer, the previous value taken as the current one, a run that forgets the lag written in its operand, the clock a minute ahead or at the start of the bar) must be caught by the same corpus. The frame's feed is guarded by a property test: for 240 seeds and 1,200 random conditions on 1m, 5m, 15m, 1h, 1D and 1W, the result at every closed bar is the same when every later bar is removed and when every later bar is replaced by arbitrary values (extreme prices, zero volume), and, on the seeds that have a market context, the same when the context days dated at or after the cut date are removed or changed (a step on a date reads the day before it); the same property run through a feeder that reads the next bar, runs the frame on to the close of a higher-timeframe bar, or lets the date lane read the context record of the date itself, reports violations (ADR 0034). What the property proves, and what it does not. It proves that, fed an honest series, the answer at a step depends on the bars up to that step and on nothing later: it guards the feed and the frame and the determinism of the chain. It cannot fail for a wrong compiler: a compiled condition is a pure function of the frame as it is at the step, so a compiler that reads the wrong lag or the wrong clock (a time one minute late, a crossing whose previous value is the current one) passes it and is caught by the interpreter and the hand examples, and "reads only the past" is held by the audit and the architecture test above. It cannot see a read of the forming bar of a higher timeframe that uses only past minutes either (a partial bar is a function of the minutes before it, and truncation does not change it); that is guarded where the bar is made — the frame never shows it (ADR 0031: the closing minute of every bucket against an independent reference, the frame-semantics tests, the prefix property) —, and the negative controls of the property are wrong feeders (the frame is sealed, so a wrapper is not possible), not a wrong compiler; the compiler is the oracle's business, with its mutant control. What none of them guards is look-ahead in the data itself (a restated close, a breadth computed with later prices: point-in-time is the data job's duty, ADR 0033).

Speed (Apple M4 Pro, Release; the benchmarks are explicit tests, which scripts/check.sh skips). Evaluation. Steady-state Evaluate allocates 0 bytes (tested over 100,000 steps of a 20-feature frame with ten conditions, date changes included; this test is in the gates). The time of a condition is bounded by its text: it never grows with the history the frame keeps or with the number of bars, but it is an upper bound and not the same for every condition. rising/falling(x, n) are a loop of exactly n steps with one read of the operand per feature in it (about 1.75 ns a read, n up to 255), with no early exit on purpose: runs are atomic over NaN, so the cost does not depend on the data; and and or skip the right side when the left one decides, so a bar can cost less than the bound. The committed benchmark Evaluate_runs_by_count gave 18 ns for rising(close, 10), 85 ns for 50, 170–190 ns for 100 and 444–449 ns for 255, and 866–868 ns for rising(rsi(14) + ema(20), 255) (the cost is linear in n: the benchmark asserts only caps four times the measured figures); RunCostTests pins the shape of the loop by counting the nodes of the expression tree, without a clock. A condition of 4,000 characters costs at most about 0.1–0.3 ms (a scratch probe, not a committed test). Ten conditions cost 245–258 ns per 1-minute step on top of the frame's own step (298 ns in that 20-feature frame; target 300 ns for the conditions, asserted by Evaluate_ten_conditions_per_set, where the share is the difference of two separately minimised timings: a guide and not a regression gate) and 47 ns while the frame stands still. The session rule of ADR 0035 costs a few nanoseconds per frame step (the 20-feature frame 0.092 → 0.094 µs; the frame step of the evaluation frame 284 → 298 ns), leaves the evaluation share unchanged within noise, and about 0.24 µs on the first bar of a session at depth 8 (doc 03 §4.1).

The strategy model as built (P3-02b, ADR 0036)#

A strategy is a typed value of schema 1 (XDrishti.Strategies.Model: StrategyDefinition, SideRules, ConditionList, StopSpec, ExitSpec, OverlaySpec, Quantity, TimeRules; sealed records that compare by value) and StrategyCompiler.Compile(definition, evaluationTimeframe, side) checks it and compiles one side for one evaluation timeframe: the result is a CompiledSide (the single feature list a frame is created from, the history depth, what the frame must be given, the warnings, and Bind(frame) → BoundSide) or the problems, each with a path (buy.trigger[1], buy.stop.lookback, time_rules.last_entry, filters[0]) and, for a problem of the language, the span inside that item. There is no YAML and no storage in it; the model arrives from C# (the three built-ins are test builders until P3-02d seeds them).

The compiled side. Features is the merge of the features of the conditions in the order of the model, then the stop's level and ATR, then those the exits read, then a close on the evaluation timeframe when nothing is on it (a frame cannot be created from an empty list and answers BarClosed only for a timeframe it has a feature on); for the example of §2 it is tf("1h").ema(20), tf("1h").ema(50), rsi(14), close, vwap, lowest(5, source=low), atr(14). BoundSide.Evaluate(frame, truths) evaluates every item (so a run can count true, false and unknown per path), writes the three-valued result of each and returns a SideEvaluation(Setup, Trigger, Invalidate) whose Fires is the one definition of the entry condition (Setup true, Trigger true, Invalidate false; unknown is not true, so an unknown invalidation neither fires nor invalidates). 3. Pipeline#

The strategy file as built (P3-02c, ADR 0055)#

The library XDrishti.Strategies.File (YamlDotNet's parser events only, pure, no I/O) turns the text of §2 into the model and back. StrategyFile.Read(text, limits?) returns the definition (null on any error), the envelope (version), every problem in one pass with its model path, line and column (file.* codes), and the position of each field; StrategyFile.Write(definition) writes one fixed layout (read then write is a fixed point); StrategyFileSchema.Json() is the JSON Schema (draft 2020-12, urn:xdrishti:strategy:1, shape only), generated from the same table as the reader and the writer and pinned by a golden file; StrategyHash.Of(definition) is the SHA-256 of CanonicalStrategy.Json(definition).

  • Shape. strategy: holds the fields of the model; the BUY side's setup, trigger, invalidate, entry, stop, exits, overlays sit directly under it and the SELL side under sell:; version is an envelope field; test and universe are read, bounded and reported as the warning file.section_not_validated; any other key is file.unknown_field. Without a sell: block [BUY, SELL] is still the compile's problem (the mirror is P3-02e).
  • Safe. Limits (256 KiB, depth 12, 5,000 nodes, 4,096 characters a scalar, 64 keys, 100 items), no anchors, aliases, tags, merge keys, second document or duplicate key; no implicit typing (a number is a plain decimal, a time is HH:mm).
  • Canonical form and hash. Taken from the model, so comments, quoting, key order, 2 versus 2.0, block versus flow style, version, test and universe do not change them; params and exit parameters are sorted by name; the order of exits and of conditions is the author's; the text of a condition is the version (rsi() and rsi(14) differ). The hashes of the three built-ins are unchanged.

Built and not yet built. For one condition, the names and look-ahead lint of step 1 and the expression-tree compile of step 2 are built in P3-02 (the library XDrishti.Strategies, doc 03 §4.2): ConditionCompiler.Compile returns every problem as data, or a compiled condition that decides over a FeatureFrame (The rules language as built, above). The schema part of step 1 is split: the typed model and the compile of its sections (at most four params, the sell: block as a field, the stop, the exits, the time rules, the filters, every problem with the path of its item) are built in P3-02b (The strategy model as built, below); the YAML file, the JSON Schema and the hash are built in P3-02c (The strategy file as built, below); the storage in lab.strategies is P3-02d; the BUY → SELL mirror is P3-02e; the explanation of errors by the assistant and the form builder come later. Steps 3 to 7 need the simulator. The engine of step 3 for one instrument is built (P3-03, P3-03a and P3-03b, doc 03 §4.3, ADR 0037 with Amendment 1, ADR 0038): Simulator.Create(definition, evaluationTimeframe, fills?) compiles a strategy and refuses by name what it cannot run yet, and Simulator.Run(instrument, bars, tick, calendar?) scans the 1-minute bars of one instrument at the closed bars of the evaluation timeframe, walks every entry and returns the trades, the positions still open when the data ended, every candidate with the reason when there is no trade, and counters that show why a rule did not fire; the first strategy it runs is ORB v1 (doc 07 §3), a bare breakout, on invented days with hand-calculated trades; the second is VWAP_PULLBACK (P3-05, doc 07 §3: the owner's proposal, 15m, BUY and SELL, hourly and daily trend setup, the stop at the pullback low), checked by hand days, a plain reference loop and the look-ahead property, and the built-in registry can declare a range for a parameter (ADR 0041 Amendment 2). Fill realism is built (P3-03b, ADR 0038): the entry is a limit order at the trigger close +0.1 % rounded to the instrument's tick that can be missed, a gapped stop fills at the open, a target never better, market-type fills pay slippage on the tick grid, and every trade carries its exact result beside the modelled one. What is not built: reading stored bars, the window of a replay and the run record (P3-04, P3-04a), the simulate verb and the trade cards (P3-04b), costs and sizing (P3-03c), swing positions (P3-03d), the walk-forward choice among exits and the learning on top of the comparison of exits on the same entries (P4-06 onward; the comparison itself is built in P4-05), the market context and the expiry dates in a simulation (P3-01d), filters, and the rest of steps 3 to 7 (the 214-instrument universe, walk-forward, robustness, the verdict, the report). A figure from this engine is a signal-level result per instrument, in-sample, with modelled fills (the entry limit of +0.1 % and slippage, ADR 0038) and no costs; the header of every result says so. Two facts of the built part carry into them. The compiler warm-up: the host that runs steps 1 and 2 on request (the Lab API, the worker) starts CompilerWarmup.Run() in the background when it starts, so that the first compile takes 3–4.5 ms instead of about 40 ms (Speed); XDrishti.Api does so with StrategyWarmupService since P3-03a, the second project that references the library, after XDrishti.Simulation (the warm-up also compiles strategy definitions since P3-02b). The first evaluations of a session: a quick test or a full test evaluates each condition at every closed bar of its timeframe, and the per-session features (vwap, or_high, or_low, today.*, prev_day.*, gap_pct) are unknown at every lag until the timeframe has closed enough bars of the date, so a crossing, a run or a lag of them is unknown at the first evaluation of every session (a crossing is known from the second bar of the feature's timeframe, rising(vwap, 3) from the fourth) and, unknown acting as false, never fires there. This is the frame's rule (ADR 0035): the simulator and the live engine neither add a guard nor treat the first bars specially, except that a frame must be fed whole sessions (a frame started in the middle of a day takes that bar's date as its session, so a live restart replays the current session from its first bar), and a strategy that wants a gap through yesterday's level writes the level form (close > prev_day.high and close[1] <= prev_day.high, Lags) or compares the daily bars (tf("1D").close > tf("1D").close[1]). A time check in a strategy is a trading window ("after 09:45"), nothing the language needs.

Runs as background jobs; progress streamed to React via SignalR; indicator results cached. As built for the quick test (P5-02, ADR 0058): the job is a hosted service of xd-api that claims queued rows of lab.lab_runs (the table is the queue; no Hangfire, not xd-worker, because only the API may name the export library that renders a stored run), max_parallel_runs at a time; progress goes to the hub as labRunProgress and labRunFinished. Full walk-forward: ~10–60 min depending on universe, timeframes and exits.

5. Guarding against "test until it passes"#

  • Every variant recorded in a per-family test ledger; thresholds tighten as variants grow.
  • Only walk-forward OOS can PASS; full_period is exploration-only.

The ledger and the gates (P5-03, ADR 0059). lab.test_ledger takes one row when a Lab run is created (not per retry; a failed or cancelled run's row stays; idempotent by run id). The family is the strategy id; the variant count N is the number of distinct strategy hashes in the family's ledger, so the same hash on another universe is one variant. With N variants the thresholds tighten by f = 1 + 0.25·log2(N) (1, 1.25, 1.5, 2 for 1, 2, 4, 16): minimum trades × f (rounded up), minimum expectancy × f, profit factor 1 + (pf − 1)·f; the fold share, drawdown and calibration gates are not changed. The verdict is PASS when every gate holds and no limit applies; FAIL when a gate other than trades is missed by more than 25 % of its adjusted threshold or the trades are below half the adjusted minimum; otherwise MARGINAL. Two honest limits cap a verdict at MARGINAL: a method other than walk_forward ("exploration, not evidence") and fewer folds than min_folds_for_pass (6). Every gate carries a reason with the actual, configured and adjusted numbers. The evaluator is pure (VerdictEvaluator in Domain); P5-04 supplies the numbers. GET /api/lab/strategies/{id}/ledger shows the rows, N and f.

The full test (P5-04, ADR 0060). Method full: all stored data, the whole universe, costs mandatory (no stored charge sheet: 422). For each declared timeframe the candidate exits (StrategyLab:FullExits, default FIXED_RR:rr=2|1.5|2.5|3; the strategy's own exit is not a candidate) run on the same entries (P4-05); the exit of each timeframe/side cell is chosen by the walk-forward of P4-06; the trades of the winners inside their test windows are pooled (a pooled fold is a test window) and the evaluator of P5-03 gives PASS / MARGINAL / FAIL with the ledger's variant count. Calibration error is not applicable (no probability model): given 0 and said in the limits. Full-period figures are printed as "exploration: in-sample" and never judged. The result is lab.lab_results (one insert-only row per run, the verdict document); the candidate runs are in research.sim_runs (actor lab:full).

Robustness (P5-05, ADR 0062). Method robust is the full test plus a robustness stage; the block is stored with the verdict in lab.lab_results and never changes the outcome. (1) Sensitivity: the first four declared parameters, each at 0.8, 0.9, 1.1 and 1.2 times the declared value (whole numbers rounded), one at a time; each point a plain run of the default exit on the run's timeframe over the whole window, in-sample, judged stable / fragile / no_base_edge / inconclusive; each point is a sweep row in the test ledger and so a variant of the family (up to 16). (2) Monte Carlo: a seeded bootstrap of the out-of-sample trades (percentiles of the mean R, drawdown, share of non-positive means). (3) By year of entry. (4) A sign-flip null instead of a random-entry run (the engine has none). (5) by_regime: unavailable until P3-01d. The field is signFlipBaseline. Limits are printed: in-sample sweep, one parameter at a time, independent-trade assumption, thin years, and that the sign-flip baseline is lenient (it tests the mean R against 0 given the trade sizes; random entries with a 2R target lose money before costs) and does not null the selection bias (the out-of-sample trades are winners of an exit selection). A parameter with a refused or zero-trade point is inconclusive, never stable; a parameter whose steps all vanish (for example a float declared as 2.0) is inconclusive with no points. A retry after a crash between the sweep rows and the result can see up to 16 more variants.

The report (P5-06, ADR 0063). GET /api/lab/runs/{id}/report for a succeeded full or robust run (409 lab.no_report otherwise), built from the stored result only: verdict and gates, out-of-sample figures, best cells, the exploration block, robustness, warnings (low_samples, cost_sensitivity, concentration, unstable_parameters, chance_not_excluded), honest limits (data range and about 2.1 years without hold-out, folds against the minimum, exploration labels, the lenient sign-flip baseline), the sections it cannot fill (notIncluded: win rate, rupees, by instrument, charts, comparisons, trade list) and a summary that is a fixed template over the report's numbers (no assistant). Also as one inert HTML page (/report/html) and a zip folder (/report/folder, with the export library's manifest).

  • Promotion always passes through paper trading.
  • The assistant can run tests but cannot promote.

6. Storage & reproducibility#

lab.strategies / lab.strategy_versions (YAML + hash; the file and the hash are P3-02c, the tables P3-02d and built, ADR 0056), lab.lab_runs (built in P5-02: the run identity, the keys of the simulation runs it produced, the counts, the located problems, the stage log, the labels), lab.lab_results, lab.test_ledger (built in P5-03: insert-only). The database is the only home of strategies (no repository folder); any version can be downloaded as a file and re-imported (ADR 0002).

Stored versions (P3-02d, ADR 0056). A version is one row, written once and never changed (xd_app can SELECT and INSERT only): the text as posted (source_text, byte for byte), the canonical text that was hashed (canonical_json, text not jsonb), the content hash (unique: the same content is one row), the parent hash and the note; the family row keeps the id, the style and whether it is a built-in, and the latest version is max(version). The three built-ins are written from embedded text by xd-api migrate after the migrations, idempotently by hash; a release that changes a text adds the next version. rr is a declared parameter of each, so --param rr=3 works on a stored strategy. A run names a stored strategy by id (latest), id and version, or hash; the engine checks the text against the stored hash before it runs (strategy_store.hash_mismatch), and the run record carries the hash, not the version number.

The library API (P5-01, ADR 0057). Create writes through IStrategyStore.AppendAsync only; the version number is the server's (max + 1, and a version in the text must equal it or be absent: 409 lab.version_exists), the same content is the same row (200, nothing written), the parent hash is the previous latest unless the request names another. The public path cannot set the store's Seed flag, so built-ins change by a release only. Texts are limited to 64 KB; a longer one is a located problem (lab.text_too_large), not a parse.

Lab runs (P5-02, ADR 0058). A Lab run is lab.lab_runs: the strategy version (id, number, hash), the universe as resolved when it was posted (a basket changed later changes nothing), the window, the method (quick), the hash of the configuration that matters (quick_test.years, .symbols, fills, cost basis) and the engine version; its key is the SHA-256 of a fixed text of those, with the instrument ids sorted. A partial unique index on the key (queued, running or succeeded) makes the same post the same run; a failed, cancelled or interrupted run frees the key. States queued, running, succeeded, failed, cancelled, interrupted; stages validate, compile, quick_test, each logged. The quick test replays the last year of stored data (ending at the last stored session) on at most 30 instruments (the first 30 of a seeded shuffle of the sorted ids when there are more; the seed is in the record), through the same handler as the simulate verb, and keeps the simulation run in the result store whole or not at all; the Lab run points at its key. Its labels say that it is exploration, not a verdict, whether it was costed (the stored sheet StrategyLab:CostSheetId when in force) or gross, the window, the sample and the stored data range. A restart ends the runs it interrupted as interrupted; the owner starts them again. xd_app inserts a run and updates its state columns only; it cannot delete.

The run record is the reproducibility record (P3-04, ADR 0037 Amendment 2; the Lab will store it). A simulation run returns a SimulationRun (schema 3) that holds enough to check it again: the strategy (its id, the effective parameters, the canonical JSON of the definition (ADR 0055: CanonicalStrategy) and its SHA-256), the engine version (SimulationEngine.Version), the window, the data-note options, the fill rules, the universe with its label, the exceptions of the trading calendar in the range of the data, and, per instrument, the SHA-256 of the stored bars it read, the applied corporate actions that changed them, the sessions that ran and those left out and why, the flagged days, the counters of the scanner and the walker, and the fate of every candidate. The run key is the SHA-256 of a fixed text of those inputs: the same key means the same inputs, and any change of data (one price by one tick), strategy text, parameter, option, fill rule, tick, window, universe label or calendar exception in range changes it. The record reads no clock and no random source; when and how long a run took belong to the caller. Because a trade does not depend on the window asked for (the replay starts at the first stored session), re-running a window of a stored run gives the same trades. A run record from before ADR 0056 differs from the same run after it only by the built-in's hash (the three built-ins gained rr as a declared parameter once, so their definition text and hash changed; the trades did not).

Where a run is kept (P3-10, ADR 0045). simulate … --store keeps the run in research.sim_runs (the header as typed columns plus the record without its trades as canonical text) and research.sim_trades (one row per trade, every field a column), insert-only for the app, idempotent by run key. research.sim_runs is the engine's output store; a later lab.lab_runs row (P5) points at a run key, so the Lab never copies trades. The same-entries comparison across exit policies (P4) joins two runs on trade_key; the evidence ledger (P7) aggregates the typed columns with open_at_end = false.

Trades with legs in the record (P4-01, ADR 0049). Engine sim-6, trade schema 5, run-record schema 6 and the export format xd-sim-export-3: trades.csv has a legs column (empty for a trade that entered and left in one fill each, which is every trade of a P3 run), run.json has the legs of a trade and the leg_charges of its costing (null otherwise), and a card of a trade with legs has a legs section. Since P4-05 (ADR 0053) the result store holds the legs in two child tables (research.sim_trade_legs and research.sim_trade_leg_charges, migration AddSimTradeLegs, insert-only) and simulate --store no longer refuses a trade with legs; a run stored under sim-5 is read as before. The new exit reason time_stop is stored (migration AddTimeStopExitReason).

Choosing and comparing exits (P4-05, ADR 0053). simulate and verify-pack take --exit and --time-stop (verify-pack one candidate only). Two candidates or more are a comparison: one scan and one walk of each candidate on the same entries, one run record and one stored run for each candidate, and a folder (xd-sim-export-4) with comparison.csv, diagnostics.csv and the trades and run record of each candidate. A stored comparison (research.sim_comparisons, migration AddSimComparisons) names its member runs, the entries key (the run key without the exit: two runs with the same entries key join on trade_key) and the text of its tables.

The exported record and its labels (P3-04b1 and P3-04b2, ADR 0041). Until the Lab stores runs, the owner runs scripts/simulate.sh and gets, under data/exports/sim/<run-id>/, trades.csv and open_at_end.csv (one row per trade; the trades the data cut short are apart on purpose), run.json (the whole run record, the labels and the format xd-sim-export-2), README.txt and manifest.json (the size and SHA-256 of every file and the export key), and, since P3-04c, index.html and a capped, deterministic sample of static HTML trade cards under cards/ (--cards, default 200): per trade the 1-minute candles of the day with entry, stop, target and exit, the timeline, the R arithmetic with every operand, the rule text, the stored 09:15 bar and the data notes, under the same banner, with no script and no statistic. The same labels are printed first on the console, written into run.json and put at the top of README.txt: exploration, not evidence of an edge; the fills (and, with --fills no-slippage, that there is no slippage and no tick rounding); the entry limit; the costs (costs: none for a gross run, costs: sheet <id> with its notes for a run charged by a stored sheet, ADR 0044); portfolio limits not simulated; in-sample; the universe as of today with its survivorship note; the data line; the engine line (agrees with a separately written reference implementation of the rule tables (P3-08, sim-6); not checked against charts or the owner's charge sheet: a second implementation written from the rule tables agrees with the engine, ADR 0047; the flag is bound to the engine version by a test); the tick; the opening bar; and the list of what the fills do not model. No file and no console line prints a performance statistic. The run id is <strategy>-<from>-<to>-<12 hex of the run key>; the same export again is recognised by hashing the files, a different one under the same id is refused unless forced, and a forced replacement keeps the old folder once as <run-id>.previous.
