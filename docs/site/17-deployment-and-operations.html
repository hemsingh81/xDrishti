17 — Deployment & Operations (Podman, local-only)

Everything runs in Podman containers on your Mac. No cloud service is required; internet is used only for broker/exchange APIs.

1. Podman machine#

  • Containers run in a Linux VM (Podman machine). Use the libkrun provider on Apple Silicon — it gives containers GPU acceleration (Vulkan), which xd-llm needs.
  • Size: 10 CPUs, 24 GB RAM, 120 GB disk (decision Q8; confirmed by the xd-llm benchmark in P0-15, 2026-10-10: with the 30B model loaded and the stack running the VM peaked at 5.3 GB because model weights live in GPU memory). Revisit the disk before tick-data storage (P13).
  • Static IP (decision Q6): not needed until automated orders (P12) — see §6.
  • The host Mac (48 GB) is already swapping heavily (28–42 GB of macOS swap in use in the sampled P0-15 runs); a resident 30B model adds ≈ 20 GB of GPU memory and loaded in 22–105 s (cause not established). xd-llm is therefore started on demand (ADR 0005).
  • Disk budget: VM disk 120 GB (originally planned 250 GB) holds the images, databases and, if used, the 18.6 GB model volume; revisit before tick data (P13).
  • Source code: local git only (decision Q7) — no remote yet. Keep a copy outside the Mac's internal disk (Time Machine or the external SSD) until a remote is chosen; xd-backup protects data, not code.
  • The Mac must be awake for nightly jobs (and during market hours for later live services): no sleep on power, wired network, small UPS recommended.

Phone access (owner security act; nothing here is done by an agent or by the repo)#

The stack never listens on the LAN: every published port stays on 127.0.0.1. The installable app (P8-21, ADR 0132) works on this Mac at http://localhost:8080 once you switch pwa on at /owner-acts (a browser treats localhost as a secure context). A phone needs HTTPS, which does not exist yet. If you want it, the researched path (spec P8-21 D1) is a private tailnet in front of the loopback proxy:

  1. Decide it is worth it: a third-party coordination service and an account (the traffic is end-to-end encrypted between your devices; the service sees metadata). Pricing and terms were not checked.
  2. Install the VPN client on the Mac and the phone, sign in, enable its name service and HTTPS certificates. Certificate names go into a public ledger: rename the Mac to a neutral name first. Keep public "funnel" sharing off and device sharing off; keep key expiry on.
  3. A second HTTPS-facing entry for the proxy (one shared Caddy snippet, X-Forwarded-Proto https, HSTS, still bound to 127.0.0.1) is not built yet; it needs its own slice and your approval. Until then do not publish port 8080 through the tunnel.
  4. Risks: a lost unlocked phone with an open session shows plans (idle timeout, lockout and sign-out clearing exist; your phone lock is the real control); the login page is reachable by anything in your tailnet.

If you do not do this, nothing is lost: "no phone access" is a valid state.

4. Secrets#

  1. Source of truth: macOS Keychain (xdrishti/<area>/<name>: DB passwords, owner sign-in, broker vault key, backup key). Broker API keys, secrets and tokens are the exception: they are entered in the app and stored encrypted in the database (item 4).
  2. deploy/xd-up.sh reads the Keychain (creating strong random DB passwords on first run) → writes secret files to ~/Library/Application Support/xDrishti/secrets (private folder) → Compose mounts them as file secrets (ADR 0003).
  3. Containers receive only what they need (mounted at /run/secrets/<ConfigKey>, read by .NET KeyPerFile provider). The owner's sign-in credentials (xdrishti/auth/owner-email|owner-name|owner-password) are never generated: xd-up.sh asks for them at a terminal (hidden password prompt) or fails with a pointer to scripts/auth-secrets.sh. They are mounted only into xd-migrate (creates the owner when none exists) and the on-demand xd-owner-reset (profile tools, xd-up.sh --owner-reset), never into the running xd-api.
  4. Broker credentials (ADR 0008, replacing the credential references of ADR 0007): the owner enters each account's API key and secret in the app (write-only, step-up); the API stores them in accounts.broker_secrets encrypted with AES-256-GCM (account id + secret name as associated data, key version per row). The key material is the Keychain item xdrishti/broker/vault-key: xd-up.sh creates it (32 random characters) only when no such item exists — an item that exists but cannot be read stops the start instead of being replaced, because another key makes every stored secret unreadable — and writes the secret file broker_vault_key, mounted only into xd-api as /run/secrets/BrokerVault__Key (the 256-bit key is derived from it with HKDF-SHA256). Back it up with the database. A second key, xdrishti/exec/handover-key (ADR 0171), is created by xd-up.sh the same way (file exec_handover_key, mounted only into xd-api and xd-exec as ExecHandover__Key, never xd-feed or xd-worker): the API seals the day's access token with it into accounts.exec_token_handover at every login, and the API refuses to start without it. A changed key only makes the hand-overs unreadable until the next login. The former scripts/broker-secrets.sh, secrets/brokers.index and the read-only secrets/brokers mount are gone (xd-up.sh deletes leftover files). The three secrets of the tool server (xdrishti/db/mcp-read, xdrishti/db/mcp-sql, xdrishti/mcp/token; 32 random characters each, created once and never replaced by xd-up.sh; files db_mcp_read_password, db_mcp_sql_password, mcp_token) go to xd-mcp; xd-migrate also reads the two passwords (it gives the read-only roles their login, ADR 0137) and xd-api the token only. Without the password files the roles stay NOLOGIN and migrate still succeeds. The key of the local model server (xdrishti/llm/api-key, 32 random characters, created once and never replaced by xd-up.sh; file llm_api_key) is mounted into xd-llm (--api-key-file) and xd-api (Assistant__Llm__ApiKey) only (ADR 0136).
  5. Never in images, compose files, environment dumps, logs or LLM context.
