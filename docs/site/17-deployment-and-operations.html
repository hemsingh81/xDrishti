17 — Deployment & Operations (Podman, local-only)

Everything runs in Podman containers on your Mac. No cloud service is required; internet is used only for broker/exchange APIs.

1. Podman machine#

  • Containers run in a Linux VM (Podman machine). Use the libkrun provider on Apple Silicon — it gives containers GPU acceleration (Vulkan), which xd-llm needs.
  • Size: 10 CPUs, 24 GB RAM, 120 GB disk (decision Q8; confirmed by the xd-llm benchmark in P0-15, 2026-10-10: with the 30B model loaded and the stack running the VM peaked at 5.3 GB because model weights live in GPU memory). Revisit the disk before tick-data storage (P13).
  • Static IP (decision Q6): not needed until automated orders (P12) — see §6.
  • The host Mac (48 GB) is already swapping heavily (28–42 GB of macOS swap in use in the sampled P0-15 runs); a resident 30B model adds ≈ 20 GB of GPU memory and loaded in 22–105 s (cause not established). xd-llm is therefore started on demand (ADR 0005).
  • Disk budget: VM disk 120 GB (originally planned 250 GB) holds the images, databases and, if used, the 18.6 GB model volume; revisit before tick data (P13).
  • Source code: local git only (decision Q7) — no remote yet. Keep a copy outside the Mac's internal disk (Time Machine or the external SSD) until a remote is chosen; xd-backup protects data, not code.
  • The Mac must be awake for nightly jobs (and during market hours for later live services): no sleep on power, wired network, small UPS recommended.

Network Members
front proxy (the only published port), seq (ops)

egress (not internal, nothing published) api only (P1-16c, P1-03)

*xd-sandbox has no egress and no access except its job inputs/outputs. xd-api joins egress for Dhan's sign-in (ADR 0008, 0009), for the read of the account's holdings (ADR 0012), for the 1-minute chart data of the Data API (ADR 0016), for the trade history and the ledger of the account (ADR 0025) and for the instrument master files and NSE's trading-holiday list (ADR 0010, ADR 0017): outbound only, no published ports, no other member. The network itself does not filter hosts; the API's HTTP clients do (HTTPS, exact host and path, method, no redirects, no cookies or credentials, size caps and timeouts):

Client Reaches only Method Limits
Broker (Dhan sign-in) auth.dhan.co: /app/generate-consent, /app/consumeApp-consent (doc 05 §8.1) POST 15 s, 256 KB; no order, position or funds endpoint is callable
Broker (Dhan holdings) api.dhan.co: /v2/holdings only, no query (doc 05 §8.2) GET 30 s, 5 MB; the stored access token goes in the access-token header and is never logged; the other api.dhan.co paths that are callable are the rows below, never an order, position or funds path
Broker (Dhan trade history) api.dhan.co: /v2/trades/{yyyy-MM-dd}/{yyyy-MM-dd}/{page} — two valid dates and a page number in the path, no query (doc 05 §8.3; ADR 0025) GET 30 s, 5 MB; calls at least Portfolio__BrokerHistory__CallSpacingMs (250) apart; the account's access token goes in the access-token header and is never logged, nor are the URL or the rows
Broker (Dhan ledger) api.dhan.co: /v2/ledger with the query of exactly from-date and to-date, each once, valid dates (doc 05 §8.3; ADR 0025) GET same limits and spacing as the trade history
Broker (Dhan chart data) api.dhan.co: /v2/charts/intraday only, no query (doc 05 §6; ADR 0016) POST 15 s, 16 MB; one request at a time, at most Data__Dhan__RequestsPerSecond (4) per second, one retry on 429/5xx; the Data account's access token goes in the access-token header and is never logged; no other chart, order, position or funds path is callable
Instrument master — Dhan images.dhan.co: /api-data/api-scrip-master-detailed.csv (doc 05 §7.1) GET 120 s, 100 MB
Instrument master — NSE nsearchives.nseindia.com: /content/indices/ind_niftytotalmarket_list.csv GET 30 s, 5 MB
Trading calendar — NSE holidays www.nseindia.com: /api/holiday-master with the query exactly type=trading (a fixed query text; the Dhan ledger above takes two date keys, the sign-in calls one key each; doc 05 §4.1, ADR 0017) GET 20 s, 1 MB; browser-like User-Agent and Accept: application/json, no cookie (none is kept or sent, and nothing from a stored secret), no redirects; a refusal is only a warning

Nothing else is needed for the master: no published port, no volume (the file is streamed, never written to disk), no secret; xd-api stays within its 1 GB limit (the 35 MB file is read as a stream). The database image already includes pg_trgm, which the migration enables for the search indexes (created by xd-migrate as xd_owner).

4. Secrets#

  1. Source of truth: macOS Keychain (xdrishti/<area>/<name>: DB passwords, owner sign-in, broker vault key, backup key). Broker API keys, secrets and tokens are the exception: they are entered in the app and stored encrypted in the database (item 4).
  2. deploy/xd-up.sh reads the Keychain (creating strong random DB passwords on first run) → writes secret files to ~/Library/Application Support/xDrishti/secrets (private folder) → Compose mounts them as file secrets (ADR 0003).
  3. Containers receive only what they need (mounted at /run/secrets/<ConfigKey>, read by .NET KeyPerFile provider). The owner's sign-in credentials (xdrishti/auth/owner-email|owner-name|owner-password) are never generated: xd-up.sh asks for them at a terminal (hidden password prompt) or fails with a pointer to scripts/auth-secrets.sh. They are mounted only into xd-migrate (creates the owner when none exists) and the on-demand xd-owner-reset (profile tools, xd-up.sh --owner-reset), never into the running xd-api.
  4. Broker credentials (ADR 0008, replacing the credential references of ADR 0007): the owner enters each account's API key and secret in the app (write-only, step-up); the API stores them in accounts.broker_secrets encrypted with AES-256-GCM (account id + secret name as associated data, key version per row). The key material is the Keychain item xdrishti/broker/vault-key: xd-up.sh creates it (32 random characters) only when no such item exists — an item that exists but cannot be read stops the start instead of being replaced, because another key makes every stored secret unreadable — and writes the secret file broker_vault_key, mounted only into xd-api as /run/secrets/BrokerVault__Key (the 256-bit key is derived from it with HKDF-SHA256). Back it up with the database. The former scripts/broker-secrets.sh, secrets/brokers.index and the read-only secrets/brokers mount are gone (xd-up.sh deletes leftover files).
  5. Never in images, compose files, environment dumps, logs or LLM context.

5. Operations#

Topic Approach
Start at boot launchd agent → podman machine start → xd-up.sh; services run with no user logged in to the app
Missed schedules On start, services catch up missed runs (e.g. EOD fetch while the Mac slept) and reconcile desired state
Schedules Stored in the database (platform.service_schedules, runs in platform.service_runs), edited on the Services screen with dependency validation and applied at the scheduler's next look (at most a minute) without restart. Built (P1-13, ADR 0018): one ServiceScheduler hosted in xd-api; the Hangfire jobs of xd-worker follow when that container exists (a deployment change, not a design one)
Database migrations EF Core migrations applied by the one-shot xd-migrate service (API image, migrate command, as xd_owner) before xd-api/xd-worker start; apps connect as least-privilege xd_app; the migrations create market.undo_csv_bars, the one SECURITY DEFINER function (owned by xd_owner, executable by xd_app only) through which the app removes bars when the owner undoes a CSV load (doc 05 §9)
Start / stop deploy/xd-up.sh (secrets → build → start → wait healthy → print URLs), deploy/xd-down.sh (--purge deletes data)
URLs (local) App http://localhost:8080 · API docs /api/docs · Seq http://localhost:5341 · PostgreSQL localhost:5433 (dev override)
Upgrades Versioned image tags; roll back by switching tag
Backups Nightly pg_dump + models + config → restic on external SSD; monthly restore test
Health ASP.NET health checks per container; failures → in-app notification
Logs Serilog → Seq; container log rotation
Disk Timescale compression; tick data (later) ~50–100 GB/year → external SSD volume
CSV inbox Host folder data/inbox/ bind-mounted into xd-worker; processed files moved to data/processed/<job-id>/
CSV folder (P1-17a) Host folder data/Stocks_CSV/ (XD_CSV_DIR) bind-mounted read-only at /data/csv into xd-api (Data__CsvFolder); xd-up.sh creates it when missing; nothing is written there (ADR 0016)
Market hours xd-feed runs all day and connects between 09:00 and 15:35 on trading days (the window of the service live-feed, editable on the Services screen); it heartbeats outside the window. Mac must be awake (the owner's job; xd-up.sh holds no keep-awake)
Remote access Off by default; optional WireGuard on home router
Simulation runs (P3-04b2) The simulate verb is not a container service: scripts/simulate.sh runs it on the host (dotnet run of the API project with the argument simulate; since P3-03f every run names its cost choice, --gross or --costs <sheet-id>) against the developer database port (xd-db on 127.0.0.1:5433, compose.dev.yaml). The one secret is the database password, read from the Keychain item xdrishti/db/app; no vault key and no owner secret. Files go to data/exports/sim/<run-id>/ (Export__Directory, git-ignored, owner-only) and, since P3-04c, include index.html and cards/ (static trade cards, --cards, default 200: the verb reads the bars of the instruments that have a card a second time, so a wide run takes longer; --cards 5 for an early look, --cards 0 for none); nothing is written to the database unless --store is given (P3-10, next row). The Lab (P5) and the scanner (P7) reuse the handlers, not the verb
Result store (P3-10) scripts/simulate.sh … --store keeps the run in research.sim_runs and research.sim_trades after the export files are written (files first; a database failure keeps them): stored: run <12> or already stored; exit 1 refused by validation, 3 a conflict (store.run_conflict: the same run key with another record, a corruption signal, nothing written) or a database failure. Default off. The runtime role can read and insert but not update or delete, so a stored run is removed by hand, connected as xd_owner (not xd_app), in one transaction with the trades first: BEGIN; DELETE FROM research.sim_trades WHERE run_id = (SELECT id FROM research.sim_runs WHERE run_key = '<key>'); DELETE FROM research.sim_runs WHERE run_key = '<key>'; COMMIT;. About 0.7 KB a trade (a 200,000-trade run is about 130 MB); revisit the plain tables (a hypertable with compression) when pg_total_relation_size('research.sim_trades') passes 2 GB. The migration AddResearchResultStore is applied by xd-migrate on the next deploy/xd-up.sh; until then --store exits 3 and names it
Verification pack (P3-09) The verify-pack verb is not a container service: scripts/verify-pack.sh runs it on the host exactly like simulate.sh (the same generic host, the same Keychain item xdrishti/db/app, Export__Directory set by the script) and writes data/exports/verify/<pack-id>/ (git-ignored, 0700/0600); verify-pack --check <log> reads files only and needs no password. It writes nothing to the database and never uses the result store. See ADR 0046.
Charge sheet (P3-03f) The cost-sheet verb (load, show, check) is not a container service either: scripts/cost-sheet.sh runs it on the host exactly like simulate.sh (the same generic host, the same Keychain item xdrishti/db/app, no vault key and no owner secret; a file argument may be relative, the script makes it absolute before it changes directory). The sheet is one row of platform.app_settings; check reads your original global transaction report files from the host (a container verb such as owner-reset mounts secrets and could not read them) and writes nothing. Since P3-03f every simulate run names --gross or --costs <id>. The migration WidenAppSettingValue (value column 500 to 8,000) is applied by xd-migrate on the next deploy/xd-up.sh
Dev loop dotnet watch and Vite dev server on the host against containerised db/llm/ml; same images for "prod"
