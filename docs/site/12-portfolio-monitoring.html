12 — Portfolio Monitoring

Add your broker accounts and monitor every trade and holding: when it was added, current value, return %, XIRR, and totals — grouped by basket, account, strategy or sector.

1. Data sources#

Source What it provides When

Lots are refined from a tradebook CSV or from trades typed in by hand (P2-03, built: §3 "Trades and the rebuild of lots"); from P2-13 also from Dhan's trade history and ledger, read nightly (ADR 0025, §3 "Dhan sync (P2-13)").

2. Domain model#

  • Transaction — immutable record (source: broker / CSV / manual; charges attached: counted in the net returns, not in the cost or the lots, P2-14). Built in P2-03 for CSV and manual trades (portfolio.transactions, §9); the broker source (source = broker) is built in P2-13 with the Dhan trade-history sync (§3).
  • Lot — each buy creates a lot; sells consume lots FIFO (matches Indian practice) → realised P&L per lot.
  • Position — open quantity, average cost as the broker reports it (charges are a separate line, not part of the cost: ADR 0026), first-added date, linked plan ticket (if any).
  • Valuation — market value at a time; a daily snapshot after close builds the portfolio value history.
  • Cash flow — dated money in/out used for XIRR.

Where acquisition dates come from#

XIRR, % return and absolute return need the date and size of every cash flow. Dhan's GET /v2/holdings gives quantity, average cost price, last traded price and ISIN, but no purchase date (docs read 2026-10-11), so the dates are set by the owner (ADR 0012, P2-01). This replaces the earlier idea (P1-16e) of deriving them from Dhan's trade and ledger APIs; ADR 0025 (P2-13) reinstates the trade API — as stored trades from which lots are rebuilt where that is safe, not as a replacement for the owner's dates.

The first import is part of saving the account's Portfolio settings (ADR 0013, P2-01a); there is no separate import endpoint or dialog. The settings carry a first import date (firstImportDate, default 1 Jan 2025, between 1990-01-01 and today India). When the account is connected, has the Portfolio role and has no holdings in the system, Save (PUT /api/accounts/{id}/portfolio) stores the settings and then imports in the same request, without any per-holding list on the settings screen: Dhan is fetched again inside one transaction, one holding with one lot (Dhan's quantity and average cost) is created for every holding Dhan lists, in the account's bucket (its own default bucket or the custom bucket chosen in the settings), dated with the first import date and flagged uses_default_date (counted on the Portfolio screen until its date is edited there). firstImport.rows = [{key, acquiredOn?}] is an optional API detail: a row's date overrides the default for its key. The run is recorded with the trigger import. The answer carries the result: import.status imported (counts imported, defaultDated, alreadyImported, unknown), skipped (the account already has holdings: nothing is imported, Dhan is not called; redated/redateSkipped say how many lots followed a changed first import date), deferred (not connected, or role off: nothing is called) or failed (the settings are still saved; import.errorCode portfolio.import_failed, import.cause the reason code such as portfolio.not_connected or portfolio.sync_running; retry with Save again or Sync now). Invalid dates or rows are 400 accounts.invalid (fields firstImportDate, firstImport.rows[i].key, firstImport.rows[i].acquiredOn) and nothing is saved. An account that is not connected keeps the stored first import date, and its first sync — manual or daily — performs the import: every holding Dhan lists gets one lot dated with the first import date (flagged as default, editable per lot) and the run is recorded as import. After that nothing imports again: saving the settings again imports nothing, and everything else arrives through the refresh below. The first import date stays editable (ADR 0015, P2-01b): saving a changed date on an account that has holdings re-dates, in the same unit of work, every lot with source = import and uses_default_date = true to the new date (the lots stay flagged; a closed lot whose closed_on is before the new date cannot take it and is skipped). Lots the owner dated by hand, lots found by refreshes and manual lots are never touched; returns and XIRR are computed on read, so they follow. No Dhan call is made (import.status stays skipped); the answer's import carries redated and redateSkipped (lot counts, 0 when the date did not change or the account has no holdings). The same date again changes nothing. The change is audited once (FirstImportDateChanged: old and new date and the counts, no per-lot data). Without holdings only the date is stored.

Lots. A holding has lots (acquired_on, qty, unit_cost); a closed lot also has closed_on, close_price and estimated. A partial sale splits a lot into a closed piece and an open remainder with the same date and cost, so every lot has one close price. The open quantities always add up to Dhan's quantity, and the holding's quantity and average cost are always Dhan's after a sync. Any lot's date can be edited later (PUT /api/holdings/{id}/lots/{lotId}); figures are computed on read, so they follow at once.

Sync rules ("Sync now" and the daily refresh run the same command, for an account that already has holdings; one transaction per account, idempotent):

Dhan says Result
A holding the account does not have (or had closed) New holding (or reopened) with one lot dated today (India), unit cost = Dhan's average cost, source added, not flagged as default date
Quantity increased by Δ A lot dated today for Δ at the implied cost max(0, (newQty × newAvg − oldQty × oldAvg) / Δ); when that is not positive, the last price (then the new average)
Quantity decreased by Δ Lots closed oldest first (FIFO) for Δ at the last price, marked estimated
Holding missing Same, for the whole quantity; the holding becomes closed (kept, with its realised result)
Same quantity Last price, price time and Dhan's average cost only

A run that fails leaves every holding untouched and is recorded (portfolio.holding_syncs: manual / auto / import, status, counts, a short safe error). One run per account at a time (advisory lock plus a unique "running" row; 409 portfolio.sync_running); a run left running by a crashed process is ended when the API starts. Safeguard against a false "Dhan lists nothing". An empty answer (a 200 [] or Dhan's documented DH-907 "no data") or a broken one can look like a sale of everything, and closing every holding then reopening it dated today would destroy the owner's acquisition dates. So a sync whose answer would close all open holdings (empty answer) or more than half of them with at least 3 (exactly half does not count; fewer than 3 never counts unless the answer is empty) changes nothing unless confirmed:

  • a manual sync answers 409 portfolio.confirmation_required with the numbers listedHoldings, openHoldings and wouldClose and a message such as "Dhan listed 0 holdings while 3 are open in xDrishti" or "Dhan listed 2 holdings but 4 of your 6 open holdings are missing"; the UI shows them and repeats the request with {"confirm": true, "expectedOpenHoldings": 6, "expectedWouldClose": 4} (both numbers are required with confirm; 400 portfolio.invalid otherwise), which applies the closes by the rules above;
  • if Dhan's answer has changed since (the numbers differ), nothing is applied and the answer is 409 portfolio.confirmation_stale with the fresh numbers;
  • an automatic run never confirms — it is recorded as skipped with the same reason text ("… — nothing was changed; press Sync now to confirm."), visible as last in the sync status, with at most one skipped record per account and India day (the latest check replaces the earlier one).

Records are kept 90 days. After an automatic run, finished holding_syncs rows older than 90 days that did not fail are deleted (at most 500 at a time); failed runs stay.

A token Dhan refuses is 409 portfolio.not_connected ("sign in to Dhan again"); Dhan being unreachable is 502 accounts.broker_error. Sells between two syncs are estimated at the last price of the sync that noticed them; a possible corporate action (split, bonus) shows up as a quantity change.

Mapping to the instrument master. By ISIN first (shares and ETFs, series EQ preferred), then by Dhan's security id within the NSE equity segment. Holdings that cannot be mapped (for example BSE only) are kept, flagged "not in master list" (mapped = false), and still get returns from Dhan's price.

Automatic refresh (per account, off by default, ADR 0013). Portfolio settings: refreshMode off | daily (the interval mode no longer exists; existing interval settings were switched off by the migration) and refreshDailyTimeIst HH:mm (default 16:00, after the close). A hosted service in xd-api looks once a minute at every Portfolio-role account whose refresh is on and runs the same sync:

  • daily: once a day from the configured India time on, weekends included; if the time was missed (the application was down) it runs as soon as possible the same day; a failed or skipped automatic attempt counts as that day's run, a manual run does not (the first automatic run of an account without holdings is recorded as import and counts too);
  • an account that is not connected (no token, expired) is not called: one skipped record per India day;
  • runs never overlap (accounts one after the other, one running row per account); "Sync now" works at any time; the whole mechanism is switched off with Portfolio:AutoRefresh:Enabled = false (doc 16). GET /api/accounts/{id}/holdings/sync-status returns refreshMode, refreshDailyTimeIst, firstImportDate, hasHoldings, the next scheduled run, running and the last run.

Gross and net (P2-14, ADR 0026). The gross figures — P&L, P&L %, XIRR, the value history, the benchmark and alpha — are price returns: they do not include dividends or charges, and the UI says so. Next to them the net figures include the dividends the owner entered and the charges paid (the charges of the stored trades, and at account and total scope the ledger's account-level costs), each counted only from the date its source is known (§3 "Dividends, charges and net returns (P2-14)"). Not in any figure: taxes (including TDS on dividends), dividend reinvestment and corporate actions. The rest of the Dhan ledger (funds in and out, anything unrecognised) is shown in the Cash & dividends panel and nowhere counted (§3 "Dhan sync (P2-13)").

Trades and the rebuild of lots (P2-03, ADR 0023)#

A broker tradebook (CSV), trades typed in by hand or (P2-13) trades read from Dhan are stored as transactions. For CSV and manual trades a holding's lots are rebuilt from the real buy and sell dates on an explicit and previewed step; the Dhan sync rebuilds automatically where that is safe (below), so the previewed step is no longer the only path. Either way XIRR, returns, the value history and the benchmark use true dates and real sale prices (a sale closes a lot at its real price, estimated = false). The broker stays authoritative for the quantity and the total cost of a holding: trades can only explain a holding, never change what Dhan says is held.

Transactions. portfolio.transactions: account, instrument (when mapped), ISIN, symbol, exchange, side buy/sell, India trade_date and optional trade_time, qty (whole shares, bigint), price, charges (one total: counted in the net returns since P2-14, as a separate line — not in the cost, the lots or the gross figures), source csv/manual/broker (broker since P2-13, with a nullable run_id), batch_id, seq (the line of the file, 0 for a manual trade), external_id, who/when and voided_at/by. A transaction is immutable except for being voided — the runtime role has no DELETE. external_id is the trade's identity and is unique per account among the trades that are not voided (a partial unique index), so a voided trade (or an undone file) can be imported again: the trade id of the file together with the trade date (t:yyyyMMdd: + id — exchanges number trades per day, so the same id on two days is two trades) when it has such a column, else a hash of (account, date, time, symbol or ISIN, side, quantity, price, order id, how many identical lines came before in the file) (h: + 32 hex), so two genuine identical trades are both kept and the same file read again adds nothing; a manual trade has a random identity (m:) and is never deduplicated. Import batches (portfolio.trade_batches): file name, SHA-256 (the file itself is never stored), counts (parsed, imported, duplicates, skipped, bad), status imported/undone, who/when; a file that adds nothing new makes no batch. Neither table is ever deleted.

The file (generic, auto-detected, UTF-8 with or without BOM, comma separated, at most 10 MB and 20,000 data rows). Headers match without regard to case or punctuation. Required: a date, a symbol or an ISIN, a side, a quantity, a price (a missing one refuses the file with 400 portfolio.invalid on field file, naming what is missing and the accepted names). Accepted names, among others — date: date, trade date, transaction date, order execution time; symbol: symbol, trading symbol, scrip, instrument, security, stock name; isin; side: trade type, side, buy/sell, transaction type; quantity: quantity, qty, traded quantity; price: price, trade price, rate, avg price; optional: exchange, trade id/trade no (the identity), order id (only part of the line hash), time, segment/instrument type (to skip non-equity rows), charges. Unknown columns are ignored. Dates: yyyy-MM-dd, dd-MM-yyyy, dd/MM/yyyy, dd-MMM-yyyy — day first, never MM/dd (13/25/2024 is a bad row) — optionally followed by an India time; a date in the future is a bad row. Numbers take . for decimals and , only to group thousands (1,234.50, 12,34,567). Side: buy/sell/b/s/purchase/sale. Symbols are upper-cased and trimmed; NSE: and -EQ are stripped. Quantity must be a whole number above 0, price above 0. Charges: a total charges/charges column is used as it is, otherwise the component columns (brokerage, STT, stamp duty, GST, taxes, …) are summed, never both. Rows for derivatives, commodity or currency segments (by the segment/instrument-type/exchange column, or by the shape of the symbol: expiry, strike, FUT, CE, PE) and BSE rows are skipped with a reason (counts per reason); a bad row (line, reason — at most 200 listed, all counted) is never imported; a trade id that repeats on the same day with identical details is counted as a duplicate, with different details it is a bad row. A cell longer than 64 characters in a date, time, number or ISIN column makes the row bad (no pattern ever looks at a huge cell). GET /api/portfolio/trades/template downloads a CSV with the canonical headers and two example rows (Date,Symbol,ISIN,Side,Quantity,Price,Exchange,Trade ID,Time,Charges).

Which holding a trade belongs to. Among the account's open holdings: by ISIN; when no holding has the trade's ISIN (or the trade has none), by symbol — but a symbol never joins two different ISINs. More than one candidate is ambiguous (not applied). A security that matches no holding is not held: its trades are stored and listed ("12 trades for 4 securities not held"), not applied; if it matches neither a holding nor an NSE share/ETF of the instrument master it is also counted as unmatched. Closed positions are not created from trades.

Reconstruction (pure, deterministic, idempotent; LotReconstructor). For a holding with the broker's quantity Q and average cost A, from its non-voided trades:

  1. Each trade is converted to today's share basis with the instrument's applied corporate actions whose ex-date is after the trade date (a trade on the ex-date or later is already on the new basis), in the direction of the bar adjustment (AdjustmentFactors: bars before the ex-date are multiplied by the action's factor): price × factor, quantity ÷ factor, cumulative over the actions in ex-date order (a 1:5 split has factor 0.2: 10 shares at 1,000 become 50 at 200; a 1:1 bonus has factor 0.5; a split and a bonus multiply). The quantity is computed exactly from the ratio and must come out whole (quantity_mismatch, reason fractional_after_adjustment, otherwise — 3 shares before a 1:2 bonus are 4.5). Suggested and ignored actions are not used. The result says adjustedFor: n.
  2. net = bought − sold; the opening quantity P0 = Q − net. P0 < 0: the trades explain more shares than Dhan holds → quantity_mismatch (negative_opening), nothing applied.
  3. Trades are walked in order: date; on one day buys before sells, then time, then the order stored (file order). An opening lot of P0 exists from the start, dated the account's first import date or the day before the first trade when that is earlier, source = import, flagged default date (editable). Each buy opens a lot (source = trade, not default; cost = price on today's basis). Each sell closes open lots first in first out — the opening lot first — into pieces closed on the sale day at the real sale price; a partial sale splits a lot (closed piece + open rest with the same date and cost). A sale larger than everything open at that point is a quantity_mismatch (sell_exceeds_open).
  4. The opening lot's unit cost follows from A, which Indian brokers keep by the weighted-average-cost method (a sale does not change it): c0 = (A × (P0 + B) − BC) ÷ P0, with B the shares and BC the cost of all the buys of the file on today's basis, rounded to 4 decimals. It holds whether or not sales used the opening lot up, and the pieces sold from the opening lot cost c0 too (consistent realised profit). When c0 is not above 0 the opening lot costs A and the rebuild says costNote: opening_cost_fallback; with P0 = 0 there is no opening lot. Invariants: the open lot quantities add up to Q; with no sales in the file and an opening lot, invested = Q × A to within 0.0001 × the opening quantity + 0.01; with sales the first-in first-out cost basis can differ from the broker's average-cost figure by nature (first-in first-out against the average-cost method; without an opening lot the real buy costs stand), so the rebuild block carries openCostAfter, brokerCost and costDelta and the screen says "cost basis differs from broker by ₹x" (they are part of the digest).
  5. Without trades the result is one lot of Q at A dated the first import date, flagged default: the state before any import.

The flow. Preview (POST /api/portfolio/trades/preview, multipart accountId + file) is read-only and returns the file (rows, parsed, skipped by reason, bad rows, duplicates, already imported, new), each security of the file (symbol, ISIN, matched, holdingId, trade counts and dates, and the rebuild: status ok | unchanged | quantity_mismatch | no_holding | ambiguous, lots before → after, hand-dated and sync-added lots that would be replaced, realised profit on the real sales, adjustedFor, q, net, opening quantity before → after, a per-holding digest), notHeld / unmatched counts and an overall digest; the list holds every held or master-listed security and at most 200 unmatched ones (securitiesTotal, unmatchedListed count them; the digest covers all). Import (POST /api/portfolio/trades/import, same body plus rebuild default true and digest) stores the new trades as one batch and, with rebuild, replaces the lots of every holding whose result is ok — all lots of the holding (hand-dated and sync-added ones too, which is why the preview counts them), deleted and re-inserted in the one unit of work of the whole import, the holding's xmin token guarding a concurrent sync or quote (the work then runs again once). With rebuild the request must carry the preview's digest: if holdings, lots, applied corporate actions or trades changed since, the answer is 409 portfolio.preview_stale (extension report: the fresh preview) and nothing is applied. 409 portfolio.sync_running while the account's holdings sync runs. Undo (POST /api/portfolio/trade-batches/{id}/undo?dryRun=true|false, default false) voids the batch's trades and rebuilds from the remaining trades the affected holdings whose lots came from trades (a holding imported without a rebuild keeps its lots); undoing twice is a no-op. Undo derives, it does not snapshot: it cannot bring back hand-dated or sync-added lots that an earlier rebuild replaced — the holding returns to one default-dated lot of Q at A (dated by the first import date) or to the shape of the remaining trades; the dry run returns the same result without changing anything (handDatedLotsReplaced, syncLotsReplaced, notRebuilt[{symbol, holdingId, reason}] for holdings that could not be rebuilt — a mismatch or ambiguous — and keep their lots). Void (POST /api/portfolio/trades/{id}/void) and add (POST /api/portfolio/trades: holding or security, side, date, quantity, price, charges; validated like a CSV row; the security must be a holding or an NSE share/ETF of the master) change no lots; the owner then rebuilds one holding with POST /api/holdings/{id}/rebuild-lots?dryRun=true|false (dry run by default; the same rebuild block). GET /api/holdings/{id}/trades lists a holding's trades (voided ones flagged), GET /api/portfolio/trade-batches the import history. History, benchmark, groups and actions caches are dropped by every one of these (the unit of work); the Action center and the notices reconcile on the next tick/read as usual. Audit events record counts only (TradesImported, TradesUndone, TradeAdded, TradeVoided, LotsRebuilt; since P2-14 also DividendAdded, DividendVoided, DividendSuggestionAccepted, DividendSuggestionDismissed, whose text carries ids only, never an amount or a note; since P2-15 also DividendsImported, DividendsUndone, DividendAliasSaved, §3 "Dividend import (P2-15)").

Lots after a rebuild. Lots made from buys have source = trade, are not flagged default and their dates are read-only (PUT /api/holdings/{id}/lots/{lotId} → 409 portfolio.lot_from_trade); the opening lot stays editable but its date must be before the earliest trade (400 portfolio.invalid, field acquiredOn); lots a later sync adds are like any other. The first-import-date re-dating (ADR 0015) skips holdings that have trade lots (counted as skipped). A later sync that changes the quantity keeps its behaviour; the next rebuild recomputes P0 = Q − net, and its preview shows the opening quantity before → after, so a change the trades do not explain is visible.

Dhan sync (P2-13, ADR 0025)#

The account's trades and ledger are read from Dhan (read-only, header access-token; the shapes and limits are in doc 05 §8.3) so the owner no longer exports a tradebook or types cash movements. Field names come from Dhan's public documentation and its published samples (read 2026-10-14; ADR 0025 amendment g), not from a real answer of the owner's account (the first real read may force small mapping changes).

  • Windows and watermark. A run reads the dates from from to today (India) in windows of at most 30 days (a constant, tuned later), oldest first. from is the request's from, else the account's watermark (per account and kind, trades | ledger: the last date a whole window was stored), else the account's first import date. Trades are read page by page (pages from 0) until the first empty page or 200 pages; the ledger is one call per window. Each window is stored in one unit of work together with the run's progress and the watermark move, so a failure part-way leaves the watermark where the last whole window put it and the next run reads the failed window again (the identities make that harmless).
  • A from that would leave a gap is refused. For both kinds a from later than the watermark + 1 is 400 portfolio.invalid (field from): it would leave dates that are never read. An earlier from is allowed and re-reads (nothing new is stored for what is already there). The check uses the older of the two watermarks: a from later than the day after it is refused. When exactly one kind was never read, from may not be later than the account's first-import date (the other kind's watermark + 1 if that is earlier); an account where neither kind was read may start at any date, and what is older than the first trade read is then the opening lot, as with a tradebook that starts late. Behind this check the pipeline keeps a defensive guard: a run whose start would leave a hole after the watermark does not rebuild lots (it cannot happen through the use cases, which refuse such a start first).
  • Windows Dhan refuses or answers "no data" for. Dhan documents no maximum span and no history depth for either endpoint (an earlier from is accepted, floor 1990-01-02; far-back reads mean many 30-day windows). DH-905 ("input exception"; how a too-wide range is expected to be refused, unverified) or 200 pages without an empty one: the window is halved once and each half is read; if a half is too large too, the run ends failed with the "history too large" text and nothing of the window is stored. DH-907 ("incorrect parameters or no data") ends the paging as an empty result only for page ≥ 1; on page 0 of a window longer than one day it is unclear (no data, or a bad range): the window is halved once and the halves are used, and a half that also answers DH-907 on page 0 is taken as empty and counted (emptyByNoData in the run's counts). On a one-day window DH-907 is an empty result (counted). The ledger has no paging (one call per window) and follows the same rule: a multi-day window answering DH-907 is halved once, and a half or a one-day window answering it is empty and counted. The sync line says "Dhan answered "no data" for N date ranges" only when more ranges answered no data than windows were read, i.e. windows were halved and still empty. A refused token (401), a rate limit (429), a 5xx or a timeout fail the run and are never read as "no data".
  • What is kept. Every NSE_EQ row whose product is not an intraday product becomes a transaction (source = broker, run_id = the run): delivery (CNC, MTF), MARGIN (on NSE_EQ only a position carried overnight; skipping it would cause quantity mismatches) and a row with no product. Other segments (BSE, derivatives, currency, commodity, other) and intraday products (INTRADAY, INTRA, MIS, CO, BO) are skipped and counted per reason (bse, derivatives, currency, commodity, non_equity, intraday: they net out within the day or are not holdings; no_symbol: the security could not be told). A row without an id, side, whole positive quantity, positive price or readable date is dropped and counted. Security. tradingSymbol can be null in Dhan's rows (customSymbol is a company name, never used as a ticker): the ticker is found through Dhan's securityId (market.instrument_broker_ids, dhan, NSE_EQ), else through the ISIN; a row no instrument matches but that has an ISIN is stored ISIN-only (like a tradebook CSV line with an ISIN and no symbol) and matched to its holding by ISIN; a row with none of ticker, resolvable id and ISIN is not stored and counted as skip reason no_symbol. Charges and ISIN. charges is the sum of the row's six charge fields (sebiTax, stt, brokerageCharges, serviceTax, exchangeTransactionCharges, stampDuty; rupees, 4 decimals, strings and "NA" tolerated) and the ISIN is stored, both on the transaction; the charges are used by the net returns (P2-14) and by nothing else — not by lots, cost or the gross XIRR.
  • Identity and duplicates. A trade's identity is t:yyyyMMdd: + Dhan's exchange trade id, the same the CSV reader gives a tradebook's trade-id column, so a trade already imported from a Dhan tradebook is a duplicate and reading the same days twice stores nothing new. Documented limits: a tradebook CSV row without a trade id has the hash identity (h:), and the same Dhan trade (t:) is then stored a second time; and a voided broker trade is stored again when its day is read again (its identity is free, as for CSV; the UI help says so).
  • Completing trades stored earlier (enrich step, P2-14). P2-13 first stored charges = 0 and no ISIN for broker trades and dropped rows without a tradingSymbol, so trades stored by an earlier read can lack an ISIN, a ticker or charges. When a window is read, the rows of it that are stored already are matched to the account's non-voided broker transactions that still lack one of these, and Transaction.EnrichFromBroker fills in only what is missing: the ISIN when empty, the ticker when empty, the charges when 0 and the read has some. It never touches the identity, side, date, quantity or price and never overwrites a value that is there; CSV and manual trades and voided trades are left alone. The completed trades are counted as enriched (a part of duplicates) in the run's counts and in the counts-only BrokerHistorySynced text, saved in the window's unit of work, and a run that enriched trades re-works the lots like one that stored trades (a trade that gained an ISIN can now be attached to its holding). The nightly read starts at the watermark, so the owner completes older trades once by reading again from the first-import date or earlier (Read from an earlier date); a second read finds nothing left to complete.
  • Runs. portfolio.broker_sync_runs: one row per kind per run (trigger manual | scheduled | first, from_date, to_date, status running | succeeded | failed | skipped, counts, error). Counts: windowsDone, windowsTotal, halved, emptyByNoData, read, stored, duplicates, enriched, dropped, skipped and skippedByReason, and for trades rebuilt, unchanged, needsReview, notRebuilt[{symbol, reason}] (at most 50 listed). Every exit of a run completes it: a failure, a crash or a cancellation ends the row as failed with a plain, safe error and the counts so far (never Dhan's text, the URL or the token); a run left running by a stopped process counts as interrupted after 30 minutes. A scheduled run that is not attempted because the token has expired is recorded as skipped (token_expired). The status figures holdingsRebuilt, holdingsNeedingReview and needsReviewSymbols (at most 50 tickers) come from the latest succeeded trades run and no other — nothing is carried forward: a quiet night whose rebuild was skipped shows 0 rebuilt, and a skipped, failed or running run neither changes nor erases them. Runs never overlap with each other or with a holdings sync of the same account (one running row per account; 409 portfolio.sync_running).
  • Trades first, then the ledger. The ledger run starts only when the trades run succeeded. Both are started by POST /api/accounts/{id}/sync/broker-history (optional {from}; answers at once with the trades run, a first backfill takes minutes) and followed by GET /api/accounts/{id}/sync/broker-history/status (watermarks, latest runs, windowsDone / windowsTotal, next scheduled run, holdingsRebuilt, holdingsNeedingReview, needsReviewSymbols). Audit: BrokerHistorySynced, counts only; a scheduled run that stored nothing and changed no lots leaves no event.
  • Automatic lot rebuild (owner's decision, no preview). After the last window of a trades run, every open holding that has broker trades is worked out by the same pure LotReconstructor as the owner's rebuild and applied only when its result is ok; unchanged is counted, quantity_mismatch, ambiguous and no_holding are left alone and counted. A holding with a hand-dated lot (an owner edit) is not rebuilt: it is needs_review and the owner uses the holding's Trades section (preview, then rebuild). Each holding is rebuilt in its own unit of work that is not retried: if the holding changed meanwhile (xmin: a sync, a quote or the owner's lot-date edit saved it — UpdateLotDate marks the holding as changed for this purpose) that rebuild is skipped as changed_meanwhile and the next run retries; the owner's edit is repeated once on what is stored, and a second concurrency conflict answers 409 portfolio.conflict. Each rebuild writes LotsRebuilt with trigger = broker_sync (counts only) and the caches are dropped by the unit of work. The rebuild is skipped when the run did not read every window, when its start would leave a hole after the watermark (a defensive guard behind the start check above), and when the run stored nothing, the previous finished trades run succeeded with nothing left to retry (nothing other than no_holding) and no holding of the account appeared, was reopened or gained a lot after that run ended (IHoldingStore.AnyAppearedSinceAsync, read from the holdings themselves, not from the previous run's counts). A run after a failed run always rebuilds.
  • Ledger. portfolio.ledger_entries (immutable): voucher date, number, description, narration (Dhan's free text: capped at 500 characters, shown as plain text), exchange, one signed amount (credit − debit), running balance and a class from a pure, table-driven classifier over description and narration, in this order: dividend (credits), charges (debits: brokerage, DP/AMC, stamp duty, GST, STT, payout and withdrawal charges, penalties …), funds_out (debits: withdrawal, payout), funds_in (credits: deposit, pay-in, UPI, NEFT …); anything else, and any entry whose sign contradicts the phrase, is other and keeps its raw text. The phrases come from Dhan's documentation and published sample (PAYBNK and FUNDS WITHDRAWAL are funds_out; FUNDS ADDED and PAYIN funds_in; DPC Interest charges) and are expected to grow after the first real read. Dhan's published ledger sample is a single object, not a list: an answer of one object (or one under data) is read as one row. Dividends: Dhan credits them to the bank account, not to the trading ledger, so a dividend entry is rare (e.g. rented stocks); the owner enters dividends from P2-14 (ADR 0026). An entry's identity is a hash of (account, voucher date, voucher number, description, signed amount, occurrence index within the same date and voucher). In the net returns (P2-14) the class decides little: an entry of class charges counts only when it names an account-level cost — a depository (DP) or demat charge, annual maintenance (AMC), delayed-payment interest (DPC Interest), a penalty or late-payment charge, a platform or subscription fee, a pledge, unpledge, payout or withdrawal charge, a call & trade fee (LedgerCosts.IsAccountLevel, a table of phrases that is expected to grow after the first real read) — and none of the trade-related phrases (brokerage, STT, stamp duty, SEBI, transaction charges, turnover, settlement, bill, contract note), which are never summed because the trade rows already carry the costs of trades (a doubt leaves a cost out, where it stays visible, instead of counting it twice). The class shown for the entry is not changed. A dividend entry is only a suggestion (below); dividends are not matched to holdings by narration.
  • Service. portfolio-broker-history ("Portfolio trades & ledger", ADR 0018): daily at 16:30 IST on trading days, editable on the Services screen, one account after the other (connected Dhan accounts with the Portfolio role); an expired token is reported as token_expired (the run fails so the owner is told; the other accounts are still read). Portfolio:BrokerHistory:Enabled seeds it on first start (doc 16). "Sync trades & ledger" works at any time.
  • Cash & dividends. GET /api/accounts/{id}/ledger?from&to&class&page&pageSize lists entries newest first with totals (count and signed amount of every class for the period, whatever class is filtered). Read-only; the answer's coverageFrom is the earliest ledger date stored for the account, whatever the filters. Shown in a drawer on the Portfolio screen (doc 13 §4). P2-14 decided: the ledger's account-level costs count in the net returns from coverageFrom on (above); its funds, dividend and other entries are shown only, and neither the gross figures nor the value history use any of it.

Not built: cash flows (deposits and withdrawals) in XIRR, charges in the cost basis, dividends read from Dhan (Dhan credits them to the bank account, not to the trading ledger; entering them is P2-14, importing the owner's dividend payout file is P2-15), matching a ledger dividend to a holding by its narration, TDS on dividends, dividend reinvestment, a total-return index benchmark, broker-specific CSV profiles (the generic format and the template come first), editing a trade (void and add again), positions and intraday P&L, creating closed holdings from trades, tax reports. The limits (10 MB, 20,000 rows, 200 listed bad rows) are fixed, not configuration.

Dividends, charges and net returns (P2-14, ADR 0026)#

The gross figures stay as they are; next to them the screen shows what the portfolio received and paid and the net return that includes it. Pure calculators in Application/Portfolio/Income (IncomeBook, IncomeCalculator, LedgerCosts, IncomeViews); the reads are IIncomeQueries.

  • Dividends are entered by the owner (P2-14: Dhan credits them to the bank account, and no API for the app's Money → Dividends list was found; since P2-15 a dividend payout file can be imported as well, below). portfolio.dividends (§9) is immutable except for being voided. POST /api/portfolio/dividends takes {holdingId} (the account is then the holding's) or {accountId} alone (unallocated: no holding, e.g. a holding long since sold and removed), payDate (1990-01-02 to today, India), amount (rupees, above 0, to the paisa), optional perShare (above 0) and note (plain text, at most 200 characters), and confirm. The same account, holding, date and amount as a dividend that is not voided is allowed (two genuine payments) but asks first: 409 portfolio.possible_duplicate, repeated with confirm: true. POST /api/portfolio/dividends/{id}/void (a mistake is voided and entered again, never edited; voiding twice is a no-op), GET /api/holdings/{id}/dividends and GET /api/accounts/{id}/dividends (newest pay date first, voided ones included and flagged, page, pageSize up to 200). 404 portfolio.not_found, 409 portfolio.role_off, 400 portfolio.invalid with field errors. Session and CSRF token, no step-up (no secret is involved). Audit: DividendAdded, DividendVoided with the id only.
  • Suggestions. GET /api/accounts/{id}/dividends/suggestions lists the account's ledger entries of class dividend with money in that the owner has not decided; POST …/suggestions/{entryId}/accept (optional {holdingId, note}: one of the account's holdings, or none) creates a dividend with the entry's amount and date and links it; POST …/suggestions/{entryId}/dismiss hides it. Both decisions are final (voiding the dividend later does not bring the suggestion back; 409 portfolio.conflict when decided meanwhile). Nothing is added without the owner and no narration is matched. Dhan's documented ledger has no ordinary dividend entry, so the list is usually empty. Audit: DividendSuggestionAccepted, DividendSuggestionDismissed, ids only.
  • Where each rupee belongs (IncomeBook). A dividend belongs to the holding it was entered for, else to its account. The charges of trades are summed per account, security and day and belong to the holding of the same account that the security resolves to by the rule trades use (§3 "Which holding a trade belongs to"): by ISIN, else by symbol when either side has no ISIN (an ISIN never joins two different ISINs), among the account's open holdings; when more than one open holding fits (an NSE and a BSE row of one ISIN) the trade is ambiguous and attached to none; only when no open holding fits are the account's closed holdings tried by the same rule (a holding sold out keeps the charges of its trades); a trade that fits no single holding belongs to the account. The ledger's entries belong to the account, and only the account-level costs of LedgerCosts count (above). So every recorded rupee is in exactly one place and the places add up to the total.
  • Figures (IncomeCalculator). For a scope: dividends and charges are the sums of what its holdings hold plus, for the accounts whose own items belong to it, the account's unallocated dividends, the trade charges of no holding and the ledger's costs; ledgerCharges is the ledger part of charges and unallocated the unallocated part of the dividends (both null when the scope has no account-level items: a holding, a bucket). totalReturnPct = (realised + unrealised + dividends) ÷ invested × 100 and netTotalReturnPct = the same less the charges, each rounded once to four decimals, null when nothing is invested or the scope has no usable price. netXirr and netXirrState: §4. Only what exists is counted: a scope with no dividend and no charge recorded has income: null (no zero row; the screen invites to add one); a trade without charges is unknown, not free (CSV, manual and early Dhan rows carry none).
  • Coverage — from which date the figures are known. Each source says from when it is known, null when it has nothing for the scope: dividendsFrom = the first dividend entered or imported (what was paid before it is not counted); tradeChargesFrom = the first stored trade that carries charges; ledgerChargesFrom = the first ledger date stored for the account (the ledger's costs before it are unknown); chargesFrom = the later of the last two when both exist, else the one that does. coverageFrom is the later start of the sources that exist for the scope: the date from which every kind of income that is counted at all is known, so a net figure is never presented as complete from before any of its sources begins. The parts are shown separately (the tiles say "from " under Dividends and under Costs). Older history helps only as far as Dhan's goes, which Dhan does not document (Read from an earlier date, doc 13 §4).
  • The income object (GET /api/holdings/summary, each row of GET /api/holdings, each group and the total of GET /api/holdings/groups; null when nothing is recorded): dividends, charges, ledgerCharges, unallocated, totalReturnPct, netTotalReturnPct, netXirr (percent number) with netXirrState (ok | insufficient | n_m | no_data | no_price), coverageFrom, dividendsFrom, chargesFrom, tradeChargesFrom, ledgerChargesFrom. For the whole portfolio or one account (no bucket narrowing it) the summary's income includes the account-level items; for a bucket only its holdings'. A holding row has the holding's own dividends and trade charges only.
  • Read load. Income is read in a fixed number of set-based queries whatever the number of dividends and trades (never one per holding): accounts, the holdings' keys (not read again when the caller has handed over the holdings it read), dividends, trade charges summed per account, security and day, and for the summary and the groups the ledger's costs and the first ledger date. A page of GET /api/holdings adds three reads (accounts, dividends, trade charges) to the session, holdings and lots statements: 6 in all, 7 when the page's holdings are not all the account's (a filter, status or group) and their keys are read once; it never reads the ledger. The net XIRR of a row is worked out for the rows of the page only, after ordering and paging, never to order by (the sort keys are the cheap sums); sort=dividends orders by the dividends entered, holdings with none last.
  • Audit and privacy. Events carry ids and counts only, never an amount or a note. The dividend note and the ledger's description and narration are untrusted text: plain text, length-capped.
Dividend import (P2-15, ADR 0028)#

The owner keeps Dhan's dividend list as a file — Date, Scrip Name, Dividend Per Share, Quantity, Dividend Paid: company names only (no symbol or ISIN), dates like 13 Jun 2024 (Sept for September), amounts with thousands separators, many rows for stocks no longer held. The application recognises such a file by itself, matches the names to the account's holdings (remembering the owner's corrections), shows what would be added, and imports it with Undo, so a whole history needs no typing and the same file again adds nothing (P2-15). Pure steps in Application/Portfolio/DividendImport (DividendColumns, DividendCells, DividendCsvReader, DividendNames, DividendNameIndex, DividendIdentity, DividendPlanner) and Application/Portfolio/Imports/FileKindDetector; the use cases are PreviewDividends, ImportDividends, UndoDividendBatch, ListDividendBatches. The flow is the one of trades (preview, then import with a digest, then Undo), without lots to rebuild.

  • Format detection (FileKindDetector). Judged from the header names alone (case and punctuation ignored), by the trade import and the dividend import alike. A tradebook has a date, a symbol or ISIN, a side, a quantity and a price. A dividend file has a date, a scrip name (or a symbol or an ISIN) and a paid amount, and no side column; when its only amount header is a plain one (Amount, Net amount, Total amount) it must also not be shaped like a tradebook (date, symbol or ISIN, quantity, price), while a header that says dividend, payout or paid (Dividend Paid, Dividend Amount, Net Dividend, Amount Paid, Payout…) always makes it a dividend file. A file with a date, symbol or ISIN, quantity and price but no side is a tradebook without sides; anything else is unknown. Accepted names, among others — date: date, pay date, payment date, payout date, dividend date, credit date; name: scrip name, scrip, company (name), security (name), stock (name), instrument (name), name; optional symbol/ticker and isin beside the name; paid amount: dividend paid, dividend amount, dividend received, net dividend, amount paid, payout, net amount, amount; optional per share: dividend per share, per share, DPS; optional quantity: quantity, qty, shares, eligible shares. Unknown columns are ignored.
  • The reader (DividendCsvReader, pure). UTF-8 with or without BOM, comma separated, double quotes around fields with commas ("1,134.00"); at most 10 MB and 20,000 data rows (the same limits as a tradebook, fixed; more is 400 portfolio.invalid, field file); empty lines are ignored. Per row the first problem makes it a bad row (line and reason — at most 200 listed, all counted in badTotal), never imported: the scrip name (not empty, has letters or digits, at most 200 characters), an ISIN (12 characters) or symbol when given, the date (dd MMM yyyy also written dd MMMM yyyy and 23 Sept 2024, dd-MMM-yyyy, yyyy-MM-dd, dd-MM-yyyy, dd/MM/yyyy — day first, never month first; a time after the date is ignored; from 1990-01-02 to today in India, so a future date is a bad row), the paid amount (above 0, rounded to the paisa, at most ₹1,000,000,000), the optional per share (0 or more, four decimals) and quantity (a whole number above 0); a date, number or ISIN cell longer than 64 characters is bad. Numbers take . for decimals and , only to group thousands. Rows identical to an earlier row (same date, normalised name, per share, quantity and amount) are counted once by the reader and listed in identicalRepeats (name, date, amount, occurrences, the first lines, at most 200 payments listed); parsedAmount still includes them. A header that is a tradebook's or a tradebook without sides is refused as portfolio.wrong_file_kind; one that is nothing known as 400 portfolio.invalid (field file) naming what is missing and the accepted names.
  • Name matching (DividendNames, DividendNameIndex). Names are compared by their key: lower case, dots and apostrophes removed, other punctuation a word break, & read as and, and the corporate words ltd, limited, corporation, corp, india, industries, inc, plc, pvt, private, company dropped (a name made only of such words keeps them), so Power Finance Corporation Ltd. and POWER FINANCE CORPORATION are one key. The rules are tried in this order and the first that answers decides; the account's holdings, the master's NSE shares and ETFs and the aliases are read once per file into an in-memory index, never per row.
    1. a remembered alias of the account (below), pointing to a holding, to an instrument of the master, or to nothing;
    2. the file's ISIN, then symbol column (when it has them) against the account's open holdings;
    3. the name's key equal to the key of an open holding's name (or of its symbol);
    4. the name's key contained in an open holding's name key, or the other way round, as whole consecutive words — only when the shorter key has at least two significant words (of, and, the, for, in do not count), so Bank of India never matches Union Bank of India; the row then carries the warning partial_name_match;
    5. the instrument master (NSE shares and ETFs), by ISIN, symbol or name key equality only (never containment), when exactly one current instrument fits (a retired one only if it is the only one): the dividend keeps instrument, ISIN and symbol but no holding;
    6. otherwise no match: the dividend is imported unallocated with the file's name as text. Where more than one holding fits rules 2 to 4 nothing is guessed: the row is ambiguous and lists up to 20 candidates. An exact name beats a contained one. Dividends of a stock no longer held (no open holding) stay unallocated or instrument-only, so they count in account and total figures but not in holding, bucket or sector groups.
  • Owner's choices and aliases. The import takes choices[{name, holdingId | instrumentId | none, remember}] — exactly one of the three, applying to every row with that name (compared by key); the holding must be one of the account's (open or closed), the instrument a share or ETF of the master; at most 2,000 choices; a choice naming no row of the file is 400 portfolio.invalid (field choices). With remember the choice is saved as an alias (portfolio.dividend_aliases, one per account and name key; pointing the same name elsewhere retargets it, "none" means "keep unallocated") and the next file with that name needs no question. Saving is explicit, audited (DividendAliasSaved, the alias id only) and never changes dividends already imported. A choice that makes a row equal to a typed-in dividend turns it into a possible duplicate.
  • Identity and duplicates. A dividend of a file is stored under external_id = d: + 32 hex characters of the SHA-256 of account, pay date, normalised name, per share, quantity, amount; it is unique per account among the dividends that are not voided (a partial unique index, §9), so the same file again stores nothing, a corrected file adds only what is new, and an undone or voided dividend can be imported again. Two payments that differ in any of those are two identities (for example 5 and 4.5 per share of one company on the same day); a corrected value (a changed amount) is therefore a new payment to the application — the old one is undone or voided by the owner. There is no occurrence index in the identity: identical rows of one file never reach it, the reader counted them once (the preview lists them, "add the second by hand if it is real"). A row that equals a dividend the owner typed in (source manual, not voided: the same holding — or both unallocated —, date and amount) is a possible duplicate: listed, skipped by default, imported only when its line is ticked (includeDuplicates). Per-row status, first that applies: imported (identity stored already), possible_duplicate, ambiguous, needs_match (no match at all), new; a name the owner or an alias sent to nothing is new (unallocated by decision). The rows that would be stored are new, needs_match and ambiguous — the last two are imported unallocated with the file's name unless the owner chooses — plus ticked duplicates.
  • Checks shown in the preview. amount_mismatch when per share × quantity differs from the paid amount by more than ₹0.01 (the paid amount wins and is what is stored); before_first_lot when the pay date is earlier than the first lot of any of the account's holdings (the net XIRR would start with money in, §4; the screen offers to read earlier trade history); partial_name_match (rule 4). Totals: the count and rupees to be added, by pay year, and beforeFirstLot {count, amount, firstLotDate}.
  • Preview, import, Undo. Preview (POST /api/portfolio/dividends/preview, multipart accountId + file) reads and stores nothing and returns {format: "dividends", file {fileName, rows, parsed, parsedAmount, repeated, distinct, identicalRepeats[], bad[], badTotal, alreadyImported, possibleDuplicates, toAdd, needsMatch, ambiguous}, items[{line, payDate, name, perShare, quantity, amount, status, match {kind: alias | isin | symbol | name | contains | master | none, holdingId, instrumentId, symbol, isin, name, candidates[{holdingId, symbol, name}]}, warnings[]}], totals {count, amount, byYear[{year, count, amount}]}, beforeFirstLot, digest}; items are the distinct rows in file order (all of them: up to 20,000, so the answer can be a few megabytes and the screen shows long tables paged, 50 rows at a time); names are untrusted plain text. Import (POST /api/portfolio/dividends/import, same body plus digest — required —, choices and includeDuplicates as JSON text) stores the rows to be added as one batch in one unit of work (all or nothing) and answers {batch, imported, amount, allocated, instrumentOnly, unallocated, alreadyImported, possibleDuplicatesSkipped, aliasesSaved, report} (report is the confirmed preview, before the choices); a file that adds nothing makes no batch (batch: null). Undo (POST /api/portfolio/dividend-batches/{id}/undo) voids the batch's dividends (nothing is deleted), marks the batch undone and leaves the remembered names alone; twice is a no-op (alreadyUndone: true, voided: 0); the same file can be imported again afterwards. History: GET /api/portfolio/dividend-batches?accountId&page&pageSize (newest first, pageSize up to 100, default 50) lists {id, accountId, accountName, fileName, sha256, parsed, imported, duplicates, bad, amount, status: imported | undone, activeDividends, createdBy, createdAt, undoneAt}. The dividend lists (GET /api/accounts/{id}/dividends, GET /api/holdings/{id}/dividends) show source: csv, the file's quantity, the scripName of an unallocated one and the batchId. Session and CSRF token, no step-up (no secret is involved and an import is undone by voiding). Errors: 404 portfolio.not_found (account, batch), 409 portfolio.role_off, 400 portfolio.invalid (fields accountId, file, digest, choices, includeDuplicates), 400 portfolio.wrong_file_kind (below), 409 portfolio.conflict when a parallel import stored the same payment meanwhile. History, benchmark, groups and income caches are dropped by the unit of work, like every portfolio write. No portfolio.sync_running: dividends do not depend on a holdings sync.
  • The digest. The preview's digest fingerprints what the owner saw: the number of bad rows and of repeated rows, the account's first-lot date, and for every distinct row its line, pay date, amount, status and the rule and holding or instrument (and candidates) its name matched. The import reads the file again (it is sent again), plans it against the current holdings, aliases and stored dividends, and answers 409 portfolio.preview_stale — extension report: the fresh preview — and stores nothing when the digest differs (a holding closed or added, an alias saved, a dividend typed in or undone since). It does not cover the owner's choices, which are the request itself.
  • Wrong file kind (portfolio.wrong_file_kind, a 400 with the extension detected). Both imports send a file to the one it belongs to instead of naming missing columns. On the trade import (preview and import): a dividend list → detected: dividends, "this looks like a dividend payout list, not a tradebook; import it with Import dividends in the Cash & dividends panel" (the screen shows a button to it); a tradebook without a buy/sell column → detected: tradebook_without_sides. On the dividend import: a tradebook → detected: trades, "import it as trades on the Portfolio screen"; a tradebook without sides → tradebook_without_sides. The sideless-tradebook explanation (a sideless Dhan tradebook export has a date, symbol, quantity, price, Order Type and Segment, but no Buy/Sell column): the file is not read, because without a side the application cannot tell purchases from sales and would have to guess, which it never does; the message says to export a tradebook that says Buy or Sell for each trade (or add that column), or to use Sync trades and ledger on the Portfolio screen to read the history from Dhan. Any other header that is not a tradebook is still 400 portfolio.invalid (field file) with the missing columns and the accepted names.
  • Audit, logs and privacy. DividendsImported (batch id, counts of valid rows, stored, not stored and bad — only when a batch was made), DividendsUndone (batch id, number voided), DividendAliasSaved (alias id): ids and counts only, never a file name, scrip name or amount. Structured log events 4181–4183 carry the account slug, counts and durations only. The file itself is never stored (name and SHA-256 only); scrip names are untrusted text, rendered as plain text everywhere. The name matching reads the account's holdings, the master's names and the aliases in one query each, so a 20,000-row preview is bounded by memory and the dedupe query, not by rows (an integration test holds it under 5 s).
  • Figures. A dividend of a file counts exactly like one typed in (P2-14): an allocated one in its holding, bucket, basket and sector groups, an unallocated or instrument-only one at account and total level, dividendsFrom is the first stored one; voiding or undoing removes it from every figure. Voiding one dividend of a batch by hand frees its identity, so importing the same file again would add that one back.
  • Not built (this story). Reading the owner's sideless tradebook, TDS on dividends, dividend reinvestment, splitting a payment across lots, matching by record-date quantity, other brokers' dividend formats beyond the header names above, a column for the account (one upload goes to the account chosen in the panel; several Dhan accounts need one file each).

Per group (basket / bucket / account / strategy / sector / total)#

Holding groups (P2-08, ADR 0021)#

GET /api/holdings/groups?by=account|bucket|sector|basket&accountId&bucketId&status&q&sort&stackBy partitions the holdings of the scope in memory and applies the same pure calculators as the summary to each group (Application/Portfolio/Groups: HoldingPartitions, GroupCalculator, over ReturnsCalculator and DayChangeCalculator) — so a group, the summary and a holding agree. Session only, read-only, no table, no job.

  • Scope. The filters of the holdings list (q, status: open by default) apply before grouping; without accountId only the accounts that count in totals (includeInTotals) are read, exactly like the summary — accounts with includeInTotals = false are in no group, not in the total and not in the children of a group, while the flat holdings list (no groupBy) still shows them. An unknown accountId gives 200 with no groups (as the list does; the summary answers 404), so for the additive groupings (account, bucket, sector; additive: true) Σ group invested / value / P&L equals the summary's for the same filters (status=all for the summary, which includes closed holdings). The weight of a group is its value over the scope's total value of priced holdings (weightPct, percent number).
  • Per group {key, name, holdings, unpriced, invested, value, pnl, pnlPct, realised, xirr, xirrState, dayChange, dayChangePct, dayChangeExcluded, weightPct, parts, income} and a total row for the whole scope (the same fields without key, name and parts). income (P2-14) is the object of §3 "Dividends, charges and net returns", null when nothing is recorded for the group. XIRR is the XIRR of the union of the group's cash flows, never an average; xirrState is ok | insufficient | n_m | no_data, or no_price. Unpriced open holdings are left out of invested, value, P&L and XIRR exactly as in the summary and counted in unpriced; a group made only of them — and the total when the whole scope is unpriced — has value, pnl, pnlPct, xirr, weightPct null, invested 0 and xirrState: "no_price" (its worth is unknown, not zero; this is what a holding row shows, whereas the summary of such a scope shows value 0 and no_data / insufficient). The day change is DayChangeCalculator over the group (holdings without a previous close are counted in dayChangeExcluded, never taken as zero).
  • Keys. The key is the account id, bucket id, basket id or the sector name; ~none is reserved for Unclassified (a holding not in the master, or whose instrument has no sector — the master's sector, doc 06) and No basket; it cannot clash with a real key (a master sector spelled ~none, in any case, is deliberately treated as Unclassified). Keys are compared ignoring case; when the master spells one sector two ways (Banks / banks) they are one group shown under the Ordinal-smallest spelling, whatever order the holdings were read in.
  • Baskets are a lens. A holding is in every live basket that holds its instrument today (archived baskets are left out; the portfolio's system baskets are a view of the buckets, not rows of market.baskets (ADR 0014), so they never count) and in No basket otherwise; additive: false. The same holding is in each group's figures and once in the total; weights can add up to more than 100 %. Membership is read on every request, so a change shows at once.
  • Sort and limit. sort = value (default direction: largest first when sort is left out), invested, pnl, pnlPct, xirr, dividends (the dividends entered; a group with none last, not zero), dayChange, name; a leading - for descending, none for ascending (so an explicit sort=value is ascending); groups without a value come last in both directions; ties by name then key; at most 200 groups, cut off without a flag (the total always covers the whole scope). Unknown by / sort / stackBy → 400 portfolio.invalid with the field names.
  • Stacked bar data. stackBy=account (only with by=sector) or stackBy=sector (only with by=account); any other combination is 400. Each group then has parts: [{key, name, value}] — the value of the group's priced holdings in each part, largest first, summing to the group's value — and the response echoes stackBy. Without stackBy, parts is null.
  • Children. GET /api/holdings?groupBy=account|bucket|sector|basket&groupKey=… (both required together; the key as above, URL-encoded; at most 100 characters) lists one group's holdings with the usual filters, sort and paging; an unknown key gives an empty page. With a group and no accountId the same accounts are read as for the groups (those that count in totals), so the children of a group are exactly the holdings it counts.
  • Income per group (P2-14). Each group's income holds the dividends and trade charges of its holdings and the net returns that include them. The dividends and costs that belong to no holding (unallocated dividends, trade charges of no holding, the ledger's account-level costs) are part of the total; they appear in the account's own group when grouping by account, and otherwise as an extra last group with the key ~unallocated (name Unallocated, no holdings, no value, xirrState: no_data, its income carrying the amounts and no percentages), so the Dividends column adds up to the total. They are part of the scope only when neither a bucket nor a text search narrows it (those belong to an account, not to a bucket or a match). At the default status=open the group figures and the total leave out the dividends and the trade charges of closed holdings, while the summary tiles (which read every holding, closed ones too) include them, so the two can differ until status=all is chosen. Rows of GET /api/holdings (also as the children of a group) carry the holding's own income and sort by dividends.
  • Cost. One read of holdings and lots, one of the sectors of their instruments (sector grouping or stackBy=sector), one of the basket members of live baskets (basket grouping or a basket child list) and the income reads (§3 "Dividends, charges and net returns"); partitioning and calculators run in memory (a few milliseconds for 500 holdings).

4. Returns and XIRR#

Computed on read from the lots by pure functions (XDrishti.Application/Portfolio/Returns), valued on today (India) at the holding's last price:

Figure Definition
Invested Σ open lot qty × unit cost
Value Σ open lot qty × last price
Unrealised P&L ₹ / % value − invested; P&L / invested × 100 (null when nothing is invested)
Realised P&L Σ closed lot qty × (close price − unit cost); realisedEstimated when any sale price is a last-seen price
Day change "—" until a previous-close source exists (P2-07)
Group (total / account / bucket) Sums of the above; the group XIRR comes from the union of all member cash flows, never an average
Total return % (P2-14) (realised + unrealised + dividends) ÷ invested × 100; invested is the cost of the open lots (§3), realised profit is in the numerator
Net total return % (P2-14) the same with the charges subtracted in the numerator

XIRR cash flows: each lot −qty × unit cost on its acquired_on; each closed lot also +qty × close price on its closed_on; plus +current value on the valuation date. XIRR is the rate r where

Σ  CFᵢ / (1 + r)^((dᵢ − d₀) / 365)  =  0
  • Newton–Raphson from a good first guess (growth of everything paid in into everything received over the money-weighted period); if it does not converge, bisection on [−0.9999, 100] (when the ends have the same sign, on the sign change nearest the guess); tolerance 1e-9. It follows the definition of a spreadsheet's XIRR (days / 365 from the first date) and agrees to better than 1e-6 with reference values from an independent 60-digit decimal bisection written in Python — not with Excel itself — on the committed sample sets (XirrTests).
  • States: ok; no_price (the holding has no usable price — a last price of 0 — so priced is false and value, P&L, P&L % and XIRR are null: its worth is unknown, it is not a total loss; such holdings are left out of group and summary invested / value / P&L / XIRR and counted in summary.unpricedCount; realised results of their closed lots still count); insufficient (shown "—": no outflow or no inflow, less than 30 days between the first and the last flow, or no solution in the range); n_m (shown "n/m": the rate is beyond ±1,000 % a year, also when it is above the solver's range); no_data (no flows).
  • Computed for any set of cash flows: one lot, a holding, a bucket, an account, the total. Percentages in the API are percent numbers (16.1 = 16.1 %).
  • Example: buy ₹1,00,000 on 1 Jan; add ₹50,000 on 1 Apr; value ₹1,72,000 on 31 Dec → XIRR ≈ 16.1% (absolute return 14.7%).
  • Net XIRR (P2-14, ADR 0026). The XIRR of the same lot cash flows as above plus each dividend as money in on its pay date and each charge as money out on its date (a refund, a negative charge, as money in), with the terminal value — today's value of what is held — as for the gross XIRR (the valuation date, at the holding's last price). Same states and rules as the gross XIRR (insufficient, n_m, no_data, no_price; less than 30 days or no flow in one direction is insufficient). Only the flows of priced holdings are used: a holding without a usable price leaves out its lot flows, its dividends and its trade charges alike (the gross XIRR already leaves it out; they still count in the dividends and charges sums), while the account-level items (unallocated dividends, trade charges of no holding, ledger costs) of a scope that includes them are always part of it; a scope whose holdings are all unpriced is no_price. A holding's net XIRR uses its own dividends and trade charges. A dividend dated before the first lot or a charge dated after the last flow is just another flow on its date. With nothing recorded there is no net figure at all (income: null).
  • Alpha is a price return. The benchmark XIRR, alpha and the value history are unchanged: the Nifty 50 price index has no dividends, so alpha stays the gross XIRR minus the benchmark XIRR, and its basis text says "price return, before dividends and charges".
  • Later (not built): a total-return index benchmark, TDS and dividend reinvestment, charges in the cost basis, a stored valuations_daily snapshot, grouping the history by basket / strategy / sector, per-holding price charts with buy/sell markers, rolling returns, intraday value. (Dividends as inflows and charges as outflows are built in the net XIRR, P2-14, above; benchmark XIRR, alpha and the value history are built, P2-07, below; the lots' quantities are the broker's, so the history uses prices adjusted for splits and bonuses.)

Value history, benchmark and drawdown (P2-07, ADR 0020)#

Computed on read, with no snapshot table and no job, by pure functions in Application/Portfolio/Returns (PortfolioHistoryCalculator, NavSeries, DrawdownCalculator, BenchmarkReturns, AdjustedCloses, HistoryResolutions) from the lots and the stored 1D aggregates.

  • Held on a day. A lot is held on d when acquired_on ≤ d and (closed_on is null or > d). Value(d) = Σ qty × adjusted close(d); Invested(d) = Σ qty × unit cost of the same lots. A lot bought and sold before a trading day comes never counts. A day without a close carries the last earlier close forward. The dates are the calendar's trading days from the earliest lot to the last stored close, plus today's live point (prices of today from a quote or the last sync, from the session's open, only when such prices exist; it replaces a stored close of the same day).
  • Adjusted prices. Stored closes are raw; the applied corporate actions of each instrument (one read for all instruments) multiply the closes before an ex-date by their factor (ADR 0017 §5), so a lot's value is continuous across a split or bonus and an action the owner confirms changes the next read.
  • Coverage. An open holding without any stored day bar (not tracked, not in the master, bars not fetched) is left out and counted (coverage.unpriced), the series is partial; it is never valued at zero. A lot acquired before its instrument's first stored close counts from that close (coverage.lateStart), not at an invented price. Closed holdings without bars make the series partial without being counted.
  • Benchmark (default master-list Nifty 50, NSE:NIFTY; stored in platform.app_settings). The same cash flows go into the index: a purchase (at its cost) buys units at that day's close, a sale (at its proceeds) sells units, at most the units held (the benchmark never goes short); BenchmarkValue = units × close, the index close carried forward. If the index has no close on or before the first flow the benchmark is unavailable (reason given), never zero. Benchmark XIRR = XIRR of the flows of the priced holdings (the same set as the portfolio XIRR) with the benchmark's value at the valuation date (last close on or before it) as the closing inflow; alpha = XIRR − benchmark XIRR in percentage points. States ok | unavailable | insufficient | n_m (summary field benchmarkState); alpha only when both rates are ok. The index has no live quote: on a live day the benchmark lines end at the index's last close (benchmark.asOf; the live point has no benchmark value, the benchmark NAV and drawdown use the days the index has), the summary reports benchmarkAsOf, and alphaBasis is last_close or live_vs_last_close (the portfolio at prices of a later trading day than that close). Chart and XIRR put a cash flow into the index at the close of the first trading day on or after its date; a lot bought and sold before a trading day comes leaves no flows.
  • NAV (unit method) and max drawdown. The first NAV is 100. NAV(d) = value of what was held the day before, at d's prices ÷ units issued so far (the previous NAV when no units exist). The day's net flow (purchases − sales, valued at d's close, so it does not move the NAV) issues flow ÷ NAV(d) units; all units are cancelled when nothing is held and the NAV carries on from where it was. Max drawdown = max over d of (peak − NAV(d)) / peak × 100 with the peak and trough dates (pct is a fall of pct %; flat or rising gives 0); the benchmark's NAV and drawdown use the same method. A deposit during a drawdown therefore neither hides nor deepens it. The drawdown is measured within the requested range (the peak must lie inside it; rangeFrom / rangeTo are its first and last day), on daily points whatever the resolution.
  • API. GET /api/portfolio/history?accountId&bucketId&from&to&resolution → points {date, value, invested, benchmarkValue, nav, benchmarkNav}, coverage, partial, benchmark, maxDrawdown, benchmarkMaxDrawdown, firstDate, lastPriceAt, resolution; week / month keep the last trading day of the period; at most 2,000 points (default: the finest resolution that fits; a given one that does not is 400 portfolio.invalid); an unknown account or bucket gives an empty history. GET/PUT /api/portfolio/benchmark (any listed master-list index; audited as PortfolioBenchmarkChanged); POST /api/portfolio/history/track-holdings and /track-benchmark use the bulk tracking command (idempotent, no job: the next Update data builds the bars). GET /api/holdings/summary adds benchmarkXirr, alpha, benchmarkState.
  • Cost. A request that would read more than 2,000,000 daily prices is 400 portfolio.invalid. Typically about 100 ms server-side (about 90 ms measured for 300 holdings over 521 days). One query for the holdings and lots, one for the day bars of every instrument of the scope and the benchmark, one for their applied actions; the result is cached 60 seconds per scope, range and resolution and dropped by anything that saves lots, holdings, accounts (first import date, Portfolio role, archive), quotes, the benchmark setting or corporate actions. Reference values: BenchmarkReturnsTests (independent 60-digit bisection in Python, ≤ 1e-6).

Income on a live price (P2-14, ADR 0026). Built (P2-10a, the screen): the Portfolio screen opens the hub while the page is visible and the market is on (pre-open to the close), and moves rows, group rows and tiles with each pricesChanged using the same arithmetic as the server (golden fixtures from the real calculators keep the two equal). A slimmer read endpoint is a follow-up (ADR 0024, P2-10a amendments).

10. Portfolio screen (React)#

  • Account tiles (one per Portfolio account + "All accounts"): value, unrealised P&L (₹, %), day change, XIRR, open positions, realised P&L, top holding and its weight, number of open action items — click to focus the whole page on that account.
  • Action center: positions that need a decision, per account — below cost, large gain, overweight, sector concentration, max holding exceeded, results due, long-term soon, lagging Nifty, not in a basket — with Open / Set alert / Add to basket / Snooze / Done (doc 15 §3). P2-09 (API built; card in the frontend part of the story): seven of the nine rules, evaluated on read by GET /api/portfolio/actions (status open/snoozed/done/all, the account and bucket scope, counts per rule and severity, "not evaluated" holdings), decisions by POST /api/portfolio/actions/{id}/snooze|done|reopen, thresholds by GET/PUT /api/portfolio/action-thresholds; the per-account tiles above are not part of that slice.
  • Header tiles: total value · invested · total P&L (₹, %) · XIRR · day change · benchmark XIRR / alpha / max drawdown (API built in P2-07). Live (P2-10a): value, P&L, day change and the weights of rows, group rows and tiles move with pricesChanged of the hub (§6); the prices line says Live, Pre-open, Delayed, Quotes or Closed from the hub's feedStatus and the times of the prices, and the summary notes how many holdings are not live. The numbers are re-read exactly every 5 minutes and after a reconnect. Income tiles (P2-14, built): under the gross tiles a second row shows Dividends (with "from " and, when there are any, the unallocated part), Costs (trade charges and the ledger's account-level costs, "from "), Net total return (with the figure before costs) and Net XIRR, each saying from which date it is complete (§3 "Dividends, charges and net returns"). While nothing is recorded (income null) there are no zeros: the tiles are replaced by an invitation — Add a dividend and Read the ledger — and the note under the tiles says the figures are price returns. Alpha, the benchmark and the value history stay price returns and say so.
  • Group by: Bucket · Basket · Account · Strategy · Sector · None — with tree-grid (expand to lots and transactions) and column chooser. P2-14 (built): a sortable Dividends column in the group table and the holdings grid (hidden below md; "—" when nothing was entered, not zero), and, for the dividends and costs that belong to no holding, an Unallocated row (key ~unallocated, last, not expandable) so the column adds up to the total; at the default open-only status the groups leave out the dividends and trade charges of closed holdings, which the summary tiles include. P2-08 (API built; screen in the frontend part of the story): None · Account · Bucket · Sector · Basket, group rows that expand to their holdings (GET /api/holdings/groups, groupBy / groupKey on the holdings list, §3), a total row, and the note "Baskets overlap — totals do not add up to the portfolio" on the basket view; strategy, lots as tree levels and the column chooser come later.
  • Charts: allocation by group, sector exposure stacked by account, portfolio value vs the same cash flows in Nifty 50 (API built in P2-07), XIRR by group. P2-08: the data of the allocation donut (the groups' value / weightPct) and of the sector-by-account stacked bar (stackBy → parts) is served by GET /api/holdings/groups.
  • Price alerts: create from the Action center or a position; evaluated by the services; list in an Alerts panel. P2-09 (API built): GET/POST /api/portfolio/alerts, POST /api/portfolio/alerts/{id}/cancel; checked by the quotes service every 5 minutes in market hours.
  • Position drawer: the holding's income facts (dividends and charges with their dates, total return with dividends, net total return, net XIRR) and a Dividends section (P2-14, built: the dividends entered for the holding, newest first, Add dividend, Void after asking; a voided dividend stays in the list and stops counting); transaction timeline, price chart with buy/sell markers, lots, alerts, linked plan ticket.
  • Filters: date range (for realised results), account, bucket, basket, status (open/closed), source.
  • Exports: CSV/Excel of positions, transactions and realised P&L.
