05 — Data & Brokers

1. Data sources (v1)#

Source Role Cost
Your CSV files (1-minute) Historical bootstrap and any bulk history you provide ₹0
Dhan Data API The only market-data API in v1: instrument master, end-of-day 1-minute/daily fetch for tracked instruments, live feed for the active set, quotes for holdings ₹499 + taxes / 30 days, on one account
Dhan Trading API Funds, positions, holdings, trade history, ledger — every Dhan account Free
NSE files (optional) Free official bhavcopy / corporate actions / holidays for reconciliation ₹0

2. Three data tiers#

  • Tier A fills history once (and whenever you add instruments or files).
  • Tier B keeps every tracked instrument complete each evening — the learning engine and nightly plan use only Tier A/B data.
  • Tier C streams live data only for what you are actively trading or holding, keeping the system light.

3. CSV import (1-minute data)#

Built so far (P1-17a, ADR 0016): one fixed profile instead of the configurable ones below — the folder Data:CsvFolder (mounted read-only at /data/csv) with files <SYMBOL>_1m.csv[.gz] whose header columns time (epoch seconds, UTC, bar start), open, high, low, close, volume are found by name (others ignored). Each file is streamed (never held in memory) through the row rules, written with binary COPY into a staging table and merged in one transaction; a file already loaded and unchanged (name, size, modified time in market.csv_files) is skipped unless forced. Rules: an inconsistent high/low (the opening bar when the open is the pre-open price) is repaired (high = max, low = min of open/high/low/close) and counted; unparseable rows, prices not above zero, negative volume, a minute twice (the first is kept) and a time that is not a whole minute are rejected and counted with the first ten reasons; zero volume and special sessions (Muhurat) are kept. CSV never overwrites Dhan; Dhan overwrites CSV. <SYMBOL> ↦ NSE:<SYMBOL> (shares and ETFs that are not retired); unknown or ambiguous symbols are listed and skipped. Profiles and the watched folder stay with P1-07/P1-08; the review step and the undo are built (below).

A file is refused as a whole, before anything of it is merged (nothing stored, the file is not recorded as loaded, the reason is in the job's failedFiles) when

  • its clock is wrong: most bars lie outside the regular session (India time) but nearly all (≥ 99 %) fit a session after adding or subtracting 5 h 30 min (the message names the shift), or most lie outside every session, or the bars are stamped with the end of each minute (15:30 present, 09:15 absent) — the streaming counterpart of the window check of the Dhan fetch (§6); a few stray bars, the 60-bar Muhurat evening session and Saturday special sessions are legitimate and never trigger it (verified on the 214 real files: 41 M rows, none refused);
  • most of its times are not epoch seconds between 2000 and 2100 (milliseconds are named as such) or are later than one day from now; a few such rows are only rejected and counted (timeOutOfRange, timeInFuture);
  • it exceeds the limits that bound the work per file: Data:Csv:MaxRowsPerFile (default 5 000 000 rows; the real files have ≈ 200 000), Data:Csv:MaxBytesPerFile (default 1 GiB read after decompression, so a gzip bomb stops), Data:Csv:MaxSpanDays (default 3 700 days ≈ 120 monthly chunks of the hypertable).

Tracking after a load. After the files, the instruments that have bars from CSV files — loaded in this run or in an earlier one, so a tracking that failed is tried again by the next run even for unchanged files — are tracked, but only those that have never had a tracking row (active or not). An instrument the owner untracked is never tracked again behind their back, by a changed file or a forced load.

Review step and undo (P1-07a, ADR 0017 §6).

  • GET /api/data/csv/files lists the folder from its directory entries and the log of loaded files only (no file is opened, so 214 files list at once): per file state — pending (never loaded, or its load was undone) · loaded (size and modified time are what they were when it was loaded) · changed (loaded, but size or modified time differ now) —, size, modified time, the symbol parsed from the name, the instrument it maps to or mapping unknown · ambiguous (several instruments, or several files, claim the symbol) · invalidName (a .csv/.csv.gz that is not <SYMBOL>_1m.csv[.gz]; other extensions are not listed), and for loaded files rows, firstBar, lastBar (null for a file loaded before the range was recorded), loadedAt and overlapsWith (the names of the other loaded files of the same instrument whose first-to-last range intersects this one's — a file renamed after its load is loaded twice; a file without a recorded range counts as covering everything; null for pending files). Changed and pending files first, then loaded, each by name; q, state, page, pageSize (≤ 200); counts by state.
  • POST /api/data/csv/preview {files[≤ 20]} is a dry run of the real reader, the same row rules, limits and session check as a load, writing nothing: per file the rows, accepted, repaired and rejected counts (rejections by reason and up to 10 examples, line numbers only), first and last bar (India time), trading days (distinct India dates), the verdict — pass, or refused with the load's own refusal message (wrong clock, wrong time unit, a limit, no usable header) — the symbol mapping, the first 5 accepted rows and what loading would do to the stored bars: would insert, would update, keep existing Dhan bars, unchanged, counted by primary-key lookups of the file's minutes against market.bars_1m (the same classification as the merge, so the counts equal what the load then reports). A request looks up at most 1 million stored bars; beyond that a spread sample of whole batches is compared and the file's comparison says sampled with the rows it compared. A request also reads at most 2 × the per-file limits of Data:Csv (rows and bytes) and works for at most 60 seconds; the files after either limit, and the one being read when the time runs out, are error with the reason. Names are checked against the folder listing: a path, a traversal, a name with control characters or a file that is gone is that file's error, never a failure of the request.
  • POST /api/data/refresh {csvFiles} loads only the named files (≤ 214, each in the folder listing with a loadable name, else 400 data.invalid naming it; only with the csv step; unchanged files are still skipped unless forceCsv). The job keeps the list (csvFiles).
  • POST /api/data/csv/files/{name}/undo (session and CSRF, no step-up) starts a job that removes the file's csv-source bars of its instrument within the file's recorded first-to-last bar — never Dhan bars, never another instrument, never a CSV bar outside the range — and then rebuilds the instrument's aggregates; the file is pending again and the audit trail says CSV load of <file> undone, N bars removed (no row data). Values that an earlier load had overwritten are not restored (no history of replaced bars is kept): loading the file again writes its current values. The removal is by instrument and range, not by file: when another loaded file of the instrument overlaps the range (overlapsWith), its bars in the overlap go too; the job then carries a warning naming those files ("…cover the same time (a.csv, b.csv): the undo removed their bars in the overlap too. They stay loaded; load them again with force…"). 404 data.csv_file_not_found (never loaded or undone already), 409 data.job_running. The app role has no DELETE on bars (§9), so the removal is market.undo_csv_bars(instrument, from, to), one SECURITY DEFINER function owned by the migrating role (xd_owner) with a pinned search path, executable by xd_app only (§9).
  • The real files are already adjusted. The 214 CSV files of the owner are split- and bonus-adjusted at the source (checked on HDFC Bank's 2025 bonus and Bajaj Finance's 2025 split: prices are continuous across the ex-dates), so corporate actions (§4.2) only matter for ex-dates after the CSV data ends; entering the historical ones would adjust the history twice.

3.1 How files arrive#

  • Upload in the Data → Import screen (multiple files / zip), or drop into the watched folder data/inbox/ (mounted into xd-worker), or CLI xd data import <path> --profile <name>.
  • One file per instrument (symbol from file name) or multi-instrument files (symbol column) — both supported.

3.2 Import profiles (column mapping)#

Different CSV sources use different layouts; a saved profile describes yours once:

csv_profiles:
  my_1min_files:
    delimiter: ","
    header: true
    symbol: { from: filename, pattern: "^(?<symbol>[A-Z0-9&-]+)_1min\\.csv$" }   # or { from: column, name: symbol }
    exchange: NSE
    columns: { timestamp: datetime, open: open, high: high, low: low, close: close, volume: volume, oi: null }
    timestamp: { format: "yyyy-MM-dd HH:mm:ss", timezone: Asia/Kolkata, label: bar_start }   # bar_start | bar_end
    prices: { adjusted: false }        # raw prices; system applies corporate-action adjustments
    session_filter: { from: "09:15", to: "15:29" }

Example accepted file (TATASTEEL_1min.csv):

datetime,open,high,low,close,volume
2026-10-05 09:15:00,152.10,152.60,151.95,152.40,412530
2026-10-05 09:16:00,152.40,152.55,152.20,152.30,198220

3.3 Import pipeline#

  1. Detect profile (or use the one specified); preview the first rows in the UI before committing.
  2. Map symbol → master list; unknown symbols are listed for you to map or skip (never guessed).
  3. Validate each row: timestamp parse, within session, OHLC consistency (low ≤ open/close ≤ high), no negative volume, no duplicate timestamps; bar-end labels shifted to bar-start.
  4. Upsert into market.bars_1m with source = csv. Precedence on overlap (configurable): Dhan official > CSV > live; conflicts beyond tolerance are logged, not silently overwritten.
  5. Refresh aggregates for the affected instrument/date range.
  6. Report: rows imported/updated/rejected per file, coverage before/after, quality issues — stored as an import job you can review and undo. Built (P1-07a): the job's report per file, the preview before the load and the undo per file (see the notes above); undo by job id is not built.

Instruments in the files are auto-added to the tracked list (configurable), so they are kept up to date by Tier B afterwards.

4. Aggregation to other timeframes#

All timeframes are built from 1-minute bars — identical logic for CSV and Dhan data.

Rule Detail
OHLCV open = first, high = max, low = min, close = last, volume = sum, OI = last
Alignment Intraday buckets anchored to the 09:15 session open: 15m = 09:15, 09:30…; 1h = 09:15–10:15 … 14:15–15:15, then 15:15–15:30 (partial, flagged)
Timeframes 5m, 10m, 15m, 30m, 1h (and any custom minute size) · 1D · 1W · 1M
Daily bar daily_source: official (Dhan daily candles, default when available) or derived (from 1-minute) — official open uses the pre-open auction price, so the two can differ slightly
Missing minutes Bucket built from available minutes; bars (the number of 1-minute bars in it) and a complete flag are stored (what complete means: see below)
Special sessions Holidays skipped; special sessions (e.g. Muhurat, a Saturday session) are kept as they come, and the trading calendar (below) names them: a special session has its own window, a 1D bar of a Muhurat evening is complete when every minute between its first and last bar is there
Implementation In the application, not continuous aggregates (ADR 0016): set-based SQL upserts (date_bin with the 09:15 origin) run by the aggregate phase of the data job, for the ranges whose 1-minute bars changed since the last build (or everything on request); real-time aggregation combines materialised + newest rows (P2)

Why not continuous aggregates. The runtime role xd_app has plain DML only and may not refresh or own a continuous aggregate; a refresh policy would need a second privileged path, and a continuous aggregate cannot express the rules above (09:15 anchoring with a partial 15:15 hour, Monday weeks, a completeness flag, a day that is the India date, a special evening session) as plainly as a query we can test. So the application builds market.bars_agg itself with idempotent upserts (a bucket that comes out the same is not written), per instrument and changed range, as xd_app, and a test recomputes every bucket with an independent implementation over fixtures (a Muhurat evening, month and week boundaries, gaps) and compares them exactly.

Bucket rules as built (all from the stored 1-minute bars; times are India time, UTC+05:30, no daylight saving):

Timeframe Bucket start (ts) bars complete
5m, 10m, 15m, 30m 09:15 + k × N minutes of the same India date (09:15, 09:30 … for 15m) 1-minute bars in the bucket exactly the minutes of the bucket's window, clipped at the 15:30 close for buckets that start before it (the 10m bucket at 15:25 and the 30m bucket at 15:15 hold 5 and 15)
1h 09:15, 10:15 … 14:15, then 15:15 (the partial 15:15–15:30 hour holds 15 bars) as above as above
1D India midnight of the India date (a Muhurat evening belongs to its own date) 1-minute bars of the date all 375 minutes of 09:15–15:29 are there; for a date without a single regular-session minute (an evening session) every minute between its first and last bar is
1W India midnight of the Monday of the week sum of its days every day with bars is complete
1M India midnight of the first of the month sum of its days every day with bars is complete

The streaming TimeframeBuilder of XDrishti.Indicators (P3-01 and P3-01c, ADR 0031, ADR 0033) reproduces these rules for 5m, 10m, 15m, 30m, 1h, 1D, 1W and 1M on a live stream of 1-minute bars and is tested against an independent grouping of the same fixtures; it emits a bucket when its last minute has arrived, or — flagged complete = false — when a later bucket or session proves the minute will not come. Where it can differ from the stored aggregates: (a) a regular date's 1D bar is closed by the 15:29 bar and any later bar of the same date (an evening bar) is ignored and counted, while the stored 1D merges every bar of the date; (b) a calendar entry that disagrees with the data (a session shorter than the bars) closes the day at the calendar's end; (c) the last bucket of a stream whose final minute never arrives is not emitted (there is no flush), and a special session without a calendar closes its last bucket and its day only at the next date. To compare with stored data, pass the same TradingCalendar.

1W and 1M in the streaming builder (P3-01c). A week or month is built from the days of the builder's own 1D rules (open = first day's open, high = highest high, low = lowest low, close = last day's close, volume and bars = the sums, complete = every day that has bars is complete) and is emitted once, when the period is over:

With a TradingCalendar Without a calendar
Emitted at the step that closes the last session of the period — the greatest date of the week (Monday to Sunday) or month with IsTradingDay — which is the step at which the 1D bar of that date closes (the Thursday when Friday is a holiday; the last weekday of a month that ends on a weekend; the last minute of a known Saturday session) at the first bar of a later period (the next Monday, the 1st of the next month): the builder cannot know that a Friday is the last session — later, never earlier

In both cases the first bar of a later period closes a period that the last session did not (a last session whose final minute never arrived, or a calendar session without bars), so a period is never lost; a period with no bar is never emitted. Where it can differ from the stored 1W / 1M: (d) the stored bucket merges every bar of the period, the streaming bar only the days the 1D lane accepts, so a bar of a period that has already been emitted (a special session the calendar did not know, a date after the calendar's last session of the period, a calendar that says Friday is a holiday while the data has Friday bars) and a bar the 1D lane ignores (an evening bar after a regular close) are ignored and counted in Ignored; (e) the streaming bar exists when the period is over, the stored one while it runs; (f) the last period of a stream is not emitted (no flush), and a stream that starts in the middle of a period gives that period only the days from its first bar.

4.1 Trading calendar (ADR 0017 §1, P1-11a)#

What a session is comes from one place, market.trading_days (one row per date that is not an ordinary weekday session; nothing is seeded), read through the pure domain type TradingCalendar and, for any slice, the application port ITradingCalendar (the confirmed days are read once per request or job and kept as an in-memory snapshot; changing the calendar invalidates it).

Column Meaning
date (PK) the India date
kind holiday (a weekday without a session) · special (a session of its own on any date: a Saturday session, the Muhurat evening)
session_from, session_to India time, to exclusive; only for special (a holiday has none)
source manual (the owner) · observed (derived from the stored bars) · nse (NSE's public holiday list)
status confirmed (counts) · proposed (waits for the owner) · dismissed (declined; kept so it is not proposed or listed again)
note, updated_at free text up to 200 characters, last change
proposal_status, proposed_kind, proposed_from, proposed_to, proposed_note a proposal next to a confirmed row (P1-11a review): what the stored bars show when it contradicts a confirmed day, e.g. a session on an NSE-listed holiday. proposal_status proposed (waits) · dismissed (declined; remembered so it is not proposed again) · null. The confirmed row keeps deciding what a session is; the proposal changes nothing until the owner confirms it
xmin PostgreSQL's row version, mapped as the optimistic-concurrency token: a save based on a row someone changed meanwhile is refused, never overwriting or deleting the newer row

TradingCalendar answers IsTradingDay(date) (a weekday that is not a confirmed holiday, or a confirmed special session), SessionOf(date) (09:15–15:30 India time, or the special window), ExpectedMinutes(date) (375, the window's length, 0 when closed), LastClosedSession(now) (today once its session is over — 15:29:59 is still before the close, 15:30:00 is after it, a Muhurat day closes at its own end —, otherwise the trading day before) and TradingDaysBetween(after, upTo) (trading days after the first date up to and including the second). Only confirmed days count; a proposal changes nothing until the owner confirms it.

"Behind" is the last bar's date against the last closed session, counted in trading days — the Data screen's status ribbon, the overview's expectedSession/daysBehind/stale and every coverage row's status (current/behind/empty) and daysBehind. A long weekend with a holiday on the Friday is therefore not "behind". The overview also carries nextHoliday (the first confirmed holiday today or later) and calendarProposals (how many days wait for confirmation).

Sources and trust (manual > observed > NSE). The owner adds a holiday or a special session (POST /api/data/calendar: confirmed at once, replacing whatever the date had), confirms a proposal (PUT /api/data/calendar/{date}/confirm) or removes a day (DELETE /api/data/calendar/{date}: the owner's own entry is deleted; a proposal or an NSE day becomes dismissed, so it comes back neither as a proposal nor from the list; removing a dismissed day deletes it; a date with a proposal next to a confirmed day dismisses only that proposal and leaves the confirmed day — remove the date again to take the day itself off). Changes are audited (doc 04 §2: CalendarDayAdded, CalendarDayConfirmed, CalendarDayRemoved, CalendarRefreshedFromNse: the date, kind and window — never the note).

  • Observed proposals are computed after every data job, from the daily aggregates (so the bars must be aggregated; while any instrument has changes that are not, nothing is concluded). A weekday on which fewer than 5 % of the instruments that have bars before and after it have any bar is a suspected holiday (a day with normal coverage, or one on which a handful of instruments lack their files, is nowhere near; a day on which only 3 of 214 instruments have bars is suspected, however it came about). A weekend date with bars from at least 5 % of the instruments, or a weekday whose bars lie in the evening window (17:30–20:00), is a special session with the window most instruments share (first bar to the minute after the last): the 2024-11-01 Muhurat evening (60 bars from 18:15) and the Saturday sessions of the real files come out this way. So is any weekday that is a confirmed holiday (NSE's list, say) on which at least 5 % of the instruments have bars, whatever their window — a holiday that was moved or called off trades a regular session (09:15–15:30), a Muhurat session on a listed Diwali holiday is in the evening. Proposals are refreshed on every run (a proposal the bars no longer support, because the day was filled in later, is withdrawn) and never confirmed by the system. One window per date: a Saturday with two separate sessions gets one window around both.
  • NSE's list (GET https://www.nseindia.com/api/holiday-master?type=trading, the CM segment, entries tradingDate dd-MMM-yyyy and description) is fetched best effort, once a day after a data job and on request (POST /api/data/calendar/refresh, always 200: succeeded false with the reason and nothing changed when NSE refuses — it often wants a browser-like client and a cookie from its home page, which are not sent — or the format has changed). A failure is only a warning of the job; manual add is the path that always works. New weekday holidays are stored confirmed (nse). A session seen on a confirmed NSE holiday does not replace it: the observation is attached to the confirmed row as a proposal (GET /api/data/calendar lists it under proposals with replaces = the kind of the confirmed day, and the overview counts it in calendarProposals), the date stays a holiday for gaps, quality and "behind" until the owner confirms the proposal (PUT …/confirm turns the day into the special session, source observed) or dismisses it (DELETE). The proposal is refreshed with every run and withdrawn when the bars no longer support it or agree with the holiday. NSE's list never overrides the owner's rows or days the owner dismissed. Withdrawing a proposal deletes the proposal row only if it has not changed since the pass read it (row version): a proposal the owner confirms at the same moment is never deleted. The endpoint is on the master-data allow-list (doc 17 §3, ADR 0010).

complete for 1W and 1M means that every day that has bars is complete — not that the week or month is over: the running week or month is complete as long as the days so far are; use the last bucket's date, not the flag, to tell an unfinished period.

ts of every bar is a UTC instant; the API shows it with the India offset (+05:30). The days, weeks and months are built from the day bars, the day bars and the intraday bars from the 1-minute bars. Prices are raw by default; adjusted=true on the bars read applies the owner's confirmed splits and bonus issues on read (§4.2).

4.2 Corporate actions and price adjustments (ADR 0017 §5, P1-10a)#

Bars are stored raw. A split or bonus issue changes the share count and so the price level; market.corporate_actions records them, and adjusted reads (GET /api/data/instruments/{id}/bars?...&adjusted=true, and the reusable application service IAdjustmentFactors for later research reads) multiply the older prices on read. Plans and anything about tradable levels use raw prices. Dividends are not adjusted (adjust.dividends: false; adjust.splits_bonus: true in doc 16).

Column Meaning
id, instrument_id the action and its instrument (unique per instrument_id, ex_date, kind)
ex_date the India date the price level changes: the first session at the new level
kind split · bonus
numerator, denominator whole numbers 1 to 100000. Split n:d = old shares : new shares — 1:5 turns one share into five (a 5:1 is a consolidation). Bonus a:b = bonus shares : shares held — 1:1 is one bonus share for each held, 1:2 one for every two
factor the price multiplier for the bars before the ex-date, derived and stored (12 decimals): split n / d (1:5 → 0.2), bonus b / (a + b) (1:1 → 0.5, 1:2 → 2/3, 1:3 → 0.75). A split 1:1 changes nothing and is refused
status suggested (found by the detection; changes nothing) · applied (counts) · ignored (declined; kept so it is not suggested again). Rows are never deleted: xd_app has no DELETE
source manual · detected · csv
note, created_at, decided_at, decided_by a note up to 200 characters, when it was created, when and by whom (the owner's e-mail) it was confirmed, edited or ignored (null while suggested)
detected_ex_date the ex-date the detection first found the action on (null for actions nobody detected); it stays when the owner corrects the ex-date, so the detection does not suggest the old date again

Adjustment (pure AdjustmentFactors): a bar whose India date is strictly before an action's ex-date is multiplied by its factor; the ex-date itself and later are not. Several actions multiply (order does not matter). Open, high, low and close are multiplied and rounded to 4 decimals only at the output; volume is divided by the cumulative factor (more shares before a split) and rounded to whole shares. It works for every timeframe: each bar uses the factor of its own start date — a 1m or intraday bar its India date, a 1D bar its day. A 1W or 1M bar is built from the adjusted day bars when its bucket contains an ex-date after its first day (open of the first day, highest high, lowest low, close of the last day, volumes added, with the same bucket rules as the aggregates: weeks from Monday, calendar months); a bucket lying wholly before or after the ex-dates has one factor for all its days and is adjusted like a day bar, one that starts on the ex-date is not adjusted. Without an applied action the adjusted weeks and months equal the raw ones. (An earlier version applied the first day's factor to the whole bucket, which was wrong for the days from the ex-date on.) The response carries adjustment {applied, factor, actions[{exDate, kind, ratio, factor}]}: applied is the number of applied actions that changed the bars returned (ex-date after the oldest bar returned), factor the cumulative factor of the oldest bar, actions those actions oldest first. Without adjusted=true the prices are raw and adjustment is null.

Detection (pure ActionDetector, over the day bars bars_agg 1D; suggestions only, never applied). A day d is a candidate when

  1. its open, or else its close, is within 2.5 % of one of the common price factors 1/2, 1/3, 1/4, 1/5, 1/10, 1/20, 2/3, 3/4 of the previous close;
  2. its volume is at least 1.5 × the median volume of the 20 sessions before it (at least 10 must exist; the volume must be above 0);
  3. the move is not reversed: neither the close of d nor the closes of the next 3 sessions that exist come back above previousClose × √factor (the middle between the old level and the new, in log terms). A candidate on the newest day is judged on the sessions there are.

Reverse splits (a price rise) are not looked for. The ratio found maps to one reading, with a note naming the other: 1/2 → split 1:2 (also bonus 1:1), 1/3 → split 1:3 (bonus 2:1), 1/4 → split 1:4 (bonus 3:1), 1/5 → split 1:5 (bonus 4:1), 1/10 → split 1:10 (bonus 9:1), 1/20 → split 1:20 (bonus 19:1), 2/3 → bonus 1:2 (split 2:3), 3/4 → bonus 1:3 (split 3:4). The owner edits the kind or ratio when confirming. A date on which the instrument has any action (any kind, any status, ignored included), or on which an action was first detected (detected_ex_date, also after the owner moved it to another ex-date), is never suggested again, and the store ignores a suggestion that exists, so running the detection again suggests nothing new. It runs after the aggregate phase of every data job (only the days that job changed, with the sessions before them as context; a failure is logged and never fails the phase; the phase message says how many were suggested) and on request (POST /api/data/corporate-actions/detect, the whole history of every share and ETF with day bars).

Owner decisions (/api/data/corporate-actions): GET (filters status, instrumentId, page, pageSize; the page also carries pending), POST (add by hand: applied at once), PUT /{id} (confirm a suggestion — an empty body confirms it as it is — or change the ex-date, kind, ratio or note; fields left out keep their value; the result is applied, also for an ignored one), POST /{id}/ignore, POST /import (CSV text symbol,exDate,kind,numerator,denominator, as the request body or the first file of a multipart upload; preview=true writes nothing; at most 5,000 lines; unknown symbols are listed and never guessed; lines that repeat an existing action of any status are skipped; bad lines are reported and skipped). Errors: data.invalid (fields), data.instrument_not_found, data.corporate_action_not_found, data.corporate_action_exists, data.corporate_action_conflicts_same_day, data.csv_already_adjusted (below). Each add, confirmation, edit, ignore and import is audited (doc 04).

A split and a bonus on one day. Applying one kind (add, confirm, edit, import) while the instrument has the other kind on that ex-date: a still-pending suggestion of the other kind is declined by itself (it was only a guess; audited as CorporateActionIgnored), an applied one blocks with 409 data.corporate_action_conflicts_same_day until it is ignored first. Ignored actions do not count. In an import such a line (or one that clashes with an earlier line of the same text) is a problem line — reported in errors, skipped — and the rest is imported.

The owner's CSV files are already adjusted — double-adjustment protection. csvAdjustedThrough (a date, or null) is, per instrument, the date of the last bar of its loaded CSV files that are not undone (max(csv_files.last_bar) in India time); it is on every item of GET /api/data/corporate-actions and on the views the add/edit/ignore return. An action with an ex-date on or before it would adjust those prices a second time, so adding it, confirming or editing a suggestion into it (when the result is applied and its ex-date, kind or ratio changes — not a note change of an applied action) and importing it is refused with 409 data.csv_already_adjusted (the problem carries adjustsCsvTwice and instruments) unless the owner consents: acknowledgeCsvAdjusted=true in the JSON body or the query of POST/PUT, and as the query acknowledgeCsvAdjusted=true of the import. The import preview (preview=true, never refused) returns adjustsCsvTwice (the importable lines that fall into the adjusted part) and warnings[{line, symbol, exDate, csvAdjustedThrough, message}] (the first 50); an import with such lines needs the acknowledgement. Duplicates that are skipped do not count. The UI shows its confirm dialog and then sends the flag.

The same guard in a simulation run (P3-04a). The research run reads the raw bars and adjusts a copy with the applied actions, so an applied action that falls into a CSV-adjusted series would adjust it twice there too. Before the replay, RunSimulationHandler asks ListCsvAdjustedThroughAsync once for all instruments of the run; if an applied action that changes the bars read (ex-date after the date of the instrument's first bar) has an ex-date on or before csvAdjustedThrough (the predicate above, CsvAdjustment.AdjustsTwice) and the request does not carry acknowledgeCsvAdjusted, the instrument is skipped as csv_adjusted_twice (its sessions are still classified and its bars hashed) and the run goes on; with the acknowledgement it runs, the record marks each such adjustment OnCsvBars, and the acknowledgement is part of the run key. The run asks again although the owner acknowledged when applying the action: a result computed on twice-adjusted prices must be a conscious choice. The rule is the screens' own, conservative one, with known edges that a test pins: it also flags an action dated before the CSV start (harmless for the CSV bars, right for earlier Dhan bars); it flags a CSV range that Dhan bars have since overwritten; a series that mixes Dhan bars and a CSV span is covered by the same predicate (ReadAsync returns the merged series with no source per bar); and an instrument with no loaded CSV, or whose files predate the recorded range, is absent from the answer, so the guard is silent for it.

Where it shows. pendingCorporateActions (the suggestions waiting) on the Data overview and the Data quality overview, and the bell notice data_corporate_actions_pending (warn) in GET /api/data/notices. Measured on the 214 CSV files of the owner (two years of 1-minute bars, which are already adjusted by their source: prices are continuous across HDFC Bank's 2025 bonus and Bajaj Finance's 2025 split — so corporate actions only apply to ex-dates after the CSV data ends; adding an earlier one would adjust the history twice) the detection suggested 4 actions in 214 × ~500 sessions, all of them real one-day price collapses (Adani Enterprises 21 Nov 2024, REC 4 Jun 2024, PGEL 8 Aug 2025) or a restructuring (Siemens 7 Apr 2025) that fall in the 2/3 and 3/4 bands and none in the split bands: the owner ignores them. Recall on those series with the adjustment undone synthetically (a split or bonus at three points of each of the 214 series): 1/10 and 1/5 99 %, 1/4 97 %, 1/3 90 %, 1/2 64 %, 2/3 41 %, 3/4 32 % — the 1.5 × volume rule is what a 1:2 split (volume ×2), a 1:2 bonus (×1.5) and a 1:3 bonus (×1.33) rarely clear, so those are the actions to add by hand or by CSV.

6. End-of-day fetch (Tier B)#

Scheduled after close (default 15:50 IST) before the nightly pipeline:

  1. Refresh Dhan token; refresh instrument master (new listings, lot sizes, expiries).
  2. For every tracked instrument: fetch today's 1-minute candles and daily candle (throttled, chunked, resumable).
  3. Detect gaps for recent days and backfill (§6.1); corporate actions (§4.2: the detection follows the aggregate phase and only suggests); calendar (§4.1: NSE's holiday list and the observed proposals follow every data job).
  4. Quality checks (§10b, the last step of the same job); reconcile with NSE files if enabled.
  5. Refresh aggregates; then the nightly pipeline starts (doc 03 §7).

Adding new tracked instruments triggers a backfill job (CSV first, then Dhan for gaps).

Built so far (P1-17a, ADR 0016 §7): the manual Dhan phase of the Update data button, without the schedule, gap detection or the daily candle. For every tracked, not retired share, ETF or index with a Dhan id (instrument_broker_ids) it calls Dhan's Data API once per window of at most 90 days, from two days before the instrument's last stored bar (the overlap proves the timestamp alignment: price differences beyond 0.05 % are counted as warnings) or Data:Dhan:InitialDays (365) back, up to now:

6.1 Scheduled run and gap backfill (ADR 0017 §2–§3, P1-12a)#

Built (P1-12a, spec; moved onto the services framework by P1-13, ADR 0018): the schedule and the gap backfill, in xd-api.

The scheduled run. The end-of-day run is the service eod of the Services screen (doc 04 §3.1): the scheduler starts the ordinary data job with the steps dhan, aggregate, quality (every step of the pipeline but csv, which is for history the owner brings by hand; the quality checks of P1-14a are §10b) and trigger daily, requested by system:data-eod, and the run ends as the job does (its progress is linked to the run record, data_job_id). The run time is set on the Services screen — by default 15:50 India time on trading days of the calendar (§4.1: no weekends or holidays, special sessions included) and never before that day's session has closed — a special evening session such as Muhurat moves the day's run to its end. Data:Eod:Enabled and Data:Eod:TimeIst are only the first-start settings: read once, when the service has no stored row, and ignored after it (a service paused there is switched off). Catch-up: when the application starts on a trading day after the run time and no run exists for the day, it runs at once (a paused service never does). At most one automatic run per day. When another data job is running, or the primary Data account cannot fetch (no account, not connected, expired) or the Dhan fetch is not available, no job starts: a skipped run is recorded (job status skipped, the reason as its error, no phase ran) and nothing is retried that day; the owner runs "Update data" by hand. A failure (a database error, a failed job) ends the run as failed; it is retried only when the service's retries setting says so (default none), and raises a notice when notify on failure is on. Jobs carry trigger (manual | daily); the overview's eod block gives enabled (the service is not paused), timeIst (the time of the stored schedule), nextRunAt (the next scheduled start; null when paused), scheduleWords and lastRun (the latest automatic data job: id, start, end, status, trigger, reason) — the same schedule the Services screen edits.

Gap detection and backfill (the Dhan phase of every job, scheduled or not). For each tracked instrument with bars, the sessions of the last Data:Gaps:LookbackSessions (default 30, 1 to 250) trading days of the calendar that have closed (never today's open session) and that lie after the day of the instrument's first bar are counted. The bars of a day come from the daily aggregate's bars column — one cheap read of a month of days; only the days of the instrument's not-yet-aggregated range (the dirty range) are counted in the 1-minute table, by its primary key — and compared with the calendar's expected minutes: 375 for a regular session, the window's length for a special one, none for a holiday or weekend (never a gap). A session with fewer bars is a gap in market.bar_gaps (instrument_id, date, expected, found, attempts, last_attempt_at, status, detected_at), status open | filled | unfillable.

Situation What happens
A gap older than the ordinary window (two days before the last bar) Recorded open and fetched in extra windows: gap sessions that follow each other in the calendar share a window, windows are cut at 90 days (the planner of §6 above); the bars go through the same merge, precedence and dirty-range path as every fetch, so the aggregates are rebuilt
A partial session inside the ordinary window Fetched anyway; recorded as a gap only if the fetch does not complete it
After the fetch: all expected bars there filled
After the fetch: more bars than before, but not all stays open (found updated, attempts + 1); asked for again by the next run
After the fetch: no more bars than before (a halt, a circuit-locked day) unfillable, attempts + 1; scheduled and ordinary runs leave it alone; "Re-fetch gaps" (refetchGaps: true) asks again
The instrument's fetch fails nothing is decided and no attempt is counted: it is retried by the next run
A known gap complete by other means (a CSV file) filled without a fetch; a filled session that lost bars (an undone file) opens again
A gap older than the lookback that is still open still retried until it is filled or unfillable

Which gaps count. The records are kept for every instrument, but the overview, GET /api/data/gaps, the hasGaps filter and the bell notice count only the gaps of tracked, not retired instruments (the quality universe): untracking or retiring an instrument takes its open gaps out of sight, tracking it again brings them back.

Start-up. The catch-up at start waits for the data worker's recovery of jobs a previous process left running (DataJobRecovery, at most two minutes), so such a job is not mistaken for a running one; when a start fails because a job runs, the day's automatic jobs are looked at again before a skipped run is recorded (a run of the day that appeared meanwhile is not followed by a skipped row), and the wait slices are clamped at zero so a clock that jumped cannot make a delay negative.

The phase reports gapsFound, gapsFilled and gapsUnfillable (sessions it asked for or found incomplete) and warns when some stay open. Notices for the bell (GET /api/data/notices, derived from state like the account notices, with an id that includes the situation): sessions are left with open gaps (data_gaps_open, warning; unfillable sessions raise nothing — they are listed, not alarming); P1-14a adds data_quality_failed (§10b). A failed automatic run (data_run_failed) was a data notice in P1-12a; replaced by the service_failed notice of the end-of-day service in P1-13 (GET /api/services/notices, governed by the service's notify on failure).

8.2 Reading the holdings (ADR 0012, P2-01)#

GET https://api.dhan.co/v2/holdings with the header access-token (the account's stored token, read from the vault) answers an array of {exchange, tradingSymbol, securityId, isin, totalQty, dpQty, t1Qty, mtf_t1_qty, mtf_qty, availableQty, collateralQty, avgCostPrice, lastTradedPrice} — no purchase date and no previous close. xDrishti uses exchange, tradingSymbol, securityId, isin, totalQty, avgCostPrice and lastTradedPrice. It is the holdings endpoint of the allow-list (GET, HTTPS, exact path, no query, no redirects, 30 s, answers up to 5 MB); the allow-list holds api.dhan.co paths for the chart data (§6), the quote (§5), and since P2-13 the trade history and the ledger (§8.3), never orders, positions or funds. A 401/403 means the saved token is expired or revoked (409 portfolio.not_connected, "sign in to Dhan again"); other 4xx and 5xx/timeouts are 502 accounts.broker_error. An empty array (HTTP 200 []) and Dhan's documented data error DH-907 ("incorrect parameters or no data present"; this request has no parameters, so here it can only mean no data) both read as an empty list; DH-1111 is not in Dhan's documentation and is only tolerated as an alias. An empty list is never trusted blindly: see the safeguard in doc 12 §3. Rows of one holding (same ISIN, or same security id and exchange) are added up (quantity summed, average cost weighted). Neither the token, the URL nor the raw answer is logged or returned.

The guard accepts exactly these shapes and still refuses every other path and method:

Endpoint Shape accepted by the guard Answer (field names from Dhan's public documentation, not yet seen in a real answer of the owner's account)

A trade row is kept when it is NSE_EQ and its product is not an intraday product — delivery (CNC, MTF), MARGIN and a row with no product are all kept: BSE, derivatives, currency, commodity and other segments are skipped per reason, and so are the intraday products (INTRADAY, INTRA, MIS, CO, BO), counted as intraday. Security. tradingSymbol can be null in Dhan's rows: the ticker is then found through Dhan's securityId (market.instrument_broker_ids, dhan, NSE_EQ), else through the isin; a row that no instrument matches but that has an ISIN is stored ISIN-only (empty ticker, like a tradebook CSV line with an ISIN and no symbol) and matched to its holding by ISIN; a row with none of ticker, resolvable id and ISIN is not stored and counted as skip reason no_symbol. Charges and ISIN. charges is the sum of the six charge fields (rupees, 4 decimals; strings and "NA" tolerated; a missing or unreadable field is 0) and the ISIN is stored with the transaction; the charges are counted in the net returns since P2-14 (ADR 0026) as a separate line, and are not used by lots, cost or the gross XIRR. A broker trade stored by an earlier read without its ISIN, ticker or charges is completed when its day is read again (only those three, only when missing, never the date, side, quantity or price; counted as enriched, doc 12 §3). A ledger amount is one signed number, credit − debit; a row with an unreadable date or amount, or that moves nothing, is dropped and counted. The classifier knows the published sample's PAYBNK (funds_out), FUNDS ADDED / PAYIN (funds_in) and DPC Interest (charges). Dividends are not in this ledger as a rule: Dhan credits them to the owner's bank account (a dividend-class entry is rare, e.g. rented stocks), so the owner enters dividends (P2-14, ADR 0026); a dividend-class entry is only offered as a suggestion. Of the charges-class entries only those naming an account-level cost (DP, AMC, delayed-payment interest, penalty, platform fee, pledge / payout / withdrawal charges, call & trade) count in the net returns; the trade-related ones (brokerage, STT, stamp duty, SEBI, transaction charges, settlements) are never summed, because the trade rows carry those costs.

Errors. 401/403 or DH-901 (token refused): portfolio.token_expired for the owner; 429/DH-904, 5xx and timeouts are failures of the run — none of these is ever turned into "no data". Since P2-16 (ADR 0027) they are noted as the reasons rate_limited and unavailable and retried quietly inside the day (1, 5 and 15 minutes by default, doc 12 §3 "Self-healing and attention items (P2-16)"); a 429 is read as DH-904 whether or not Dhan's body carries the code (an empty body included), so a rate limit is never mistaken for a refusal; any other 4xx is rejected and not retried. Since P2-18 (ADR 0030) the reason is a structured failure kind set where the status and code are read (a 429, or a 4xx with DH-904, is RateLimited); no code matches the text of a message. Only the HTTP status and a well-formed Dhan code are logged; never the token, the URL, the rows or Dhan's text.

Window too large — DH-905. Dhan documents no maximum span and no history depth for either endpoint, so windows start at 30 days; an earlier from is accepted (floor 1990-01-02) and far-back reads mean many 30-day windows. DH-905 ("input exception", how a too-wide range is expected to be refused; unverified), or 200 pages of trades without an empty one, halves the window once and each half is read on its own; if a half is too large too, the run ends failed with the "history too large" text and nothing of the window is stored.

No data — DH-907. "Incorrect parameters or no data present" cannot tell an empty window from a bad request. The decision (ADR 0025, amended after the first review): on page ≥ 1 of a trades read it ends the paging (empty result); on page 0 of a window longer than one day it is unclear — the window is halved once and the halves are used, and a half that also answers DH-907 on page 0 is taken as empty and counted (emptyByNoData), so a systematic parameter error does not pass silently; on a one-day window it is an empty result (counted). The ledger has no paging (one call per window) and follows the same rule: a multi-day window answering DH-907 is halved once, and a half or a one-day window answering it is empty and counted. The sync status line names the count ("Dhan answered "no data" for N date ranges") only when more ranges answered no data than windows were read. (The chart client of §6 reads DH-907 as a failure instead; the holdings read of §8.2 as an empty list.) The first real read settles whether Dhan answers 200 [] or DH-907 for a day without trades. Mapper version (P2-16). IBrokerTrades and IBrokerLedger each report a MapperVersion (the Version constant of DhanTradeMapper and DhanLedgerMapper, 1 today); a change to a mapper that could make rows readable which an older version had to drop must raise it, and the next run then reads again the stored windows that dropped rows (doc 12 §3). Deepening (P2-16). The nightly run may read one year before the earliest date read so far, per day and up to 8 years back, while the trades do not explain a holding; it stops at the first year Dhan refuses with something retrying cannot change or that holds no trade. How the run uses these reads — windows, watermark, gap refusal, rebuild — is in doc 12 §3 "Dhan sync (P2-13)".

Imported ledger entries and the DP file (P2-17, ADR 0029). The ledger API is not the only source of portfolio.ledger_entries: since P2-17 an entry has a source — broker (read from the endpoint above, with its run) or import (made from a DP-charges sheet the owner downloaded from Dhan, with its batch, the security's ISIN and the quantity). An imported entry is class charges, a negative amount, description "DP charges", and counts in the net returns like any account-level cost (once: a line whose amount equals a charges entry of the Dhan ledger on the same day is skipped as already in the ledger, and ₹0 and buy-side lines are not stored). The sheet is read from legacy .xls, .xlsx or CSV (ExcelDataReader 3.7.0 behind ISpreadsheetReader, no conversion step); nothing is fetched from Dhan for it and no allow-list entry is needed. Imports are undone by voiding (the entry leaves the lists and the figures; nothing is deleted). How the file is read, matched and previewed: doc 12 §3 "Dhan report imports (P2-17)".

The chunks of bars_1m are protected too. A hypertable's chunks are tables of their own (_timescaledb_internal._hyper_*_chunk, and for compressed ones _hyper_*_chunk_compressed), reachable by name, so the missing DELETE on market.bars_1m would mean little if xd_app could delete from them. It cannot: TimescaleDB gives every new chunk — ordinary and compressed, whenever created — the privileges of the hypertable (xd_app has SELECT, INSERT, UPDATE on them, no DELETE, TRUNCATE, REFERENCES or TRIGGER), and the default privileges that grant DELETE on new tables do not override that. This is verified by DataTableGrantsTests against the real extension as the real role (privilege check and an attempted DELETE/TRUNCATE on a chunk created after the migrations and on a compressed chunk), so no extra migration or event trigger is needed; a TimescaleDB upgrade that changed it fails that test.

Residual risk (accepted). xd_app has UPDATE on bars_1m (the merge needs it), including its source column, so a bug or an attacker with the app's database credentials could relabel Dhan bars as csv, after which undo_csv_bars could remove them. The DELETE protection is therefore only as strong as the app's honesty about source; a column-level privilege would break the merge's upsert, and the risk is accepted for a single-owner local system. undo_csv_bars does not reject ±infinity as a range end (date_bin passes it through): called directly with one, it would remove all csv-source bars of that one instrument and the matching aggregates — still inside the function's scope (one instrument, CSV source, never Dhan), and the application only ever calls it with the recorded first and last bar of a file. An explicit check would mean replacing the whole function in a further migration; it was left out and is documented here instead.

The one door for removing bars (P1-07a). market.undo_csv_bars is the only way xd_app can remove bars, and DataTableGrantsTests proves its narrowness as xd_app against the real extension: a direct DELETE/TRUNCATE is still refused; the function deletes only CSV rows of the one instrument within the range (ends included) and nothing for a wrong instrument or a range without CSV bars; Dhan rows survive; another role cannot execute it (and a GRANT … TO PUBLIC by xd_app grants nothing); xd_app cannot CREATE OR REPLACE, ALTER or DROP it; a caller's hostile search_path (a schema with decoy tables, an always-true >= operator, failing date_bin/now functions, a temp table of the same name) is never picked up. On compressed chunks the delete works (TimescaleDB decompresses the batches the delete touches, with the function owner's rights): the chunk is then partially compressed (status compressed + partial), all rows remain readable, and the compression policy — or compress_chunk(…, if_not_compressed => true) — packs it again. Verified on TimescaleDB 2.30 (the version of the compose stack).

Where it runs. The quality run is the fourth step of the data job (csv, dhan, aggregate, quality, always in that order), recorded in market.quality_runs / market.quality_results. A job therefore shares everything a data job has: the single one-at-a-time rule (a quality run and a data job exclude each other, 409 data.job_running), the worker, the progress (the job's quality block: done of total instruments, passed/warned/failed, runId) and the recovery at start-up (a run still running that began before the process is marked failed; a run whose data job ended is failed when the next one starts). Without steps "Update data" still runs csv, dhan, aggregate — the quality step is only run when the request lists it (trigger of the run: after_job). The scheduled end-of-day run is dhan, aggregate, quality (daily). POST /api/data/quality/run {instrumentId?} is a job with the single step quality; the fix actions are jobs about one instrument (instrumentId on the job): Re-fetch = dhan (the instrument only, refetchGaps so unfillable days are asked for again) → aggregate → quality; Refresh aggregates = aggregate (the instrument's window marked changed and rebuilt) → quality. A job about one instrument is not counted as the last run of a phase on the Data screen and runs no calendar upkeep.

The window. The last Data:Quality:Sessions (default 5, 1 to 60) trading sessions of the calendar that have closed (never today's open one), the same for every instrument. Instruments: tracked, not retired, with bars. For every instrument the 1-minute bars are read once, by the primary key, from the earlier of the Monday and the 1st of the month of the window's first session (the week and month buckets reach back that far) to now, and the stored aggregates from bars_agg by its primary key. About 560,000 rows for 214 instruments; measured 1.7 s for the whole run on generated data (TimescaleDB in a container).

Verdict. Status = the worst of completeness, sanity, spikes, aggregates and freshness (pass · warning · fail). Score 0–100 = completeness 30 × (share of expected minutes stored) + aggregates 25 + sanity 20 + freshness 15 + spikes 10, where a failed check earns nothing and a spike warning half (so a stale instrument scores 85, one with a tampered aggregate 75). An instrument whose checks crash is recorded as fail with score 0 (fail-closed; the reason is in the log). The run's score is the mean of its instruments.

Results. 11. Biases avoided#

Survivorship (bounded and disclosed, not avoided: no table of historical index membership is built, a basket is tested with today's members and says so, ISS-22 in the roadmap), look-ahead (closed bars only; higher-TF from last closed bar; point-in-time regime), selection (basket rules are dated; point-in-time membership available). The regime and the other market-context features are read as of the previous session (the latest day strictly before the date being traded, ADR 0033), so the close of the day being traded is never in them; the daily records written by the context data job must themselves be point-in-time (no restated closes, breadth from that day's closes only). The closed-bar rule is built into XDrishti.Indicators (P3-01, ADR 0031) and checked from two sides: the frame never shows the bar still forming (a test builds a forming bar worth 200 against a closed bar worth 100 and asserts 100), and a prefix property (the outputs for the first k bars do not change when more bars are fed) guards against hidden state and any dependence on later input. The prefix property alone cannot detect a forming-bar leak in a push-only API, which is why the frame-semantics tests exist.

The data is never repaired, and the replay says what it left out (P3-04, ADR 0037 Amendment 2; figures from the scan of the owner's 214 files on 2026-10-18). The simulator reads the stored bars as they are. A date on which the calendar has no session (a weekend, a holiday), a special session, and a regular session with fewer than 90 % of its 375 minutes are excluded, counted and noted per instrument, and treated like a closed market (so prev_day_* and the check below read the previous session that ran); a trading day of the calendar with no bar at all is counted as missing. The 427 complete Saturday and Sunday dates of the files are closed days unless the calendar (§4.1) has a confirmed special session for them; three dates hold 635 short sessions (2024-05-18, 2024-11-01, 2025-10-21). A day whose first open is more than 20 % from the previous close, on the adjusted series, is flagged (informational), gets no entry and restarts the indicators; a split or bonus that explains the jump makes the adjusted series continuous, so it is not flagged. The opening bar that the importer widened (§3) is stored data and is not touched. Every run records a SHA-256 of the stored bars it read, so a backfill that changes a price changes the run key. Survivorship is bounded and disclosed (above): a basket universe is labelled members as of today.
