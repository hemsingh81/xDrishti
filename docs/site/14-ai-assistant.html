14 — AI Assistant (local LLM)

1. Roles#

Job Who Why
Signals, stops, targets, sizes Deterministic .NET engine Exact, testable
P(win), expected R Gradient-boosted trees in ML.NET (trained & scored in .NET) Measurable accuracy
Exit choice, ranking, selection Deterministic rules on learned statistics Auditable
Daily briefing, weekly review LLM Language summarisation
Questions about your data LLM + read-only tools Numbers come from tools
Draft strategy rules for the Strategy Lab LLM (you confirm; tests decide) Faster research
Propose hypotheses (one variable) LLM (engine validates) Research help
Suggest instruments / basket changes / next-day focus LLM + engine evidence → suggestions inbox; you accept or reject Human in the loop
Extract data from filings/announcements (later) LLM (validated) Unstructured text
Predict prices / make trade decisions Never Unverifiable

2. Setup#

Component Choice
Model server xd-llm: llama.cpp server (image quay.io/ramalama/ramalama, pinned) on the libkrun Podman machine with GPU (Vulkan), OpenAI-compatible API; started on demand (ADR 0005)
Main model Qwen3-30B-A3B Q4_K_M (MoE, ≈ 18.6 GB; measured 41 tok/s at 8K context in the container); alternate gpt-oss-20b (12 GB) — final pick by the eval set (§5). Context 16K default, 32K supported; keep prompts ≤ 8K tokens
Small model none — the MoE main model is faster than a dense 8B; a dense 14B was rejected (first token 27 s)
Embeddings nomic-embed-text or bge-m3 (for search over notes/docs)
Fallback Host-native llama.cpp (Metal) — measured 1.1–1.4× faster generation and 1.4–1.8× faster prompt reading than the container, loads in 5–10 s; endpoint change only. The container meets the speed thresholds, so it stays the default

Model choice is config; select by our eval set, not leaderboards.

3. Integration (.NET)#

  • xd-api assistant endpoint uses Microsoft.Extensions.AI with tool calling; streams to React.
  • Tools are served by xd-mcp (ModelContextProtocol C# SDK 2.3.0, Streamable HTTP, stateless, a bearer token per client, ADR 0137) under two read-only DB roles (xd_mcp_sql for run_sql, xd_mcp_read for the typed tools), each able to SELECT only from the reviewed views of schema aiv (36 views; the portfolio ones are empty until the owner turns the portfolio context on, in the database itself). Built (P9-02): list_tables, describe_table, run_sql(sql, maxRows) over aiv (one SELECT, 200 rows, 5 s, labelled "ad-hoc query, not checked by the report engine"), lab_validate(yaml) (stores nothing). Built (P9-05, ADR 0139): get_report(report, query) (the report engine's own handlers, gross only, each figure a state), list_runs(kind), get_plan(date), get_cell(key | strategy, timeframe, side), get_portfolio(groupBy) (empty until the portfolio context is on), get_basket(name), get_instrument(symbol, bars), search_notes(query), get_learning(kind), get_system_status(), calc(expression) (exact decimals: the only source of a derived number) and, inside the API, make_chart(spec) (columns of earlier results of the turn, never numbers). Sixteen tools in all, under 2,200 tokens of schema. lab_run is dropped (P9-00 D9): a run is proposed, never started by the model.
  • The endpoint (P9-03, ADR 0138): POST /api/assistant/chat streams turn, status, tool_call, tool_result, token, iteration_discard, ping, done, error. The loop (up to the owner's budget of 1 to 12 tool calls, default 6; history of the last 6 messages with one line per old call, never old results; 10,000 characters of results per turn; 900 answer tokens; 180 s) is the application's, over a model port and the tool-server port. Off by default (no ai.settings row = 409 assistant.disabled, nothing called); turning it on or raising a setting is the owner's act with a fresh password in the body, switching off needs none. Grounding: every figure of the answer is looked up in the tool results of that turn (and the question and the tool arguments); unmatched figures are marked, not removed, and the message is ungrounded (a figure computed by the model itself is unmatched: derived numbers come from calc). Audit: ai.prompts, ai.conversations, ai.messages, ai.tool_calls and ai.model_calls are insert-only for the application role; each turn can be replayed from them. One turn at a time; no chat while the nightly run is running.
  • Guardrails: numbers only from tool results; no write tools (a draft is text the model writes for you to read; only your confirm, with the switch on and your password, stores a version or starts a quick test, ADR 0141); no promotion; no config changes (only proposed diffs you apply in the Config screen); prompts and tool calls logged in ai.*; broker secrets never in context. If the LLM is down, the nightly plan is unaffected.

4. Features#

  1. Daily briefing (≤ 300 words): regime, the tickets with one-line rationale, risks, system changes. Built in P9-06 (ADR 0140): the app builds the facts, the model only phrases, a deterministic guard rejects any number, symbol or claim not in the facts, and a fixed-format text is stored instead; the weekly review works the same way. Both services start paused and the model is used only when the assistant and Assistant:Briefing:UseModel are both on.
  2. Ask your data: "Expectancy of 15m SELL setups in high-vol regimes in 2025?" → query + numbers + chart. Also portfolio and baskets: "XIRR of MyLongTerm vs Nifty this year?", "Which basket worked best for 15m setups?"
  3. Strategy drafting: English idea → DSL YAML → validation → you confirm → Lab run → summary. Built in P9-07a (ADR 0141): the model writes text, the Lab validator and four checks decide whether it is offered, you confirm with a fresh password and the switch on, and a quick test starts on the universe you pick; the chat tool lab_propose_run only proposes a draft, and the optional auto quick test is off by default and your act with your password.
  4. Hypothesis and basket proposals for the learning loop (doc 09 §5). Built in P9-08 (ADR 0142): the engine selects a pack, the model proposes up to three items, the engine re-reads the evidence and checks every rule, only what passes lands in the Suggestions inbox, and your accept (switch allow_proposal_accept and a fresh password) writes a proposed hypothesis or changes a basket; the auto option accepts hypotheses only and is off by default. Next-day focus and insight references are not built.
  5. Event flags (later): classify announcements for the event-risk filter.

5. Eval set (re-run on every model/prompt change)#

Task Test Pass
Data questions 30 questions with known answers ≥ 90% exact numbers
Briefing 10 historical plans No numbers absent from input; all tickets covered (the guard of P9-06 is the checker; set B measures how many first attempts it accepts)
Strategy drafting 10 ideas Valid DSL; matches intent on review
Event flags 200 labelled announcements Precision on "material" ≥ 80%

Event flags set (P15-07, ADR 0188): the 200 announcements are drawn by xd eval announcements sample from the stored, dated announcements (240: 200 main and 40 reserve, half from the categories a pre-registered baseline file calls material), labelled by the owner (material, non_material or unsure; the definition is in eval/README.md) and imported with xd eval announcements import; the text stays in the git-ignored data/eval/, only a manifest of ids and hashes is committed. Until the labels exist set D is not_evaluable (waiting for labels). Precision on the sample is a stratified estimate (half the rows are from material-looking categories); the report prints the population-weighted figure beside it, with weights recomputed from the labelled rows per stratum.

The flag (P15-08, ADR 0189): xd filings extract gives each stored announcement one answer from the local model: material, a category from a closed list, a short reason and three optional fields. One request, no tool, temperature 0, seed 1337; the announcement sits between random-token fences under a prompt that declares it data; the answer is parsed against a closed schema (anything else is invalid_output, stored as a state and a closed reason, never guessed); an order value is kept only if the text contains it. Rows are insert-only in filings.extractions with the model and prompt hashes; that row is the per-call record, and no ai.model_calls row is written (backfill, set D, hostile set). Set D classifies the labelled rows through the same code and passes only with at least 200 rows, at least 30 predicted material, precision of material at least 0.80 and a better result than the category baseline by the exact sign test (p < 0.05); a pass whose interval reaches under 0.80 is labelled weak evidence. The thresholds min_predicted_material and baseline_sign_p made every earlier accepted run stale. The flag is a stored feature: nothing in selection, planning, checks, simulation, scoring or execution reads it, and llm-1 enters protocol X (P15-10) only after the newest accepted run has set D PASS.

The eval runs with xd eval (P9-09, ADR 0143): a synthetic fixture database, graders written as code (no model judge), the pass thresholds in eval/thresholds.json (data 27 of 30; plans raw 8 and repaired 9 of 10 with no escape; ideas first shot 8 and repaired 9 of 10; events precision 0.80 once 200 labelled rows exist), every rate with its Wilson interval, a paired sign test between two runs, and a baseline only the owner accepts. It is re-run on every model, runtime or prompt change; the accepted run goes stale at once when the fingerprint of the model, runtime, prompts, sets, thresholds or fixture changes.

6. Hermes Agent (Nous Research) — decision#

What it is: open-source (MIT) always-on agent: persistent memory, self-written skills, built-in cron, MCP client, messaging gateways (Telegram, WhatsApp…), works with local OpenAI-compatible models.

Decision: not part of the core. Build the built-in assistant first. Evaluate Hermes in Phase 9 as an optional front-end (phone access, scheduled summaries) connected only to xd-llm and xd-mcp.

Why cautious: a third-party review (Sept 2026) cites 44 published CVEs (UNVERIFIED: the figure was not reproduced; several 2026 CVE records exist, see P9-10 D9) including high-severity remote-code-execution and supply-chain issues, and an audit found unrestricted shell and credential-file access in default config; self-written skills/memory can persist errors or injected instructions; it needs ≥ 64K context (corrected from "32–64K": Hermes rejects smaller windows, P9-10 D6). The PoC bench is built (P9-10, ADR 0144); the verdict is the owner's.

If adopted, mandatory hardening: own image from a pinned release (no curl | bash); shell, browser, web-search, file-system and media tools disabled; only xd-mcp registered; no secrets mounted; egress only to xd-llm/xd-mcp; skills git-tracked and memory reviewed weekly; messaging off by default; monthly CVE check.

PoC pass criteria: hardened container works with the local model · ≥ 90% on the data-question eval · 8/10 strategy drafts valid · cron summary delivered 5 days running · prompt-injection probe (malicious journal note) causes no unintended tool calls · runs alongside the core stack without memory pressure · clear benefit over the built-in assistant.
