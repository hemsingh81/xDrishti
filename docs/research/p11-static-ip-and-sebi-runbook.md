# P11-05 runbook: static IP and SEBI re-check (decision record and questions)

- **Source:** [spec P11-05](../specs/P11-05-static-ip-and-sebi-recheck-runbook.md); copied here on 2026-10-28 with the "Who answers" column added to every question and check (spec amendment 1). Facts of section 2 were read on 2026-10-24.
- **How to use it:** you do the enquiries (the system cannot write to Dhan or phone an ISP and sends nothing for you). Write each answer in the last column with its date and source (a ticket number, a reply date; never an IP address, client id or token). Then write the three records in the app (Live, Compliance tab; the form needs `Live__Writes__Enabled=true` in the deployment). `xd live compliance show` prints them.
- **Status of the facts:** none of section 2 is a primary legal text; rows marked `UNVERIFIED` are unconfirmed.

### 1. Why now, and what is NOT needed in P11
Orders typed by the owner in Dhan's own app or website are not API orders, so no static IP and no algo registration are needed to run P11 (the P11 plan and doc 19 §5 agree; the framework text is UNVERIFIED, see 2). The enquiry starts at week 0 because the long items are outside the owner's control: an ISP lead time, Dhan's reply time, and a **7-day lock** after an IP is set at Dhan. Target: records `static_ip`, `dhan_ip_read_policy` and `sebi_recheck` written before the P11 exit check; P12 does not start without them.

### 5. Checks the owner can do without anyone's answer
| # | Check | Who answers | Why it matters | Result · date · source |
|---|---|---|---|---|
| C1 | **Evidence you already have for D1:** the Services screen shows the `portfolio-broker-history` and holdings syncs; if they succeed from the current dynamic home address while **no** IP is whitelisted at Dhan, then reads are not blocked by the whitelist today. Write the dates of the last successes in the record (a fact from the app, not a promise about the future). | You, from the Services screen | Tells whether today's read sync is at risk before Dhan answers D1 | |
| C2 | **Public address and CGNAT:** note the address a "what is my IP" service shows and compare it with the router's WAN address; if they differ, or the WAN address is in 100.64.0.0/10 or a private range, the line is behind CGNAT. Do not write the address in the record; write "matches" or "differs". | You, from the router and a public service | A shared address cannot be whitelisted for one person | |
| C3 | **After the ISP activates the static IP:** restart the router, check the public address again, and note only "unchanged after restart". | You | A static address must survive a restart | |
| C4 | **Egress path:** the Podman machine's outbound traffic leaves through the Mac and the router, so the whitelisted address is the router's WAN address; a VPN, a phone hotspot or a second line changes it. Keep VPNs off the Mac while trading. | You | The address Dhan sees must be the one whitelisted | |
| C5 | **Re-check the texts:** read the SEBI circular of 4 Feb 2025 and the 30 Sep 2025 extension on sebi.gov.in (Legal > Circulars), the NSE circulars named in section 2 on nseindia.com (Resources > Circulars), and Dhan's API changelog; note any change of the 10-orders-per-second threshold, the static-IP rule or the algo-id rule in the `sebi_recheck` summary with the circular id in `sources`. | You, on the primary sites | Section 2 rests on broker and blog summaries, not the circular texts | |

### 6. Options and the recommendation
| Option | Verdict |
|---|---|
| ISP static IPv4 on the home line (outbound only, no port forwarding) | **Recommended**: simplest, local-only, about Rs 350 a month in one reported case |
| VPS or cloud relay with a fixed IP forwarding orders | Rejected: puts a remote component with the order credential outside the Mac, against "local only"; adds a failure and attack surface |
| Dynamic address, re-whitelist daily | Rejected: the 7-day lock makes it impossible |
| Trade by hand forever | Valid fallback if the answers are unfavourable; P12 then stays at `assisted` |

### 7. Decision record format
The record in the app has the fields of the Contract. Write three records before the P11 exit: (a) `dhan_ip_read_policy` with outcome from D1 (or `unanswered` and the date asked), (b) `static_ip` with the state (`requested` / `active` / `whitelisted`), the ISP name, monthly cost, IP version, the date whitelisted and the derived lock end, (c) `sebi_recheck` with `rechecked_no_change` or `rechecked_changed`, a summary of what was read (circular ids and dates in `sources`), `nextReviewOn` about 90 days ahead. Never write an IP address, client id or token anywhere.

### 8. Re-check calendar
At the P11 exit; then every 90 days while P12 is planned or live; at once on any Dhan or exchange notice. The notice in the bell is the reminder.
